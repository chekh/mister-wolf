# Протокол обработки жалоб (complaint protocol)

**Версия:** жалобный контур v2 (спека 2026-09-01 §4.2) — `wolf complain` + Стюард
**Статус:** продукт-минимум, без LLM в самой команде

---

## 1. Что такое жалоба

Жалоба — hot-signal от владельца или агента на правило, playbook или агента.
Это структурированный объект типа `complaint` (status `open`) с четырьмя
обязательными полями — `about` / `rule` / `evidence` / `proposal`: что не так,
какое правило плохо, доказательство и предложение. Урок с `trigger_keywords` —
продукт расследования; жалоба — вход в него.

## 2. Подать жалобу

```bash
wolf complain \
  --about skill:apprentice \
  --rule "Правило требует npx vitest run перед отчётом" \
  --evidence "Воркер сдал задачу без прогона тестов: e2e red, лог-цитата" \
  --proposal "STOP-гейт в playbook перед шагом отчёта"
```

- `--about` — цель жалобы: id базового агента (`worker-implementer`, `mr-wolf`,
  `steward`, …), `skill:<имя>` или существующий mem-id; неизвестная цель —
  честная ошибка CLI;
- `--rule` — какое правило плохо (указатель + что оно требует);
- `--evidence` — доказательство: дословная цитата + что произошло
  (файл/тест/числа); `--text` — deprecated-алиас;
- `--proposal` — предлагаемое изменение правила;
- `--created-by` — автор (дефолт: env `WOLF_ACTOR`, иначе `user:cli`).

Команда создаёт объект `complaint` (status `open`, тег `complaint`), relation
`complain` к адресату и событие `complaint` в сигнальном логе (hot-signal,
[signal-log.md](./signal-log.md)).

## 3. Конвейер обработки

```text
жалоба (wolf complain → объект complaint, status open)
  → обнаружение: координатор/диспетчер видит открытую жалобу
    (wolf search "status:open type:complaint" / wolf call в начале сессии)
  → триаж диспетчера (executor-lead); воркер Стюарда сам не вызывает
  → Стюард расследует: читает правило-адресат, evidence, контекст
  → Стюард создаёт новую версию правила/playbook (полное содержимое, не дифф):
      wolf add --type playbook --title "<skill> playbook vN+1: …" \
        --set owner_skill=skill:apprentice --set version=vN+1 \
        --set steps="[шаг 1,шаг 2,шаг 3]"
  → сапсейд старой версии: wolf supersede <old-playbook-id> <new-playbook-id>
  → вердикт записывается в жалобу (итог — в body жалобы,
    либо отдельным объектом с relation)
  → жалоба закрывается: wolf transition <complaint-id> resolved
```

Жалобная воронка (подача → вердикт → закрытие, рецидивы по адресатам) видна в
`wolf analytics --view steward` ([analytics.md](./analytics.md)).

## 4. Обязанности сторон

- **Владелец/воркер** — подаёт жалобу с конкретикой: правило, дословное
  evidence, предложение. Не мутирует playbook сам.
- **Координатор/диспетчер** — видит открытые жалобы, передаёт их Стюарду;
  не разбирает сам.
- **Стюард** — единственный, кто мутирует контекст агента: новая версия
  playbook → supersede → вердикт → закрытие жалобы. Без жалобы/фидбека не
  меняет ничего.

## 5. Инварианты

1. Воркер сам себя не мутирует — мутация только через Стюарда.
2. Playbook версифицируется: замена только через `supersede`, полное
   содержимое новой версии + причина в конце.
3. Жалоба без вердикта не закрывается; вердикт доступен пост-аудиту.
