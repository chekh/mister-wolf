# Dogfooding Hardening — дизайн-спека волн 0–3

Статус: reviewed (4 линзы: точность/приёмка/минимализм/апгрейд — 2026-09-27, отчёты в `.wolf/orchestration/report-2026-09-27-spec-review-*.md`; апгрейд-линза добрана координатором после зависания спавна). Дата: 2026-09-27.
Основание: dogfooding-анализ (`docs/research/dogfooding-analysis-2026-09.md`) + ревью плана и спеки.

## 1. Контекст и цель

Анализ 5 внешних инсталляций: ядро (call-доставка, onboarding-рендер, lesson-культура) подтверждено; при этом путь записи `add` падает в 23–42% вызовов, router не доставляет playbook агенту executor-lead в 100% спавнов, `brief` деградирует до 22–68 с (главная тяга — полный скан проекта на каждом вызове), поверхность MCP раздута дублями, телеметрия не позволяет принять ни один фикс.

Цель волн 0–3: **измеримость → ядро → гигиена → диета**, не сломав ни одну из 5 инсталляций при обновлении.

## 2. Принципы

P1. **Апгрейд-безопасность через инварианты, а не процесс** (см. §5): у одного пользователя и 5 локальных инсталляций нет контура для dry-run-церемоний.
P2. **Измеримость до ремонта.** Ничего не улучшается, пока метрика текущего состояния не собрана (волна 0 + soak перед волной 1).
P3. **Ленивые решения.** Data-fix вместо подсистем; where-условие вместо слоёв; deprecated-флаг вместо удаления там, где миграция дороже пользы.
P4. **Rollout через штатный контур**: `wolf sync` (штампованные файлы) и обновление npm-пакета — единственные каналы. Ручные правки — только для собственных данных (теги, trigger_keywords).

## 3. Текущее состояние (базлайн, верифицирован ревью)

Версия 2.9.0; глобальный npm-пакет; MCP — через локальный `dist/`. Инсталляции: 5 внешних + dogfood; `projects.yaml` schema_version: 2; frontmatter schema_version: 1.

Ключевая механика (файл:строки проверены линзами):

- **upgrade = npm-самообновление** (`src/app/use-cases/upgrade.ts:3` — «самообновление глобальной npm-установки»). Проектного мигратора НЕ существует.
- **sync не трогает `.wolf/`** (`sync-base-set.ts:6` — «память (.wolf/, seeded playbook'и) НЕ трогается никогда»); действует только на штампованные файлы вне `.wolf` (AGENTS.md, `.opencode/agents|skills|commands|plugins`).
- **sync молча перезаписывает штампованные файлы** при отличии контента (`opencode-renderer.ts:127-133`, ветка `updated`); `conflict` — только для unstamped. Ветки «локально-мутированный штампованный» не существует.
- router: гвард 1:1 (`templates/opencode/plugins/wolf-router.ts:70`); в дефолтных playbook нет executor-lead (by design — `templates/base/agents/executor-lead.md:23-25` отказ от инъекций).
- call-инъекции: `get-call-injections.ts` — пул все active `call-injection`, порога важности нет; fallback `.slice(0,3)` только при `--for` с пустым матчем; `ftsScore=1` захардкожен.
- `target` не обрезается (`memory-call.ts:56`) — промпты утекают в metrics.
- `brief`: `store.list()` (`generate-agent-brief.ts:21`) + **scanProject на каждом вызове** (`mcp-tools.ts:369-371`) — двойной полный обход.
- session_id: `resolveSessionId()` = `env.WOLF_SESSION` (`src/domain/actor.ts:15`), env **никем не выставляется** → null в 100% телеметрии.
- `memoryClass` в MCP list принимается и молча игнорируется (`mcp-schemas.ts:14-16` vs `list-memory-objects.ts:4-8`); enum кода — `working|canonical`.
- Мёртвое: `prune()` (0 call-sites), `artifact_sources` (0 ридеров), run-log (читатель без писателя), типы `escalation|decision-request|document-native` (0 экземпляров везде).

## 4. Волны

Каждый пункт: Требование / Приёмка / Апгрейд.

### Волна 0 — Инструментация и soak (блокер волны 1)

**0.1 Поля телеметрии.** Новые ключи класть в существующий объект `detail` (top-level ключи вырезаются zod-strip при чтении — `SignalEventSchema`):

- `mcp_call.detail`: `error.message`, `error.code`, `error_class_id` (переиспользовать существующий classifyError), `args_summary` для add (type, title≤80, ключи extra, без body), `memory_id` для get, CLI-имя команды для `actor=user:cli`;
- `delivery.detail`: `injection_bytes` (байты; токен-аппроксимация — не-цель);
- `router.log` при hit: имя playbook (различать canonical/fallback);
- обрезка `target` до 200 символов (`memory-call.ts:56`).

Приёмка: на dogfood поля заполняются (fault-injection для error-полей — принудительная ошибка add с кривым полем); старые jsonl-строки читаются без ошибок; сверка механики с `2026-09-04-p1-telemetry-identity-design.md` — без дублирования идентичности.
Апгрейд: аддитивно в append-поток; старые файлы не мигрируются (отсутствие поля = норма).
Поле `model` — **не делаем** (продюсера нет, решений не обслуживает).

**0.2 Session-ключ, CLI-канал.** `WOLF_SESSION` никто не выставляет → продюсер: CLI-обёртка/рамки (штампованные шаблоны через sync). Скоуп — **только CLI-канал**: MCP-сервер long-lived, один env на все запросы = фальшивая сессия и риск задушить конституцию дедупликацией (1.3 от этого защищён). Приёмка: не «≠null», а **дискриминативность** — уникальных session_id ≈ числу сессий за окно.
Апгрейд: продюсер приезжает со sync-шаблонами; без него пункт — no-op, волна 1.3 не стартует (data-gate).

**0.3 Soak.** После релиза 0.1/0.2 — окно набора: ≥7 дней ИЛИ ≥30 burst'ов ИЛИ ≥30 add на активный проект. До окончания soak волна 1 не принимается.

### Волна 1 — Ядро

**1.1 Router: fallback-playbook + executor-lead.**

- в `wolf-router.ts`: fallback-playbook для любого agent-id при miss (канон остаётся приоритетом; в router.log fallback-hit помечен именем);
- playbook executor-lead в дефолтный набор; из `executor-lead.md` убирается отказ от инъекций.
- Warning на неизвестный agent-id — не делаем (miss-лог уже пишется).

Приёмка: miss-rate executor-lead 100% → <5% (miss = нет ни канона, ни fallback); hit-rate worker-\*/mr-wolf ±1 пп; n≥100 строк router.log/проект.
Апгрейд: fallback в коде — доставляется бинарём (работает без sync); playbook-файл и правка executor-lead.md — штампованные файлы через sync. **Требование к sync: ветка mutated-skip** — штампованный файл с контентом, отличным и от старого, и от нового канона (локальная мутация), не перезаписывается: skip + warning (сегодня — молчаливый `updated`, `opencode-renderer.ts:127-133`). Это единственное новое sync-требование волн.

**1.2 Надёжность core-loop.**

- 1.2.a `add` error-rate 23–42% → <5%. Диагностика по 0.1; кандидаты от ревью: `.strict()` snake/camel-несоответствие (add ждёт `expected_answer`, create_info_request — `expectedAnswer`), plain Error без хинта типа (`memory-types.ts:353-355`). Timebox диагностики — 1 день; если корень в схеме данных и требует миграции frontmatter — выносится из волн в отдельную спеку (апгрейд-контур §5). Приёмка: error-rate <5% пер-проектно, n≥30, контроль знаменателя — суточные add не падают (передиета), резка по error_class_id.
- 1.2.b `brief` — двухэтапно: (этап 1) не звать scanProject на каждом вызове (инкрементальный скан/кэш скана с инвалидацией по mtime — см. `2026-07-02-incremental-indexing`); не `store.list()` целиком (`generate-agent-brief.ts:21`). Замер p50/p90 (p95 на n≈19 шумный). Если после этапа 1 p90 всё ещё >1 с — этап 2 (кэш контента brief) отдельным решением по данным. Приёмка: p90 < 1 с, n≥20, непустота брифа — контентная проверка e2e.
- 1.2.c `search` c `include_body` (дефолт false) + обязательный дефолтный limit при include_body (иначе отдаются все ряды — `sqlite-search-index.ts:157-160`) и обрезка body. Body уже лежит в FTS5 — второй заход в store не нужен. Кандидат на дефер при нехватке ёмкости. Приёмка: доля search, за которыми в окне Δt следует get той же памяти (джойн по `detail.memory_id`), ↓ >3×; знаменатель search не падает.

Апгрейд 1.2: правки рантайма — бинарём; новых схем нет; include_body — опциональный параметр (старые клиенты не затронуты).

**1.3 Delivery: только trigger_keywords.** Точные ключи у топ-2 «конституционных» памятей trading-signal — ручная правка объектов (P4: свои данные). Сессионная дедупликация — **за data-gate**: конвейер спавнит свежие контексты, каждому нужна конституция (§5.5 анализа: «работает как спроектировано»); пока 0.2 не дал дискриминативных session_key и burst-статистики, дедупликация концептуально не определена. Приёмка (после soak, если вернём): repeat-streak ≤2 в 95% burst'ов; конституция ≥1 доставки на спавн-контекст (guardrail).

### Волна 2 — Гигиена

**2.1 Теги EN-only.** Политика — текст в onboarding-шаблоне (решение `mem_20260927_..._9ffed6`); слияние ru/en-дублей — ручной проход владельца (пар ≈ две; интерактивный CLI — не-цель). Приёмка: доля ru/en дубль-пар = 0; новые ru-теги <5% от новых тегов. Апгрейд: только текст шаблона через sync.

**2.2 Фильтр memory_class в `list`.** Починить существующий no-op (`mcp-schemas.ts` принимает, `list-memory-objects.ts` игнорирует); маппинг терминов: `curated ≡ canonical` (enum кода — `working|canonical`, «machine» в коде не существует — не вводить новый enum); дефолт — canonical-only, `--all` для полноты. **Search и delivery не меняются.** Апгрейд: where-условие на существующем поле, миграций нет.

**2.3 Init/doctor-гигиена.** Секрет-детект (предупреждение при секретоподобных файлах в `.wolf/`) + предложение `.gitignore .wolf/` — вопросом, не действием; ghost-детект в doctor (маркер `wolf:onboarding` есть, `.wolf/memory/` нет → warning). ExistsSync-фильтр и авто-регистрация реестра — **не делаем**: список проектов показывает только doctor, мёртвые пути он уже чистит; новый write-path в runtime — риск гонок. Апгрейд: аддитивное поведение при новых вызовах.

## 5. Апгрейд-контур

### 5.1 Релизы

Один минорный релиз на волну, CHANGELOG обязателен (`mem_20260831_..._004788`). Порядок 0→1→2→3; внутри волны допускается дробление. **Каждый релиз сопровождается актуализацией документации и сайта** (§5.5, правило `mem_20260928_..._fb4166`): релиз без обновления docs/сайта не считается завершённым.

### 5.5 Doc-Release sync (правило владельца)

Каждый выпуск версии/подверсии с функциональными изменениями обновляет в том же релизе:

1. **CHANGELOG** — уже обязательный минимум (`mem_20260831_..._004788`);
2. **docs/ + README** (языковая политика `mem_20260831_..._5422a2`: EN-витрина/RU-внутрянка, билингвальная пара README): новые/удалённые/изменённые CLI-команды, MCP-инструменты, поля телеметрии, типы объектов, флаги;
3. **Сайт** `https://chekh.github.io/mister-wolf/` (VitePress `docs/site`, автодеплой `deploy-docs.yml`): разделы поверхности инструментов и руководств — в актуальном состоянии; для волн, меняющих пользовательскую поверхность (0.1 поля, 1.2.c include_body, 2.2 фильтр, 3.1/3.2 диета), — обновление соответствующих страниц до влития релиза.

Механика: доки-обновление входит в DoD каждой задачи волны (см. план), а не отдельной задачей «потом». Приёмка: staging-smoke §5.3 дополняется проверкой «доки соответствуют фактической поверхности: `wolf --help`, MCP-каталог, docs/site — консистентны». Спецификация изменений (спеки/plans) не входит в витринные доки — только пользовательская поверхность.

### 5.2 Инварианты вместо процесса

Проектного мигратора в wolf upgrade **не строим** (не-цель; upgrade остаётся npm-самообновлением). Безопасность обновлений — четырьмя инвариантами:

- (i) **Аддитивность**: все изменения данных/событий — новые поля в `detail`, новые файлы; ничего существующего не переформатируется;
- (ii) **mutated-skip в sync**: штампованный файл, отличающийся от обоих канонов (старого и нового), не перезаписывается — skip + warning (реализация в 1.1; защищает и локальные правки агентов вроде executor-lead.md);
- (iii) **zod-strip** для выпавших полей конфига (паттерн `artifact_sources`);
- (iv) **Идемпотентность по построению**: все операции — merge/skip-семантика; повторный запуск не меняет результат (проверяется staging-smoke, не отдельным тестовым каркасом).

### 5.3 Staging-smoke (перед каждым релизом)

На копии живого проекта (не на живом): после обновления пакета + sync — `wolf call` отдаёт непустой набор; `brief` работает; старая телеметрия читается (прирост malformedLines = 0); повторный sync — no-op; повторный вызов upgrade — no-op; `npm run check` + e2e в CI; **доки и сайт соответствуют фактической поверхности** (§5.5: `wolf --help`, MCP-каталог, docs/site консистентны).

### 5.4 Телеметрия обновления (окно 24–48ч после релиза)

1. есть mcp_call с новой `wolf_version`; 2. суточные delivery ≥50% медианы 7 дней до (на активный проект — детектор тихой смерти call); 3. mcp_call error-rate ≤ pre+2 пп; 4. после ручного tags/trigger-фикса — топ-конституция продолжает доставляться 48ч.

## 8. Протокол приёмки волны 1 (на 5 инсталляциях)

Дизайн: one-group pre-post со ступенчатым запуском (dogfood+Tender — канарейки; trading-signal +7 дней; переходное окно даёт одновременные pre/post двух групп). Единицы: строка router.log; burst (гэп >60 c в пределах session_key); событие mcp_call. Фильтрация: `detail.wolf_version` + ts против дат релиза. Окна: pre 14 дней; post 72ч (алерт) + 14 дней (приёмка). Min-n/проект: add≥30, brief≥20, router≥100, burst≥30; недобор — продлевать окно, не ослаблять порог. Контрольные метрики: суточные delivery (±50%), суточные add, hit-rate worker-\* (±1 пп), error-rate search/get/list, malformedLines. Подсчёт — одной командой (расширение `wolf analytics`; критерий волны 0: метрики приёмки волн 1–3 считаются машинно). Дашборд 7 метрик — вне спеки, отдельный пункт дорожной карты после наполнения полей.
