## 1. Проблема

После релизов 2.0.0/2.0.1 в реестре остались шесть открытых находок догфудинга
(см. Sources). Ни одна не блокирует, но вместе они — тот самый слой
«шероховатостей первого контакта», который отличает 2.x от продукта:

1. **F9 (остаток)** — document-ref'ы, создаваемые `scan`/`bootstrap`, получают
   id вида `doc_docs_superpowers_specs_…` (склейка пути, `scan-project.ts:92`).
   Это вне канона `mem_ГГГГММДД_slug_hash`: у объекта нет ни даты, ни хеша, а
   путь превращён в псевдо-токены. Вариант D (2.0.0) убрал основную FTS-боль,
   но канон по-прежнему нарушен, и аналитика по id не работает.
2. **F10** — зоопарк типов: в таксономии `document` помечен `deprecated: true`,
   реальный тип — `document-ref` (есть ещё `document-native`). Пользователь,
   набравший `wolf list --type document`, получает **молча пустой вывод** —
   ни ошибки, ни подсказки валидных типов.
3. **F5** — лог init печатает 13 безликих строк `SKILL.md created`: какие
   скиллы и куда — не видно.
4. **F6** — вводящие в заблуждение сообщения init: `platform configs: skipped`
   читается как «агенты не установлены» (а пропущен только мердж конфига),
   `Restart your agent platform…` печатается даже когда конфиг не писался.
5. **F16** — каждый `npm run check` оставляет ~5 мёртвых записей в глобальном
   `~/.config/wolf/projects.yaml`: часть тестов делает init во временных
   каталогах без изоляции окружения (тот же класс, что F14, но в vitest).
6. **Recreate-guard** — F13-guard (`safeCwd`) стоит на главном входе CLI, но
   путь `init --recreate` резолвит cwd иначе и в удалённом каталоге падает
   старым сырым стеком.

## 2. Решения

### 2.1. Канон id для document-ref (F9)

**Формат:** `mem_<YYYYMMDD>_doc_<slug>_<hash8>`, где

- `<slug>` — basename документа без расширения, приведённый к slug-канону
  (пример: `mem_20260902_doc_architecture_9f31c2ab`);
- `<hash8>` — первые 8 hex `sha256(canonical path)`; коллизия slug+hash в
  пределах памяти → суффикс `-2`, `-3` (правило tie-break задокументировать в
  докстринге генератора).

Путь в id исчезает → исчезает и остаточный FTS-шум от id-токенов. Генератор
(`scan-project.ts`) меняется в одном месте; заголовок объекта берётся из
первого заголовка документа (уже так) — поиск должен бить по содержимому.

**Совместимость:** старые `doc_*`-объекты продолжают читаться (2.x не смотрит
на формат id при парсинге) — миграция отдельная, см. §2.6.

### 2.2. Таксономия типов (F10)

- `wolf list --type document`: тип `document` — **deprecated alias** на
  `document-ref`. Поведение: резолвится в `document-ref`, на stderr — warning
  `тип 'document' устарел, используйте 'document-ref'` (exit 0 — чужие
  скрипты не ломаем).
- Полностью неизвестный тип (`--type documnt`): exit 1, stderr —
  `неизвестный тип 'documnt'; ближайший: 'document-ref'; допустимые: rule, …`
  (подсказка по edit-distance ≤ 2).
- Список допустимых типов для подсказки — из `memory-types.ts` (единый
  источник), не хардкод.

### 2.3. Лог init: имена и честность (F5, F6)

- Скиллы: вместо N строк `SKILL.md created` — построчно
  `[skill] <имя> → <путь>` (пример: `[skill] wolf-lesson → .opencode/skills/wolf-lesson/SKILL.md`).
- Мердж платформенного конфига: при записи —
  `opencode.json: written (mcp.wolf, default_agent=mr-wolf, subagent_depth=2)`
  (перечень фактических ключей); при реальном skip —
  `opencode.json: skipped (<причина>)` — причина обязательна.
- `Restart your agent platform…` — печатать **только** если конфиг был записан
  или изменён (флаг `written` из результата writeConfig).

### 2.4. Изоляция vitest (F16)

- `tests/setup.ts`: до импортов тестов выставлять
  `XDG_CONFIG_HOME` (и при наличии — собственную переменную конфига, если
  такая поддерживается) в пер-рановый `mkdtemp`-каталог; также изолировать
  `HOME` не нужно — wolf читает конфиг через XDG-путь.
- `vitest.config.ts`: `test.setupFiles: ['./tests/setup.ts']`.
- Проверка-инвариант (unit): после тестового init во временном каталоге
  глобальный реестр не существует/не изменился.

### 2.5. Guard на всех входах (recreate-corner)

- Аудит: grep всех `process.cwd()` в `src/adapters/cli/**` — каждый вход
  идёт через `safeCwd()` (или единый bootstrap-путь runCli). Отдельных точек
  резолва cwd быть не должно.
- E2E: `init --recreate` в удалённом каталоге → однострочник + exit 1 (тот же
  контракт, что F13).

### 2.6. Миграция id (однократная, явная)

- Новый подкоманд фреймворка: `wolf migrate doc-ids` (dry-run по умолчанию,
  `--apply` — как у существующего `wolf migrate`).
- Алгоритм: (1) найти объекты с id, не соответствующими канону §2.1;
  (2) вычислить новый id; (3) переименовать файл, обновить frontmatter;
  (4) **переписать все ссылки на старый id во всех объектах памяти**
  (relations, supersede-цепочки, thread-указатели, complaint/triage-поля);
  (5) `rebuild-index`; (6) отчёт: сколько переименовано, сколько ссылок
  переписано, список коллизий.
- Scan при наличии `doc_*`-объектов печатает напоминание
  `обнаружены объекты вне канона id: запустите wolf migrate doc-ids` (не
  мигрирует сам — миграция только явная, см. Q2).
- Новые document-ref'ы (после миграции или в новых проектах) создаются сразу
  в каноническом формате.

## 3. Критерии приёмки (проверяемы по отчёту)

| #   | Критерий                                                                                                                                                                                         |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| AC1 | `wolf scan` в проекте с документами создаёт id по канону `mem_ГГГГММДД_doc_<slug>_<hash8>` (unit-тест на формат + e2e на свежем скане)                                                           |
| AC2 | `wolf list --type document` → результат document-ref'ов + warning на stderr, exit 0; `wolf list --type documnt` → exit 1 + подсказка допустимых                                                  |
| AC3 | Лог init: строки скиллов с именами и путями; ключи конфига перечислены при записи; рестарт-подсказка только при записи (unit на формирование строк)                                              |
| AC4 | После полного `npm run check` sha256 `~/.config/wolf/projects.yaml` идентичен до/после; `wolf doctor` не находит новых записей                                                                   |
| AC5 | `init --recreate` в удалённом каталоге → однострочник + exit 1 (e2e)                                                                                                                             |
| AC6 | `wolf migrate doc-ids` на копии памяти площадки: dry-run показывает план, `--apply` переименовывает и переписывает ссылки; после — `wolf list`, `wolf search`, `wolf brief` работают; коллизий 0 |
| AC7 | `npm run check` зелёный; CHANGELOG 2.1.0: Changed (формат id document-ref + миграция), Fixed (F5/F6/F16/guard)                                                                                   |

## 4. Риски

- **Перепись ссылок при миграции** — единственное по-настоящему опасное место:
  неполная замена оставит битые relations. Погашение: dry-run по умолчанию,
  отчёт с числами, e2e на копии реальной памяти площадки (AC6), поиск битых
  ссылок после миграции (grep старых id по памяти — 0 вхождений).
- **Alias `document`** может скрыть от пользователя опечатку — погашено
  warning'ом на stderr (не молчаливый).
- Формат id меняется у живого продукта — CHANGELOG-запись обязательна
  (Breaking-маркировка не нужна: парсинг id не завязан на формат, миграция
  добровольная, но рекомендованная).

## 5. План валидации

1. Unit: генератор id (формат, коллизии), резолв типов (alias/неизвестный),
   формирование строк лога init, изоляция XDG в setup.
2. E2E: свежий scan → канон; `init --recreate` в удалённом cwd; миграция на
   копии памяти площадки (сравнение до/после: число объектов неизменно,
   ссылки переписаны, поиск работает).
3. Ручная приёмка координатором на pristine-площадке (по мотивам сценария 1
   из MANUAL-NOTES).
