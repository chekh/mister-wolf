## 1. Контекст и цель

Замеры на живом dogfood-репо (main 2.11.0, отчёт оптимизатора 2026-09-28, `/usr/bin/time`, 2–3 прогона): warm `wolf call` 4.7–6.0 с (главный объяснитель — O(n)-пересчёт всего сигнального лога на каждую доставку, 995 мс за проход при 38.7k строк, линейная деградация с ростом лога), router-плагин 5–7 с молчания на каждый chat-turn (TTL кэша 2.5 с не попадает в каденцию сообщений), `--version` 1.04–1.30 с при node-baseline 0.08 с (eager import-граф 47 командных модулей, 1.12–1.18 с до любой логики), `wolf brief` 8.02 с с write-churn на ~121 файл (~121 atomic write + ~121 строка events.jsonl + ~242 SQLite-stmt на каждый вызов).

При этом доставка (главная ценность Wolf) неизмерима: в recap нет строки доставки, в analytics нет панели, скиллы не телеметрируются вовсе («использование принципиально неизмеримо» — консилиум, M18-гейт), повторы инъекций внутри сессии не отслеживаются.

Цель 2.12: **доставка становится быстрой и измеримой**, апгрейд 6 инсталляций — без поломок (инварианты §5). Метрики успеха (продуктовый диалог): тёплый вызов контекста < 2 с; задержка роутера < 500 мс; `--version` < 300 мс; промахи доставки видны одной командой.

## 2. Принципы

P1. **Апгрейд-безопасность через инварианты, а не процесс** (§5) — у пользователей нет контура dry-run.
P2. **Замер до ремонта, замер после** — каждое изменение имеет базлайн «до» (§3) и проверяемый порог «после» (§4, §8).
P3. **Ленивые решения** — счётчик-сайдкар вместо БД; TTL вместо инвалидации; ранний стоп вместо батча; отдельный jsonl вместо расширения enum-схемы.
P4. **Доставка через штатный контур**: рантайм — бинарём npm-пакета; плагин wolf-router и тексты рамок — штампованные файлы через `wolf sync` (mutated-skip §5).
P5. **Мягкость лимитов** — предупреждение, не блокировка; дедупликация не пересекает границу сессии (конституция каждому новому контексту — guardrail dogfooding 1.3).

## 4. Состав волны

Каждый пункт: Требование / Дизайн / Приёмка / Апгрейд. Состав согласован с владельцем (продуктовый диалог, Т3 + сводная таблица 2.12); отклонения от буквы брифа — §10.

### 4.A Производительность ядра

**A1 (OPT-1, P0) Инкрементальные счётчики delivery вместо O(n)-пересчёта лога.**

- Требование: `appendSignal` не читает сигнальный лог на каждой keyed-записи. Пожизненный кап на деградацию записи телеметрии.
- Дизайн: сайдкар `.wolf/metrics/signal-counts.json` — `{ [signalKey]: count }`. Путь записи: под существующим `FsMemoryLock` (замер оптимизатора: ~1 мс, 4 syscall — вне подозреваемых) — прочитать сайдкар (отсутствует/бит → один полный rebuild-scan лога, там же), инкремент ключа, append строки в jsonl, атомарная перезапись сайдкара (tmp+rename). `readPatterns` — один раз на процесс, мемо. Возвращаемый контракт `appendSignal` (`{key, count, patternFixed}`) не меняется.
- Приёмка: warm `wolf call` p90 < 2 с (§8); время записи доставки не зависит от длины лога — замер при текущих 38.7k строк и на синтетическом логе +10k строк (разница в пределах шума); паттерны Ф21 продолжают фиксироваться (кластер пересекает порог после снижения `learning.pattern_threshold` — regress-тест).
- Апгрейд: сайдкар — новый файл в `.wolf/metrics/` (gitignored), derived/rebuildable; отсутствующий файл = штатный холодный старт с одним scan.

**A2 (OPT-2, P0) Router: TTL кэша минуты + один get при miss.**

- Требование: задержка роутера на chat-turn < 500 мс p90; спавны CLI — только при редком miss кэша.
- Дизайн: (а) `CACHE_TTL_MS` 2500 → 300 000 (5 минут; playbook — canonical-память, мутируется Стюардом редко; отрицательный результат кэшируется тем же TTL — уже так, `value: null`); (б) цикл get (`:92-102`) — ранний стоп на первом кандидате, прошедшем гвард владельца, в порядке релевантности поиска; `--hide-superseded` в запросе уже отсекает старые версии, выбор max-version избыточен (осознанное упрощение: при нескольких одновременно активных версиях побеждает релевантность — §7); (в) строка router.log дополняется `ms=<resolve>` и `bytes=<playbook bytes>` — k=v-парсер толерантен к новым ключам (B-10), для чтения поля добавляются в `RouterLogRow` (nullable).
- Приёмка: p90 `ms` по строкам router.log < 500 мс на окне ≥100 строк/проект; доля variant=canonical не падает > 5 пп против pre-окна (ранний стоп не теряет канон); негативный кэш живёт (отсутствие playbook не порождает спавны на каждый ход — счётчик спавнов в тесте шаблона).
- Апгрейд: плагин — штампованный файл через sync, mutated-skip (§5.ii).

**A3 (OPT-3, P0) Lazy import команд.**

- Требование: `--version` < 300 мс; boot без выполнения команды < 300 мс; налог eager-импортов снят со всех CLI-вызовов.
- Дизайн: регистрация команд по статическим метаданным (name/description/аргументы), тело — `await import()` внутри action. `ensureCurrentSchema` — после разбора argv и выбора команды, до выполнения action (например, commander `preAction`-хук); `--version`/`--help`/неизвестная команда гард не платят. Путь восстановления `init --recreate` (обход гарда, `cli-entry.ts:125-133`) сохраняется дословно.
- Приёмка: `--version` < 300 мс (10 прогонов `/usr/bin/time`); e2e-каталог команд зелёный (каждая команда загружается и выполняется); схема-гард по-прежнему выполняется до side-effect'ов команд (тест: команда против битого `.wolf/config.yaml` даёт прежний хинт).
- Апгрейд: внутренняя механика, бинарём.

**A4 (OPT-4, P1) Один store.list() в get-call-injections.**

- Требование: ровно один полный обход дерева на `wolf call` вместо 5.
- Дизайн: один `list()` без фильтров в начале + фильтрация по типу/статусу в памяти (прецедент легитимизирован комментарием T013 в `generate-agent-brief.ts:21-24`); минимум — захоистить идентичный rules-запрос `:63`/`:79`.
- Приёмка: instrumentation-тест — счётчик вызовов `store.list` на path `call --for X --thread Y` равен 1; регрессий ранжирования нет (снимок вывода на фиксированном наборе).
- Апгрейд: внутренняя механика.

**A5 (OPT-7, P1) brief: персистный scan-snapshot + diff-before-save.**

- Требование: повторный brief на неизменном дереве не пишет ничего и не обходит дерево целиком.
- Дизайн: snapshot `.wolf/cache/scan-snapshot.json` — `{sig, snapshot}` (сигнатура — `projectTreeSignature`, B-6). Hit по сигнатуре → полный скан пропущен. Diff-before-save для scan-объекта и doc-refs: не писать (и не писать событие в events.jsonl, не индексировать), если title/path/created_at не изменились; `updated_at` не тикает при отсутствии изменений (перестаёт инвалиддировать MCP parse-кэш по 203 файлам shared/). `renderScanBody` выполняется только при изменении snapshot. Один файл кэша, перезапись; `.wolf/` уже gitignored.
- Приёмка: повторный brief на неизменном дереве: прирост events.jsonl = 0 строк, atomic write = 0 (замер по mtime .md), CLI brief p90 < 5 с; при изменении дерева (touch каталога) — полный скан отрабатывает, doc-refs корректны (существующие id сохраняются — §2.1 F9).
- Апгрейд: кэш derived; старый wolf игнорирует `.wolf/cache/` (каталог новый, читателей нет).

**A6 (OPT-5, P1, попутно) Конфиг по mtime при error-ветке.**

- Требование: убрать sync-yaml-parse с горячего пути телеметрии.
- Дизайн: мемоизация `loadWolfConfigSync` по mtime+size файла (паттерн процессной мемоизации — `src/adapters/version.ts:5-16`; для конфига — по mtime, конфиг живёт дольше процесса); в `appendMcpCallSignal` (`:399-404`) конфиг читается только при `input.error`.
- Приёмка: тест — ок-вызов не читает config.yaml (счётчик open); error-вызов классифицирует по проектной таксономии как раньше.
- Апгрейд: поведение идентично при отсутствии изменений.

**A7 (OPT-6, P2, попутно) LIMIT в SQL.**

- Требование: search не маппит в JS строки за пределами limit (предусловие будущего include_body — T014).
- Дизайн: `LIMIT ?` в SQL, когда задан `options.limit` и нет file_path-фильтра; file_path-фильтр — до маппинга (SQL WHERE по `source` через json_extract или эквивалент). 3× `JSON.parse` в `rowToResult` — только по вошедшим строкам.
- Приёмка: тест — запрос с limit=N возвращает ≤N строк и готовит ≤N объектов (instrumentation prepare/rowToResult); результаты поиска идентичны прежним на фиксированном индексе (снимок).
- Апгрейд: поведение read-only путей, миграций нет.

**A8 (OPT-9, P2, попутно) Lazy SQLite.**

- Требование: read-only команды не открывают SQLite и не платят DDL.
- Дизайн: конструктор `SQLiteSearchIndex` хранит dbPath; `Database` + схема — при первом обращении (indexObject/search/rebuild/searchAll). Работает в связке с A3 (native-модуль уходит из критического boot-пути).
- Приёмка: `wolf --version`/`wolf list` не создают `.wolf/` SQLite-файла (замер отсутствия mkdir/open); `wolf search` работает как раньше (e2e).
- Апгрейд: внутренняя механика.

### 4.B Наблюдаемость доставки

**B1 Строка доставки в recap.**

- Требование (Т3, дословно): «доставок N, промахов M, топ промахов» — одной командой входа в сессию.
- Дизайн: `generateRecap` получает опциональную зависимость — чтение router.log (парсер существует, B-10); новая секция «Delivery (7d)»: `доставок N, промахов M, топ промахов: <agent-id> (×k), …`. Окно 7 дней — константа. N = строк `playbook=hit` (canonical+fallback — доставка состоялась), M = `variant=fallback` (канон не найден, доставлен универсальный), топ промахов — топ-3 agent-id по fallback; M ⊆ N (промах — это доставка fallback'ом), канонических доставок = N − M — при реализации строка/дока не должны провоцировать чтение «N и M независимы». Нет router.log / нет строк в окне → секция опускается (пустой проект — штатная ситуация).
- Приёмка: на dogfood секция заполняется числами, сверка ручным подсчётом `grep -c` по router.log за окно; старый вывод recap без router.log не меняется (снимок).
- Апгрейд: read-only поверх существующего лога.

**B2 Панель доставки в `analytics --view delivery`.**

- Требование (Т3): топ доставляемых, miss-rate по agent-id, средний размер инъекции; `--json` — машинный вывод (дефолт для агентов — как в существующих view).
- Дизайн: `delivery` добавляется в union views (`analytics.ts:25-54`) и в `build-analytics` (routerLog уже на входе — `:430`): (а) топ доставляемых — count по `detail.name` delivery-сигналов за окно; (б) miss-rate по agent-id — доля fallback в router.log; (в) средний размер инъекции — mean `detail.injection_bytes` (delivery-сигналы) + mean `bytes` (router.log, после A2); (г) скиллы — топ вызовов из B3; (д) applied% — колонка E (ниже). Окно и фильтры — как у существующих view (те же конвенции `filterAnalytics`).
- Приёмка: `wolf analytics --view delivery --json` на dogfood отдаёт непустой объект со всеми секциями; числа (а)–(в) сверяются ручным jq-подсчётом по тем же логам.
- Апгрейд: новый view аддитивен; старые view не меняются.

**B3 Телеметрия skill-invocation (T2 консилиума, H).**

- Требование: событие при вызове скилла агентом — иначе ценность скиллов и M18-гейт неизмеримы.
- Дизайн: плагин wolf-router подписывается на `tool.execute.before` (документированный хук opencode-плагинов; `input.tool === 'skill'` → имя скилла из args) и пишет строку в новый файл `.wolf/metrics/skill-invocations.jsonl`: `{ts, skill, agent?}` — agent-id из маркера system-промпта, если доступен в контексте хука, иначе без атрибута. Пишет напрямую fs (паттерн писателя router.log), fail-safe try/catch. Отдельный файл — потому что enum событий `SignalEventSchema` закрытый (`session-metrics-log.ts:42-51`): новый тип события в общем логе дал бы malformedLines у старых читателей при откате; отдельный файл — инвариант «новые файлы» (§5.i). Форма входа хука (состав полей) проверяется при реализации; при отсутствии agent-атрибута в хуке — запись без него, счётчики по имени скилла достаточны для M18.
- Приёмка: вызов скилла в тест-сессии → строка в файле; `analytics --view delivery` показывает счётчики скиллов; падение плагина не роняет сессию (fail-safe тест).
- Апгрейд: новый файл, старыми версиями не читается; отсутствие файла = нет данных (штатно).

### 4.C Сессионная дедупликация (Т3)

- Требование: запись доставляется в session_key один раз; повторно — только при изменении контрольной суммы текста. Принцип: «повторы для новых исполнителей — норма; повторы внутри сессии — налог».
- Дизайн:
  - _Продюсер ключа_ (плагин, вместе с A2): при загрузке плагин ставит `process.env.WOLF_SESSION = 'opc-<uuid>'`, если env отсутствует; per-spawn override в `runWolf` (`:66`) убирается — спавны и bash-вызовы волка агентом наследуют один ключ на процесс opencode. Известный потолок (ponytail): несколько одновременных чатов в одном процессе opencode шарят ключ — это консервативно (недо-дедупликация, не пере-дедупликация); путь апгрейда — per-session обёртка, если измеримая проблема. Бонус: ключ перестаёт быть «фальшивой сессией на все доставки» в терминах 0.2 — становится дискриминативным по процессам ≈ сессиям.
  - _Реестр доставок_: `.wolf/cache/sessions/<session_key>.json` — `{delivered: {[memory_id]: checksum}, injectedBytes}`. Читается/пишется в `getCallInjections` (новый опциональный вход `sessionKey` из `resolveSessionId()`): id уже в реестре с той же checksum блока (sha256, обрезка до 16 hex) → skip из вывода; checksum отличается → доставить и обновить. `sessionKey === null` (MCP-канал) → фильтр выключен. Запись реестра — рядом с delivery-сигналом в `memory-call.ts`.
  - _GC_: при любом обращении к каталогу sessions удаляются файлы старше 7 дней по mtime (без отдельного cron).
  - _Guardrail_: новый session_key = полная доставка без ограничений; fallback-ветка `wolf call` без `--for` (весь пул) дедуплицируется тем же правилом.
  - _Пустой вывод объясняет себя_: если дедупликация отфильтровала всё, `wolf call` печатает `[wolf] N инъекций уже доставлены в этой сессии (дедупликация; изменившиеся записи доставляются повторно)` вместо «No active call injections» — молчаливая пустота читалась бы агентом как «память пуста» (тихая смерть контекста; прецедент — «пустой call объясняет себя» продуктового диалога, Т2).
- Приёмка: e2e — два `call --for X` в одной сессии (WOLF_SESSION зафиксирован): второй не доставляет уже доставленные id и печатает строку дедупликации; изменение тела записи → повторная доставка; свежий WOLF_SESSION → полная доставка; repeat-streak ≤ 2 в 95% burst'ов на dogfood-окне (юнит: burst = гэп > 60 с в пределах session_key — определение §8 dogfooding); доля новых сессий с непустой доставкой ≥ 95% (§8 — контроль тихой смерти; дедупликация по построению снижает суточные totals, поэтому порог привязан к первому вызову каждой сессии, а не к объёму).
- Апгрейд: реестр — derived-кэш в gitignored каталоге; отсутствие = нет дедупликации (поведение 2.11). Поведение без продюсера ключа (старый плагин, без sync) = сегодняшний день.

### 4.D Мягкий лимит контекста (Т3)

- Требование: предупреждение при > 20% контекста сессии на инъекции; настраивается, не блокирует.
- Дизайн: конфиг `.wolf/config.yaml`: `delivery.context_budget_tokens` (дефолт 200 000) и `delivery.context_warning_pct` (дефолт 20); отсутствующие ключи = дефолты (§5.iii). Трекинг: `injectedBytes` в реестре сессий (4.C) инкрементится на каждую доставку; при пересечении порога `wolf call` печатает в stderr одну строку `[wolf] инъекции сессии ~<X>% бюджета контекста (<байты>/<бюджет>) — лимит предупреждения <Y>%`. Доставка не режется, код возврата не меняется. Граница: считается call-канал; playbook роутера (1× на сессию по идемпотентности `INJECT_HEADER`) в сумму не входит — его bytes видны в панели B2. Токен-аппроксимация: bytes/4 (стандартная эвристика; точная токенизация — не-цель, прецедент 0.1).
- Приёмка: fault-injection — реестр с накрученным `injectedBytes` > порога → строка в stderr, вывод и exit code не меняются; конфиг без ключей → дефолты без ошибок; конфиг с ключами → применяется (тест обоих).
- Апгрейд: новые ключи конфига — zod-strip у старых читателей (§5.iii).

### 4.E Метрика «доля применений» (Т3)

- Требование: индикатор (не приговор) — событие повторного обращения к доставленной записи в той же сессии; подсветка «доставляется много, применений не видно» — фильтр гнили конституции.
- Дизайн: без нового writer — аналитический join в B2: delivery-сигнал `(session_id, detail.name)` ∩ последующий в той же сессии mcp_call get c `detail.memory_id` равным доставленному id → `applied`. Колонка `applied%` в топе доставляемых (B2а); строка-подсветка: `deliveries ≥ 10 и applied% < 10%` за окно. Покрытие: CLI-канал (session_id не null — после продюсера 4.C); MCP-канал (session null) — вне метрики, явно (MCP session identity — не-цель dogfooding §6).
- Приёмка: на dogfood-окне ≥ 7 дней join непуст и сверяется ручной проверкой 5 пар (доставка → get в той же сессии); панель отображает applied% и подсветку.
- Апгрейд: read-only вычисление поверх существующих полей (0.1).

## 6. Не-цели

- **Демон/резидентный сервис** ради скорости — ломает local-first spawn-модель (отчёт оптимизатора: «что сознательно не предлагаю»).
- **Преждевременный бандлинг** — сначала lazy import (A3); бандл — если профилирование покажет остаток.
- **Read-path из SQLite / персистентный parse-кэш** (OPT-10 b/c) — отдельная будущая спека (design-решение source-of-trift + инвалидация); type-предфильтрация OPT-10a — кандидат туда же, не входит в 2.12.
- **`store.get()` детерминированный путь** (OPT-11) — вне 2.12 (роутер перестает звать get K раз — A2; scan.get закрывается кэшем A5).
- **Ротация логов** (OPT-8) — вне 2.12: A3+A1 капируют основные пути деградации; retention-решение требует отдельного дизайна окна аналитики (§8); кандидат 2.13.
- **MCP session identity** — не-цель dogfooding §6; дедупликация и applied% — CLI-канал.
- **Детектор «упоминаний» скиллов в тексте сообщений** — шумный продюсер без сигнальной ценности; телеметрируется вызов (tool.execute) — см. §10.
- **Блокирующие лимиты / резка доставки** — только предупреждение (принцип Т3).
- **Точная токенизация** для лимита — bytes/4 достаточно для индикатора.
- **Поле `model`, tags-merge, dry-run upgrade** — наследованные не-цели прецедента.

Правка: в 4.C явно описан продюсер (env от плагина на процесс opencode) и зависимость W8 → W6; в §7 — риск «несколько чатов одного процесса».

Правка: покрытие явно ограничено CLI-каналом (после продюсера 4.C), MCP — ссылка на не-цель; иначе задача была бы принята с навечно пустой метрикой.

### Линза 2: Минимальность

Вопросы: что можно выкинуть без потери ценности? Каждая механика — минимальный ли вариант?

Находки и правки:

1. **[выкинуто] Отдельный writer/событие для applied-метрики (4.E).** Join на существующих полях (0.1: `detail.memory_id`, `session_id`) даёт метрику без нового кода записи. Оставлен чистый analytics-join.
2. **[выкинуто] Детектор упоминаний скиллов** (§10.1) — вызов закрывает измеримость, упоминание — шум.
3. **[выкинуто] Суммирование playbook-байтов в лимит D** (§10.2) — playbook и так 1×/сессию; усложнение ради полноты не окупается.
4. **[упрощено] A1: выбран сайдкар-счётчик, а не «кластер-детект по tail».** Вариант из отчёта (tail-K + patterns.jsonl) дешевле по IO, но теряет точность счётчика — а точный count нужен порогу Ф21 (фиксация паттерна ровно один раз). Сайдкар точен, дёшев (ms) и rebuild'аем. Альтернатива зафиксирована как отвергнутая.
5. **[упрощено] A2: ранний стоп вместо батча/параллельных get.** Battch/parallel — больше кода при том же UX-результате; типичный случай = 1 get.
6. **[проверено] Каждая задача S/M — ни одна не тянет на L.** Крупнейшие диффы (W4, W5, W6, W8) — локальные механики в 1–2 файлах. Дробление волны на 10 задач оправдано границами файлов/каналов доставки (бинарё vs sync), не искусственное.
7. **[оставлено] recap-окно 7 дней константой** — конфиг-кнопка для окна одной строки recap не окупается (YAGNI); в §6 не вынесено, но и не параметризовано.

### Линза 3: Данные / телеметрия

Вопросы: все метрики измеримы? Пороги обоснованы источником, не выдуманы?

Находки и правки:

1. **[исправлено] «доставок N» без определения N.** Уточнено: N = `playbook=hit` (canonical+fallback), M = `variant=fallback` — «промах» = канон не найден. Данные существуют с 2.11 (B-10), новых writer'ов не требуется.
2. **[исправлено] порог «canonical-share − 5 пп» появился как контроль.** Ранний стоп A2 теоретически может предпочесть релевантный не-канон — контрольная метрика в §8 делает риск наблюдаемым, порог симметричен прецеденту (hit-rate ± 1 пп / error-rate ± 2 пп).
3. **[проверено] все пороги §8 привязаны к источникам**: < 2 с / < 500 мс / < 300 мс — продуктовый диалог («Метрики успеха»); 0 строк events.jsonl — бриф («не растёт на ~120 строк/вызов»); repeat-streak ≤ 2 / 95% и суточные delivery ≥ 50% медианы — прецедент dogfooding 1.3/§5.4; ±1–2 пп — прецедент §8. Новый порог «CLI brief p90 < 5 с» — расчётный (8.02 − boot 0.9 − проход 0.5–1.0 − sys-churn ≈ 4–5 с), помечен как расчётный, подтверждается на канарейке до приёмки.
4. **[исправлено] «средний размер инъекции» без спецификации.** Уточнено: mean `detail.injection_bytes` (delivery-сигналы, пишется с 0.1) + mean `bytes=` (router.log, после A2) — два канала раздельно, не смешиваются.
5. **[проверено] дискриминативность сессий после 4.C**: смена продюсера (fresh-per-spawn → per-process) не ломает burst-юнит §8 (гэп > 60 с внутри ключа) и приближает «уникальных session_id ≈ числу сессий» (приёмка 0.2) — свежий-на-спавн давал больше ключей, чем сессий. Отражено в 4.C.
6. **[исправлено] сайдкар-счётчики и воспроизводимость Ф21.** Добавлена приёмка A1: кластер, уже пересёкший порог в прошлом, не фиксируется повторно (счётчик monotone по построению — считаем события, а не окна); regress-тест на снижение `pattern_threshold`.
7. **[исправлено] контрольная метрика «суточные delivery ≥ 50% медианы» невалидна при дедупликации.** Порог унаследован из прецедента (там он ловил тихую смерть call), но дедупликация снижает totals по построению — ложно сработал бы на каждом проекте. Заменена на «непустая доставка в новые сессии ≥ 95%» (join mcp_call(call) × delivery по session_id; первый вызов каждой сессии), totals переведены в мониторинговые числа без порога (§8).
8. **[исправлено] «warm call» не был определён.** Порог p90 < 2 с без определения серии неизмерим. §8: серия 10 прогонов `/usr/bin/time`, warm = прогоны 2–10 (первый — cold, filesystem-кэш холодный, не порогируется).

Итог линз: спека исполнима (все механики лежат на верифицированный базлайн; исполнимость-линза исправила 6 пунктов: декомпозиция порогов, измеримость router/dedup/applied, пустой вывод, неявная зависимость W1→W2; несущие механики перепроверены по коду после написания), минимальна (4 выкинутых механики, 2 упрощения при сохранении порогов), метрики измеримы и обоснованы (все пороги привязаны к источникам; единственный расчётный порог помечен; невалидный при дедупликации контроль заменён; warm определён). Правки внесены в текст до публикации журнала.
