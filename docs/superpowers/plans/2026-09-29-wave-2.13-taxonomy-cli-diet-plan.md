## 1. Порядок, потоки, релиз

**Порядок блоков: C (диета) → A (таксономия) → B (CLI)** — ступенчатые влития, обоснование по спеке:

1. **Диета первой** сокращает поверхность до реформы: learn-конвейер (спека C3) вычищает хвосты из деклараций до их полной замены в A; council/session-checkpoint-команды (C15/C16) обязаны уйти до карты §5.4 спеки — иначе пишут в поглощаемые типы; run/coord/stage (C1/C2/C5) убирают команды до пересборки реестра и help-бюджета (§6.6 спеки). Диета не зависит ни от A, ни от B.
2. **Таксономия второй** — реформа данных: 7 деклараций, статусы thread, фасеты, alias-чтение (инвариант v), passthrough, migrate (§8 спеки). Кодово зависит от C только в одном файле (`memory-types.ts` — DRAFT_FIELDS/DECAY_FIELDS умирают заменой деклараций в A, а не правкой в C), поэтому потоки C и A не пересекаются.
3. **CLI третьим**, потому что генерируется из A: генератор неймспейсов (§6.3 спеки) требует `MEMORY_TYPES` из 7 типов и guard «7/7»; `add --type thread` обязан создавать `WORK-THREAD.md` (§10.1 спеки) — условие смерти create (§6.2). Часть B не зависит от A (edit/archive/relation §6.1/§6.4, окна §6.5, скрытие plumbing §6.6) — разрабатывается параллельно, вливается третьей ступенью. Механизм окна A→B безопасен: старые create-писатели валидируются zod-схемами, а не декларациями (`create-work-thread.ts:54` — `WorkThreadSchema.parse`), поэтому после влития A compile/тесты живы, а написанное между влитиями читается alias-слоем P211.

**Дробление релиза: один 2.13.0** (спека §8.3: двойной не нужен — сессии получают «tool not found»/подсказки и самовосстанавливаются, прецедент обоснования T030). Stage-влития — да, релизы — нет: влития C → A → B в main дают контрольные точки интеграции (каждое — `npm run check` зелёный), но промежуточный npm-пакет с половиной диеты пользователю бесполезен, а migrate обязан приехать в том же бинарье, что и alias-чтение (инвариант v спеки §8.1). Финал — 2.13.0 с миграцией.

Нумерация: **P2xx ↔ блоки спеки (A/B/C + §8/§10/§11/§12)**; P200/P230/P231 — протокольные (baseline, релиз, приёмка) по §10/§8.3/§12 спеки и прецеденту P100/P111/P112.

## 3. Валидация волны (staging-контур + пороги §10 спеки)

Единицы: объект памяти (id; sha256(body) для всех, sha256(frontmatter+body) — только немигрируемые, P200(в)), строка events.jsonl, строка help, tool-вызов MCP.

Команды:

- **npm run check** — в каждом потоковом worktree перед витием каждого шага ступени; pre-existing failures фиксировать отдельно и не чинить без права.
- **prettier --write** на каждый изменённый `docs/**/*.md` (format:check покрывает доки — гейт валит check).
- **e2e**: `nohup npm run e2e > /private/tmp/<поток>-e2e-$(date +%m%d).log 2>&1 &` + опрос хвоста; закладываться до ~30 мин; имена логов уникальны на поток (урок `mem_20260928_...ec1f9e`).
- **Staging-миграция** (P213, повторяется в P230 на релизном бинарье):

  ```bash
  STAGE=/private/tmp/dogfood-2.13-stage-$(date +%m%d)
  rsync -a <dogfood>/.wolf "$STAGE/"
  cd "$STAGE" && git init && git add -A && git commit -m stage
  wolf list --json | jq -r '.[].id' | sort > ids-before.txt
  wolf migrate taxonomy            # dry-run; отчёт сохранить
  wolf migrate taxonomy --apply
  wolf list --json | jq -r '.[].id' | sort > ids-after.txt
  diff ids-before.txt ids-after.txt && echo "LOSS: none"
  wolf migrate taxonomy --apply    # повторный — no-op (0 строк плана)
  wolf call --for task && wolf brief && wolf search тест && wolf list
  git checkout -- .wolf && wolf rebuild-index   # ветка отката; ids == before
  ```

  Аналогично для Tender (`tender-2.13-stage-<ммдд>`). Полнота потерь: id-множества + checksum немигрируемых + body-checksum мигрированных (снапшот P200; полная checksum к мигрированным неприменима — frontmatter меняется картой §5.4). При ре-ране в тот же день — суффикс HHMM в имени каталога (rsync в существующий каталог смёржит устаревшие файлы → ложно-зелёный diff).
