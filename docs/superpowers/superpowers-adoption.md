## 1. Что такое superpowers и почему его стоит перенять

**superpowers** — фреймворк процессов для AI-кодинг-агентов (набор из 16 «скиллов»
— инструкций-процедур вроде «сначала дебаг root-cause, потом фикс»). Его сила не
в текстах скиллов, а в **четырёх механизмах**, которые заставляют агента реально
их соблюдать:

1. **Гарантированный автостарт.** Хук при старте сессии сам инжектит мета-скилл
   в контекст агента. Агенту не нужно «помнить» о правилах — они появляются сами.
2. **Триггеры «Use when…».** У каждого скилла есть описание-триггер («используй,
   когда пишешь план»). Агент ищет нужный процесс по ситуации, а не грузит всё.
3. **Связи между процессами.** Скиллы ссылаются друг на друга маркерами
   (`REQUIRED SUB-SKILL: …`) — из «напиши план» автоматически вытекает «исполняй
   план так». Граф процессов читается простым grep'ом.
4. **Проверка поведения, а не текста.** Pressure-тесты: провокационный промпт
   подаётся живому агенту, и тест проверяет — вызвал ли агент нужный скилл или
   проигнорировал. Тестируется дисциплина, а не код.

## 2. Что у Wolf было до этого и чего не хватало

У Wolf сильная **память**: типизированные объекты (22 типа), жизненные циклы,
поиск, оркестрация. Но знание не всегда **доезжало** до агента:

| Проблема | Как страдал агент |
|---|---|
| Стартовый ритуал (`wolf brief`) был пунктом протокола в AGENTS.md | Агент мог забыть/пропустить → работал без контекста проекта |
| Уроки без ручной инжекции не доставлялись никогда | Записали урок про merge — а при следующем merge никто его не увидел |
| Связи между объектами памяти строились временными скриптами | Граф знаний не мог пополняться штатно |
| Нет проверок «меняет ли запись памяти поведение» | Ошибки доставки знания находились только реактивно, постфактум |

## 3. Что сделано: 4 механизма superpowers → инфраструктура Wolf

Общий принцип переноса: **берём механизмы, а не контент**. Каждый садится на
уже существующую инфраструктуру Wolf, ничего дублирующего не заводится.

### ✅ 1. Автостарт — плагин `wolf-session-start.js` (Phase 15, `798a187`)

**Как у superpowers:** bash-хук инжектит мета-скилл при старте сессии.
**Как у нас:** JS-плагин OpenCode (у Wolf другой таргет — bash-вариант не копировали).
При старте сессии плагин сам выполняет `wolf recap` (+ `call --for`) и кладёт
результат в первое user-сообщение с защитой от повторной инжекции.

**Зачем:** стартовый ритуал стал гарантией платформы, а не договорённостью.
Свежая сессия получает снимок проекта даже если агент забыл протокол.

### ✅ 2. Триггеры — `trigger_keywords` на lesson/rule (Phase 16, `798a187`)

**Как у superpowers:** у каждого скилла триггер «Use when…».
**Как у нас:** поле `trigger_keywords` у объектов типов lesson/rule; матчинг в
`wolf call --for <тема>`.

**Зачем:** знание доставляется **в момент использования** — это главный механизм
ценности памяти. Раньше урок без ручной инжекции не доставлялся никогда.
Проверено end-to-end: `add --type lesson --set 'trigger_keywords=[merge]'` →
`call --for merge` возвращает этот урок.

### ✅ 3. Связи — двухуровневая схема (Phase 17, `fad84b9`)

**Как у superpowers:** только текстовые ссылки `superpowers:<имя>` + маркеры
обязательности (REQUIRED/BACKGROUND); позиционные ссылки («см. выше») и
force-load канонизированы как анти-паттерны.
**Как у нас:** два уровня —
- машиночитаемые рёбра: `wolf relation add` (relations.jsonl, автоинверсия) —
  их читают solve/council;
- текстовая конвенция `wolf:<type>:<id>` с маркерами REQUIRED/BACKGROUND в
  документации — резолвится через `wolf get`.

**Зачем:** проза не запросывается графом, поэтому одной конвенцией не обойтись;
но и рёбра без читаемой конвенции не живут в документах. Здесь Wolf сделал шаг
дальше superpowers — у них CLI для связей нет вовсе. E2E-сценарии переведены с
временных .mjs-скриптов на штатный CLI.

### ✅ 4. Red Flags — таблица против рационализации (Phase 19, `fad84b9`)

**Как у superpowers:** в мета-скилле таблица «отговорка → реальность», потому что
рационализация («это не считается задачей», «я и так помню») — задокументированная
причина срыва любой агентской дисциплины.
**Как у нас:** §6 в `.wolf/SKILL.md` — 7 отговорок, специфичных для памяти
(«найдётся поиском», «запишу потом»), каждая с контрдействием.

**Зачем:** ноль кода, работает через авторитет документа. Дешёвый compliance-механизм.

### ⏸ 5. Поведенческие тесты памяти (Phase 18 — отложено осознанно)

**Как у superpowers:** стимул-промпт → живой агент → grep по tool-call: вызван ли
нужный скилл; отдельно детектируются «premature action» (тулы до вызова скилла).
**Почему отложено:** нужен запуск LLM на каждый тест — дорого для общего `check`;
сейчас доставка знания проверяется реактивным циклом `solve`. Схема зафиксирована
в roadmap (Phase 18 [L]), чтобы не потерять: harness «стимул + wolf call» против
mock-агента, отдельным npm-скриптом вне check.

## 4. Что это даёт пользователю Wolf (итог одной фразой на пункт)

- Сессия **всегда** начинается с актуального состояния проекта — без надежды на память агента.
- Урок, записанный once, **сам всплывает** когда тема совпала — память начала работать.
- Знания связаны графом, который пополняется штатной командой и читается и машиной, и человеком.
- Отговорки от ритуалов пресекаются документом, который агент видит на каждом старте.
