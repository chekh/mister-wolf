# Дизайн: дистрибуция и инсталляция Mr.Wolf

- **Дата:** 2026-08-30 (рев. 2 — после валидации тремя линзами)
- **Статус:** на валидации (цикл 2)
- **Контекст решения:** публичный релиз Wolf как инструмента для AI-агентов; установка «двумя командами» + bootstrap

## 1. Цель

Любой человек или AI-агент ставит Wolf тремя командами:

```bash
npm install -g mister-wolf   # уровень 0: машина
cd my-project && wolf init   # уровень 1: проект
wolf bootstrap               # наполнение памяти документами проекта
```

После **перезапуска агентской платформы** MCP-сервер Wolf подключён (Claude Code дополнительно требует approval project-scope MCP-сервера при первом старте — init сообщает об этом явно). Путь `npx mister-wolf init` — только try-out памяти без записи MCP-конфига (см. §4).

## 2. Принятые решения (диалог 2026-08-30 + правки по ревью цикла 1)

| Вопрос             | Решение                                                                                                                                                                                                                                                     |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Цель дистрибуции   | Публичный пакет (npm + GitHub), open-source                                                                                                                                                                                                                 |
| Модель установки   | Голый бинарь, вся настройка — командами; никаких собственных lifecycle-скриптов (preinstall/install/postinstall), пишущих в конфиги. Native-сборка зависимости (better-sqlite3) — не «postinstall wolf'а», различие фиксируется unit-тестом (§7)            |
| Инициализация      | Per-project `wolf init`, идемпотентный, неинтерактивный (ни одна команда wolf не ждёт ввода); проектов много — каждый инициализируется отдельно. **init ≠ bootstrap**: init создаёт скелет + MCP-конфиги, bootstrap (существующая команда) наполняет память |
| Платформы v1       | opencode + Claude Code + интерфейс адаптера (новая платформа = один файл)                                                                                                                                                                                   |
| Публикация         | GitHub public (репо `chekh/mister-wolf`, уже подключён как origin) + npm public + MIT                                                                                                                                                                       |
| npm-имя            | `mister-wolf` (свободно, совпадает с репо; `mr-wolf` занят — work-queue библиотека). Риск тайпсквота отработан в README (§7)                                                                                                                                |
| Windows            | **Не заявлена в v1** (пребилды у better-sqlite3 формально есть, но мы её не тестируем; best-effort, issue принимаются)                                                                                                                                      |
| Публикация CI      | Trusted publishing (OIDC) + `--provenance`, без долгоживущих токенов (см. §5)                                                                                                                                                                               |
| Native-зависимость | **Bump better-sqlite3 до актуального мажора с пребилдами под Node 22/24** до публикации (9.x собирала пребилды только под ABI 108/115/120 — см. §8)                                                                                                         |

## 3. Архитектура: три уровня инсталляции

### Уровень 0 — машина (один раз)

- `npm install -g mister-wolf` даёт бинарь `wolf` (bin уже объявлен: `dist/bootstrap/cli.js`).
- Установка ничего не пишет в конфиги пользователя и платформ.
- Глобальный юзер-конфиг: `$XDG_CONFIG_HOME/wolf/` (по умолчанию `~/.config/wolf/`):
  - `config.yaml` — непроектные настройки (LLM routing v2, модельные предпочтения);
  - `projects.yaml` — реестр инициализированных проектов (пути); пишет `wolf init`, читает `wolf doctor`, чистит мёртвые записи.

### Уровень 1 — проект (один раз на проект)

`wolf init` в корне проекта. Идемпотентный, неинтерактивный, повторный запуск = штатная перенастройка:

1. **Скелет `.wolf/`** — через существующий `init-project-memory`/`FsProjectInitializer`, **но с семантикой ensure-без-перезаписи**: существующие `config.yaml` и память не трогаются (текущий баг перезаписи — фиксируется в рамках scope, §8).
2. **Стартовый scan** документов проекта (лёгкий; глубокое наполнение — отдельная команда `wolf bootstrap`, для которой чинится дедупликация при повторе, §8).
3. **Платформы**: детект по файлам-маркерам; для каждой обнаруженной пишет MCP-конфиг через адаптер (§4). **Кейс «платформа не детектирована»**: warning + skip MCP-конфига, init успешен (память создана), подсказка `--platform <id>`.
4. **Реестр**: регистрация проекта в `$XDG_CONFIG_HOME/wolf/projects.yaml`.

Флаги: `--platform opencode,claude` — явный список **заменяет** текущий набор (wolf-записи платформ вне списка удаляются из их конфигов). Флаг `all` не вводится (неоднозначен). Дефолт без флага — авто-детект (объединение найденных).

**Вывод init** (машиночитаемо и по-человечески): результат per-platform (записан / пропущен + причина), напоминание «перезапусти платформу», для Claude — «одобри MCP-сервер при первом старте». Ненулевой exit — только если не записано ни одного конфига при явном `--platform`.

**npx-путь:** `npx mister-wolf init` работает как try-out (скелет + память), но **никогда не пишет MCP-конфиг**: под npx проверка «wolf на PATH» всегда истинна (шим из `_npx`-кэша), поэтому критерий не PATH, а сам факт npx-запуска. Init предупреждает и даёт инструкцию глобальной установки; повторный глобальный `wolf init` достраивает конфиги (идемпотентность).

### Уровень 2 — время (обновления)

Глобальный бинарь + много проектов = рассинхрон версий схемы. Решения:

- **Маркер версии схемы** в `.wolf/config.yaml` (`schema_version`; при отсутствии — легаси-версия).
- **Ленивая миграция:** guard при двух точках входа (`cli.ts`, `mcp.ts`) — проверка версии при любой команде; расхождение → миграция. Параллельный старт двух платформ на одном проекте: миграция под эксклюзивным лок-файлом `.wolf/migrate.lock`, маркер версии пишется атомарным rename. **Носитель схемы — fs-layout + config.yaml** (SQLite — лишь кэш; «бэкап БД» не делается): бэкапятся мигрируемые файлы в `.wolf/backup/<timestamp>/`.
- Схема проекта **новее** бинаря → честная ошибка «обнови wolf» с требуемой версией, без записи.
- **`wolf doctor`:** по реестру проектов — версия бинаря vs схема каждого проекта, пути, валидность конфигов платформ; чистка мёртвых записей реестра.

## 4. Адаптеры платформ

```ts
interface McpCommand {
  command: string; // 'wolf' — глобальный бинарь на PATH
  args: string[]; // ['mcp']
}

interface PlatformAdapter {
  id: string; // 'opencode' | 'claude'
  detect(projectRoot: string): boolean; // файлы-маркеры платформы
  readConfig(projectRoot: string): Config; // для деактивации лишних wolf-записей
  writeConfig(projectRoot: string, cmd: McpCommand): void;
}
```

- **Канонический McpCommand — `{ command: 'wolf', args: ['mcp'] }`** (глобальный бинарь). Никакого `npx … mcp` в конфигах: резолв нативной зависимости на каждый старт платформы недопустим.
- **Ключ идемпотентности — имя MCP-сервера `wolf`:** существующая запись `wolf` (в т.ч. ручная dev-запись `node dist/…` у догфудеров) находится и её команда заменяется; чужие серверы и секции не трогаются.
- **Атомарная запись:** временный файл + rename; при невозможности записи (права) — отказ **до** изменения файла, без partial-записи. Конфликт значений в чужих полях — не перетираем, warning.
- V1-реализации: **OpencodeAdapter** (маркеры: `opencode.json` / `opencode.jsonc` / `.opencode/`), **ClaudeAdapter** (маркеры: `.mcp.json` / `.claude/`). Новая платформа = один адаптер без изменений init.
- **Коллизия bin на PATH:** на npm существует пакет `wolf` (Wolfram CLI, тот же bin) — при его установке глобальный `wolf` конфликтует; документируем в README (порядок разрешения PATH), публичных действий v1 не требует.

## 5. Публикация

- Репо: `github.com/chekh/mister-wolf` — уже подключён как `origin`, публичный. Лицензия MIT (`LICENSE` есть).
- npm: имя `mister-wolf`, bin `wolf`; в `package.json` — rename `name`, поля `license`, `repository`, `files`, `engines`.
- **Состав пакета (load-bearing):** `"files": ["dist"]` — без него tarball сломан: `dist/` в `.gitignore` и не уедет вовсе, а трекаемые `wolf-experiment/` (500+ файлов) и `.external-research/` утекут. README/LICENSE включаются npm автоматически. CI перед publish логирует `npm pack --dry-run` (манифест — аудит-след).
- **Аутентификация публикации:** npm **trusted publishing** (OIDC, `permissions: id-token: write`, токен не хранится) + `npm publish --provenance`. Fallback: granular-токен только на `mister-wolf` + GitHub Environment с required reviewers. Явный `permissions: contents: read` в workflow. Тег-триггер не срабатывает из форков (push тега требует write-доступ); `workflow_dispatch` — только с environment protection.
- **Publish job = `npm run check` + `npm run e2e` → publish.** Публикация — точка невозврата; e2e тестирует ровно публикуемый артефакт (правило проекта: E2E после каждого плана).
- **Sanity-check тег↔версия:** CI-шаг `test "v$(node -p "require('./package.json').version")" = "${GITHUB_REF_NAME}"`.
- CI/publish — на **Node 22** (опционально матрица 22/24; текущий ci.yml на Node 20 рассинхронизирован с README).
- Зависимости к v1: better-sqlite3 — актуальный мажор с пребилдами Node 22/24; `@modelcontextprotocol/server` — стабильная версия вместо `^2.0.0-alpha.2` (beta-SDK в runtime публичного пакета — churn-риск).
- Версионирование: semver вручную (bump + тег); changesets/semantic-release — YAGNI.
- Пути установки: `npm i -g mister-wolf` (основной), `npx mister-wolf init` (try-out, §3), dev-путь клонированием сохраняется (README: предупреждение о PATH-shadowing при одновременном глобальном wolf и dev-клоне).

## 6. Обработка ошибок и ограничения

- **Платформы:** `better-sqlite3` — darwin/linux-glibc (x64, arm64) на Node 22/24 (после bump, §5 — проверка `prebuild-install` входит в план). **Alpine/musl — не поддержан v1; Windows — не заявлена v1** (§2). Два разных сообщения об ошибках: «пребилда для этой платформы нет (musl) — не поддерживается v1» ≠ «сборка не удалась — проверь node-gyp prerequisites».
- Схема проекта новее бинаря → ошибка «обнови wolf», без записи (§3).
- Нет прав на запись конфига платформы → отказ до изменения файла, без partial-записи (§4).
- `.wolf/` повреждён → **неинтерактивное** восстановление: безопасный дефолт + подсказка флага `--recreate` (создать заново из бэкапа/с нуля). Ни одна команда не ждёт ввода — agent-first принцип.
- `wolf init` вне проекта → внятная диагностика, ничего не создаётся.

## 7. Тестирование

- **Unit:** адаптеры — детект по маркерам; `writeConfig` идемпотентен (второй вызов не меняет файл; запись `wolf` с чужой командой заменяется; чужие записи целы); атомарность при отказе прав. Миграции — легаси-проект без маркера → миграция + бэкап; схема из будущего → отказ без записи. Package-гигиена: unit-тест «в package.json нет preinstall/install/postinstall/prepublish».
- **E2E:** `npm pack` → установка tarball глобально **в изолированном tmp-HOME** (XDG переопределён — не трогаем реальный `~/.config` дев-машины) → `wolf init` в тестовом проекте с маркерами обеих платформ → конфиги содержат wolf-сервер → `wolf brief` отвечает → повторный init ничего не портит → **npx-кейс**: init без глобального бинаря не пишет MCP-конфиг и честно предупреждает → **tarball-assert**: состав пакета = `dist/` + README + LICENSE (ничего лишнего).
- **README (agent-first):** первая строка Installation — предупреждение тайпсквота («`mister-wolf`, **не** `mr-wolf` — второй пакет чужой и выполнит свои install-скрипты»); три шага install → init → bootstrap; напоминание о перезапуске платформы и Claude-approval; статус Windows/musl; `npx` = try-out; dev-путь + PATH-shadowing; заметка «native-сборка зависимости — это не postinstall wolf'а».
- **SECURITY.md в v1** (куда репортить уязвимости); CONTRIBUTING — post-v1.

## 8. Scope

- **Трогаем:**
  - `package.json`: rename `name` → `mister-wolf`, `files: ["dist"]`, `engines: node >=22`, `license`, `repository`; **bump better-sqlite3** до мажора с пребилдами Node 22/24; **@modelcontextprotocol/server → стабильная версия**;
  - `src/`: команда `init` (адаптеры, реестр, неинтерактивный вывод), `doctor`, маркер `schema_version` + ленивая миграция + guard в `cli.ts`/`mcp.ts`, фикс перезаписи `config.yaml` в `FsProjectInitializer`, дедупликация `wolf bootstrap` при повторе;
  - `tests/`: новые unit/e2e из §7 (включая tarball-assert и package-гигиену);
  - `README.md` (Installation + тайпсквот + платформенный статус), `SECURITY.md`, `.github/workflows/publish.yml` (+ Node 22 в существующем CI).
- **Не трогаем:** ядро памяти, learn-механизмы, остальные команды CLI — кроме точек входа (`cli.ts`, `mcp.ts`) для миграционного guard.
- **Follow-up (вне scope, фиксируем):** платформо-нейтральный текст bootstrap-brief (сейчас ссылается на `.opencode/agents/steward.md` — ломается для Claude-юзеров).
