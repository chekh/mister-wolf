# Дизайн: дистрибуция и инсталляция Mr.Wolf

- **Дата:** 2026-08-30
- **Статус:** утверждён в диалоге, ожидает ревью спеки
- **Контекст решения:** публичный релиз Wolf как инструмента для AI-агентов; установка «двумя командами»

## 1. Цель

Любой человек или AI-агент ставит Wolf двумя командами:

```bash
npm install -g mister-wolf   # уровень 0: машина
cd my-project && wolf init   # уровень 1: проект
```

После этого MCP-сервер Wolf подключён к агентской платформе проекта.

## 2. Принятые решения (зафиксированы в диалоге 2026-08-30)

| Вопрос | Решение |
|---|---|
| Цель дистрибуции | Публичный пакет (npm + GitHub), open-source |
| Модель установки | Голый бинарь, вся настройка — командами; никаких postinstall-скриптов, пишущих в конфиги |
| Инициализация | Per-project `wolf init`, идемпотентный; проектов много — каждый инициализируется отдельно |
| Платформы v1 | opencode + Claude Code + интерфейс адаптера (новая платформа = один файл) |
| Публикация | GitHub public (репо `chekh/mister-wolf`, уже подключён как origin) + npm public + MIT |
| npm-имя | `mister-wolf` (свободно, совпадает с репо; `mr-wolf` занят — work-queue библиотека 0.1.1) |

## 3. Архитектура: три уровня инсталляции

### Уровень 0 — машина (один раз)

- `npm install -g mister-wolf` даёт бинарь `wolf` (bin уже объявлен в package.json: `dist/bootstrap/cli.js`).
- Без postinstall-магии: установка ничего не пишет в конфиги пользователя и платформ.
- Глобальный юзер-конфиг `~/.config/wolf/`:
  - `config.yaml` — непроектные настройки (LLM routing v2, модельные предпочтения);
  - `projects.yaml` — реестр инициализированных проектов (пути); пишет `wolf init`, читает `wolf doctor`.

### Уровень 1 — проект (один раз на проект)

`wolf init` в корне проекта, идемпотентный (повторный запуск = штатная перенастройка):

1. Создаёт/проверяет `.wolf/` (переиспользует существующий use-case `bootstrap-project`).
2. Стартовый scan документов проекта.
3. Определяет агентские платформы по файлам-маркерам; для каждой пишет MCP-конфиг (см. адаптеры).
4. Регистрирует проект в глобальном реестре `~/.config/wolf/projects.yaml`.

Флаги: `--platform opencode|claude|all` (дефолт — авто-детект), `--force` (переписать конфиг платформы).

Ключевое следствие: **проект ≠ платформа** — один проект может обслуживать несколько платформ одновременно.

### Уровень 2 — время (обновления)

Глобальный бинарь + много проектов = рассинхрон версий схемы БД. Решение:

- **Ленивые миграции:** при первой команде в проекте проверяется версия схемы `.wolf/`; при расхождении — auto-migrate с автоматическим бэкапом БД.
- Схема проекта **новее** бинаря → честная ошибка «обнови wolf», не падаем и не пишем.
- **`wolf doctor`:** по реестру проектов показывает картину машины — версия бинаря vs схема каждого проекта, пути, валидность конфигов платформ.

## 4. Адаптеры платформ

Интерфейс (один файл на платформу):

```ts
interface PlatformAdapter {
  id: string;                                  // 'opencode' | 'claude'
  detect(projectRoot: string): boolean;        // файлы-маркеры платформы
  writeConfig(projectRoot: string, mcpCommand: McpCommand): void; // идемпотентная запись
}
```

V1-реализации:
- **OpencodeAdapter** — маркер: `opencode.json` / `.opencode/`; пишет секцию MCP в `opencode.json`.
- **ClaudeAdapter** — маркер: `.mcp.json` / `.claude/`; пишет `.mcp.json`.

Запись идемпотентна: повторный `writeConfig` не дублирует сервер и не портит чужие секции конфига. Новая платформа (Gemini CLI, Cursor и т.д.) = один новый адаптер без изменений init (стыкуется с направлением PoC #2 — мультиплатформенная гармонизация).

## 5. Публикация

- Репо: `github.com/chekh/mister-wolf` — уже подключён как `origin`, публичный.
- Лицензия: MIT (`LICENSE` в корне).
- npm: имя `mister-wolf`, bin `wolf`.
- CI: GitHub Actions — на тег `v*`: `npm run check` → `npm publish`; токен публикации — секрет репозитория.
- Версионирование: semver вручную (bump + тег); changesets/semantic-release — YAGNI.
- Поддерживаемые пути установки: `npm i -g mister-wolf` (основной), `npx mister-wolf init` (без глобальной установки, медленнее из-за native-зависимости).

## 6. Обработка ошибок и ограничения

- **`better-sqlite3` (нативный модуль):** пребилды покрывают darwin/linux-glibc (x64, arm64). **Alpine/musl в v1 не заявляем** — известное ограничение, фиксируем в README. Фейл сборки native → понятное сообщение про node-gyp prerequisites.
- Схема проекта новее бинаря → ошибка «обнови wolf» с версией требуемой схемы.
- Нет прав на запись конфига платформы → явная ошибка до начала записи, без partial-записи.
- `wolf init` вне проекта / в корне без прав → внятная диагностика, ничего не создаётся.
- `.wolf/` повреждён → init предлагает восстановление через пересоздание с бэкапом, не молча чинит.

## 7. Тестирование

- **Unit:** адаптеры платформ — детект по маркерам, идемпотентность `writeConfig` (второй вызов не меняет файл); ленивые миграции — старая схема → новая, бэкап создаётся, схема «из будущего» → отказ.
- **E2E (в policy «E2E после каждого плана»):** `npm pack` → глобальная установка tarball в чистом tmp → `wolf init` в тестовом проекте с маркерами обеих платформ → конфиги платформ содержат wolf-сервер → `wolf brief` отвечает.
- **README:** agent-first секция Installation — команды, которые агент выполняет сам, без чтения человека.

## 8. Scope

- **Трогаем:** `package.json` (name, files, license, repository), `src/` (команда init, doctor, адаптеры платформ, ленивые миграции, глобальный конфиг), `README.md` (Installation), `LICENSE`, `.github/workflows/publish.yml`.
- **Не трогаем:** ядро памяти, learn-механизмы, существующие команды CLI.

## 9. Риски

| Риск | Митигция |
|---|---|
| Формат конфигов платформ меняется | Изоляция в адаптере — правка одного файла |
| Пребилды better-sqlite3 не покрывают экзотические платформы | Явно заявленная поддержка darwin/linux-glibc; README фиксирует ограничение |
| Реестр `projects.yaml` расходится с диском (проект удалён) | `wolf doctor` чистит мёртвые записи |
| Клонирование репо на машину без сборки (старый путь установки) | Сохраняем рабочим: `npm install && npm run build` остаётся dev-путём |
