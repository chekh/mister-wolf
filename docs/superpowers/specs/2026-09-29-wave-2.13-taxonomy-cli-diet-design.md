## 1. Контекст и цель

Ядро доставки подтверждено dogfooding'ом, но продукт покрыт слоем неиспользуемой механики: 26 core-типов при живом ядре из 7, ~44 верхнеуровневых CLI-команд при канонической пятёрке глаголов, три аналитических поверхности одного датасета, 570-строчный дамп таксономии в config.yaml каждого проекта, автоконвейер уроков без трафика (patterns.jsonl — 4 строки у обоих активных проектов, §4.3 консилиума). Новичок видит 20 концепций первого класса вместо одной петли «поправил → закрепилось → доставилось → окупилось».

Цель 2.13 — **сжать продукт до честного ядра, не потеряв ни одну запись ни в одной инсталляции**: 7 типов + фасеты с цветом, каноническая пятёрка CLI-глаголов, слияние окон состояния, диета мёртвого кода.

## 2. Принципы

- P1 **Данные неприкосновенны.** Ни один сценарий старых данных не теряется: alias-чтение старых фронтматтеров/каталогов, идемпотентный migrate с отчётом, конфликт не трогается (прецедент `layout-migration.ts`).
- P2 **Дословность диалога.** Т1/Т2 согласованы владельцем дословно; отклонения от формулировок — только вверх по безопасности, не вниз по функциональности.
- P3 **Схема — единственный источник.** Команды type-неймспейсов, MCP-поля add и справочник CLI генерируются из таксономии; ручные дубликаты умирают.
- P4 **Диета не расползается.** Удаляется только то, что перечислено в §6; каждый пункт имеет источник (M/K/T-находка или решение владельца) и базлайн. Кандидаты вне списка — в открытые вопросы, не в код.

### 5.1 Выжившие типы (дословно Т1)

`rule`, `lesson`, `decision`, `thread`, `complaint`, `tool`, `note` (новый универсальный).

Новые декларации (замена `CORE_TAXONOMY_DECLS` целиком):

| --------- | ------------------------------------------------------- | ------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| rule      | — / `rules`                                             | active, superseded, obsolete, proposed, accepted, rejected, archived           | scope (enum), applies_to, trigger, trigger_keywords                                     |
| lesson    | `lessons` / `lessons`                                   | FULL                                                                           | trigger_keywords                                                                        |

- tool: поля `usage_count`/`last_used_at` оживают — инкремент при `wolf tool use` (T3: «оживить или удалить»; точка интеграции уже существует — `memory-tool.ts:97`). Статус-машина (авто-активация) — вне 2.13 (T5, волна A).

### 5.2 Статусы thread (поглощение blocker / info-request / open-question)

Дословно Т1: blocker/info_request/question — статусы thread. Конкретика:

- `MemoryStatus` расширяется: `+ 'blocked'`, `+ 'waiting_answer'` (статус `open` уже существует, `memory-types.ts:3-19`).
- `ALLOWED_TRANSITIONS` (`governance.ts:35-69`) дополняется: `active → blocked|waiting_answer|open`; `blocked → active|archived`; `waiting_answer → active|archived`; `open → active|archived` (строка `open` уже есть :52, дополняется `active`).
- Семантика: тред, ожидающий внешнего разрешения — `blocked`; тред, задавший вопрос наверх — `waiting_answer`; тред с открытым вопросом без адресата — `open`. Содержательное наполнение (impact/workaround, текст вопроса/ответа) живёт note'ом в треде с соответствующим фасетом — объект-тип не заводится.
- Разрешение: `blocked|waiting_answer|open → active` (обратный переход) или `→ archived`.

### 5.3 Фасеты

- **Закрытый словарь в конфиге**, первый — «характер записи». Дефолт (7 значений, диапазон 7–10 согласован диалогом :9): `howto`, `pitfall`, `context`, `metric`, `history`, `legacy`, `constraint`. Конфиг-ключ:

  ```yaml
  facets:
    character: [howto, pitfall, context, metric, history, legacy, constraint]
  ```

- **Проверка при add**: `--facet` валидируется против словаря; свободный ввод отвергается ошибкой со списком допустимых значений (прецедент формата — `getDeclaration`, `memory-types.ts:357-362`). Для `note` facet обязателен; для прочих типов запрещён (ошибка).
- **Хранение**: frontmatter `facet: <value>` (schema_version фронматтера не меняется — аддитивное поле).
- **Индексация**: колонка `facet` в `memory_meta` и `memory_search` (`sqlite-search-index.ts:223,236` — ALTER при открытии, индекс пересобирается `rebuild-index`); фильтры `list --facet`, `search` по фасету.
- **Цветовая подсветка** фасетов в `list`/`search`/`call` выводе: статическая карта facet→ANSI-код в коде (константа, не конфиг). Отключение: не-TTY (`process.stdout.isTTY === false`), `NO_COLOR`, `WOLF_NO_COLOR` — агенты (call через MCP/pipe) получают плоский текст автоматически. Дословно Т1: подсветка «в CLI-выводе и списках агентов» — цвет только в терминальных списках.

### 6.3 Генерация type-неймспейсов из таксономии

- `wolf <type> add` и `wolf <type> list` **для всех 7 типов** генерируются одним генератором из деклараций: обязательные поля декларации → обязательные флаги, enum → choices (фасет — выбор из словаря §5.3). ### 8.2 Миграция данных (первоклассный раздел)

**Команда:** `wolf migrate taxonomy` — dry-run по умолчанию, `--apply` для исполнения; прецедент doc-ids (`memory-migrate.ts:21-34`).

**Отчёт (перед выполнением, дословно Т1):** таблица «id | старый тип → новый (фасет/статус) | from → to», сводка по типам, отдельные блоки: конфликт-строки, unparsable (не трогаются), active call-injections (предупреждение о доставке §5.4), треды со сменой статуса. Подтверждение = явный `--apply` после dry-run.

**Правила безопасности:**

1. **Ни один объект не теряется**: count объектов до/после равен (мучительность проверяется критерием §10.3); unparsable и конфликты не трогаются (exit 2, прецедент).
2. **Чужие поля сохраняются — включая будущие правки**: strip срабатывает не только при миграции, но и при каждом чтении (`parseFileSafe` → `MemoryObjectSchema.parse`, strip по умолчанию) — первый же `edit` мигрированного note потерял бы legacy-поля. Поэтому **базовая `MemoryObjectSchema` переводится на passthrough** (неизвестные ключи сохраняются в объекте и переживают update/save цикл); миграция дополнительно преобразует сырой frontmatter без типовой схемы. Note-декларация не объявляет legacy-полей — они живут в frontmatter до первой смысловой правки владельцем. Guard: e2e «note с чужими полями переживает edit без потерь» (§10.3).
3. **Идемпотентность**: повторный `--apply` — no-op (файлы уже на новых путях с новыми типами; признак — `type` ∈ 7 новых).
4. **Откат**: до `--apply` требуется чистый git-состояние `.wolf/memory/` (проекты по формуле Т6 «память коммитится»); в не-git каталоге — явное `--force` с предупреждением. Откат = `git checkout .wolf/memory` + `rebuild-index`. Автобэкап не строится (данные версионируются git'ом — P4 прецедента).
5. **Статусы тредов** меняются только у тредов, находящихся в `active`, с активным (незавершённым) blocker/info-request/open-question; каждый случай — строкой отчёта. Всё прочее (тред в `completed/paused/archived`, несколько разных поглощаемых статусов у одного треда) — конфликт-строка, не трогается.
6. **task-brief**: migrate не трогает ни данные, ни конфиг; декларацию переносит владелец dogfood-репо в свой `config.yaml` при приёмке волны (не migrate). Критерий — чтение существующих tasks/-объектов после миграции.

**Совместимость чтения без миграции:** alias-слой `DEPRECATED_TYPE_ALIASES` расширяется полной картой §5.4 (`src/domain/memory-types.ts:349` + резолвер при парсинге, предупреждение — прецедент `list-memory-objects.ts:33-46`); старые каталоги — резервные корни чтения (§5.5). Инсталляция, не запустившая migrate, продолжает работать: чтение/поиск — да, запись новых — по новым путям.
