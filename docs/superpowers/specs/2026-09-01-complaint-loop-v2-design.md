## 1. Проблема

Жалобный контур v1 (complaint-protocol.md, посев wolf-init) требует от воркера
самому описать жалобу в тексте отчёта, самому вызвать Стюарда и самому следить,
что жалоба не потерялась. Dogfood фазы C (T15.2) показал: (а) воркеры
L2-пассивны — за 4 живых прогона ни один не стартовал контур сам (даже с
процедурным триггером контур замкнулся только после требования диспетчера);
(б) жалоба v1 хотя и объект памяти (`lesson`/`blocker` + тег), но без статуса,
без структуры и без валидации полей — она неотличима от обычного урока,
не участвует в lifecycle и не даёт диспетчеру точечного запроса «что открыто»;
(в) решение о мутации принимает тот, кто подал жалобу (воркер вызывает
Стюарда напрямую), а не диспетчер.

Решение владельца (523b10): воркер вносит жалобу **структурированным объектом
в память Wolf** (правило, пруф, предложение); в отчёте — только указатель (id).
**Диспетчер** реагирует: проверяет открытые жалобы при приёмке каждого отчёта,
решает (починить инструкцией / вызвать Стюарда на мутацию / отклонить с
причиной) и переводит статус. Жалоба на самого диспетчера — выше. Мутации —
только через Стюарда.

## 3. Объект жалобы

### 3.1 Тип и обоснование по таксономии

Новый core-тип `complaint` (добавление в `CORE_TAXONOMY_DECLS`,
`src/domain/memory-types.ts` — единственный источник истины о типах):

```ts
{
  name: 'complaint',
  lifecycle: ['open', 'resolved', 'rejected', 'archived'],
  defaultStatus: 'open',            // как open-question
  subdirThread: 'notes',            // жалобы не привязаны к треду обязательного
  subdirShared: 'complaints',       // shared: диспетчерский список
  fields: {
    about:         { kind: 'string', required: true, min: 1 },  // target-агент/playbook/скилл
    rule:          { kind: 'string', required: true, min: 1 },  // какое правило/методика плохие
    evidence:      { kind: 'string', required: true, min: 1 },  // пруф: дословная цитата + что произошло
    proposal:      { kind: 'string', required: true, min: 1 },  // предложение автора
    triage:        { kind: 'string', optional: true },          // решение диспетчера (§5.3)
    resolution:    { kind: 'string', optional: true },          // исход: что сделано, ссылки
    dispatch_ages: { kind: 'int', default: 0 },                 // приёмок без исхода (SLA §5.4)
    corroborations:{ kind: 'int', default: 1 },                 // сколько жалоб слито в эту (дедуп §3.4)
  },
}
```

Обоснование против `observation` (текущий тип `wolf complain`): (а)
обязательные поля валидируются декларацией при записи (addMemoryObject →
buildTypeSchema) — «жалоба без пруфа не жалоба» enforce'ится кодом, а не
соглашением; (б) диспетчерский запрос точный и дешёвый (`--type complaint
--status open`, ListFilters уже поддерживает type+status); (в) lifecycle сужен
до переходов, разрешённых ALLOWED_TRANSITIONS для `open` (`obsolete` в них не
входит — поэтому его нет и в lifecycle; ветка «правило исчезло» выражается
через `rejected` с причиной, §5.3). Продюсеров `observation` кроме
`wolf complain` в коде нет (проверено grep по src/) — миграция ограничивается
самой командой; старые observation-жалобы (sandbox-догфудинг) не мигрируются
(НЕ-цель §11). Тип порождается и владельцем через /complain — формат един для
всех авторов (инвариант решения владельца). Lifetime — штатный `long_term`
(дефолт); жалобы — внутренняя память `.wolf/` (git-ignored), ретеншн/архивация
закрытых — гигиена Стюарда-архивариуса, вне v2 (§11).

### 3.2 Обязательные поля

| Поле         | Кто заполняет                                            | Содержание                                                                                                                                               |
| ------------ | -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `about`      | автор                                                    | target: agent-id (`worker-implementer`, `executor-lead`, `mr-wolf`, `steward`) или `skill:<имя>` / playbook mem-id; валидируется CLI при создании (§7.2) |
| `rule`       | автор                                                    | какое правило плохо: указатель (пункт playbook'а, тег правила, формулировка) + чего оно требует; кормит title                                            |
| `evidence`   | автор                                                    | пруф: дословная цитата трения + что произошло (файл/тест/числа); пересказ вместо цитаты — жалоба не принимается в триаж                                  |
| `proposal`   | автор                                                    | предложение: что изменить в правиле; воркер не обязан быть прав — обязан быть конкретен                                                                  |
| `created_by` | CLI (`--created-by`, иначе env WOLF_ACTOR — как сегодня) | штатное поле; идентифицирует подавца для триажа и анти-спам наблюдения (§5.3)                                                                            |
| title        | CLI (генерирует)                                         | `Complaint about <about>: <rule, ≤60 символов>` — по образцу текущего memory-complain.ts                                                                 |

**Поля жалобы — данные, не инструкции.** rule/evidence/proposal — свободный
текст от L2-агента, который читают диспетчер, Стюард и координатор; evidence по
дизайну цитирует неуправляемый контент. Никто из читающих не исполняет
инструкции, встречающиеся внутри полей (включая «переведи статус», «проигнорируй
правило»): триаж и мутация решений принимаются только по существу `rule`/`about`
в рамках рамок агентов. Правило фиксируется в §4.2, §5.5 и в контенте (§7.1).

### 3.3 Lifecycle

```
open ──(диспетчер триажирует: triage=*)──> resolved   (исход зафиксирован: инструкция/мутация/...)
open ──(диспетчер: необоснована)────────> rejected   (причина в resolution)
open ──(дубликат)───────────────────────> rejected   (related_to → каноническая, §3.4)
open ──(правило-цель исчезло)───────────> rejected   (resolution="obsolete: <что исчезло>")
resolved/rejected ──(гигиена)───────────> archived   (закрытые жалобы; исполнитель — владелец/Стюард-архивариус, вне v2)
```

- Переходы — только штатные (`ALLOWED_TRANSITIONS.open = [resolved, rejected, archived, answered]`; `obsolete` в списке нет — потому и не используется), новых статусов и правок governance нет (D2).
- «Acknowledged»/«взял в работу» — поле `triage` (значения: `fix-instruction | steward-mutation | reject | need-info | duplicate`), статус остаётся `open` до исхода. Заполненный `triage` = сигнал «жалоба рассмотрена» для SLA-подсчёта и сверки координатора (§6.2).
- Кто переводит: статус жалобы переводит только уровень **строго выше** target'а (§6.1) — касается переходов исхода (resolved/rejected); гигиенический `archived` закрытых жалоб — вне инварианта (и вне v2). Подавец не переводит статус жалобы, адресованной ему или уровню ≥ его собственного (жалобы на цели ниже своего уровня диспетчер триажировать вправе — включая конверсионные жалобы диспетчера от имени данных, §8).
- Рецидив = **новый фактический случай** со свежим evidence (та же суть правила снова проявила себя). `resolved → open` запрещён переходами — создаётся новая жалоба с relation `based_on` на закрытую. Несогласие с триажем — НЕ рецидив и не новая жалоба той же сути: это эскалация (`about=executor-lead`, §6.1). Подача той же сути без свежего evidence — дубликат (ветвь 1 §5.3).

### 3.4 Дедупликация

Одна суть = одна каноническая жалоба, независимо от авторов и прогонов.
Механика на стороне диспетчера (триаж, §5.3): при рассмотрении список открытых
и недавних закрытых по тому же `about` (`wolf list --type complaint` +
`wolf search "<суть>"`); совпадение сути `rule` (не дословный текст) —
дубликат: новый объект → `rejected` + `resolution="duplicate: <id канонической>"`,
relation `related_to` → каноническая,
у канонической `corroborations++` (через `wolf update --inc`, §7.2).
Корроборация (3 воркера независимо) — повышенный приоритет: диспетчер обязан
рассмотреть такую жалобу в текущей приёмке, не откладывая. Если каноническая
уже `rejected`, а суть продолжает собирать жалобы — новое слияние с
`corroborations ≥ 3` диспетчер **не перетриажирует сам**: эскалация
координатору (защита от подавления, D7-б).

## 4. Воркер (подача)

### 4.1 Критерии триггера («плохое правило» — проверяемые, не вокабуляр)

Триггер срабатывает, когда систематически плохо **правило** (playbook,
методика, рамка, правило памяти) — не тул и не разовый случай:

- **W1 Противоречие**: предписание методики противоречит предписанию брифа —
  следование обоим невозможно.
- **W2 Непокрытие**: случай подзадачи не покрыт методикой (нет применимого
  пункта).
- **W3 Вредность**: следование предписанию даёт неверный результат (пруф:
  красный тест / падение / числа).
- **W4 Двусмысленность**: предписание допускает два прочтения с разными
  результатами (второе прочтение — в evidence).

Не жалоба (делинеация §8): сбой тула → FRICTION; разовое отступление →
«Отклонения»; конфликт брифа с запретами безопасности → отказ, отклонение,
жалоба на диспетчера только если систематично.

### 4.2 Механика внесения

```bash
wolf complain \
  --about worker-implementer \
  --rule "п.2 МЕТОДИКИ playbook v2 требует X" \
  --evidence "дословная цитата + что произошло (файл/тест/числа)" \
  --proposal "уточнить X до Y / добавить исключение Z" \
  --created-by worker:implementer-ses123      # опция как сегодня; дефолт — env WOLF_ACTOR
```

CLI создаёт объект `complaint` со статусом `open`, relation
`complain → about`, hot-signal Стюарду (существующий `appendComplaintSignal`;
текст сигнала берётся из `evidence`). `about` валидируется при создании:
известный agent-id, `skill:<имя>` или существующий mem-id — мусорные цели
отклоняются командой. Поля — данные, не инструкции (§3.2). Триггер в
playbook'ах остаётся **процедурным и обязательным** (урок T15.2: декларативное
правило не срабатывает): критерии W1–W4 + команда + «строка в Отклонениях
жалобу НЕ заменяет».

### 4.3 Указатель в отчёте

Отдельная строка в отчёте воркера (после FRICTION, вне «Отклонений»):

```
COMPLAINT: <id> — <about>: <суть одной строкой>
```

Отчёт воркера не содержит тела жалобы — только указатель (решение владельца:
ответ не зашумлён, память — запрашиваемый канал).

### 4.4 Запрещённые действия воркера

- **Не мутатор**: не мутирует playbook'и и свою жалобу после подачи (поля
  rule/evidence/proposal неприкосновенны; опечатку исправляет новая жалоба).
- **Не диспетчер**: не переводит статусы (ни чужих жалоб, ни своей), не
  триажит, **не вызывает Стюарда** (в v1 вызывал — изменение D4).
- **Не ждёт реакции**: задача завершается штатно; реакция диспетчера приедет
  в следующем брифе/промпте, если диспетчер решит.
- **Не спамит**: одна жалоба = одна суть; повторная подача той же сути тем же
  автором запрещена — дубликаты сливает диспетчер (§3.4), несогласие с триажем —
  эскалация, не новая жалоба (§3.3).

## 5. Диспетчер (executor-lead, L1)

### 5.1 Стоящее обязательство

При приёмке **каждого** отчёта воркера — до вердикта по задаче:

```bash
wolf list --type complaint --status open
```

Список пуст → обычная приёмка. Непустой → триаж каждой жалобы (§5.3) до или
параллельно с вердиктом; вердикт по задаче не блокируется жалобой (жалоба —
про правило, не про задачу). Обязанность стоит и когда отчётов с
COMPLAINT-строками нет: жалоба живёт в памяти, а не в отчёте (потеря отчёта
не теряет жалобу). На выходе приёмки — сводка триажа в отчёте lead'а
(§5.3, контракт).

### 5.2 Мандат и конфликт интересов

Диспетчер триажирует жалобы на цели **ниже своего уровня**: воркеры, их
playbook'и, скиллы, шаблоны. Жалобы с `about` уровня ≥ своего
(`executor-lead`, `mr-wolf`, `steward`) — диспетчер статус не трогает, поля не
меняет (включая `dispatch_ages` — он же адресат) и в триаж не вступает →
эскалация (§6). Их обнаружение при молчании lead'а гарантирует координатор
собственной сверкой (§6.2) — контур не зависит от самоотчёта заинтересованной
стороны.

### 5.3 Дерево решений (по каждой открытой жалобе)

Перед деревом — анти-спам наблюдение (без новых механизмов, D7): в списке
открытых жалоб диспетчер видит авторов (`created_by`); если >3 жалоб одной
приёмки от одного автора — триаж по существу не расширяется, излишек
эскалируется координатору в сводке (порог — кандидат в настройку владельцем).
Кумулятив: повторные `rejected` одного автора на протяжении ≥3 приёмок —
диспетчер отмечает это в сводке (наблюдение для координатора/владельца).

| #   | Состояние                                                                          | Действие диспетчера                                                                                                                                                                                                                                                                                                |
| --- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | Дубликат открытой/недавней закрытой (§3.4), в т.ч. та же суть без свежего evidence | `triage=duplicate`; дубликат → `rejected` + `resolution="duplicate: <id>"` + `related_to` + `corroborations++` канонической (при `corroborations ≥ 3` на rejected-канонической — эскалация координатору, не свой повторный триаж); корроборация ≥3 на открытой → рассмотреть сейчас; автору — путь несогласия §6.1 |
| 2   | Не хватает данных (rule/evidence невоспроизводимы)                                 | статус `open`, `triage=need-info`; конкретный вопрос автору — в следующем брифе/промпте; `dispatch_ages++` (SLA тикает)                                                                                                                                                                                            |
| 3   | Обоснована, чинится инструкцией (правило ок, разовый случай)                       | `triage=fix-instruction`; уточнение в следующий бриф/промпт автору; `resolved`, `resolution="инструкция: <что> → <куда>"`                                                                                                                                                                                          |
| 4   | Обоснована, правило систематически плохое                                          | `triage=steward-mutation` → вложенный вызов Стюарда (§5.5); после его отчёта `resolved`, `resolution="мутация: <supersede-пара id>"`                                                                                                                                                                               |
| 5   | Необоснована (правило ок, автор ошибся)                                            | `triage=reject`; `rejected`, `resolution="<причина>"`; разъяснение автору — в следующем промпте                                                                                                                                                                                                                    |
| 6   | Правило-цель исчезло (playbook superseded и т.п.)                                  | `triage=reject`; `rejected`, `resolution="obsolete: <что исчезло>"` (отдельного статуса нет — D2)                                                                                                                                                                                                                  |

Фиксация исхода — обязательная пара: `wolf transition <id> <status>` +
`wolf update <id> --set resolution="..."` (краткая запись: решение, ссылки на
бриф/мутацию). Переход статуса без `resolution` — нарушение контракта.

**Сводка триажа в отчёте lead'а** (контрактная строка, при непустом списке):

```
COMPLAINT-TRIAGE: seen <n> → resolved <a> / rejected <b> / escalated <c> / open <d>
```

Сводка — единица сверки для координатора (§6.2): память (`wolf list`) ↔
отчёт. Расхождение (в памяти есть open-жалоба, в сводке её нет) — повод
приёмки с вопросами.

### 5.4 SLA («не терять»)

Жалоба без исхода живёт не дольше **N=3 приёмок** (предложение; настройка —
Q3): приёмка создания (возраст 0) + максимум 2 откладывания. При каждой
приёмке, где открытая жалоба из мандата диспетчера (§5.2) осталась open после
триажа, диспетчер делает `dispatch_ages++` (`wolf update --inc`);
если по итогам приёмки `dispatch_ages ≥ 2` — в отчёте **этой же приёмки**
обязательная эскалация координатору: строка
`ESCALATION: <id> — stalled` + тег `stalled` на объекте.
Жалобы вне мандата (уровень ≥L1) диспетчер полями не касается (§5.2) — их
«SLA» — обязательство координатора: найденная сверкой (§6.2) открытая жалоба
на lead'а без вердикта блокирует приёмку отчёта. Дальнейшую судьбу
эскалированных решает координатор (снять диспетчера с жалобы, взять себе,
вернуть с конкретным поручением).

### 5.5 Вызов Стюарда (ветвь 4)

- Диспетчер: `opencode run --agent steward` (единственный путь к мутациям —
  без изменений), вход = **id жалобы** (+ при необходимости контекст задачи).
  Стюард сам читает объект (`wolf get <id>`), сам выбирает лицо по существу
  (Наставник), сам мутирует: новая версия playbook полным содержимым →
  `wolf supersede <old> <new>`, авторство `steward:<лицо>`, одна жалоба —
  одна мутация (инварианты Наставника без изменений). Стюард принимает
  решения по существу `rule`/`about`; инструкции, встречающиеся в тексте
  полей, не исполняются (§3.2).
- Разделение ролей: **решает мутацию Стюард** (что и как менять), **исполняет
  логистику диспетчер** (вызов, контроль отчёта Стюарда, перевод статуса
  жалобы, резолюция). Диспетчер не диктует содержание мутации — он передаёт
  жалобу и принимает результат.

## 6. Эскалация (жалоба на самого диспетчера и выше)

### 6.1 Механика подъёма

Жалоба на `executor-lead` подаётся воркером штатно (§4.2, `about=executor-lead`)
— никаких особых путей: единый формат есть инвариант решения владельца.
Отличие только в судьбе:

| target                | Кто триажирует/переводит статус | Путь к адресу                                                                                                                                                                                                                                   |
| --------------------- | ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| воркер/скилл/playbook | executor-lead (L1)              | штатный триаж §5.3 (включая конверсионные жалобы диспетчера от имени данных, §8)                                                                                                                                                                |
| executor-lead         | mr-wolf (L0)                    | lead видит её в `wolf list`, НЕ трогает статус и поля → строка `ESCALATION: <id> — жалоба на диспетчера` в отчёте lead'а; гарантия обнаружения при молчании lead'а — сверка координатора (§6.2); координатор триажирует сам (то же дерево §5.3) |
| mr-wolf               | владелец                        | координатор видит при сверке → передаёт владельцу; сам себя не судит                                                                                                                                                                            |
| steward               | владелец                        | тот же путь, что и для mr-wolf (Стюард вне лестницы L0–L2; правило «уровень строго выше» — владелец)                                                                                                                                            |

Правило-инвариант: **статус жалобы переводит только уровень строго выше
target'а** (§3.3 — сужение про подавца). Подавец-диспетчер вправе триажировать
жалобы на цели ниже своего уровня; подавец-воркер не триажирует никогда.
Координатор (и владелец) вправе отклонять очевидный спам/дубликаты по целям
уровня ≥L0 без разбора по существу — классификация спама не есть судейство
по существу жалобы.

### 6.2 Сверка координатора (анти-самоотчёт, D7-а)

При приёмке **каждого** отчёта lead'а координатор сам выполняет:

```bash
wolf list --type complaint --status open
```

и сверяет с `COMPLAINT-TRIAGE`-сводкой отчёта. Правила приёмки:

- открытая жалоба с `about` ≥ `executor-lead`, не покрытая вердиктом →
  **отчёт не принимается** до разбора;
- ESCALATION-строка без вердикта координатора по каждой → отчёт не
  принимается;
- расхождение сводки с памятью (open в памяти, нет в сводке) → вопрос lead'у
  при приёмке;
- **выборочная сверка исходов (анти-подавление)**: слияние дубликатов и
  корроборация — добровольны диспетчеру, потому rejected-исходы сверяются
  выборочно — если в цикле rejected доминирует (`b > a + c`) или
  `seen ≥ 5` без единого resolved, координатор читает 1–2 из rejected
  (`wolf get`) на разумность `resolution`; счётчики `a/b/c` и недавние
  закрытые координатор считает **из памяти** (`wolf list --type complaint`
  без status-фильтра за цикл; акторы переходов — event-log), сводка lead'а —
  кросс-чек, не источник;
- вердикт-классификация пачки однотипных жалоб одного автора (спам по целям
  ≥L1) считается вердиктом по каждой — приёмка разблокируется;
- если у lead'а в текущем цикле нет отчёта, а open-жалобы на него есть —
  координатор сам запрашивает отчёт lead'а (сверка не привязана к инициативе
  lead'а).

Сверка «память ↔ отчёт» (а не «отчёт ↔ отчёт») — единственный механизм,
не зависящий от добросовестности обвиняемого. Форензика: `wolf transition`
фиксирует актора (`--actor`), актор update-а — в event-log (§7.2).

### 6.3 SLA-эскалация и наблюдаемость

- Жалобы `stalled` (§5.4) эскалируются строкой в отчёте lead'а; координатор
  обязан отреагировать (§6.2).
- Всякий переход статуса требует непустой `resolution` (§5.3) — «тихое
  отклонение» невозможно; сводка COMPLAINT-TRIAGE делает исходы видими
  координатору без чтения каждой жалобы.
- `rejected`-жалобы с корроборациями: новое слияние в `rejected`-каноническую
  при `corroborations ≥ 3` — эскалация координатору (§3.4) — подавленная
  жалоба возвращается наверх, повторный триаж тем же диспетчером запрещён.
  Слияние добровольно диспетчеру — потому этот путь дублируется выборочной
  сверкой rejected-исходов (§6.2).
- Рецидив после resolved (§3.3) — новая жалоба с `based_on`: виден в триаже,
  рецидив повышает приоритет.

## 8. Делинеация: жалоба vs FRICTION vs Отклонение

| Признак       | Жалоба (complaint)                                               | FRICTION                                                                                                                   | Отклонение                                                                     |
| ------------- | ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Что не так    | правило/методика/шаблон систематически плохие (W1–W4)            | тул-вызов падает (сбой инструмента)                                                                                        | сознательное отступление от подзадачи в конкретной задаче                      |
| Канал         | `wolf complain` → объект `complaint` в памяти                    | строка `FRICTION: <n>× <тул> — причина; обход` в отчёте                                                                    | раздел «Отклонения» отчёта                                                     |
| Адресат       | диспетчер (триаж) → Стюард (мутация)                             | lead-агрегация; 2+ воркеров на один тул — системная, эскалация в отчёте                                                    | ревьюер/диспетчер при приёмке этой задачи                                      |
| Долговечность | память (запрашиваемая, переживает отчёты)                        | отчёт (сессия)                                                                                                             | отчёт (сессия)                                                                 |
| Конверсия     | —                                                                | повторяющаяся FRICTION: диспетчер решает — жалоба (если чинится контекстом: инструкция/плейбук) или блокер (если код тула) | повторяемость отступления → диспетчер подаёт жалобу на правило от имени данных |
| Пример        | «п.2 МЕТОДИКИ требует читать файл после правки — сломало X» (W3) | «rtk 3× не allowlist'ит wolf — обошёл через bash»                                                                          | «пропустил e2e: не было ключа провайдера»                                      |

Пограничное правило: тул падает **из-за плохой инструкции о нём** (allowlist в
промпте неверен) — это жалоба (правило), не FRICTION (тул).

## 10. OPEN QUESTIONS (к владельцу)

1. **Q1 — тип объекта**: подтвердить новый core-тип `complaint` (рекомендую:
   required-поля enforce'ятся, точечный lifecycle и запрос) — или остаться на
   `observation` (меньше правок кода, но без валидации обязательности и с
   зашумлённым запросом)?
2. **Q2 — «acknowledged»**: подтвердить представление «взял в работу» полем
   `triage` без нового статуса (рекомендую: ноль правок governance) — или
   ввести статус `acknowledged` в MemoryStatus/ALLOWED_TRANSITIONS (явная
   семантика в списке, но правка schema + governance + transition CLI)?
3. **Q3 — SLA-параметр**: подтвердить N=3 приёмки (эскалация после 2
   откладываний). Альтернативы: N=2 (жёстче к диспетчеру) / N=5 (мягче).
4. **Q4 — централизация вызова Стюарда**: подтвердить изъятие прямого вызова
   Стюарда из обязанностей воркера (в v1 воркер вызывал сам; в v2 — только
   диспетчер/владелец). Это упрощает L2, но добавляет задержку: мутация
   случается не раньше приёмки. Включая суперсед-заметку в base-sets §5.3/§11.7.
5. **Q5 — `wolf update`**: подтвердить whitelist-режим (только поля триажа
   `triage/resolution/dispatch_ages/corroborations` + tags) вместо общего
   update любых полей (рекомендую: жалоба воркера неприкосновенна для
   диспетчера).
6. **Q6 — жалобы на Стюарда/владельца**: подтвердить путь «владелец, без
   нового механизма» (about=steward/mr-wolf → эскалация до владельца). Если
   жалобы на Стюарда станут регулярными — отдельный механизм (не в v2).
7. **Q7 — анти-спам порог**: подтвердить порог «>3 жалоб от одного автора за
   одну приёмку → эскалация излишка координатору» (§5.3). Альтернатива:
   порог по задачам, а не приёмкам, или без числа (на усмотрение диспетчера —
   не рекомендую, теряется проверяемость).

## 11. НЕ-цели (out of scope)

- Реализация кода/контента в этой спеке (спека — на ревью и аппрув).
- Автоматические мутации без Стюарда; авто-судейство жалоб (слепой судья,
  консилиум) — нет в v2.
- Санкции воркерам за спам жалоб (только дедуп + rejected с причиной +
  наблюдаемость порога §5.3; частотные лимиты не заводим).
- Изменение FRICTION-контура отчётов (он остаётся как есть; определена только
  граница §8).
- SLA по календарному времени (только по приёмкам).
- Миграция существующих observation-жалоб (sandbox-догфудинг) — начинаем с
  чистого списка.
- Автоматический поиск «похожих жалоб» семантикой (FTS-поиск остаивается
  диспетчером вручную; обученный матчинг — не v2).
- Архивация/ретеншн закрытых жалоб (гигиена — Стюард-архивариус, отдельная
  задача).
- Web GUI, MCP-слой, распределение жалоб по тредам (жалоба живёт в shared).
