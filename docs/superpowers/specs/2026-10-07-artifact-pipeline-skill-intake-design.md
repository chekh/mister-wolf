# Спека: конвейер артефактов (roadmap → requirements → design → plan → test-plan) + подключение скиллов

Дата: 2026-10-07. Базлайн: main `eb3f6e3` (2.14.1, hotfix-цикл опубликован).
Статус: DESIGN APPROVED (дизайн утверждён владельцем в продуктовом диалоге 2026-10-07, 12 вопросов-ответов).
Это последняя спека в старой конвенции `docs/superpowers/specs/`; следующие циклы идут по новому конвейеру (догфуд, §5 блок D).

## 1. Контекст и цель

Скиллы `wolf-brainstorm` и `wolf-plan` порождают два документа-монолита: спеку (47–96K: требования, архитектура, критерии, чек-листы и журнал ревью в одном файле) и план (50–80K). Следствия:

- ревью-линзы читают весь монолит, хотя вопрос каждой линзы узкий;
- владелец не может согласовать технический документ целиком — язык сжатый, со сленгом, термины не из его домена;
- релизный чек-лист и раздел «Доки и сайт» дублируются канонической копипастой в каждом документе;
- исторические планы доходили до 65–80% кода от объёма (analytics-dashboard 3747/4703 строк кода; распределение по файлам см. §3);
- документы-артефакты разбросаны по четырём папкам (`docs/plans/`, `docs/planning/`, `docs/master-plans/`, `docs/superpowers/{specs,plans}/`) без единого реестра.

Цель — разложить конвейер документов на маленькие связанные артефакты с проверкой детерминированными инструментами, закрепить языковую дисциплину по аудиториям и добавить подключение внешних скиллов через контур качества Wolf.

Термины (употребляются по тексту):

- **Артефакт** — markdown-документ конвейера в `docs/dev/`.
- **AC** — acceptance criteria, критерии приёмки требования.
- **Гибрид требований** — формат записи требований: EARS («Когда X — система должна Y») для условного поведения, shall-формулировки для ограничений, Gherkin-сценарии для нетривиальных AC. Инвариант формата — атомарность, ID, проверяемость; конкретный шаблон подчинён читаемости.
- **CR** — change request, append-only запись в журнале изменений requirements.md (прототип — ADR): дата, затронутый REQ/NFR, что/почему, кем утверждено, какие downstream-артефакты перегенерированы. Документ — единственный источник истины, CR — запись намерения.
- **wave-файл** (`docs/dev/wave-<волна>.md`) — волновой артефакт: состав волны, порядок потоков и влитий, канонический релизный чек-лист (единственная копия — планы фич не дублируют).
- **Контракт** — сигнатура, тип, схема данных, формат события, инвариант; в отличие от тела функции, не содержит реализации.
- **Линза** — узкий ревьюер wolf-review, один вопрос — одна пара файлов.
- **Skill intake** — процесс подключения внешнего скилла (поиск → ревью → гейт → установка → регистрация).

## 2. Принципы

- **Артефакт пишется для своего читателя** (расширение решения `mem_20261001_..._0d12c0` «бриф учитывает получателя» на все документы конвейера):
  - `requirements.md` — язык владельца: полные предложения, ноль сленга, термины домена без сокращений, новое понятие объясняется при первом употреблении, смысловое сжатие запрещено. Тест качества: владелец может пересказать каждое требование своими словами; не может — дефект требования, а не читателя.
  - `design.md`, `plan.md`, `test-plan.md` — технический язык допустим; глоссарий в начале design.md, термин вводится до использования.
- **Контракты, не тела реализации.** design.md содержит контракты кодом (типы, схемы, форматы событий; блоки ≤ 10 строк) и ADR-карточки (контекст → решение → последствия). Псевдокод и алгоритмы в design.md разрешены — когда точное описание логики делает дизайн однозначнее прозы. Запрещена копипаста реализации продукта в design.md и plan.md. Урок старых планов: ошибка была не в наличии кода, а в наличии готовой реализации в документе планирования.
- **AC — единый источник.** Критерии приёмки пишутся один раз в requirements.md (ID формата `REQ-NN`), из них выводятся сценарии test-plan.md и критерии приёмки волны. Не писать трижды.
- **Без лимитов длины прозы.** Атомарность = «одна запись — одно требование», но запись несёт столько контекста, сколько нужно для однозначного понимания. Ясность — цель, длина — не метрика.
- **Детерминизм через тулинг, не через дисциплину.** Папки, шаблоны и индексы создают команды Wolf (`scaffold`/`sync`/`doctor`), скиллы их вызывают, а не создают файлы вручную. Уникальность и консистентность гарантирует машина; линзы ловят смысл, скрипты — механику.
- **Ноль новых CLI-команд.** Только расширения существующих поверхностей (канон диеты 2.13, правило P4 «диета не расползается»).
- **Гейт владельца на мутациях поведения.** Владелец утверждает requirements.md (единственный документ, который он читает целиком) и подключение каждого внешнего скилла. Технические артефакты ревьюят линзы, владельцу — выжимка на визу. Исключение: **ADR-карточки design.md — продуктовые выборы, не техника** — требуют визы владельца (прецедент: немедленный пилот архивариуса, отменён как самодеятельность).
- **Масштаб артефакта = масштаб изменения.** Полный профиль папки фичи (4 артефакта) — для фич; fix-профиль (requirements.md, где журнал изменений и есть содержание + plan.md) — для фиксов и мелочей; полный цикл не навязывается хотфиксу.
- **Эволюция зафиксирована.** Правка approved-артефакта идёт через CR-запись и сбрасывает статусы downstream-артефактов (правило «правка артефакта = переревью по входящим рёбрам», память 0908, теперь с механикой).
- **Перемещение, не копирование.** Пункт роадмапа живёт ровно в одном файле; при переходе backlog → волна он перемещается. Дубли между файлами — finding линта.

## 4. Состав (четыре блока)

### 4.1. Анатомия requirements.md (индустриальные прототипы: Volere, ISO 29148, XP/3C, EARS, MoSCoW, Amazon Working Backwards, Spec Kit)

Структура документа — 7 секций:

```markdown
# <Название фичи> — функциональные требования

1. Контекст и проблема — зачем, прозой, бизнес-языком; метрика успеха
   (дух Amazon PR-FAQ)
2. Область — что входит; НЕ входит (не-цели уровня требований)
3. Глоссарий — бизнес-термины фичи, если появились новые
4. Функциональные требования — записи REQ-NN (анатомия ниже)
5. Нефункциональные (NFR-NN) — производительность, безопасность, совместимость;
   каждая с измеримым критерием
6. Ограничения и допущения — что считаем данным
7. Журнал изменений (CR) — append-only (см. термины §1)
```

Анатомия записи требования:

```markdown
### REQ-07 — <Название>

- История: Как <роль>, я хочу <возможность>, чтобы <выгода>. ← XP/3C
- Требование: Когда <условие>, система должна <поведение>. ← гибрид EARS
- Обоснование: <зачем это бизнесу — словами владельца> ← Volere rationale
- AC: <измеримый критерий; нетривиальные — Given/When/Then> ← fit criterion
- Приоритет: Must | Should | Could ← MoSCoW
- Источник: <диалог 2026-10-07 / жалоба mem-… / ревью-линза> ← Volere origin
```

Критерии готовности записи (гейт линзы полноты; часть проверяет линт): одно требование — одна запись; есть история И формальная запись; есть AC (REQ без AC — finding); есть источник; неопределённость помечена `[НЕОПРЕДЕЛЕНО: вопрос]`, не сжата (прототип Spec Kit `[NEEDS CLARIFICATION]`); владелец пересказывает своими словами. Шаблон scaffold (A1) воплощает эту анатомию дословно. Выброшено из прототипов осознанно: satisfaction-оценки Volere (нечем собирать), формальные матрицы трассировки ISO (у нас трассировка — рёбра и линт), исполняемый Gherkin (дорог в поддержке).

### Блок A — Тулинг (детерминированный слой)

- **A1. `wolf scaffold artifact <slug>`** — новый kind в `SCAFFOLD_KINDS`. Полный профиль: `docs/dev/<дата>-<slug>/` (дата = сегодня) с четырьмя шаблонами — `requirements.md` (дословно анатомия §4.1), `design.md`, `plan.md`, `test-plan.md`; fix-профиль: `--fix` — только `requirements.md` (CR-журнал как содержание) + `plan.md`. Каждый с YAML-front-matter `slug`, `title`, `status: draft` (значения draft/review/approved per-артефакт, §5), `created`. Отказ при существующем слаге (уникальность имён — машина, не дисциплина). Команда остаётся hidden.
- **A2. Индекс в `wolf sync`.** Sync дополнительно перегенерирует `docs/dev/INDEX.md` (таблица: слаг, дата, title, status из front-matter, профиль папки). Идемпотентность — по прецеденту штампов: повторный sync без изменений не пишет. `roadmap/_index.md` вырезан из состава решением ревью 2026-10-07 (список из 3–5 самоописательных файлов — `ls` отвечает на тот же вопрос). Оговорка: если INDEX в догфуде окажется шумом — режется без жалобы.
- **A3. Линт в `wolf doctor`** — новая секция «Артефакты» (появляется при наличии `docs/dev/`):
  - уникальность `REQ-NN`/`NFR-NN` внутри папки; битые ссылки `REQ-NN` → раздел design.md;
  - REQ без строки `AC:` и без `Источник:`; `[НЕОПРЕДЕЛЕНО: …]` в approved-документе;
  - CR-запись без отметки о перегенерации downstream;
  - механические дубли: совпадающие нормализованные тексты требований в одной папке и один пункт в двух файлах роадмапа;
  - согласованность roadmap ↔ папки: волна со статусом «выпущена» ↔ существует папка фичи; папка в `docs/dev/` ↔ есть строка в файле волны роадмапа;
  - готовность фичи: все задачи plan.md `[x]` + статус approved → подсказка «готова к релизу»; частичный прогресс — подсказка «в работе»;
  - скиллы-призраки: `.opencode/skills/<имя>/` без тул-объекта в памяти (зеркало призраков AGENTS.md из 2.14; исключение — скиллы базового набора, они сеются из шаблонов и регистрируются базлайн-списком).
- **A4. Части и индексы частей.** Если design.md/plan.md доросли (ориентир обзора ~5–15K), они делятся на подпапки `design/A-<имя>.md` с генерируемым `_index.md`; линзы ревьюят файл, а не папку. Механика деления — ручная (LLM), индекс — sync.

### Блок B — Скиллы конвейера

- **B1. `wolf-design` (новый скилл).** Вход: `requirements.md` (+ кодовая база). Выход: `design.md` — компоненты и ответственность, контракты кодом, псевдокод алгоритмов, ADR-карточки ключевых решений, глоссарий. Запрещена копипаста реализации. Исполняется чистым воркером (новых агентов нет — скилл = промпт, диспетчеризация не меняется). Владение NFR: записи `NFR-NN` живут в requirements.md (§4.1, секция 5); design на них ссылается и добавляет технические бюджеты/решения, собственных ID-записей не заводит — двойное владение не допускается.
- **B2. `wolf-brainstorm` v2.** Выход меняется: вместо спеки-монолита — `requirements.md` по анатомии §4.1 (структура 7 секций, записи REQ/NFR с ID, история + формальная запись + AC + обоснование + приоритет + источник; неопределённость — маркером `[НЕОПРЕДЕЛЕНО]`). Второй режим — roadmap-триаж: диалог с владельцем → вердикты «волна N / бэклог / отклонено + причина» → запись в `docs/dev/roadmap/` (файл волны, `backlog.md`, `rejected.md`; пункт перемещается, не копируется).
- **B3. `wolf-plan` v2.** Вход: `requirements.md` + `design.md`. Выход: `plan.md` — задачи: цель + ссылка на §design + file:line базлайна; без копипасты реализации и без переопределения контрактов (единственный источник контрактов — design). План остаётся обзорным: крупные детали — только ссылками на design, не пересказом. Каждая задача — чекбокс `- [ ]`: исполнитель обновляет на `[x]` в конце задачи вместе со строкой «сделано → коммит»; чекбокс — истина завершённости для восстановления прерванной работы, вердикты и контекст живут в памяти Wolf.
- **B4. `wolf-testplan` (новый скилл).** Вход: `requirements.md` + `design.md`. Выход: `test-plan.md` — сценарий на каждый REQ-NN в формате Given/When/Then + маппинг на e2e/юнит-файлы. Отдельный от планирования скилл: ось специализации скиллов = тип артефакта, один скилл — одна работа (как линзы).
- **B5. `wolf-review` v2 — линзы по парам файлов.** Полнота → requirements.md, включая критерии готовности записей §4.1 (атомарность, недвусмысленность, проверяемость — семантика; механику ловит линт); консистентность → design.md (включая соответствие базлайну кода); соответствие → plan.md против design (включая сверку чекбоксов с отчётами при приёмке волны); покрытие AC → test-plan.md против requirements. Гейты: владелец аппрувит requirements до запуска технических ступеней; **ADR-карточки design.md — владельцу на визу отдельно**; следующие ступени генерируются только после аппрува предыдущей (Kiro-паттерн гейта).
- **B6. `wolf-sdd`/`wolf-execute`** — потребляют plan.md; правка косметическая (ссылки на test-plan при валидации волны). Семантика фиксируется: wolf-sdd — основной диспетчерский путь; wolf-execute — FLAT-fallback для агентов без диспетчеризации, mr-wolf его не использует (правило роли `mem_20260903_..._e95317`). Вопрос о судьбе wolf-execute как скилла — в backlog роадмапа, вне этой спеки.
- **B7. Переработка дисциплинарной оси** (принцип: «берём, но перерабатываем», не «берём целиком»). Seed двух новых скиллов — глубокой адаптацией: `receiving-code-review` (фидбек владельца = высший приоритет лестницы; жалобы идут по протоколу жалоб, не «внедри совет»; уроки фидбека → память) и `writing-skills` (наш жизненный цикл скиллов: templates/base → рендер со штампами → sync; таблица трассировки адаптации — обязательный раздел; граница с intake). Ревизия существующих под конвейер и опыт памяти: TDT — сценарии test-plan.md = заготовки КРАСНОЙ фазы; verification — верификация = условие переворота чекбокса plan.md; worktrees — вобрать агрегат Стюарда по параллельным воркерам; finishing — ревизия под trunk-based. Паттерн трассировки (источник → судьба пункта → почему) обязателен для каждого адаптированного скилла.
- **Ось специализации.** Шесть скиллов конвейера + intake-обёртка покрывают существующие типы артефактов; новый специализированный скилл заводится при появлении повторяющегося типа работы, не заранее (YAGNI). Две оси скиллов Wolf: артефактная (новый тип артефакта → скилл) и дисциплинарная (повторяющийся срыв дисциплины → скилл-принуждение; детектор — жалобы-контур). Дефолт-набор — 18 скиллов (§4.1 не касается; таблица в гайде); security — строго опциональная линза, не дефолт; capability-скиллы мира (anthropics/vercel и др.) — через intake, не в дефолт.

### Блок C — Skill intake (подключение внешних скиллов)

- **C1. Скилл-обёртка процесса** (единственный новый скилл блока; рабочее имя `wolf-skill-intake`): протокол поиска (`npx skills find`, leaderboard skills.sh; критерии качества: ≥1K установок, репутация источника, звёзды репо), подготовка ревью-верdict'а, регистрация после аппрува владельца.
- **C2. Ревью-линза кандидата**: воркер читает SKILL.md: опасные инструкции (`rm -rf`, `curl | sh`, секреты), конфликты с рамкой/правилами проекта (по памяти Wolf), качество промпта. Вердикт — владельцу.
- **C3. Гейт владельца**: без явного «да» установка не идёт (чужой скилл меняет поведение агентов — вес мутации лица). Откат: `npx skills remove` + `wolf supersede`/archive тул-объекта.
- **C4. Регистрация**: `wolf add --type tool` с extra `owner_skill`, `version`, `source` (URL/репозиторий) — тип и поля существуют; ребро на проект/поток по необходимости.
- **C5. Наблюдаемость** — уже существует, проверяется приёмкой: телеметрия `skill-invocations.jsonl`, жалобы `skill:<имя>`, секция линта A3 (призраки).

### Блок D — Догфуд и миграция

- **D0. Волновой артефакт.** Волна получает **`docs/dev/wave-<волна>.md`** (наследие файловой конвенции `wave-2.14-…-plan.md`, плоско рядом с фичевыми папками; зеркально `roadmap/<волна>.md`: триаж → исполнение): состав волны, порядок потоков и влитий, канонический релизный чек-лист — единственная копия, планы фич ссылаются, не дублируют. Первым wave-файлом становится план этой самой волны.
- **D1. Догфуд на собственной волне.** План ревизии этой спеки (wolf-plan) исполняется по старой схеме, но все артефакты планирования волны после слияния блока A/B структурируются под новую схему; следующий после этой волны цикл идёт по конвейеру полностью (его requirements.md — первый артефакт `wolf scaffold artifact`).
- **D1.5. review.md в git.** Каждая папка фичи получает `review.md` — append-only журнал вердиктов линз и гейтов владельца (строка на линзо-итерацию: линза/дата/вердикт/ключевые находки/что исправлено). Назначение: чистый агент без памяти Wolf отвечает на вопрос «почему так, а не иначе»; детали вердиктов — в памяти Wolf, в git — свод.
- **D1.6. Метрика веса цикла.** После первого полного догфуда — замер в память Wolf: реальное время цикла (requirements → релиз) против монолитной эпохи; при деградации — резать помеченных кандидатов на упрощение (INDEX.md, объём анатомии записи) без новой спеки.
- **D2. Миграция роадмапа**: свернуть `docs/superpowers/plans/2026-10-02-product-roadmap-2.15-plus.md` (64K, untracked) + действующие вердикты треда `b0368a` в `docs/dev/roadmap/` (файлы волн + backlog + rejected).
- **D3. Заморозка старых папок**: `docs/plans/`, `docs/planning/`, `docs/master-plans/`, `docs/superpowers/{specs,plans}/` не переносятся (на них ссылается память Wolf); в README каждой — заглушка «архив, новые артефакты в docs/dev/». Заглушки — единственные правки в этих папках.
- **D4. Документация продукта**: гайд по конвейеру (docs/guide/), обновление README/base-set-документации, страница сайта при релизе.

## 9. Риски

- **Расползание диеты**: блоки тянут «заодно» рефакторинг скиллов вне скоупа → правило P4; кандидаты — в открытые вопросы.
- **Скиллы v2 меняют привычный цикл команд**: воркеры/лиды ошибаются в новых входах → guard-тесты рамок (§6.4) + догфуд до релиза (D1).
- **Линт хрупок к формату** (front-matter, вариации Markdown) → tolerant-парсинг по прецеденту readJsonl; линт ругается, но не блокирует sync.
- **Внешний CLI skills.sh изменится** → скилл-обёртка изолирует вызовы; при поломке — деградация к ручному поиску, контур (линза, гейт, регистрация) не страдает.
- **Двойная конвенция во время перехода** (старые спеки/планы рядом с docs/dev) → заморозка заглушками (D3) + правило «новое — только в docs/dev/» в гайде.
- **Языковая дисциплина не проверяется скриптом** → тест «владелец пересказывает требование» встроен в гейт B5; жалоба на язык требования — через контур поправок.
- **Вес процесса съест выигрыш** (5 файлов на фичу + wave-файл + CR + чекбоксы) → противоядия встроены: fix-профиль, ось «масштаб артефакта = масштаб изменения», метрика веса цикла после первого догфуда (D1.6) с предрешёнными кандидатами на вырезание.
- **Двойная запись прогресса** (чекбоксы plan.md vs отчёты в памяти Wolf) разъедется → контракт: чекбокс = истина завершённости, обновляет исполнитель как часть DoD; линза «соответствие» сверяет при приёмке волны.
- **review.md разрастается** → формат «строка на линзо-итерацию», детали — в память Wolf.
