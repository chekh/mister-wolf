## 1. Контекст и цель

Жалобный контур v2 жив (resolved за минуты), но разомкнут: исход жалобы не фиксируется связью, «resolved → мутация playbook» — на усмотрении разрешающего, дефолтного следующего шага нет. Уроки пишет исполнитель-лид (98 в Tender), но контур агрегации не существует: Стюард не вызывается (0,05%), уроки копятся без затухания. Мультипроектность лежит в реестре-«телефонной книге» без команды просмотра, гигиены песочниц и детекта призраков. Фундаментальный дефект целостности: коллизия детерминированного id при add молча перезаписывает объект без event-следа.

Цель 2.14 — **замкнуть контур поправок (жалоба → исход → мутация лица; уроки → агрегат → затухание класса) и сделать перенос памяти формулой git, закрыв дефект целостности add**.

## 2. Принципы

- P1 **Данные неприкосновенны.** Guard отказывает, а не перезаписывает; агрегация архивирует (объект остаётся), не удаляет; любое перезаписывающее save оставляет event-след.
- P2 **Дословность диалога.** Т5/Т6 согласованы дословно; отклонения — только по формату носителя (не по функции), каждое помечено в тексте.
- P3 **Механизмы переиспользуются.** Вызов Стюарда един с жалобным (сигнал + строка состояния + вложенный `opencode run --agent steward`); двухшаговость — по прецеденту migrate (предложение → подтверждение применением); компенсирующие записи — по прецеденту relation remove.
- P4 **Состав не расширяется.** Вне блоков A–E — только открытые вопросы; экспорт/импорт архивом, глобальная память, веб-интерфейс — отклонено владельцем.

## 5. Блок A — Целостность

### 5.1 Guard коллизии id (P0, жалоба)

В `addMemoryObject` после генерации id и **внутри существующего lock** (`add-memory-object.ts:76-148`): `store.get(object.id)` — если объект существует, `UserFacingError` с подсказкой (формат — прецедент `getDeclaration`):

```
Memory object "<id>" already exists (same title produced same id).
Use: wolf edit <id> (правка) | wolf supersede <id> <new-id> (смена) | другой --title.
```

Отказ до `store.save` — файл не тронут, count объектов неизменен. Проверка на `get` — один locate-обход (add не hot-path; прецедент производительности волны 2.12 не задет).

### 5.2 Event на любое перезаписывающее save

`MarkdownMemoryStore.save` получает опциональную зависимость `overwriteLog?: Pick<EventLog, 'append'>`; контейнер (`createCliContainer`) связывает store и log одной строкой. Если целевой файл существует, **до записи** пишется событие:

```json
{
  "type": "memory.overwritten",
  "payload": { "memory_id": "<id>", "prev_title": "<обрезка 120>", "prev_status": "<статус>" }
}
```

Тип добавляется в enum `MemoryEventSchema` (аддитивно, инвариант (i) 2.13). Это закрывает перезапись на уровне хранилища — включая любые будущие пути, минуя «забывчивые» use-cases. Guard §5.1 делает этот путь для add недостижимым; событие — страховка контракта «перепись всегда со следом». Событие пишется **до** записи: крах между событием и записью оставляет след намеренной перезаписи (для аудита безопаснее молчания); обратный порядок терял бы след при краше после записи.

## 6. Блок B — Контур поправок

### 6.1 Классификация жалоб: техническая / поведенческая

Поле `kind: 'technical' | 'behavioral'` в декларации complaint (опциональное; старые жалобы читаются без него, вывод «—»). Дефолт-эвристика в `memory-complain.ts`: `about` ∈ `BASE_AGENT_IDS` или `skill:*` → `behavioral`; mem-id → `technical`. Флаг `--kind` переопределяет (владелец/лид всегда прав). Минимально: одно поле + три строки эвристики, без отдельного механизма классификации.

### 6.2 Связь «жалоба → исход»

Пара предикатов `outcome` / `outcome_of` (по слоту в enum + строка в `INVERSE`; прецедент пары `complain`/`complained_by`). Исход фиксируется исполнителем, закрывающим жалобу (после resolved/completed):

| Исход      | Запись                                                                                       |
| ---------- | -------------------------------------------------------------------------------------------- |
| Закреплено | `<artifact-id> -outcome_of-> <complaint-id>` (артефакт: rule/lesson/playbook-объект/мутация) |
| Отклонено  | `<complaint-id> -outcome-> rejected` (литерал; дублирует статус, но даёт читаемый граф)      |
| Отложено   | `<complaint-id> -outcome-> deferred` (литерал)                                               |

Пишется существующим `wolf relation add`; читается `wolf relation list --of <complaint-id>` (обе стороны рёбра — `memory-relation.ts:43`). Литеральные токены допустимы: `object` — свободная строка (прецедент agent-id в `complain`). Дисциплина — протокольная (рамка, §6.4), не кодовая.

### 6.3 Эскалация поведенческих жалоб

Триаж существующего дерева (`executor-lead.md:69-84`) дополняется одной строкой: поведенческая жалоба (kind=behavioral) после resolved с исходом «закреплено» идёт ветвью steward-mutation — вложенный вызов Стюарда с входом = id жалобы и id артефакта. Технические — существующим порядком (файл-очередь `dispatch_ages`, SLA). Автоспавна нет: вызов делает диспетчер по инструкции (механизм един с жалобным — P3).

### 6.4 Видимость исходов

`recap` дополняется строкой блока «Контур поправок»: `жалоб без исхода: K` — resolved-жалобы без исходящего `outcome`-ребра. Счётчик из relation-лога + объектов; детектор — одна фильтрация, без индексов.

## 7. Блок C — Стюард-агрегатор

### 7.1 Триггеры (событийные, механизм един с жалобным — Т5 дословно)

1. **Завершение цикла Волфа** — инструкция в рамке координатора (`mr-wolf.md`, раздел приёмки): после приёмки отчётов цикла выполнить `wolf recap`; при непустой строке неагрегированных уроков (§7.4) — вложенный вызов Стюарда. Координатор обнаруживает, Стюард агрегирует, владелец подтверждает.
2. **Старт новой сессии/треда** — строка в `call`-выводе (banner) при наличии зрелых неагрегированных уроков (§7.2): сессия/владелец видит и вызывает Стюарда.

Дополнительный hot-сигнал в телеметрию не вводится: строка состояния в recap/call + инструкция рамки покрывают оба триггера той же механикой, что и жалобный (строка состояния → вложенный вызов).

### 7.2 Детектор неагрегированных уроков

Неагрегированный = lesson в `active` без **живого** входящего ребра `aggregated_in` (§7.3): ребро учитывается, только если агрегат-субъект находится в `proposed` или `active`; рёбра от `rejected`/`archived` агрегатов детектор игнорирует — отклонённый кластер возвращается в строку «неагрегированных» и виден для повторного вызова Стюарда (отказ действительно бесплатен, §7.3/Р2). «Зрелые» (порог показа строки): count ≥ 3 **или** старейшему ≥ 7 дней. Константы в коде (не конфиг — YAGNI). Одна функция-детектор, переиспользуется в recap и call.

### 7.3 Агрегация: двухшаговость «было → стало → почему» (Т5 дословно)

**Шаг 1 — Стюард готовит** (вложенный вызов, вход = проект):

- выбирает кластер зрелых уроков по теме/классу (LLM-решение агента; подсказка CLI — детектор §7.2 и `list --type lesson`);
- создаёт обобщённый lesson: `review_state: proposed` (дефолт agent-актора, `add-memory-object.ts:88`), тело по контракту: `## Было` (N исходных, id + суть по строке) / `## Стало` (обобщение ИЛИ пункт инструктажа для лица ИЛИ предложение правила) / `## Почему` (паттерн класса);
- пишет рёбра `<aggregate-id> -aggregates-> <source-id>` на каждый исходник (пара предикатов `aggregates`/`aggregated_in` — тот же слот enum, что §6.2);
- при мутации лица: готовит новую версию playbook-объекта (proposed) с ребром `outcome_of` к жалобе/урокам-причинам — применение владельцем через `wolf supersede` (рамка Стюарда: мутации через память, `steward.md:59-60`).

**Шаг 2 — применение по подтверждению владельца.** Очередь подтверждения = память Wolf (P2-отклонение по формату: не отдельный файл-очередь, а proposed-объекты — `list --type lesson --status proposed` уже показывает очередь; функция та же). Команда-применение:

```
wolf aggregate apply <aggregate-id>   # plumbing, --hidden (прецедент think/update)
```

Атомарно (под lock): aggregate `proposed → active`, все исходники по рёбрам `aggregates` → `archived` (погашение доставки — §3.3), событие `memory.aggregated` `{aggregate_id, source_ids[]}`. FS не транзакционен: при частичном сбое повторный `apply` **дозавершает** оставшиеся исходники (идемпотентность по исходникам: уже archived пропускаются, отчёт each-run); полный no-op — только когда агрегат active и все исходники archived. Отказ = `wolf transition <aggregate-id> rejected` — исходники остаются active, их рёбра `aggregated_in` перестают учитываться детектором (§7.2), кластер снова виден как неагрегированный (ложные кластеры бесплатны). Мутация лица и предложение правила применяются владельцем существующими командами (`supersede` / `add --type rule --created-by user:*`) — автоприменения мутаций нет (P4, бриф «что НЕ делаем»). Ничего из предложенного не блокирует конвейер: proposed-агрегаты и строки-индикаторы не влияют на доставку и работу сессий (критерий линзы безопасности).

**Перераспределение, не надстройка** (Т5 дословно): агрегат заменяет исходники в доставке (archive гасит доставку исходников, active агрегат доставляется по их trigger_keywords — Стюард переносит ключевые триггеры исходников в тело агрегата на шаге 1); пункт инструктажа в лице лида заменяет повторы уроков в брифах. Двойная доставка исключена транзакционностью apply (риск Р1, §14).

### 7.4 Видимость и метрика затухания

- Строка recap/call: `неагрегированных уроков: N (зрелых: M) — вызовите Стюарда: opencode run --agent steward`.
- Строка recap: `предложенных агрегатов: P — wolf aggregate apply <id> для подтверждения`.
- **Метрика Т5** (снижение новых уроков/жалоб того же класса после агрегации) в `analytics --view steward`: таблица на каждый active-агрегат: `агрегат | исходников | новых уроков того же класса 7д до / 7д после | жалоб того класса до / после`. **Класс** = множество тегов (теги агрегата ∪ теги исходников); запись «того же класса» = имеет ≥1 общий тег с классом; считаются события `memory.added` (lesson/complaint) относительно даты `memory.aggregated`. Ограничение честно фиксируется: теги свободные, кластер — эвристика (§14, Р3).

## 8. Блок D — Перенос и реестр (Т6)

### 8.1 `wolf projects` (список + статистика)

### 8.2 Гигиена реестра

- **Песочницы**: doctor классифицирует записи под `os.tmpdir()` (macOS `/var/folders/…`) как `sandbox` и чистит тем же механизмом, что `missing` (`doctor.ts:36-40`), с пометкой в отчёте. ## 11. Критерии приёмки

### 11.1 Блок A

- e2e: `add --type decision` с дублирующимся title дважды (в пределах мс-окна идентификатора — фиксированный clock фикстуры) → вторая команда exit ≠ 0 с подсказкой edit/supersede/title; count объектов == 1; файл неизменен; events — ровно один `memory.added`.
- юнит: `save` поверх существующего файла пишет `memory.overwritten` с `prev_title` до записи (фикстура существующего объекта); новый объект — событие не пишется.
- guard-тест: длинные title с общими первыми 40 символами (slug-склейка) дают отказ, не перезапись.

### 11.2 Блок B

- `complain --about executor-lead …` → kind=behavioral по умолчанию; `--kind technical` переопределяет; у старой жалобы без kind вывод «—» (фикстура).
- `relation add <rule-id> outcome_of <complaint-id>` → `relation list --of <complaint-id>` показывает обе стороны; литерал `rejected` принимается схемой.
- recap на фикстуре с resolved-жалобой без рёбер исхода показывает `жалоб без исхода: 1`; после записи исхода — 0.

### 11.3 Блок C

- Сценарий e2e (скрипт-фикстура, роль Стюарда — оператор теста): 3 active lessons с общим тегом → add proposed-агрегат + рёбра `aggregates` → recap показывает `предложенных агрегатов: 1` → `wolf aggregate apply` → агрегат active, исходники archived, events содержит `memory.aggregated` с `source_ids` из 3 id; повторный apply — no-op с отчётом; фикстура частичного сбоя (1 исходник вновь active) — apply дозавершает только его.
- Доставка после apply: call с topic по trigger_keywords доставляет агрегат и не доставляет ни один исходник (e2e).
- Отказ: `transition <agg> rejected` → исходники остаются active (e2e).
- recap/call: строка неагрегированных появляется при 3 active lessons без `aggregated_in` и не появляется при 2 свежих; аналитика `--view steward` содержит таблицу агрегата с нулевыми «после» на свежих данных и корректными «до».
- Рамки: `mr-wolf.md` содержит инструкцию циклового вызова; `executor-lead.md` — строку эскалации kind=behavioral (guard-тест базового набора — текст рамок содержит маркеры).

### 11.4 Блок D

- `wolf projects` на фикстуре реестра (2 живых + 1 missing): таблица 3 строки с вычисленными именем/версией/активностью/размером, сводка; missing помечен.
- doctor: запись в tmpdir → `sandbox — pruned` в отчёте; cwd с AGENTS.md-маркером без `.wolf/memory` → issue «памяти нет»; cwd с памятью без маркера → issue «не подключён».
- Самолечение: команда в незарегистрированном cwd с `.wolf/memory` добавляет запись; повторная команда не переписывает файл (mtime неизменен).
- `npm run check` зелёный; docs:build зелёный; `prettier --check` на изменённых доках зелёный.
