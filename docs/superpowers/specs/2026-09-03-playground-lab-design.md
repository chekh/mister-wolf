# Дизайн: полигон испытаний `playground-lab/`

- Дата: 2026-09-03
- Статус: утверждён владельцем (диалог wolf-brainstorm, 2026-09-03)
- Предшественники: `scenario-lab/` (методика кампании концепта, поглощается), `playground/` (расходная pristine-площадка, существует)

## 1. Цели и границы

Проблема: знание о тестировании размазано по 4 местам — реестр находок
`.wolf/orchestration/playground-issues.md`, сырой протокол
`playground/MANUAL-NOTES.md`, сценарии зашиты в `playground/README-PLAYGROUND.md`,
уроки в main-памяти Wolf. Сущности «эксперимент» нет; часть материала гибнет
при reset площадки.

Решение — три зоны с ясными ролями:

- **`playground/` — расходный материал.** Удаляется, пересоздаётся,
  дублируется без потерь. Никаких артефактов опытов внутри. Всё, что должно
  выжить, переносится в лабораторию сразу по завершении эксперимента.
- **`playground-lab/` — постоянная зона проекта** (main-репо, git): методика,
  карты экспериментов, реестры, измерения, скрипты.
- **Память Wolf (main) — индекс состояния** по аналогии с document-ref:
  активный эксперимент, статусы, уроки — без переноса протоколов в память.

Не входит в scope: спавнер мультиинстансов и автоматизация A/B (управление
площадкой вручную, как решено с владельцем; скрипты быстрой очистки/восстановления —
существующий reset + новая проверка pristine).

## 2. Структура каталога

```
playground-lab/
  README.md              # методика полигона: сущности, жизненный цикл, границы
  templates/
    experiment-card.md   # шаблон карты эксперимента
  experiments/           # по одной карте на эксперимент: YYYY-MM-DD-<slug>.md
  registry/
    findings.md          # реестр находок (переезд playground-issues.md)
    scenarios.md         # библиотека сценариев (переезд сценариев 1–7)
  measurements/          # сырые данные измерений, подкаталог на эксперимент
  archive/
    scenario-lab/        # поглощённая кампания разработки концепта (см. §7)
  scripts/
    verify-pristine.sh   # проверка, что площадка чистая (нужен ли reset)
```

Намеренно не заводится (YAGNI, пересмотреть при боли): `vocabularies/`
(словари статусов живут в README), `data/*.jsonl` (реестры — человекочитаемый
md), `generated/` (агрегаты вручную), собственный SKILL.md (методика в README).

## 3. Сущности и жизненный цикл

### Эксперимент (карта, `experiments/YYYY-MM-DD-<slug>.md`)

Поля карты (шаблон в `templates/experiment-card.md`):

- `id`: `EXP-ГГГГММДД-<slug>`
- `гипотеза` — одно проверяемое утверждение
- `сетап` — вариант(ы) инстанса площадки; для сравнительных опытов — явные
  варианты (например, `variant-wolf` vs `variant-baseline`: два одинаковых
  проекта с разными агентами)
- `метод измерения` — какие метрики и как снимаются (весовые токены по
  правилу mem_20260824__d072b4: input + 0.1×cache_read + 5×output; время;
  число итераций/правок)
- `сценарии` — ссылки на карты из `registry/scenarios.md`
- `протокол` — ход прогона и наблюдения (в карте или `measurements/<id>/`)
- `находки` — F-id из реестра
- `вердикт` — подтверждена/опровергнута + следствия

Статусы: `planned → running → analyzed → concluded`.

Заимствовано из схем scenario-lab: структурированные поля ожидаемого
поведения (`expected_visible_behavior`), конфигурации Wolf
(`wolf_configuration`), артефактов (`artifacts`: inputs/outputs/lifecycle) —
в облегчённой md-форме, без YAML-канцелярита, пока не понадобится валидатор.

### Находка (`registry/findings.md`)

Формат действующего реестра сохраняется: таблица
`ID | Дата | Сценарий | Тип | Описание | Статус`, статусы
`open → in-brief → fixed / rejected / documented`. F-нумерация продолжается
(F1–F16 перенесены как есть).

### Сценарий (`registry/scenarios.md`)

Переиспользуемая карта прогона: шаги, чек-лист проверки, ожидания.
Начальное наполнение — сценарии 1–7 из `playground/README-PLAYGROUND.md`.

### Измерение (`measurements/<exp-id>/`)

Сырые данные: логи прогонов, счётчики токенов, тайминги. Выжимка с
интерпретацией — в карту эксперимента; сырьё не редактируется.

## 4. Граница с памятью Wolf (гибрид «индексируем, не переносим»)

- Старт эксперимента → `wolf add --type experiment`: гипотеза одной строкой,
  путь к карте, статус. `wolf brief` показывает активный опыт.
- Смена статуса → `wolf transition` соответствующего объекта.
- Завершение → уроки (`--type lesson`) и решения (`--type decision`) в память
  с тегом `playground`; карта остаётся материалом в git.
- Находки: состояние ведётся в реестре-файле; в память уходят только
  требующие действия владельца (blocker/open-question) — как в текущей практике.

## 5. Скрипты и шум снапшота

- `scripts/playground-reset.sh` (main-репо) остаётся единственным способом
  пересоздания площадки. Дополнения:
  - исключить из снапшота `docs/site/public` (тяжёлые ассеты витрины ~4.1M —
    шум для pristine-площадки);
  - после reset переживают только `README-PLAYGROUND.md` (как сейчас) —
    поэтому сырые протоколы из площадки переносятся в лабораторию до reset.
- Новый `playground-lab/scripts/verify-pristine.sh`: проверяет признаки
  чистоты (нет `.wolf/`, нет `.opencode/`, чистый git площадки) и печатает,
  нужен ли reset. Используется перед каждым экспериментом.
- `docs/site` в main-репо не переносится и не реорганизуется: это VitePress-корень
  (`docs:dev/build/preview` в package.json), разделение «публичная EN-витрина vs
  RU-внутрянка» уже осмысленное. Шум решается фильтрацией снапшота, не переносом.

## 6. Миграция существующего

| Источник | Судьба |
|---|---|
| `.wolf/orchestration/playground-issues.md` | `git mv` → `playground-lab/registry/findings.md` (F1–F16 как есть) |
| Сценарии 1–7 из `playground/README-PLAYGROUND.md` | → `registry/scenarios.md`; в README-PLAYGROUND остаются только запуск/пересоздание |
| `playground/MANUAL-NOTES.md` | Объявляется черновиком-протоколом; материал существующих сценариев 3–4 переносится в карты/`measurements/`, файл обнуляется |
| Work-thread dogfooding (mem_20260901_dogfooding_ploshchadki) | Обновить указатели путей через решение в памяти Wolf |
| Правило «память площадки неприкосновенна» | Без изменений; дополняется: артефакты опытов живут в `playground-lab/`, площадка расходная |

## 7. Поглощение scenario-lab

Проверка содержимого подтвердила ценность: корпус исследований концепта
(80 scenario-карт, 80 playthrough'ов, 80 extraction-отчётов — база concept v3),
методические references, дисциплина схем шаблонов.

- `git mv scenario-lab playground-lab/archive/scenario-lab/` — история git
  сохраняется; кампания помечается завершённой.
- Харвест в дизайн лаборатории: поля карт и дисциплина схем (см. §3).
- Глобальный скилл `mr-wolf-scenario-lab`
  (`~/.config/opencode/superpowers/skills/…`): обновить 2 зашитых абсолютных
  пути на `…/playground-lab/archive/scenario-lab/`, добавить пометку
  «кампания завершена, материал в архиве полигона».
- Поправить ссылку на старый путь в
  `docs/superpowers/specs/2026-08-31-base-sets-design.md`.
- Решение о поглощении — `wolf add --type decision`.

## 8. Критерии приёмки

1. Каталог `playground-lab/` создан со структурой §2; README описывает
   сущности, жизненный цикл и границы зон (площадка расходная).
2. Реестр находок переехал (F1–F16 сохранены, нумерация продолжается),
   сценарии 1–7 — в `registry/scenarios.md`, старый `playground-issues.md`
   удалён из `.wolf/orchestration/`.
3. `verify-pristine.sh` существует, запускается, корректно распознаёт чистую
   и грязную площадку (проверено на обоих состояниях).
4. Reset-скрипт исключает `docs/site/public` из снапшота; пересозданная
   площадка остаётся pristine (init — первый эксперимент).
5. `scenario-lab/` в корне отсутствует, доступен как
   `playground-lab/archive/scenario-lab/`; пути в глобальном скилле и спеке
   base-sets обновлены.
6. Шаблон карты эксперимента и один образец-карта (эксперимент «онбординг v2»,
   по материалам сценариев 3–4 из MANUAL-NOTES) существуют и заполнены по шаблону.
7. Решения (создание лаборатории, поглощение scenario-lab) зафиксированы в
   памяти Wolf; `npm run check` зелёный.
