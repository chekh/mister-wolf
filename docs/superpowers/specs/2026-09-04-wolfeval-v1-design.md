## 1. Контекст и мотивация

Доказательная база Wolf остановилась на E3 (dogfood): по `docs/concept/maturity.md`
ни один компонент не достиг E4 (benchmark). Утверждения уровня «память
уменьшает стоимость повторной задачи» (CLM-003) и «постоянная организация
повышает качество на длительном пробеге» (CLM-004) имеют статус
`unsupported until E1b/E1a`. Программа E1a–E1e спроектирована, но не запущена;
B1–B3 оказались тестами механики, а не эффективности (§3.3).

Собственные доказательные данные 2026-09-03…04 показывают, почему одиночные
сессии не могут доказать продольный эффект:

| Эксперимент                          | Дизайн                                         | Результат                                                                                                          | Урок для методики                                                                                                  |
| ------------------------------------ | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| X1 (A/B, микрозадача)                | wolf vs bare baseline, N=3+3                   | wolf дороже: +65.4% весовых токенов, +91.4% времени; tool 5=5; качество 6/6; mr-wolf-тулов 0 вызовов в обеих руках | на короткой дистанции Wolf платит оверхед носителя и не получает дивидендов; память задачей не запрашивалась вовсе |
| X2 (память-критичная задача)         | WOLF-MEM (урок в памяти) vs NO-MEM, N=3 vs N=2 | экономии нет (+7.1% веса у WOLF-MEM); 0 контактов с уроком в 5 валидных прогонах; обе стороны читали гейт-скрипт   | даже «память-критичная» одиночная задача не гарантирует контакта с памятью, если знание выводимо чтением кода      |
| L1v2 (port-trap, невыводимое знание) | урок-рецепт vs чистая память, N=3+3            | честный ноль: итерации 2=2, вес +7.7%, 0/6 контакта с уроком                                                       | выразительный фейл теста обесценивает накопленное знание — агент выводит рецепт сам                                |

Дополнительно: F21 (hang) + F22 (невосстановимые метрики) испортили один из
шести прогонов X2 — статус `analyzed` вместо `concluded`; F24
(самоуничтожение ловушки) и F25 (silent truncation, маскируется под успех) —
классы инфра-риска, которые обязана ловить методика, а не удача.

Вывод: эффект Wolf — **накопительный**. Он проявляется только на траектории,
где (а) знание создаётся в ранних сессиях, (б) контекст принудительно
разрывается между сессиями, (в) поздние эпизоды **потребляют** ранее созданное
знание, (г) истина проверяется по конечному состоянию, а не по самоотчёту
агента. Одиночная A/B-сессия систематически недооценивает Wolf (платит оверхед
без дивидендов) — это дизайн-артефакт, а не свойство продукта. WolfEval v1 —
минимальный каркас для честного измерения такого эффекта.

## 4. Семья задач TF-1 и кампания WEV-001

### 4.1 Семья TF-1 «infra-hardening»

Единственная семья v1 (П1): поддержка и эволюция тестовой/измерительной
инфраструктуры небольшого TS-проекта — реальный класс проектной работы, из
которого выросли F1–F25.

Инстанс — fixture-репозиторий: срез кода mister-wolf на коммите **до релиза
2.0.0** (конкретный хэш фиксируется в `fixtures/` при сборке; правило выбора —
последний коммит перед тегом v2.0.0). На этом срезе одновременно живы все шесть
целевых дефектов (F4, F15, F5+F6, F8, F13, F14+F16 — все закрыты в
2.0.0–2.1.0). Git-история обезглавливается (`git init` + один initial commit) —
чтобы фикс был недоступен через `git log`. Сборка инстанса — по конвенции
playground-reset (снапшот + фильтр волчьих артефактов); исправность фикстуры
проверяет `verify-fixtures.sh`: все шесть дефектов воспроизводятся красным.

Существенный нюанс разделения двух волчьих версий (П4):

- **код инстанса** — исторический срез (объект работы агента, «проект-жертва»);
- **волчий CLI** (`wolf init`, MCP-сервер, плагины) — пинованный релизный tag
  ≥2.1.0 (инструмент измерения не должен сам быть багом F4-класса).

Обе величины фиксируются в environment-lock (§5.3) отдельно.

разрешённые пути + (волчья рука) память не содержит активных объектов,
противоречащих правилу E4, без пометки superseded.

### 4.3 Правила авторинга эпизодов (уроки X2/L1v2)

1. Знание должно быть **создано** в раннем эпизоде и **потреблено** в позднем:
   эпизоды-потребители (E2, E3, E6b) выбираются в той же зоне, что
   эпизоды-производители (E1, E6a).
2. Задача-потребитель не должна допускать дешёвого вывода знания чтением кода
   (урок X2: обе стороны прочитали гейт-скрипт, и урок не понадобился). Реплей
   F-инцидентов снижает риск: знание о структуре конвейера распределено, а не
   лежит в одном файле с комментарием.
3. Ловушка не должна фейлиться «выразительно» (урок L1v2: рецепт в тексте
   ошибки обесценивает накопленное знание) — воспроизведение дефекта даёт
   минимум диагностики в stdout.
4. Промпты эпизодов дословно одинаковы в обеих руках; различается только
   системный слой (механизм накопления) — гейт E4, пункт 4.

### 4.4 Holdout

Скрытые оракулы и критерии скоринга недоступны агенту: живут в
`hidden-oracles/`, не копируются в инстанс. Дословные промпты эпизодов — в
`instances/WEV-001/`, хэш набора — в карточке (task_set_hash). Unseen
holdout-варианты задач (второй изоморфный набор для confirmatory-фазы) —
roadmap (§10); v1 честно фиксирует это как границу доказательства (§11).

## 6. Метрики и scorers

### 6.1 Первичные метрики v1

| Метрика                             | Определение                                                                                                                                           | Scorer                            |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------- |
| Campaign Success Rate (CSR)         | доля повторов кампании, чей финальный аудит зелёный (все эпизодные оракулы PASS, проверки инстанса зелёные, CFR-событий нет)                          | `campaign-audit.sh` + сводка      |
| Cost per Successful Campaign (CPSC) | суммарные весовые токены всех сессий повтора (формула wolf-session.sh: `input + 0.1×cache_read + 5×output`), делённые на число успешных кампаний руки | `analysis/cost` из sessions.jsonl |
| Critical Failure Rate (CFR)         | доля повторов с ≥1 критическим событием; классы фиксированы до запуска и **не усредняются** — каждое событие разбирается отдельно                     | `analysis/cfr` + экспертный триаж |

Классы критических ошибок (severity-классификация до запуска, по предложению
§7): ложная приёмка (агент заявил DONE, оракул FAIL); повреждение (изменены
защищённые файлы); использование superseded-правила (E4); scope violation
(правки вне разрешённых путей); потеря данных (уничтожение накопленного
состояния без приёмки).

**Human-minutes per Success — вычеркнута из v1** (П5): в headless-режиме не
измеряется. Лимитация зафиксирована в §11; инструментирование — roadmap (§10).
Публичные формулировки до инструментирования не могут ссылаться на «меньшее
участие человека».

### 6.2 Вторичные метрики (по применимости к v1)

Применяются: first-pass success (по эпизодам); wall-clock; токены по
компонентам; tool-вызовы; recovery rate (E5: кампания завершена после обрыва);
duplicate work / re-investigation (E2, E3, E6b: повторные чтения/правки уже
исследованных зон по логу сессии); stale-knowledge usage (E4); memory-contact
(WOLF: события `mcp_call` mr-wolf-\* из P1-телеметрии; BASE: контакты с
собственными заметками); symmetry of solution (E6a/E6b).

Не применяются в v1 (нет семьи/механики): pass^k; time-to-payback;
LearningGain/TransferGain (WEV-002); NoiseTax/false retrieval (нет шум-семьи);
PaybackSession (нет второго режима бюджета).

## 7. Статистика и критерий успеха

### 7.1 A/A до A/B (П10)

Дизайн: две идентичные копии WOLF-руки (A1/A2), усечённая кампания E1–E3,
3 повтора, слепой скоринг. A/A проверяет **прибор**, а не эффект, поэтому
усечённой кампании достаточно: reset-процедуру (инстансы действительно
идентичны — diff после сборки), скорер (та же кампания даёт сопоставимые
исходы), порядок/прогрев провайдерского кеша (X1: input монотонно падает,
cache_read растёт — интерливинг обязателен), variance провайдера.

Критерий продолжения к A/B: устойчивая асимметрия исходов одного направления
во всех 3 парах (например, все A1 успешны, все A2 нет) → **стоп и диагностика
reset/скорера**, бюджет на A/B не тратится. Шумная симметрия (расхождения без
систематики) — ожидаемое состояние, продолжаем.

### 7.2 Повторы, кластеры, порядок

- Единица рандомизации и анализа — **повтор кампании** (кластер), не ран и не
  эпизод: эпизоды внутри кампании коррелированы общим накопленным опытом
  (статпротокол evidence.md: единица рандомизации — последовательность
  проекта).
- 3 повтора на руку; порядок пар рандомизируется до старта и фиксируется в
  run-configs (блоки AB/BA/AB или эквивалент); внутри повтора — кампания
  подряд, E1→E6b.
- Между повторами — полная пересборка инстансов обеих рук (fresh fixture +
  init). Внутри повтора ничего не откатывается: артефакты эпизода N остаются к
  эпизоду N+1 (это и есть продольный дизайн).

### 7.3 Минимальный практический эффект (формально, до запуска)

В карточке WEV-001 фиксируется:

- первичное направление: CPSC(WOLF) < CPSC(BASE);
- MPE (кандидат для утверждения владельцем): CPSC(WOLF) ≤ 0.85 × CPSC(BASE)
  при CSR(WOLF) ≥ CSR(BASE) и CFR(WOLF) ≤ CFR(BASE). Порог −15% прагматический:
  величина заметная для решения «внедрять/не внедрять», при этом заведомо
  меньше оверхеда носителя на одиночной доставке (PoC #3, H2: 2.3–3.3× к
  статике) — кампания должна окупать оверхед многократно, поэтому порог
  консервативен к заявлению успеха и не требует статистической значимости на
  3 кластерах;
- интерпретация зафиксирована заранее: достижение MPE при 3 кластерах =
  направленный сигнал + обкатанная инфраструктура; недостижение = отсутствие
  свидетельств, НЕ доказательство отсутствия эффекта (§11).

### 7.4 Stopping rule и обработка невалидных прогонов

- Fixed: 3 повтора на руку (A/A: 3 пары), досрочных остановок и добавлений
  нет; все прогоны публикуются (runs.jsonl), включая невалидные.
- Невалидный прогон (F21-hang: exit 124; F25-truncation: структурный брак
  лога; F24-класс: сломанная фикстура) → **один** ретрай; при повторном фейле
  повтор помечается invalid, анализ — на выживших с явной записью асимметрии
  (прецедент X2: N=3 vs N=2, статус analyzed вместо concluded).
- Плановый обрыв E5 помечается отдельным флагом в runs.jsonl (`planned_kill`)
  и маркером лаунчера: exit 124 сам по себе не отличает его от F21-hang —
  скорер невалидности учитывает только непомеченные 124.
- Bootstrap — по кластерам (повторам кампании), не по ранам; на 3 кластерах
  CI заведомо широки — это заявлено как граница, а не спрятано.

## 11. Риски и лимитации

### 11.1 Что v1 МОЖЕТ доказать

- Направленный сигнал: наличие/отсутствие практической разницы между
  структурированной памятью Wolf и дисциплинированными файловыми заметками на
  одной кампании одного класса задач, при фиксированном окружении.
- Работоспособность конвейера: реплей → эпизод → оракул → скоринг → отчёт
  (цель v1 по П1 — инфраструктура не менее, чем результат).
- Отсутствие катастрофы: CFR-классы (ложная приёмка, повреждение,
  superseded-правило) на измеренной траектории.

### 11.2 Что v1 НЕ МОЖЕТ доказать (границы)

- Публикационное доказательство: 3 кластера на руку не дают узких CI; bootstrap
  по кластерам это честно покажет (П6).
- Обобщаемость: одна семья задач, одна кампания, один срез кода — вне области
  измерения v1.
- Экономию участия человека: human-minutes не измеряется (П5).
- Причинную декомпозицию: без абляций разница рук смешивает память, инъекции и
  лица (осознанно: «механизм накопления» как целое).
- Эффекты иерархии/Council/Стюарда: отключены или не реализованы.
