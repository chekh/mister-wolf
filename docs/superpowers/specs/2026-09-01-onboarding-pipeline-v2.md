## 1. Проблема

Первый контакт пользователя с Wolf в свежем проекте (`wolf init`) сегодня
даёт четыре эффекта, три из которых — дефекты онбординга:

1. **«Чужая память» (F8)**: init автоматически скает проект и кладёт 97–98
   document-ref'ов в «пустую» память. Владелец расценил это как замусоривание:
   пользователь ещё ничего не решил, а память уже «помнит» весь репозиторий.
2. **MCP не подключён (F4)**: платформенный конфиг (`opencode.json` с MCP-сервером
   и дефолтным агентом) не пишется первым init'ом — детекция платформы не видит
   каталог `.opencode/`, который сама же init создаёт позже. Пользователь обязан
   запустить init дважды, иначе первая сессия проходит без Wolf.
3. **Пайплайн не доведён до конца**: init и bootstrap существуют как отдельные
   команды без формальной связи, а свёртка черновиков Стюардом (протокол
   `steward-bootstrap.md`) не имеет ни сигнала («надо свернуть»), ни критерия
   погашения («свёрнуто»). Сообщения init (F5–F7) не объясняют, что делать дальше.
4. **Жёсткий пин моделей (model-pin)**: все шесть шаблонов агентов несут
   `model: zai-coding-plan/glm-5.3|5.2` — в чужих окружениях без этого
   провайдера агенты Wolf неработоспособны; какими моделями будут работать
   wolf и steward, init сегодня не спрашивает и не настраивает.

Цель v2: после `wolf init` → `wolf bootstrap` → первого запуска opencode проект
получает чистую память, подключённый MCP, дефолтного агента Mr.Wolf,
осознанно выбранные платформы и модели агентов (без жёстких пинов)
и **самозаводящийся** контур доведения онбординга до конца: сессия Mr.Wolf видит
сигнал «свёртка не выполнена», вложенно вызывает Стюарда, тот приводит память
в порядок — сигнал гаснет.

## 3. Архитектура: машина состояний

```
                wolf init                    wolf bootstrap                Стюард (шаг 5
UNINIT ───────────────────────▶ INITIALIZED ─────────────────▶ BOOTSTRAPPED ──протокола)──▶ FOLDED
                                     │                              │                        │
                                     │ пишет: init-report           │ пишет: drafts,          │ пишет: accepted/rejected,
                                     │ (type=report, теги           │ doc-refs, thread(active)│ doc-refs active/stale,
                                     │ wolf-init+onboarding-v2)     │                         │ thread completed, decision
                                     ▼                              ▼                         ▼
                                  читает хук (recap):            читает хук (recap):       читает хук (recap):
                                  «run wolf bootstrap»           «буди Стюарда вложенно»    тишина (сигнала нет)
```

| Состояние    | Маркер (кто пишет)                                                                         | Что читает хук                                                |
| ------------ | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------- |
| UNINIT       | — (`.wolf/` нет или без маркеров)                                                          | — (плагин не установлен / тишина)                             |
| INITIALIZED  | init-report `status=active`, теги `wolf-init`+`onboarding-v2` (пишет `wolf init`)          | секция Onboarding: «bootstrap не выполнен → `wolf bootstrap`» |
| BOOTSTRAPPED | + thread «Bootstrap: наполнение стартовой памяти» `status=active` (пишет `wolf bootstrap`) | секция Onboarding: «свёртка не выполнена → вложенный Стюард»  |
| FOLDED       | thread `completed` или `archived` (пишет Стюард / владелец)                                | секции нет — сигнал погашен                                   |

Правила вывода секции (детекция в `generate-recap.ts`, объекты уже в памяти —
дополнительных запросов нет):

1. thread по константе заголовка (та же, что в `bootstrap-project.ts`) найден и
   `active` → fold-сигнал (независимо от init-report: покрывает legacy-проекты,
   свёрстанные до v2);
2. иначе init-report (теги `wolf-init` + `onboarding-v2`, `status=active`) есть,
   а thread **отсутствует** → bootstrap-сигнал (при `paused`-thread — тишина:
   владелец сознательно отложил, не назойливим);
3. иначе (нет ни того, ни другого; thread `completed`/`archived`/`paused`) →
   секции нет.

Обратных переходов нет; каждый шаг идемпотентен (§8). Состояние живёт только в
памяти Wolf — config.yaml не расширяется (D8). Lifecycle work-thread
(`active|paused|completed|archived`, memory-types.ts) учтён во всех правилах.

**Входы init (рев.4)**: платформы (§4.4) и модели (§4.5) — определяются до
рендера набора и становятся частью состояния INITIALIZED. Повторный init:

- **платформы**: явный выбор (флаг или TTY-ответ) заменяет детектированный
  набор платформ — контракт `--platform` сохранён, wolf-записи платформ вне
  списка удаляются;
- **модели**: routing-объект один (guard по тегам, как init-отчёт §4.1);
  совпадающий выбор → unchanged, иной → supersede + re-render агентов
  (diff-семантика `updated` — §4.5; сегодня renderBaseSet скипает
  существующее, правка названа в §10). Миграция не нужна: смена моделей —
  штатный повторный init, состояние пайплайна не меняется.

8. Реестр проектов (как сейчас).

### 4.1 Объект-отчёт init

```
type:        report
title:       Init report: <projectName>
tags:        [wolf-init, onboarding-v2]
created_by:  wolf-init
status:      active
body (markdown):
  ## Сделано (made)        — файлы набора (относительные пути), конфиг платформы
                              (mcp.wolf + default_agent: written/unchanged/needs-fix), AGENTS.md (created/appended/skip),
                              платформы (выбранные + источник: flag/tty/default), модели
                              (primary/worker: подставлены / omit — с reason)
  ## Обнаружено (found)    — уже существовавшие агенты/скиллы/команды/плагины/конфиги
                              (wx-skip), существующий AGENTS.md, версии
  ## Требует поправки (needs-fix) — actionable: конфликт default_agent, «скорректируйте
                              блок Wolf в AGENTS.md», «подключите MCP перезапуском платформы»,
                              «модели не настроены: wolf init --model-primary <id> [--model-worker <id>]»
                              (omit-случай, §4.5)
```

Связь шагов: bootstrap дописывает id init-отчёта в свой currentState (§5.2);
в теле отчёта ссылок на будущие шаги нет (отчёт — снимок момента init).

Теги — единственный машинный маркер (D4): extra-поля у `report` не декларированы
и отвергаются конвейером добавления. Guard идемпотентности: перед записью
`list({type: 'report'})` → фильтр по тегам; найден → **skip** (в выводе:
«init-report уже существует, не дублирую»). Обновление отчёта при повторном
init — не делаем: повторный init по wx-политике ничего не меняет, менять в
отчёте нечего.

### 4.2 AGENTS.md

- Отсутствует → рендер `templates/base/AGENTS.md` в корень: холодный старт
  (`wolf call` + `wolf brief`), фиксация значимого (`wolf add`/`supersede`),
  «состояние проекта — только у Wolf», лестница приоритетов, указатели на
  docs. Штамп `wolf:rendered` + маркер `<!-- wolf:onboarding v2 -->`.
- Существует, маркера нет → в конец дописывается маркированный блок (тот же
  контент, обёрнут маркерами `<!-- wolf:onboarding v2 -->` … `<!-- /wolf:onboarding -->`).
  Чужой контент не трогаем (D3: «дополнение/пометка, не перезапись»).
- Маркер есть → skip (в отчёт: found).
- ★ Механика рендера — новая ветка рендерера, а не «раскладка»: цель в корне
  проекта (а не `.opencode/`), две семантики — create (wx + штамп) и
  marker-append (блок без штампа). `wolf sync` обновляет только штампованный
  цельный файл (созданный create-веткой); append-блок синку не принадлежит и не
  трогается (обновление блока — повторный marker-append только при смене маркера
  версии, вне MVP).

  basename).
- «Restart your agent platform…» — только если MCP реально записан в этом
  прогоне; «skipped»-формулировки переформулированы без «агенты не установлены».
- Финальный блок «Дальше»: (1) `wolf bootstrap` — первичный образ памяти;
  (2) перезапуск opencode — подхватить MCP и дефолтного агента Mr.Wolf.
- npx try-out — прежняя подсказка про установку.

### 4.4 Платформы: явный выбор вместо молчаливой детекции (D10)

Источники выбора платформ, по убыванию авторитета:

1. **Флаг `--platform <ids>`** (неинтерактивный, для агентов/CI) — контракт
   текущего CLI сохранён: список валидируется по известным id (`opencode`,
   `claude`), wolf-записи платформ вне списка удаляются.
2. **TTY-вопрос** (интерактивный): init всегда предлагает **opencode** как
   дефолт (набор opencode-only и рендерится безусловно — D2/D3 base-sets,
   независимо от маркеров); платформы, найденные по маркерам, **добавляются**
   к предложению («найден `.claude/` — добавить claude?»), выбор
   множественный; ответ = тот же авторитет, что и флаг.
3. **Неинтерактивный дефолт** (не-TTY, без флага): opencode — по факту рендера
   набора (D2: набор opencode-only, покрывается безусловно); claude — по
   маркерам, не зависящим от рендера (нет маркеров — claude просто не
   подключается; отдельного warning не нужно — безопасный дефолт D12).

Что это устраняет в F4: корень дефекта — детекция, которая «не видит»
каталог, создаваемый самим init'ом, и решает молча. В v2 решение о платформе
всегда осознано: пользователь ответил на вопрос, передал флаг или получил
поведение, задокументированное дефолтом рендера. Детекция по маркерам
сохраняется только как источник предложения (TTY) и неинтерактивного дефолта
(claude) — гейтом больше не является ни для одной платформы.

Мультиплатформенность: выбор может включать несколько платформ; базовый набор
(агенты/плагины/скиллы/команды) рендерится для opencode — единственной
платформы с рендером (D1 base-sets); claude получает MCP-конфиг через
claude-adapter (как сегодня) без набора; AGENTS.md рендерится в корень
независимо от платформ (§4.2). Расширение рендера набора на claude — зона
base-sets, не этой спеки. Граничный случай — явный выбор **без** opencode
(`--platform claude`): набор всё равно рендерится (рендер не гэйтится
платформами — как сегодня), а wolf-записи opencode удаляются контрактом
`--platform`; итоговое состояние (`.opencode/` с агентами Wolf, но без
`mcp.wolf`) — осознанное, в отчёте — needs-fix с подсказкой.

### 4.5 Модели и роутинг (D11)

**Проблема пинов.** Все шесть шаблонов агентов несут жёсткий пин
`model: zai-coding-plan/glm-5.3` (worker-implementer — glm-5.2): в окружениях
без этого провайдера агенты Wolf неработоспособны (FRICTION model-pin,
решение e983a4). В v2 пины из шаблонов **удаляются** — вместо них
плейсхолдеры, подстановку делает рендер.

**Роли.** Минимальная схема — две роли: `primary` (mr-wolf, steward,
executor-lead, worker-reviewer, worker-researcher) и `worker`
(worker-implementer); дефолт `worker` = `primary` (одна модель на всё —
легитимный ответ опроса). Per-agent зоопарк ролей — сознательно нет (YAGNI;
две роли покрывают сегодняшнее деление 5.3/5.2).

**Определение при init.**

- TTY: init предлагает варианты и спрашивает: (а) авто-детект доступных
  провайдеров «по возможности» — ENV-ключи известных провайдеров и
  пользовательский глобальный конфиг opencode (только чтение); найденное —
  первые предложения списка; (б) свободный ввод идентификатора
  `<providerID>/<modelID>`; (в) skip — модели не настраиваем (omit).
- Не-TTY: флаги `--model-primary <id>`, `--model-worker <id>`; без флагов —
  авто-детект окружения; не удалось — omit (ниже).

**Хранение.** Routing-объект в памяти Wolf: `type=rule`, `memory_class:
working`, `scope: 'project'` (обязательное поле `rule`; прецедент —
bootstrap-work-thread) — «класс „параметры“» из PoC #4 это паттерн body, а не
поле таксономии (`MemoryClass = working | canonical`; таксономия не
расширяется). Теги `wolf-routing` + `models`, body = `{primary, worker}`.
Guard — один активный объект по тегам (как init-отчёт §4.1); смена —
supersede (lifecycle `rule` содержит `active`/`superseded`). Память —
единственный источник состояния (канон проекта); `opencode.json` и
`config.yaml` не расширяются — вторую истину рядом с памятью не заводим;
extra-полей у `rule` не декларировано и конвейер их отвергает — значения
едут в body.

**Подстановка.** Шаблоны агентов получают плейсхолдеры: `model:
{{model.primary}}` (worker-implementer — `{{model.worker}}`). Рендер базового
набора уже владеет механизмом подстановки (`{{tool.*}}` через manifest;
неизвестных `{{…}}` словарь не валидирует — расширение контекстом `model.*`
беспрепятственно). Отрендеренные файлы несут конкретные id; рендер —
проекция выбора. Повторный init с иными моделями → re-render агентов с
diff-семантикой: `RenderAction` = `updated` при расхождении контента,
`skipped` при совпадении (семантика syncBaseSet `fresh ≠ current`); сегодня
renderBaseSet безусловно скипает существующее — расширение названо в §10.
Если модели не определены (skip / не-TTY без флагов и авто-детекта): рендер
**опускает** строку `model:` — это построчная семантика рендера (убрать
плейсхолдер вместе с переводом строки), а не чистая подстановка `{{…}}`;
интерактивная сессия работает на платформенной модели по умолчанию;
`opencode run` с рамкой без `model:` падает (PoC #4) — известное поведение,
needs-fix отчёта содержит точную команду донастройки
(`wolf init --model-primary <id>`).

**Влияние на wolf-router.ts.** В MVP — нулевое: плагин остаётся
playbook-роутером (детерминированная доставка методик), подстановка моделей
происходит на рендере. Runtime-подмена алиасов (сменить модель без повторного
init, следуя supersede-цепочке) плагином невозможна в opencode 1.18.25 — хука
подмены модели нет (PoC #4: provider hook = статические описания; рабочий
механизм — адаптер запуска с `--model`). Run-слой — Q9, вне MVP онбординга.

**Согласованность с `wolf sync`.** Sync ре-рендерит шаблоны агентов тем же
механизмом подстановки — без контекста моделей он перезаписал бы корректные
frontmatter литералами `{{model.*}}` (или молча прошёл бы их насквозь).
Поэтому sync читает routing-объект той же командой и подставляет `model.*`
как init; routing-объекта нет (легаси до v2) — sync ведёт себя как init без
выбора: опускает `model:`-строку. Правка названа в §10 (исключение из
«sync не трогаем» рев.3 — только модельный контекст, прочая семантика
AGENTS.md/sync не меняется).

**Что видят Стюард/воркеры.** Модель сессии вложенного агента = значение,
подставленное в его рендер (`worker-*` → роль worker, steward → primary);
отдельного механизма для вложенных вызовов нет — рендер един. Если модели
не настроены, вложенный `opencode run --agent steward` не стартует до
донастройки (поведение выше) — Mr.Wolf видит это как явную ошибку запуска,
а не тихую деградацию.

### 4.6 Двухрежимный CLI (D12)

- **TTY** (`process.stdout.isTTY`): вопросы о платформе (§4.4) и моделях
  (§4.5) с предложениями; Enter — принять дефолт. Библиотека промптов — на
  реализации (достаточно readline; тяжёлых зависимостей не добавляем).
- **Не-TTY**: флаги `--platform`, `--model-primary`, `--model-worker`
  покрывают все входы; вопросы не задаются, дефолты — §4.4 п.3 и §4.5
  (авто-детект окружения → omit). Конфиг-файл для init не заводим до спроса
  (Q10): флаги уже машиночитаемы, второй вход — второй путь ошибок.
- **CI/агентский прогон без флагов**: безопасный дефолт + needs-fix, exit 0 —
  НЕ ошибка. Обоснование: init не деструктивен и идемпотентен, жёсткий отказ
  сломал бы автоматические прогоны (включая будущие npx-сценарии), а
  донастройка — штатный повторный `wolf init` с флагами; needs-fix содержит
  точную команду. Help-строка «non-interactive» меняется на «interactive in
  TTY; non-interactive with flags» — смена обещания осознанная (решение
  1450c8: агенты получают неинтерактивный режим, человек — интерактивный).

## 5. Шаг 2 — `wolf bootstrap` v2

Остаётся как есть (скан → черновики `proposed` из фактов → doc-ref'ы →
work-thread; дедуп по title, переиспользование thread). Правки:

1. ★ Guard «fold уже был»: существующий thread со `status ≠ active`
   (`completed`/`archived`/`paused`) → no-op с сообщением «Онбординг уже
   свёрнут/отложен (thread <status>); для пересоздания — владелец вручную».
   Иначе повторный bootstrap после fold регрессировал бы память к черновикам:
   дедуп смотрит только `proposed`, а после свёртки их нет.
2. ★ «Указатель что и когда сделано» (D5) — расширяется существующий thread
   (без extra: createWorkThread их не принимает):
   - `currentState` при создании: `init <ts> ✓ (report <id init-отчёта — по тегам wolf-init>; absent → «без отчёта»); bootstrap <ts>: черновиков N, document-ref'ов M` — «что и когда»;
   - дальнейшие события — в events.jsonl автоматически (id, статусы, timestamps).
3. Doc-ref'ы: создаются здесь и только здесь (D5). Нейминг id и поведение FTS —
   без изменений до отдельного фикса F9 (§7).

## 6. Шаг 3 — первая сессия opencode

### 6.1 Дефолтный агент: merge-семантика в `opencode.json`

`default_agent: mr-wolf` пишет init (D2). Семантика:

- ключ отсутствует → устанавливается;
- присутствует и равен → `unchanged`;
- присутствует и отличен → **не трогаем**, исход `unchanged` с `reason:
default_agent=<значение> занят; mr-wolf не назначен` → строка уходит в
  needs-fix отчёта (канал: `PlatformInitOutcome.reason`);
- `'unchanged'` вычисляется по **обоим** ключам (mcp.wolf и default_agent):
  равенство одного не должно маскировать отсутствие второго;
- существующий `opencode.jsonc` при rewrite теряет комментарии — известное
  ограничение адаптера (ponytail-комментарий в opencode-adapter.ts). Rewrite —
  механизм один, триггер — расхождение `mcp.wolf` **или** `default_agent` (v1
  не трогала конфиг с корректным mcp.wolf, но без default_agent — v2 такой
  перепишет); jsonc-оговорка покрывает оба ключа, AST-редактор — вне MVP.

### 6.2 Сигнал pending-fold

Канал: `wolf recap` → плагин wolf-session-start уже доставляет recap внутрь
`<session_context>` первого сообщения (L0/L1; маркер-идемпотентность, повтор
после /clear — MAJ-1). Плагин **не меняется** (D6): секция — часть recap-текста.

Тексты секции `## Onboarding` (формулировки — контракт для рамки mr-wolf):

- bootstrap-сигнал: «Onboarding v2: init выполнен, bootstrap — нет. Предложи
  владельцу запустить `wolf bootstrap` (запуск — по подтверждению владельца).»
- fold-сигнал: «Onboarding v2: артефакты init+bootstrap в памяти, свёртка не
  выполнена. Вложенно вызови Стюарда (task tool, subagent_type=steward, бриф:
  протокол docs/guide/steward-bootstrap.md). Не вызывай Стюарда напрямую и не
  сворачивай сам.»

### 6.3 Вложенный вызов Стюарда

- Механизм: task tool с `subagent_type=steward` из сессии Mr.Wolf. Правки
  шаблона рамки mr-wolf (обе обязательны, иначе рамка противоречит сама себе):
  - `permission.task` → `{"*": deny, "executor-*": allow, "steward": allow}`;
  - раздел «Запреты»: «Спавнь только `executor-*`; **исключение — один вложенный
    Стюард** по онбординг-сигналу и жалобному контуру (/complain, base-sets
    §5.3)». Steward уже `mode: all` — виден как subagent.
- Плюс шаг процедуры: «Onboarding-сигнал в recap → один вложенный вызов Стюарда
  → принять отчёт → убедиться, что секция погасла (`wolf recap`)».
- Fallback (документированный): `opencode run --agent steward "…"` (PoC #3).
- Стюард делает свёртку строго по `docs/guide/steward-bootstrap.md` (шаги 1–6:
  сверить черновики с фактами → accepted/rejected → doc-refs active/stale →
  thread completed → decision). Шаг 5 закрывает thread → критерий D8 → сигнал
  погашен.
- Границы Стюарда: рамка «не аналитик» — свёртка = сверка фактов и переходы
  статусов, не исследование. **Отклонение от решения владельца (явное, Q6 §11)**:
  «глубокое изучение проекта»\_owner не вкладывается в рамку Стюарда-мутатора;
  предлагаемое прочтение: Стюард сворачивает память, а глубокое изучение Mr.Wolf
  диспетчерит сразу после fold (worker-researcher, отдельная задача координатора
  по его стандартной процедуре). До ответа владельца пункт числится отклонением,
  требующим подтверждения.

### 6.4 Безопасность: анти-цикл и анти-спам

- **Цикл невозможен структурно**: steward `permission.task: deny` — никого не
  спавнит; mr-wolf спавнит Стюарда максимум один раз за сессию (процедура).
- **Видимость сигнала**: сессии `worker-*` (L2) recap не получают (плагин режет
  по префиксу). Вложенная сессия Стюарда (`agent-id: steward`) сигнал видит —
  ожидаемо и безвредно: текст обращён к Mr.Wolf, а самовызов Стюарду запрещён
  (task: deny + рамка).
- **Краш свёртки — не катастрофа**: сигнал гаснет только по `completed`/`archived`
  thread'у, а не по факту вызова Стюарда. Недоделанная свёртка → сигнал в
  следующей сессии → повтор. Переходы статусов идемпотентны.
- **Спам-контроль**: внутри сессии инъекция одна (маркер); повтор после /clear —
  штатный режим всех wolf-инъекций; в рамках сессии Mr.Wolf не назойлив
  (предложил — владелец отказал — не повторяет до следующей сессии). Мягкий лимит
  повторов между сессиями не заводим (YAGNI) — упорно падающий Стюард виден
  владельцу по events.jsonl.
- Отказ владельца от онбординга вовсе: после bootstrap — закрыть thread вручную
  (`wolf transition <thread> completed` — или `archived`); **до bootstrap** —
  перевести сам init-отчёт (`wolf transition <init-report> completed`), убив
  bootstrap-сигнал в зародыше. Оба пути сигнал гасят (документируются).

| Legacy-проект (до v2)         | Нет init-report: если thread active → fold-сигнал работает; иначе тишина. Деградация грациозная, миграция не требуется                                                                                                                       |
| npx try-out                   | Память-скелет есть, отчёта и плагина нет → пайплайн молчит; после глобальной установки повторный init пишет конфиги, набор и отчёт — штатный ход (устаревший npx-отчёт исключён, §4 п.5)                                                     |

## 9. План верификации

Сценарий на площадке (`playground/`, pristine-reset), каждый шаг — чек:

1. **pristine → `wolf init`**: (а) `wolf list --type document-ref` → пусто
   (F8 закрыт); (б) base set 6/13/3/2 по путям в выводе (F5); (в) `opencode.json`
   существует, содержит `mcp.wolf` и `default_agent: mr-wolf` (F4 закрыт);
   (г) AGENTS.md создан с маркером; (д) ровно один init-report с секциями
   made/found/needs-fix; (е) сообщение «Дальше» упоминает bootstrap (F7).
2. **Повторный `wolf init`**: все файлы skipped, отчёт не задублирован, вывод
   без «restart»-шума про уже записанное.
3. **TTY-сценарий** (псевдо-TTY): вопросы платформы (предложение opencode,
   Enter — дефолт) и моделей (предложения из окружения) отработаны;
   в отрендеренных агентах нет пинов `zai-coding-plan/…` — только
   выбранные id; routing-объект создан, теги `wolf-routing`+`models`.
4. **Неинтерактивный прогон**: `wolf init --platform opencode
--model-primary <test-id> --model-worker <test-id>` без TTY — вопросов
   нет, результат эквивалентен TTY-выбору тех же значений; без модельных
   флагов — `model:`-строки опущены, needs-fix в отчёте с командой
   донастройки, exit 0 (D12).
5. **Смена моделей повторным init**: routing-объект superseded (один активный),
   агенты re-rendered (diff → `updated`; без diff → `skipped`), init-отчёт не
   задублирован; смена платформ `--platform` — прежний контракт (удаление вне
   списка).
6. **`wolf bootstrap`**: черновики proposed ≥ 2, doc-ref'ы созданы, thread
   active, в currentState указатель с id init-отчёта; повторный запуск — дедуп;
   после ручного `completed` — no-op (guard).
7. **Первая сессия** (`opencode` в площадке): (а) агент по умолчанию — Mr.Wolf;
   (б) в первом сообщении есть `<session_context>` с recap, содержащим секцию
   `## Onboarding` с fold-сигналом.
8. **Вложенный Стюард**: Mr.Wolf вызывает task tool `subagent_type=steward`;
   Стюард выполняет протокол: правила → accepted, refs → active/stale,
   thread → completed, decision записан.
9. **Погашение**: следующая сессия — секции Onboarding нет; правила видны в
   recap (F11 закрыт: «Правила (accepted/active)»).
10. **Ретресс-контроль**: `npm run check` репозитория Wolf зелёный; повторный
    bootstrap после fold — no-op (guard).

Unit/integration (для реализации): recap-секция в состояниях §3 (включая
paused/archived); init без скана; guard отчёта по тегам; merge-политика
default_agent (absent/present-equal/present-different, unchanged по обоим
ключам, reason-канал); AGENTS.md (absent/present-marker/present-no-marker);
bootstrap guard `status ≠ active`; идемпотентность повторов каждого шага;
двухрежимный CLI (TTY-вопросы / флаги / не-TTY-дефолт); подстановка
`{{model.*}}` (выбраны / omit); routing-guard и supersede; предложения
моделей из окружения (ENV/глобальный конфиг opencode); приоритет источников
платформ (флаг > TTY > дефолт рендера); diff-ветка renderBaseSet
(`updated`/`skipped`); модельный контекст `wolf sync` (с routing-объектом /
без → omit).

## 10. Scope и НЕ-цели

**Трогаем (при реализации)**:

- `init-project.ts` — порядок, удаление скана, opencode-исход, init-отчёт,
  входы платформ/моделей (§4.4–§4.6), routing-объект (guard/supersede);
- `generate-recap.ts` — секция Onboarding + фильтр accepted;
- `bootstrap-project.ts` — guard `status ≠ active`, указатель в currentState;
- `memory-init.ts` — двухрежимный CLI (TTY-вопросы/флаги/дефолты), вывод v2;
- `opencode-adapter.ts` — merge default_agent (семантика §6.1, расширение
  результата writeConfig под reason-канал);
- рендер базового набора — контекст подстановки `{{model.*}}` (manifest уже
  владеет механизмом `{{tool.*}}`); ★ **diff-ветка renderBaseSet** для
  повторного init при смене моделей (существует + diff контента → `updated`,
  совпадение → `skipped`; семантика syncBaseSet `fresh ≠ current` — сегодня
  renderBaseSet безусловно скипает существующее); ★ построчный omit
  `model:`-строки при отсутствии выбора;
- `wolf sync` — ★ контекст моделей при ре-рендере агентов: чтение
  routing-объекта той же командой, подстановка `model.*` как в init; без
  routing-объекта — omit `model:` (§4.5). Единственное исключение из «sync
  не трогаем» рев.3; прочая семантика sync (AGENTS.md-восприятие) не меняется;
- `templates/base/agents/*.md` — удаление жёстких пинов
  `model: zai-coding-plan/glm-5.3|5.2` (6 файлов) → плейсхолдеры
  `{{model.primary}}`/`{{model.worker}}` (D11);
- `templates/base/agents/mr-wolf.md` — permission.task + «Запреты» + процедура;
- `templates/base/AGENTS.md` (новый) + рендерер: root-цель, create/marker-append
  ветки, sync только для штампованного цельного файла, относительный путь в
  BaseSetOutcome;
- тесты ко всему выше.

Таксономия памяти (`memory-types.ts`), `createWorkThread`, store/index/FTS,
MCP-слой, `wolf sync` (семантика AGENTS.md из рев.3 — в рендерере §4.2;
единственное новое исключение рев.4 — модельный контекст §4.5),
claude-adapter, `templates/opencode/plugins/wolf-router.ts` и
`wolf-session-start.js` — **не трогаем**: маркеры едут в тегах и body
(D4/D5), плагины не участвуют в модельном слое MVP (D11, Q9).

**НЕ-цели**:

- Код в этой спеке — её предмет; реализация отдельным планом.
- Мультиплатформенность за пределами выбора при init: набор, плагины и
  модельный слой — opencode-only; claude получает MCP-конфиг без набора, а
  модели для него не указываются вовсе (решение e983a4: «не указывать модель
  или платформо-специфичный механизм»); расширение рендера на claude —
  base-sets.
- Runtime run-роутер алиасов моделей (смена модели без повторного init,
  обёртка `--model` по supersede-цепочке) — вне MVP онбординга (Q9; PoC #4
  доказал осуществимость, смена моделей покрывается повторным init).
- Конфиг-файл для неинтерактивного init — не заводим до спроса (Q10).
- Гарантированный авто-детект провайдеров — «по возможности» (решение
  1450c8): окружение молчит → явный вопрос/флаг, не тихий выбор.
- Фиксы F9 (нейминг/FTS doc-ref'ов) и F10 — отдельные задачи (§7).
- Автозапуск bootstrap из сессии без ведома владельца — сознательно нет (§8).
- Миграция существующих проектов на v2-маркеры — не требуется (грациозная
  деградация, §8).
- Изменение lifecycle правил (accepted ≠ active) — семантика сохраняется (D9).
- Очистка/архив существующей памяти при повторном init — не входит (см. Q1).
- AST-редактор JSONC (сохранение комментариев при rewrite) — вне MVP (§6.1).

## 12. Критерии приёмки реализации

1. Площадочный сценарий §9 проходит целиком: pristine → init (чистая память,
   opencode.json с MCP и default_agent, AGENTS.md, один отчёт) → bootstrap →
   первая сессия (Mr.Wolf по умолчанию, fold-сигнал в recap) → вложенный
   Стюард → свёртка → сигнал погашен, конвенции видны в recap.
2. Повторные запуски каждого шага идемпотентны (§8), включая no-op bootstrap
   после fold и тишину при paused/archived.
3. F4, F5, F6, F7, F8 закрыты; F11 закрыт (recap: accepted ∪ active);
   интеракции F9/F10 зафиксированы в §7 и не регрессируют.
4. `npm run check` репозитория Wolf зелёный; полное E2E после плана
   (правило проекта).
5. Анти-цикл/анти-спам подтверждены структурно (§6.4): steward никого не
   спавнит, сигнал гаснет только по completed/archived, L2-сессии без сигнала.
6. Платформы и модели (§4.4–§4.6): явный выбор работает в обоих режимах
   (TTY-вопросы, флаги), жёстких пинов `zai-coding-plan/…` в отрендеренном
   наборе нет (плейсхолдеры подставлены или `model:` опущена с needs-fix),
   routing-объект один (supersede при смене), повторный init с новыми
   платформами/моделями обновляет рендер без дублей; не-TTY без флагов —
   exit 0.
