## 1. Проблема

Первый контакт пользователя с Wolf в свежем проекте (`wolf init`) сегодня
даёт четыре эффекта, три из которых — дефекты онбординга:

1. **«Чужая память» (F8)**: init автоматически скает проект и кладёт 97–98
   document-ref'ов в «пустую» память. Владелец расценил это как замусоривание:
   пользователь ещё ничего не решил, а память уже «помнит» весь репозиторий.
2. **MCP не подключён (F4)**: платформенный конфиг (`opencode.json` с MCP-сервером
   и дефолтным агентом) не пишется первым init'ом — детекция платформы не видит
   каталог `.opencode/`, который сама же init создаёт позже. Пользователь обязан
   запустить init дважды, иначе первая сессия проходит без Wolf.
3. **Пайплайн не доведён до конца**: init и bootstrap существуют как отдельные
   команды без формальной связи — у онбординга нет ни сигнала («не завершён»),
   ни критерия погашения («завершён»). Сообщения init (F5–F7) не объясняют,
   что делать дальше.
4. **Жёсткий пин моделей (model-pin)**: шаблоны агентов несут
   `model: zai-coding-plan/glm-5.3|5.2` — в чужих окружениях без этого
   провайдера агенты Wolf неработоспособны; какую модель выберет пользователь
   для Mr.Wolf и его агентов, init сегодня не спрашивает и не настраивает.

Цель v2: после `wolf init` → `wolf bootstrap` → первого запуска opencode проект
получает чистую память, подключённый MCP, дефолтного агента Mr.Wolf,
осознанно выбранные платформы и одну модель агентов (без жёстких пинов)
и **самозаводящийся** контур доведения онбординга до конца: сессия Mr.Wolf
видит сигнал «онбординг не завершён», уточняет у пользователя — предложить
`wolf bootstrap` (вплоть до исполнения прямо в сессии) или следовать пути
пользователя (включая глубокое изучение проекта); сигнал гаснет, когда
онбординг закрыт (bootstrap-thread → completed).

## 3. Архитектура: машина состояний

```
                wolf init                    wolf bootstrap                закрытие thread
UNINIT ───────────────────────▶ INITIALIZED ─────────────────▶ BOOTSTRAPPED ───────────▶ ONBOARDED
                                      │                              │                 (completed/archived —
                                      │ пишет: init-report           │ пишет: drafts,  пишет пользователь или
                                      │ (type=report, теги           │ doc-refs,       Mr.Wolf в диалоге, §6.3)
                                      │ wolf-init+onboarding-v2)     │ thread(active)
                                      ▼                              ▼
                                   читает хук (recap):            читает хук (recap):
                                   «онбординг не завершён:        «онбординг не завершён:
                                   bootstrap не выполнен»         завершение не выполнено»
                                   → диалог §6.3                  → диалог §6.3 (путь пользователя)
```

| Состояние    | Маркер (кто пишет)                                                                         | Что читает хук                               |
| ------------ | ------------------------------------------------------------------------------------------ | -------------------------------------------- |
| UNINIT       | — (`.wolf/` нет или без маркеров)                                                          | — (плагин не установлен / тишина)            |
| INITIALIZED  | init-report `status=active`, теги `wolf-init`+`onboarding-v2` (пишет `wolf init`)          | секция Onboarding: bootstrap-сигнал (§6.2)   |
| BOOTSTRAPPED | + thread «Bootstrap: наполнение стартовой памяти» `status=active` (пишет `wolf bootstrap`) | секция Onboarding: продолжение-сигнал (§6.2) |
| ONBOARDED    | thread `completed` или `archived` (пишет пользователь / Mr.Wolf в диалоге, §6.3)           | секции нет — сигнал погашен (Q4)             |

Правила вывода секции (детекция в `generate-recap.ts`, объекты уже в памяти —
дополнительных запросов нет):

1. thread по константе заголовка (та же, что в `bootstrap-project.ts`) найден и
   `active` → продолжение-сигнал (независимо от init-report: покрывает
   legacy-проекты, бутстрапнутые до v2);
2. иначе init-report (теги `wolf-init` + `onboarding-v2`, `status=active`) есть,
   а thread **отсутствует** → bootstrap-сигнал (при `paused`-thread — тишина:
   владелец сознательно отложил, не назойливим);
3. иначе (нет ни того, ни другого; thread `completed`/`archived`/`paused`) →
   секции нет.

Переход BOOTSTRAPPED → ONBOARDED закрывает пользователь (или Mr.Wolf с его
согласия) в диалоге — предписанной авто-роли нет (Q6): пайплайн никого не
спавнит. Обратных переходов нет; каждый шаг идемпотентен (§8). Состояние живёт
только в памяти Wolf — config.yaml не расширяется (D8). Lifecycle work-thread
(`active|paused|completed|archived`, memory-types.ts) учтён во всех правилах.

**Входы init (рев.4/рев.5)**: платформы (§4.4) и модель (§4.5) — определяются до
рендера набора и становятся частью состояния INITIALIZED. Повторный init:

- **платформы**: явный выбор (флаг или TTY-ответ) заменяет детектированный
  набор платформ — контракт `--platform` сохранён, wolf-записи платформ вне
  списка удаляются;
- **модели**: routing-объект один (guard по тегам, как init-отчёт §4.1);
  совпадающий выбор → unchanged, иной → supersede + re-render агентов
  (diff-семантика `updated` — §4.5; сегодня renderBaseSet скипает
  существующее, правка названа в §10). Миграция не нужна: смена моделей —
  штатный повторный init или переопределение в bootstrap-сессии (§4.5),
  состояние пайплайна не меняется.

   конфигов и без набора (как сейчас), и ★ **без init-отчёта**: пайплайн
   «молчит» до полноценной установки — отчёт из npx-прогона иначе навсегда
   застынет устаревшим (guard §4.1 не обновляет существующий).
7. ★ AGENTS.md (D3) — §4.2.
8. Реестр проектов (как сейчас).
9. ★ Init-отчёт — ровно один объект (D4) — §4.1.
10. ★ Вывод v2 (F5/F6/F7) — §4.3.

### 4.1 Объект-отчёт init

```
type:        report
title:       Init report: <projectName>
tags:        [wolf-init, onboarding-v2]
created_by:  wolf-init
status:      active
body (markdown):
  ## Сделано (made)        — файлы набора (относительные пути), конфиг платформы
                              (mcp.wolf + default_agent: written/unchanged/needs-fix), AGENTS.md (created/appended/skip),
                              платформы (выбранные + источник: flag/tty/default), модель
                              (primary: <id>, источник flag/tty — подставлена всем агентам)
  ## Обнаружено (found)    — уже существовавшие агенты/скиллы/команды/плагины/конфиги
                              (wx-skip), существующий AGENTS.md, версии
  ## Требует поправки (needs-fix) — actionable: конфликт default_agent, «скорректируйте
                              блок Wolf в AGENTS.md», «подключите MCP перезапуском платформы»
```

Связь шагов: bootstrap дописывает id init-отчёта в свой currentState (§5.2);
в теле отчёта ссылок на будущие шаги нет (отчёт — снимок момента init).

Теги — единственный машинный маркер (D4): extra-поля у `report` не декларированы
и отвергаются конвейером добавления. Guard идемпотентности: перед записью
`list({type: 'report'})` → фильтр по тегам; найден → **skip** (в выводе:
«init-report уже существует, не дублирую»). Обновление отчёта при повторном
init — не делаем: wx-политика набора не меняется; смена модели меняет
routing-объект и ре-рендер агентов (§3 «Входы init», §4.5), но не отчёт —
актуальная модель всегда живёт в routing-объекте, отчёт остаётся снимком
момента init.

### 4.4 Платформы: явный выбор вместо молчаливой детекции (D10)

Источники выбора платформ, по убыванию авторитета:

1. **Флаг `--platform <ids>`** (неинтерактивный, для агентов/CI) — контракт
   текущего CLI сохранён: список валидируется по известным id (`opencode`,
   `claude`), wolf-записи платформ вне списка удаляются.
2. **TTY-вопрос** (интерактивный): init всегда предлагает **opencode** как
   дефолт (набор opencode-only и рендерится безусловно — D2/D3 base-sets,
   независимо от маркеров); платформы, найденные по маркерам, **добавляются**
   к предложению («найден `.claude/` — добавить claude?»), выбор
   множественный; ответ = тот же авторитет, что и флаг.
3. **Неинтерактивный дефолт** (не-TTY, без флага): opencode — по факту рендера
   набора (D2: набор opencode-only, покрывается безусловно); claude — по
   маркерам, не зависящим от рендера (нет маркеров — claude просто не
   подключается; отдельного warning не нужно — безопасный дефолт D12).

Что это устраняет в F4: корень дефекта — детекция, которая «не видит»
каталог, создаваемый самим init'ом, и решает молча. В v2 решение о платформе
всегда осознано: пользователь ответил на вопрос, передал флаг или получил
поведение, задокументированное дефолтом рендера. Детекция по маркерам
сохраняется только как источник предложения (TTY) и неинтерактивного дефолта
(claude) — гейтом больше не является ни для одной платформы.

Мультиплатформенность: выбор может включать несколько платформ; базовый набор
(агенты/плагины/скиллы/команды) рендерится для opencode — единственной
платформы с рендером (D1 base-sets); claude получает MCP-конфиг через
claude-adapter (как сегодня) без набора; AGENTS.md рендерится в корень
независимо от платформ (§4.2). Расширение рендера набора на claude — зона
base-sets, не этой спеки. Граничный случай — явный выбор **без** opencode
(`--platform claude`): набор всё равно рендерится (рендер не гэйтится
платформами — как сегодня), а wolf-записи opencode удаляются контрактом
`--platform`; итоговое состояние (`.opencode/` с агентами Wolf, но без
`mcp.wolf`) — осознанное, в отчёте — needs-fix с подсказкой.

### 4.5 Модели и роутинг (D11, Q7)

**Проблема пинов.** Шаблоны агентов несут жёсткий пин
`model: zai-coding-plan/glm-5.3` (worker-implementer — glm-5.2): в окружениях
без этого провайдера агенты Wolf неработоспособны (FRICTION model-pin,
решение e983a4). В v2 пины из шаблонов **удаляются** — вместо них
плейсхолдеры, подстановку делает рендер.

**Одна модель при init (Q7).** init спрашивает ровно одну модель — для
Mr.Wolf (роль `primary`). Семантика по умолчанию: **все агенты базового
набора рендерятся этой моделью**, включая worker-implementer (его роль
`worker` инициализируется значением `primary`). Обоснование: минимальный
барьер первого контакта — один вопрос вместо анкеты; деление 5.3/5.2 —
оптимизация конкретного окружения, а не онбординговый выбор; per-agent
зоопарк ролей — сознательно нет (YAGNI). Переопределение `worker` — позже,
в bootstrap-сессии («Смена и переопределение»): routing-объект
редактируется, повторный init не нужен. Двухролевая анкета рев.4 (D11)
корректируется решением Q7.

**Определение при init.**

- TTY: один вопрос — идентификатор `<providerID>/<modelID>` модели Mr.Wolf;
  предложения — авто-детект доступных провайдеров «по возможности» (ENV-ключи
  известных провайдеров и пользовательский глобальный конфиг opencode, только
  чтение) первыми строками списка; свободный ввод; Enter — принять первое
  предложение. Пропустить модель нельзя: init без модели не существует
  (Q11 выравнивает не-TTY — TTY не слабее).
- Не-TTY: флаг `--model <id>` — **обязателен**; без него — жёсткая ошибка
  (§4.6, Q11). Авто-детект в не-TTY модель молча не подставляет — явность
  важнее удобства: CI/агентские прогоны получают детерминированный контракт.

**Хранение.** Routing-объект в памяти Wolf: `type=rule`, `memory_class:
working`, `scope: 'project'` (обязательное поле `rule`; прецедент —
bootstrap-work-thread) — «класс „параметры“» из PoC #4 это паттерн body, а не
поле таксономии (`MemoryClass = working | canonical`; таксономия не
расширяется). Теги `wolf-routing` + `models`, body = `{primary, worker}`;
init пишет `worker = primary` (одна модель на всё — дефолт Q7).
Guard — один активный объект по тегам (как init-отчёт §4.1); смена —
supersede (lifecycle `rule` содержит `active`/`superseded`). Память —
единственный источник состояния (канон проекта); `opencode.json` и
`config.yaml` не расширяются — вторую истину рядом с памятью не заводим;
extra-полей у `rule` не декларировано и конвейер их отвергает — значения
едут в body.

**Подстановка.** Шаблоны агентов получают плейсхолдеры: `model:
{{model.primary}}` (worker-implementer — `{{model.worker}}`). Рендер базового
набора уже владеет механизмом подстановки (`{{tool.*}}` через manifest;
неизвестных `{{…}}` словарь не валидирует — расширение контекстом `model.*`
беспрепятственно). init всегда располагает моделью (Q7/Q11) — рендер всегда
подставляет конкретные id; рендер — проекция выбора. Ветка omit
(построчное удаление `model:`-строки вместе с переводом строки) остаётся
только для `wolf sync` над легаси-проектом без routing-объекта (ниже).
Повторный init с иной моделью → re-render агентов с diff-семантикой:
`RenderAction` = `updated` при расхождении контента, `skipped` при
совпадении (семантика syncBaseSet `fresh ≠ current`); сегодня renderBaseSet
безусловно скипает существующее — расширение названо в §10.

**Влияние на wolf-router.ts.** В MVP — нулевое: плагин остаётся
playbook-роутером (детерминированная доставка методик), подстановка моделей
происходит на рендере. Runtime-подмена алиасов (сменить модель без повторного
init, следуя supersede-цепочке) плагином невозможна в opencode 1.18.25 — хука
подмены модели нет (PoC #4: provider hook = статические описания; рабочий
механизм — адаптер запуска с `--model`). Run-слой — Q9 (решён: вне MVP
онбординга, §10).

**Согласованность с `wolf sync`.** Sync ре-рендерит шаблоны агентов тем же
механизмом подстановки — без контекста моделей он перезаписал бы корректные
frontmatter литералами `{{model.*}}` (или молча прошёл бы их насквозь).
Поэтому sync читает routing-объект той же командой и подставляет `model.*`
как init; routing-объекта нет (легаси до v2) — sync опускает `model:`-строку
(построчная семантика; интерактивная сессия работает на платформенной модели
по умолчанию; `opencode run` с рамкой без `model:` падает — PoC #4).
Правка названа в §10 (исключение из «sync не трогаем» рев.3 — только
модельный контекст, прочая семантика AGENTS.md/sync не меняется).

**Смена и переопределение (bootstrap-сессия).** Штатный путь смены модели —
без повторного init: в bootstrap-сессии Mr.Wolf (или пользователь) делает
supersede routing-объекта (`wolf add` нового + `wolf supersede <old> <new>`
с body `{primary, worker}`) и запускает `wolf sync` — ре-рендер агентов
модельным контекстом (см. выше). Так переопределяется и `worker` — например,
более дешёвая модель на worker-implementer. Повторный init с `--model`
остаётся эквивалентным путём (guard/supersede/re-render, §3 «Входы init»).

**Что видят воркеры.** Модель сессии вложенного агента = значение,
подставленное в его рендер (`worker-*` → роль worker, по умолчанию =
primary); отдельного механизма для вложенных вызовов нет — рендер един.
Стюард и его шаблон steward.md — вне онбординга (Q6, §10): пайплайн его
не вызывает; модельный пин в steward.md уйдёт отдельной правкой base-sets.

### 4.6 Двухрежимный CLI (D12, Q11)

- **TTY** (`process.stdout.isTTY`): вопросы о платформе (§4.4) и одной модели
  (§4.5) с предложениями; Enter — принять дефолт/первое предложение.
  Библиотека промптов — на реализации (достаточно readline; тяжёлых
  зависимостей не добавляем).
- **Не-TTY**: флаг `--platform <ids>` (необязателен — дефолты §4.4 п.3) и
  флаг `--model <providerID/modelID>` (**обязателен**); вопросы не задаются.
- **Не-TTY без `--model` — жёсткая ошибка (Q11)**: ненулевой exit, stderr с
  понятным сообщением и точной командой: «non-interactive init requires a
  model; re-run: wolf init --model <providerID/modelID> [--platform <ids>]».
  Обоснование (корректировка D12 рев.4): тихий omit + needs-fix при exit 0

  PoC #4) за «безопасным дефолтом»; явная ошибка дешевле тихой поломки.
  CI/агентские прогоны обязаны передавать модель явно — детерминированный
  контракт. Автоинициализация (окружение само подставляет модель как дефолт

- Конфиг-файл для init не заводим до спроса (Q10): флаги уже машиночитаемы,
  второй вход — второй путь ошибок. Help-строка «non-interactive» меняется
  на «interactive in TTY; non-interactive requires --model» — смена
  обещания осознанная (решение 1450c8: агенты получают неинтерактивный
  режим, человек — интерактивный).

Остаётся как есть (скан → черновики `proposed` из фактов → doc-ref'ы →

## 6. Шаг 3 — первая сессия opencode

### 6.1 Дефолтный агент: merge-семантика в `opencode.json`

`default_agent: mr-wolf` пишет init (D2). Семантика:

- ключ отсутствует → устанавливается;
- присутствует и равен → `unchanged`;
- присутствует и отличен → **не трогаем**, исход `unchanged` с `reason:
default_agent=<значение> занят; mr-wolf не назначен` → строка уходит в
  needs-fix отчёта (канал: `PlatformInitOutcome.reason`);
- `'unchanged'` вычисляется по **обоим** ключам (mcp.wolf и default_agent):
  равенство одного не должно маскировать отсутствие второго;
- существующий `opencode.jsonc` при rewrite теряет комментарии — известное
  ограничение адаптера (ponytail-комментарий в opencode-adapter.ts). Rewrite —
  механизм один, триггер — расхождение `mcp.wolf` **или** `default_agent` (v1
  не трогала конфиг с корректным mcp.wolf, но без default_agent — v2 такой
  перепишет); jsonc-оговорка покрывает оба ключа, AST-редактор — вне MVP.

### 6.2 Сигнал «онбординг не завершён»

Канал: `wolf recap` → плагин wolf-session-start уже доставляет recap внутрь
`<session_context>` первого сообщения (L0/L1; маркер-идемпотентность, повтор
после /clear — MAJ-1). Плагин **не меняется** (D6): секция — часть recap-текста.

Тексты секции `## Onboarding` (формулировки — контракт для рамки mr-wolf);
оба текста — диалог с пользователем, никаких авто-ролей (Q6):

- bootstrap-сигнал: «Onboarding v2: init выполнен, bootstrap — нет. Уточни у
  пользователя: предложить выполнить `wolf bootstrap` (можно исполнить прямо
  в сессии: `wolf bootstrap`; в dogfood-репо Wolf — `node
dist/bootstrap/cli.js bootstrap`) или следовать пути пользователя.
  Действия с побочными эффектами — только с согласия пользователя.»
- продолжение-сигнал: «Onboarding v2: bootstrap выполнен, онбординг не
  завершён (thread active). Работай под управлением пользователя — свёртка
  черновиков, глубокое изучение проекта — как решит пользователь;
  предписанных ролей нет. Когда онбординг завершён — предложи закрыть thread
  (`wolf transition <id> completed`) и закрой с согласия пользователя.»

### 6.3 Диалог Mr.Wolf с пользователем (Q6)

Стюард из онбординга исключён (решение владельца `ec0d2d`): пайплайн никого
не спавнит и не назначает авто-ролей. Правки рамки mr-wolf для этого не
нужны — сигнал-текст секции (§6.2) есть контракт поведения, а CLI Wolf
агенту уже доступен (AGENTS.md холодного старта). Процедура:

1. **Сигнал**: каждая сессия до погашения получает секцию `## Onboarding` в
   `<session_context>` (§6.2); какой из двух текстов — решает состояние (§3).
2. **Уточнение**: Mr.Wolf спрашивает пользователя: (а) выполнить
   `wolf bootstrap` сейчас; (б) пойти путём пользователя — включая
   глубокое изучение проекта (Mr.Wolf диспетчерит worker-researcher'ом по
   своей стандартной процедуре, если пользователь того хочет — это выбор
   пользователя, не предписание пайплайна). Самозапуск bootstrap без
   согласия — запрещён (§8).
3. **Исполнение в сессии**: по согласию Mr.Wolf исполняет bootstrap прямо в
   сессии через CLI — bash-вызов `wolf bootstrap` (в dogfood-репо Wolf —
   `node dist/bootstrap/cli.js bootstrap`) из корня проекта. Вывод
   команды (черновики N, doc-ref'ы M, thread id) — обычный stdout/stderr:
   Mr.Wolf читает его как результат и докладывает пользователю. Recap в
   текущей сессии уже инъекцирован и не перечитывается — смена текста
   секции видна со следующей сессии (маркер-идемпотентность).
4. **Завершение**: онбординг закончен, когда пользователь считает его
   законченным; Mr.Wolf предлагает закрыть thread — `wolf transition <id>
completed` (или `archived`) — и выполняет по согласию. Критерий
   погашения сигнала — статус thread (Q4/D8).
5. **Свёртка черновиков** (drafts → accepted/rejected, doc-refs →
   active/stale) — по пути пользователя: вручную, воркерами под управлением
   Mr.Wolf или иначе — как решит пользователь; предписанной роли нет.
   Протокол `steward-bootstrap.md` перестаёт быть шагом онбординга
   (Стюард — мутатор по жалобам, вне онбординга, §10).

### 6.4 Безопасность: анти-цикл и анти-спам

- **Цикл невозможен структурно**: онбординг никого не спавнит (Q6) —
  нечему зациклиться; CLI-вызов bootstrap конечен и идемпотентен (§8).
- **Видимость сигнала**: сессии `worker-*` (L2) recap не получают (плагин
  режет по префиксу) — сигнал адресован только Mr.Wolf.
- **Краш/прерывание диалога — не катастрофа**: сигнал гаснет только по
  `completed`/`archived` thread'у (Q4), а не по факту команды или ответа
  пользователя. Недоведённый онбординг → сигнал в следующей сессии →
  диалог повторяется. Переходы статусов идемпотентны.
- **Спам-контроль**: внутри сессии инъекция одна (маркер); повтор после
  /clear — штатный режим всех wolf-инъекций; в рамках сессии Mr.Wolf не
  назойлив (спросил — пользователь ответил — не повторяет до следующей
  сессии). Мягкий лимит повторов между сессиями не заводим (YAGNI) —
  упорно не закрываемый онбординг виден владельцу по events.jsonl.
- Отказ владельца от онбординга вовсе: после bootstrap — закрыть thread
  вручную (`wolf transition <thread> completed` — или `archived`);
  **до bootstrap** — перевести сам init-отчёт (`wolf transition
<init-report> completed`), убив bootstrap-сигнал в зародыше. Оба пути
  сигнал гасят (документируются).

## 10. Scope и НЕ-цели

**Трогаем (при реализации)**:

- `init-project.ts` — порядок, удаление скана, opencode-исход, init-отчёт,
  входы платформ/моделей (§4.4–§4.6), routing-объект (guard/supersede);
- `generate-recap.ts` — секция Onboarding + фильтр accepted;
- `bootstrap-project.ts` — guard `status ≠ active`, указатель в currentState,
  вывод v2 (финал `renderBrief` — диалоговый, без предписаний авто-ролей, §5);
- `governance.ts` — матрица переходов: `active → paused` для work-thread
  (сегодня `paused` недостижим из `active`, а §3/§5/§8 на нём опираются —
  «владелец сознательно отложил»);
- `memory-init.ts` — двухрежимный CLI (TTY-вопросы/флаги/жёсткая ошибка
  не-TTY без `--model`), вывод v2;
- `opencode-adapter.ts` — merge default_agent (семантика §6.1, расширение
  результата writeConfig под reason-канал);
- рендер базового набора — контекст подстановки `{{model.*}}` (manifest уже
  владеет механизмом `{{tool.*}}`); ★ **diff-ветка renderBaseSet** для
  повторного init при смене моделей (существует + diff контента → `updated`,
  совпадение → `skipped`; семантика syncBaseSet `fresh ≠ current` — сегодня
  renderBaseSet безусловно скипает существующее); ★ построчный omit
  `model:`-строки — ветка только для `wolf sync` над легаси без
  routing-объекта (§4.5; init всегда подставляет);
- `wolf sync` — ★ контекст моделей при ре-рендере агентов: чтение
  routing-объекта той же командой, подстановка `model.*` как в init; без
  routing-объекта — omit `model:` (§4.5). Единственное исключение из «sync
  не трогаем» рев.3; прочая семантика sync (AGENTS.md-восприятие) не меняется;
- `templates/base/agents/*.md` — удаление жёстких пинов
  `model: zai-coding-plan/glm-5.3|5.2` (5 файлов: mr-wolf, executor-lead,
  worker-implementer, worker-reviewer, worker-researcher) → плейсхолдеры
  `{{model.primary}}`/`{{model.worker}}` (D11); steward.md — вне онбординга
  (см. НЕ-цели);
- `templates/base/AGENTS.md` (новый) + рендерер: root-цель, create/marker-append
  ветки, sync только для штампованного цельного файла, относительный путь в
  BaseSetOutcome;
- тесты ко всему выше.

Таксономия памяти (`memory-types.ts`), `createWorkThread`, store/index/FTS,
MCP-слой, `wolf sync` (семантика AGENTS.md из рев.3 — в рендерере §4.2;

**НЕ-цели**:

- Код в этой спеке — её предмет; реализация отдельным планом.
- Мультиплатформенность за пределами выбора при init: набор, плагины и
  модельный слой — opencode-only; claude получает MCP-конфиг без набора, а
  модели для него не указываются вовсе (решение e983a4: «не указывать модель
  или платформо-специфичный механизм»); расширение рендера на claude —
  base-sets.
- Runtime run-роутер алиасов моделей (смена модели без повторного init,
  обёртка `--model` по supersede-цепочке) — вне MVP онбординга (Q9; PoC #4
  доказал осуществимость, смена моделей покрывается повторным init).
- Конфиг-файл для неинтерактивного init — не заводим до спроса (Q10).
- Гарантированный авто-детект провайдеров — «по возможности» (решение
  1450c8): окружение молчит → явный вопрос/флаг, не тихий выбор.
- Фиксы F9 (нейминг/FTS doc-ref'ов) и F10 — отдельные задачи (§7).
- Автозапуск bootstrap без согласия пользователя — сознательно нет;
  исполнение в сессии — только по явному согласию (§6.3, §8).
- **Стюард — вне онбординга** (Q6): пайплайн его не вызывает и не назначает;
  рамка, протокол `steward-bootstrap.md`, permissions и жалобный контур
  (/complain, base-sets §5.3) — без изменений; модельный пин в `steward.md`
  уйдёт отдельной правкой base-sets (та же болезнь model-pin, вне этой спеки).
- Автоинициализация не-TTY (окружение/CI без явного `--model` доводится
  до рабочего состояния автоматически) — roadmap после спроса, не MVP (Q11).
- Миграция существующих проектов на v2-маркеры — не требуется (грациозная
  деградация, §8).
- Изменение lifecycle правил (accepted ≠ active) — семантика сохраняется (D9).
- Очистка/архив существующей памяти при повторном init — не входит (см. Q1).
- AST-редактор JSONC (сохранение комментариев при rewrite) — вне MVP (§6.1).
