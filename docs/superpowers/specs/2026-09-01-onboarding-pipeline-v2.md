## 1. Проблема

Первый контакт пользователя с Wolf в свежем проекте (`wolf init`) сегодня
даёт три эффекта, два из которых — дефекты онбординга:

1. **«Чужая память» (F8)**: init автоматически скает проект и кладёт 97–98
   document-ref'ов в «пустую» память. Владелец расценил это как замусоривание:
   пользователь ещё ничего не решил, а память уже «помнит» весь репозиторий.
2. **MCP не подключён (F4)**: платформенный конфиг (`opencode.json` с MCP-сервером
   и дефолтным агентом) не пишется первым init'ом — детекция платформы не видит
   каталог `.opencode/`, который сама же init создаёт позже. Пользователь обязан
   запустить init дважды, иначе первая сессия проходит без Wolf.
3. **Пайплайн не доведён до конца**: init и bootstrap существуют как отдельные
   команды без формальной связи, а свёртка черновиков Стюардом (протокол
   `steward-bootstrap.md`) не имеет ни сигнала («надо свернуть»), ни критерия
   погашения («свёрнуто»). Сообщения init (F5–F7) не объясняют, что делать дальше.

Цель v2: после `wolf init` → `wolf bootstrap` → первого запуска opencode проект
получает чистую память, подключённый MCP, дефолтного агента Mr.Wolf и
**самозаводящийся** контур доведения онбординга до конца: сессия Mr.Wolf видит
сигнал «свёртка не выполнена», вложенно вызывает Стюарда, тот приводит память
в порядок — сигнал гаснет.

## 3. Архитектура: машина состояний

```
                wolf init                    wolf bootstrap                Стюард (шаг 5
UNINIT ───────────────────────▶ INITIALIZED ─────────────────▶ BOOTSTRAPPED ──протокола)──▶ FOLDED
                                     │                              │                        │
                                     │ пишет: init-report           │ пишет: drafts,          │ пишет: accepted/rejected,
                                     │ (type=report, tag wolf-init) │ doc-refs, thread(active)│ doc-refs active/stale,
                                     │                              │                         │ thread completed, decision
                                     ▼                              ▼                         ▼
                                  читает хук (recap):            читает хук (recap):       читает хук (recap):
                                  «run wolf bootstrap»           «буди Стюарда вложенно»    тишина (сигнала нет)
```

| Состояние     | Маркер (кто пишет)                                                                       | Что читает хук                                                                |
| ------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| UNINIT        | — (`.wolf/` нет или без маркеров)                                                        | — (плагин не установлен / тишина)                                               |
| INITIALIZED   | init-report `status=active` (пишет `wolf init`)                                          | секция Onboarding: «bootstrap не выполнен → `wolf bootstrap`»                    |
| BOOTSTRAPPED  | + thread «Bootstrap: наполнение стартовой памяти» `status=active` (пишет `wolf bootstrap`)| секция Onboarding: «свёртка не выполнена → вложенный Стюард»                     |
| FOLDED        | thread `status=completed` (пишет Стюард, шаг 5)                                          | секции нет — сигнал погашен                                                     |

Правила вывода секции (детекция в `generate-recap.ts`, объекты уже в памяти —
запросов дополнительных нет):

1. thread по константе заголовка (та же, что в `bootstrap-project.ts`) найден и
   `active` → fold-сигнал (независимо от наличия init-report: покрывает legacy-
   проекты, сверстаные до v2);
2. иначе есть init-report (tag `wolf-init`, `extra.pipeline=onboarding-v2`) и
   thread отсутствует/`completed`-нет → bootstrap-сигнал;
3. иначе (нет ни того, ни другого / thread `completed`) → секции нет.

Обратных переходов нет; каждый шаг идемпотентен (§8). Состояние живёт только в
памяти Wolf — config.yaml не расширяется (D8).

## 4. Шаг 1 — `wolf init` v2

Порядок операций (правки против текущего `init-project.ts` помечены ★):

1. Проверка корня проекта (как сейчас).
2. Скелет памяти + маркер схемы (как сейчас).
3. ★ **Скан удалён** (D1/F8): `scanProject` из init исключён; `documentCount`
   уходит из результата. Полный скан — зона bootstrap (D5) и ручного `wolf scan`.
4. Рендер базового набора (wx-политика) + посев playbook'ов (как сейчас, D3
   base-sets). В набор добавляется ★ шаблон AGENTS.md (§4.2).
5. ★ Платформы (D2/F4): opencode — `writeConfig` выполняется всегда при
   отрендеренном наборе (детекция больше не гейтит opencode); claude — детекция
   до рендера, как сейчас. npx try-out — без конфигов и без набора (как сейчас;
   память и init-отчёт пишутся — плагина нет, сигнала нет, пайплайн молчит до
   полноценной установки).
6. ★ AGENTS.md (D3) — §4.2.
7. Реестр проектов (как сейчас).
8. ★ Init-отчёт — ровно один объект (D4) — §4.1.
9. ★ Вывод v2 (F5/F6/F7) — §4.3.

### 4.1 Объект-отчёт init

```
type:        report
title:       Init report: <projectName>
tags:        [wolf-init, onboarding]
created_by:  wolf-init
status:      active
extra:       pipeline=onboarding-v2, step=init   (--set)
body (markdown):
  ## Сделано (made)        — файлы набора (полные пути), конфиг платформы
                             (mcp.wolf + default_agent), AGENTS.md (created/appended/skip)
  ## Обнаружено (found)    — уже существовавшие агенты/скиллы/команды/плагины/конфиги
                             (wx-skip), существующий AGENTS.md, версии
  ## Требует поправки (needs-fix) — actionable: конфликт default_agent, «скорректируйте
                             блок Wolf в AGENTS.md», «подключите MCP перезапуском платформы»
```

Guard идемпотентности: перед записью `list({type: 'report'})` → фильтр по
`tags ∋ wolf-init` && `extra.pipeline === 'onboarding-v2'`; найден → **skip**
(в выводе: «init-report уже существует, не дублирую»). Обновление отчёта при
повторном init — не делаем: повторный init по wx-политике ничего не меняет,
менять в отчёте нечего.

### 4.2 AGENTS.md

- Отсутствует → рендер `templates/base/AGENTS.md` в корень: холодный старт
  (`wolf call` + `wolf brief`), фиксация значимого (`wolf add`/`supersede`),
  «состояние проекта — только у Wolf», лестница приоритетов, указатели на
  docs. Штамп `wolf:rendered` + маркер `<!-- wolf:onboarding v2 -->`.
- Существует, маркера нет → в конец дописывается маркированный блок (тот же
  контент, обёрнут маркерами `<!-- wolf:onboarding v2 -->` … `<!-- /wolf:onboarding -->`).
  Чужой контент не трогаем (D3: «дополнение/пометка, не перезапись»).
- Маркер есть → skip (в отчёт: found).

### 4.3 Вывод init (F5/F6/F7)

- Каждая строка base set — с путём от корня проекта (не «SKILL.md created», а
  `.opencode/skills/wolf-debug/SKILL.md created`).
- «Restart your agent platform…» — только если MCP реально записан в этом
  прогоне; «skipped»-формулировки переформулированы без «агенты не установлены».
- Финальный блок «Дальше»: (1) `wolf bootstrap` — первичный образ памяти;
  (2) перезапуск opencode — подхватить MCP и дефолтного агента Mr.Wolf.
- npx try-out — прежняя подсказка про установку.

## 5. Шаг 2 — `wolf bootstrap` v2

Остаётся как есть (скан → черновики `proposed` из фактов → doc-ref'ы →
work-thread; дедуп по title, переиспользование thread). Правки:

1. ★ Guard «fold уже был»: существующий thread `completed` → no-op с сообщением
   «Онбординг уже свёрнут (thread completed); для пересоздания — владелец
   вручную». Иначе повторный bootstrap после fold регрессировал бы память к
   черновикам (дедуп смотрит только `proposed`).
2. ★ «Указатель что и когда сделано» (D5) — расширяется существующий thread:
   - `extra`: `pipeline=onboarding-v2`, `init_report=<id init-отчёта>` (связь
     шагов; ищется по tag `wolf-init`, отсутствует — поле опускается, legacy);
   - `currentState` при создании: `init <ts> ✓ (report <id>); bootstrap <ts>:
     черновиков N, document-ref'ов M` — «что и когда»; дальнейшие события —
     в events.jsonl автоматически.
3. Doc-ref'ы: создаются здесь и только здесь (D5). Нейминг id и поведение FTS —
   без изменений до отдельного фикса F9 (§7).

## 6. Шаг 3 — первая сессия opencode

### 6.1 Дефолтный агент

`default_agent: mr-wolf` в `opencode.json` пишет init (D2). Ключ существует и
отличается — не трогаем, needs-fix в отчёт. Существующий равный — `unchanged`.

### 6.2 Сигнал pending-fold

Канал: `wolf recap` → плагин wolf-session-start уже доставляет recap внутрь
`<session_context>` первого сообщения (L0/L1; маркер-идемпотентность, повтор
после /clear — MAJ-1). Плагин **не меняется** (D6): секция — часть recap-текста.

Тексты секции `## Onboarding` (формулировки — контракт для рамки mr-wolf):

- bootstrap-сигнал: «Onboarding v2: init выполнен, bootstrap — нет. Предложи
  владельцу запустить `wolf bootstrap` (запуск — по подтверждению владельца).»
- fold-сигнал: «Onboarding v2: артефакты init+bootstrap в памяти, свёртка не
  выполнена. Вложенно вызови Стюарда (task tool, subagent_type=steward, бриф:
  протокол docs/guide/steward-bootstrap.md). Не вызывай Стюарда напрямую и не
  сворачивай сам.»

### 6.3 Вложенный вызов Стюарда

- Механизм: task tool с `subagent_type=steward` из сессии Mr.Wolf. Требует
  правки шаблона рамки mr-wolf: `permission.task` → `{"*": deny,
  "executor-*": allow, "steward": allow}` и шаг процедуры «Onboarding-сигнал →
  один вложенный вызов Стюарда → принять отчёт → убедиться, что секция погасла
  (`wolf recap`)». Steward уже `mode: all` — виден как subagent.
- Fallback (документированный): `opencode run --agent steward "…"` (PoC #3).
- Стюард делает свёртку строго по `docs/guide/steward-bootstrap.md` (шаги 1–6:
  сверить черновики с фактами → accepted/rejected → doc-refs active/stale →
  thread completed → decision). Шаг 5 закрывает thread → критерий D8 → сигнал
  погашен.
- Границы Стюарда сохраняются: рамка «не аналитик» — свёртка = сверка фактов и
  переходы статусов, не исследование; глубокое изучение проекта за пределами
  свёртки — отдельная задача Mr.Wolf (worker-researcher), вне этого пайплайна.

### 6.4 Безопасность: анти-цикл и анти-спам

- **Цикл невозможен структурно**: steward `permission.task: deny` — никого не
  спавнит; mr-wolf спавнит Стюарда максимум один раз за сессию (процедура);
  воркеры Стюарда не видят (L2 без recap — плагин уже режет).
- **Краш свёртки — не катастрофа**: сигнал гаснет только по `completed`,
  а не по факту вызова Стюарда. Недоделанная свёртка → сигнал в следующей
  сессии → повтор. Переходы статусов идемпотентны.
- **Спам-контроль**: внутри сессии инъекция одна (маркер); повтор после /clear —
  штатный режим всех wolf-инъекций; в рамках сессии Mr.Wolf не назойлив
  (предложил — владелец отказал — не повторяет до следующей сессии).
- Отказ владельца от онбординга вовсе: закрыть thread вручную
  (`wolf transition <thread> completed`) — сигнал гаснет (документируется).

## 8. Идемпотентность и частичные прогоны

| Сценарий                          | Поведение                                                                                                                                                                                             |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Повторный `wolf init`             | wx-политика набора, skip посева, guard отчёта (§4.1), AGENTS.md по маркеру — ничего не перезаписывается. Существующая память **не трогается** (init никогда не чистит/архивирует; «чистая память» — свойство первого прогона, не повторного) |
| Повторный `wolf bootstrap`        | Дедуп черновиков (сейчас) + guard completed (§5.1)                                                                                                                                                    |
| Краш между init и bootstrap       | Состояние INITIALIZED устойчиво: скелет и отчёт атомарны на своих шагах; хук честно говорит «bootstrap не выполнен»                                                                                   |
| Краш внутри bootstrap             | Дедуп по title довершает начатое; thread переиспользуется по заголовку                                                                                                                                |
| Краш внутри свёртки               | Сигнал остаётся (thread active); следующая сессия повторяет вызов; переходы идемпотентны                                                                                                              |
| init есть, bootstrap пропущен     | Хук: bootstrap-сигнал; Mr.Wolf предлагает команду владельцу (не запускает сам — побочные эффекты только с согласия)                                                                                   |
| Legacy-проект (до v2)             | Нет init-report: если thread active → fold-сигнал работает; если thread completed → тишина. Деградация грациозная, миграция не требуется                                                              |

## 9. План верификации

Сценарий на площадке (`playground/`, pristine-reset), каждый шаг — чек:

1. **pristine → `wolf init`**: (а) `wolf list --type document-ref` → пусто
   (F8 закрыт); (б) base set 6/13/3/2 по путям в выводе (F5); (в) `opencode.json`
   существует, содержит `mcp.wolf` и `default_agent: mr-wolf` (F4 закрыт);
   (г) AGENTS.md создан с маркером; (д) ровно один init-report с секциями
   made/found/needs-fix; (е) сообщение «Дальше» упоминает bootstrap (F7).
2. **Повторный `wolf init`**: все файлы skipped, отчёт не задублирован, вывод
   без «restart»-шума про уже записанное.
3. **`wolf bootstrap`**: черновики proposed ≥ 2, doc-ref'ы созданы, thread
   active c extra-связью на init-report; повторный запуск — дедуп.
4. **Первая сессия** (`opencode` в площадке): (а) агент по умолчанию — Mr.Wolf;
   (б) в первом сообщении есть `<session_context>` с recap, содержащим секцию
   `## Onboarding` с fold-сигналом.
5. **Вложенный Стюард**: Mr.Wolf вызывает task tool `subagent_type=steward`;
   Стюард выполняет протокол: правила → accepted, refs → active/stale,
   thread → completed, decision записан.
6. **Погашение**: следующая сессия — секции Onboarding нет; правила видны в
   recap (F11 закрыт: «Правила (accepted/active)»).
7. **Ретресс-контроль**: `npm run check` репозитория Wolf зелёный; повторный
   bootstrap после fold — no-op (guard).

Unit/integration (для реализации): recap-секция в трёх состояниях (§3);
init без скана; guard отчёта; merge-политика default_agent
(absent/present-equal/present-different); AGENTS.md
(absent/present-marker/present-no-marker); bootstrap guard completed;
идемпотентность повторов каждого шага.

## 10. Scope и НЕ-цели

**Трогаем (при реализации)**: `init-project.ts` (порядок, удаление скана,
opencode-исход), `generate-recap.ts` (секция + фильтр accepted), 
`bootstrap-project.ts` (guard, extra), `memory-init.ts` (вывод),
`templates/base/agents/mr-wolf.md` (permission + процедура),
`templates/base/AGENTS.md` (новый), рендерер (раскладка AGENTS.md),
`opencode-adapter.ts` (merge default_agent), тесты.

**НЕ-цели**:

- Код в этой спеке — её предмет; реализация отдельным планом.
- Мультиплатформенность: пайплайн настраивается под opencode (единственная
  платформа с рендером набора, D1 base-sets); claude — только прежняя детекция.
- Фиксы F9 (нейминг/FTS doc-ref'ов) и F10 — отдельные задачи (§7).
- Автозапуск bootstrap из сессии без ведома владельца — сознательно нет (§8).
- Миграция существующих проектов на v2-маркеры — не требуется (грациозная
  деградация, §8).
- Изменение lifecycle правил (accepted ≠ active) — семантика сохраняется (D9).
- Очистка/архив существующей памяти при повторном init — не входит (см. Q1).
