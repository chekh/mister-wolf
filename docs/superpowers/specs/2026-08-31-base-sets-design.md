## 1. Проблема

Концепция предполагает трёхуровневую организацию агентов (канон §5.0:
L0 координатор → L1 executor → L2 воркеры), но сами агенты, скиллы и команды
не включены в репозиторий Wolf, и `wolf init` не создаёт базовых наборов.
Пользователь, добавивший Wolf в проект, не получает агентской формы — только
память. Цель: после `wolf init` проект сразу получает рабочий набор
агентов/скиллов/команд, отражающий накопленный опыт этого проекта и лучшее
из superpowers.

## 3. Архитектура

```
npm-пакет wolf
├── templates/base/                  # нейтральный контент (без имён тулов harness'а)
│   ├── agents/*.md                  # рамка + объявление лица (§4)
│   ├── skills/<имя>/SKILL.md        # процессы; вызовы только wolf CLI
│   ├── commands/*.md                # рамочные команды (паттерн analyze-doc)
│   └── plugins/                     # шаблоны инъекции состояния
├── src/adapters/render/             # рендерер
│   ├── manifest.ts                  # tool-mapping per harness
│   └── opencode/                    # первый адаптер: agents/, skills/, command/, plugins/
└── src/app/use-cases/               # init (расширяется), sync (новый)
```

- Рендер = (а) подстановка имён тулов из манифеста harness'а — плейсхолдеры
  вида `{{tool.<имя>}}` (например `{{tool.task}}` → `task` + `subagent_type`),
  (б) генерация frontmatter (model/tools/permissions; enforcement — канон §6
  п.5 «автономия по пробегу», детали архив v2.0 §2.6), (в) раскладка в
  `.opencode/{agents,skills,command,plugins}` целевого проекта. Зависимость
  однонаправленная: адаптер → Wolf, никогда наоборот (канон §7.3).
- **Дистрибуция шаблонов (C1)**: `templates/` включается в npm-пакет —
  `package.json` → `"files": ["dist", "templates"]`. Рендерер читает шаблоны
  из корня установленного пакета (не из `dist/`), поэтому `build: tsc` правок
  не требует.
- Язык шаблонов — **русский** (рабочие объекты, «внутрянка»; правило
  «EN-витрина, RU-внутрянка» относится к витринным документам вроде README).

## 4. Принцип «рамка + лицо» (для всех агентов)

```
Агент = РАМКА + ЛИЦО (0..n)
├── Рамка     — статична: роль, границы, запреты, протокол контура лица.
│               Меняется только sync'ом с новой версией набора.
├── Лицо      — мутирующий контекст = playbook в памяти (тег, версия,
│               supersede-цепочка) + триггер активации.
│               Нет playbook'а → агент безликий (статичное поведение) —
│               это данные, не структурное исключение.
├── Мутатор   — всегда Стюард (жалоба → новая версия playbook'а через
│               supersede). Воркеры и координаторы сами ничего не мутируют
│               (канон §3.4 — атрибуция `steward:<лицо>`, §4.2 — инвариант
│               вызова).
└── Доставка  — per-harness, решает рендерер (канон §7.1, три механизма):
    ├── plugin-inject: плагин-инъекция по agent-id маркеру, ноль расходов
    │   в рантайме (opencode; доказано PoC #4) — основной
    ├── pull: агент сам делает `wolf search "<тег> playbook"` перед задачей
    │   (generic fallback)
    └── bake-in: sync вживляет актуальную версию playbook'а в файл со
        штампом; источник playbook'а — память целевого проекта, при пустой —
        стартовые playbook'и посева (§7). Мутации доезжают следующим sync'ом
        (minimal-платформы)
```

- Лицо = playbook + триггер + конвейер + экспозиция (канон §4.3 «Лица —
  открытый реестр»). Матрица лиц Стюарда — не особый случай, а «много лиц +
  триггерный выбор» того же механизма.
- Терминология фиксируется: **рамка / лицо / мутатор / доставка**. Слоты,
  профили, портреты — не вводим.
- Обязательная тройка атрибутов шаблона агента: **рамка + лицо + способ
  доставки** (единая формулировка для §5.1 и критерия §11.3).

### Исправляемые отклонения текущих файлов от канона

1. `steward.md` захардкодил протокол Наставника в рамке → протокол переезжает
   в playbook памяти (посев, §7), рамка остаётся с матрицей лиц.
2. `apprentice.md` — самомутация (агент сам пишет новую версию playbook'а) →
   нарушает канон §3.4/§4.2: мутатор всегда Стюард. Агент исключается из
   набора (D2); функция раскладывается: исполнение — worker-researcher,
   методика — playbook в памяти, эволюция — жалоба → Стюард-Наставник.

## 6. wolf-review — doc-review скилл

В superpowers скилла ревью документов нет (оба code-review — про код).
Строим из доказанных частей:

- **Рамка**: паттерн analyze-doc — методика в памяти Wolf, эволюционирует без
  рестарта; файл — тонкая рамка.
- **Мульти-линзовость**: линзы = playbook-объекты; диспетч lens-воркеров
  (worker-reviewer) в чистых сессиях — изоляция бьёт по слепым зонам
  саморевью. Перспективы для документов: полнота → консистентность →
  типоспецифичные (осознанное отклонение от REVIEW-001 архива v2.0 §2.5:
  security-линза опущена). Узкий ревьюер, чужие замечания запрещены.
- **Оркестратор цикла** — агент mr-wolf по протоколу скилла (спавн линз,
  дедуп, подсчёт, счётчик раундов). Продуктового кода оркестрации нет (§10).
- **Контракты**: `SUMMARY: X critical / Y major / Z minor` +
  `VERDICT: APPROVED | CHANGES_REQUIRED` (стандартизировано; в REVIEW-001
  архивной версии использовалось «CHANGES»).
- **Критерий сходимости**: 0 critical / 0 blocking **или** лимит раундов
  (по умолчанию 3).
- **Цикл**: автор правит → перезапуск только упавшей линзы. Конфликты находок
  между линзами разрешает владелец (слепой судьи в MVP нет).

## 7. Механика init / sync

- **`wolf init`**: скелет памяти (как сейчас) + рендер базового набора сразу
  (D3) + **посев стартовых playbook'ов** в память целевого проекта
  (детерминированная запись через memory-store, идемпотентно по тегу+версии:
  протокол Наставника, стартовые методики воркеров — M3).
  - Политика записи — **wx-политика** (флаг `'wx'`, EEXIST игнорируется):
    создаёт только отсутствующее; существующие файлы не трогает — независимо
    от штампа (штампованные обновляет только sync — M1).
  - Рендер подчиняется guard'у `isNpxRun()`: в npx try-out режиме набор не
    пишется (M17).
  - Вывод пользователю: сводка «создано / пропущено» по файлам и seeded
    playbook'ам (m4).
- **`wolf sync`**: повторный рендер из шаблонов установленного пакета.
  - Обновляет **только** штампованные файлы. Штамп ставится и init'ом, и
    sync'ом, синтаксис по типу файла (M14): `<!-- wolf:rendered
base=<имя> set=<версия пакета wolf> -->` в `.md`, `// wolf:rendered …`
    в `.ts/.js`. Источник версии — `package.json` установленного пакета (M11).
  - Файлы без штампа не трогает; конфликт (unstamped на месте шаблонного) —
    в отчёт с опциями разрешения: переименовать / удалить / принять текущий
    (M10). Решает владелец.
  - Orphaned stamped-файлы (шаблон исчез из пакета) — в отчёт, авто-удаления
    нет (m3).
- **Откат**: штампованные файлы безопасно удалять вручную (список — в отчёте
  sync); тулинг отката/удаления набора — вне MVP (M13).
- **Стюард и sync**: документированный сценарий — Стюард инициирует sync
  после смены версии набора (D4); отдельного кода нет.

## 8. Обработка ошибок

- Renderer громко падает на неизвестном шаблоне/манифесте без маппинга.
- `sync` молчит на unstamped файлах (только отчёт).
- `init` идемпотентен (wx-политика).
- Доставка лиц: сбой pull-режима (wolf недоступен) → агент работает по рамке
  и сообщает об отсутствии лица; plugin-inject fail-safe (тихий скип).

## 9. Тестирование

- **Unit**: подстановка плейсхолдеров `{{tool.*}}`; штампы по типам файлов
  (запись/чтение/сравнение версий); конфликт-детекция; посев playbook'ов
  (идемпотентность); один нейтральный шаблон → три доставки со структурными
  проверками (§11.4); сценарии ошибок §8: fail-fast рендера, pull-fallback,
  plugin fail-safe (m13).
- **Integration**: `init` в tmp-проекте создаёт полный набор (агенты/скиллы/
  команды/плагины + память с seeded playbook'ами); повторный init ничего не
  ломает; `sync` обновляет stamped, не трогает unstamped, репортит конфликты
  и orphaned.
- **E2E**: init → структура `.opencode/` + `.wolf/` присутствует →
  `npm run check` **репозитория Wolf** зелёный (tmp-проект проверяется
  структурными тестами — m14).

## 10. Scope

**Трогаем**: `templates/` (новый), `src/adapters/render/` (новый),
`src/app/use-cases/` (init расширяется, sync новый), CLI-команда `sync`,
`package.json` → `files` (C1), тесты.

**Не трогаем**: ядро памяти (store/index/FTS — кроме детерминированного посева
через существующий store-API), чистку мёртвых зависимостей
`.opencode/package.json`, Web GUI, MCP-слой.

**Смежное, вне scope (отдельные задачи)**: миграция собственного `.opencode/`
Wolf на рендер из шаблонов (dogfood, M15/M16); судьба `wolf scaffold`
(`scaffold-agent.ts` — второй генератор тех же путей: унифицировать или
удалить после реализации, M18).

## 11. Критерии приёмки реализации

1. `wolf init` в чистом проекте создаёт: память (`.wolf/`) + посев стартовых
   playbook'ов + 6 агентов + 13 скиллов + 2 команды + 2 плагина в
   `.opencode/`; сводка создано/пропущено выведена.
2. Повторный `init` не перезаписывает существующие файлы (wx-политика);
   `sync` обновляет только штампованные, unstamped не трогает, конфликты и
   orphaned видны в отчёте.
3. Каждый шаблон агента содержит обязательную тройку: рамка + лицо (тег
   playbook'а) + способ доставки; у Стюарда — матрица лиц; протокол
   Наставника — в seeded playbook'е, не в рамке.
4. Один нейтральный шаблон рендерится в три доставки; структурный чек-лист
   unit-теста: plugin-inject → agent-id маркер присутствует; pull → команда
   `wolf search "<тег> playbook"` в рамке; bake-in → вживлённый playbook +
   штамп (M5).
5. wolf-review: **ручная приёмка** (догфудинг) — линзовый прогон mr-wolf'ом
   на тестовом документе даёт SUMMARY/VERDICT и останавливается по критерию
   сходимости или лимиту раундов; автотест цикла не требуется (M4).
