## 1. Проблема

Концепция предполагает трёхуровневую схему агентов (wolf → executor → workers),
но сами агенты, скиллы и команды не включены в репозиторий Wolf, и `wolf init`
не создаёт базовых наборов. Пользователь, добавивший Wolf в проект, не получает
агентской формы — только память. Цель: после `wolf init` проект сразу получает
рабочий набор агентов/скиллов/команд, отражающий накопленный опыт этого проекта
и лучшее из superpowers.

## 2. Принятые решения

| # | Решение | Альтернатива, которую отклонили |
|---|---|---|
| D1 | Нейтральные шаблоны + рендер per-harness; opencode — первый адаптер | Только opencode (YAGNI-риск признан оправданным в обратную сторону: канон §7.3 требует per-platform рамок) |
| D2 | Ядро агентов — по концепции и аудиту использования (итог: 6, см. §5.1); проработка заново, не копирование | Все 16 существующих агентов (часть — экспериментальные PoC) |
| D3 | `wolf init` рендерит набор сразу, включая Стюарда | Скелет + наполнение Стюардом (§7.4) — самоубийственно: Стюарда некому вызвать, пока его файл не материализован (курица-и-яйцо) |
| D4 | `wolf sync` — единственная механика регенерации; Стюард — документированный сценарий вызова sync, без отдельного кода | Sync только через агента |
| D5 | Единый принцип «рамка + лицо» для всех агентов (канон §4, без умножения терминов) | Слоты мутаций только у воркеров, координаторы статичны |
| D6 | Именование смешанное: 7 ролей §2.10 → `wolf-*`; дисциплинарные скиллы — описательные имена | Всё в `wolf-*` (потеря гранулярности) / всё как в superpowers (игнор канона) |

## 3. Архитектура

```
npm-пакет wolf
├── templates/base/                  # нейтральный контент (без имён тулов harness'а)
│   ├── agents/*.md                  # рамка + объявление лиц (§4)
│   ├── skills/<имя>/SKILL.md        # процессы; вызовы только wolf CLI
│   ├── commands/*.md                # рамочные команды (паттерн analyze-doc)
│   └── plugins/                     # шаблоны инъекции состояния
├── src/adapters/render/             # рендерер
│   ├── manifest.ts                  # tool-mapping per harness
│   └── opencode/                    # первый адаптер: agents/, skills/, command/, plugins/
└── src/app/use-cases/               # init (расширяется), sync (новый)
```

Рендер = (а) подстановка имён тулов из манифеста harness'а
(`Task → task + subagent_type`, `Skill → skill`), (б) генерация frontmatter
(model/tools/permissions по §2.6 enforcement), (в) раскладка в
`.opencode/{agents,skills,command,plugins}` целевого проекта.
Зависимость однонаправленная: адаптер → Wolf, никогда наоборот (§7.3).

## 4. Принцип «рамка + лицо» (для всех агентов)

```
Агент = РАМКА + ЛИЦА (0..n)
├── Рамка     — статична: роль, границы, запреты, протокол контура лица.
│               Меняется только sync'ом с новой версией канона.
├── Лицо      — мутирующий контекст = playbook в памяти (тег, версия,
│               supersede-цепочка) + триггер активации.
│               Нет playbook'а → агент безликий (статичное поведение) —
│               это данные, не структурное исключение.
├── Мутатор   — всегда Стюард (жалоба → новая версия playbook'а через
│               supersede). Воркеры и координаторы сами ничего не мутируют.
└── Доставка  — per-harness, решает рендерер:
    ├── plugin-inject: плагин-инъекция по agent-id маркеру, ноль расходов
    │   в рантайме (opencode; доказано PoC #4)
    ├── pull: агент сам делает `wolf search "<тег> playbook"` перед задачей
    │   (generic fallback)
    └── bake-in: sync вживляет актуальную версию playbook'а в файл со
        штампом; мутации доезжают следующим sync'ом (minimal-платформы)
```

- Лицо = playbook + триггер + конвейер + экспозиция (формула §4 канона).
  Матрица лиц Стюарда (Наставник/Библиотекарь/Архивариус) — не особый случай,
  а «много лиц + триггерный выбор» того же механизма.
- Терминология фиксируется: **рамка / лицо / мутатор / доставка**.
  Слоты, профили, портреты — не вводим.

### Исправляемые отклонения текущих файлов от канона

1. `steward.md` захардкодил протокол Наставника в рамке → протокол переезжает
   в playbook памяти, рамка остаётся с матрицей лиц.
2. `apprentice.md` — самомутирующийся агент (сам пишет новую версию playbook'а)
   → противоречит инварианту «воркер сам себя не мутирует» (PoC #3).
   Агент исключается из набора (D2); функция раскладывается: исполнение —
   worker-researcher, методика — playbook в памяти, эволюция — жалоба →
   Стюард-Наставник.

## 5. Состав базового набора

### 5.1 Агенты — 6

| Агент | Уровень | Роль | Лица на старте |
|---|---|---|---|
| mr-wolf | L0 | координатор: брифы, решения, приёмка отчётов; кода не касается | нет (безликий, thin §2.2) |
| executor-lead | L1 | декомпозиция брифа, диспетчеризация воркеров, отчёт | нет |
| worker-implementer | L2 | однозадачные правки кода; task: deny; allowlist брифа | playbook методики (жалобный контур) |
| worker-reviewer | L2 | ревью против брифа, VERDICT-контракт | playbook критериев |
| worker-researcher | L2 | исследование кода/документов/веба, findings; исполнение /analyze-doc | playbook методики анализа |
| steward | фон | контур мутаций: матрица лиц (Наставник/Библиотекарь/Архивариус), вызов вложенный по триггеру | 3 лица (Наставник работает, остальные — по мере реализации) |

Каждый агент прорабатывается заново по концепту: контекст-бюджеты (§2.2),
enforcement (§2.6: permission.task, depth, allowlist), тиринг моделей (§2.9).
Проверяемое требование: в спеке агента явно указано, что в рамке, какой у него
тег лица, кто мутатор.

**Исключены явно** (аудит: следов использования нет, one-shot коммит a280475):
`boss`, `check-architecture`, `check-coverage`, `check-placeholders`,
`check-types`, `refine-applier`, `refine-resolver`. Их функция
(детерминированные проверки) живёт в конвейере активации/hard validators.
**PoC-артефакты**: `apprentice-inj` (доставку решает плагин), `analyzer-static`
(контрольная группа A/B).

## 6. wolf-review — doc-review скилл

В superpowers скилла ревью документов нет (оба code-review — про код).
Строим из доказанных частей:

- **Рамка**: паттерн analyze-doc — методика в памяти Wolf, эволюционирует
  без рестарта; файл — тонкая рамка.
- **Мульти-линзовость**: линзы = playbook-объекты; диспетч lens-воркеров
  (worker-reviewer) в чистых сессиях — изоляция бьёт по слепым зонам
  саморевью. Перспективы по REVIEW-001 (§2.5): полнота → консистентность →
  типоспецифичные; узкий ревьюер, чужие замечания запрещены.
- **Контракты**: `SUMMARY: X critical / Y major / Z minor` +
  `VERDICT: APPROVED | CHANGES_REQUIRED`.
- **Критерий сходимости**: 0 critical / 0 blocking **или** лимит раундов
  (по умолчанию 3) — бюджет против бесконечного цикла.
- **Цикл**: автор правит → перезапуск только упавшей линзы.

## 7. Механика init / sync

- **`wolf init`**: существующий скелет памяти (без изменений) + рендер
  базового набора сразу (D3 — включая Стюарда). Идемпотентность: `wx`-политика
  (существующие файлы не перезаписываются), повторный запуск безопасен.
- **`wolf sync`**: повторный рендер из шаблонов установленного пакета.
  Перезапись **только** файлов со штампом
  `<!-- wolf:rendered base=<имя> canon=<версия> -->`. Файлы без штампа
  (правленные вручную) не трогаются; конфликт (unstamped на месте
  шаблонного) — в отчёт пользователю.
- **Стюард и sync**: документированный сценарий — Стюард инициирует sync
  после смены версии канона (D4); отдельного кода нет.

## 8. Обработка ошибок

- Renderer громко падает на неизвестном шаблоне/манифесте без маппинга.
- `sync` молчит на unstamped файлах (только отчёт).
- `init` идемпотентен (EEXIST-политика как у текущего config.yaml).
- Доставка лиц: сбой pull-режима (wolf недоступен) → агент работает по рамке
  и сообщает об отсутствии лица; plugin-inject fail-safe (тихий скип).

## 9. Тестирование

- **Unit**: подстановка tool-mapping; штампы (запись/чтение/сравнение версий);
  конфликт-детекция; один нейтральный шаблон → три способа доставки →
  семантика мутаций сохраняется.
- **Integration**: `init` в tmp-проекте создаёт полный набор
  (агенты/скиллы/команды/плагины + память); повторный init ничего не ломает;
  `sync` обновляет stamped, не трогает unstamped.
- **E2E**: init → структура `.opencode/` присутствует → `npm run check` зелёный.

## 10. Scope

**Трогаем**: `templates/` (новый), `src/adapters/render/` (новый),
`src/app/use-cases/` (init расширяется, sync новый), CLI-команда `sync`,
тесты.
**Не трогаем**: ядро памяти (store/index/FTS), чистку мёртвых зависимостей
`.opencode/package.json` (отдельная задача), Web GUI, MCP-слой.

## 11. Критерии приёмки реализации

1. `wolf init` в чистом проекте создаёт: память (как раньше) + 6 агентов +
   13 скиллов + 2 команды + 2 плагина в `.opencode/`.
2. Повторный `init`/`sync` не перезаписывает файлы без штампа; штампованные
   обновляет; конфликт виден в отчёте.
3. Каждый шаблон агента содержит рамку + объявление лица + способ доставки;
   у Стюарда — матрица лиц; протокол Наставника — в playbook'е, не в рамке.
4. Один нейтральный шаблон рендерится в три доставки (plugin-inject / pull /
   bake-in) с сохранением семантики мутаций (unit-тест).
5. wolf-review: линзовый прогон на тестовом документе даёт SUMMARY/VERDICT
   и останавливается по критерию сходимости или лимиту раундов.
6. `npm run check` зелёный; полное E2E после плана (правило проекта).
