## 1. Контекст и цель

Init остаётся главным барьером первого запуска: обязательные файлы, обязательный вопрос о модели
(формат «провайдер/модель», который новичок не может принять), небезопасный повторный запуск на
живом проекте. Отзывы зафиксированы в треде `b0368a`; вердикт unpin принят (`592fc6`). Отдельно
принята проблема worktree: память `.wolf/` не следует за worktree — изоляция делает агентов слепыми,
наивный шаринг заражает доставку чужим контекстом (`08fbf3`). Хвосты №8 (durability/секреты) и №9
(объяснимость пустого call и ошибок) закрывают гигиену доставки; docs-синхронизация закрепляет
внешние поверхности.

Цель 2.16 — **первый запуск без барьеров (init, который не требует решений, которых нет у новичка),
честная доставка контекста через worktree-границу и гигиена доставки (durability, секреты,
объяснимость)**.

## 2. Принципы

- P1 **Init проектируется один раз под финальный набор** (scaffold-kind, INDEX, новый base-set) —
  закрепление `c62cfc`; исключить переделку init в следующих волнах.
- P2 **Узкий дефолт доставки по асимметрии цены** (`08fbf3`): недоставка лечится промоушеном одной
  командой, заражение — потраченными разборами без ловца.
- P3 **Данные неприкосновенны** (наследие 2.14): существующие user pins не трогаем; миграции ничего
  не удаляют у настроенных проектов; guard'ы отказывают, а не перезаписывают.
- P4 **Состав не расширяется**: вне WP1–WP6 и вердиктов по T4–T7 — только открытые вопросы;
  лица/версии/async/архив — волны B/C, глобальная память — отклонена владельцем.
- P5 **Честность о непроверенном**: платформенное наследование моделей не проверено ([НЕПР]) — до
  прохождения exit-критерия наследование не заявляется работающим.

## 4. WP1 — Init-ядро 2.0

**Проблема.** `wolf init` требует решений, которые новичок не может принять: обязательный набор
файлов, вопрос о модели, отсутствие безопасного повторного запуска. Повторный init на живом проекте
не показывает последствий. Метрика активации не определена (Q11 — дефолт в §11).

**Решение.**

- Снятие обязательности файлов: базовый init создаёт только согласованный минимум по явному
  согласию; всё остальное — опции.
- Конфигурируемое интервью: дефолт — один развёрнутый вопрос о назначении и соглашениях проекта;
  ответ сеется в стартовую память (decision/note), не в governing-инструкции. Механизм конфигурации
  состава интервью — вне 2.16 (дефолт зашит; конфигурируемость — кандидат следующей волны).
- Неинтерактивный путь: init без TTY завершается без обязательных вопросов (после WP2 — и без
  `--model`).
- Осторожный init (K6): повторный init на живом проекте показывает diff и требует подтверждения;
  blind-reseed base-set запрещён (прецедент ограничений базовых наборов, спека `2026-08-31-base-sets-design.md`).
- Проектирование один раз под финальный набор: scaffold-kind (`wolf scaffold artifact` — спека
  конвейера A1), INDEX (`docs/dev/INDEX.md` — A2), новый base-set (спека базовых наборов) — init не
  переписывается под них в следующих волнах (P1).
- Без доинформирования: онбординг-механики «догоняющего обучения» не вводятся (out of scope драфта).

**Краевые случаи.** Пустой/битый конфиг — init трактуется как первый запуск; отказ на
подтверждении diff — проект не изменён (exit до записи); init в linked worktree — memory-root
резолвится в общий `.wolf/` (WP3), рендеры `.opencode/` создаются локально в worktree; порог
«минимума файлов» — минимальный набор: маркер onboarding-блока в AGENTS.md/CLAUDE.md, скелет
`.wolf/memory/`, конфиг (дефолт делегирован, владелец может ветировать).

**Отвергнутые альтернативы.** Доинформирование/интервью-ветвление по ответам (вне волны, тред
`b0368a`); автосоздание полного профиля без согласия (против «явного согласия»); отдельная команда
«dry-run init» — осторожный init с diff уже покрывает (YAGNI).

## 5. WP2 — Unpin моделей по умолчанию

**Проблема.** Init спрашивает модель («не помню формат провайдер/модель») и пиннит model-строки в
профили — смена платформенного дефолта не подхватывается («не могу сменить модель субагентов в
сессии»). Вердикт `592fc6`: init больше не спрашивает модель и не пиннит model-строки.

**Решение.**

- Omit-режим model-строк в генерируемых профилях — база уже в коде (`substitute()` в
  `src/adapters/render/manifest.ts`, статически зафиксировано на 2.14, драфт A2); init по умолчанию
  не пишет model-строки.
- `--model` остаётся opt-in, включая dogfood-routing проекта; неинтерактивный init без обязательного
  `--model`.
- Существующие user pins не трогаются (мера безопасности миграции; предложено драфтом, принимается
  спекой) — **делегированное решение, владелец может ветировать**.
- Q-S: supersede «Q11-старого» (вопрос о модели при init обязателен, «пропустить нельзя») и
  «Q7-старого» (worker=primary, воркеру пиннится primary-модель) из треда `b0368a` — **механический
  процесс при влитии WP2, не отдельная задача** (делегированное решение): при приёмке WP2 исполнитель
  ищет старые объекты-решения (`wolf search`); если зафиксированы отдельными объектами —
  `wolf supersede <old-id> <id-решения волны 2.16>`, если нет — фиксирует факт supersede строкой в
  релизном решении 2.16 в память Wolf.

**Краевые случаи.** Платформенное наследование не проверено [НЕПР] — закрывается e2e без сети
(§14, критерий 1); профиль с сохранённым user pin после апгрейда читается как есть; dogfood-routing
проекта волка продолжает работать через opt-in.

**Отвергнутые альтернативы.** Инструмент смены моделей субагентов — отклонён (`592fc6`, YAGNI: без
пиннинга боль исчезает); удаление чужих model-строк у настроенных проектов — вне волны (P3);
интерактивный выбор «унаследовать или пиннить» — лишний вопрос там, где дефолт один.

## 6. WP3 — Память через common-dir, scope-гейтинг, нормализация related-путей

Спека из трёх механизмов, делить нельзя (`08fbf3` дословно, ничего не теряется):

### 6.1 Резолв memory-root через git common-dir

Linked worktree резолвит memory-root в `.wolf/` основного чекаута (`git rev-parse --git-common-dir`);
рендеры `.opencode/` остаются локальными для worktree — это коммитируемые git-артефакты. Fallback:
вне git-репозитория или без common-dir — локальный `.wolf/` как сегодня.

**Миграция существующих проектов.** Локальные `.wolf/`, созданные в linked worktree до 2.16 (когда
память писалась локально), осознанно не мигрируются и в этой волне не подсвечиваются: после смены
резолва они перестают читаться, но физически остаются на месте (P3 — ничего не удаляется и не
перезаписывается; данные владельца не теряются). Doctor-подсветка «worktree has a local `.wolf/`
while memory root resolves elsewhere» — кандидат в отдельную мелкую задачу после волны (рядом с
находками осиротевших scope §6.2).

### 6.2 Scope-гейтинг

Поле `scope` (passthrough, прецедент `owner_skill`); при записи из linked worktree дефолт
`worktree:<имя>`, `--scope main` — для универсальных фактов. Доставка фильтрует: worktree-scoped
объект виден только в том же worktree. Промоушен `wolf promote <worktree>` — шаг
finishing-a-development-branch при влитии (scoped-объекты ворктрии становятся main). Осиротевшие
scoped-объекты удалённой ворктрии — находка doctor; решение об очистке — за владельцем (автоудаления
нет, P3).

### 6.3 Нормализация related-путей

`related.files`/`related.docs` нормализуются в project-relative при записи (точка —
`add-memory-object.ts:96` по решению `08fbf3`; верификация file:line — в плане волны); абсолютный
путь вне проекта — отказ записи. Прецедент: `tool-librarian.ts:151`.

**Краевые случаи (из `08fbf3`).** Конкурентная запись двух ворктрий — файловый стор + busy-retry
достаточно; dangling related-линки на неслитые артефакты легитимны — опциональная находка doctor
только для `status: accepted`; аналитика по ворктриям — опциональное поле `origin`, YAGNI до спроса.

**Отвергнутые альтернативы (`08fbf3`).** Симлинк `.wolf` (ручной init, Windows); неймспейсы
per-worktree (YAGNI, потребности не было); env-override как основное решение (дисциплина вместо
механизма).

## 7. WP4 — Хвост №8: durability, .gitignore, doctor-секреты (P0-security)

**Проблема.** Хранилище рассыпается при частичной потере (markdown/events/index расходятся);
`.gitignore` не имеет шаблона — мусор и секреты рискуют попасть в git; doctor может печатать
значения секретов.

**Решение.**

- Durability-сплит (G7 каталога `95c272`): восстановление markdown/events/index друг из друга;
  стратегия приоритетов источников фиксируется в плане волны (markdown — истина объектов, events —
  истина журнала; кандидат).
- `.gitignore`-шаблон в составе init: игнорировать локальное/секретное, коммитить память — по
  формуле переноса («память коммитится — клонирование переносит», спека 2.14 §8.3).
- Doctor-секреты: doctor и все команды волка не печатают значения секретов (маскирование в выводе).
  Граница трактовки — делегированная (владелец может ветировать): в 2.16 маскируется вывод doctor —
  единственный канал, куда попадают фрагменты чужих файлов; тела объектов в get/list (авторский
  контент пользователя) не маскируются.

**Краевые случаи.** Рассинхрон после краша записи (прецедент 2.14: событие до записи); повреждённый
events.jsonl — восстановление идемпотентно, повторный запуск дозавершает (прецедент `aggregate apply`);
конкурентная запись — busy-retry (общее с WP3).

**Отвергнутые альтернативы.** Полная транзакционность FS (нереалистична — идемпотентность вместо
транзакций, прецедент 2.14); автобэкапы вне git (новый носитель без спроса, YAGNI); хранение
секретов в памяти Wolf (не задача волка).

## 8. WP5 — Хвост №9: пустой call объясняет себя, ошибки называют флаг

**Проблема.** Пустой `call` молчит — непонятно, работает ли доставка вообще (E5); ошибки не
называют релевантный флаг — пользователь не знает, чем поправить (K2).

**Решение.** Пустой call печатает объяснение (почему пусто: нет объектов/фильтры/активный scope) и
следующий шаг; ошибки UserFacingError называют релевантный флаг (формат подсказки — прецедент
guard-ошибок 2.14).

**Краевые случаи.** Пусто из-за scope-фильтра WP3 — объяснение обязано назвать активный scope
(worktree-кейс «слепоты» становится самодиагностируемым); не-TTY — тот же вывод без интерактива.

**Отвергнутые альтернативы.** Автоматический fallback доставки на main-scope при пустом worktree —
против узкого дефолта P2 (заражение — вот чего избегаем); отдельная диагностическая команда —
объяснение в самом выводе дешевле (YAGNI).

## 9. WP6 — Docs-синхронизация

**Проблема.** Дрейф README/AGENTS/сайта от команд (тема T1): поверхности расходятся с кодом между
релизами.

**Решение.** Точечные правки живых гайдов под состав волны (init, unpin, worktree-память, promote);
grep-чек внешних поверхностей (README/AGENTS/сайт против удалённых/переименованных команд) — пункт
релизного чек-листа волны (до автоматизации — ручная проверка, §5.2 драфта). T17-касания из драфта
покрываются теми же точечными правками — отдельного объёма T17 в волне нет.

**Краевые случаи.** Поверхности на трёх носителях (README, рамки, сайт) — grep-чек по списку команд
волны; расхождение — блокер релиза.

**Отвергнутые альтернативы.** Автоматизация grep-чека в CI в этой волне (кандидат — отдельная
мелкая задача после волны); генерация доков из кода (не зрелого уровня проекта).

## 11. Q11 — метрика активации init и окно приёмки повторяемости

**Делегированный дефолт (сформулирован из драфта §7 и треда `b0368a`; владелец может ветировать
при ревью спеки):**

- **Метрика активации** — «init → работа»: запуск init считается _завершённым_ при зелёном
  `wolf doctor` на проекте (0 issues) и _активированным_, если в течение 7 календарных дней после
  init в проекте появилась ≥1 wolf-сессия с записью в память (события проекта в `events.jsonl` /
  session-metrics — штатная телеметрия, без новых носителей; «инструмент замера штатный» —
  exit-критерий 7 драфта).
- **Повторяемость** — свежий init на чистом проекте воспроизводит канонический минимум файлов
  детерминированно, без сети (детерминизм подтверждается пофайловыми existsSync-ассертами e2e;
  snapshot-сравнение полного дерева в волне не строится); повторный init на живом проекте — diff +
  подтверждение, без неожиданных перезаписей (exit-критерии 3 и 6 драфта).
- **Окно приёмки** — 14 календарных дней с релиза 2.16.0; в окне минимум 2 догфуд-инициализации
  (mister-wolf + playground); замер зафиксирован в память Wolf (решение/заметка) **до закрытия
  окна**.
- **Порог** — блокирующий: автотесты повторяемости зелёные и 0 doctor-issues на свежих init;
  сигнальный (не блокирующий): ≥1 из 2 догфуд-инициализаций активирована ≤ 7 дней; провал
  сигнального — решение владельца (патч или пересмотр дефолта), авто-отката состава нет.

## 12. D1.6 — замер веса цикла конвейера

По спеке конвейера §4-D1.6 (`52031b`): после первого полного догфуда волны 2.16 — замер в память
Wolf: реальное время цикла (requirements → релиз) против монолитной эпохи. Этап пост-релизной
приёмки волны: замер фиксируется до закрытия волны в памяти. При деградации — резать помеченных
кандидатов на упрощение (INDEX.md, объём анатомии записи) **без новой спеки** (порог деградации —
решение владельца по данным замера; спека не назначает число заранее — честнее одна базовая линия,
чем вымышленный порог).

## 13. Порядок, зависимости, не-цели

Порядок: (1) WP2+WP1 совместный проход (init без модели — один дизайн); (2) WP3 (задаёт scope для
WP1/WP5-кейсов); (3) WP4, WP5, T4, T6 параллельно (файловые множества дизъюнктны; T6 —
регрессионный e2e-контур); (4) WP6; релиз; (5) пост-релиз: окно приёмки Q11 (§11) и D1.6 (§12).

**Не-цели (вне 2.16):** глобальная память (отклонена владельцем); веб-интерфейс; доинформирующие
онбординг-механики; инструмент смены моделей субагентов; удаление чужих model-строк; полный rework
качества доставки (T7 — отложен); legacy-миграция в CI (T5 — отложена); лица/версии/async/архив
(волны B/C драфта); изменения таксономии и жалобного контура 2.14.

## 14. Критерии приёмки волны

1. **E2E без сети (unpin):** свежий проект — профили без model-строк; смена платформенного дефолта
   → модели субагентов следуют платформе. До прохождения наследование не заявляется работающим
   ([НЕПР] закрывается только этим критерием).
2. Неинтерактивный init завершается без `--model` (тест).
3. Минимальный путь: init с одним вопросом создаёт только согласованный минимум файлов (тест).
4. Пустой call печатает объяснение и следующий шаг; при scope-фильтре называет активный scope
   (тест).
5. Doctor не печатает значения секретов (тест).
6. Повторный init показывает diff и требует подтверждения; отказ — проект не изменён (тест).
7. Метрика активации и окно приёмки зафиксированы в этой спеке (§11); замер выполнен штатным
   инструментом и записан в память Wolf в окне приёмки.
8. **Worktree (e2e):** linked worktree читает/пишет общий `.wolf/`; worktree-scoped объект не виден
   в main до `wolf promote`, после promote виден; `related.files` с абсолютным путём вне проекта —
   отказ записи.
9. T4: unknown-статус не даёт TypeError (тест). T6: e2e-тройка — коллизия ID не перезаписывает;
   proposed не попадает в call; supersede-цикл отклоняется.
10. D1.6: замер веса цикла зафиксирован в память Wolf после первого полного догфуда.
11. `npm run check`, `docs:build`, `prettier --check` зелёные; CHANGELOG и changelog-страница сайта
    синхронны.
