## 1. Проблема (из ревью)

1. Память видна только на стадии «добавлено»:Wolf не знает, что память **досталась** агенту (retrieved), **влетела** в контекст (injected), была **процитирована** (cited) и **сработала** (applied) → главный вопрос продукта «память помогает или копится?» остаётся открытым.
2. `mcp_call` не несёт версию Wolf — нельзя отделить эффекты обновлений в аналитике.
3. Координация трёхуровневой схемы (брифы, ревью, приёмки, блокеры) живёт прозой отчётов — нет машинных событий → координационная аналитика невозможна.

## 2. Решения

| #   | Решение                                                                                                                                                                                                                                                                                           | Альтернатива, отклонённая                                                                                        |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| D1  | Событие `memory_stage` (SignalEventName): `detail.stage: 'retrieved'\|'injected'\|'cited'\|'applied'`, `detail.memory_ids: string[]`, actor. Автоматические писатели в коде Wolf: search/get → `retrieved` (ids из выдачи), brief/call → `injected` (ids инъекций). Для внешних акторов — CLI `wolf memory-stage --stage <s> --ids <id,...> [--actor <a>]` (cited/applied — писательская ответственность harness, гайд в доках) | Скрытое «угадывание» applied по эвристикам: недостоверно; парсинг прозы отчётов: хрупко                              |
| D2  | `mcp_call` + поле `wolf_version` (runtime-версия из package.json на момент вызова, пишется автоматически в обёртке)                                                                                                                                                                                 | Версия из env: писатель-зависимо                                                                                      |
| D3  | Событие `coord_event` (SignalEventName): `detail.kind: 'handoff'\|'review'\|'acceptance'\|'blocker'\|'escalation'`, `detail.actor_from`, `detail.actor_to` (опц.), `detail.refs: string[]` (id брифа/отчёта/блокера), `detail.note` (опц.). CLI `wolf coord --kind <k> [--from a] [--to b] [--ref id,...] [--note s]` — пишет все уровни (L0-координатор на диспетче/приёмке, lead'ы на отчётах) | Отдельная коллекция для координации: второй источник истины против Ф-инвариантов единого сигнального лога             |
| D4  | Аналитика `--view memory`: воронка стадий added→retrieved→injected→cited→applied (счётчики по уникальным id памяти + events), **атрибуция**: доля задач с вердиктом accepted, перед которыми в той же сессии (`session_id`) была инъекция памяти — `attributionCoveragePct` (null при отсутствии task_evaluated/injected данных, reason); уникальные memory-id, доходившие до applied | Глобальный join по времени без сессии: шум от параллельных сессий                                                     |
| D5  | Аналитика `--view coordination`: счётчики по kind × actor, последние N событий, связь с blocker-потоком (open/resolve пары по refs)                                                                                                                                                                  | Полный DAG координации: избыточно для P2                                                                              |

## 3. Не делаем (границы P2)

Span-модель и OTEL-совместимость (P3+), SQLite-проекция, WolfEval-кампании и `campaign_id` (P3), автоматическое инструментирование внешних harness (даём CLI + гайд; плагин OpenCode — отдельный проект), auto-citation-парсинг прозы, per-memory ROI в деньгах (после накопления applied-данных, P3).

## 4. Критерии приёмки

1. `wolf search`/`get` пишут `memory_stage` retrieved с ids выдачи; `wolf brief`/`call` пишут injected с ids инъекций (unit-тесты roundtrip).
2. `wolf memory-stage` пишет cited/applied для перечисленных id (roundtrip-тест; невалидная стадия/пустые ids — ошибка CLI).
3. Каждый `mcp_call` содержит `wolf_version` (unit-тест обёртки).
4. `wolf coord` пишет coord_event всех kind (roundtrip-тесты; без --kind — ошибка).
5. `--view memory`: воронка стадий + attributionCoveragePct (fixture-тесты: сценарий с accepted+injected → доля; без данных → null+reason); `--view coordination`: counts kind×actor + свежие события (fixture-тест).
6. Доки: signal-log.md, analytics.md + сайт EN/RU, Harness integration (cited/applied/coord) — примеры живые.
7. `npm run check` зелёный; e2e-набор прогнан на чистом чекауте (урок v2.6.0); merge в main; РЕЛИЗ НЕ ДЕЛАТЬ.
