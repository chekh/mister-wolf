## 1. Цель и определение обучения

**Обучение** = изменение конфигурации поведения агента по измеренному опыту,
закреплённое для будущих сессий. Накапливание памяти без изменения конфигурации
поведения — не обучение (это хранение).

**Целевая функция:** качество работы агента (доля принятых критериев, меньше
rejected-циклов и FRICTION) при нехудшей стоимости (весовые токены) и времени.
Критерий «стало лучше» всегда тройной: качество ↑, стоимость и время — не хуже.
Компромиссы оцениваются по Парето-фронту (используется в GEPA, §5).

**Единица адаптации** — объект памяти или файл конфигурации, который меняет
поведение агента в будущих сессиях:

| Единица           | Носитель                                                                   | Пример                                 |
| ----------------- | -------------------------------------------------------------------------- | -------------------------------------- |
| Правило           | `type: rule` (+ `trigger_keywords`)                                        | «для X используй Y — проверено»        |
| Урок              | `type: lesson` (+ `trigger_keywords`)                                      | обход известной ловушки тула           |
| Параметр процесса | файл конфигурации, версионируется git                                      | порог N≥3, лимит ретраев               |
| Шаблон            | markdown-шаблон брифа/промпта                                              | структура task-brief                   |
| Роль/скилл        | файл `.opencode/agents/*.md`, `.wolf/SKILL.md`                             | Analyzer-Worker, Стюард                |
| Playbook          | `type: playbook` (+ `trigger_keywords`, steps/order, owner_skill, version) | методика скилла/команды в памяти (§13) |

Субъект записи — не только пользователь: **Стюард** (§10) — самостоятельный
субъект памяти, вносит rule/lesson/playbook от своего имени (`created_by`:
агент) под пост-аудитом дайджестом (решение владельца 2026-08-29; §2.5, §14).

## 2. Контур обучения — 6 стадий

```
сигналы → паттерны → кандидаты → grounding → принятие → доставка
   P20  →   P21    →    P22    →  P22/P23  →   P22    →  готово (P15/P16)
```

Под каждой стадией: существующие механизмы Wolf и явно помеченные пробелы (GAP).
Нумерация фаз — по roadmap-v2 (блок Self-Learning Phases).

### 2.1. Сигналы

Сбор измеренного опыта каждой сессии.

**Существует:**

- `events.jsonl` — audit trail всех операций с памятью (lifecycle, supersede, decisions).
- Отчёты оркестрации `.wolf/orchestration/report-*.md` — обязательные секции
  Validation Results и FRICTION (протокол executor-lead); rejected-циклы ревью,
  счётчики тул-ошибок воркеров — в тексте.
- `session-summary` (core type) — авто-фиксация lifecycle-событий.
- `think`-последовательности (`wolf think start/add/conclude`) — мысли с типом
  `evidence`, заключаются в `decision` с `based_on`-ссылками.
- Весовые метрики сессий (замеры токенов — прецеденты в
  `report-2026-08-26-bench-tokens.md`, правило сессий `mem_20260824__d072b4`).

**GAP (Phase 20):** метрики существуют в прозе отчётов, не машиночитаемы.
Контур обучения читает пер-сессионный `session-metrics.jsonl` — схема
OTEL GenAI v1.41 Layer 1+2 (expert-013 M20-01/02): `session_id`, `timestamps`,
`gen_ai.*`, `orchestration.*`, `outcome`, `tool_errors.by_class`. Файл —
derived/rebuildable артефакт (инвариант §9); markdown-отчёты — только для
людей, контур парсит исключительно машиночитаемые логи (практика полей
LLM-observability — Datadog, Elastic).

Нормализация ошибок — 2-ступенчатая (M20-03): детерминированный классификатор
`error_class_id` в горячем пути по таблице `error_class_taxonomy` в
`.wolf/config.yaml` (20–50 классов, покрытие ≥95% ошибок; M20-04, [ЦИТ]
Datadog Patterns) + холодный `ErrorClassRefiner` (LLM через адаптер
`opencode run`) — только для `uncategorized`.

`events.jsonl` дополняется 8 orchestration-событиями (M20-05, [ЦИТ] OTEL
GenAI v1.41 Agent Spans): session_started, session_ended, rejected_cycle,
friction, delivery, tool_error, llm_call, worker_spawned. **delivery_event —
третий тип сигнала** контура (M20-06): факт срабатывания delivery-механизма —
измеримый вход для decay (§6) и метрик доставки (§2.6).

Writer-матрица (M20-07; решение Q3 — §18): воркеры пишут фрагменты
`emit-metrics.jsonl` в каталог сессии `.wolf/orchestration/<session>/`;
executor-lead детерминированно мержит их в канонический `session-metrics.jsonl`
— инвариант «запись без LLM» + files as source of truth; CLI
`wolf metrics emit` не вводится (spawn процесса на каждое событие — оверхед
горячего пути).

Observability самого контура — Layer 1 meta-metrics (M20-08):
`signal_coverage`, `uncategorized_errors`, `orphan_signals`; агрегаты доставки
— в derived-файле `delivery-stats.json` (S20-09; canonical-лог не шумим).
Без сигнального лога стадии 2–5 не имеют входа — поэтому Phase 20 первая
в цепочке.

### 2.2. Паттерны

Выявление повторяющегося (N≥3 однотипных сигналов).

**Существует:**

- `wolf insights` Level 1 — эвристический анализ без LLM: top tags, частые
  `related.files`, stale/superseded/conflicting decisions, плотности по типам.
- FRICTION-подсчёт в отчётах (правило executor-lead: ≥2 воркера на один тул —
  системная проблема) — ручной прототип порога N≥2 для тул-ошибок.

**GAP (Phase 21):** базис детекции — **детерминированная rule-based
кластеризация O(n)** по нормализованному ключу `tool_name:error_class_id`
(expert-013 M21-01/02; [ЦИТ] PostHog, Datadog Patterns): класс ошибки
определяется классификатором Ф20 (§2.1), кластер — группа сигналов с одним
ключом. Эмбеддинг-кластеризация ревизии 27.08 **понижена до опционального
semantic-слоя** (S21-03): локальные UMAP+HDBSCAN поверх накопленных кластеров
для emergent-паттернов ([ЦИТ] Clio pipeline, Anthropic); запуск —
**событийный триггер** (порог накопления кластеров / рост
`uncategorized_errors`), не календарный; реализация — после подтверждения
потока уровнем 1 (§14, ИТОГИ исследования §5). LLM-уточнение границ кластеров
— только холодный `ErrorClassRefiner` (§2.1), не слой детекции. Порог N≥3 —
параметр процесса (класс «параметры», см. §3), настраивается автономно.
Замена базиса и мотивировка — §21, п. 1.

Observability — Layer 2 meta-metrics (S21-04): `cluster_density`,
`cluster_stability`, `emerging_patterns`.

### 2.3. Кандидаты

Превращение паттерна в draft-кандидата с evidence.

**Существует:**

- Типы `lesson`/`rule` с полем `trigger_keywords` (Phase 16) — целевой носитель.
- `rule` governance: создаётся пользователем; агент — нет (Phase 6) —
  расширяется в Phase 22: Стюард становится allowed-источником с пост-аудитом
  (решение владельца 2026-08-29; §2.5, §14).
- Lifecycle: статусы, `review_state` (draft → accepted), `wolf transition <id> <status>`.
- Evidence-ссылки: `wolf relation add <subject> <predicate> <object>` (Phase 17,
  16 предикатов, автоинверсия, relations.jsonl) + текстовая конвенция
  `wolf:<type>:<id>` с маркерами REQUIRED/BACKGROUND.

**GAP (Phase 22):** роль Analyzer-Worker (воркер, которому отдаётся кластер
сигналов и контракт «верни draft-rule с evidence-ссылками ≥3») не описана в
промптах ролей; протокол Sandbox Replay Holdout (§5) не реализован; механизм
negative constraints (§6) — отсечение повторной генерации отклонённых
кандидатов — не формализован. Требования к роли (expert-013): Analyzer-Worker
обязан работать на **фронтирной модели** (M22-02; STOP-предупреждение:
рекурсивная структура деградирует на слабых моделях, arXiv 2310.02304);
контракт включает **bounded proposal context** — 4 элемента Self-Harness
(M23-02; arXiv 2606.09498): editable surfaces, failure patterns, passing
behaviors, previous edit summaries; каждый draft несёт **манифест правки**
(M23-03; §5): `predicted_effect`, `regression_risks`, `blast_radius`,
`risk_level`. Evidence ≥3 + holdout-валидация — уже в ревизии 27.08 (M22-01,
подтверждено; §5).

### 2.4. Grounding

Проверка «меняет ли кандидат поведение» на данных, а не на мнении.

**Существует:**

- `wolf solve` — реактивный цикл проверки доставки знания (симптом → разбор → починка).
- E2E-сьют (14 файлов) — регрессионная база поведения CLI/MCP.
- Схема pressure-тестов спроектирована (Phase 18, deferred): стимул-промпт +
  `wolf call` против детерминированного mock-агента; сценарий падает при удалении
  call-injection и проходит при его наличии.

**GAP (Phase 22 — Sandbox Replay Holdout; Phase 23 — pressure-тесты):** Phase 18 не реализована
(усилие L, решение 2026-08-26 — не сейчас). В контуре самообучения она сливается
с STOP-гейтом в Phase 23: pressure-тесты становятся обязательным барьером перед
активацией любой автономной адаптации. Sandbox Replay Holdout draft-rule (§5) —
часть Phase 22.

### 2.5. Принятие (пост-аудит)

Переход кандидата в активное состояние — **пост-аудит** (решение владельца
2026-08-29): Стюард (режим grow, §10) вносит rule/lesson/playbook от своего
имени **сразу** (`created_by`: агент, `review_state` фиксирует происхождение),
а пользователь ревизует накопленное дайджестом `wolf learn digest` задним
числом — отменой или правкой; откат — одна операция (`wolf supersede` /
`wolf transition`, §5).

Два события разведены жёстко (expert-014): «вносит сразу» = создание записи
без пре-аппрува человека (`created_by`: агент, `review_state` неактивен,
запись НЕ доставляема); «активация» = только после зелёного Sandbox Replay
Holdout (детерминированный гейт, §5) — лишь тогда запись становится
доставляемой через `trigger_keywords`; доставляемость до вердикта запрещена.

**Существует:**

- Lifecycle-переходы (`ALLOWED_TRANSITIONS`, терминальные статусы: archived,
  completed, accepted, resolved, obsolete, answered) — принудительно в write protocol.
- `wolf supersede <old> <new>` — обратимая замена: старый объект сохраняется,
  получает `superseded_by` (см. §5).
- Governance-атрибуты `memory_class` / `truth_role` / `lifetime` (Phase 6) —
  правило становится `canonical/source_of_truth` только через гейт.

**GAP (Phase 22):** Phase 6 enforcement («активный `rule` создаёт только
пользователь») расширяется: allowed-источником становится Стюард с
пост-аудитом. Компенсаторы вместо пре-аппрува: read-only зоны (§5, §9),
экзамен Sandbox Replay Holdout (§5) до активации, одно изменение за итерацию
(§10), откат supersede+git (§5), сверка «предсказание vs факт» по манифесту
правки в пост-аудит-дайджесте (§5). Гейт человека сохраняется ровно в двух
точках: bootstrap-отчёт (однократно, §12) и переходы на уровень автономии C
(§14). Автоппрув-окна (expert-009/010) отклонены — §7, §21.

### 2.6. Доставка

Знание доезжает до исполняющего агента в нужный момент.

**Существует полностью:**

- `wolf call --for <тема>` + `trigger_keywords` на lesson/rule (Phase 16) —
  матчинг активных объектов по теме.
- Плагин автостарта `.opencode/plugins/wolf-session-start.js` (Phase 15) —
  инжект `wolf recap` + `wolf call --for` в первое user-сообщение, гарантия
  платформы вместо дисциплины агента.
- `.wolf/SKILL.md` §6 Red Flags — контррационализационная таблица (Phase 19).

**GAP:** нет. Факт доставки — **delivery_event**, третий тип сигнала контура
(M20-06; §2.1): измерение эффекта доставки (доставлено ли правило в сессию,
где тема совпала; изменилось ли поведение) ведётся по нему, агрегаты —
`delivery-stats.json` (derived, S20-09); вход для decay (§6) и метрик доверия
staged autonomy (§14).

## 3. Классы адаптации ↔ границы автономии B

Уровень автономии B (решение `...8e7089`): низкий риск — автономно,
высокий (новые правила, промпты ролей, мета-уровень) — через человека.
Адаптирующий ≠ исполняющий: агент, меняющий конфигурацию, не исполняет задачу
в той же сессии, и наоборот.

Уровни оркестрации адаптации (MCC-04): **L0** — inline-адаптация в исполняющей
сессии — **запрещена** (единственное исключение — запись сигналов: это
наблюдение, не адаптация; §9); **L1** — адаптация в отдельной оркестрационной
сессии (режим grow Стюарда, §10) — **цель v1**; **L2** — условный уровень
(несколько координированных адаптационных сессий), вводится только по метрикам
доверия (§14).

| Класс адаптации    | Примеры                                                                   | Цена/риск                    | Автономия (стартовый режим B+, §14)    | Механизм                                                                                           |
| ------------------ | ------------------------------------------------------------------------- | ---------------------------- | -------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Параметры процесса | порог N≥3, лимиты ретраев, таймауты, теги `context_criticality` (Q1, §18) | дёшево, откат тривиален      | автономно                              | конфиг-файл + git; изменения видны в сигнальном логе                                               |
| Записи памяти      | rule / lesson / playbook                                                  | дёшево, откат = supersede    | Стюард автономно с пост-аудитом (§2.5) | Sandbox Replay Holdout (§5) + манифест правки + пост-аудит-дайджест (§6)                           |
| Шаблоны            | шаблоны брифов, промпты→команды, SCP                                      | средне                       | draft автономно, применение — гейт     | GEPA-кандидаты (Phase 24; только детерминированные метрики — ниже), Sandbox Replay Holdout + ревью |
| Структура          | скиллы, роли, промпты ролей, мета-уровень                                 | дорого, влияет на все сессии | только гейт человека                   | AFlow-роутинг — только эвристики (Phase 25); создание — человеком (спавн агентов — §11, v1.1+)     |

Правило границы: адаптация автономна тогда и только тогда, когда (а) класс —
параметры или записи памяти (rule/lesson/playbook при B+: Стюард от своего
имени с пост-аудитом, §2.5), (б) STOP-гейт (Phase 23) зелёный, (в) откат —
одна операция (git revert / `wolf supersede`). Всё остальное — draft + гейт.

**Жёсткое ограничение применимости GEPA (Phase 24).** GEPA-скоринг применяется
только к задачам с **детерминированной метрикой качества** — процент упавших
тестов, число rejected-циклов и аналогичные воспроизводимые числовые метрики:
Парето-перебор ревизий требует числовую воспроизводимую метрику (GEPA,
arXiv 2507.19457). Открытые/субъективные задачи (дизайн-качество, «читаемость»)
из GEPA-контура исключены — для них только гейт человека, без автоматического
скоринга. Расширение на открытые задачи — v2, только если появится
детерминированный прокси-скор.

Числовые границы GEPA (expert-013; [ЦИТ] Decagon ablation, март 2026):
фронтир-рефлектор обязателен — слабая модель не меняет промпт (GPT-4o-mini
выдал 65 символов правок — ноль изменений поведения; M24-01); размер выборки
20–100 примеров (500 → −2% качества, +75% раздувания, 10× стоимости; M24-02);
лимит длины шаблона 1500 символов (4× компрессия при −0.8% качества; M24-03);
constraint-блок в обратной связи рефлектору против утечки примеров в шаблон
(M24-04; GEPA FAQ). Парето-перебор — по инстансам задач, не по осям Q/C/T
(S24-05; GEPA arXiv 2507.19457, Algorithm 2). Триггер запуска GEPA — паттерн
Ф21 (N≥3 сигналов на одном шаблоне), не календарь (S24-06; §7).

## 5. Гейты и обратимость

**STOP-гейт (Phase 23, слита с Phase 18).** Перед любой автономной адаптацией —
pressure-тесты: harness «стимул-промпт + `wolf call`» против детерминированного
mock-агента, отдельный npm-script вне `check` (запуск агента дорог). Критерий
покрытия: сценарий падает при удалении delivery-механизма (call-injection,
trigger_keywords, правило) и проходит при его наличии; детекция premature action
(действия до доставки знания) — по образцу superpowers `tests/explicit-skill-requests`.

**Read-only зоны (M23-01; [ЦИТ] AHE arXiv 2604.25850).** Ни Стюард, ни
Analyzer-Worker, ни спавннутые агенты (§11) не меняют: код гейтов,
`events.jsonl`, `session-metrics.jsonl`, `relations.jsonl`, core pack, модель,
скелет (§13). Нарушение отклоняется валидатором механически, без LLM.

**Манифест правки и сверка (M23-03; AHE decision observability).** Каждый
кандидат несёт `predicted_effect`, `regression_risks`, `blast_radius`,
`risk_level` (§2.3); пост-аудит-дайджест сверяет предсказание с фактом по
сигнальному логу — расхождение само по себе сигнал о качестве генерации.

**Sandbox Replay Holdout (Phase 22; прежде — «holdout-валидация»).**
Draft-правило проверяется **реплеем исторических промптов в изолированном
mock-окружении** — детерминированный mock-агент, тот же harness, что у
STOP-гейта (Phase 23). Кластер N≥3 делится: правило применяется к
holdout-сигналам, не участвовавшим в генерации, и должно покрывать их (тот же
error_class/тул) без ложных срабатываний на соседних кластерах. Вердикт
вычисляется по наблюдаемому поведению при реплее, **не LLM-as-a-judge**:
недетерминированный судья делает гейт невоспроизводимым (критика
LLM-as-a-judge на holdout — внешний эксперт, неверифицировано; инженерное
обоснование: гейт обязан быть воспроизводимым и дешёвым в повторных прогонах).
Практика replay-валидации на исторических промптах — eval-наборы Braintrust.
Вердикт фиксируется в объекте с evidence (M22-03 — уже в рев. 27.08,
подтверждено).

**Гейт человека (пост-аудит при B+; §2.5, §14).** Записи памяти Стюард вносит
сам с пост-аудитом; структура и шаблоны — принятие только человеком
(`wolf transition` → accepted). Гейт человека сохраняется для bootstrap-отчёта
(однократно, §12), переходов уровня C (§14) и изменений read-only зон.

**Обратимость.**

- `wolf supersede` — старая версия сохраняется, `superseded_by` указывает на новую;
  история читаема, откат = supersede в обратную сторону.
- Отклонённый кандидат — draft не активируется; причина отклонения фиксируется
  (объект/терминальный переход), сигнал возвращается в пул паттерн-детекции;
  отклонение дополнительно порождает negative constraint (§6).
- Все артефакты — файлы (markdown+frontmatter canonical, конфиги, relations.jsonl):
  git даёт построчный откат; SQLite/индексы — derived, rebuildable.
- Откат активной адаптации: деактивация правила (`wolf transition`) или supersede;
  регресс ловится STOP-гейтом и E2E.

## 6. Negative Constraints, Decay и observability контура

**Negative Constraints (Phase 22).** Отклонённые в пост-аудите draft-правила
сохраняются как **hard constraints** для Analyzer-Worker: повторная генерация
похожих кандидатов по тому же кластеру блокируется на уровне контракта
генерации. Носитель — существующая механика Wolf, отдельный json не заводится:
объект `type: lesson` с `trigger_keywords` по теме кластера; связь с отклонённым
draft — `wolf relation add` (Phase 17). Обоснование носителя: (а) семантика
`lesson` — «обход известной ловушки»; ловушка здесь — повторная генерация
отклонённого; (б) доставка — штатный `wolf call --for` в промпт
Analyzer-Worker'а до генерации: Phase 16 (`trigger_keywords` + call-injection)
уже фильтрует активные объекты по теме, новый механизм доставки не нужен;
(в) lifecycle уже даёт управляемую жизнь constraint'а (supersede/archived при
изменении решения в пост-аудите). Поля constraint-объекта (M22-04; [ЦИТ]
Co-Evolving Agents arXiv 2511.22254): `feedback_type: negative`,
`rejection_reason`, `candidate_hash` — хэш делает дедуп механическим
(diversity collapse — Weng); генерация кандидата с similarity >0.8 к
отклонённому блокируется до передачи Analyzer-Worker'у (S22-06; порог [ВА],
§16).

**Decay (Phase 22) — в единицах пробега, не календаря** (решение владельца
2026-08-29, старше M26-03). У `rule`/`lesson`/`playbook` поле
`last_triggered_at` (основа TTL, не `created_at` — M26-01; [ЦИТ] Microsoft
VSCode dataset arXiv 2605.08538: продление при срабатывании,
Ebbinghaus-реинфорсмент) дополняется счётчиком `sessions_since_last_trigger`:
штамп ставится при каждом срабатывании call-injection (delivery_event, §2.1).
Объект, не сработавший N сессий, получает `review_required` — значение
`review_state`, не lifecycle-статус: объект остаётся активным, но попадает в
очередь пересмотра Стюарда. TTL по типам [ВА] (§16): session-summary 30 /
lesson, rule 90 / decision 180 / core ∞ сессий без срабатывания (перенос
дневных дефолтов expert-005 условен — калибровка обязательна). Drift-индикаторы
актуальности помимо TTL: смена стека (git), новые `error_class` в логе,
падение `rule_utilization` <0.5 от baseline [ВА] (§16). Проверка — фоновая
команда без демона: decay-прогон выполняется в составе `wolf learn
digest`/`wolf learn status` и может подвешиваться к плагину автостарта
(Phase 15). Консолидация при чистке — **дедуп, не суммаризация** (M26-02;
[ЦИТ] Microsoft arXiv 2605.08538 §5: мерж-кластеризация роняет accuracy до
48.4%): близкие объекты связываются/supersede'ятся, содержание не «сжимается»
LLM.

**Пост-аудит-дайджест вместо алертов.** Пользователь получает
`wolf learn digest` — пост-аудит внесённого Стюардом (§2.5) с пороговой
накопительной логикой: дайджест собирается, когда накоплено ≥K элементов
(новые записи Стюарда, Sandbox Replay Holdout-вердикты, сверки манифестов
«предсказание vs факт» — §5, decay-очередь `review_required`) либо прошло D
единиц ПРОБЕГА (сессий, не дней) с прошлого дайджеста; дефолты K=5, D=30 [ВА]
(§16). Автоппрув-окна отсутствуют (§7; решение Q4 — §18). Обоснование:
алерты на каждое событие вызывают HITL-усталость и выученное игнорирование
(тезис об алерт-усталости — внешний эксперт, неверифицировано; инженерно:
пакетная обработка дешевле прерываний, а порог K гарантирует, что решение
принимается на накопленной статистике, а не на единичном шуме).

**Observability контура: `wolf learn status`.** Health-check самообучения:
какие кластеры собраны и почему (состав сигналов, порог N≥3, ключ
`tool_name:error_class_id`), какие draft-правила отклонены и почему (причина +
ссылка на negative constraint), состояние decay-очереди. Отвечает на вопросы
«почему собран кластер» и «почему отклонён draft» без чтения сырых логов.

**Meta-metrics контура (Layers 1–4)** — здоровье самого обучения, вход в
критерии staged autonomy (§14):

| Layer         | Метрики                                                              | Позиция |
| ------------- | -------------------------------------------------------------------- | ------- |
| 1 — сигнал    | `signal_coverage`, `uncategorized_errors`, `orphan_signals`          | M20-08  |
| 2 — паттерны  | `cluster_density`, `cluster_stability`, `emerging_patterns`          | S21-04  |
| 3 — кандидаты | `draft_generation_rate`, `holdout_pass_rate`, `evidence_quality`     | S22-05  |
| 4 — гейты     | `stop_gate_pass_rate`, `false_positive_rate`, `regression_detection` | S23-04  |

## 8. Критерии успеха v1 (измеримые)

Базовые значения фиксируются на Phase 20 (до любых адаптаций) — сравнение всегда
«до/после» по сигнальному логу. Конкретные числовые пороги N≥3 и размеры holdout
устанавливаются при writing-plans соответствующих фаз; здесь — проверяемые
условия приёмки.

1. **Сигнальный лог (P20):** каждая оркестрационная сессия оставляет
   `session-metrics.jsonl` (схема OTEL GenAI v1.41 Layer 1+2:
   `session_id`, `timestamps`, `gen_ai.*`, `orchestration.*`, `outcome`,
   `tool_errors.by_class`);
   детерминированный классификатор `error_class_id` покрывает ≥95% ошибок
   (таксономия 20–50 классов в конфиге); events.jsonl несёт 8
   orchestration-событий + delivery_event; markdown-отчёты контуром обучения
   не парсятся; `wolf insights` считает по логу плотности и топ-повторы без
   LLM; Layer 1 meta-metrics (signal_coverage, uncategorized_errors,
   orphan_signals) вычислимы.
2. **Паттерн-детекция (P21):** кластер ≥3 однотипных сигналов детектируется
   детерминированной rule-based кластеризацией O(n) по ключу
   `tool_name:error_class_id` (без векторных БД; `ErrorClassRefiner` —
   холодное LLM-уточнение uncategorized) и выдаёт паттерн с evidence-ссылками
   на исходные сигналы; опциональный semantic-слой (UMAP+HDBSCAN) — по
   событийному триггеру; insights L2 через адаптер `opencode run` опционально.
3. **ExpeL-цикл (P22):** ≥1 rule сгенерирован из реальных сигналов (не
   ручной), evidence ≥3, манифест правки (predicted_effect, regression_risks,
   blast_radius, risk_level) приложен, Sandbox Replay Holdout-вердикт (реплей
   в mock-окружении, не LLM-as-a-judge) зафиксирован и **предшествует
   активации**, а не следует за ней — порядок «создание (недоставляемая
   запись) → вердикт → активация → доставка» проверяется тестом; Стюард
   создал rule от своего имени (`created_by`: агент) → запись видна в
   пост-аудит-дайджесте → откат одной операцией (проверяется тестом).
4. **STOP-гейт (P23):** pressure-сценарий падает при удалении delivery-механизма
   и проходит при его наличии; прогон вынесен из `check` в отдельный npm-script.
5. **Доставка:** активные rule/lesson, влияющие на поведение, имеют
   `trigger_keywords`; факт доставки в сессию с совпавшей темой виден в
   сигнальном логе (до/после — сравнимо).
6. **GEPA (P24):** скоринг качество/стоимость/время считается по сигнальному
   логу для ≥2 ревизий одного шаблона брифа — только на задачах с
   детерминированной метрикой качества (процент упавших тестов, число
   rejected-циклов; открытые задачи исключены); применение — только через гейт.
7. **AFlow (P25):** эвристика глубины ревью для ≥1 типа задач согласована
   человеком (гейт) и даёт нехудшие метрики против базовой линии.
8. **Общий инвариант:** каждая слитая адаптация не ухудшает стоимость/время
   (в пределах шума метрик) при росте качества — проверяется сравнением
   сигнального лога до/после на одном и том же типе задач.
9. **Negative Constraints + Decay + observability (P22):** отклонённый в
   пост-аудите кандидат (constraint с `feedback_type: negative`,
   `rejection_reason`, `candidate_hash`) блокирует повторную генерацию
   похожего (similarity >0.8) — negative constraint доставлен в промпт
   Analyzer-Worker'а через `wolf call --for` (проверяется тестом);
   `rule`/`lesson` имеют `last_triggered_at` + `sessions_since_last_trigger`,
   не сработавшие за TTL-пробег [ВА] получают `review_required` и попадают в
   дайджест; drift-индикаторы (смена стека, новые error_class, падение
   `rule_utilization` <0.5 от baseline) отслеживаются; `wolf learn digest`
   собирается по пороговой логике (≥K=5 элементов или D=30 сессий пробега);
   `wolf learn status` отвечает на вопросы «почему собран кластер» и «почему
   отклонён draft» и выводит Layer 1–4 meta-metrics.

## 9. Invariants

Четыре инварианта контура (MCC-01; сквозные по всем expert-порциям).
**Инварианты не меняются без отдельного решения пользователя.**

1. **«Запись без LLM» в горячем пути.** `session-metrics.jsonl`,
   `events.jsonl`, `emit-metrics.jsonl` пишутся детерминированно;
   `error_class_id` классифицируется таблицей, не LLM; LLM-уточнение
   `uncategorized` — только в холодном пути (`ErrorClassRefiner`, §2.1).
2. **«Адаптирующий ≠ исполняющий».** L0 (inline-адаптация) запрещён;
   единственное исключение — запись сигналов (это наблюдение, не адаптация);
   цель v1 — L1 (§3, §10).
3. **Files as source of truth.** Все canonical-артефакты — markdown+frontmatter
   или JSON/JSONL; SQLite, векторные индексы, `session-metrics.jsonl`,
   `delivery-stats.json` — derived, rebuildable; git даёт построчный откат.
4. **Local-first.** LLM — опциональный адаптер `opencode run`; память (запись,
   поиск, доставка) работает без LLM; эмбеддинги только локальные и только в
   опциональном semantic-слое (§2.2).

## 10. Стюард (Steward): единый агент управления и наставничества

**Определение.** Стюард (рабочее название; final name TBD — открытый вопрос
владельца) — единый агент с широким контекстом, не разделённый на «босса» и
«учителя». Два режима: **run** — оркестрация задач (спавн и контроль
воркеров) и **grow** — наставничество: цикл обучения, чистка и актуализация
памяти, внесение решений от своего имени. Разделение режимов — та же
дисциплина «адаптирующий ≠ исполняющий» (§9): одна сессия не совмещает
исполнение задачи и адаптацию.

**Триггеры режима grow.** Автоматические — событийные пороги: паттерн Ф21
(N≥3 однотипных сигналов), молчание правила (decay-очередь, §6),
drift-индикаторы (§6). Ручные — `wolf complain`: критика пользователя —
**hot-signal высшего приоритета** (SCC-05) — эскалация приоритета L1-цикла,
не онлайн-адаптация; Стюард проводит расследование по сохранённым данным
сессий (метрики, события, трейсы — всё записывается) и находит корневую
причину (таймаут, плохой бриф, сломанный инструмент).

**Пост-аудит как режим полномочий** (решение владельца 2026-08-29; §2.5):
Стюард пишет rule/lesson/playbook-содержимое от своего имени сразу;
пользователь ревизует дайджестом задним числом (отмена/правка).

**Правила завершённости цикла** — вместо токен-бюджетов (решение владельца:
лимит убил бы эффективность наставника; экономность — свойство метода, а не
настройки):

- цикл начинается с цели и заканчивается **одним изменением** — или явным
  «ничего не меняем» с причиной;
- проверка гипотезы — ≤5 шагов [ВА] (§16); расширение scope — отдельная
  явная задача, не продолжение текущего цикла;
- «нужен факт — проверь и запиши», а не рассуждай.

**Экономность.** Стюард обязан быть токен-бережливым: bounded proposal
context (M23-02), bounded digest, никаких фоновых демонов — только прогон
по триггеру.

**Чистка и актуализация накопленного.** Не только проблемы, но и принятые
решения: протухшее гасить (decay, §6), устаревшее корректировать (supersede),
конфликтующее сводить (insights: conflicting decisions) — консолидация
дедупом, не суммаризацией (M26-02).

## 11. Состав агентов: динамическая адаптация и спавн

Состав агентов — сам объект адаптации ([ЦИТ] AHE arXiv 2604.25850 —
редактируемый компонент harness'а; Voyager arXiv 2305.16291 — эволюционирующий
арсенал). Проект стартует с **минимального набора**; специализированные агенты
(например, devops) появляются под задачи проекта и отмирают вместе с ними.
Решение о спавне принимает Стюард (режим run/grow, §10); пользователь видит
его в пост-аудит-дайджесте. Реализация — направление v1.1+ (roadmap); в v1
состав статичен, кроме ролей контура (§4).

**Семь предохранителей спавна:**

1. **Карантин / испытательный срок:** новый агент начинает как «стажёр» —
   низкорисковые задачи, отчёты через Стюарда с усиленной проверкой; полная
   автономия — после N успешных задач.
2. **Минимальный скоуп при спавне:** узкий набор инструментов, read-only вне
   задачи — не может «всё сломать», потому что не имеет доступа.
3. **Blast-radius оценка перед спавном:** тот же аппарат, что для правил
   (пороги 0.2/0.6 [ВА], §16); высокий радиус — длиннее карантин или отказ.
4. **Одно изменение за раз:** не спавнить нескольких новых агентов
   одновременно — при регрессии невозможна атрибуция.
5. **Автогашение:** агент, не показавший пользы за испытательный пробег,
   гасится автоматически (архив).
6. **Post-audit журнал:** «появился агент X: почему, что сделал, чего стоит» —
   в дайджесте; откат одной командой (агент = файл-роль + запись в реестре).
7. **Запрет критичных зон:** ни один новый агент не получает доступа к
   read-only зонам (§5, §9) независимо от назначения.

## 12. Bootstrap: адаптация при подключении к проекту

Первый уровень адаптации — на старте, не через долгие сессии проб и ошибок.
При подключении к существующему проекту Wolf однократно глубоко изучает его
(документы, код, конфиги; входы — codegraph, AGENTS.md), может задать вопросы
пользователю и составляет **стартовые правила + стартовый состав агентов**
под задачу.

**Permissions-профиль проекта** настраивается там же: доверенные каталоги
(`/tmp`, worktrees `.worktrees/`, `.wolf`), требуемые инструменты, сетевые
доступы. Цель — дальнейший процесс без лишних ручных согласований. Профили
допусков по ролям (базовый воркер, специализированный агент) наследуются от
профиля проекта; допуски вне профиля — через явное ревизование, а не точечные
запросы в моменте.

**Пре-аппрув — только bootstrap-отчёт** (однократно): отчёт с предложениями
(правила, состав, допуски, причины) показывается пользователю до применения —
единственное место, где пре-аппрув оправдан (массовое первичное изменение).
Дальше — обычный пост-аудит (§2.5, §14).

## 13. Память как источник истины: слои, playbook, рамочная доставка

Принцип: **максимум — в память, статика — минимальна.** Многие артефакты
сегодня читаются только при рестарте платформы (определения агентов, скиллы,
AGENTS.md) — их нельзя адаптировать на ходу; память Wolf доступна в любой
момент.

| Слой                                                           | Где живёт                                                                                                | Кто меняет                                                  |
| -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| Скелет (минимальные определения агентов, протокол «зови Wolf») | статика, read-only для контура                                                                           | никто — «ДНК» системы, без неё память не загрузит саму себя |
| Поведенческий (правила, уроки, playbook-содержимое)            | память Wolf, доставляется в рантайне                                                                     | Стюард (пост-аудит) + пользователь                          |
| Ролевой (рамки ролей/скиллов)                                  | тонкая статичная рамка (идентичность, протокол подтягивания, критичные инварианты) + содержимое в памяти | рамку — человек; содержимое — Стюард без рестарта платформы |
| Инструменты/допуски                                            | конфиг платформы (opencode), read-only для контура                                                       | bootstrap-профиль (однократно, §12)                         |

**Тип `playbook`.** Содержимое методики — объект памяти: `trigger_keywords`,
`steps`/`order`, `owner_skill`, `version`. Рамка файла роли/скилла/команды
остаётся статичной и тонкой; следующая сессия получает новую версию
содержимого через обычную доставку — обновление скиллов и агентов без
рестарта платформы; вся инфраструктура памяти (decay по пробегу, supersede,
доставка) работает и для playbook.

**Границы честности.** Рамка не бывает пустой: в ней живёт протокол
подтягивания («вызови `wolf search` по тегу `skill:X` перед этапом Y») и
критичные шаги (безопасность, приёмка) — инъекция из памяти вероятностна,
гарантированность нужна только скелету. Порядок шагов методики кодируется в
самом объекте (`steps`/`order`) и читается потребителем детерминированно;
доставка и поиск порядок не пересобирают вероятностно (expert-014).

**PoC подтверждён (2026-08-29).** Агент-рамка — 3/3: (1) методика доставляется
из памяти — ответ строго по формату playbook v1; (2) фидбек пользователя →
агент сам зафиксировал v2 и supersede'нул v1; (3) новая сессия — сразу v2 без
рестарта opencode. Команда/скилл — 3/3: та же рамка, то же содержимое,
эволюция v2→v3 без рестарта. Артефакты: `.opencode/agents/apprentice.md`,
`.opencode/command/analyze-doc.md`, `.opencode/skills/analyze-doc/SKILL.md`.

Находки PoC: (а) типа `playbook` в таксономии не было — добавлен этой
ревизией (§1, §21); (б) «рецидив рекомендаций без применения» — анализ без
применения порождает повторение одних и тех же рекомендаций — аргумент
полного цикла анализ→применение; вписан в мотивацию Ф20–22 (контур без
примечания лишь тиражирует одни и те же находки — см. ИТОГИ исследования,
PoC #2).

**Направления (не v1):** `wolf scaffold agent|skill|command` — генерация
рамки + playbook в памяти одной командой; мультиплатформенная гармонизация —
рамки per-platform (opencode / Claude Code / Cursor / Codex), содержимое общее
в Wolf; формат SKILL.md у opencode совместим с Claude Code, адаптеры простые:
Wolf как единый источник методик для всех агентских платформ.

## 14. Governance: staged autonomy (B → B+ → C)

Автономия контура растёт по стадиям; единица измерения — **пробег** (сессии),
не календарь (замена дневных окон expert-010 — §21, п. 12).

| Стадия | Определение                                                                                                                                                                                                                                                                                                           |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **B**  | пре-аппрув: все записи памяти — через гейт человека до применения                                                                                                                                                                                                                                                     |
| **B+** | пост-аудит: Стюард вносит записи от своего имени сразу, пользователь ревизует дайджестом задним числом. **Стартовый режим v1** (решение владельца 2026-08-29). Компенсаторы: read-only зоны (§5, §9), экзамен Sandbox Replay (§5), одно изменение за итерацию (§10), откат supersede+git (§5), сверка манифестов (§5) |
| **C**  | расширенная автономия (сокращение объёма пост-аудита): только по метрикам доверия в пробеге + отдельное решение пользователя                                                                                                                                                                                          |

Критерии апгрейда B+ → C ([ВА]-дефолты чекпоинтов 30/60/90 сессий; пороги
expert-010, окна переведены из дней в пробег — §21, п. 12; §16):
delivery_recall ≥95% (окно 180 сессий), regression_detections = 0 (окно 120
сессий), rule_utilization ≥85% (окно 90 сессий), human_override_rate <5% —
все условия одновременно; плюс стабильные Layer 1–4 meta-metrics (§6) — на
каждом чекпоинте Стюард предлагает переход, пользователь решает. Критерий
возврата B+ → B (симметричен апгрейду; expert-014): высокая доля отмен
записей Стюарда по итогам пост-аудита в первых дайджестах — ≥30% отмен за
окно чекпоинта [ВА] (§16) — сигнал вернуться к пре-аппруву; возврат —
решением пользователя. Связь с уровнями оркестрации (MCC-04, §3): B/B+
работают на L1 (режим grow Стюарда); L2 синхронен переходу к C. Понижение
стадии — тем же механизмом (решение пользователя), откат записей — supersede.

## 17. Чеклисты рисков (24 режима отказа)

Обязательная проверка при каждой адаптации (MCC-02); состав — дословно из
expert-013 §3.B, добавлены метки фаз применения.

**B.1 Survey (arXiv 2607.13104) — 5 режимов; применение: Ф21/22/23.**

- [ ] Catastrophic scaffolding collapse: обновление Σ_t не ломает ранее решённые задачи → STOP-гейт + regression testing
- [ ] Over-optimization to judge: агент не обманывает evaluator → используем Φ_metric, не Φ_judge
- [ ] Signal sparsity: сигналы не слишком шумные → порог N≥3
- [ ] Computational overhead: ресурсы в пределах бюджета → batch-обработка
- [ ] Lack of transfer: улучшения переносятся на held-out → holdout-валидация

**B.2 Proofs Not Promises — 4 ungoverned failure modes; применение: Ф23.**

- [ ] Unsealed evaluation: все стадии L=(F,C,H,G,S,E,A) покрыты
- [ ] Authority boundary violations: Aegis envelope не нарушен
- [ ] Missing evidence bundle: evidence bundle complete
- [ ] Adversarial evasion: Cassius-поверхность проверена

**B.3 Trehan & Chopra + Weng — 9 режимов; применение: Ф22/Ф26.**

- [ ] Bias toward defaults: система не скатывается в дефолтные решения
- [ ] Implementation drift: код не деградирует через итерации
- [ ] Memory degradation: память не теряет важные детали (дедуп, не суммаризация)
- [ ] Over-optimism «numerical duct tape»: система не маскирует проблемы числами
- [ ] Insufficient domain intelligence: решения учитывают доменную специфику
- [ ] Weak scientific taste: отбор кандидатов качественный
- [ ] Diversity collapse: дедуп по `candidate_hash` работает
- [ ] Negative results loss: отклонённые кандидаты сохраняются как `feedback_type: negative`
- [ ] Weak evaluators: evaluator'ы адекватные (Φ_metric)

**B.4 GEPA (Decagon + FAQ) — 6 режимов; применение: Ф24.**

- [ ] Bloat: длина шаблона ≤ лимита (1500 символов дефолт)
- [ ] Переобучение: размер выборки 20–100, golden splitting
- [ ] Утечка примеров: Constraint-блок в обратной связи
- [ ] Metric gaming: только шаблоны с детерминированной μ
- [ ] Локальный оптимум: Парето по инстансам (встроено в GEPA)
- [ ] Over-optimization to judge: Φ_metric, не Φ_judge
