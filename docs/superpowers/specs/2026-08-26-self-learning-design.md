## 1. Цель и определение обучения

**Обучение** = изменение конфигурации поведения агента по измеренному опыту,
закреплённое для будущих сессий. Накапливание памяти без изменения конфигурации
поведения — не обучение (это хранение).

**Целевая функция:** качество работы агента (доля принятых критериев, меньше
rejected-циклов и FRICTION) при нехудшей стоимости (весовые токены) и времени.
Критерий «стало лучше» всегда тройной: качество ↑, стоимость и время — не хуже.
Компромиссы оцениваются по Парето-фронту (используется в GEPA, §5).

**Единица адаптации** — объект памяти или файл конфигурации, который меняет
поведение агента в будущих сессиях:

| Единица           | Носитель                                       | Пример                          |
| ----------------- | ---------------------------------------------- | ------------------------------- |
| Правило           | `type: rule` (+ `trigger_keywords`)            | «для X используй Y — проверено» |
| Урок              | `type: lesson` (+ `trigger_keywords`)          | обход известной ловушки тула    |
| Параметр процесса | файл конфигурации, версионируется git          | порог N≥3, лимит ретраев        |
| Шаблон            | markdown-шаблон брифа/промпта                  | структура task-brief            |
| Роль/скилл        | файл `.opencode/agents/*.md`, `.wolf/SKILL.md` | Analyzer-Worker, куратор        |

## 2. Контур обучения — 6 стадий

```
сигналы → паттерны → кандидаты → grounding → принятие → доставка
   P20  →   P21    →    P22    →  P22/P23  →   P22    →  готово (P15/P16)
```

Под каждой стадией: существующие механизмы Wolf и явно помеченные пробелы (GAP).
Нумерация фаз — по roadmap-v2 (блок Self-Learning Phases).

### 2.1. Сигналы

Сбор измеренного опыта каждой сессии.

**Существует:**

- `events.jsonl` — audit trail всех операций с памятью (lifecycle, supersede, decisions).
- Отчёты оркестрации `.wolf/orchestration/report-*.md` — обязательные секции
  Validation Results и FRICTION (протокол executor-lead); rejected-циклы ревью,
  счётчики тул-ошибок воркеров — в тексте.
- `session-summary` (core type) — авто-фиксация lifecycle-событий.
- `think`-последовательности (`wolf think start/add/conclude`) — мысли с типом
  `evidence`, заключаются в `decision` с `based_on`-ссылками.
- Весовые метрики сессий (замеры токенов — прецеденты в
  `report-2026-08-26-bench-tokens.md`, правило сессий `mem_20260824__d072b4`).

**GAP (Phase 20):** метрики существуют в прозе отчётов, не машиночитаемы.
Нужен сигнальный лог: измеритель эмитит на каждую сессию структурированный
`session-metrics.json` — OTEL-совместимые поля `task_id`, `timestamps`,
`weighted_tokens`, `verdict`, `rejected_cycles` (с причинами), `tool_errors`
(по типам), длительность — параллельно markdown-отчётам. Markdown-отчёты —
только для людей; контур обучения читает исключительно JSON (практика полей
LLM-observability — Datadog LLM Observability, Elastic Observability). Без
него стадии 2–5 не имеют входа — поэтому Phase 20 первая в цепочке.

### 2.2. Паттерны

Выявление повторяющегося (N≥3 однотипных сигналов).

**Существует:**

- `wolf insights` Level 1 — эвристический анализ без LLM: top tags, частые
  `related.files`, stale/superseded/conflicting decisions, плотности по типам.
- FRICTION-подсчёт в отчётах (правило executor-lead: ≥2 воркера на один тул —
  системная проблема) — ручной прототип порога N≥2 для тул-ошибок.

**GAP (Phase 21):** строковый матчинг однотипности (нормализация «тул + тип
ошибки + контекст») заменён сравнением векторных представлений. Выбор v1 —
**локальная эмбеддинг-кластеризация** сигналов на этапе детекции: косинусная
близость в памяти, без векторных БД (объём сигнального лога мал — O(n²)
попарных сравнений достаточно; представления derived/rebuildable; практика
кластеризации без выделенной векторной БД — PostHog). Обоснование выбора:
(а) инвариант local-first «запись не требует LLM» сохраняется — эмбеддинги
считаются при детекции, не при логировании; (б) решение
`mem_20260826_llm_sintez_wolf_cherez_adapter_opencode_56d96c` уже разрешает
локальные эмбеддинги (запрещает только внешние); (в) устойчивость к
вариативности формулировок ошибки, которую строковый ключ не ловит.
Альтернатива — LLM-тегирование `error_class_id` при логировании — отклонена
как обязательный слой: LLM на каждом сигнале ломает local-first запись и
добавляет стоимость на каждый сигнал (тезис о достаточности тегирования —
внешний эксперт, неверифицировано). `error_class_id` допускается как
опциональное уточнение границ кластеров через адаптер `opencode run`
(Level 2 `wolf insights`: LLM — внешний процесс, память остаётся local-first).
Порог N≥3 — параметр процесса (класс «параметры», см. §3), настраивается автономно.

### 2.3. Кандидаты

Превращение паттерна в draft-кандидата с evidence.

**Существует:**

- Типы `lesson`/`rule` с полем `trigger_keywords` (Phase 16) — целевой носитель.
- `rule` governance: создаётся пользователем; агент — нет (Phase 6). Draft от
  агента обязан проходить гейт — совпадает с уровнем автономии B (§3).
- Lifecycle: статусы, `review_state` (draft → accepted), `wolf transition <id> <status>`.
- Evidence-ссылки: `wolf relation add <subject> <predicate> <object>` (Phase 17,
  16 предикатов, автоинверсия, relations.jsonl) + текстовая конвенция
  `wolf:<type>:<id>` с маркерами REQUIRED/BACKGROUND.

**GAP (Phase 22):** роль Analyzer-Worker (воркер, которому отдаётся кластер
сигналов и контракт «верни draft-rule с evidence-ссылками ≥3») не описана в
промптах ролей; протокол Sandbox Replay Holdout (§5) не реализован; механизм
negative constraints (§6) — отсечение повторной генерации отклонённых
кандидатов — не формализован.

### 2.4. Grounding

Проверка «меняет ли кандидат поведение» на данных, а не на мнении.

**Существует:**

- `wolf solve` — реактивный цикл проверки доставки знания (симптом → разбор → починка).
- E2E-сьют (14 файлов) — регрессионная база поведения CLI/MCP.
- Схема pressure-тестов спроектирована (Phase 18, deferred): стимул-промпт +
  `wolf call` против детерминированного mock-агента; сценарий падает при удалении
  call-injection и проходит при его наличии.

**GAP (Phase 22 — Sandbox Replay Holdout; Phase 23 — pressure-тесты):** Phase 18 не реализована
(усилие L, решение 2026-08-26 — не сейчас). В контуре самообучения она сливается
с STOP-гейтом в Phase 23: pressure-тесты становятся обязательным барьером перед
активацией любой автономной адаптации. Sandbox Replay Holdout draft-rule (§5) —
часть Phase 22.

### 2.5. Принятие

Гейт перехода кандидата в активное состояние.

**Существует полностью:**

- Lifecycle-переходы (`ALLOWED_TRANSITIONS`, терминальные статусы: archived,
  completed, accepted, resolved, obsolete, answered) — принудительно в write protocol.
- `wolf supersede <old> <new>` — обратимая замена: старый объект сохраняется,
  получает `superseded_by` (см. §5).
- Governance-атрибуты `memory_class` / `truth_role` / `lifetime` (Phase 6) —
  правило становится `canonical/source_of_truth` только через гейт.
- Для `rule` гейт человека уже встроен: активный `rule` создаёт только
  пользователь (куратор, §4, действует от его лица по explicit permission).

**GAP:** нет — стадия закрывается существующими механизмами + ролью куратора (Phase 22).

### 2.6. Доставка

Знание доезжает до исполняющего агента в нужный момент.

**Существует полностью:**

- `wolf call --for <тема>` + `trigger_keywords` на lesson/rule (Phase 16) —
  матчинг активных объектов по теме.
- Плагин автостарта `.opencode/plugins/wolf-session-start.js` (Phase 15) —
  инжект `wolf recap` + `wolf call --for` в первое user-сообщение, гарантия
  платформы вместо дисциплины агента.
- `.wolf/SKILL.md` §6 Red Flags — контррационализационная таблица (Phase 19).

**GAP:** нет. Измерение эффекта доставки (доставлено ли правило в сессию, где
тема совпала; изменилось ли поведение) — метрики сигнального лога Phase 20.

## 3. Классы адаптации ↔ границы автономии B

Уровень автономии B (решение `...8e7089`): низкий риск — автономно,
высокий (новые правила, промпты ролей, мета-уровень) — через человека.
Адаптирующий ≠ исполняющий: агент, меняющий конфигурацию, не исполняет задачу
в той же сессии, и наоборот.

| Класс адаптации    | Примеры                                   | Цена/риск                    | Автономия при B                    | Механизм                                                                                           |
| ------------------ | ----------------------------------------- | ---------------------------- | ---------------------------------- | -------------------------------------------------------------------------------------------------- |
| Параметры процесса | порог N≥3, лимиты ретраев, таймауты       | дёшево, откат тривиален      | автономно                          | конфиг-файл + git; изменения видны в сигнальном логе                                               |
| Шаблоны            | шаблоны брифов, промпты→команды, SCP      | средне                       | draft автономно, применение — гейт | GEPA-кандидаты (Phase 24; только детерминированные метрики — ниже), Sandbox Replay Holdout + ревью |
| Структура          | скиллы, роли, промпты ролей, мета-уровень | дорого, влияет на все сессии | только гейт человека               | AFlow-роутинг — только эвристики (Phase 25); создание — человеком                                  |

Правило границы: адаптация автономна тогда и только тогда, когда (а) класс —
параметры, (б) STOP-гейт (Phase 23) зелёный, (в) откат — одна операция
(git revert / `wolf supersede`). Всё остальное — draft + гейт.

**Жёсткое ограничение применимости GEPA (Phase 24).** GEPA-скоринг применяется
только к задачам с **детерминированной метрикой качества** — процент упавших
тестов, число rejected-циклов и аналогичные воспроизводимые числовые метрики:
Парето-перебор ревизий требует числовую воспроизводимую метрику (GEPA,
arXiv 2507.19457). Открытые/субъективные задачи (дизайн-качество, «читаемость»)
из GEPA-контура исключены — для них только гейт человека, без автоматического
скоринга. Расширение на открытые задачи — v2, только если появится
детерминированный прокси-скор.

Инструменты — только существующие: `wolf add/get/search/supersede/transition/

`wolf learn digest` и `wolf learn status` (Phase 22, §6) плюс необходимые для
сигнального лога (Phase 20 определит форму: отдельная команда или расширение
`wolf insights`). Алерты не вводятся: куратор работает с батч-дайджестом
(обоснование — §6).

## 5. Гейты и обратимость

**STOP-гейт (Phase 23, слита с Phase 18).** Перед любой автономной адаптацией —
pressure-тесты: harness «стимул-промпт + `wolf call`» против детерминированного
mock-агента, отдельный npm-script вне `check` (запуск агента дорог). Критерий
покрытия: сценарий падает при удалении delivery-механизма (call-injection,
trigger_keywords, правило) и проходит при его наличии; детекция premature action
(действия до доставки знания) — по образцу superpowers `tests/explicit-skill-requests`.

**Sandbox Replay Holdout (Phase 22; прежде — «holdout-валидация»).**
Draft-правило проверяется **реплеем исторических промптов в изолированном
mock-окружении** — детерминированный mock-агент, тот же harness, что у
STOP-гейта (Phase 23). Кластер N≥3 делится: правило применяется к
holdout-сигналам, не участвовавшим в генерации, и должно покрывать их (тот же
error_class/тул) без ложных срабатываний на соседних кластерах. Вердикт
вычисляется по наблюдаемому поведению при реплее, **не LLM-as-a-judge**:
недетерминированный судья делает гейт невоспроизводимым (критика
LLM-as-a-judge на holdout — внешний эксперт, неверифицировано; инженерное
обоснование: гейт обязан быть воспроизводимым и дешёвым в повторных прогонах).
Практика replay-валидации на исторических промптах — eval-наборы Braintrust.
Вердикт фиксируется в объекте с evidence.

**Гейт человека (автономия B).** Структура и шаблоны — принятие только человеком
или куратором с explicit permission (`wolf transition` → accepted; для `rule` —
создание пользователем уже enforcement'ом Phase 6).

**Обратимость.**

- `wolf supersede` — старая версия сохраняется, `superseded_by` указывает на новую;
  история читаема, откат = supersede в обратную сторону.
- Отклонённый кандидат — draft не активируется; причина отклонения фиксируется
  (объект/терминальный переход), сигнал возвращается в пул паттерн-детекции;
  отклонение дополнительно порождает negative constraint (§6).
- Все артефакты — файлы (markdown+frontmatter canonical, конфиги, relations.jsonl):
  git даёт построчный откат; SQLite/индексы — derived, rebuildable.
- Откат активной адаптации: деактивация правила (`wolf transition`) или supersede;
  регресс ловится STOP-гейтом и E2E.

## 6. Negative Constraints, Decay и observability контура

**Negative Constraints (Phase 22).** Отклонённые куратором draft-правила
сохраняются как **hard constraints** для Analyzer-Worker: повторная генерация
похожих кандидатов по тому же кластеру блокируется на уровне контракта
генерации. Носитель — существующая механика Wolf, отдельный json не заводится:
объект `type: lesson` с `trigger_keywords` по теме кластера; связь с отклонённым
draft — `wolf relation add` (Phase 17). Обоснование носителя: (а) семантика
`lesson` — «обход известной ловушки»; ловушка здесь — повторная генерация
отклонённого; (б) доставка — штатный `wolf call --for` в промпт
Analyzer-Worker'а до генерации: Phase 16 (`trigger_keywords` + call-injection)
уже фильтрует активные объекты по теме, новый механизм доставки не нужен;
(в) lifecycle уже даёт управляемую жизнь constraint'а (supersede/archived при
изменении решения куратора).

**Decay (Phase 22).** У `rule`/`lesson` появляется поле `last_triggered_at`:
штамп ставится при каждом срабатывании call-injection (факт доставки — уже
метрика Phase 20). Объект, не сработавший за N дней, получает
`review_required` — значение `review_state`, не lifecycle-статус: объект
остаётся активным, но попадает в очередь пересмотра куратора. Проверка —
фоновая команда без демона: decay-прогон выполняется в составе `wolf learn
digest`/`wolf learn status` и может подвешиваться к плагину автостарта
(Phase 15). N — параметр процесса (класс «параметры», §3); базовое значение
устанавливается при writing-plans Phase 22 по baseline-данным сигнального лога
(Phase 20).

**Батч-дайджест вместо алертов.** Куратор получает `wolf learn digest` с
пороговой накопительной логикой: дайджест собирается, когда накоплено ≥K
элементов (draft-кандидаты, Sandbox Replay Holdout-вердикты, decay-очередь
`review_required`) либо прошло D дней с прошлого дайджеста. Обоснование:
алерты на каждое событие вызывают HITL-усталость и выученное игнорирование
(тезис об алерт-усталости — внешний эксперт, неверифицировано; инженерно:
пакетная обработка требований куратора дешевле прерываний, а порог K
гарантирует, что решение принимается на накопленной статистике, а не на
единичном шуме).

**Observability контура: `wolf learn status`.** Health-check самообучения:
какие кластеры собраны и почему (состав сигналов, порог N≥3, близость), какие
draft-правила отклонены и почему (причина + ссылка на negative constraint),
состояние decay-очереди. Отвечает на вопросы «почему собран кластер» и
«почему отклонён draft» без чтения сырых логов.

| DGM (open-ended эволюция кода)                 | дорого и непредсказуемо; не соответствует local-first и обратимости                                                                                                      |
| ADAS (поиск топологии оркестрации с нуля)      | оркестрация Wolf уже выверена практикой (executor→workers→reviewer); поиск топологии — overhead без гарантий                                                             |
| TextGrad (вычислительный граф поверх промптов) | накладные расходы инфраструктуры градиентов ради выигрыша, покрываемого GEPA-перебором шаблонов                                                                          |
| A-MEM (динамическая связность памяти)          | отложено в v2 (Phase 26): `trigger_keywords` (Phase 16) уже закрывают связность доставки; триггер переоценки — деградация recall `trigger_keywords` по метрикам Phase 20 |
| Календарный каденс обучения                    | отклонён: event-driven пороги (N≥3) вместо расписания — адаптация по сигналу, а не по календарю                                                                          |
| Обязательный LLM-слой                          | память local-first: запись и поиск никогда не требуют LLM; LLM — только опциональный адаптер `opencode run` для синтеза (Phase 21)                                       |

## 8. Критерии успеха v1 (измеримые)

Базовые значения фиксируются на Phase 20 (до любых адаптаций) — сравнение всегда
«до/после» по сигнальному логу. Конкретные числовые пороги N≥3 и размеры holdout
устанавливаются при writing-plans соответствующих фаз; здесь — проверяемые
условия приёмки.

1. **Сигнальный лог (P20):** каждая оркестрационная сессия оставляет
   `session-metrics.json` (OTEL-совместимые поля: task_id, timestamps,
   weighted_tokens, verdict, rejected_cycles, tool_errors); markdown-отчёты
   контуром обучения не парсятся — только JSON; `wolf insights` считает по
   логу плотности и топ-повторы без LLM.
2. **Паттерн-детекция (P21):** кластер ≥3 однотипных сигналов детектируется
   локальной эмбеддинг-кластеризацией (без векторных БД; `error_class_id` —
   опциональное LLM-уточнение) и выдаёт паттерн с evidence-ссылками на
   исходные сигналы; insights L2 через адаптер `opencode run` опционально.
3. **ExpeL-цикл (P22):** ≥1 draft-rule сгенерирован Analyzer-Worker'ом из
   реальных сигналов (не ручной), evidence ≥3, Sandbox Replay Holdout-вердикт
   (реплей в mock-окружении, не LLM-as-a-judge) зафиксирован;
   куратор принял или отклонил с причиной; путь draft→активация невозможен без
   гейта (проверяется тестом).
4. **STOP-гейт (P23):** pressure-сценарий падает при удалении delivery-механизма
   и проходит при его наличии; прогон вынесен из `check` в отдельный npm-script.
5. **Доставка:** активные rule/lesson, влияющие на поведение, имеют
   `trigger_keywords`; факт доставки в сессию с совпавшей темой виден в
   сигнальном логе (до/после — сравнимо).
6. **GEPA (P24):** скоринг качество/стоимость/время считается по сигнальному
   логу для ≥2 ревизий одного шаблона брифа — только на задачах с
   детерминированной метрикой качества (процент упавших тестов, число
   rejected-циклов; открытые задачи исключены); применение — только через гейт.
7. **AFlow (P25):** эвристика глубины ревью для ≥1 типа задач согласована
   человеком (гейт) и даёт нехудшие метрики против базовой линии.
8. **Общий инвариант:** каждая слитая адаптация не ухудшает стоимость/время
   (в пределах шума метрик) при росте качества — проверяется сравнением
   сигнального лога до/после на одном и том же типе задач.
9. **Negative Constraints + Decay + observability (P22):** отклонённый
   куратором кандидат блокирует повторную генерацию похожего — negative
   constraint доставлен в промпт Analyzer-Worker'а через `wolf call --for`
   (проверяется тестом); `rule`/`lesson` имеют `last_triggered_at`, не
   сработавшие за N дней получают `review_required` и попадают в дайджест;
   `wolf learn digest` собирается по пороговой логике (≥K элементов или D
   дней); `wolf learn status` отвечает на вопросы «почему собран кластер» и
   «почему отклонён draft».
