# Базовый набор

Базовый набор — агентская обвязка, которую Mr. Wolf доставляет в проект: агенты, скиллы, команды, плагины opencode и плейбуки. Источник истины — каталог `templates/` npm-пакета `mister-wolf`: `wolf init` рендерит набор в проект, `wolf sync` перерендеривает его позже (см. [Платформа и обслуживание — wolf sync](/ru/guide/cli/platform#wolf-sync)). Набор также дописывает онбординг-блок в корневой `AGENTS.md` проекта (маркер `<!-- wolf:onboarding v2 -->`; чужой контент не трогается).

Состав ниже — каталог `templates/base/` в пакете.

## Агенты — 6 → `.opencode/agents/`

| Агент                | Роль                                                                                                        |
| -------------------- | ----------------------------------------------------------------------------------------------------------- |
| `mr-wolf`            | Координатор (L0): брифы, диспетчеризация executor'ов, приёмка по отчётам; кода не касается                  |
| `steward`            | Наставник (фон): мутатор playbook'ов в памяти Wolf по жалобам; вызов только вложенный                       |
| `executor-lead`      | Уровень 1: принимает Task Brief, декомпозирует, исполняет сам или через воркеров, возвращает отчёт          |
| `worker-implementer` | Однозадачный исполнитель кода (L2): ровно одна подзадача, правки по allowlist, самопроверка, короткий отчёт |
| `worker-researcher`  | Исследует код, документы и веб по одному вопросу; findings с источниками и confidence                       |
| `worker-reviewer`    | Ревьюит код/документы воркеров против требований брифа; вердикт по контракту VERDICT/SUMMARY                |

## Команды — 3 → `.opencode/command/`

| Команда       | Что делает                                                               |
| ------------- | ------------------------------------------------------------------------ |
| `analyze-doc` | анализ документа по методике из памяти Wolf (playbook worker-researcher) |
| `complain`    | жалоба владельца в контур мутаций памяти: complaint → триаж → Стюард     |
| `doc-review`  | мульти-линзовое ревью документа через скилл wolf-review                  |

## Плагины — 2 → `.opencode/plugins/`

Плагины приезжают из harness-слоя пакета (`templates/opencode/plugins/`) и входят в тот же штампованный набор:

- `wolf-router` — детерминированная доставка playbook-контекста агенту (по маркеру `agent-id`); решения о маршрутизации пишет в `.wolf/router.log` (с наблюдаемыми полями `ms=`/`bytes=`), вызовы скиллов — в `.wolf/metrics/skill-invocations.jsonl`: скиллы теперь измеримы (см. [Аналитика — панель доставки](/ru/guide/cli/analytics#панель-доставки)).
- `wolf-session-start` — инъекция bootstrap-контекста, когда в актуальном транскрипте нет маркера (покрывает старт сессии, `/clear` и compact); ведёт ключ `WOLF_SESSION`: с 2.13 `opc-<uuid>` наследуется между спавнами CLI одной логической сессии (ключ ставится только при отсутствии) — дедупликация доставки работает на всю сессию (см. [Телеметрия — ключи сессий](/ru/guide/telemetry#ключи-сессий)).

## Плейбуки — 6 → посев в память Wolf

Плейбуки — исключение: это **не** штампованные файлы. С 2.13 это больше не тип `playbook`: `wolf init` сеет их в память `.wolf/` объектами `note` с `facet: howto` и полем `owner_skill` (скип, если `owner_skill` уже посеян). Дальше они — память: мутации идут через жалобный контур и Стюарда, `wolf sync` их не трогает. См. [Модель памяти](/ru/guide/memory).

| Плейбук                       | Содержание                           | Владелец             |
| ----------------------------- | ------------------------------------ | -------------------- |
| `complaint-protocol`          | подача жалоб и дерево триажа         | `mr-wolf`            |
| `executor-lead-playbook`      | конвейер декомпозиции и приёмки лида | `executor-lead`      |
| `steward-nastavnik`           | протокол мутации playbook'ов         | `steward`            |
| `worker-implementer-playbook` | методика и формат отчёта исполнителя | `worker-implementer` |
| `worker-researcher-playbook`  | методика анализа и формат findings   | `worker-researcher`  |
| `worker-reviewer-playbook`    | зоны обзора и VERDICT-контракт       | `worker-reviewer`    |

## Штампованные файлы и sync

Агенты, скиллы, команды и плагины набора доставляются и обновляются как **штампованные** (stamped) файлы: каждый несёт маркер `wolf:rendered base=<base> set=<version>` сразу после frontmatter. `wolf sync` перерендеривает только штампованные файлы — память (`.wolf/`) не трогается:

- `created` — файла не было;
- `skipped` — штампованный контент идентичен;
- `updated` — файл штампован, но отличается от шаблона: **локальные правки штампованного файла перезаписываются** рендером;
- `conflict` — на месте шаблона нештампованный файл: решает владелец — переименовать, удалить или оставить как есть;
- `orphaned` — штампованный файл, чей шаблон исчез из пакета; можно удалить.

Нештампованный файл — ваш (политика `wx`): `wolf init` его пропускает, `wolf sync` сообщает конфликт вместо перезаписи. Источник истины — всегда `templates/` в npm-пакете: обновления шаблонов приезжают с пакетом (`wolf upgrade`) и попадают в проект через `wolf sync`. Оговорка: npx try-out режим никогда не пишет базовый набор.

Хотите кастомизировать агента или скилл? Делайте это в памяти, а не в штампованном файле: подайте жалобу (`wolf complain`) и пусть Стюард мутирует playbook — либо форкните файл, сняв штамп, приняв, что `wolf sync` больше им не управляет.
