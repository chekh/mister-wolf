# Базовый набор

Базовый набор — агентская обвязка, которую Mr. Wolf доставляет в проект: агенты, скиллы, команды и плейбуки. Источник истины — каталог `templates/` npm-пакета `mister-wolf`: `wolf init --full` рендерит набор в проект, дальнейшие обновления приезжают проектным проходом `wolf upgrade` (`--here` — один проект; см. [Платформа и обслуживание — wolf upgrade](/ru/guide/cli/platform#wolf-upgrade) и сценарий на [Обновление проекта и парка](/ru/guide/upgrade)). Набор также поставляет онбординг-блок для корневого `AGENTS.md` проекта (маркер `<!-- wolf:onboarding v4 -->`): новый файл получает его в составе штампованного whole-file рендера, существующему блок дописывается, а всё вне маркеров сохраняется байт-в-байт.

Состав ниже — каталог `templates/base/` в пакете.

## Агенты — 9 → `.opencode/agents/`

| Агент                | Роль                                                                                                                                                                                                                                                                                                                       |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `mr-wolf`            | Ведущий: уточняет цель, часть работы выполняет сам, нанимает восемь исполнителей wolf-* напрямую и принимает их результаты по evidence |
| `wolf-architect`     | Требования, design, test-plan и план в границах назначенного документа |
| `wolf-developer`     | Одна законченная часть реализации с тестами и проверяемым результатом |
| `wolf-editor`        | Один проход редактуры читаемости готового документа без исследований |
| `wolf-expert`        | Ограниченная профессиональная позиция по одному вопросу и линзе; читает файлы проекта, включая код, через tool-enabled read-канал в границах проекта; запись, shell, субагенты, webfetch и внешние каталоги остаются запрещены; при деградации — packet-only с явным `channel`; см. [Экспертный консилиум](/ru/guide/council) |
| `wolf-release-engineer` | Подготовка выпуска и проверка конкретной принятой ревизии |
| `wolf-researcher`    | Адресное исследование или диагностика конкретного неизвестного; findings с источниками и confidence; по явно назначенному архитектурному вопросу сравнивает варианты и возвращает рекомендацию — файлы не пишет и архитектуру не утверждает |
| `wolf-reviewer`      | Независимое ревью конкретной ревизии по назначенной линзе; вердикт по контракту VERDICT/SUMMARY |
| `wolf-tester`        | Независимая проверка поведения, интеграции и регрессии |

Агент `steward` в набор 3.0.0 не входит: роль временно выведена из штатной маршрутизации и вернётся в следующем релизе; её механизмы — история лиц и приём жалоб — сохранены (см. [Стюард и обучение](/ru/guide/feedback)).

Каждое поручение несёт блок execution: запрошенные model/variant, режим execute/solve, бюджет обращений и условие остановки. С 2.24.0 в нём есть и ось плотности — `density standard|draft`. Режим выбирает ведущий при записи TASK; отсутствие поля означает `standard`. В `draft` исполнитель сокращает видимую служебную запись — повторные пересказы, изложение очевидного, ритуальные подытоги, — сохраняя обязательные проверки, права, evidence и независимую приёмку; существенная неопределённость расширяет адресную проверку, а не сокращает ответ; неподдержанная плотность возвращается ведущему. Приёмка сверяет наблюдаемые действия, evidence и результат, а не ярлык draft в RESULT. Числовая экономия не заявляется; измеримое сравнение — отдельное наблюдение (роадмап A1.2).

Для L0/L1 bootstrap доставляет полный текст установленного `using-skills`, а не отдельный пересказ. Агент проверяет маршрут при новой цели или этапе; другие скиллы загружает до их выполнения. L2 получает пассивный контур и назначенные методики. Если полный текст недоступен, bootstrap явно сообщает об ограничении.

wolf-work-strategy загружается один раз для поручения и повторно при смене версии или утрате текста. Он помогает выбрать действие; обязательные проектные гейты и роли сохраняются. Вопрос может заменить дорогое расследование, включая установление факта; очевидный факт из входов агент выясняет сам. Без диалога внутри вызова L2 возвращает вопрос L1 существующим контрактом. Обновление шаблонов не заменяет согласование старого active playbook через действующий контур Стюарда.

wolf-user-report загружается для запрошенного или согласованного самостоятельного документа для человека, включая его обновление. Скилл доступен в полном базовом наборе, но не загружается автоматически для реплик в диалоге и машинных RESULT/EVIDENCE. Заданный формат и рамки роли сохраняются; оформление не запускает новое исследование. Темы и шаблоны остаются ресурсами проекта, без обязательных CSS-профилей в поставке.

wolf-document-readability загружается, когда готовый документ — требования, CR, design/ADR, план, test-plan, инструкция или отчёт — идёт по маршруту редактуры читаемости: автор передаёт текст назначенному L2 техническому писателю до содержательного ревью. Проход сохраняет содержание и точность (утверждения, числа, даты, ID, ссылки, условия, статусы, чекбоксы, append-only части), не исследует код, не проверяет технические решения и не создаёт документацию с нуля. Он не заменяет содержательное ревью (wolf-review) и не является самостоятельным документом для человека (wolf-user-report); один проход приходится на первый выпуск или существенную переработку, автоматически к диалогу и служебным TASK/RESULT скилл не применяется.

Плагины приезжают из harness-слоя пакета (`templates/opencode/plugins/`) и входят в тот же штампованный набор:

Штатная доставка плагинов не требует: с 3.0.0 `wolf init` не устанавливает плагины Wolf — они поставляются в резерве в `templates/opencode/plugins-reserved/`, и наличие файла там не означает включённый плагин. Если вы оставили их включёнными с прежнего релиза, они продолжают работать:

Если плагин включён, он пишет решения о маршрутизации в `.wolf/router.log` (с наблюдаемыми полями `ms=`/`bytes=`), вызовы скиллов — в `.wolf/metrics/skill-invocations.jsonl` (см. В штатной доставке 3.0.0 плагин не установлен, поэтому этих записей — включая счётчики скиллов — нет; их отсутствие не означает отсутствие вызовов. Оценки затрат считаются по исходным usage и сессиям OpenCode (`opencode.db`).
- `wolf-session-start` — опциональный (в резерве): инъекция bootstrap-контекста, когда в актуальном транскрипте нет маркера (покрывает старт сессии, `/clear` и compact); ведёт ключ `WOLF_SESSION`: с 2.13 `opc-<uuid>` наследуется между спавнами CLI одной логической сессии (ключ ставится только при отсутствии) — дедупликация доставки работает на всю сессию (см. [Телеметрия — ключи сессий](/ru/guide/telemetry#ключи-сессии)).

## Плейбуки — объекты памяти, больше не сеются

Плейбуки — исключение: это **не** штампованные файлы. С 2.13 это больше не тип `playbook`: `wolf init --full` сеет их в память `.wolf/` — с 2.17 объектами `face` (версионируемый core-тип с полем `owner_skill`; скип, если уже есть живое лицо или legacy-заметка с этим `owner_skill`). Дальше они — память: мутации идут через жалобный контур и Стюарда (версии `wolf face` с обязательной записью мутации), проход обновления их не трогает. Поэтому проход добавляет недостающее лицо, но никогда не перерендеривает существующее; `wolf init --yes` перерендеривает лицо, пока оно ещё с инициатором `seed`/`migration`, а лицо, уже версионированное Стюардом или владельцем, не трогает никто. Проект, посеянный в прошлом релизе, сохраняет своё тело, пока не сработает один из этих путей (см. [Troubleshooting — устаревшая формулировка в доставленном плейбуке](/ru/guide/troubleshooting#_16-доставленныи-плеибук-все-еще-содержит-устаревшую-формулировку)). Legacy-заметки мигрируются через `wolf face migrate`. См. [Модель памяти](/ru/guide/memory).

Команды лица остаются только за владельцем. `wolf face restore --from <id|vN>` и `wolf face migrate` отказывают внутри агент-сессии (`WOLF_SESSION=opc-*`) так же, как `wolf face breakglass`: в агент-сессии актор — `user:cli`, а не владелец, а `restore` берёт тело целиком из версии-основы, поэтому накопленные правки живого лица теряются; отказ журналируется (`memory.face.denied`). В терминале владельца обе команды работают как раньше. `wolf scaffold agent|skill|command <name>` отказывает, если живое лицо с тем же `owner_skill` уже существует, и называет его id и версию, — заглушка scaffold больше не может затереть живое лицо; новое имя работает как раньше, а существующее лицо обновляет Стюард (`wolf face new` с `WOLF_ACTOR=agent:steward`), не scaffold. Скаффолд 3.0.0 самодостаточен: каркас агента не несёт лица, ссылки на роутер и дефолт-модели.

С 3.0.0 базовый набор не сеет playbook-лица: поведение агентов доставляется рамками, стартовым блоком `AGENTS.md` и именованными скиллами, а не инъекцией playbook-объектов — ни один шаблон больше не несёт `owner_skill`. Лица остаются типом памяти, который проект может вести; версии и мутации — [Доставка и доверие](/ru/guide/delivery) и [Стюард и обучение](/ru/guide/feedback).

## Штампованные файлы и sync

Агенты, скиллы, команды и плагины набора доставляются и обновляются как **штампованные** (stamped) файлы: каждый несёт маркер `wolf:rendered base=<base> set=<version>` сразу после frontmatter. Проход обновления (`wolf upgrade` — проектный проход; `--here` — один проект; `wolf sync` — депрекированный алиас) перерендеривает только штампованные файлы — память (`.wolf/`) не трогается:

- `created` — файла не было;
- `skipped` — штампованный контент идентичен;
- `updated` — файл штампован, но отличается от шаблона: **локальные правки штампованного файла перезаписываются** рендером;
- `updated (stamp drift healed)` — контент идентичен шаблону, кроме самой строки `wolf:rendered …` (её поставил старый релиз): волф перезаписывает файл, выравнивая штамп, и обновляет свидетеля. Это не решение и не `behind` в `--check` — устаревший штамп сам по себе не является локальной правкой;
- `conflict` — на месте шаблона нештампованный файл: решает владелец — переименовать, удалить или оставить как есть;
- `protected` — в frontmatter файла стоит `protect: true` (или `protect: X.Y.Z`): файл не перезаписывается и не удаляется, что бы ни говорил релиз;
- `kept` — вы приняли локальный контент штампованного файла (`wolf upgrade --resolve <файл>=keep`): свидетель запоминает его как принятый, и следующий проход не откатывает вашу правку;
- `orphaned` — штампованный файл, чей шаблон исчез из пакета; можно удалить либо удержать через `protect`.

Значение `set=` фиксирует версию пакета, который последним отрендерил файл: проход обновления берёт его из запущенного CLI, а не из карты обновления, поэтому это тот релиз, который вы установили и запустили, — не обязательно тот, о котором читали. Отсюда и `stamps 2.21.2 · map 2.22.0` в `wolf upgrade --check`: записи ещё не было. Файл под `protect:` не перерендеривается никогда, поэтому сохраняет `set=` последнего рендера; значение `protect:` фиксирует релиз только в форме `X.Y.Z` — `protect: true` версии не несёт.

Нештампованный файл — ваш (политика `wx`): `wolf init` его пропускает, проход обновления сообщает конфликт вместо перезаписи. Источник истины — всегда `templates/` в npm-пакете: обновления шаблонов приезжают с пакетом (`wolf upgrade`) и попадают в проект через его проектный проход. Оговорка: npx try-out режим никогда не пишет базовый набор.

### Онбординг-блок в `AGENTS.md`

`AGENTS.md` управляется в одном из двух режимов, и оба сохраняют ваше авторство:

- **Штампованный whole-file режим — то, что пишет свежий `init`**: у `AGENTS.md` есть штамп `wolf:rendered …` и файл принадлежит волфу целиком — локальные правки дают `mutated`, судьбу решают `take`/`keep`. Ключ `protect` здесь недоступен, потому что файл поставляется без YAML-frontmatter.
- **Блочный режим — то, что `init` дописывает, если `AGENTS.md` уже существовал**: волф владеет только строками между `<!-- wolf:onboarding v4 -->` и `<!-- /wolf:onboarding -->`. Всё выше и ниже остаётся байт-в-байт, включая переводы строк. Сам блок — версионируемый формат: существующий ранний блок (`v2`/`v3`) распознаётся и обновляется на месте до `v4` (двухуровневый протокол: mr-wolf и исполнители wolf-*, адресные входы, правила docs/dev); второй блок не дописывается никогда, а текст **внутри** блока — зона волфа и не сохраняется. Сломанная пара маркеров (открывающий без закрывающего) делает файл чужим: он пропускается и сообщается как `onboarding markers broken`, решением не становится.

`wolf upgrade` никогда не дописывает блок в `AGENTS.md` без штампа и без маркеров — его создаёт только `init`. Файл, который создавал не волф, остаётся чужим.

Хотите кастомизировать агента или скилл? Делайте это в памяти, а не в штампованном файле: подайте жалобу (`wolf complain`) — в 3.0.0 она принимается и фиксируется; Стюард, мутирующий playbook, временно отключён — либо форкните файл, сняв штамп, приняв, что проход обновления больше им не управляет. Если нужно всего лишь сохранить локальную версию файла, которым волф управляет, объявите намерение в самом файле (`protect: true` или `wolf upgrade --resolve <файл>=protect`), а не снимайте штамп: файл остаётся видимым в `wolf upgrade --check`, и в этом весь смысл. Полный сценарий: [Обновление проекта и парка](/ru/guide/upgrade).

## Адресная маршрутизация и средства проекта

using-skills содержит компактное ядро и тематические references: когда, как и какой
результат. Назначенный навык доступен напрямую; L2 не обходит каталог. L1 собирает
помощника из L2, лица и скиллов, а программные средства обслуживают механику.

### Справочник внутреннего языка агентов

С 2.29.0 using-skills поставляет `references/agent-language.md` — статичную спецификацию внутреннего языка агентов: общие термины (TASK, RESULT, DONE ≠ ACCEPTED, EVIDENCE, VERDICT, COMPLAINT и остальные), правила употребления R1–R6 и escape-высказывание для ситуаций, которые форма не покрывает. Какую проблему решает: этот язык сопровождает каждую передачу работы между агентами, и пересказы терминов, разбросанных по контрактным текстам, дрейфуют и вызывают переспросы — один письменный справочник даёт всем агентам одни и те же слова. Слоты сообщений остаются нормативными в `contracts.md`; спецификация ссылается на него и новых обязательных полей не вводит.

Статус — этап наблюдения. Спецификация фиксирует существующие конструкции и не меняет runtime; снижает ли она переспросы и дрейф смысла на самом деле, не измерялось, и до конца этапа язык зафиксирован. Если проблема в самом термине или форме, жалобы получили предмет LANGUAGE — `LANGUAGE/ambiguous-definition`, `LANGUAGE/insufficient-form`, `LANGUAGE/excessive-requirement` (см. [Стюарда](/ru/guide/feedback)). Человек во всех случаях получает обычный язык.

Три инженерских скилла встроены в существующий маршрут, а не добавляют в него стадию: цель доходит до L1, `wolf-design` применяет методику software-design там, где открыты границы и контракты, дальше идут существующие plan и test-plan, исполнитель получает `wolf-code-craft`, а действующее независимое ревью и проверки проекта остаются на своих местах.

На явно назначенный архитектурный вопрос researcher отвечает сравнением вариантов и рекомендацией — саму архитектуру утверждает ответственный уровень. Упрощение (`wolf-code-simplify`) назначается отдельно, когда названная сложность требует разбора; это не автоматический дополнительный круг, а лишнюю сложность в текущем мандате исполнитель устраняет сам. Документы и операции без программной реализации инженерный набор автоматически не получают.

Скиллы дополняют возможности, которые накапливает организация (см. [Возможности и границы](/ru/guide/capabilities)), и не добавляют агента, лицо и поверхность runtime.

Карточка tool хранит ссылку на исходники проекта вместо копии в `.wolf/tools/`:
точка входа регистрируется по проектному пути, дополнительные значимые файлы
добавляются повторяемым `--resource`, а явный `--update` обновляет тот же ID
карточки при изменении исходника. Прежние регистрации продолжают работать без
массового переноса. Проверка `source_digest` подтверждает только неизменность
перечисленных файлов; среда и побочные эффекты зависят от контракта карточки.
`tool use` — учёт использования, не выполнение. Полный синтаксис команд со всеми
флагами: [справочник CLI](/ru/guide/cli/command-reference).
