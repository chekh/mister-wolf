# Базовый набор

Базовый набор — агентская обвязка, которую Mr. Wolf доставляет в проект: агенты, скиллы, команды, плагины opencode и плейбуки. Источник истины — каталог `templates/` npm-пакета `mister-wolf`: `wolf init --full` рендерит набор в проект, дальнейшие обновления приезжают проектным проходом `wolf upgrade` (`--here` — один проект; см. [Платформа и обслуживание — wolf upgrade](/ru/guide/cli/platform#wolf-upgrade) и сценарий на [Обновление проекта и парка](/ru/guide/upgrade)). Набор также дописывает онбординг-блок в корневой `AGENTS.md` проекта (маркер `<!-- wolf:onboarding v3 -->`; чужой контент не трогается, а всё вне маркеров сохраняется байт-в-байт).

Состав ниже — каталог `templates/base/` в пакете.

## Агенты — 6 → `.opencode/agents/`

| Агент                | Роль                                                                                                                                                                                 |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `mr-wolf`            | Координатор (L0): брифы, диспетчеризация executor'ов, приёмка по отчётам; кода не касается                                                                                           |
| `steward`            | Наставник (фон): мутатор playbook'ов по жалобам, агрегатор зрелых уроков ([контур](/ru/guide/feedback), [агрегация](/ru/guide/feedback#steward-aggregation)); вызов только вложенный |
| `executor-lead`      | Уровень 1: принимает Task Brief, декомпозирует, исполняет сам или через воркеров, возвращает отчёт                                                                                   |
| `worker-implementer` | Однозадачный исполнитель кода (L2): ровно одна подзадача, правки по allowlist, самопроверка, короткий отчёт                                                                          |
| `worker-researcher`  | Исследует код, документы и веб по одному вопросу; findings с источниками и confidence                                                                                                |
| `worker-reviewer`    | Ревьюит код/документы воркеров против требований брифа; вердикт по контракту VERDICT/SUMMARY                                                                                         |

Для L0/L1 bootstrap доставляет полный текст установленного `using-skills`, а не отдельный пересказ. Агент проверяет маршрут при новой цели или этапе; другие скиллы загружает до их выполнения. L2 получает пассивный контур и назначенные методики. Если полный текст недоступен, bootstrap явно сообщает об ограничении.

## Плагины — 2 → `.opencode/plugins/`

Плагины приезжают из harness-слоя пакета (`templates/opencode/plugins/`) и входят в тот же штампованный набор:

- `wolf-router` — детерминированная доставка playbook-контекста агенту (по маркеру `agent-id`); решения о маршрутизации пишет в `.wolf/router.log` (с наблюдаемыми полями `ms=`/`bytes=`), вызовы скиллов — в `.wolf/metrics/skill-invocations.jsonl`: скиллы теперь измеримы (см. [Аналитика — панель доставки](/ru/guide/cli/analytics#панель-доставки)).
- `wolf-session-start` — инъекция bootstrap-контекста, когда в актуальном транскрипте нет маркера (покрывает старт сессии, `/clear` и compact); ведёт ключ `WOLF_SESSION`: с 2.13 `opc-<uuid>` наследуется между спавнами CLI одной логической сессии (ключ ставится только при отсутствии) — дедупликация доставки работает на всю сессию (см. [Телеметрия — ключи сессий](/ru/guide/telemetry#ключи-сессий)).

## Плейбуки — 6 → посев в память Wolf

Плейбуки — исключение: это **не** штампованные файлы. С 2.13 это больше не тип `playbook`: `wolf init --full` сеет их в память `.wolf/` — с 2.17 объектами `face` (версионируемый core-тип с полем `owner_skill`; скип, если уже есть живое лицо или legacy-заметка с этим `owner_skill`). Дальше они — память: мутации идут через жалобный контур и Стюарда (версии `wolf face` с обязательной записью мутации), проход обновления их не трогает. Legacy-заметки мигрируются через `wolf face migrate`. См. [Модель памяти](/ru/guide/memory).

| Плейбук                       | Содержание                           | Владелец             |
| ----------------------------- | ------------------------------------ | -------------------- |
| `complaint-protocol`          | подача жалоб и дерево триажа         | `mr-wolf`            |
| `executor-lead-playbook`      | конвейер декомпозиции и приёмки лида | `executor-lead`      |
| `steward-nastavnik`           | протокол мутации playbook'ов         | `steward`            |
| `worker-implementer-playbook` | методика и формат отчёта исполнителя | `worker-implementer` |
| `worker-researcher-playbook`  | методика анализа и формат findings   | `worker-researcher`  |
| `worker-reviewer-playbook`    | зоны обзора и VERDICT-контракт       | `worker-reviewer`    |

## Штампованные файлы и sync

Агенты, скиллы, команды и плагины набора доставляются и обновляются как **штампованные** (stamped) файлы: каждый несёт маркер `wolf:rendered base=<base> set=<version>` сразу после frontmatter. Проход обновления (`wolf upgrade` — проектный проход; `--here` — один проект; `wolf sync` — депрекированный алиас) перерендеривает только штампованные файлы — память (`.wolf/`) не трогается:

- `created` — файла не было;
- `skipped` — штампованный контент идентичен;
- `updated` — файл штампован, но отличается от шаблона: **локальные правки штампованного файла перезаписываются** рендером;
- `updated (stamp drift healed)` — контент идентичен шаблону, кроме самой строки `wolf:rendered …` (её поставил старый релиз): волф перезаписывает файл, выравнивая штамп, и обновляет свидетеля. Это не решение и не `behind` в `--check` — устаревший штамп сам по себе не является локальной правкой;
- `conflict` — на месте шаблона нештампованный файл: решает владелец — переименовать, удалить или оставить как есть;
- `protected` — в frontmatter файла стоит `protect: true` (или `protect: X.Y.Z`): файл не перезаписывается и не удаляется, что бы ни говорил релиз;
- `kept` — вы приняли локальный контент штампованного файла (`wolf upgrade --resolve <файл>=keep`): свидетель запоминает его как принятый, и следующий проход не откатывает вашу правку;
- `orphaned` — штампованный файл, чей шаблон исчез из пакета; можно удалить либо удержать через `protect`.

Нештампованный файл — ваш (политика `wx`): `wolf init` его пропускает, проход обновления сообщает конфликт вместо перезаписи. Источник истины — всегда `templates/` в npm-пакете: обновления шаблонов приезжают с пакетом (`wolf upgrade`) и попадают в проект через его проектный проход. Оговорка: npx try-out режим никогда не пишет базовый набор.

### Онбординг-блок в `AGENTS.md`

`AGENTS.md` управляется в одном из двух режимов, и оба сохраняют ваше авторство:

- **Блочный режим** (то, что создаёт `init`): волф владеет только строками между `<!-- wolf:onboarding v3 -->` и `<!-- /wolf:onboarding -->`. Всё выше и ниже остаётся байт-в-байт, включая переводы строк. Сам блок — версионируемый формат: существующий блок `v2` распознаётся и обновляется на месте до `v3` (в блоке появилась строка про намерения владельца — `protect` и `--review`); второй блок не дописывается никогда, а текст **внутри** блока — зона волфа и не сохраняется. Сломанная пара маркеров (открывающий без закрывающего) делает файл чужим: он пропускается и сообщается как `onboarding markers broken`, решением не становится.
- **Штампованный whole-file режим**: у `AGENTS.md` есть штамп `wolf:rendered …` и файл принадлежит волфу целиком — локальные правки дают `mutated`, судьбу решают `take`/`keep`. Режим старше блочного; ключ `protect` здесь недоступен, потому что файл поставляется без YAML-frontmatter.

`wolf upgrade` никогда не дописывает блок в `AGENTS.md` без штампа и без маркеров — его создаёт только `init`. Файл, который создавал не волф, остаётся чужим.

Хотите кастомизировать агента или скилл? Делайте это в памяти, а не в штампованном файле: подайте жалобу (`wolf complain`) и пусть Стюард мутирует playbook — либо форкните файл, сняв штамп, приняв, что проход обновления больше им не управляет. Если нужно всего лишь сохранить локальную версию файла, которым волф управляет, объявите намерение в самом файле (`protect: true` или `wolf upgrade --resolve <файл>=protect`), а не снимайте штамп: файл остаётся видимым в `wolf upgrade --check`, и в этом весь смысл. Полный сценарий: [Обновление проекта и парка](/ru/guide/upgrade).
