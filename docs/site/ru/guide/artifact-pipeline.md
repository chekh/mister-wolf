# Артефактный конвейер

Каждая фича в проекте на Wolf живёт в документах, а не в племенном знании. Артефактный конвейер — документная лента, которую проходит фича: `pre-requirements.md` → `requirements.md` → `change-request.md` → `design.md` → `test-plan.md` → `plan.md`, вместе в датированной папке `docs/dev/<YYYY-MM-DD>-<slug>/`. Картину дополняют ещё две локации: wave-файл собирает то, что поставляет релизная волна, а папка роадмапа `docs/dev/roadmap/` хранит записи дальнего горизонта.

Ничто в конвейере не «готово» оттого, что его написал агент, — оно готово, когда прошло ворота.

## Что это

Конвейер — набор документов фичи, движущихся по статусам под воротами владельца и линз. Папка фичи стартует scaffold-командой и растёт через ревью; `wolf sync` держит индексы актуальными (депрекированный с 2.19.0 алиас — индексы регенерирует именно он), `wolf doctor` линтит результат. Лента покрывает:

- папку фичи `docs/dev/<YYYY-MM-DD>-<slug>/` с шестью файлами пакета;
- wave-файл текущей релизной волны;
- папку роадмапа `docs/dev/roadmap/`.

## Команды

Конвейер крутят четыре команды — и с 2.17.1 пишущая сессия сначала владеет claim'ом одиночного писателя:

```bash
wolf claim acquire dev:<date>-<slug>  # own the artifact — scaffold refuses without it
wolf scaffold artifact <slug>         # create docs/dev/<YYYY-MM-DD>-<slug>/ with the full 6-file package
wolf scaffold artifact <slug> --fix   # fix profile: requirements.md + plan.md only
wolf sync                             # regenerate indexes — idempotent
wolf doctor                           # lint the documents
```

Полный профиль пишет пакет в объявленном порядке — `pre-requirements.md`, `requirements.md`, `change-request.md`, `design.md`, `test-plan.md`, `plan.md`. `pre-requirements.md` фиксирует намерение и рамку до формальных требований (он их не утверждает); `change-request.md` — append-only список запросов на изменение пакета. Если папка уже существует (например, brainstorm записал `pre-requirements.md` в тот же день), команда делает top-up: добавляет только недостающие документы и никогда не перезаписывает существующий. Папка строится из текущей даты и slug, поэтому пакет, начатый в другой день, не пополняется — его продолжают вручную либо осознанно начинают пакет новой даты. Когда все файлы на месте, команда сообщает, что добавлять нечего.

Claim — замок записи конвейера: два агента, редактирующие одну папку фичи, молча затирали бы друг друга, поэтому `wolf scaffold artifact` без активного claim'а отвечает отказом `No claim held` — в сообщении отказа точная команда `claim acquire`. Закончив писать, сессия освобождает владение (`wolf claim release dev:<date>-<slug>`) или передаёт его (`--transfer-to <actor>`); `wolf claim list` показывает, кто чем владеет. Claim истекает через 24 часа, так что упавшая сессия не запирает папку навсегда.

`wolf sync` генерирует `docs/dev/INDEX.md` — таблицу фич плюс секцию "Waves" — и файлы `_index.md` внутри подпапок design и plan. Повторный запуск ничего не меняет. (Как команда базового сета депрекирован в 2.19.0 → `wolf upgrade --here`; регенерация индексов — причина, по которой алиас ещё существует.)

`wolf doctor` сообщает находки по документам в своей секции `## Artifacts (docs/dev)` (см. [Платформа и обслуживание](/ru/guide/cli/platform)). Классы находок:

- дубликаты id REQ/NFR;
- битые ссылки на id REQ;
- REQ без критериев приёмки или без Source;
- метка `[НЕОПРЕДЕЛЕНО]` («undefined») внутри одобренного документа;
- запись CR без downstream-артефактов, с номером не по форме `CR-<YYYY-MM-DD>-NN` или без утвердившего;
- сброс статусов downstream после правки upstream;
- дубликаты требований;
- дубликаты записей роадмапа;
- готовность папки — отсутствие файлов набора;
- призрачные скиллы — перечислены в наборе, но отсутствуют в памяти.

## Статусы артефактов

Каждый артефакт проходит ровно три статуса: `draft → review → approved`. Это вся доска — ни канбана, ни колонок, ни wip-лимитов. Статус отвечает на один вопрос: прошёл ли этот документ свои ворота?

## Ворота

Ворота решают каждый переход. Владелец одобряет `requirements.md`; ADR-карточки внутри `design.md` получают отдельную визу владельца; следующая стадия открывается только после одобрения предыдущей. Линзы ревьюят пары файлов:

| Линза           | Ревьюит                  | Пара            |
| --------------- | ------------------------ | --------------- |
| Полнота         | requirements             | requirements.md |
| Консистентность | design                   | design.md       |
| Соответствие    | plan ↔ design            | plan.md         |
| Покрытие AC     | test-plan ↔ requirements | test-plan.md    |

Security — строго опциональная линза: её нет в базовом наборе. Добавляйте её осознанно, когда фича того требует.

## Эволюция

Одобрено не значит заморожено — это значит, что изменения теперь имеют цену. Изменение входит через `change-request.md`: нумерованная запись (`CR-<YYYY-MM-DD>-NN`) с тем, что и почему меняется, затронутыми REQ/NFR, утвердившим и списком downstream-артефактов для перегенерации. Затем запрос обновляет `pre-requirements.md`/`requirements.md`, а статусы downstream сбрасываются в `draft` и снова должны заслужить одобрение. Поток: замечание → change-request → pre-requirements/requirements → design → test-plan → plan.

`change-request.md` — отдельный документ, а не раздел «Журнал изменений (CR)» внутри `requirements.md`: тот раздел фиксирует изменения самих требований, а `change-request.md` — запросы, которые могут затронуть любой документ пакета. Линт `wolf doctor` следит за механикой в обоих: CR без списка downstream, устаревшие downstream-статусы, номер не по форме и ссылка на несуществующий REQ всплывают как находки.

## Дисциплина языка

`requirements.md` пишется на языке владельца, без жаргона — документ должен выдержать чтение непрограммистом. Технические артефакты (`design.md`, `plan.md`, `test-plan.md`) пишутся техническим языком, с глоссарием там, где терминам это нужно. Перевод происходит на стадии design, один раз, а не в каждом разговоре.

## Оси скиллов и базовый набор

Две оси растят набор скиллов вокруг конвейера:

- **Артефактная ось** — новый тип артефакта получает собственный скилл, обучающий агентов, как его производить.
- **Дисциплинарная ось** — многократно нарушаемая дисциплина получает enforcement-скилл; детектор — контур поправок ([Контур обучения](/ru/guide/feedback)).

Базовый набор поставляет 28 скиллов (сверено с `templates/base/skills` в пакете; сам набор описан в [Базовом наборе](/ru/guide/base-set)):

| Скилл                            | Ось             | Назначение                                                                                    |
| -------------------------------- | --------------- | --------------------------------------------------------------------------------------------- |
| `wolf-brainstorm`                | артефактная     | структурированный диалог до творческой работы → requirements.md                               |
| `wolf-design`                    | артефактная     | стадия design с ADR-карточками → design.md                                                    |
| `wolf-plan`                      | артефактная     | zero-context планы, где каждая задача — бриф воркера → plan.md                                |
| `wolf-testplan`                  | артефактная     | тест-план, выведенный из AC требований → test-plan.md                                         |
| `receiving-code-review`          | дисциплинарная  | применять ревью-замечания с технической строгостью, а не слепо                                |
| `writing-skills`                 | дисциплинарная  | создавать, править и проверять скиллы до развёртывания                                        |
| `test-driven-development`        | дисциплинарная  | красный-зелёный-рефактор до кода реализации                                                   |
| `verification-before-completion` | дисциплинарная  | прогнать проверки до любого заявления «готово»                                                |
| `using-git-worktrees`            | дисциплинарная  | изолированные worktree для фичевой работы                                                     |
| `finishing-a-development-branch` | дисциплинарная  | выбрать интеграцию: мерж, PR или уборка                                                       |
| `using-skills`                   | рабочий процесс | загрузка процессной методики до ответа и действий                                             |
| `wolf-work-strategy`             | workflow        | выбор пути, раннего вопроса и достаточности работы                                            |
| `wolf-git`                       | workflow        | этапы Git и поставляемый регламент                                                            |
| `requesting-code-review`         | рабочий процесс | проверка работы на соответствие требованиям перед мержем                                      |
| `wolf-debug`                     | рабочий процесс | root-cause до фиксов                                                                          |
| `wolf-execute`                   | рабочий процесс | плоский линейный fallback исполнения                                                          |
| `wolf-explain`                   | дисциплинарная  | понятное объяснение результатов и ограничений пользователю                                    |
| `wolf-user-report`               | artifact        | отчёт человеку: содержание, HTML/CSS и шаблоны проекта                                        |
| `wolf-handoff`                   | рабочий процесс | продолжить в свежей сессии без потери прогресса                                               |
| `wolf-review`                    | рабочий процесс | мульти-линзовое ревью документов                                                              |
| `wolf-sdd`                       | рабочий процесс | subagent-driven development                                                                   |
| `wolf-release-docs`              | рабочий процесс | релизный проход документации: карта покрытия, EN/RU, generated                                |
| `wolf-skill-intake`              | рабочий процесс | подключение внешних скиллов через intake-цикл с воротами владельца                            |
| `wolf-software-design`           | рабочий процесс | инженерная методика внутри wolf-design: границы, контракты, зависимости и владение состоянием |
| `wolf-code-craft`                | дисциплинарная  | полная реализация назначенного поведения понятными средствами без ненужной сложности          |
| `wolf-code-simplify`             | дисциплинарная  | адресное упрощение названной сложности с сохранением контракта — по отдельному назначению     |
| `wolf-feedback`                  | рабочий процесс | адресный вопрос, трение, жалоба и ограниченная диагностика сессии                             |
| `wolf-visual-dialogue`           | рабочий процесс | наглядное обсуждение, обратная связь и согласованный документ                                 |

Инженерный маршрут едет по существующей ленте: `wolf-software-design` появляется внутри стадии design, `wolf-code-craft` — в задаче исполнителя, `wolf-code-simplify` — только как отдельно назначенное упрощение. Ни один из них не добавляет артефакт в конвейер и не добавляет стадию; упрощение — не автоматический дополнительный круг после каждой правки, лишнюю сложность исполнитель устраняет в текущем мандате. Документы и операции без программной реализации инженерный набор не получают.

Две вещи осознанно не входят в базовый набор. Security — опциональная линза, включается пофичево. Скиллы способностей из внешнего мира — внешние знания и инструменты — приезжают через [skill intake (подключение скиллов)](/ru/guide/skill-intake), никогда не предустановлены.
