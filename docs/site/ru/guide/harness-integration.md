# Интеграция харнессов

Страница предназначена авторам подключения агентной среды к Wolf. Интеграция должна сохранять состояние проекта и доставлять нужный контекст, сохраняя простоту работы пользователя. Доступ к памяти через MCP отличается от полной организации ролей и доставки плейбуков.

## Выберите глубину интеграции

| Интеграция               | Ответственность                                                                                                                                |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Память через CLI или MCP | Чтение и обновление памяти поддержанными операциями                                                                                            |
| Доставка контекста       | Передача актуального состояния проекта и методики в сессию                                                                                     |
| Агентная организация     | Двухуровневая организация: ведущий нанимает конечных исполнителей wolf-\* напрямую; конечные брифы, контракты результата и независимая приёмка |
| Совершенствование        | Приём разрешённой обратной связи (Стюард в 3.0.0 временно отключён) и доставка новых версий лиц                                                |

Основная эксплуатационная интеграция — OpenCode. Подключение MCP на другой платформе само по себе не воспроизводит каждый плагин или механизм делегирования OpenCode. См. [MCP](/ru/guide/mcp), [Базовый набор](/ru/guide/base-set) и [Доставку и доверие](/ru/guide/delivery).

## Идентичность сессии

CLI сохраняет явно заданный `WOLF_SESSION`; иначе процесс получает сгенерированный ключ `cli-<uuid>`. Плагины OpenCode передают ключи `opc-<uuid>` дочерним CLI-процессам. Не используйте один глобальный ключ для всех несвязанных задач и не объявляйте model/variant подтверждёнными, если харнес не предоставляет эти сведения.

Долгоживущий MCP-сервер пишет события с `session_id: null`, а не выдаёт все обращения за одну пользовательскую сессию. Актуальная семантика ключей и каналов: [Телеметрия](/ru/guide/telemetry).

`WOLF_ACTOR` определяет автора поддерживающих его операций; явный параметр автора команды может иметь приоритет. Проверяйте help конкретной команды вместо предположения об одинаковых флагах во всех каналах.

## Usage и доставка — разные события

Команды памяти автоматически записывают стадии получения и доставки. Объект в выдаче поиска найден; доставленный объект попал в контекст. Это ещё не подтверждает следование содержимому или применение.

Ручные команды `memory-stage` и `coord` удалены. Аналитика продолжает читать существующие события стадий и координации, но наличие событий не означает существование текущего ручного writer или полного покрытия trace.

Для usage завершённых ходов помощника используйте поддержанный локальный импорт OpenCode:

```bash
wolf usage import --dry-run
```

Перед настоящим импортом проверьте выбранную БД и временное окно. Команда читает локальную БД и добавляет сигналы usage; задачи она не перезапускает. Поддержка источника, дедупликация, отсутствие variant и другие границы описаны в [Телеметрии](/ru/guide/telemetry).

## Фиксируйте реальную приёмку

Для действительно оценённой задачи `wolf task-eval` записывает вердикт и необязательные идентификаторы задачи, сессии и кампании. Scorer должен обозначать фактического оценщика артефакта. Основания проверки остаются с задачей: запись телеметрии — наблюдение, а не сама проверка.

Для необязательных сравнений используйте разные сессии при разных условиях кампании. Атрибуция связывает записи по session identity; неизвестные идентификаторы и неполное покрытие источника должны оставаться видимыми. См. [Аналитику](/ru/guide/analytics).

## Контракты событий для авторов интеграций

При интеграции кодом используйте штатный writer сигналов и актуальную схему. Источник — [`session-metrics-log.ts`](https://github.com/chekh/mister-wolf/blob/main/src/adapters/fs/session-metrics-log.ts). События содержат время, вид, идентичность сессии, сведения о модели/агенте и автора оркестрации; поля идентичности schema-v2 поддерживают дедупликацию и привязку задач.

Неизвестные поля отбрасываются при чтении. Совместимость схемы не разрешает сохранять секреты или полные промпты. Сбой телеметрии не должен ломать основную задачу; не создавайте конкурирующий журнал состояния проекта. Поля событий и приватность — в [Телеметрии](/ru/guide/telemetry); точные параметры CLI — в [справочнике команд](/ru/guide/cli/command-reference).

## Сохраняйте границы восстановления

Контрольная точка должна содержать цель, принятые решения, завершённое, оставшиеся вопросы и расположение артефактов. Свежий воркер получает конечный контекст поручения; продолжение — состояние ещё не принятого результата. Общий корень памяти worktree не изолирует все чтения; соблюдайте [Изоляцию чтения](/ru/guide/read-isolation).

Сохранённая контрольная точка поддерживает смысловое восстановление. Она не доказывает остановку прежнего писателя, не передаёт автоматически владение исполнением и не предоставляет crash recovery процессов. Эти обязанности явно обеспечивает харнес и протокол задачи.
