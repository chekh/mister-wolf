# Платформа и обслуживание

## `wolf init`

Инициализировать память Mr. Wolf для проекта (интерактивно в TTY; неинтерактивный запуск работает без флагов). С 2.16 по умолчанию — минимальный набор файлов и никакого пиннинга модели.

| Опция              | Описание                                                                                                    |
| ------------------ | ----------------------------------------------------------------------------------------------------------- |
| `--platform <ids>` | Явный список платформ через запятую (opencode,claude); заменяет текущий набор                               |
| `--model <id>`     | Модель для Mr. Wolf и его агентов (`<providerID>/<modelID>`); opt-in — по умолчанию model-строки не пишутся |
| `--full`           | Отрисовать полный базовый набор (agents/skills/commands/plugins) вместо минимального (по умолчанию: false)  |
| `--yes`            | Re-init: применить план без интерактивного подтверждения (по умолчанию: false)                              |
| `--recreate`       | Забэкапить битый .wolf/config.yaml и пересоздать из дефолтов                                                |

В терминале `wolf init` задаст один вопрос интервью (назначение проекта, стек, конвенции — Enter, чтобы пропустить; ответ засеется в стартовую память). Неинтерактивный запуск (скрипты, CI) флагов не требует — ничего не пиннится. Повторный init на живом проекте печатает план и требует подтверждения; `--yes` применяет его без вопросов.

```bash
wolf init --platform opencode,claude
```

## `wolf bootstrap`

Сканировать проект и создать черновую стартовую память: proposed-правила, document-ref'ы, work-thread. Опции: `--created-by <actor>`.

```bash
wolf bootstrap
```

## `wolf mcp`

Запустить MCP-сервер (stdio).

```bash
wolf mcp
```

## `wolf scaffold`

Создать рамку платформы opencode (agent|skill|command) + playbook в памяти Wolf.

```bash
wolf scaffold <kind> <name> [options]
```

| Аргумент/опция         | Описание                                       |
| ---------------------- | ---------------------------------------------- |
| `<kind>`               | Тип рамки: agent, skill, command               |
| `<name>`               | Имя рамки                                      |
| `--persona <text>`     | Текст тела agent-рамки (только agent)          |
| `--model <model>`      | model во frontmatter агента (только agent)     |
| `--from-playbook <id>` | Переиспользовать существующий playbook id      |
| `--created-by <actor>` | Автор (дефолт: env WOLF_ACTOR, иначе user:cli) |

```bash
wolf scaffold agent apprentice --persona "Ты ученик" --model "your-model-id"
```

## `wolf tool`

Библиотекарь инструментов.

### `wolf tool register`

Зарегистрировать скрипт как tool-объект (копирует в `.wolf/tools/`). Опции: `--name <name>` (уникальное), `--language <language>` (typescript, python, bash, ...), `--contract-in <text>`, `--contract-out <text>`, `--contract-env <text>`, `--notes <text>` (тело объекта), `--force` (пропустить проверку похожих тулов), `--created-by <actor>`.

```bash
wolf tool register <script-path> --name check --contract-in "нет" --contract-out "exit 0/1"
```

### `wolf tool list`

Список; `--status <status>` (active, candidate, deprecated, archived).

### `wolf tool use`

Отметить использование (+1 к usage_count, напомнит контракт).

```bash
wolf tool use <name-or-id>
```

### `wolf tool expose`

(Пере)сгенерировать `.opencode/skills/<name>/SKILL.md` (идемпотентно). Файл начинается с YAML-frontmatter, а маркер `<!-- generated from tool:… -->` идёт сразу после него.

### `wolf tool deprecate`

Вывести тул в deprecated (требуется причина): `--reason <text>`.

```bash
wolf tool deprecate <name-or-id> --reason "заменён линтером"
```

### `wolf tool revive`

Оживить deprecated-тул (deprecated → active).

### `wolf tool stats`

Счётчики использования + экономика переиспользования (сигнальный лог + legacy run-log). Канонический источник — сигнальный лог; исторический `.wolf/run-log.jsonl` ещё подмешивается в переходном окне — запусти `wolf migrate run-log`, чтобы архивировать его и убрать двойной счёт.

```bash
wolf tool list --status active
wolf tool use check
```

## `wolf taxonomy`

Таксономия памяти.

### `wolf taxonomy sync`

Перезаписывает `.wolf/config.yaml`, сохраняя проектные типы и настройки, и ставит штамп `wolf_version`, которому принадлежит канон таксономии. Дамп `memory_types.core` больше не пишется.

### `wolf taxonomy show`

Напечатать эффективную таксономию (код-канон + проектные типы).

## `wolf migrate`

Разовая миграция layout: `objects/<type>/` → `threads/<tid>/<subdir>/` + `shared/`. По умолчанию dry-run; `--apply` — выполнить.

```bash
wolf migrate --apply
```

### `wolf migrate run-log`

Архивирует устаревший `.wolf/run-log.jsonl` в `.wolf/metrics/archive/run-log-<дата>-legacy.jsonl` (локальная дата; при коллизии имени — следующий свободный суффикс `-2`, `-3`). Запусти после обновления, если удалённая в 2.13 run-обёртка раньше писала run-лог: пока legacy-файл на месте, analytics считает старые прогоны дважды — канонический источник теперь сигнальный лог. Перенос — rename (содержимое не переписывается); команда печатает счётчик строк. Идемпотентно: файла нет → `nothing to migrate`, exit 0.

```bash
wolf migrate run-log
```

### `wolf migrate doc-ids`

Разовая миграция id `document-ref` на канонический формат: объекты с id вне канона получают id, вычисленный из `source.path` + `created_at`; коллизия с id любого объекта памяти даёт следующий свободный суффикс `-2`, `-3`. Фаза `--apply` переименовывает файлы, заменяет id в frontmatter, переписывает все ссылки на старый id по `.md` памяти и `relations.jsonl` — по границе id, чтобы существующий `doc_X2` не рвался при замене `doc_X` — и перестраивает поисковый индекс. Служебные зоны не трогаются: `briefs/`, `quarantine/`, `events.jsonl`.

По умолчанию dry-run; `--apply` применяет (флаг срабатывает и на родителе: `wolf migrate --apply doc-ids`). Отчёт — таблица `id → new id` и итоги `renamed / refs rewritten / conflicts / problems`; `document-ref` без `source.path` попадает в problems (миграция невозможна), занятый целевой путь — конфликт (объект не трогается). Конфликты дают exit 2.

```bash
wolf migrate doc-ids --apply
```

## `wolf validate`

Проверить целостность хранилища; `--fix` — карантин битых объектов.

```bash
wolf validate --fix
```

## `wolf doctor`

Проверить все зарегистрированные проекты: binary vs schema version, платформенные конфиги, чистка мёртвых записей.

У найденного конфига opencode проверяется и то, что пишет адаптер: `default_agent`, `experimental.subagent_depth` ≥ 2, deprecated верхнеуровневый `subagent_depth` (сообщается как игнорируемый opencode v2), легаси-плоская запись `mcp.wolf` (сообщается как deprecated: наша — «migrate», чужая — не трогается), а также frontmatter managed-агента со смешанными v1/v2-полями. `--repair` канонизирует конфиг — пишет нативную MCP-запись и `experimental.subagent_depth` — помимо ремонта хранилища.

| Опция       | Описание                                                                               |
| ----------- | -------------------------------------------------------------------------------------- |
| `--repair`  | Починить хранилище текущего проекта: пересобрать индекс, добить события `memory.added` |
| `--dry-run` | С `--repair`: напечатать план без записи                                               |

```bash
wolf doctor
```

## `wolf sync`

> **Депрекирован в 2.19.0** — заменён на `wolf upgrade --here`; алиас ещё работает в 2.20.0 (печатает уведомление DEPRECATED и перерендеривает штампованные файлы). Текст уведомления всё ещё говорит `removed in 2.20.0` — устаревшая формулировка, команда жива.

Перерендерить базовый набор Wolf (только штампованные файлы; память не трогается). Состав набора и механика штампов: [Базовый набор](/ru/guide/base-set).

```bash
wolf sync
```

### Локально правленные файлы не перезаписываются

Штампованный файл, правленный локально (контент отличается и от записанного рендера, и от нового), — не перезаписывается: sync пишет `skipped — mutated ...` в отчёт и оставляет решение владельцу. Вернуть канонический рендер — удалить файл или снять правку: следующий sync пересоздаст (или обновит) его.

Свидетель хэшей последнего рендера — `.opencode/wolf-sync-state.json`. Первый sync после апгрейда с ≤ 2.10.0 свидетеля не находит, поэтому файлы обновляются по-старому (однократный bootstrap); со второго прогона защита активна. Удалите файл-свидетель, чтобы принудительно перерендерить всё.

## Сессии и окружение

`WOLF_SESSION` — env-переменная, привязывающая телеметрию к сессии, — теперь продюцируется самим CLI: каждый вызов без явного `WOLF_SESSION` получает свежий `cli-<uuid>`, стабильный в рамках всего процесса (общий для всех писателей телеметрии команды). Явно выставленный `WOLF_SESSION` не перезаписывается. Штампованные плагины opencode (`wolf-router`, `wolf-session-start`) передают свежий `opc-<uuid>` при каждом spawn CLI — иначе унаследованный env long-lived процесса opencode свалил бы все доставки в одну фальшивую сессию. Обновления шаблонов плагинов приезжают проектным проходом `wolf upgrade` (`--here` — один проект).

`wolf mcp` сознательно не сессионируется: MCP-сервер — long-lived процесс с одним окружением, один session id на все запроси был бы фальшивой атрибуцией — телеметрия MCP-канала пишется с `session_id: null` (см. [Телеметрия](/ru/guide/telemetry)).

## `wolf upgrade`

**Unified update (2.19.0): одна команда обновляет всё.** npm-фаза
(`npm install -g mister-wolf@latest`) завершается проходом по всем проектам,
зарегистрированным в реестре wolf: штампованные файлы базового сета
перерендериваются, посеянные лица обновляются, карта обновления строго
сверяется (см. [Базовый набор](/ru/guide/base-set)). Между фазами CLI
ре-исполняет себя, поэтому проектный проход всегда идёт свежеустановленным
бинарником; вывод обеих фаз — в один терминал.

**Намерения владельца (2.20.0)** добавляют недостающую половину: именованные
решения, четыре глагола разрешения, in-file защиту (`protect`) и машинный
канал. Полный сценарий с фактическим выводом и всеми ограничениями —
на странице [Обновление проекта и парка](/ru/guide/upgrade); здесь —
справочник флагов.

| Опция                     | Описание                                                                                                                              |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `--check`                 | Read-only сводка свежести CLI и всего парка: без установки, без записи, exit всегда `0`; печатает и секцию `Protections`              |
| `--here`                  | Обновить только текущий проект: полный шаг в cwd, без npm-самообновления и реестра                                                    |
| `--yes`                   | Применить план без интерактивного подтверждения: `mutated` копируется в бэкап и берётся эталон, `conflict`/`diverged` держат exit `2` |
| `--resolve <цель=глагол>` | Разрешить решение: `<файл\|N>=take\|keep\|protect\|pin`, флаг повторяемый, списки через запятую                                       |
| `--show <файл\|N>`        | Показать одну цель с диффом `локальный → эталон` (read-only)                                                                          |
| `--review`                | Разобрать решения по одному с диффом (TTY); без TTY печатает рецепт и ничего не пишет                                                 |
| `--json`                  | Печатать ровно один машинный документ в stdout (`wolf.upgrade/1`, либо `wolf.upgrade.check/1` с `--check`)                            |

```bash
wolf upgrade                              # npm-фаза + проектный проход (план, потом подтверждение)
wolf upgrade --check                      # read-only: свежесть CLI и парка + protections
wolf upgrade --here                       # обновить только этот проект, вне реестра
wolf upgrade --review                     # решения по файлам, с диффом
wolf upgrade --resolve 2=take --resolve .opencode/agents/foo.md=protect
wolf upgrade --show 2                     # что сделает `take` с этим файлом?
wolf upgrade --yes --json > run.json      # тихий проход, машинный канал
```

Диспетчеризация флагов выполняется один раз — в action команды — и
завершается до npm-фазы и re-exec: `--check` (сильнее `--here`), затем
`--show`, `--review`, `--resolve`, потом `--here`, и только bare
`wolf upgrade` / `--yes` доходит до npm-фазы. Несовместимые пары — ошибка
аргументов (exit `1`, без записи): `--review` с `--json`/`--resolve`/`--yes`/`--show`/`--check`,
`--show` с `--resolve`/`--yes`/`--check`, `--resolve` с `--yes`/`--check`.

Фактический вывод `--check` (2.20.0, фикстурный парк из двух проектов, по
одному защищённому файлу; абсолютные пути сокращены):

```text
wolf upgrade — check
- cli: installed 2.20.0 · available 2.19.0
ok: proj · /Users/…/proj — current
- stamps 2.20.0 · map 2.20.0
- 1 protected (intentional)
warn: proj2 · /Users/…/proj2 — needs decision
- stamps 2.20.0 · map 2.20.0
- mutated: .opencode/skills/wolf-review/SKILL.md · 1 protected (intentional)
Protections
- proj · .opencode/command/complain.md · protect: 2.20.0 · behind (base 2.20.0)
- proj2 · .opencode/skills/wolf-explain/SKILL.md · protect: 2.19.0 · behind (base 2.20.0)
- 2 protected files · release: wolf upgrade --resolve <file>=take
ok: Done (read-only)
```

Классификация парка по проектам: `current` (делать нечего — сюда же входят
защищённые и `kept`-файлы), `behind` (штампованные файлы отличаются от карты
доступного релиза), `needs decision` (штампованный файл правился локально —
mutated-файлы никогда не перезаписываются — либо на месте цели волфа лежит
файл без штампа), `unknown` (проект не покрыт картой обновления релиза —
«вне покрытия» **не** значит «актуален»). Каждая строка называет файлы, а не
только считает их. Отсутствующая карта деградирует сводку до штампов
(помечается ненадёжной).

Ожидаемый комбинированный прогон (интерактивное подтверждение сначала
печатает по-проектный план):

```text
wolf upgrade — projects       # фаза 2 (re-exec): проход по реестру
- adminvps — updated
- verify: 31/31 ok
- mister-wolf — needs decision
- verify: 29/30 ok · 1 needs decision
updated 1 · up-to-date 0 · worktree 0 · pinned 0 · missing 0 · needs decision 1 · errors 0 · new 0 · changed 31 · deprecated 0 · removed 0 · faces seeded 0
warn: Done with attention
```

Exit-коды: `0` — готово (или делать нечего), `1` — сбой (ошибка npm, ошибка
шага проекта, ошибка аргументов), `2` — готово с вниманием: хотя бы один
проект требует решения (mutated/conflict — mutated-файлы не перезаписываются,
решение остаётся за владельцем — либо `diverged`-лицо памяти: это зона
Стюарда, глаголом `--resolve` не адресуется). Не-TTY запуск без `--yes`
печатает план и останавливается с `Cancelled: --yes is required` — exit `0`,
без изменений. Если spawn ре-исполняемого бинарника упал после успешной
npm-фазы, wolf печатает `CLI updated; projects not touched — run wolf upgrade
again for the project pass` и выходит с `1`: npm-фаза идемпотентна — просто
повторите `wolf upgrade`, продолжение начнётся с проектного прохода.

Чего команда **не** гарантирует: карта обновления покрывает только файлы,
перечисленные в релизе, — файлы вне её не сверяются; `unknown`-проекты
никаких обещаний не получают; удаления — только по явному подтверждению;
незарегистрированные проекты упоминаются лишь подсказкой скана (топ-5 по
давности), без записи. Память (`.wolf/`) не трогается ни одним проходом —
мутации лиц идут через контур жалоб и Стюарда. Dev/linked-установке CLI
откажет честно (самообновление сломало бы ссылку). Авто-merge контента нет:
решение — это целиком `take` или `keep`.
