# Обновление проекта и парка

Wolf управляет файлами в проектах: агенты, скиллы, команды, плагины, онбординг-блок `AGENTS.md`. Новый релиз приносит новые версии этих файлов, а вы часть из них со временем правите по своим причинам. Эта страница — про шов между двумя сторонами: как обновление показывает, что хочет изменить, как сказать «бери» или «это моё», и как тихий прогон остаётся обратимым.

Модель — три слоя, от разового к постоянному:

| Слой               | Чем выражается                                        | Что делает обновление                               | Срок жизни                    |
| ------------------ | ----------------------------------------------------- | --------------------------------------------------- | ----------------------------- |
| Решение, разово    | `--review`, `--resolve 3=take\|keep\|protect\|pin`    | применяет глагол к этому файлу                      | пока файл снова не разойдётся |
| Намерение, в файле | `protect: true` / `protect: X.Y.Z` в YAML-frontmatter | больше не трогает файл (ни перезаписи, ни удаления) | навсегда, пока ключ не снят   |
| Тишина, машинно    | `--yes` + `--json`                                    | применяет план, копируя то, что перезаписывает      | один прогон                   |

Ничего из этого не меняет отношения прохода к **памяти** (`.wolf/`): лица — память, проход их не переписывает (см. [Модель памяти](/ru/guide/memory)).

## Прочитать план до записи

`wolf upgrade --check` только читает — по парку целиком и с `--here` для одного проекта. Exit всегда `0`: это отчёт, а не гейт.

```bash
wolf upgrade --check          # весь реестр
wolf upgrade --here --check   # только текущий каталог
```

Фактический вывод (2.20.0, парк из двух проектов, по одному защищённому файлу):

```text
wolf upgrade — check
- cli: installed 2.20.0 · available 2.19.0
ok: proj · /Users/…/proj — current
- stamps 2.20.0 · map 2.20.0
- 1 protected (intentional)
warn: proj2 · /Users/…/proj2 — needs decision
- stamps 2.20.0 · map 2.20.0
- mutated: .opencode/skills/wolf-review/SKILL.md · 1 protected (intentional)
Protections
- proj · .opencode/command/complain.md · protect: 2.20.0 · behind (base 2.20.0)
- proj2 · .opencode/skills/wolf-explain/SKILL.md · protect: 2.19.0 · behind (base 2.20.0)
- 2 protected files · release: wolf upgrade --resolve <file>=take
ok: Done (read-only)
```

Проект получает один класс:

- `current` — делать нечего: файлы равны эталону, защищённые и принятые локальные (`kept`) держатся;
- `behind` — штампованные файлы отличаются от карты обновления доступного релиза; проход просто обновит их;
- `needs decision` — штампованный файл правили локально (`mutated`) либо на месте цели волфа лежит файл без штампа (`conflict`). Сам проход такие не решает;
- `unknown` — проект не покрыт картой обновления этого релиза (`foreign`-файлы, нечитаемые проекты, сломанные онбординг-маркеры). Вне покрытия **не** значит «актуален».

Каждая строка называет файлы: `mutated:`, `differ:` (все пути, а не счётчик), `foreign:`, `missing:`. Секция `Protections` печатается всегда — `Protections: none`, если держать нечего — и это и есть аудит второго слоя из таблицы выше.

Файл со штампом, отличающийся от эталона **только** строкой `wolf:rendered …`, решения не требует: проход молча перерендерит его и обновит штамп. В `--check` он показан как `current` — `identical` здесь значит «решать нечего», а не «байт-равенство».

Номер карты (`map 2.20.0`) — релиз, чья карта обновления используется. Карта генерируется из фактического диффа шаблонов этого релиза, поэтому `map: 0 new · 0 changed …` для релиза, который тронул только блок `AGENTS.md`, — честный результат, а не дефект.

## Разбор решений по одному

```bash
wolf upgrade --review            # парк, интерактивно
wolf upgrade --here --review     # один проект
```

В TTY команда идёт по решениям по порядку, показывает дифф `локальный → эталон` и выбор:

```text
[3/7] .opencode/agents/foo.md — mutated · base 2.20.0
  локальный: 42 строки · эталон: 38 строк · −12 +8
  --- a/эталон 2.20.0
  +++ b/локальный
  @@ …  (не более 40 строк diff; «… ещё N строк»)
  выбор: [t]ake [k]eep [p]rotect [v]pin [s]kip  (a — применить ко всем похожим, q — выйти)
```

- `t` **take** — файл становится эталоном; локальный контент сначала уходит в бэкап.
- `k` **keep** — локальный контент принимается как текущее состояние: свидетель пишет его с `origin: keep`, и следующий проход его не откатит.
- `p` **protect** — `keep` плюс `protect: true` во frontmatter: файл держится навсегда.
- `v` **pin** — `keep` плюс `protect: <base>`: держится, версия базы фиксируется в файле.
- `s` **skip** — оставить решение на потом.
- `a` — применить выбранный глагол ко всем оставшимся целям того же вида и кода (например все `agent`/`mutated`); список затронутых файлов печатается до применения. `q` завершает цикл; уже принятые решения остаются применёнными (каждое атомарно).

Без TTY команда ничего не пишет — печатает нумерованный список и точные команды:

```text
wolf upgrade — review
warn: review (non-interactive): 1 file needs a decision
-   1  proj2  .opencode/skills/wolf-review/SKILL.md  mutated  base 2.20.0
- review interactively: wolf upgrade --review  (in a TTY)
- apply a decision:    wolf upgrade --resolve 1=take  (or keep|protect|pin)
- inspect a file:      wolf upgrade --show 1
```

Коды выхода: `0` решений не осталось, `2` решения (или `diverged`-лица) остались, `1` сбой записи.

## Посмотреть один файл: `--show`

```bash
wolf upgrade --here --show 1
wolf upgrade --show .opencode/agents/foo.md
```

Только чтение. Печатает состояние цели и дифф, который применил бы `take`:

```text
wolf upgrade — show
- file:      .opencode/agents/worker-reviewer.md   (project: proj /Users/…/proj)
- protect:   none
- base:      2.20.0   file stamp: 2.20.0   witness: render @ 2.20.0 (75516f576854…)   drift: local ≠ base
- --- a/local (as is)   +++ b/base 2.20.0   (what --resolve …=take gives you)
-   @@ -63,6 +63,2 @@
-    - Никогда: `rm -rf` вне системного tmp, `sudo`, …
warn:   -## Local addition
warn:   -
warn:   -Keep the review verdict in one line.
- release:   wolf upgrade --resolve .opencode/agents/worker-reviewer.md=take
```

У защищённого файла `protect:` показывает значение (`2.19.0 (pinned; recognized)`); у файла вне карты обновления — `base: n/a (file outside the update map)` с пояснением и без подсказки `take`: брать нечего. `--show` принимает и цель, которая сейчас не является решением (защищённый файл, orphan): у такой цели нет номера, адресуйте путём. Exit `1` — только для неизвестной цели.

## Применить решение: `--resolve`

```bash
wolf upgrade --here --resolve 1=take
wolf upgrade --resolve .opencode/agents/foo.md=keep --resolve 2=protect
wolf upgrade --resolve my-proj/.opencode/agents/foo.md=pin,.opencode/command/baz.md=take
```

- Цели: номер решения `N`, относительный путь (в `--here` от cwd, в парке `<проект>/<путь>` либо `<путь>`, уникальный в парке) или комбинация. Путь, начинающийся с цифры, пишется как `./3=…`.
- Глаголы: `take`, `keep`, `protect`, `pin`.
- Все ошибки разбора и области собираются и печатаются **до** записи; при ошибке не применяется ничего. Дубликат цели в одной команде отвергается (`target listed twice`).
- Порядок применения — порядок реестра, не порядок ввода. Каждое решение атомарно (`бэкап → файл → свидетель`), поэтому сбой на шаге _k_ оставляет 1…_k−1_ применёнными и повторяемыми, печатает `error: <файл> — <причина>` и даёт exit `1`.
- `--resolve` не запускает ни npm-фазу, ни проектный проход; остальные категории (`new`/`changed`/`removed`) применяет следующий обычный `wolf upgrade`. Комбинация `--resolve` с `--yes` — ошибка аргументов: `--yes` описывает проход, а не отдельное решение.

Что глагол делает с файлом и свидетелем:

| Глагол    | Файл                                                   | `protect` | Бэкап                                            |
| --------- | ------------------------------------------------------ | --------- | ------------------------------------------------ |
| `take`    | эталон, атомарно; ключ снимается                       | снят      | да, если локальный контент отличается от эталона |
| `keep`    | не меняется (снимается только строка ключа, если была) | снят      | нет — терять нечего                              |
| `protect` | `protect: true` вставляется во frontmatter             | `true`    | нет                                              |
| `pin`     | `protect: <base>` вставляется во frontmatter           | `X.Y.Z`   | нет                                              |

Какие глаголы осмысленны — зависит от цели:

| Цель                                             | `take`                                              | `keep`                                     | `protect` / `pin`                                     |
| ------------------------------------------------ | --------------------------------------------------- | ------------------------------------------ | ----------------------------------------------------- |
| `mutated` со штампом                             | эталон + бэкап                                      | принять локальный                          | принять + держать                                     |
| `conflict` (файл без штампа на месте цели волфа) | эталон + бэкап (файл становится штампованным)       | отказ: `use protect (hold) or take (base)` | держать как санкционированную вариацию (верный ответ) |
| защищённый файл                                  | снять ключ, взять эталон, локальное → бэкап         | снять ключ, принять локальный              | идемпотентно / обновить зафиксированную версию        |
| orphan (штамп есть, эталона в карте нет)         | отказ: `no base for a file outside the update map`  | отказ                                      | держать                                               |
| `AGENTS.md` (штампованный, whole-file)           | эталон + бэкап                                      | принять локальный                          | отказ: нет YAML-frontmatter                           |
| `AGENTS.md` (блочный, без штампа)                | свежий файл целиком (блочное владение прекращается) | no-op — он и так вне синка                 | отказ: нет frontmatter                                |
| `kept` (принятый локальный контент)              | эталон + бэкап                                      | идемпотентно                               | принять + держать                                     |

Фактический вывод применения:

```text
wolf upgrade — resolve
ok: resolved: 1 (take: 1)
- take proj/.opencode/agents/worker-reviewer.md (local saved: .wolf/backup/upgrade/2026-10-25/.opencode/agents/worker-reviewer.md)
- no decisions — nothing needs a decision
ok: Done
```

И отказ, который держит конфликт честным:

```text
wolf upgrade — resolve
error: cannot keep .opencode/command/complain.md: conflict stays: use protect (hold) or take (base)
warn: 1 file needs a decision
-   1  proj  .opencode/command/complain.md  conflict
error: Failed
```

## Держать файл навсегда: `protect`

`protect` живёт в YAML-frontmatter wolf-управляемого agent/skill/command-файла — в самом файле, а не в центральном списке (решение владельца: намерения живут в файлах, к которым относятся).

```markdown
---
description: 'Worker-reviewer (L2): …'
mode: all
protect: true
---
```

| Значение                | Смысл                                                                        |
| ----------------------- | ---------------------------------------------------------------------------- |
| `true`                  | держать локальный контент навсегда                                           |
| `X.Y.Z` (полная версия) | держать и зафиксировать версию базы                                          |
| `false`                 | не защищён (эквивалент отсутствия ключа)                                     |
| пусто, `~`, `null`      | **держать + warn** (недописанный ключ fail-safe, а не «молча снятая защита») |
| любое иное              | **держать + warn**                                                           |

Считается только frontmatter — строка `protect:` в теле файла защитой не является. Ключ в кавычках (`"protect":`), с отступом или табом — вне грамматики: не защищает и не нормализуется. Если ключ объявлен дважды, побеждает первый, второй попадает в warn (`protect declared twice, first value wins`).

Запись ключа (`protect`, `pin` или вручную) — построчная правка: строка вставляется последней строкой frontmatter-блока, существующие строки `protect:` заменяются, остальное — порядок ключей, комментарии, пробелы, переводы строк — остаётся байт-в-байт. Файл без frontmatter волф защищать отказывается:

```text
cannot protect <path>: no YAML frontmatter — add one or use keep
```

Отказ намеренный: молча изобретённый frontmatter-блок изменил бы форму файла, который создавал не волф.

Сравнение — нормализационное, и именно поэтому ключ дешёвый: контент сравнивается **без всех строк `protect:`** — и с эталоном, и со свидетелем. Поэтому добавление, смена значения и снятие ключа никогда не дают ложный `mutated`, а держимый файл продолжает работать после релиза, изменившего базу — он просто показывается как `behind`, пока его не возьмут или не перепинят.

Защищённый файл не перезаписывает ничто: ни проход, ни `--yes`, ни исцеление штампа. И не удаляет: цель, которую релиз хочет удалить, остаётся на диске с кодом `protected` и подсказкой `wolf upgrade --resolve <путь>=keep` (снятие ключа — после этого следующий проход снова видит удаление). `take` — единственный глагол сильнее `protect`, и он сначала копирует локальный контент в бэкап.

Аудит по всей машине — это `grep`, потому что маркер лежит в файлах:

```bash
grep -rn --include='*.md' '^protect:' ~/dev/*/.opencode/agents ~/dev/*/.opencode/skills ~/dev/*/.opencode/command
```

То же структурно: секция `Protections` в `wolf upgrade --check` или `protections[]` в `wolf upgrade --check --json`.

`AGENTS.md` защитить нельзя: в штатном шаблоне у него нет frontmatter, и ручной frontmatter защищаемым его не делает. Используйте два режима владения — блочный сохраняет ваш текст вне маркеров, штампованный whole-file означает, что файлом владеет волф целиком.

## Тихие прогоны: `--yes` и бэкапы

`--yes` — для скриптов, CI и длинных парков. Он всё равно печатает план, но применяет его без вопроса.

```bash
wolf upgrade --yes                    # парк, без вопросов
wolf upgrade --here --yes             # один проект
wolf upgrade --yes --json > run.json  # машинный канал
```

Что `--yes` решает: `mutated`-файлы — сначала бэкап, потом эталон, потом свидетель. Чего не решает: `conflict` (файл без штампа на месте цели волфа — это ваше решение, `wx`-политика сильнее `--yes`) и `diverged`-лицо (память, зона Стюарда). Они держат exit `2`.

```text
wolf upgrade — here
Plan
- plan: proj · /Users/…/proj
- composition 2.20.0 → 2.20.0
- map: 0 new · 0 changed · 0 deprecated · 0 removed · seed×6
- outside the registry — manual mode
ok: proj — updated
- base-set: 1 updated, 30 identical
- faces: … skipped-live …
- verify: 37/37 ok
- 1 protected (intentional)
- took base for .opencode/skills/wolf-review/SKILL.md (local saved: .wolf/backup/upgrade/2026-10-25/.opencode/skills/wolf-review/SKILL.md)
updated 1 · new 0 · changed 0 · deprecated 0 · removed 0 · faces seeded 0
ok: Done
```

Каждой перезаписи предшествует копия в `.wolf/backup/upgrade/<YYYY-MM-DD>/<путь>` (один каталог на дату прогона). Вторая перезапись того же файла в тот же день становится `base.<ext>`, `base-2.<ext>`, … — существующий бэкап не перезаписывается никогда. Цель `removed` копируется туда же перед удалением.

Восстановление — копирование обратно:

```bash
cp .wolf/backup/upgrade/2026-10-25/.opencode/skills/wolf-review/SKILL.md \
   .opencode/skills/wolf-review/SKILL.md
wolf upgrade --here --resolve .opencode/skills/wolf-review/SKILL.md=protect
```

После копирования файл — обычный `mutated` (контент не равен ни свидетелю, ни эталону); замороженный через `protect`, он перестаёт быть решением. **Сборщика мусора нет**: бэкапы лежат, пока вы их не удалите; права и время не сохраняются (копия контента, а не артефакт ФС).

## Машинный канал: `--json`

`--json` печатает ровно один документ в stdout — без баннера и человеческих строк — и совместим со всеми режимами, кроме `--review`.

```bash
wolf upgrade --check --json | jq '.projects[] | {name, class, mutated}'
wolf upgrade --yes --json | jq -e '.exit == 0' > /dev/null
```

Две схемы:

- `wolf.upgrade/1` — режимы `pass`, `here`, `check`, `resolve`, `show`. Верхний уровень: `schema`, `exit` (совпадает с кодом процесса), `mode`, `cli{installed,available}`, опциональный `error`, `plan`, `projects[]`, `decisions[]`, `diverged[]`, `protections[]`. У проекта: `status` (`updated` / `up-to-date` / `needs-decision` / `error` / `skipped` с `skipReason`), `files[]{path,code,inMap}`, `protected[]{path,value,behind}`, `backups[]{file,backup}`.
- `wolf.upgrade.check/1` — `--check`. `cli`, `projects[]{name,path,class,differ[],missing[],mutated[],foreign[],details[],protected[]}`, `diverged[]`, `protections[]`. `exit` всегда `0`; `class` — `current` / `behind` / `needs-decision` / `unknown`.

`decisions[].n` — та же нумерация, что в текстовом выводе, поэтому потребитель `--json` и человеческий рецепт не расходятся. Контракт стабильности: аддитивные поля допустимы в минорах, переименование или удаление — только в новом мажоре (`/2`).

## `AGENTS.md` и онбординг-блок

Проход и `init` управляют `AGENTS.md` в двух режимах:

- **Блочный (по умолчанию для проекта, инициализированного волфом).** В файле есть `<!-- wolf:onboarding v3 -->` … `<!-- /wolf:onboarding -->`. Волф владеет только строками между маркерами; всё выше и ниже — байт-в-байт ваше (CRLF-файл сохраняет CRLF). Пользовательский текст **внутри** блока не сохраняется — блок зона волфа.
- **Штампованный whole-file.** У `AGENTS.md` есть штамп `wolf:rendered …`: файл принадлежит волфу целиком, локальные правки дают `mutated`, а `take`/`keep` решают его судьбу. `protect` здесь недоступен (нет frontmatter).

Детект блока версионно-агностичен: существующий блок `v2` в проекте на 2.19.0 распознаётся и обновляется на месте до `v3` (в блоке появилась строка про намерения владельца), вместо дописывания второго блока. `init` дополнительно приводит штамп штампованного файла к текущей базе; `upgrade` не дописывает блок в `AGENTS.md` без штампа и без маркеров — файл, который создавал не волф, остаётся чужим (`wx`-политика).

Сломанные маркеры (открывающий без закрывающего) делают файл чужим: он пропускается, в деталях шага и в `--check` печатается `onboarding markers broken`, и решением он не становится. Почините маркеры руками (допишите закрывающую строку) — следующий прогон снова им управляет.

## `init` и пропавший `mcp.wolf`

`wolf doctor` раньше советовал `wolf init` при отсутствующей записи `mcp.wolf`, а минимальный `init` платформенных конфигов не писал. Теперь минимальный `init` на проекте, где конфиг платформы уже существует, чинит запись (и `default_agent` / `subagent_depth`), сохраняя остальной JSON. Файл конфига, которого не было, он по-прежнему **не создаёт** — минимальный init остаётся минимальным, а `--platform opencode` остаётся явным способом записать конфиг платформы. Битый JSONC не трогается: `init` сообщает `skipped` с причиной и завершается с exit `0`. Второй `init` сообщает `unchanged`.

## Ограничения, названные прямо

- **Авто-merge контента нет.** Только целиком `take`/`keep`. Нужен слитый файл — возьмите эталон и заново примените правку либо защитите файл и поддерживайте его сами.
- **`diverged`-лица не адресуемы.** Они печатаются отдельной секцией (`faces (steward zone): … diverged (vX.Y.Z)`) и держат exit `2`, но глагола `--resolve` для них нет: лицо — память, а память мутируется через жалобный контур и Стюарда.
- **У `orphan` нет эталона.** Штампованный файл, чья цель исчезла из пакета, можно только держать (`=protect`) или удалить вручную; `take` отвергается.
- **Бэкапы не собираются сборщиком мусора** (см. выше) и не сохраняют метаданные файла.
- **Exit-модель не изменилась** с 2.19.0: `0` готово, `1` сбой, `2` готово с вниманием (включая `diverged`).
- **Старые версии волфа не знают `protect`**: ключ для них — локальная правка (`mutated`, никогда не перезаписывается), а новые записи свидетеля они читают как `mutated` по всем файлам свидетеля. Контент не теряется; лечится апгрейдом парка, а не борьбой с ним, а откат к 2.19.0 чинится повторным апгрейдом или восстановлением `.opencode/wolf-sync-state.json`.
- **Карта покрывает только файлы, объявленные для релиза.** Вне карты ничего не сверяется; `unknown`-проекты утверждений не получают; незарегистрированные проекты только упоминаются подсказкой, но никогда не пишутся.
- **Regression guard — это живой прогон, а не гарантия.** То, что ключ `protect` не попадает в model-запрос, доказано на opencode v2.1.4; будущий opencode, начавший пробрасывать неизвестные ключи агента, ловится этим guard'ом, а лекарство — `--resolve <файл>=keep`.

## Полный круг, от начала до конца

```bash
npm i -g mister-wolf@2.20.0
wolf upgrade --check                       # только чтение: что изменилось, по проектам и файлам
wolf upgrade --review                      # пройти решения с диффом
wolf upgrade --resolve .opencode/agents/foo.md=protect   # это моё, навсегда
wolf upgrade --resolve 2=take --resolve 3=keep           # эти два: эталон / локальный
wolf upgrade --here --check                # подтверждение: current, решений нет
```

Если это скрипт:

```bash
wolf upgrade --check --json | jq -r '.projects[] | select(.class=="needs-decision") | .path'
wolf upgrade --yes --json > upgrade-run.json || echo "attention: exit $?"
grep -c 'local saved:' upgrade-run.json   # каждая перезапись обратима
```
