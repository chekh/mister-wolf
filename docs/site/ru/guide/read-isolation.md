# Изоляция чтения

Где память с worktree-scope фильтруется, а где — нет. Эта страница — замороженный
контракт (NFR-03, дизайн 2.17.1 §6): состав ниже меняется только изменением
требований, никогда — тихой правкой в коде.

Worktree-scope существует, чтобы память, записанная в linked-worktree-копии
(`worktree:<id>`), оставалась в ней: инъекции не утекают в другие копии и в
main-чекоут. Перевод записи в общую память — явная команда `wolf promote`.

## Изолировано: только `wolf call`

Путь доставки применяет scope-фильтр во всех ветвях отбора:

- `wolf call` — все режимы: обычный, `--for <тема>`, `--thread <id>`;
- MCP-канал зеркалит список CLI-команд: тул `call` в каталоге MCP наследует ту же
  изоляцию. Сегодняшний каталог MCP (`search`, `get`, `list`, `add`, `transition`,
  `brief`, `recap` + `ping`) не содержит тула `call`.

## Не изолировано: вся память проекта

Всё остальное читает всю память проекта:

- `wolf search` / `get` / `list` / `show`;
- `wolf brief`, `wolf recap`;
- `wolf think` / `solve`;
- `wolf doctor`;
- relation- и analytics-пути (`wolf relation`, `wolf analytics`);
- команды лиц (`wolf face list/history/show`) — лица фильтруются по `owner_skill`,
  а не по scope.

MCP read-инструменты (`mr-wolf_search`, `mr-wolf_get`, `mr-wolf_list`, `mr-wolf_brief`,
`mr-wolf_recap`) зеркалят эти CLI-команды и тоже не изолированы: MCP-поверхность —
зеркало CLI-списка, отдельного поведения изоляции нет.

## Расширение списка

Добавление нового изолированного read-пути — изменение требований, а не решение на
уровне кода. Состав выше охраняет doc-тест (`tests/unit/read-isolation-doc.test.ts`):
он падает, если предикат видимости появился вне пути доставки `call` или если
документы разошлись с замороженным списком.
