# Архитектура

Wolf связывает агентов, скиллы, инструменты, правила и память проекта единым процессом работы. Двухуровневая организация удерживает исходную цель при смене сессий и исполнителей. Отдельный контур совершенствования позволяет опыту изменять методики, доставляемые в последующие сессии, — Стюард за ним временно отключён в 3.0.0.

Эта страница предназначена разработчикам и авторам интеграций. Роли описаны в [Организации](/ru/guide/organization), версии лиц и доставка — в [Доставке и доверии](/ru/guide/delivery).

## Два связанных контура

| Контур            | Ответственность                                                                                  | Что сохраняется                                       |
| ----------------- | ------------------------------------------------------------------------------------------------ | ----------------------------------------------------- |
| Выполнение        | Волф отвечает за намерение и приёмку и часть работы выполняет сам; исполнители wolf-* выполняют конечные задачи | Состояние работы, решения, отчёты и контрольные точки |
| Совершенствование | Разрешённая обратная связь обрабатывается и лица версионируются через управляемый контур (Стюард временно отключён в 3.0.0) | Новая методика, причины изменений и история версий    |

Организация — рабочий протокол, поддержанный рамками агентов и разрешениями платформы. Запись инструкции не доказывает, что каждая граница обеспечена кодом. Из архитектурного описания нельзя выводить наличие работающего runtime консилиума или автоматического планировщика политик.

## Источники истины

Документы проекта входят в его память: требования, дизайн, планы и отчёты сохраняют канонические файлы. Wolf регистрирует ссылки и связывает документы с работой; это не означает автоматическое копирование каждого документа в каждый промпт.

Собственные объекты Wolf хранятся в `.wolf/memory/` как Markdown с YAML frontmatter. Таксономия содержит 8 core-типов: `rule`, `lesson`, `decision`, `thread`, `complaint`, `tool`, `face`, `note`. Области и жизненный цикл — в [Модели памяти](/ru/guide/memory).

Каталог `templates/` пакета — источник штампованных рамок, скиллов, команд и плагинов. Лица — версионируемые объекты памяти; обновление пакета не заменяет молча действующие методики проекта. Карточка инструмента ссылается на канонические исходные файлы проекта. SQLite-индексы и генерируемые платформенные файлы производны; порядок их обновления отличается от порядка изменения описываемых источников.

## Границы кода

| Каталог                | Ответственность                                                                |
| ---------------------- | ------------------------------------------------------------------------------ |
| `src/domain/`          | Схемы памяти, таксономия, жизненные циклы, политики и чистые вычисления        |
| `src/app/use-cases/`   | Операции приложения: bootstrap, поиск, агрегация, версии лиц                   |
| `src/ports/`           | Интерфейсы хранилищ, индексов, файлов, блокировок, часов и других зависимостей |
| `src/adapters/fs/`     | Markdown-хранилище и JSONL-логи событий и сигналов                             |
| `src/adapters/sqlite/` | Восстанавливаемый полнотекстовый индекс                                        |
| `src/adapters/cli/`    | Разбор команд и пользовательский вывод                                         |
| `src/adapters/mcp/`    | Доступ к операциям приложения через MCP                                        |
| `src/bootstrap/`       | Сборка зависимостей и входные точки CLI/MCP                                    |
| `templates/base/`      | Общие рамки, скиллы, команды и стартовые плейбуки                              |
| `templates/opencode/`  | Плагины доставки для OpenCode                                                  |

CLI-команда или MCP-запрос обращается к сценарию приложения, который работает через порты. Адаптеры предоставляют файловую систему и индекс. Платформенные интеграции зависят от Wolf; домен не зависит от внутреннего устройства сессий OpenCode.

## Файлы и восстановление

| Путь                                  | Назначение                                               |
| ------------------------------------- | -------------------------------------------------------- |
| `.wolf/config.yaml`                   | Конфигурация проекта                                     |
| `.wolf/memory/`                       | Собственные объекты памяти и рабочие треды               |
| `.wolf/memory/relations.jsonl`        | Связи объектов                                           |
| `.wolf/memory/events.jsonl`           | История событий памяти                                   |
| `.wolf/cache/index.sqlite`            | Поисковый индекс; восстанавливается `wolf rebuild-index` |
| `.wolf/metrics/session-metrics.jsonl` | Локальные сигналы использования и обратной связи         |
| `.wolf/router.log`                    | Решения доставки плейбуков OpenCode                      |

Связанные worktree используют общий корень памяти, но платформенные файлы остаются локальными. Фильтрация scope ограничена путём доставки, описанным в [Изоляции чтения](/ru/guide/read-isolation); worktree не является частной копией всей памяти.

## Эксплуатационные границы

Контрольные точки сохраняют смысл и состояние для продолжения работы. Они не предоставляют движок исполнения с leases, heartbeats или автоматическим восстановлением упавших процессов. Локальное хранение не означает локальный запуск модели: выбранный провайдер получает контекст, отправленный харнесом.

Действующее обучение включает запись уроков и авторизованные мутации лиц; агрегация Стюардом временно приостановлена в 3.0.0. Автоматический decay и runtime консилиума — направления разработки, а не текущие гарантии исполнения. Детали реализации остаются в исходниках и [справочнике CLI](/ru/guide/cli/); [концепт и матрица зрелости](https://github.com/chekh/mister-wolf/tree/main/docs/concept) сохраняют историю замысла и статусы.
