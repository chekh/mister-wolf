# Экспертный консилиум

Экспертный консилиум — ограниченный метод совещания для трудных решений: когда обоснованные варианты действительно конфликтуют, причина не ясна после разумной диагностики, архитектурный выбор дорог для отмены или исполнитель и reviewer придерживаются содержательного спора. Рутинная работа и однозначные ошибки консилиума не собирают — они идут обычным процессом.

## Когда применять

- конфликт обоснованных вариантов, где выбор меняет результат;
- неопределённая причина после разумной диагностики;
- дорогой архитектурный выбор;
- содержательный спор исполнителя и reviewer.

Консилиум созывает mr-wolf (ведущий) — сам по себе он не возникает. Один первый раунд, не более одного уточняющего; продолжение требует новой цели.

## Как устроен консилиум

1. Лид готовит вопрос-пакет для каждого эксперта.
2. Каждый эксперт отвечает **независимо**: claims, evidence, assumptions, confidence, risks — плюс `LIMITS` там, где надёжного ответа нет. Первый раунд идёт без доступа к чужим мнениям.
3. Лид синтезирует: принятые утверждения, отклонённые альтернативы, неразрешённые разногласия и обязательную дальнейшую проверку (`required_validation`).
4. Решение остаётся у ответственного уровня. Рекомендация — не решение.

`insufficient_evidence` — допустимый исход: метод предпочитает честное «на этих данных решить нельзя» навязанному выбору.

## Роль wolf-expert

`wolf-expert` — агент базового набора (в 3.0.0 агентов девять): исполнитель с узкой профессиональной позицией по одному вопросу. Он не выдаёт приёмку, не записывает память и не делегирует.

Канал эксперта по умолчанию — **tool-enabled чтение в границах проекта**: файлы проекта, включая код, читаются штатно, а `glob`/`grep` доступны, чтобы эксперт мог найти нужный файл. Всё остальное запрещено: запись, shell, субагенты, webfetch, браузер, скиллы и чтение вне проекта (`external_directory` отклоняется целиком). Env-файлы и типовые секрет-файлы — `.npmrc`, `.netrc`, `.git-credentials`, `*.pem`, `*.key`, `id_rsa`/`id_ed25519` — остаются под `ask`-защитой: широкое чтение проекта не открывает их молча.

Граница состоит из двух частей, и нужны обе. Пути вне проекта отклоняет host. Ссылки для этой проверки **не разрешаются**: symlink внутри проекта, ведущий наружу, читается как внутренний путь — поэтому лид обязан провести аудит ссылок до запуска: ни одна ссылка внутри проекта не должна разрешаться за его пределы (`realpath` каждой; ссылки в `node_modules`, ведущие внутрь проекта или в его main-чекоут, — норма). Утекающая ссылка делает канал непригодным: убери её или переходи на packet-only. Правило «есть хоть одна ссылка» слишком грубо — оно отключило бы канал в любом Node-проекте.

Права выдаёт **конфигурация базового набора** (профиль агента в `.opencode/agents/`), а не текст поручения: перечень путей в TASK выдачей не является и инструментов не включает. Именно поэтому мёртвое правило `read packet/*` заменено рабочим read-правилом — каталога `packet/` в проектах нет.

Перед первым раундом лид обязан провести **функциональную пробу канала**, отдельную от аудита symlink: короткий вызов эксперта с заданием прочитать адресный файл проекта и вернуть конкретную строку. Проба успешна только если в ответе есть **факт содержимого**; `permission.rejected`, отсутствие tool-вызова или ответ из доставленного текста означают, что канал не tool-enabled. Аудит symlink доказывает изоляцию, но не работоспособность чтения — одна проверка не заменяет другую.

Если канал непригоден, эксперт работает **packet-only** (из доставленных материалов) **и деградация называется явно**: в RESULT первой строкой идёт фактический `channel` — `tool-enabled` | `packet-only` | `denied`, а при `channel != tool-enabled` обязателен `isolation_limits` с перечнем фактов, не подтверждённых чтением. Приёмка tool-enabled без доказательств не заявляется.

## Запись консилиума

Консилиум сохраняется как memory-note (v2-конверт: вопрос, мнения экспертов, синтез) одной операцией:

```bash
wolf council record --input council.json
```

MCP-форма — `council_record`, один тул каталога из восьми. Write-path валидирует строгую схему конверта, хранит canonical JSON, идемпотентен по `request_key` (повтор не создаёт дублей) и восстанавливает связи вопроса, мнений и синтеза. См. [справочник CLI](/ru/guide/cli/command-reference) и [интеграцию MCP](/ru/guide/mcp).

Аналитика читает все исторические форматы (legacy-консилиумы, alias и v2-конверты) одним смешанным потоком: отсутствие голоса — не таймаут, а `envelope_participation` показывает фактическое участие в записанном консилиуме. См. [Аналитику](/ru/guide/analytics).

## Чего он не гарантирует

- Консилиум не заменяет тесты, git-гейты, независимую приёмку и действующую цепочку полномочий.
- Уверенность эксперта — не доказательство: синтезированные утверждения требуют указанной проверки.
- Созыв — решение ответственного уровня, а не автоматический триггер.

Методика и роль приходят с обычным базовым набором (`wolf init` / `wolf upgrade`). Изоляция чтения описана отдельно: [Изоляция чтения](/ru/guide/read-isolation).
