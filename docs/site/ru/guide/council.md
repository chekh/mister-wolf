# Экспертный консилиум

Экспертный консилиум — ограниченный метод совещания для трудных решений: когда обоснованные варианты действительно конфликтуют, причина не ясна после разумной диагностики, архитектурный выбор дорог для отмены или исполнитель и reviewer придерживаются содержательного спора. Рутинная работа и однозначные ошибки консилиума не собирают — они идут обычным процессом.

## Когда применять

- конфликт обоснованных вариантов, где выбор меняет результат;
- неопределённая причина после разумной диагностики;
- дорогой архитектурный выбор;
- содержательный спор исполнителя и reviewer.

Консилиум созывает ответственный уровень (обычно L1) — сам по себе он не возникает. Один первый раунд, не более одного уточняющего; продолжение требует новой цели.

## Как устроен консилиум

1. Лид готовит вопрос-пакет для каждого эксперта.
2. Каждый эксперт отвечает **независимо**: claims, evidence, assumptions, confidence, risks — плюс `LIMITS` там, где надёжного ответа нет. Первый раунд идёт без доступа к чужим мнениям.
3. Лид синтезирует: принятые утверждения, отклонённые альтернативы, неразрешённые разногласия и обязательную дальнейшую проверку (`required_validation`).
4. Решение остаётся у ответственного уровня. Рекомендация — не решение.

`insufficient_evidence` — допустимый исход: метод предпочитает честное «на этих данных решить нельзя» навязанному выбору.

## Роль worker-expert

`worker-expert` — агент базового набора (с 2.31.0 агентов семь): воркер L2 с узкой профессиональной позицией по одному вопросу. Он не выдаёт приёмку, не записывает память и не делегирует.

По умолчанию эксперт **packet-only**: отвечает из доставленного пакета, без инструментов. Опциональный профиль **tool-enabled** даёт ровно один read-allowlist — `packet/*` — и запрещает всё остальное: запись, shell, субагентов, webfetch и чтение вне пакета; `external_directory` вне scope отклоняется целиком. Изоляцию чтения для этого профиля обеспечивает платформа. Перед tool-enabled-прогоном пакет проходит аудит symlink, чтобы allowlist нельзя было обойти ссылкой.

Если платформа не гарантирует ограничений tool-enabled, эксперт работает packet-only **и деградация называется явно** — приёмка tool-enabled без доказательств не заявляется.

## Запись консилиума

Консилиум сохраняется как memory-note (v2-конверт: вопрос, мнения экспертов, синтез) одной операцией:

```bash
wolf council record --input council.json
```

MCP-форма — `council_record`, один тул каталога из восьми. Write-path валидирует строгую схему конверта, хранит canonical JSON, идемпотентен по `request_key` (повтор не создаёт дублей) и восстанавливает связи вопроса, мнений и синтеза. См. [справочник CLI](/ru/guide/cli/command-reference) и [интеграцию MCP](/ru/guide/mcp).

Аналитика читает все исторические форматы (legacy-консилиумы, alias и v2-конверты) одним смешанным потоком: отсутствие голоса — не таймаут, а `envelope_participation` показывает фактическое участие в записанном консилиуме. См. [Аналитику](/ru/guide/analytics).

## Чего он не гарантирует

- Консилиум не заменяет тесты, git-гейты, независимую приёмку и действующую цепочку полномочий.
- Уверенность эксперта — не доказательство: синтезированные утверждения требуют указанной проверки.
- Созыв — решение ответственного уровня, а не автоматический триггер.

Методика и роль приходят с обычным базовым набором (`wolf init` / `wolf upgrade`) вместе с seed-лицом `worker-expert-playbook`. Изоляция чтения описана отдельно: [Изоляция чтения](/ru/guide/read-isolation).
