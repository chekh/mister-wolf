# Агрегация Стюарда

Уроки накапливаются: сессия за сессией агенты записывают мелкие наблюдения, и доставка начинает тонуть в почти-дубликатах. Стюард (фоновый агент контура — см. [Базовый набор](/ru/guide/base-set)) сворачивает зрелые уроки в агрегаты: один обобщённый урок заменяет кластер повторов. **Перераспределение, не надстройка** — агрегат забирает доставку, исходники гаснут.

## Триггеры

Два событийных триггера, оба — одна строка состояния, без демонов:

1. **Завершение цикла** — координатор после приёмки отчётов цикла выполняет `wolf recap`; непустая строка агрегации = вложенный вызов Стюарда.
2. **Старт сессии** — `wolf call` печатает баннер при наличии зрелых неагрегированных уроков: сессия (или владелец) сразу видит долг.

```text
## Стюард: агрегация
неагрегированных уроков: N (зрелых: M) — вызовите Стюарда: opencode run --agent steward
```

«Неагрегированный» = урок в `active` без **живого** входящего ребра `aggregated_in` (рёбра от `rejected`/`archived` агрегатов не считаются — отклонённый кластер возвращается в пул и остаётся видимым). Кластер **зрелый** — достойный строки — когда в нём ≥ 3 уроков или старейшему ≥ 7 дней.

## Шаг 1 — Стюард готовит

Стюард вызывается вложенно (вход — проект). Он:

1. выбирает кластер зрелых уроков по теме/классу (решение LLM; CLI даёт только детектор и `wolf list --type lesson`);
2. создаёт обобщённый урок `review_state: proposed` с контрактом тела: `## Было` (N исходников, id + суть по строке) / `## Стало` (обобщение, или пункт инструктажа для лица, или предложение правила) / `## Почему` (паттерн класса);
3. пишет `wolf relation add <aggregate-id> aggregates <source-id>` на каждый исходник;
4. переносит `trigger_keywords` исходников в агрегат — он должен срабатывать везде, где срабатывали они.

Для мутации лица Стюард готовит новую proposed-версию плейбука (с ребром `outcome_of` к жалобе/урокам-причинам); применяет владелец через `wolf supersede`. Автоприменения нет.

## Шаг 2 — владелец подтверждает

Очередь подтверждения — сама память: proposed-агрегаты видны через `wolf list --type lesson --status proposed`, `wolf recap` их считает:

```text
предложенных агрегатов: P — wolf aggregate apply <id> для подтверждения
```

Команда применения — скрытый plumbing (как `think`/`update`):

```bash
wolf aggregate apply <aggregate-id>
```

Атомарно, под lock: агрегат `proposed → active`, каждый исходник `→ archived` (архив гасит их доставку), в лог падает событие `memory.aggregated`. Повторный `apply` после частичного сбоя **дозавершает** дело — уже archived пропускаются; полный no-op — только когда всё уже применено. С этого момента доставка несёт агрегат вместо кластера — двойная доставка исключена той же транзакцией.

**Отказ бесплатен:** `wolf transition <aggregate-id> rejected` — исходники остаются `active`, их рёбра `aggregated_in` перестают считаться, кластер снова виден как неагрегированный. Ложный кластер стоит только времени Стюарда.

## Работает ли? Метрика затухания

`wolf analytics --view steward` отвечает на главный вопрос — снизила ли агрегация поток уроков и жалоб того же класса:

```text
aggregation decay (7d before / after):
aggregate    src  lessons -/+7d  complaints -/+7d
mem_…        4    6 / 0          2 / 0
note: class = free-tag heuristic (>=1 shared tag); upgrade path — pattern_key
```

На каждый active-агрегат: сколько новых уроков и жалоб того же класса (≥ 1 общий тег) появилось за 7 дней до и после `memory.aggregated`. Класс — эвристика свободных тегов, сноска говорит об этом честно; путь апгрейда — `pattern_key`. См. [Аналитика](/ru/guide/cli/analytics).
