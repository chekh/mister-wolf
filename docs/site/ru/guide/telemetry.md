# Телеметрия

Mr. Wolf измеряет собственное использование — локально, детерминированно, без LLM в контуре записи. Эта страница описывает, что именно попадает в `.wolf/`, какие поля несут события и как прочитать данные обратно. Никуда наружу ничего не уходит.

## Что логируется

| Файл                                  | Писатель                                                 | Содержимое                                        |
| ------------------------------------- | -------------------------------------------------------- | ------------------------------------------------- |
| `.wolf/metrics/session-metrics.jsonl` | сам Wolf: CLI-команды, MCP-хендлеры, инъекции brief/call | append-only JSONL, одно событие на строку         |
| `.wolf/router.log`                    | опциональный плагин `wolf-router` (в резерве с 3.0.0)    | решения о доставке playbook (hit/miss по агентам) |

Сигнальный лог — канонический источник телеметрии. Битая строка не роняет контур: она попадает в счётчик (`malformedLines`) и пропускается.

Здесь разобраны три события, с которыми вы реально столкнётесь: `mcp_call` — каждый вызов тулзы/команды, `delivery` — доставка памяти в контекст агента и `run` — завершённый turn, импортированный из базы OpenCode.

## mcp_call

Пишется на каждый вызов MCP-тулзы `mr-wolf_*` и инструментированных CLI-команд (`add`, `get`, `list`, `search`, `call`, `brief`). Топ-левел поля: `tool_name`, `duration_ms`, `outcome` (`ok` \| `error`; `error` — только throw хендлера, текстовый «not found» — это `ok`) и актор (`system:wolf` у MCP-канала, `user:cli` у CLI-канала).

Поля `detail`:

| Поле             | Семантика                                                                             | Канал      |
| ---------------- | ------------------------------------------------------------------------------------- | ---------- |
| `method`         | вызанный метод / имя команды                                                          | оба        |
| `wolf_version`   | runtime-версия Wolf (из package.json)                                                 | оба        |
| `args_summary`   | только `add`: `{type ≤40 симв, title ≤80 симв, extra_keys}` — body не пишется никогда | оба        |
| `memory_id`      | только `get`: запрошенный id                                                          | оба        |
| `memory_ids`     | только `search`: id результатов, первые 10 (MCP-канал; CLI `search` поле не пишет)    | MCP        |
| `cli_command`    | имя команды                                                                           | только CLI |
| `error.message`  | при ошибке: сообщение, обрезанное до 200 симв                                         | оба        |
| `error.code`     | при ошибке: машинный код, если есть                                                   | оба        |
| `error_class_id` | при ошибке: детерминированный класс (тот же классификатор, что у `tool_error`)        | оба        |

## delivery

Пишется, когда память реально доезжает до контекста агента (инъекции `wolf brief` / `wolf call`, доставка skill и frame):

| Поле                     | Семантика                                            |
| ------------------------ | ---------------------------------------------------- |
| `detail.name`            | что доставлено (имя объекта памяти)                  |
| `detail.mechanism`       | `skill` \| `frame` \| `plugin` \| `search` \| `call` |
| `detail.target`          | цель доставки, обрезается до 200 симв                |
| `detail.injection_bytes` | размер инъекции в байтах                             |
| `session_id`             | ключ сессии у CLI-канала (`null` у MCP — см. ниже)   |

## run

`wolf usage import` читает локальную SQLite-базу площадки OpenCode 2.2.5 (`~/.local/share/opencode/opencode.db`) **только на чтение** и переносит завершённые assistant-turn'ы в тот же сигнальный лог через тот же писатель `appendSignal` — второго писателя нет. Опции: `--db`, `--since`, `--until`, `--task-map <json {session_id: task_id}>`, `--dry-run`, `--json`; окно по умолчанию — с начала вчерашнего дня. Дедупликация: `event_id = sha256("opencode-usage:v1|" + message_id)` — повторный импорт неизменного источника строк не добавляет.

| Поле                                     | Семантика                                       |
| ---------------------------------------- | ----------------------------------------------- |
| `ts`                                     | время завершения turn'а (`time.completed`)      |
| `tokens`                                 | `{input, output, cache_read}`                   |
| `weighted`                               | `input + 0.1*cache_read + 5*output`             |
| `duration_ms`                            | `completed − created`                           |
| `outcome`                                | `stop`/`tool-calls` → `ok`, `error` → `error`   |
| `run_id` · `trace_id`                    | id сессии прогона · родительская сессия         |
| `attempt` · `task_id` · `schema_version` | только при retry · только из `--task-map` · `2` |

Ограничения: `variant` модели не переносится, `cost` не вычисляется, `reasoning` и `cache.write` не входят в `output`/`weighted`, незавершённые turn'ы пропускаются, а пустой набор событий означает неизвестное покрытие, а не нулевой расход. Подробности команды: [справочник CLI](/ru/guide/cli/command-reference).

## Ключи сессий

- `cli-<uuid>` — продюцируется самим CLI, один на вызов: один CLI-процесс получает один стабильный id, общий для всех его писателей телеметрии. Явно выставленный `WOLF_SESSION` не перезаписывается.
- `opc-<uuid>` — передаётся опциональными штампованными плагинами opencode (`wolf-router`, `wolf-session-start`; в резерве с 3.0.0) при каждом spawn CLI. Иначе long-lived процесс opencode с одним унаследованным env свалил бы все доставки в одну фальшивую сессию. Обновления шаблонов приезжают проектным проходом `wolf upgrade`.
- MCP-канал — без сессии by design: `wolf mcp` — long-lived сервер с одним окружением на все запроси; один session id был бы фальшивой атрибуцией, поэтому события пишутся с `session_id: null`.

## Приватность

- Всё локально: `.wolf/` внутри проекта; ни сетевых вызовов, ни экспорта телеметрии.
- `target` обрезается до 200 символов — промпты целиком в лог не попадают.
- `body` объекта памяти не попадает в телеметрию никогда: `args_summary` несёт только type, title и ключи extra-полей.
- `error.message` обрезается до 200 символов.
- Неизвестные поля отбрасываются схемой при чтении — лог append-only и derived (можно удалить, восстановится использованием).

## Как читать

Аналитическая выборка `acceptance` превращает сырые события в машинно-проверяемые метрики — miss-rate роутера по агентам, error-rate и p50/p90-латентность по тулам, burst'ы доставок, search→get follow, vitality за 72 ч:

```bash
wolf analytics --view acceptance --json
```

Та же выборка доступна через MCP (`mr-wolf_analytics` с `view: "acceptance"`). Что метрики означают: [Аналитика — машинная приёмка](/ru/guide/cli/analytics#машинная-приемка).
