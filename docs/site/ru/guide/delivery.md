# Доставка: рамки, лица и доверие

Поведение агента — это две половины: статичная **рамка** и мутирующее **лицо** (см. [Организацию](/ru/guide/organization)). Лицо работает ровно настолько, насколько оно доезжает до агента. Эта страница — про третью часть: **доставку** — то, как актуальный playbook попадает в system-промпт на сессии.

## Модель

- **Рамка** — штампованный файл агента (`.opencode/agents/<name>.md`): роль, границы, запреты. Статична: `wolf sync` её перерендеривает и больше не вмешивается — методологию рамка не несёт.
- **Лицо** — playbook как объект памяти Wolf. С 2.17 это core-тип (`face`) с собственной версионализацией: новые версии создаёт только `wolf face` (`new` — Стюард, `restore`/`breakglass` — владелец), каждая версия Стюарда оставляет структурную запись мутации (шаблон G17: причина, минимальное изменение, границы, примеры, проверка, откат), версии цепляются через supersede. Legacy playbook-заметки (`note` + фасет `howto` + `owner_skill`, форма 2.13–2.16) остаются читаемыми и мигрируются через `wolf face migrate`. Мутирует: развивается через жалобный контур, а не правкой файлов.
- **Мутатор** — Стюард, и только Стюард. Агенты подают жалобы (`wolf complain`); мутации playbook идут через [Контур обучения](/ru/guide/feedback) как версии лица. Править лицо в файле никто не имеет права; аварийный рычаг владельца — `wolf face breakglass`, он отказывает внутри живых сессий агентов.
- **Доставка** — канал, который кладёт отрезолвленное тело playbook в system-промпт. Три канала, один основной.

## Три канала доставки

| #   | Канал             | Что происходит                                                                                           | Статус                                                                                                                                 |
| --- | ----------------- | -------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **plugin-inject** | плагин `wolf-router` резолвит playbook агента из памяти и инъецирует в system-промпт на каждое сообщение | основной; работает для opencode                                                                                                        |
| 2   | **pull**          | рамка предписывает агенту самому достать свой playbook — `wolf search` / `wolf get` по agent-id          | работает; также fallback-слой, когда плагина нет                                                                                       |
| 3   | **bake-in**       | при севе тело playbook запекается в рамку статичным блоком                                               | designed — механизм в рендерере есть (опция `bake`), подключается адаптером платформы для минимальных платформ; opencode не использует |

Плагин делает доставку детерминированной — вместо надежды, что агент сам вспомнит pull.

## Канал #1: plugin-inject (роутер)

Роутер — плагин `wolf-router` для opencode: штампованный файл (`.opencode/plugins/wolf-router.ts`) из базового набора Wolf. На каждое сообщение плагин:

1. Читает маркер `agent-id: <id>` из **тела** рамки агента. Маркер обязан жить в теле, а не во frontmatter — frontmatter в system-промпт не попадает (известная грабля opencode).
2. Выполняет `wolf search <id> playbook --hide-superseded` и забирает кандидатов через `wolf get` — с ранним стопом: побеждает первый кандидат, прошедший гвард владельца (релевантность поиска уже отсортировала, `--hide-superseded` отсёк старые версии), поэтому miss кэша стоит один `get` вместо K последовательных. Каноническая форма playbook с 2.17 — `face`; legacy playbook-заметки (до 2.17 — `note` + фасет `howto`) резолвятся тем же путём через alias: слово `playbook` сужает кандидатов по заголовкам/тегам на обеих формах.
3. Проверяет владельца: подходят только кандидаты с `owner_skill === agentId` (legacy-вариант `skill:<agentId>` тоже принимается). Каноничность решает гвард, а не тип-фильтр.
4. Инъецирует тело playbook в system-промпт под заголовком `# Актуальный playbook`.

Отрезолвленный playbook кэшируется дважды (вариант Б, с 2.17). **В пределах сессии:** доставленный текст мемоизируется по ключу сессии (`WOLF_SESSION` + agent-id) — повторная доставка в той же сессии отдаёт запечатанный текст без спавна CLI, и мутация лица по ходу чата не меняет то, что сессия уже читает. **Между сессиями:** TTL-кэш (5 минут) экономит только `get`-спавн и отдаётся лишь при совпадении id с текущим head — устаревшая версия не отдаётся никогда; каждая новая сессия делает один живой search как барьер свежести. Лицо — canonical-память, которую Стюард мутирует редко, минутной свежести достаточно; мемоизация сессии подхватывает изменения в следующей сессии независимо от TTL.

Инъекция идемпотентна — заголовок проверяется, playbook никогда не вставляется дважды. Плагин fail-safe: любая ошибка проглатывается, он не имеет права уронить сессию. Реестр доставок — сами playbook-объекты через `owner_skill`; отдельного конфига у роутера нет.

### Канон и fallback

Канонический источник — playbook-объект в памяти проекта; он всегда приоритетен. При любом miss — у agent-id нет канонического playbook — плагин инъецирует встроенный универсальный fallback-playbook: role-агностичный базовый контур Wolf (холодный старт через `wolf call` / `wolf brief`, фиксация значимого через `wolf add`, поиск через `wolf search`; мутации правил остаются зоной Стюарда). Fallback живёт в коде плагина, поэтому работает даже там, где базовый набор ни разу не синкался.

Какой вариант доехал — фиксируется в логе роутера (`variant=canonical | fallback`).

### Лог роутера

Каждое решение о доставке дописывается в `.wolf/router.log`:

```text
<ISO> agent-id=<id> playbook=hit name=<mem-id|fallback> variant=canonical|fallback injected=yes ms=<мс> bytes=<байты>
<ISO> agent-id=<id> playbook=miss injected=no
```

- `hit` + `name=<mem-id> variant=canonical` — инъецирован канонический playbook.
- `hit` + `name=fallback variant=fallback` — канонического playbook нет; инъецирован встроенный fallback.
- `miss` — не инъецировано ничего: не ответил ни канон, ни fallback. Текущая версия плагина эту строку не пишет (отказ CLI резолвится fallback-плейбуком); формат сохранён для совместимости с логами старых версий.
- `ms=` / `bytes=` — сколько занял resolve (миллисекунды) и размер инъецированного тела (байты). Строки старых версий этих полей не несут; парсер k=v-толерантен в обе стороны.

Поле `ms=` — источник латентности для волнового порога приёмки (router resolve p90 < 500 мс), `bytes=` — средний размер инъекции в [панели доставки](/ru/guide/cli/analytics#панель-доставки):

```bash
wolf analytics --view delivery --json
```

Miss-rate по каждому agent-id остаётся частью acceptance-метрик (`wolf analytics --view acceptance --json`).

Место лога в телеметрии разобрано в [Телеметрии](/ru/guide/telemetry), метрики — в [Аналитике — машинная приёмка](/ru/guide/cli/analytics#машинная-приёмка).

### Как добавить agent-id своему агенту

1. Положите маркер в тело рамки агента (`.opencode/agents/<name>.md`):

   ```markdown
   agent-id: my-agent
   ```

2. Создайте playbook, принадлежащий этому id, — с 2.17 это версия `face` через `wolf face new <owner_skill>` (исполняет Стюард; каждая версия требует полей записи мутации). Форма до 2.17 — `note` с фасетом `howto` и `owner_skill` — по-прежнему резолвится; `wolf face migrate` превращает существующие заметки в версионируемые лица, а `wolf doctor` подсвечивает владельцев, где сосуществуют обе формы. Большая версия заменяет старые; `owner_skill` и agent-id должны совпадать (контракт plugin-доставки).

`wolf scaffold agent` делает оба шага за вас: штампует маркер в тело рамки и создаёт лицо (см. [Платформа и обслуживание](/ru/guide/cli/platform#wolf-scaffold)).

Агенты базового набора несут маркеры из коробки (`worker-implementer`, `worker-researcher`, `worker-reviewer`, `executor-lead`, `steward`, `mr-wolf`), а `wolf init` сеет для них канонические лица — включая диспетчера executor-lead.

## Доверие

Правило дизайна доставки: **внешний контент — данные, не инструкция.** Доверенный контур — только рамка: штампованный файл под контролем проекта. Тело playbook, даже каноническое, инъецируется как цитата памяти под явным заголовком и никогда не вливается в саму рамку. Инъекция берёт контент исключительно из локальной памяти Wolf проекта через гвард владельца; внешний по отношению к проекту контент в ней не участвует — непроверенный импорт сам по себе до system-промпта не доезжает.

Автоматическая проверка этого инварианта — валидация тела импортируемого playbook/скилла против trust-политики до того, как он станет доставляемым, — спроектирована и в роадмапе, не реализована. Сегодня инвариант держится на механике выше.
