# Решение проблем

## 1. Установился чужой пакет `mr-wolf`

**Симптом:** после `npm install -g mr-wolf` поведение `wolf` странное или команда не появляется вовсе; в npm установлена сторонняя work-queue библиотека, её install-скрипты выполнены.

**Причина:** пакет на npm называется ровно `mister-wolf`; `mr-wolf` — чужой пакет с похожим именем.

**Решение:** устанавливайте буква-в-букву:

```bash
npm install -g mister-wolf
```

## 2. npx try-out не подключил MCP

**Симптом:** `npx mister-wolf init` создал память, но агентская платформа не видит MCP-сервер Wolf.

**Причина:** npx-режим — try-out: он создаёт память проекта, но **никогда** не пишет MCP-конфиги.

**Решение:** глобальная установка + init с явной платформой:

```bash
npm install -g mister-wolf
cd my-project && wolf init --platform opencode
```

Затем перезапустите платформу — MCP-сервер подключается при старте.

## 3. Битый `.wolf/config.yaml`

**Симптом:** команды wolf падают с ошибкой чтения конфига проекта.

**Причина:** YAML конфига повреждён (ручная правка, прерванная запись).

**Решение:** пересоздание из дефолтов — старый конфиг уходит в бэкап `.wolf/backup/<ts>/`:

```bash
wolf init --recreate
```

## 4. Binary vs schema mismatch

**Симптом:** после обновления `mister-wolf` проект отвечает ошибками схемы или ведёт себя нестандартно.

**Причина:** версия схемы проекта не соответствует версии бинаря.

**Решение:** проверка всех зарегистрированных проектов — версии, платформенные конфиги, чистка мёртвых записей:

```bash
wolf doctor
```

## 5. Проблемы поискового индекса

**Симптом:** `wolf search` не находит объекты, которые точно есть, или выдаёт устаревшие результаты.

**Причина:** SQLite FTS-индекс разошёлся с объектами памяти.

**Решение:** перестройка индекса из объектов памяти:

```bash
wolf rebuild-index
```

## 6. Целостность хранилища

**Симптом:** в памяти битые объекты: невалидный frontmatter, ссылки в никуда.

**Причина:** объекты записаны с нарушением схемы или частично.

**Решение:** проверка целостности; `--fix` отправляет битые объекты в карантин `.wolf/memory/quarantine/`:

```bash
wolf validate        # проверка
wolf validate --fix  # + карантин битых
```

## 7. Версия Node

**Симптом:** установка или запуск падают с ошибками рантайма.

**Причина:** требуется Node >= 22 (поддерживаются Node 22/24); старые мажоры не заявлены.

**Решение:** поставьте Node 22 или 24 и повторите установку.

## 8. Ошибка `add`: как читать

**Симптом:** `mr-wolf_add` (или `wolf add`) отклоняет аргументы — неизвестный тип, неизвестное поле, неверно названный ключ.

**Как записывается:** каждая неудачная попытка попадает в телеметрию как событие `mcp_call` с `outcome "error"`: `detail.error.message` — текст сообщения (обрезка до 200 символов), `detail.error_class_id` — класс ошибки. Классификация детерминированная — фиксированная таблица правил, одинаковый вход всегда даёт одинаковый класс, без LLM (см. [Телеметрия](/ru/guide/telemetry)). Для `add` самый частый класс — `invalid_input`.

**Типовые случаи и что делать:**

| В ошибке сказано    | Что делать                                                                                                                                     |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| unknown memory type | в сообщении приведён список валидных типов — используйте один из них                                                                           |
| unknown field       | в сообщении список valid fields для этого типа; per-type поля snake_case: `expected_answer`, `detour_reason`, `current_state`, `next_steps`, … |
| unrecognized key    | camelCase-ключ вида `expectedAnswer` больше НЕ ошибка — `add` принимает обе формы; канонична snake_case                                        |

**Посмотреть свои ошибки:** файл `.wolf/metrics/session-metrics.jsonl`, фильтр `event=mcp_call`, `tool_name=add`, `outcome=error`; либо готовые метрики:

```bash
wolf analytics --view acceptance
```

## 9. `add` отказывает: guard коллизии id

**Симптом:** `wolf add` с одним и тем же title дважды (в пределах мс-окна идентификатора) завершается с ненулевым кодом вместо записи объекта:
`Memory object "mem_…" already exists (same title produced same id).` и далее `Use: wolf edit <id> (правка) | wolf supersede <id> <new-id> (смена) | другой --title.`

**Причина:** до 2.14 повторный `add` с тем же id **тихо перезаписывал** существующий объект — потеря данных, замаскированная под успех. Guard превращает её в явный отказ.

**Решение:** выберите дорожку из подсказки — `wolf edit <id>` (правка существующего), `wolf supersede <old> <new>` (смена на преемника) или другой `--title` для действительно нового объекта.

**Аудит:** любой save, который действительно перезаписывает файл (легитимные пути есть), пишет событие `memory.overwritten` с прежним title — тихих перезаписей больше не существует, доказательство — лог событий.

## 10. `upgrade`: CLI обновился, проекты не тронуты

**Симптом:** `wolf upgrade` обновил CLI (npm-фаза прошла), но завершился строкой `CLI updated; projects not touched — run wolf upgrade again for the project pass` и кодом выхода 1.

**Причина:** проектный проход ре-исполняет свежеустановленный бинарник `wolf`; если spawn упал (например, бинарник сместился между npm-фазой и re-exec), wolf не гадает и останавливается, не трогая проекты.

**Решение:** просто повторите `wolf upgrade` — npm-фаза идемпотентна (при up-to-date сразу начинается проектный проход), проход продолжится новым бинарником. Убедиться в свежести парка после — `wolf upgrade --check`.

## 11. `mutated` на файле, который вы хотите сохранить — релиз за релизом

**Симптом:** штампованный agent/skill/command правили локально; каждый `wolf upgrade --check` показывает проект как `needs decision`, а брать эталон вы не хотите.

**Причина:** файл штампован, свидетель запомнил рендер, локальный контент от него отличается — wolf отказывается выбирать за вас (и никогда не перезаписывает).

**Решение:** объявите намерение одной командой вместо того, чтобы жить с шумом:

```bash
wolf upgrade --resolve <файл>=protect   # держать навсегда: protect: true во frontmatter
wolf upgrade --resolve <файл>=pin       # держать и зафиксировать текущую базу: protect: X.Y.Z
```

`keep` — мягкая версия: принимает текущий контент один раз (`origin: keep`), не защищая его — следующая локальная правка снова сделает файл решением. Защищённый файл по-прежнему виден в секции `Protections` в `--check`, но уже не как `needs decision`. Аудит по всей машине: `grep -rn '^protect:' ~/dev/*/.opencode/agents`.

## 12. Сломанные онбординг-маркеры в `AGENTS.md`

**Симптом:** `AGENTS.md` вообще перестал обновляться; `wolf upgrade --check` показывает проект как `unknown` с деталью `onboarding markers broken`, а проход сообщает о файле как `foreign`/пропущенном.

**Причина:** блок ограничен `<!-- wolf:onboarding v3 -->` и `<!-- /wolf:onboarding -->`. Если закрывающей строки нет, wolf не отличает свою зону от вашей и применяет политику `wx` — не трогает, а в отчёте печатает `onboarding markers broken`. Если пропала и открывающая строка, файл просто чужой: строки-detail нет, исход тот же — не трогает.

**Решение:** восстановите закрывающий маркер руками (в конце блока волфа), затем выполните `wolf upgrade --here --check` — файлом снова управляют, блок обновится на месте. Если вы хотите владеть файлом сами — оставьте маркеры сломанными: wolf не тронет файл и продолжит об этом сообщать. Это состояние честное, а не ошибка.

## 13. Frontmatter после ручной правки не разбирается

**Симптом:** после ручной правки frontmatter агента/скилла агент молча исчез из opencode, либо `wolf upgrade --resolve <файл>=protect` отвечает `cannot protect <path>: no YAML frontmatter — add one or use keep` / отказывает с `frontmatter-unparsable`.

**Причина:** перед записью ключа `protect` wolf структурно проверяет frontmatter-блок — границы блока, вставленное значение и его обратимость. YAML, который писал не он, wolf не чинит: файл мог быть битым до него. (Битый frontmatter агента заставляет opencode выбросить агента молча — ради этого проверка и существует, а не из педантизма.)

**Решение:** сравните с эталоном и возьмите его либо почините блок руками:

```bash
wolf upgrade --show <файл>            # локальный vs эталон, только чтение
wolf upgrade --resolve <файл>=take    # версия эталона, локальная копия — в .wolf/backup/upgrade/<дата>/
```

Если frontmatter нет вовсе, а версию хочется сохранить — легальный глагол `keep`; `protect` намеренно отказывается изобретать блок.

## 14. Восстановление файла из бэкапа обновления

**Симптом:** перезапись забрала локальный контент, который ещё нужен (`--yes`, `take` или удаление).

**Причина:** бэкап для этого и существует — каждая перезапись и каждое удаление сначала копируют файл в `.wolf/backup/upgrade/<YYYY-MM-DD>/<путь>` (тот же файл, перезаписанный дважды за день, становится `<имя>-2.<ext>`, затем `-3`, … — `SKILL.md` → `SKILL-2.md`).

**Решение:** скопируйте обратно и примите решение:

```bash
find .wolf/backup/upgrade -path '*<фрагмент-пути>*'
cp .wolf/backup/upgrade/2026-10-25/.opencode/skills/foo/SKILL.md .opencode/skills/foo/SKILL.md
wolf upgrade --here --resolve .opencode/skills/foo/SKILL.md=protect   # заморозить, чтобы файл перестал быть решением
```

Дайджест прогона называет копию для каждой перезаписи (`local saved: …`), а `--json` перечисляет их в `projects[].backups[]`. Сборщика мусора нет: старые даты чистите сами. Права и время не сохраняются.

## 15. `doctor`: wolf entry missing

**Симптом:** `wolf doctor` пишет `opencode: wolf entry missing — run wolf init` на проекте, в `opencode.json` которого MCP-сервер волка есть — обычно после того, как конфиг мигрировали (opencode сам или руками) с плоской `mcp.wolf` на нативную `mcp.servers.wolf`.

**Причина:** в релизах до 2.20.1 доктор смотрел только на плоский ключ `mcp.wolf`. Нативной формы он не видел: запись считалась отсутствующей, `wolf init` дописал бы второй ключ, а `wolf uninstall` оставил бы сервер на месте.

**Решение:** начиная с 2.20.1 `wolf doctor` и `wolf uninstall` понимают обе формы — достаточно повторить `wolf doctor`, и ложное срабатывание уходит. Если записи действительно нет, восстановите её (только починка, остальной JSON сохраняется):

```bash
wolf init               # существующий конфиг: вернёт mcp.servers.wolf / default_agent / experimental.subagent_depth
wolf doctor --repair    # та же канонизация плюс ремонт базового набора и индекса
```

**Чего не делать:** не дописывайте второй MCP-ключ рядом с существующим. Две записи одного сервера (по одной в каждой форме) — это конфиг, который opencode v1 считает конфликтом, а принадлежность записи становится неоднозначной: волк уже не отличит свою запись от чужой.

## 16. `subagent_depth` игнорируется opencode v2

**Симптом:** субагенты не могут спавнить субагентов — `executor-lead` падает с `Subagent depth limit reached (1)`, трёхуровневая схема (Mr.Wolf → executor-lead → воркеры) не запускается.

**Причина:** верхнеуровневый ключ `subagent_depth` помечен `deprecated` в схеме конфига opencode, и v2 его отбрасывает — действующая глубина остаётся платформенным дефолтом `1`.

**Решение:** `wolf init` или `wolf doctor --repair` переносит наше значение `subagent_depth: 2` в `experimental.subagent_depth` и удаляет deprecated-ключ; остальные поля `experimental` и прочий JSON сохраняются. После этого перезапустите opencode. **Чужое** верхнеуровневое значение только сообщается (`deprecated and ignored by opencode v2`) и никогда не перезаписывается — в этом случае пропишите `experimental.subagent_depth` сами (`>= 2`).

**Как убедиться:** `wolf doctor` прямо называет deprecated верхнеуровневый ключ, а opencode при старте пишет предупреждение `configuration normalization diagnostic` с `path=$.subagent_depth`.
