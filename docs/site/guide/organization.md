# Organization keeps the goal in view

The three levels exist to maintain direction over a long assignment: L0 keeps the user's intent, L1 organizes the route to a result, and L2 performs bounded tasks. A local difficulty returns to the level holding the needed context; acceptance connects work back to the original goal. Memory carries recorded state across sessions. The Steward improves methods through a separate, cross-cutting loop.

## Responsibility

| Level         | Owns                                                               | Boundary                                                                                          |
| ------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| L0 — Wolf     | Intent, goal, success criteria, communication and final acceptance | Does not perform subject work or call L2 directly                                                 |
| L1 — Executor | Decomposition, dependencies, assignments, integration and delivery | Assigns subject work to L2, including small tasks; retains decisions and permitted Git operations |
| L2 — Worker   | One finite result or research question                             | Does not expand scope or spawn other agents                                                       |

Frames combine instructions with harness permissions. Some boundaries are permission-enforced; others are behavioral protocols. A prohibition in text is not proof that every action is machine-validated.

## Working cycle

| Step                   | Responsible             | Result                                                        |
| ---------------------- | ----------------------- | ------------------------------------------------------------- |
| Goal and brief         | User and L0             | Intent, scope and acceptance criteria                         |
| Plan                   | L1                      | Finite tasks, dependencies, assigned methods and verification |
| Execution              | L2 under L1             | Verifiable partial results or specific questions              |
| Integration and report | L1                      | Combined result, criteria checks and limitations              |
| Acceptance             | L0                      | Verdict against the goal and evidence                         |
| Checkpoint             | Responsible participant | Significant state and next step recorded in memory            |

A checkpoint is also useful inside long work: before handoff, after a significant milestone, at a difficulty or risky decision. It preserves recorded meaning; unrecorded findings can be lost, and automatic process recovery is not provided.

## Compose an assistant and choose a session

L1 composes an assistant from an L2 instance, an appropriate face, assigned skills, inputs and tools. The brief supplies the result, contribution to the goal, criteria, boundaries, sources, methods, verification, budget and return condition. Implementation, research and review profiles receive only applicable fields; a missing required input comes back as a question.

Responsibility level does not determine the model or its reasoning depth. Model/variant selection uses actual host capabilities; a wish in a brief does not prove the setting was applied. The `standard|draft` density shortens service text while preserving substantial evidence and checks.

After deciding to delegate, the hiring L0 or L1 chooses `fresh` for a new independently acceptable result, `continue` for the same unaccepted result, or `replace` for a replacement on that task. Before replacement, stop writing, preserve the result and transfer ownership. A timeout does not prove writing stopped. Clean context depends on actual history inheritance by the host; limitations must be explicit. Small related operations are grouped into a finite L2 assignment, not transferred to L1.

An L1 instance owns a bounded delivery, not the entire goal, thread or user session. After that delivery is accepted, the next independently acceptable result gets a new L1 even when work is sequential and the topic stays the same. Corrections to the same unaccepted result may continue with the existing L1. The new executor receives relevant artifacts, evidence, constraints and decisions rather than the previous chat history.

When distributing a goal across several L1 deliveries needs substantive planning, L0 commissions an L1 to prepare bounded briefs, dependencies, parallel launch conditions and an integration owner. L0 accepts that plan and assigns the L1 executors; the planner does not spawn peers. Ready independent deliveries may run in parallel within the overall budget and host capabilities. A small coherent delivery needs no separate planner. Shared plans and memory have one assigned writer; existing verification and acceptance gates remain in force.

## Acceptance

The report connects criteria to artifacts, verification commands, exit codes and material limitations. Where needed, retain revisions/hashes, independent review and unresolved risks. Executor self-checks do not replace required independent acceptance. Significant risk may require a separate reviewer before L0's final verdict.

## Council: designed

Executable Council is not shipped. The design calls for independent opinions at hard forks: uncertainty, high risk, irreversibility, conflicting evidence or stalled progress. Synthesis should preserve accepted claims, rejected alternatives and dissent; the authorized owner still decides. Budget and rounds are bounded. This is future design, not an instruction to invoke an available runtime.

## Improve the organization

The working cycle retains experience. The Steward handles supported feedback, aggregates compatible lessons and changes faces under the authorized protocol. It is not a fourth execution level. Methods can change while history and owner control remain.
