# unified-update — функциональные требования

Волна 2.19.0. Статус — черновик на утверждение владельцу (через L0); открытые
вопросы собраны в конце документа.

## 1. Контекст и проблема

Mr. Wolf установлен как глобальный CLI и живёт в парке проектов. Аналитика
парка (2026-10-23, 17 живых памятей) показала: релизы CLI выходят, но парк за
ними не следует — base-set штампы проектов 2.16.2–2.17.1 при актуальной
2.18.5, вызовов 2.18.x в метриках нет. Обновление сегодня — набор ручных шагов
на каждый проект (`npm i -g`, `wolf sync`, повторный `wolf init --full` для
посева новых лиц), которых никто не делал.

Корневой пробел (расследование 2026-10-23): `wolf sync` никогда не трогает
память — сеет лица только `wolf init`. Шаблон executor-lead появился в base-set
в v2.11.0, ПОСЛЕ init большинства проектов, поэтому у парка нет лица
executor-lead → 91% промахов доставок уходят в fallback-плейбук. Даже
запущенный `wolf sync` этот класс потерь не закрывает.

Цель 2.19.0 (решение владельца): «один раз выполнил обновление — обновил всё».
Команда обновления предлагает обновить ВСЕ проекты, зарегистрированные в
глобальном реестре Wolf, и выполняет это: обновляет CLI, затем доводит каждый
проект — перерисовывает base-set и досевает недостающие базовые лица. Вторая
половина цели (решение владельца 2026-10-23, mem*20261023_karta_obnovleniya*…):
каждый релиз поставляет декларативную карту обновления, а проход и сверка
опираются на неё, а не на косвенные признаки — инвентаризация парка показала,
что штамп `set=` отражает версию запускавшего бинарника, но не состав набора
(прецедент: 30 файлов `set=2.17.0` при составе скиллов из 2.18.0).

Метрика успеха: после одного запуска команды на реальном парке (4+ проекта в
реестре) все проекты соответствуют карте релиза (строгая сверка REQ-11), их
штампы обновлены, у каждого базового агента есть активное лицо (owner_skill =
agent_id), доля fallback-доставок по executor-lead в router.log падает до нуля
для новых сессий.

## 2. Область

Входит:

- Расширение существующей команды `wolf upgrade` до единой точки обновления:
  самообновление CLI → подтверждение → проход по всем проектам из реестра.
- Per-project обновление: `wolf sync` base-set + досев недостающих базовых
  лиц (семантика init-посева) + отчёт по проекту.
- Сводный отчёт по парку: обновлено / актуально / пропущено-мутировано /
  ошибки / досеяны лица.
- Изоляция сбоев: ошибка одного проекта не прерывает остальные.
- Карта обновления релиза: генератор скелета из diff base-set + курируемая
  семантика, поставка в npm-пакете, потребление проходом и строгая сверка
  проекта с картой (REQ-10…REQ-12).
- Пиннинг: флаг `pinned: true` в реестре — upgrade показывает и пропускает,
  самолечение уважает (REQ-13).
- Ручной режим `wolf upgrade --here`: полный проектный шаг в текущем
  каталоге, вне реестра, без самообновления CLI (REQ-14); `wolf sync` —
  deprecated-алиас 2.19.0 с перенаправлением на upgrade (удаление 2.20.0).
- Стилизованный терминальный вывод поверхностей upgrade (`upgrade` /
  `--check` / `--here`): переиспользуемый renderer-модуль как стандарт
  вывода (REQ-15); остальные команды — инкрементально после 2.19.0
  (допущение L0, в пакете на подтверждение).
- Расширение `wolf upgrade --check` на парк (read-only сводка устаревания).

НЕ входит (не-цели 2.19.0):

- Async learning — авто-генерация лиц из статистики роутера (→ 2.20.0).
- Улучшение логирования / новый observability-канал (→ 2.20.0).
- Авто-курирование семантики карты: генератор делает скелет из diff, смысл
  категорий курируется человеком на релиз (REQ-10).
- Удаления base-set без подтверждения списка (REQ-02/REQ-11); удаление или
  деприкация существующих объектов памяти по карте — единственная мутация
  памяти прохода это посев новых лиц (REQ-03); deprecated-лица репортятся,
  не лечатся (REQ-11).
- Принудительный бэкфилл реестра: автозапись всех найденных `.wolf/` на диске
  в реестр без ведома пользователя. Граница обновления — ТОЛЬКО реестр;
  незарегистрированные проекты не трогаются (решение владельца
  mem_20261023_sostav_2_19_0_i_granitsa_obnovleniya_tol_906915). Пиннинг —
  флаг `pinned: true` (REQ-13), не снятие регистрации.
- Расширение `wolf sync` новой функциональностью — он deprecated-алиас
  2.19.0 (прежде­действие + подсказка-перенаправление на `wolf upgrade`,
  удаление 2.20.0); вся логика обновления живёт в upgrade. Инвариант «память
  вне посева не трогается» — см. REQ-07.
- Исправление дефектов данных лиц (например, superseded-объект без
  `owner_skill` в mister-wolf) — зона Стюарда, не конвейера обновления.
- Многопользовательские и сетевые среды: реестр локален на машину.

## 3. Глоссарий

- **Реестр** — `~/.config/wolf/projects.yaml`: локальный список проектов
  (путь, версия схемы, дата). Пишет `wolf init`; самолечение (2.14, P331)
  дописывает cwd при любой wolf-команде в проекте с живой памятью.
- **Base-set** — штампованные файлы шаблонов (agents/skills/commands/plugins,
  AGENTS.md), поставляемые пакетом; перерисовываются проектным шагом
  `wolf upgrade` (включая `--here`); `wolf sync` — deprecated-алиас 2.19.0.
- **Штамп** — маркер `wolf:rendered … set=X.Y.Z` в штампованном файле;
  версия base-set проекта.
- **Лицо (face)** — версионный плейбук агента в памяти проекта; канонический
  источник доставок. Активное лицо с `owner_skill = <agent-id>` делает доставку
  канонической вместо fallback.
- **Посев / досев** — создание лицом v1 из шаблона `templates/base/playbooks/`
  (инициатор seed): недостающие сеются, живые не перезаписываются, legacy-head
  поглощается атомарно (механика 2.17.1).
- **Карта обновления** — версионируемый полный манифест состава релиза
  (инвентарь артефактов) с категориями new / changed / deprecated / removed
  относительно предыдущего релиза + инструкции посева лиц; источник истины
  СОСТАВА набора — сверка работает с любой исходной версии проекта, дельты
  промежуточных релизов не компонуются. Штамп `set=` — только свидетель
  касания, не манифест (может отражать версию запускавшего бинарника,
  инвентаризация §3.4).
- **Пиннинг** — удержание проекта вне обновлений флагом `pinned: true` в
  записи реестра (REQ-13); самолечение P331 флаг уважает. Снятие регистрации
  пиннингом не является (запись будет дописана обратно).
- **Worktree-скоп** — запись реестра, указывающая на git-worktree (путь под
  `.worktrees/` или git common-dir ≠ toplevel); обновление чужого рабочего
  checkout по умолчанию пропускается.
- **Самообновление** — `npm i -g mister-wolf@latest`, выполняемый командой
  `wolf upgrade` (уже реализовано, включая `--check` и отказ для
  linked-установок).
- **Linked-установка** — запуск wolf из репо/`npm link`; самообновление для
  неё честно отказывает.

## 4. Функциональные требования

### REQ-01 — Единая команда обновления «всё сразу»

- История: Как владелец парка проектов, я хочу одной командой обновить и CLI,
  и все зарегистрированные проекты, чтобы обновление перестало быть ручной
  работой на каждый проект и релиз.
- Требование: Когда пользователь запускает `wolf upgrade` в глобальной
  установке и в реестре есть проекты, система должна после фазы самообновления
  CLI предложить обновить все проекты реестра и при подтверждении выполнить
  проход по ним.
- Обоснование: парк отстаёт на 5 релизов не потому, что обновление
  невозможно, а потому что оно ручное и многошаговое; единая команда —
  единственный путь, которым парк вообще будет обновляться.
- AC:
  - Given реестр из ≥1 живого проекта и доступный npm, When `wolf upgrade`
    завершён с подтверждением, Then CLI на latest-версии и каждый
    подтверждённый проект соответствует карте релиза (строгая сверка REQ-11);
    штампы `set=` обновлены до latest — как свидетель касания, не как
    манифест состава (инвентаризация §3.4); исключения — файлы со статусом
    «требует решения» из skipped-mutated (мутации не перезаписываются,
    REQ-03/REQ-11) и пропущенные worktree-скопы / pinned-проекты
    (REQ-02/REQ-13).
  - Given пустой реестр, When `wolf upgrade`, Then CLI обновлён, выведено
    «зарегистрированных проектов нет» (с подсказкой `wolf projects`), выход 0.
  - Given npm-фаза не удалась (нет сети/прав), Then CLI и проекты не изменены
    (проектный проход не выполняется — полный отказ), exit ≠ 0.
- Приоритет: Must
- Источник: решённые вводные владельца 2026-10-23; тред
  mem_20261023_volna_2_19_0_unified_update_odno_obnovle_15b75a

### REQ-02 — Список проектов и подтверждение до любых изменений

- История: Как владелец парка, я хочу до изменений увидеть, какие проекты
  будут обновлены и с каких версий, чтобы решение было осознанным.
- Требование: Когда фаза самообновления CLI завершена, система должна
  вывести список проектов реестра (имя, путь, целевая версия, сводку
  категорий карты — new / changed / deprecated / removed, удаления явно)
  и запросить подтверждение; не-интерактивно — флаг `--yes` применяет
  список без вопросов. Worktree-скопы (запись реестра — путь под
  `.worktrees/`, либо git common-dir ≠ toplevel) и pinned-проекты (REQ-13)
  показываются в списке со статусами `worktree` / `pinned` и по умолчанию
  пропускаются: sync в чужом рабочем checkout создал бы незакоммиченные
  изменения; pinned — осознанное исключение владельца.
- Обоснование: проход меняет файлы в чужих репозиториях; граница «только
  реестр» осмысленна лишь тогда, когда пользователь видит, кого трогает.
- AC:
  - Given TTY, When список выведен и подтверждение отклонено, Then проекты не
    изменены (изменён только CLI), выход 0.
  - Given `--yes`, When список выведен, Then проход выполняется без
    интерактивного вопроса.
  - Given не-TTY запуск без `--yes`, When список выведен, Then проектный
    проход пропускается (обновлён только CLI), выход 0.
  - Given проект из реестра с несуществующим путём, Then он показан в списке
    как `missing` и пропущен без остановки прохода.
  - Given worktree-скоп в реестре, When список выведен и проход подтверждён,
    Then скоп показан со статусом `worktree` и не изменён.
- Приоритет: Must
- Источник: решённые вводные 2026-10-23 (граница реестра, пиннинг);
  прецедент `wolf uninstall` (план → `--yes`); ревью 2026-10-23 — F1
  (worktree-скопы), F8 (не-TTY без --yes)

### REQ-03 — Per-project шаг: sync base-set + досев недостающих лиц

- История: Как владелец проекта, я хочу, чтобы обновление доводило проект до
  полной работоспособности новой версии — файлы И лица, чтобы доставки
  агентов стали каноническими без ручного re-init.
- Требование: Когда проект подтверждён к обновлению, система должна выполнить
  для него (а) перерисовку base-set с семантикой `wolf sync` (штампованные
  файлы; мутированные — пропуск с указанием), и (б) досев базовых лиц с
  семантикой init-посева: недостающие — сеять, живые лица — не перезаписывать,
  legacy-head — поглощать атомарно одной операцией.
- Обоснование: это закрывает корневой пробел, дающий 91% fallback-промахов —
  «init до появления шаблона, sync не сеет»; без досева обновление снова
  оставит проект без лиц.
- AC:
  - Given проект со штампами 2.16.2 без лица executor-lead, When проект
    обновлён до 2.19.0, Then штампы файлов = `set=2.19.0` и в памяти проекта
    есть активное лицо executor-lead с `owner_skill=executor-lead`
    (инициатор seed).
  - Given проект с живым (активным) лицом воркера, When проход завершён,
    Then это лицо не изменено и не переверсионировано.
  - Given проект с legacy-записью владельца без лица, When проход завершён,
    Then посеяно лицо v1 и legacy-head поглощён (supersede) атомарно, дублей
    кандидатов для доставки нет.
  - Given мутированный пользователем штампованный файл, When проход завершён,
    Then файл не перезаписан и перечислен в отчёте проекта как
    skipped-mutated.
- Приоритет: Must
- Источник: расследование ts-update 2026-10-23 (H2, §3.2, §6); механика
  seedBasePlaybooks (2.17.1)

### REQ-04 — Проход по проектам выполняется новой версией CLI

- История: Как владелец, я хочу, чтобы после обновления проекты получили
  base-set и лица именно новой версии, чтобы повторный запуск не понадобился.
- Требование: Когда самообновление CLI завершилось установкой новой версии,
  система должна выполнить проектный проход средствами уже новой версии
  (штампы и шаблоны лиц — новой версии), а не кодом запущенного старого
  бинарника.
- Обоснование: `wolf upgrade` стартует старым кодом; проход старым кодом
  посеял бы старые шаблоны и старые штампы — видимая видимость обновления без
  его содержания.
- AC:
  - Given обновление 2.18.5 → 2.19.0, When проход завершён, Then штампы
    обновлённых проектов = 2.19.0, посеянные лица — из шаблонов 2.19.0, а
    состав набора подтверждён картой релиза (REQ-11) — штамп лишь свидетель
    касания.
  - Given `--check` (без установки), Then проектный проход не выполняется
    вовсе.
- Приоритет: Must
- Источник: исследование механики memory-upgrade.ts (запуск из старого
  бинарника), 2026-10-23

### REQ-05 — Сводный отчёт по парку

- История: Как владелец, я хочу итог в одну экранную страницу — что
  обновлено, что пропущено и почему, — чтобы не разбирать логи каждого
  проекта.
- Требование: Когда проход завершён, система должна вывести сводный отчёт:
  версию CLI (from → to), по каждому проекту статус (updated / up-to-date /
  skipped-mutated = «требует решения» / worktree / pinned / error / missing)
  и число досеянных лиц, итоговые счётчики — включая счётчик «требует
  решения» и счётчики по категориям карты обновления (new / changed /
  deprecated / removed — REQ-11). Отчёт рендерится стандартом терминального
  вывода REQ-15 (styled в TTY, plain вне TTY — данные идентичны).
- Обоснование: «обновил всё» должно быть проверяемо одним взглядом; молчание
  о пропусках (мутации, ошибки) — это скрытый частичный успех.
- AC:
  - Given проход по 3 проектам (один актуален, один с мутацией, один с
    ошибкой), When завершён, Then отчёт различает все три исхода, итог
    содержит счётчики: обновлено 1, актуально 1, «требует решения» 1, ошибок
    1, и число досеянных лиц суммарно.
  - Given подтверждённый проход, в карте 2 removed и 1 deprecated, When
    завершён, Then счётчики категорий показывают removed: 2, deprecated: 1.
- Приоритет: Must
- Источник: бриф волны 2026-10-23; FRICTION-опыт ручного обновления парка

### REQ-06 — Изоляция сбоев per-project

- История: Как владелец парка, я хочу, чтобы ошибка одного проекта не
  останавливала обновление остальных, чтобы один битый репозиторий не держал
  весь парк на старой версии.
- Требование: Когда проектный шаг завершается ошибкой, система должна
  зафиксировать её в отчёте проекта и продолжить проход; итоговый код выхода
  ненулевой при ≥1 error ИЛИ ≥1 статуса «требует решения» (skipped-mutated,
  REQ-11), иначе 0.
- Обоснование: парк неоднороден (чужие репо, worktree-скопы, missing-пути);
  отказ всего прохода из-за одного проекта повторяет нынешнюю ручную боль.
- AC:
  - Given 2 проекта, первый бросает исключение, When проход завершён, Then
    второй проект обновлён, отчёт помечает первый как error с причиной, exit
    code = 1.
  - Given 0 ошибок и ≥1 пункт «требует решения» (мутированный файл), Then
    exit ≠ 0.
  - Given все проекты успешны и пунктов «требует решения» нет, Then exit
    code = 0.
- Приоритет: Must
- Источник: бриф волны 2026-10-23 (обработка сбоев — явная вводная)

### REQ-07 — Память нетронута вне посева (инвариант проектного шага)

- История: Как владелец, я хочу уверенности, что обновление файлов не
  трогает память кроме явного посева, чтобы граница «посев — только
  осознанный шаг» сохранилась.
- Требование: Проектный шаг `wolf upgrade` (проход по реестру и режим
  `--here`, REQ-14) не создаёт, не изменяет и не удаляет объекты памяти
  (включая лица), кроме посева новых лиц по инструкциям карты (REQ-03).
  `wolf sync` как deprecated-алиас (2.19.0) сохраняет прежнюю семантику до
  удаления в 2.20.0: память не трогает, посев не выполняет; после удаления
  команда-алиас исчезает без замены.
- Обоснование: D4 (лица — зона Стюарда/явного посева); единая точка
  обновления не должна молча мутировать память; алиас уходит без изменения
  контракта, чтобы миграция была предсказуемой.
- AC:
  - Given проект, When выполнен deprecated-алиас `wolf sync`, Then множество
    id объектов памяти (сравнение множеств, не только счётчиков) не
    изменилось, выведена подсказка-перенаправление на `wolf upgrade`.

- Требование: Проход не должен приводить к потере объектов памяти или
  пользовательских правок штампованных файлов ни при каком исходе (успех,
  частичный сбой, прерывание по Ctrl-C на середине парка).
- AC: Given прерывание прохода после k-го проекта, Then в каждом проекте
  число объектов памяти не меньше, чем до прохода, а мутированные файлы
  не перезаписаны (сравнение слепков до/после на тестовом парке).
- Источник: бриф волны (безопасность как явная NFR-вводная)

### NFR-02 — Идемпотентность повторного запуска

- Требование: Повторный запуск `wolf upgrade` сразу после успешного не должен
  создавать дубликаты лиц/объектов или переписывать актуальные проекты.
  Per-project шаг атомарен пофазно: sync base-set и посев лиц — раздельные
  фиксируемые шаги (сбой посева не откатывает sync и наоборот), повторный
  запуск доводит незавершённое.
- AC:
  - Given два последовательных запуска на одном парке, Then второй показывает
    все проекты как up-to-date/актуально: 0 новых объектов памяти, 0
    перезаписанных файлов, exit 0.
  - Given проход прерван (сбой/Ctrl-C) на k-м из N проектов, When запуск
    повторён, Then проекты до точки сбоя не перезаписаны (up-to-date),
    остальные доведены до конца, дубликатов лиц/объектов нет.
- Источник: механика init-посева (идемпотентность 2.17.1); бриф волны

### NFR-03 — Приемлемое время на парк

- Требование: Проектный шаг (перерисовка base-set + посев лиц + строгая
  сверка по карте, REQ-11) должен укладываться в интерактивно приемлемое
  время: весь проход без npm-фазы по парку до 20 проектов — не более 3 минут
  на рабочей машине владельца; скан REQ-09 — вне этого бюджета.
- AC: Приёмка на реальном парке (4 проекта) — проход завершается за ≤ 40 с;
  per-project шаг (render + посев + сверка по карте) — ≤ 7 с в среднем
  (замер вручную, фиксируется в приёмочном отчёте).
- Источник: бриф волны (время на парк 4–20 проектов); правка r3 — бюджет
  пересчитан с учётом сверки по карте (REQ-11)

### NFR-04 — Observability без нового канала логирования

- Требование: Наблюдаемость прохода обеспечивается существующими
  механизмами: stdout-отчёты, events.jsonl посева (actor=seed/initiator),
  router.log доставок. Новые лог-каналы/форматы не вводятся.
- AC: После прохода факт посева каждого лица виден в events.jsonl проекта
  стандартными событиями face-журнала; никаких новых файлов логов в `.wolf/`
  не появляется.
- Источник: решение владельца о составе 2.19.0 (логирование → 2.20.0)

## 6. Ограничения и допущения

- **Граница обновления — только реестр** (решение владельца
  mem_20261023_sostav_2_19_0_i_granitsa_obnovleniya_tol_906915). Пиннинг —
  флаг `pinned: true` в записи реестра (REQ-13, решение владельца по ОВ-6);
  снятие регистрации пиннингом не является (самолечение P331 допишет запись
  обратно). Фикстуры/полигоны покрываются общим пиннингом (ОВ-7 закрыт).
- **Карта — источник истины состава** (решение владельца): штамп `set=` —
  только свидетель касания (инвентаризация §3.4: штампы 2.17.0 при составе
  2.18.0 в живом парке). Сверка прохода — по карте (REQ-11), штампы
  вторичны. Карта действует на файловые артефакты base-set: существующие
  объекты памяти по карте не удаляются и не депрекейтятся; единственная
  мутация памяти прохода — посев новых лиц по инструкциям карты (REQ-03,
  согласовано с REQ-07/D4).
- **Реестр**: пишут `wolf init` и самолечение P331 (любая wolf-команда в cwd
  проекта с живой памятью дописывает запись; best-effort). Субкоманды
  `wolf projects add` нет; подсказка REQ-09 ведёт к запуску wolf-команды в
  проекте, а не к новой субкоманде. Принудительный бэкфилл — не-цель.
- **Самообновление уже реализовано**: `wolf upgrade` выполняет
  `npm i -g mister-wolf@latest` изнутри CLI (спавн npm), отказывает для
  linked-установок, `--check` — read-only. 2.19.0 расширяет команду, новое
  имя не вводится (конвенция: короткие однословные top-level команды).
- **`wolf sync` — deprecated-алиас 2.19.0** (решение владельца): выполняет
  прежнее действие + подсказку-перенаправление на `wolf upgrade`; удаление в
  2.20.0. Ручной путь обновления — `wolf upgrade --here` (REQ-14).
  CHANGELOG-upgrade-заметки начиная с 2.19.0 указывают `wolf upgrade`, не
  `wolf sync`.
- **Порядок фаз обязателен**: сначала CLI, потом проекты новой версией
  (REQ-04). Если npm-фаза не удалась (нет сети/прав) — полный отказ без
  проектного прохода (решение владельца по ОВ-4, окончательно: «одно
  обновление обновляет всё», частичный проход запутывает).
- **Субкоманда `wolf projects add` не вводится** (ОВ-2 закрыт): регистрации
  достаточно самолечения P331 + подсказки REQ-09; новая субкоманда — лишняя
  поверхность.
- **`--check` вместо `--dry-run`** (ОВ-3 закрыт, подтверждено владельцем):
  read-only проверку даёт расширенный `--check` (REQ-08); отдельный
  dry-run-флаг не вводится.
- **Не исправляем дефекты данных**: superseded-объекты и дубли без
  `owner_skill` конвейер обновления не лечит — это ручная/Стюард зона;
  B0-нарушения подсвечиваются в отчёте (conflict), как в init. (Кейс
  executor-lead в mister-wolf закрыт Стюардом 2026-10-23 — лицо
  восстановлено, resolve=canonical; чистка v2-note-дубля — вне волны 2.19.0,
  зона Стюарда, ОВ-5 закрыт.)
- **Таксономия config.yaml** — обновляется ручной `wolf taxonomy`, в
  автоматический проход не входит; карта декларирует её как класс вне
  покрытия v1 (инвентаризация §3.5/§4, кандидат будущих волн).
- **Живые сессии в обновляемом проекте**: агенты в открытых сессиях доигрывают
  на уже загруженной (старой) версии плагина — это ожидаемо и безопасно: посев
  пишет новые объекты памяти, конфликтов записи нет. Вывод прохода
  предупреждает: канонические доставки вступают в силу для новых сессий.
- **Шаблоны и версии**: package.json — единственный источник версии
  (правило памяти); все номера версий полные X.Y.Z; штампы `set=` пишутся
  версией выполненного прохода.
- **Платформа**: macOS/одна машина/один пользователь; реестр и скан REQ-09
  локальны; сетевые/мультиюзерные сценарии вне области.
- **Документация и сайт**: релизный чек-лист (README/docs/сайт/CHANGELOG,
  страница Changelog синхронна через docs:build) раскрывается разделом
  «Документация и сайт» на этапе плана волны — обязательный по правилам
  памяти; в требованиях фиксируется только его необходимость (см. CR). Шаг
  карты обновления (REQ-12) входит в этот же релизный чек-лист.
