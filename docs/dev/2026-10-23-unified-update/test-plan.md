# unified-update — тест-план

Волна 2.19.0. Входы: requirements.md (approved, 15 REQ / 46 AC / 4 NFR),
design.md (approved, 6 ADR), plan.md (approved, T1–T15, 6 фаз; журнал).
Baseline: main `db2d280`. План описывает что/как/где проверять; тесты
пишут исполнители фаз по TDD (чувствительная к дефекту проверка — до
реализации поведения). Oracle — AC/инварианты/design, не предложенный
код.

## Стратегия и уровни

| Уровень        | Что покрывает                                                                                                                                        | Средства                                        |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| Юнит           | Движок сверки, renderer (plain-оракул + TermEnv-фейки), pinned/гварды, exit-модель, seed-missing-only ветки, генератор карты + guard, spawn-контракт | vitest, tmp-каталоги                            |
| Интеграционный | Проектный шаг и проход на фикстурном парке (tmp-проекты с .wolf), скан, --here, --check, депрекация sync, идемпотентность/прерывание                 | vitest + фикстуры парка, изолированный HOME/XDG |
| e2e            | Сквозные сценарии поверхностей CLI (вкл. re-exec-паттерн), гейт влитий                                                                               | `npm run e2e` (таймаут ≥ 1200 с)                |
| Ручная приёмка | Реальный npm/latest, реальный TTY (styled), реальный парк, тайминги NFR-03                                                                           | процедуры в разделе «Ручные процедуры»          |

Изоляция: все тесты с реестром/памятью — только tmp (ОС-tmp
opencode-каталог или фикстурный root); изоляция через env
(XDG_CONFIG_HOME/HOME на tmp — по прецедентам существующих e2e). Реальных
секретов и внешних побочных действий нет; npm-сеть в авто-тестах
мокируется/пропускается.

## Решение вопроса плана №1 — e2e-паттерн re-exec

Вопрос: как тестировать спавн нового бинарника из старого без реального
`npm i -g`. Решение (три уровня, фиксируется здесь; отметить в T8):

1. **Контракт spawn — юнит с фейковым бинарником.** В точке spawn путь
   ребёнка берётся из env `WOLF_UPGRADE_CHILD_BIN` (дефолт —
   `<npmPrefix>/bin/wolf`; env существует только для тестового контура,
   продуктовое поведение не меняет). Тест T8 подставляет Node-стаб:
   пишет маркер argv/state в tmp, эмулирует exit 0/1/2 и сбой старта
   (ENOENT). Проверяются: argv (`upgrade-projects --no-banner --state …`),
   stdio inherit (наследует те же fd), env: process.env, проксирование
   exit-кода, сбой spawn → UserFacingError «CLI обновлён; проекты не
   тронуты — повтори wolf upgrade» + exit 1.
2. **Само-спавн smoke (e2e).** `WOLF_UPGRADE_CHILD_BIN` указывает на
   текущий `dist` wolf: реальный бинарник запускается как ребёнок,
   наследует stdio/env, `upgrade-projects --help`-режим завершается 0 —
   доказывает жизнеспособность транспорта на реальном артефакте.
3. **Сквозной проход — e2e фазы 2 напрямую.** Полный проход по
   фикстурному парку вызывает `upgrade-projects` (фаза 2) минуя npm:
   фаза 1 уже покрыта уровнями 1–2 и существующими тестами npm-фазы.
   Реальный «старый→новый» переход — ручная приёмка (чек-лист п.9
   плана).

Downstream T8 (отметить в брифе задачи): задокументировать env
`WOLF_UPGRADE_CHILD_BIN` в design §«Контракт spawn» при следующей
ревизии + комментарий в коде в точке spawn.

## Фикстуры

### Фикстурный парк (генерация в tmp на каждый прогон)

| ID              | Состояние                                                           | Ожидание прохода                                                                                |
| --------------- | ------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| P-clean         | `.wolf/memory` живая; base-set `set=2.17.1`; лица executor-lead нет | updated + seeded(executor-lead), exit 0                                                         |
| P-mutated       | штампованный файл с ручной правкой (контент ≠ рендер)               | skipped-mutated → «требует решения», файл не тронут, exit 2                                     |
| P-pinned        | запись реестра `pinned: true`                                       | статус pinned, файлы/память не тронуты                                                          |
| P-worktree      | путь под `.worktrees/` (git-фикстура: common-dir ≠ toplevel)        | статус worktree, не изменён                                                                     |
| P-missing       | путь записи не существует                                           | статус missing, проход продолжается                                                             |
| P-diverged      | лицо с initiator ≠ seed/migration, тело ≠ шаблону                   | diverged → «требует решения»                                                                    |
| P-legacy        | legacy-head без живого лица                                         | seeded v1 + legacy-absorbed (supersede атомарно)                                                |
| P-future-schema | `schema_version` выше текущей                                       | error пункта, обход продолжается (открытый вопрос дизайна №2 — предложение закрепляется тестом) |
| P-unregistered  | живая `.wolf/` вне тестового реестра (для REQ-09)                   | найдена сканом, реестр не изменён                                                               |

Карта для фикстур — тестовый `update-map.json` (мини-инвентарь: 2–3
FileEntry по категориям new/changed/deprecated/removed + 1–2 FaceEntry
с seed); deprecated-цель с живым лицом и removed-цель входят в
мини-карту (фикстуры для R11.4/R11.2; носитель — P-clean). Читается
загрузчиком T1 (инжект packageRoot на фикстуру — тестовый контур).

### Тестовый реестр и изоляция

Реестр — tmp `projects.yaml` с P-clean/P-mutated/P-pinned/P-worktree/
P-missing (+ дубликат realpath для дедупа, битый-yaml вариант для
гварда). Изоляция env (HOME/XDG_CONFIG_HOME → tmp) по прецедентам
существующих e2e. Прерывание: интеграционный сценарий убивает процесс
прохода (SIGINT) после k-го проекта — детерминированный механизм:
поллинг файл-маркера k-го проекта → kill (без таймингов; бриф T13),
затем повторный запуск.

### Слепки (NFR-01/02)

До/после прохода: множество id объектов памяти каждого проекта + SHA
мутированных файлов + состав base-set. Хелпер слепка — общая
тест-утилита волны (`tests/helpers/park-snapshot.ts`, новый);
используется и в идемпотентности (повторный прогон: 0 новых объектов, 0
перезаписей).

Владельцы фикстур (назначение): T6 — фикстуры проекта + хелпер слепка
`tests/helpers/park-snapshot.ts`; T7 — парк реестра +
`integration/upgrade-park.test.ts`.

## Негативные и граничные сценарии (сводно)

- Битый `projects.yaml` (не-валидный yaml) → error + exit 1, НЕ «пустой
  реестр» (T4, юнит гварда).
- Карта из будущего (version карты > версии CLI) → загрузчик честный
  error пункта/команды, не молчаливое использование (T1, юнит).
- Пустой реестр (R01.2) и реестр из одних worktree/pinned (прогон без
  изменений, exit 0, статусы в отчёте) — T7.
- Сброс/нет сети в npm-фазе (R01.3) — мок-отказ npm.
- Скан REQ-09 недоступен (права) → молча (R09.2).
- Дубликат realpath в реестре → дедуп, одна запись в плане, дубль в
  отчёте (T4/T7).
- Прерывание SIGINT посреди парка (N01.1/N02.2) — хук k-го проекта.
- deprecated-файл удалён вручную до прохода → пункт получает
  «требует решения» (факт ≠ ожиданию), не error (T5, таблица кодов).

## Приёмка волны

1. Гейт каждого влития в main: полный `npm run check` + полный
   `npm run e2e` (таймаут ≥ 1200 с) — lead (T13).
2. Сквозной прогон фикстурного парка (P-clean/mutated/pinned/worktree/
   missing/diverged/legacy) — счётчики/exit 0/1/2, повторный прогон —
   идемпотентность; автозапись wall-time per-project.
3. Слепки NFR-01/02 в артефакт приёмки (docs/dev/2026-10-23-unified-
   update/acceptance.md): множества id, SHA, тайминги, счётчики.
4. Ручные процедуры (ниже) + приёмка на реальном парке — чек-лист
   плана п.9 (пост-релиз).
5. flake-политика: единичный wall-таймаут под нагрузкой → изолированный
   реран + один полный повтор; повторяемый красный — фикс, не ретрай.

## Ручные процедуры

- **R12.1/R12.2 (карта в релизе):** прогон чек-листа релиза: генератор
  скелета → курирование → `node scripts/generate-update-map.mjs --verify`
  (exit 0) → карта в `files` → `npm pack --dry-run | grep update-map` —
  результат фиксируется в release-отчёте.
- **R15.1 (styled в реальном TTY):** в живом терминале `wolf upgrade
--check | cat` (plain) против `wolf upgrade --check` (styled): данные
  идентичны, styled имеет рамки/логотип/цвет; скрин в приёмку.
- **N03.1 (тайминги):** на реальном парке (4 проекта) — `time wolf
upgrade --yes` после `npm i -g` вручную; per-project тайминги из
  отчёта прогона; результат ≤ 40 с / ≤ 7 с среднее — в приёмочный отчёт.
- **R10.1 (публикация):** после `npm publish` — распаковка tarball 2.19.0:
  update-map.json присутствует, version = 2.19.0.

## Открытые вопросы

1. Точная изоляция e2e реестра (env vs параметр CLI) — берётся из
   прецедентов существующих e2e на первой задаче, их трогающей (T4);
