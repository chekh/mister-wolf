# 1. REQ-332-1 — инстанс без межвызовного кэша (unit, T-1.x)

- T-332-1.1 (AC-1.1): инстанс → `suppressions()`; внешний append строки suppression
  в файл (прямой writeFileSync, имитация другого процесса) → тот же инстанс
  `suppressions()` содержит новую запись. Красный на базе (кэш).
- T-332-1.2 (AC-1.2): внешний append → `resolveSuppression(newId, …)` тем же
  инстансом успешен; второй resolve — «unknown or already resolved».
- T-332-1.3 (AC-1.3): внешний append записи с id X → `recordSuppression(…id X)`
  тем же инстансом отказывает (дубликат виден); с новым id — успешен.
- T-332-1.4 (AC-1.4): внешний append observation → `setObservation` того же
  инстанса мержит поверх внешнего значения; `observations()` возвращает
  актуальное.
- T-332-1.5 (AC-1.1, deliveries): внешний append delivery → `deliveries()` того же
  инстанса видит строку.

# 2. REQ-332-2 — общий корень (unit-адаптер + integration, T-2.x)

Реализация сценариев — реальный git: `git init` main + `git worktree add`
(child_process, как в живом стенде; tmp-каталоги, очистка в afterEach).

- T-332-2.1 (AC-2.1): журнал в main (запись suppression через инстанс от main);
  инстанс, созданный ОТ ПУТИ worktree, `suppressions()` видит ту же запись;
  use-case доставки с noteLog от worktree не доставляет подавленную заметку.
  Красный на базе (журнал уходит в wt/.wolf).
- T-332-2.2 (AC-2.2): инстанс от worktree регистрирует suppression → инстанс от
  main видит её в `suppressions()` (симметрия).
- T-332-2.3 (AC-2.3): resolve из worktree-инстанса снимает запись для main-инстанса.
- T-332-2.4 (AC-2.4): фикстура legacy `index.sqlite` (tests/fixtures/micro-note-index-330)
  в main-чекоуте, файла журнала нет; первый вызов из worktree-инстанса
  выполняет миграцию в ОБЩИЙ корень (журнал появляется в main/.wolf/memory).
- T-332-2.5 (AC-2.5): не-git каталог и обычный чекаут: путь журнала = сам каталог

  изменений путей).

# 3. REQ-332-3 — граница записи (unit, T-3.x)

- T-332-3.1 (AC-3.1): файл с валидными строками + обрывок хвоста
  (`{"kind":"suppression","record":{"suppression_id":"cnr_trunc`) →
  `recordSuppression` успешен; полное чтение (`suppressions()`/`deliveries()`)
  без ошибок; обрывок не присутствует в файле.
- T-332-3.2 (AC-3.2): валидная строка без `\n` (готовая запись JSON + no newline) →

- T-332-3.3 (AC-3.3): обрыв хвоста → report-сценарий (record+resolve) полностью
  успешен; повторное чтение отдельным инстансом (свежие глаза) — без ошибок;
  в файле нет невалидных строк.
- T-332-3.4 (AC-3.4): невалидная строка в середине файла → `UserFacingError`

- T-332-3.5: файл пуст/нет директории → запись создаёт директорию и файл

# 4. Сквозной сценарий приёмки (главный критерий ревьюера)

Живой стенд (повтор воспроизведения ревьюера на исправленной сборке):

1. main-чекоут + linked worktree одного проекта с micro-note.
2. Подавление через CLI в main → `brief` в linked worktree НЕ содержит заметку;
   `contradict list` из worktree показывает запись.
3. «Запущенный процесс» (механизм MCP = один инстанс на процесс): скрипт,
   держащий инстанс журнала, видит CLI-report, сделанный после его создания,
   и успешно resolve-ит новый id (стенд d1.mjs).
4. Обрыв строки → CLI report успешен → brief/list работают, файл валиден.
5. Все ответы трёх каналов согласованы (одинаковый список открытых записей).
