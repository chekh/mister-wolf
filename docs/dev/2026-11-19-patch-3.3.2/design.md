# 1. Носитель изменений

Все три дефекта чинятся внутри `src/adapters/fs/jsonl-micro-note-delivery-log.ts`
и его тестов; точки входа (CLI/MCP) остаются без изменений. Контракты
(`MicroNoteDeliveryLog`-порт, формат строки журнала, CLI/MCP-поверхность) не
меняются.

# 2. ADR-332-1 (REQ-332-1): чтение состояния на каждую операцию, кэша нет

`load()` перестаёт выходить по флагу `loaded`: каждый публичный вызов
(`suppressions()`, `recordSuppression()`, `resolveSuppression()`,
`deliveries()`, `recordDelivery()`, `observations()`, `setObservation()`)
перечитывает файл и строит состояние заново (три коллекции очищаются и
наполняются заново). Триггер миграции сохраняется: файла нет →
`migrateLegacy()` (проверка `existsSync` дешёвая, идемпотентность по факту
существования файла не меняется).

Рассмотренные альтернативы (отклонены):

- Инвалидация по mtime/size — сложность и остаточная гонка (изменившийся файл
  того же размера в ту же секунду); выигрыш несущественен.
- FS-watcher в адаптере — новый механизм ради микрокэша; файл журнала мал,
  операции доставки и так делают более тяжёлый I/O (sqlite, скан проекта).

Стоимость: одно чтение малого файла + парс строк на операцию журнала; операции
журнала и так сопровождаются записью. Память процесса не растёт (состояние
перестраивается, а не копится).

# 3. ADR-332-2 (REQ-332-2): общий корень резолвит сам адаптер

Конструктор адаптера сохраняет сигнатуру `(baseDir)`, но внутри резолвит общий
корень памяти `resolveMemoryRoot(baseDir).root` и использует его для пути
журнала (`<root>/.wolf/memory/micro-note-delivery.jsonl`) и для поиска legacy
`index.sqlite` (`indexPath(root)`).

Обоснование выбора «внутри адаптера», а не правки четырёх точек входа:
устраняется целый класс ошибок — любая будущая точка входа не сможет передать
локальный путь; текущие четыре сайта (`memory-brief.ts`, `memory-call.ts`,
`memory-contradict.ts`, `mcp-tools.ts`) не меняются вовсе. Вне linked worktree
`resolveMemoryRoot(baseDir).root === baseDir` — поведение существующих проектов
не меняется (AC-2.5), повторной миграции нет (файл журнала уже в общем корне,
который для них совпадает с прежним путём).

MCP-сервер: инстанс по-прежнему один на процесс — после ADR-332-1 это
корректно: каждая операция читает актуальное состояние файла.

Правило идемпотентности миграции не меняется: признак выполненной миграции —
существование файла журнала В ОБЩЕМ КОРНЕ.

# 4. ADR-332-3 (REQ-332-3): repair-on-write

`append()` перед записью приводит хвост файла к границе последней корректной
строки:

1. Файла нет — просто создаём (как сейчас).
2. Файл заканчивается `\n` — граница корректна, пишем как сейчас.
3. Хвост после последнего `\n` (или файл целиком без `\n`):
   - хвост разбирается как валидная строка журнала — это полная запись без
     завершающего `\n` (обрыв ровно между записью и newline): финализируем —
     дописываем `\n`, запись не теряется (AC-3.2);
   - хвост не разбирается — обрывок частичной записи: обрезаем файл
     (`truncateSync`) до границы последнего `\n` (или до нуля, если `\n` нет),
     затем дописываем новую строку (AC-3.1).

Чтение (`load()`) не меняется: незавершённая последняя строка прощается,
битая строка в середине — `UserFacingError` с именованной причиной (AC-3.4).
Так подтверждённая запись не может оставить файл нечитаемым (AC-3.3):
после любого успешного `append` файл — последовательность полных строк.

Принятое ограничение: read-modify-truncate в `append` не под замком — гонка
двух одновременных appender'ов остаётся вне скоупа (см. requirements §3),
как и в 3.3.1.

# 5. Совместимость и откат

- Формат файла не меняется: журнал, созданный 3.3.1, читается 3.3.2 без
  миграции; откат на 3.3.1 — чтение того же файла (обрывок хвоста 3.3.1
  прощает только в позиции последней строки).
- Доставка/подавление между 3.3.1 и 3.3.2 в обычном чекауте поведенчески
  эквивалентны; в linked worktree 3.3.2 «подхватывает» общий журнал main.
- Откат релиза: возврат на тег v3.3.1, журнал данных не теряет (формат один).
