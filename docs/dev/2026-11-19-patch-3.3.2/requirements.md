# 1. Цель

Закрыть три дефекта пост-релизного ревью v3.3.1 (вердикт владельца
CHANGES*REQUIRED, 2026-11-19): D1 (P1) — долгоживущий процесс (MCP-сервер)
не видит изменения журнала, сделанные другими процессами; D2 (P1) — linked
worktree читает/пишет собственный журнал вместо общего корня памяти;
D3 (P2) — запись после оборванной последней строки делает журнал нечитаемым.
Все три дефекта воспроизведены ведущим на опубликованном коде v3.3.1
(стенд `/private/var/folders/p*/p7msymwd55vbzp44kkmnbc3w0000gn/T/opencode/repro-332`,
доказательства в файлах 21–42). Исправления идут от базы `9de0f6f9` (тег v3.3.1).

**Главный критерий приёмки релиза — дословные сценарии ревьюера:**

> Общая память должна давать одинаковый ответ из CLI, запущенного MCP и linked
> worktree. После обрыва записи команда должна либо безопасно продолжить работу,
> либо явно отказать до подтверждения успеха.

Требования патча 3.3.1 (`docs/dev/2026-11-18-patch-3.3.1/requirements.md`,
REQ-331-1..5) остаются в силе; патч 3.3.2 не меняет контракты адресации
(`resolve --id`) и носитель (append-only JSONL) — он восстанавливает
семантику 3.3.0 «один журнал на проект» на новом носителе и добавляет
самовосстановление записи.

Активные ограничения:

- REQ-03 «unknown stays unknown» действует (неразличение неизвестного и
  разрешённого id сохраняется).
- Контракт CLI (`wolf contradict report|resolve|list`) и MCP
  (`note_contradiction`) не меняется; каталог 10 тулов ≤ 12 не растёт.
- Формат журнала (строка = `{kind, record}`) не меняется; семантика миграции
  ADR-3 сохраняется (существование файла журнала — признак выполненной
  миграции; legacy-строки в index.sqlite — замороженная копия).
- Замороженные legacy-строки остаются прямыми чтениями вне публичного контракта.

# 2. Требования (REQ) и критерии приёмки (AC)

Каждая REQ имеет контрактом регрессионный тест: на базе `9de0f6f9` он красный
(дефект воспроизведён на стенде), после исправления — зелёный.

## REQ-332-1 (D1, P1) — инстанс журнала не кэширует состояние между операциями

Существующее поведение (дефект): `load()` выходит по флагу `loaded`
(`src/adapters/fs/jsonl-micro-note-delivery-log.ts:55-57`, v3.3.1) — инстанс,
созданный при старте долгоживущего процесса (MCP-сервер держит один инстанс,
`src/adapters/mcp/mcp-tools.ts:173`), читает файл один раз за жизнь процесса.
Записи, добавленные другим процессом (CLI), невидимы: brief доставляет заметку
с открытым противоречием, а resolve нового id отвечает «unknown». Воспроизведено
(стенд 30-d1: before=1, внешний report ok, after=1, resolveErr=unknown).

- AC-1.1: инстанс журнала после внешнего добавления записи (другой процесс)
  возвращает актуальный список подавлений без перезапуска процесса.
- AC-1.2: resolve id, добавленного другим процессом, успешен тем же инстансом.
- AC-1.3: проверка дубликата id в `recordSuppression` видит записи, добавленные
  другими процессами (повтор id → отказ, retry с новым id — успех).
- AC-1.4: наблюдения (observations) сливаются с внешними изменениями по тем же
  правилам, что и в пределах одного процесса.

## REQ-332-2 (D2, P1) — журнал и legacy-индекс резолвятся через общий корень памяти во всех точках входа

Существующее поведение (дефект): все четыре точки входа передают адаптеру путь
ТЕКУЩЕГО чекаута (`memory-brief.ts:40` — `process.cwd()`, `memory-contradict.ts:28`,
`memory-call.ts:48`, `mcp-tools.ts:173` — `baseDir`), тогда как хранилище заметок
и весь контейнер резолвят общий корень через `resolveMemoryRoot()`
(`src/bootstrap/container.ts:51`). В linked worktree журнал уходит в локальный
`.wolf` рабочего дерева: подавление из main не скрывает заметку в worktree
(стенд 23: count=1 после подавления), `list` в worktree не видит открытых
записей (стенд 24: «no open suppressions»), report из worktree не виден в main
(стенд 26). В 3.3.0 подавления жили в `index.sqlite` по общему корню
(`indexPath(mem.root)`) — 3.3.1 регрессировала общность.

- AC-2.1: подавление, зарегистрированное в main-чекоуте, скрывает микроноту в
  `wolf brief`/`wolf call` исполняемых из linked worktree того же проекта.
- AC-2.2: `contradict list` из linked worktree показывает те же открытые записи,
  что и из main (в обе стороны: report из worktree виден в main).
- AC-2.3: resolve записи из linked worktree снимает ту же запись, что видна в main.
- AC-2.4: миграция ADR-3, запущенная из linked worktree при отсутствии файла
  журнала, находит legacy `index.sqlite` в общем корне и создаёт журнал там же.
- AC-2.5: вне linked worktree (обычный чекаут, не-git каталог) путь журнала
  не изменяется — существующие проекты не мигрируют повторно.

## REQ-332-3 (D3, P2) — запись восстанавливает границу последней корректной строки

Существующее поведение (дефект): `append()` дописывает строку в конец без
проверки хвоста (`jsonl-micro-note-delivery-log.ts:92-95`); после оборванной
последней строки (crash во время append) следующая запись приклеивается к
обрывку — файл становится нечитаемым («corrupted mid-file»), при этом команда
записи УЖЕ подтвердила успех (стенд 40/41: report exit=0, затем brief/list
exit=1).

- AC-3.1: перед добавлением записи обрывок последней строки (невалидный JSON
  без завершающего `\n`) отбрасывается; запись успешна, файл после записи
  читается полностью без ошибок.
- AC-3.2: валидная последняя строка без завершающего `\n` финализируется
  (добавляется `\n`) и НЕ теряется; новая запись дописывается после неё.
- AC-3.3: после обрыва записи следующая команда записи либо безопасно
  продолжает работу (восстановив границу), либо отказывает ДО подтверждения
  успеха; подтверждённая запись не оставляет файл нечитаемым.
- AC-3.4: битая строка в СЕРЕДИНЕ файла по-прежнему отказ с именованной
  причиной (молчаливой потери состояния нет — поведение 3.3.1 сохраняется).

# 3. Не входит в состав (вне скоупа)

- Блокировки параллельной записи в журнал (гонка двух одновременных appender'ов
  существует и в 3.3.1; локальный однопользовательский инструмент, команды
  уровня проекта уже синхронизируются memory-lock; отдельный носитель для
  блокировок журнала — будущая волна при реальных свидетельствах).
- NO_COLOR-чувствительность теста ANSI-цветов из окружения ревьюера
  (в нашем CI и без переменной 2486/2486 зелёные; не воспроизведена как дефект).
- Изменения CLI-поверхности, MCP-каталога, формата журнала и миграции.
