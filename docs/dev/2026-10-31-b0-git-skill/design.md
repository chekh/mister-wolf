# b0-git-skill — дизайн

## Глоссарий

- **Канон** — `docs/reference/git-collaboration-policy-v1.1.md` (версия 1.1, 1 ноября
  2026, sha256 `df7d3d82…56c208`). Единственный источник редактирования текста.
- **Поставляемая копия** — `templates/base/skills/wolf-git/reference/git-collaboration-policy-v1.1.md`,
  байт-идентична канону; рендерится в `<project>/.opencode/skills/wolf-git/reference/…`.
- **Base-set** — множество файлов, которое рендерер кладёт в проект:
  `src/adapters/render/opencode/opencode-renderer.ts:114` (`templateFiles`) рекурсивно
  обходит `templates/base/{agents,skills,commands}` через `walkAbs:133`.
- **Карта** — `update-map.json`, полный инвентарь целей синка; `kind` выводится из
  префикса пути (`scripts/generate-update-map.mjs:78` `kindForPath`), поэтому вложенный
  файл внутри `base/skills/<name>/` — это `kind: "skill"`, а не новый класс.

## Компоненты и ответственность

| Компонент           | Ответственность                                                                               | Файл                                                                                             |
| ------------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Канон регламента    | нормативный текст, неприкосновенные bytes                                                     | `docs/reference/git-collaboration-policy-v1.1.md` (REQ-01)                                       |
| Скилл `wolf-git`    | когда запускать Git-этап, что проверить, как реагировать на отказ, куда смотреть в регламенте | `templates/base/skills/wolf-git/SKILL.md` (REQ-02, REQ-05)                                       |
| Поставляемая копия  | полный текст в установленной поставке                                                         | `templates/base/skills/wolf-git/reference/git-collaboration-policy-v1.1.md` (REQ-03)             |
| Точки входа методик | одна ссылка на `wolf-git` из соседних скиллов                                                 | `using-git-worktrees`, `finishing-a-development-branch`, `wolf-handoff`, `using-skills` (REQ-04) |
| Guard-тесты         | канон↔копия, sha256, frontmatter, лимит размера, рендер в tmp, карта                          | `tests/unit/skills/wolf-git-contract.test.ts` (NFR-01/02)                                        |
| Карта обновления    | согласованность templates↔карта↔package.json                                                  | `update-map.json` (генерируется существующим скриптом)                                           |
| Формат-границa      | канон не переформатируется                                                                    | `.prettierignore` (ADR-6)                                                                        |

Ни одного нового компонента исполнения: ни агента-контролёра, ни scheduler, ни
команды `wolf`, ни поля схемы. Всё, что скилл называет, — стандартный `git` и
существующие команды памяти Wolf.

## Контракты

**Контракт пути (REQ-03).** Ссылка в скилле относительна файлу скилла:

```
templates/base/skills/wolf-git/reference/git-collaboration-policy-v1.1.md
   → <project>/.opencode/skills/wolf-git/reference/git-collaboration-policy-v1.1.md
```

Рендерер добавляет одну строку-штамп `<!-- wolf:rendered … -->` перед содержимым
(`src/adapters/render/stamp.ts:22` `insertStamp`), поэтому sha256 сравнивается между
каноном и **шаблоном** (оба без штампа), а не с файлом в установленном проекте.

**Контракт frontmatter скилла** — как у существующих: ровно `name` (= имя каталога) и
`description` с триггером применения.

**Контракт содержания SKILL.md** (NFR-01, REQ-05): разделы

1. Обязательный вход — что проверяется до любого действия, полномочия берутся из брифа.
2. Вход / возобновление (G0) — регламент §6; различение «нарушено» / «не удалось проверить».
3. Создание ветки и worktree (G1) — §7, §4.1; baseline = явный SHA, не текущий HEAD.
4. Сохранение (checkpoint) — §8.
5. Передача (G2) — §9, §4; поля handoff.
6. Завершение и уборка (G9) — §15, §16; условия, при которых каталог остаётся.
7. Приёмка и интеграция — §10, §11: чего в реализации нет.
8. Что не поставлено — явный список.
9. Гейт перехода и «не пропускай процесс» (таблица антипаттернов, как в соседних скиллах).

Бюджет: ≤ 150 строк, ≤ 8000 байт. Регламент не пересказывается: этап → проверка →
§-ссылка.

## ADR-карточки

### ADR-1 — Канон: версия 1.1 в `docs/reference/`, bytes неприкосновенны

**Контекст.** Владелец передал регламент версии 1.1 (1 ноября 2026, 553 строки, 77.4 КБ,
sha256 `df7d3d826349c4758c338044d1bd9577446f8ff563182e9a2e8a283e5056c208`). Roadmap §11 и
сноска [GIT1] ссылаются на версию 1.0 от 26.10.2026; расхождение — в §22 регламента:
стандартная интеграция изменена с squash на merge commit `--no-ff`, squash оставлен
исключением. Roadmap задним числом не правится.

**Решение.** Канон — `docs/reference/git-collaboration-policy-v1.1.md` под git; каталог
`docs/reference/` уже используется (`cli.md`). Файл добавлен как есть, без
переформатирования; запрет на правку по существу зафиксирован в requirements §2.

**Последствия.** sha256 остаётся проверяемым и совпадает с переданным владельцем; любая
будущая редакция — новый файл с новой версией в имени, старый не переписывается.

### ADR-2 — Доставка: вложенный ресурс внутри каталога скилла, без нового FileKind

**Контекст.** `package.json` `files: ["dist","templates","update-map.json"]` — документация
`docs/` в npm-пакет не попадает, поэтому положить регламент рядом с каноном и «сослаться»
из установленного проекта нельзя. `FileKind = agent|skill|command|plugin`
(`src/adapters/fs/update-map.ts:26`), класса «reference document» нет. Новый FileKind —
новый публичный контракт, то есть выход за B0.

**Решение.** Использовать существующий рекурсивный обход `templates/base/skills/**`:
положить копию внутрь каталога скилла как `reference/git-collaboration-policy-v1.1.md`.
`walkAbs` (`opencode-renderer.ts:133`) отдаёт её как обычную цель рендера, `syncBaseSet`
штампует и обновляет её, `orphaned`-детект её видит, `kindForPath` классифицирует как
`skill`, карта генерируется существующим скриптом. Ни `update-map.ts`, ни схема карты,
ни CLI не меняются (NFR-03).

**Последствия.** Полный текст оказывается в проекте ровно там же, где скилл — относительная
ссылка всегда разрешается. Плата: копия в двух местах → guard-тест на byte-равенство и
закреплённый sha256 (NFR-02). Изменение текста требует явного шага копирования; забытая
синхронизация ловится тестом, а не ревью.

### ADR-3 — Скилл короткий и адресный; регламент не инжектится

**Контекст.** 77 КБ в контексте агента ломают бюджет и вытесняют рабочую задачу.

**Решение.** `SKILL.md` ≤ 150 строк: этапы, проверки, реакция на отказ, §-ссылки.
Полный текст — только адресное чтение нужного раздела по пути из ADR-2.

**Последствия.** Агент платит за регламент ровно столько, сколько нужно этапу. Пересказ
неизбежно теряет оговорки, поэтому каждая проверка ссылается на раздел, а не заменяет его.

### ADR-4 — G0/G1/G2/G9 проводятся доступными операциями; непоставленное названо

**Контекст.** Регламент §19.2 требует «один фактический сборщик Git-состояния»,
структурированный JSON и вердикт `нарушено / не удалось проверить`. В 2.22.1 такого
инструмента нет: B0.5 (read-only inspect) и B1 (переносимые операции) — отдельные срезы.

**Решение.** Скилл формулирует проверки как последовательность доступных команд `git`
(`status --porcelain`, `rev-parse HEAD`, `worktree list --porcelain`, `rev-list`,
`merge-base --is-ancestor`, `for-each-ref`, `ls-remote` + время наблюдения) и требует
явно писать «не удалось проверить», когда команда недоступна (нет сети, нет remote).
MR-статусы, CI-проверки, очередь интеграции, теги, registry и структурный вердикт
помечены как непоставленные; G3–G8 остаются в существующем ручном процессе.

**Последствия.** Скилл не заявляет машинного обеспечения гейтов; разрыв между
инструкцией и реализацией виден читателю, а не обнаруживается на инциденте.

### ADR-5 — Полномочия: решают бриф и рамка, скилл не расширяет прав

**Контекст.** Регламент §3: назначенный владелец задачи «вправе и обязан» делать
checkpoint, «повторное разрешение на каждый коммит не требуется»; при этом «явное
ограничение задачи, например «не коммитить», и более высокие ограничения сохраняются;
тогда заранее назначенный L1 отвечает за сохранность». Рамка `executor-lead` (этот
репозиторий) говорит: «Коммиты — только если бриф явно поручает».

**Решение.** Скилл не выдаёт прав: он проверяет, что полномочие на запись/коммит/
публикацию назначено брифом задачи, и при его отсутствии требует, чтобы сохранял
назначенный L1. Внутри уже назначенного полномочия отдельное разрешение на каждый
checkpoint не запрашивается (§3). Правило «повторное разрешение не нужно» относится к
границе уже выданного полномочия, поэтому противоречия с рамкой нет: рамка —
действующее ограничение проекта.

**Последствия.** Живые лица (`executor-lead`, playbook'и) не правятся в B0: их изменение
идёт через Стюарда. Остаток среза: если владелец захочет привести рамку к §3 дословно
(постоянное полномочие на checkpoint), это отдельная мутация лица, а не часть B0.

### ADR-6 — Канон исключён из prettier, а не переформатирован

**Контекст.** `npm run check` → `format:check` покрывает `docs/**/*.md`. Переданный
регламент не отформатирован prettier (baseline-падение зафиксировано в plan.md). Правка
форматирования изменила бы bytes и sha256 канона.

**Решение.** Добавить путь канона в `.prettierignore` с комментарием-причиной.

**Последствия.** sha256 остаётся доказательством; формат-гейт зелёный; поставляемая копия
находится в `templates/**`, вне области `format:check`, и сравнивается байтами с каноном.

## Сверка с действующими методиками (REQ-04)

| Норма                             | Где сказано                                                                                                                                   | Что говорит `wolf-git`                                                                                                     | Противоречие |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ------------ |
| Baseline не «текущий HEAD»        | `using-git-worktrees`: «Создай worktree от явно выбранного baseline, не от случайного текущего HEAD»; регламент §7                            | то же: ветка от проверенного SHA `main`, подзадача — от опубликованного SHA родителя                                       | нет          |
| Путь worktree                     | `using-git-worktrees`: «local .worktrees/<task> — рекомендуемый fallback, не универсальный запрет»; политика памяти `.worktrees/<имя-задачи>` | путь задаёт бриф задачи; `.worktrees/<task>` — дефолт репозитория                                                          | нет          |
| Один писатель                     | регламент §3; `wolf-handoff`: «Нельзя одновременно продолжать запись старым и новым исполнителем»                                             | то же, плюс проверка «прежняя запись прекращена» до смены владельца                                                        | нет          |
| Сохранение ≠ публикация ≠ приёмка | регламент §2 (таблица состояний); `finishing-a-development-branch`: «push, создание PR, merge и cleanup различны»                             | то же; checkpoint обязателен на логических границах, а не перед каждым действием                                           | нет          |
| Отказ git не лечится force        | `finishing-a-development-branch`: «не добавляй force автоматически»; регламент §15.2                                                          | то же: `--force`, `reset --hard`, `clean -f`, `branch -D` по умолчанию запрещены                                           | нет          |
| Уборка только по гейту            | `finishing-a-development-branch`: «Не удаляй branch/worktree до подтверждения успешной интеграции»; регламент §15.1                           | то же: G9-проверки, включая ignored-файлы и потомков                                                                       | нет          |
| Полномочия на коммит              | `executor-lead` рамка: «Коммиты — только если бриф явно поручает»                                                                             | ADR-5: скилл не выдаёт прав, сохраняет назначенный L1                                                                      | нет          |
| Порядок процесса                  | `using-skills`: процессные скиллы раньше исполнительских; «Требуется изоляция записи → `using-git-worktrees` перед изменениями»               | `wolf-git` вызывается на Git-границах и отправляет к `using-git-worktrees`/`wolf-handoff`/`finishing-a-development-branch` | нет          |

Связи оформляются: в `wolf-git` — ссылки на все пять методик; в `using-git-worktrees`,
`finishing-a-development-branch`, `wolf-handoff` — одна строка-указатель на `wolf-git`;
в `using-skills` — строка в таблице обязательных методик. Живые лица не правятся (ADR-5).
