# 2.32.0 — английские ID записей памяти — дизайн

Основание: решения владельца `mem_20261106_resheniya_vladeltsa_po_volne_2_32_0_q1_q_5f7bb5`
(Q1 — slug от агента-создателя, Q2 — детерминированный суффикс и tie-break),
уточнение стадии 2 (2026-11-06). План — [plan.md](plan.md), проверки — [test-plan.md](test-plan.md).

## 1. Проблема

ID записи строился транслитерацией русского заголовка: `mem_20260930_resheniya_po_arhitekture_ab12cd`.
Это даёт кириллический смысл в латинской оболочке, шумный FTS и ID, которые человек не читает.
Владелец решил: ID новых записей = дата + английский slug, который даёт агент-создатель;
транслитерация русского заголовка убирается; сеть и LLM в CLI не добавляются.

## 2. Контракт ID

```
mem_<YYYYMMDD>_<slug>_<hash6>     // slug передан и валиден
mem_<YYYYMMDD>_<hash6>            // slug отсутствует или невалиден (fallback, без слов)
```

- `YYYYMMDD` — дата создания (UTC, как и раньше).
- `slug` — английский, нижний регистр, `a-z0-9` и дефисы между словами
  (`^[a-z0-9]+(?:-[a-z0-9]+)*$`), длина 1…40 после нормализации.
- `hash6` — первые 6 hex `sha256("<slug>|<YYYYMMDD>")`; для fallback — `sha256("<date>")`.
- Нормализация входа: trim → lower → пробелы/подчёркивания → дефис → сжатие дефисов →
  обрезка до 40 по границе слова. Нормализация не подставляет слова и не переводит.

## 3. Валидация и fallback

| Вход                                     | Поведение                                                                                      |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `--slug release-plan`                    | `mem_20261106_release-plan_<hash6>`                                                            |
| `slug` в верхнем регистре / с пробелами  | нормализуется (`Release Plan` → `release-plan`), ID строится                                   |
| кириллица в slug (`--slug релиз`)        | невалидно → **fallback** `mem_20261106_<hash6>`; CLI печатает предупреждение, запись создаётся |
| slug не передан (MCP/внутренние callers) | fallback `mem_20261106_<hash6>`                                                                |
| slug длиннее 40                          | обрезается по границе слова                                                                    |

Fallback — не ошибка: запись создаётся, деградация видима в выводе команды и в предупреждении
`warnings`. Транслитерация как заменитель запрещена (Q1): «тихого» русского slug не бывает.

## 4. Детерминизм и коллизии

- Одинаковые `slug` + дата дают одинаковый ID (хеш не зависит от времени суток, миллисекунд
  и порядка вызовов). Это и есть Q2: повторяемость вместо прежнего `date.toISOString()` с мс.
- `generateMemoryId` остаётся чистой синхронной функцией; store она не читает.
- Коллизия разрешается на уровне `add`:
  1. `store.get(id)` пуст → запись создаётся.
  2. объект с тем же `title` и `type` уже есть → **отказ** с подсказкой (`wolf edit` /
     `wolf supersede` / другой `--slug`). Это прежняя защита от дублей (P0 817efd) и она
     сохраняется: одинаковый заголовок в один день — это дубль, а не вторая запись.
  3. объект с тем же id, но другим `title`/`type` (агент переиспользовал slug) → **tie-break**:
     `…_<hash6>-2`, затем `-3`, … первый свободный id. Детерминированно при том же состоянии стора.
- Существующие ID не переименовываются: чтение, поиск, ссылки, supersede работают по строке id.

## 5. Обратная совместимость и миграция

- Схема памяти id не валидирует по регулярке (id — строка) → старые ID остаются валидными.
- `document-id.ts` — отдельный канон (`mem_<date>_doc_<slug>_<hash8>`), не меняется: там slug
  происходит из имени файла документа, а не из заголовка. Транслитерация для document-ref
  остаётся локальной в `document-id.ts` (перенос карты из `hash-id-generator.ts`), иначе
  смена slug'ов сломала бы уже проиндексированные документы.
- Миграционная оговорка: исторические записи с транслитерированными ID остаются как есть;
  массового переименования нет. Смешанный вид памяти — ожидаемое состояние, документация
  памяти это прямо говорит.

## 6. Точки вызова (все — один контракт)

| Файл                                                   | Вход для slug                                                 |
| ------------------------------------------------------ | ------------------------------------------------------------- |
| `src/app/use-cases/add-memory-object.ts:138`           | новый `input.slug` (CLI `--slug`, MCP `slug`), иначе fallback |
| `src/app/use-cases/thinking.ts:60`                     | `input.slug` (опционально), иначе fallback                    |
| `src/app/use-cases/thinking.ts:122`                    | `input.slug`, иначе fallback (tid)                            |
| `src/app/use-cases/create-mutation-record.ts:96`       | `input.slug`, иначе fallback                                  |
| `src/app/use-cases/create-memory-repair-request.ts:41` | `input.slug`, иначе fallback                                  |

Транслитерации на call sites нет ни на одном пути: генератор получает только `slug | undefined`.

## 7. Каналы

- CLI `wolf add --slug <english-slug>` (и генерённые `<type> add` через ту же форму опций).
- MCP `memory_add`/`add` — поле `slug` (строка, опционально).
- Внутренние use-case'ы (`thinking`, mutation, repair) принимают `slug` от вызывающего слоя.
- Вывод: при fallback CLI/MCP сообщают, что slug не применён (warnings/строка результата).

## 8. ADR

**ADR-1. Slug даёт создатель, а не CLI.** Контекст: local-first, без сети и LLM в CLI;
любой встроенный переводчик даёт недетерминизм и требует провайдера. Решение: slug — вход,
валидация и fallback — в CLI. Последствия: качество slug'ов зависит от агента; при пропуске
получаются безсловные ID, и это видно.

**ADR-2. Хеш от slug+дата.** Контекст: прежний суффикс включал миллисекунды, повторность
была невозможна. Решение: `sha256(slug|date)` — повторяемость и предсказуемость. Последствия:
меняется поведение новых записей; два разных объекта с одинаковым slug в один день требуют
tie-break или явного отказа.

**ADR-3. Дубль заголовка — отказ, а не `-2`.** Контекст: P0-инцидент тихой перезаписи;
tie-break не должен открывать путь к параллельным дублям. Решение: `-2` только при реальном
расхождении title/type. Последствия: пользователь видит отказ и осознанно выбирает
`wolf edit`/`supersede`. Уточнение реализации (стадия 3): потоки, где один заголовок
законно повторяется (жалобы на то же правило, wrap-up сессии, запись совета, предложение),
передают `idFingerprint` — отпечаток содержания, который участвует только в fallback-хеше
и никогда не попадает в id. Разное содержание → разные id, одинаковое → прежний отказ.
