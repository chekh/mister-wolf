# 2.32.0 — UX отчёта upgrade, английские ID памяти, пакет цели — план волны

База: `595f29840e414e2470acb06c20ec594cf98b93d2` (main, 2.31.0). Целевая версия —
полный номер **2.32.0** (minor). Профиль планирования — LITE: этот plan.md играет роль
брифов и контракта; отдельные requirements/design/test-plan создаются только там, где
направление требует полноценного проектирования (`W232-T04`, см. ниже).

Документ — план, а не отчёт о выполнении: ни одна задача не считается сделанной по

## 1. Контекст, цель и границы

Источники: тред `mem_20261106_volna_2_32_0_ux_otcheta_upgrade_angliysk_65bb58`, решение
владельца о скоупе `mem_20261106_skoup_2_32_0_pre_requirements_md_change_173b7b`, решение
владельца по Q1–Q8 `mem_20261106_resheniya_vladeltsa_po_volne_2_32_0_q1_q_5f7bb5`, тред
Upgrade UX `mem_20261024_upgrade_ux_namereniya_vladeltsa_i_tikhiy_e6daf7`.

Цель волны — три независимых направления в одном minor-релизе:

1. **UX отчёта `wolf upgrade`** — разметка без шума: три различимых маркера,
   отсутствие маркера статуса на строках-подробностях, `needs decision` по кодам
   отдельными строками. Плюс два дефекта подачи рамки: заголовок доставленного
   using-skills читается как ошибка; рассинхрон версии «Жалобного протокола» в
   доставленном наборе.
2. **Английские ID записей памяти** — новые ID = дата + английский slug, который даёт
   агент-создатель при создании записи; CLI валидирует формат, при отсутствии или
   некорректности — fallback «дата + короткий хеш» без слов. Транслитерация русского
   заголовка убирается, сеть/LLM в CLI не добавляются, существующие ID не
   переименовываются (решение Q1).
3. **Пакет документов цели** — `pre-requirements.md` как полноценный первый документ
   пакета и `change-request.md` в папке цели; шаблоны, `wolf scaffold artifact`,
   правила линта/doctor, порядок документов и разводка с разделом «Журнал изменений
   (CR)» в requirements.md.

Вне scope волны: переименование существующих записей памяти; миграция исторических
пакетов `docs/dev/*` под новый порядок документов; переработка остальных отчётов
CLI (кроме общих маркеров рендерера); новые продуктовые обещания по консоли O1/U1;
изменение контракта `--json` (`wolf.upgrade/1`); правка живых лиц в обход Стюарда.

### W232-T02@v1 — Отчёт upgrade: три маркера, детали без статуса, needs decision по кодам

- Цель: убрать визуальный шум из отчёта `wolf upgrade` (парковый проход и `--here`),
  не меняя данные и `--json`.
- Вход/норма: этот блок §3; baseline `src/adapters/cli/report-renderer.ts:13`,
  `:28-32`, `:43-49`, `:102-113`, `:196-203`;
  `src/app/use-cases/upgrade-projects.ts:440-467`, `:499-513`, `:517-524`, `:527-561`,
  `:581-600`; `src/adapters/cli/commands/memory-upgrade.ts:252-287`;
  `src/app/use-cases/verify-against-map.ts:18-31` (`NEEDS_DECISION_CODES`).
- Контракт (решение L1, обратимо):
  1. `MARKERS` различает глифы: `info` → `●` (cyan, без изменений), `ok` → `✓`,
     `skip` → `·` (dim). `warn`/`error` не меняются. Различимость обязательна и без
     цвета (16/mono), поэтому глифы разные, а не только оттенки.
  2. `ReportNode` получает `{ kind: 'detail'; text: string }`. Рендер: в plain — строка
     без префикса; в styled — без глифа, с выравниванием продолжения по той же колонке,
     что у `line`. Смысл: деталь не выдаёт себя за статус.
  3. В `detail` переводятся: `base-set:`, `faces:`, `verify:`, строки `needs decision`,
     `protected/kept`, `backupDigestLines`, `hint:`, строки путей скана, `composition`,
     `map:`, `duplicate registry entry`. Статусными (`line`) остаются: строка проекта,
     `schema:` (это состояние шага), финальная строка exit-таблицы, skip-строка плана.
  4. `needs decision` печатается отдельными строками **по коду** в фиксированном порядке
     `conflict` → `skipped-mutated` → `diverged`, формат
     `needs decision (<code>): <path> (<code>), …` → один путь на строку при переносе;
     сейчас `diverged` из перечисления исключён (`verifyNameLines` фильтрует его), это
     дефект покрытия. Счётчик `verify: N/M ok · K needs decision` сохраняется дословно.
  5. Единственная реализация деталей шага: `memory-upgrade.ts:252-287` дублирует
     `projectsSection`; дубль заменяется импортом одной функции.
- Allowlist: `src/adapters/cli/report-renderer.ts`, `src/app/use-cases/upgrade-projects.ts`,
  `src/adapters/cli/commands/memory-upgrade.ts`, `tests/unit/adapters/*report*`,
  `tests/unit/adapters/commands/upgrade-projects.test.ts`, `tests/unit/use-cases/upgrade-projects.test.ts`,
  `tests/integration/upgrade-park.test.ts`, `tests/integration/upgrade-here.test.ts`,
  `tests/e2e/upgrade.e2e.ts`, `tests/e2e/upgrade-exec.e2e.ts`, `tests/e2e/upgrade-park-modes.e2e.ts`.
  Вне allowlist — `src/app/use-cases/project-step.ts`, `verify-against-map.ts`, JSON-схемы.
- AC: (1) три маркера различимы в styled и в plain; (2) у `base-set/faces/verify/needs decision`
  нет глифа-статуса; (3) `needs decision` — отдельные строки по коду, `diverged` видим;
  (4) `--json` не изменился (проверяется существующим тестом/фикстурой, полный
  `buildPassJsonDoc` не меняется); (5) рамки не рвутся на width 60/80/120 (снэпшоты);
  (6) отчёты `wolf upgrade`, `wolf upgrade --here`, `--yes`, TTY-confirm используют один
  и тот же формат деталей.
- Проверка: `npx vitest run tests/unit/adapters tests/unit/use-cases tests/integration`,
  затем `npx vitest run --config tests/e2e/vitest.config.ts tests/e2e/upgrade.e2e.ts`,
  живой прогон `node dist/bootstrap/cli.js upgrade --here` на фикстуре (не на этом проекте).
- Бюджет: 10 обращений к инструментам. Стоп: расхождение ожиданий снэпшотов больше чем в

## 7. Риски

- **R1. Контракт slug (Q1).** Английский slug обязан передать агент-создатель; пока
  навыки и роли этого не делают, большинство записей уйдёт в hash-fallback и ID станут
  безсловными. Компенсация: тексты скиллов/команд (T07) и явное сообщение о деградации;
  сеть и LLM в CLI не добавляются, поэтому «тихого» автоперевода-заменителя нет.
- **R2. Смена поведения новых ID (Q2).** Текущий хеш-суффикс включает
  `date.toISOString()` с миллисекундами (`hash-id-generator.ts:43-47`), поэтому «тот же
  заголовок» даёт разные ID; решение Q2 меняет это осознанно. Риск — тесты/потребители,
  ожидающие старую форму и старую нестабильность.
- **R3. Обратная совместимость.** Существующие ID должны читаться, искаться и валидироваться;
  `document-id.ts` — отдельный канон, его не трогаем. Проверять на реальной памяти проекта.
- **R4. Посев лиц не обновляет существующие лица.** Правка шаблона не чинит уже
  установленные лица; по Q3 живое лицо этой установки обновляется контуром Стюарда, а для
  остальных проектов остаётся известное ограничение (фиксируется в troubleshooting, T07).
- **R5. Top-up scaffold (Q4 (a)).** Новое поведение при существующей папке обязано
  добавлять только недостающие документы; ошибка реализации перезапишет принятые
  документы пакета. Проверка — тест «повторный запуск не меняет существующие файлы».
- **R6. English-surface gate.** Кириллица в строковых литералах `src/adapters/**` запрещена
  (`scripts/check-english-surface.mjs`); по Q1 словаря перевода больше нет, ограничение
  касается только кода валидации slug и сообщений о деградации.
- **R7. Снэпшоты отчёта.** Изменение маркеров/деталей затрагивает существующие ожидания
  тестов; обновление снэпшотов допустимо только после проверки, что изменение — цель, а не
  побочный эффект.
- **R8. update-map.** Забытая регенерация карты означает, что `wolf upgrade` у пользователей
  не доставит новые шаблоны; порядок T08→T09 обязателен.
- **R9. Слепая правка живого лица.** Прямая запись в `.wolf/memory` в обход Стюарда
  запрещена рамкой; при отсутствии полномочия — partial, не «тихая правка».
- **R10. Среда.** Известные ловушки этой машины: rtk-плагин перехватывает stdout (`git`/`npm`/`cat`) —
  читать вывод через файл и `read`; подписка `zai-coding-plan` истекла, маршрут агентов —
  `company/fb-zai-glm-5.3`; живой прогон opencode с изолированным `XDG_DATA_HOME` ломает
  провайдера. Живые проверки — на фикстурах, не на рабочей установке.
