# E1 срез-1 — TASK-контракт ACTIVE_CONSTRAINTS и DECISIONS[] — дизайн

## Глоссарий

- Ядро TASK — обязательный список элементов поручения в
  `templates/base/skills/using-skills/references/contracts.md`; профиль
  implement/review/research добавляет применимое.
- Условная применимость — элемент ядра передаётся, когда действует; отсутствие
  элемента означает отсутствие действующих ограничений/решений, а не пропуск.

## Компоненты и ответственность

- `templates/base/skills/using-skills/references/contracts.md` — канон: определение
  двух блоков ядра, инвариант условной применимости, словарь.
- `templates/base/skills/wolf-handoff/SKILL.md` — состав snapshot: оба блока
  явными пунктами.
- `templates/base/skills/wolf-execute/SKILL.md` — поведение L2 при продолжении.
- `templates/base/skills/wolf-sdd/SKILL.md` — поведение L1: блоки в следующем
  вызове той же задачи.
- `templates/base/agents/executor-lead.md` — TASK-программа и порядок replace.
- `docs/site/ru/guide/organization.md` — пользовательское описание состава TASK.

## Контракты

Точные тексты правок (единый источник для plan; исполнителю даются эти формулировки).

**1. contracts.md, список ядра — два новых пункта после «Входы и назначенная методика»:**

```markdown
- `ACTIVE_CONSTRAINTS` — действующие ограничения задачи: короткие строки
  «что действует → источник/основание» (правило/решение памяти с ID, документ
  с revision). Отсутствует — ограничений сверх общих норм нет; пересказ всех
  правил проекта не требуется.
- `DECISIONS[]` — принятые по задаче решения, влияющие на текущую работу:
  `D-id`, что решили (одной строкой), почему/что отвергнуто, основание/источник.
  Одна строка на решение; не история обсуждения. Отсутствует — влияющих решений нет.
```

**2. contracts.md, инварианты ядра — дополнение после «Опускание неприменимого…»:**

```markdown
ACTIVE_CONSTRAINTS и DECISIONS[] передаются, когда действуют: их отсутствие —
заявление об отсутствии действующих ограничений/решений, а не пропуск поля.
```

**3. contracts.md, словарь:** «ядро из восьми элементов» → «ядро из десяти элементов».

**4. wolf-handoff, состав snapshot — пункт «утверждённые решения и активные
методики — IDs/версии;» заменяется двумя:**

```markdown
- действующие ограничения задачи (`ACTIVE_CONSTRAINTS`) и активные методики/политики — IDs/версии;
- принятые решения (`DECISIONS[]`: D-id, что решили одной строкой, почему, основание/источник) — только влияющие на продолжение;
```

**5. wolf-execute, абзац «После результата заверши вызов…» — дополнение после
«уже достаточное не повторяй.»:**

```markdown
Соблюдай `ACTIVE_CONSTRAINTS` своего TASK и не переоткрывай без нового основания
вопросы, закрытые в `DECISIONS[]`; контрпример или изменившееся основание верни L1.
```

**6. wolf-sdd, цикл задачи п. 3 — фраза «Следующий вызов получает решённый вопрос,
короткий остаток и новый конечный лимит.» заменяется на:**

```markdown
Следующий вызов получает решённый вопрос, короткий остаток, новый конечный лимит
и действующие `ACTIVE_CONSTRAINTS`/`DECISIONS[]` той же задачи.
```

**7. executor-lead.md, TASK-программа (строка «TASK — короткая программа…»):
перечисление «…полная методика действия, относящиеся политики/исключения,
инструменты и стоп-условие.» →**

```markdown
…полная методика действия, относящиеся политики/исключения и действующие
`ACTIVE_CONSTRAINTS`/`DECISIONS[]`, инструменты и стоп-условие.
```

**8. executor-lead.md, инвариант 8 выбора сеанса: «известный результат и открытые
замечания передаются через handoff» →**

```markdown
известный результат, открытые замечания и действующие
`ACTIVE_CONSTRAINTS`/`DECISIONS[]` передаются через handoff
```

**9. docs/site/ru/guide/organization.md, абзац о ядре брифа:** «ядра из восьми
элементов» → «ядра из десяти элементов», в перечисление после «…и ожидаемый отчёт»
добавить: «, а при продолжении задачи — действующие ограничения (`ACTIVE_CONSTRAINTS`)
и принятые решения (`DECISIONS[]`: D-id, что решили, почему, основание), чтобы новая
сессия не переоткрывала решённое».

## ADR-карточки

- ADR-1: Блоки — элементы ядра, а не профильные поля. Контекст: блоки нужны любому
  профилю (implement/review/research) при продолжении/замене, но не каждой задаче.
  Решение: включить в ядро с условной применимостью (аналогично «применимое ядерное
  поле нельзя опустить»). Последствия: словарь считает 10 элементов; простой TASK
  без действующих ограничений/решений не раздувается.
- ADR-2: wolf-plan не правится. Контекст: скилл уже предписывает «перечень полей не
  дублируй, сошлись на канон» (п. 3 Процесса). Решение: правка канона покрывает
  wolf-plan; дубль текста создал бы второй источник. Последствия: объём diff меньше,
  согласование — одно место.
- ADR-3: `.opencode/` и релизные артефакты не правятся. Контекст: установленная
  копия набора синхронизируется re-stamp'ом при выпуске (прецедент 2.25.0/2.25.1),
  релизный цикл 2.26.0 вне среза. Решение: правится только источник `templates/base`
  и docs. Последствия: живая копия проекта обновится при выпуске; в срезе фиксируется
  как ограничение, не как дефект.
- ADR-4: Исполнительские правки выполняются одним L2-мандатом. Контекст: 6 файлов,
  ~15 строк, один канонический смысл. Решение: один implement-мандат с allowlist
  всех файлов и точными текстами из «Контрактов»; независимый reviewer проверяет
  соответствие и качество после. Последствия: один порядок интеграции, один владелец
  общих файлов (§13).
