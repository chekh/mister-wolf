# A1.1 — минимальные измерения (доступные сигналы)

## 1. Контекст и проблема

Срез A1.1 роадмапа v4 (ред. 9, NOW 2 из 2): один importer/writer уже
существующих сигналов даёт корректный run-итог — модель, доступные токены,
длительность, task/run/attempt identity. Сейчас в
`.wolf/metrics/session-metrics.jsonl` событий `run` два (30.08.2026), писатель
run-сигналов удалён в 2.13; расход агентских сессий не наблюдается. Без этого не
проверяются ни экономия fresh L2, ни стоимость исправлений, ни число циклов
(A1.2, E1).

Метрика успеха: после среза локальный прогон импорта даёт run-итоги реальных
сессий с токенами/моделью/длительностью; повторный импорт не удваивает расход;
отсутствующее значение показано как «неизвестно».

## 2. Область

Входит: чтение одного подтверждённого источника usage, маппинг в существующую
схему `SignalEvent` (событие `run`), дедупликация, human/machine отчёт,
fixtures источника и учёта, документация ограничений источника.

НЕ входит: A1.2/REQ-12…16 (экономное поведение), E2/REQ-23B (полный учёт,
стоимость, reasoning/provenance-поля), новые LLM-вызовы, изменение публичной
схемы памяти, универсальный provider collector, реакции на `detail`-поля,
дашборды и новые вью аналитики.

## 3. Глоссарий

- **Turn** — один ответ модели (assistant-сообщение) в локальной БД площадки.
- **Run** — фактический запуск агента; в источнике ему соответствует сессия,
  идентичность — `run_id = session_id`.
- **Attempt** — номер повтора внутри run по данным источника (`retry.attempt`).
- **Run-итог** — агрегат по run: модель, суммарные токены, длительность,
  идентичности, явные «неизвестно».

## 4. Функциональные требования

### RQ-01 — Один подтверждённый источник usage

- История: Как владелец, я хочу видеть фактический расход агентских сессий,
  чтобы оценивать организацию работы, а не гадать.
- Требование: Источник usage подтверждён образцом записи, маппинг зафиксирован
  в design §Контракты; при недоступности источника команда сообщает об этом и
  ничего не пишет.
- Обоснование: roadmap §6 — первое действие A1.1; «источник не подтверждён —
  открытая задача, а не повод придумать расход».
- AC: Given доступная локальная БД площадки, When выполняется импорт, Then
  записаны `run`-события из подтверждённого источника; Given БД отсутствует/
  нечитаема, Then exit≠0, лог не изменён, в выводе причина.
- Приоритет: Must
- Источник: roadmap v4 §6, requirements 2.22.0 REQ-23A

### RQ-02 — Ровно один importer/writer

- История: Как владелец, я хочу один путь записи сигналов, чтобы цифры не
  расходились между сборщиками.
- Требование: Существует ровно один importer/writer этих сигналов; второй
  сборщик расхода не создаётся; чтение выполняется существующим
  `readSignalLog`, запись — существующим `appendSignal`.
- AC: В кодовой базе один модуль пишет usage-производные `run`-события; новых
  писателей `run` нет.
- Приоритет: Must
- Источник: roadmap §6, REQ-23A

### RQ-03 — Корректный run-итог и устойчивые ID

- История: Как владелец, я хочу повторно импортировать логи без двойного
  счёта, чтобы цифры не раздувались.
- Требование: Run-итог содержит модель, доступные токены, длительность,
  идентичности task/run/attempt; `run_id` различает запуски, `attempt` берётся
  из источника, `task_id` — только из подтверждённой явной связи; `event_id`
  воспроизводим, повторный импорт того же исходного события не создаёт запись.
- AC: Given два разных run одной задачи с `attempt=1` и повтор первого
  события, When импорт выполняется дважды, Then оба run входят ровно один раз,
  а повторное событие не добавляется.
- Приоритет: Must
- Источник: REQ-23A AC 1/8, roadmap §6 «Идентичность и повторный импорт»

### RQ-04 — Старые и неполные логи

- История: Как владелец, я хочу, чтобы старые логи читались, чтобы новая
  телеметрия не ломала историю.
- Требование: Старые записи (v1 без identity-полей), малформ-строки и
  неполные записи источника не роняют импорт; отсутствующие данные дают
  «неизвестно», а не 0; незавершённый turn не импортируется и не считается
  нулевым.
- AC: Given лог с v1-записями и битой строкой, When импорт и аналитика
  выполняются, Then падения нет, битая строка посчитана, v1-записи сохранены.
- Приоритет: Must
- Источник: REQ-23A «Старые логи читаются», roadmap §6

### RQ-05 — Токены не подменяются суррогатами, ограничения видны

- История: Как владелец, я хочу честные числа и видимые пробелы, чтобы не
  принимать решения по прокси.
- Требование: Токены берутся только из полей источника; `weighted` —
  существующая формула; `reasoning`/`cache.write` не добавляются к `output`
  второй раз, а их семантика помечена как неизвестная; стоимость не
  вычисляется; длительность — измеренное время turn, не длина ответа;
  ограничения источника перечислены в выводе и документации.
- AC: Given прогон импорта, Then вывод содержит блок ограничений с явными
  «неизвестно», и ни одно неизвестное значение не записано как 0.
- Приоритет: Must
- Источник: REQ-23A AC 3/4/6, roadmap §6

### RQ-06 — Совместимость и покрытие тестами

- История: Как владелец, я хочу, чтобы поставка не ломала существующие
  контракты.
- Требование: Публичная схема памяти (`SignalEventSchema`) не меняется, новых
  LLM-вызовов нет, `npm run check` зелёный, тесты адресные, fixtures источника
  и учёта добавлены, документация и генерируемые справочники синхронны.
- AC: `git diff` не содержит изменений `SignalEventSchema`; `npm run check`
  exit 0 на точной revision; есть fixture исходных записей и fixture лога.
- Приоритет: Must
- Источник: REQ-23A, roadmap §2 п.5, §13 гейт выпуска

## 5. Нефункциональные требования (NFR)

### NFR-01 — Совместимость с существующими логами

- Требование: Импорт и чтение обязаны работать с логом, содержащим записи v1
  без `event_id`/`schema_version`.
- AC: Тест на fixture-логе с v1-записями проходит; новые поля не обязательны.
- Источник: roadmap §14 NFR-01

### NFR-02 — Идемпотентность

- Требование: Повторный запуск импорта на неизменном источнике не добавляет
  строк в сигнальный лог.
- AC: Второй прогон: `appended=0`, размер лога не изменился.
- Источник: REQ-23A AC 1/8, NFR-08

### NFR-03 — Read-only доступ к источнику

- Требование: Источник открывается только на чтение; импорт не пишет в БД
  площадки.
- AC: Открытие с `readonly: true`; в коде нет DDL/DML по БД источника;
  недоступность на запись не влияет на работу.
- Источник: roadmap §2 п.13, safety

### NFR-04 — Стоимость прогона

- Требование: Размер источника — гигабайты, поэтому импорт ограничен окном
  (`--since/--until`) и не сканирует таблицу сообщений без индекса.
- AC: Окно по умолчанию — 1 сутки; запрос использует индекс по
  `time_created`/`session_id`; время прогона на окне 7 суток измерено и
  задокументировано.
- Источник: измерения среза (Slice Reality Check)

## 6. Ограничения и допущения

- Источник — локальная база площадки (OpenCode 2.2.5); другой площадки/версии
  в срезе нет. Отсутствие источника — честный отказ, не ноль.
- `task_id` не выводится из заголовков/имён агентов: только явная карта
  соответствия. Отсутствие карты = «неизвестно».
- `cost` источника недостоверен (0 при отсутствии прайсинга) — не
  импортируется.
- `cache.write` и `reasoning` есть в источнике, но их семантика относительно
  `output` не документирована — не смешиваются, помечены как неизвестные.
