# B0.5 — read-only git inspect — функциональные требования

## 1. Контекст и проблема

Агенты интерпретируют Git-состояние текстом (`git status`, `git log` глазами модели),
отсюда ложные «всё чисто» при недоступном remote, незавершённой операции или
расхождении с целью. Roadmap v4 ред. 9 (§11, B0.5) закрывает это одной
детерминированной read-only операцией: структурированный факт + вердикт вместо
текстовой интерпретации. Метрика успеха: L1 и B0/wolf-git читают один и тот же
машиночитаемый вывод и не собирают Git-состояние по-своему.

## 2. Область

Входит: одна read-only CLI-операция `wolf git-inspect` с JSON-выводом (факты,
вердикт `PASS | VIOLATION | UNKNOWN`, reasons, allowed_next_actions); текст
скилла wolf-git, ссылающийся на неё; unit- и e2e-проверки на реальном
состоянии.

НЕ входит: commit/push/cleanup/MR (B1); решение «можно ли писать» — это
полномочие задачи и B1; запись в память Wolf из самой команды; fetch или иное
изменение refs; CI/очередь интеграции (G/H).

## 3. Глоссарий

- **Вердикт** — `PASS` (все обязательные проверки выполнены, нарушений нет),
  `VIOLATION` (обнаружен факт, нарушающий ожидания), `UNKNOWN` (обязательная
  проверка не выполнена — не успех и не нарушение).
- **Наблюдение remote** — способ и время получения знаний о remote: `ls-remote`
  (живое) или tracking-ref (локальная копия, может устареть).
- **baseline** — SHA, от которого задача начата (передаётся входом
  `--baseline`); **target** — цель задачи, фиксируется входом `--target`; по
  заданному target требуется remote-наблюдение (иначе строка 9 таблицы
  решений даёт UNKNOWN); сравнение ветки с remote выполняется по её upstream
  (произвольная цель сравнения — вне среза, B1).

## 4. Функциональные требования

### REQ-01 — Структурированный факт Git-состояния

- История: Как L1-агент, я хочу детерминированный сбор Git-фактов одной
  командой, чтобы не интерпретировать текстовый вывод git самостоятельно.
- Требование: `wolf git-inspect [--baseline <sha>] [--target <ref>] [--owner <id>]`
  в cwd репозитория сообщает поля `repository`, `worktree`, `branch`, `head`,
  `baseline`, `target`, `dirty`, `unfinished_git_operation`, `local_vs_remote`,
  `branch_owner`, `freshness_of_remote_observation`; каждый факт указывает
  конкретные refs/SHA.
- Обоснование: ложное «всё чисто» при недоступном remote или незавершённой
  операции — наблюдаемая потеря качества работы агентов (roadmap §11).
- AC: на фикстурном репозитории вывод содержит все перечисленные поля с
  фактическими SHA/refs; вне git-репозитория — `UNKNOWN` с reason, не падение
  без вывода.
- Приоритет: Must
- Источник: roadmap v4 §11 (ред. 9); тред mem_20261103_srez_b0_5….

### REQ-02 — Вердикт с reasons и допустимыми действиями

- История: Как L1-агент, я хочу вердикт `PASS | VIOLATION | UNKNOWN` с
  объяснением, чтобы принимать следующее решение без переинтерпретации фактов.
- Требование: команда возвращает `verdict`, `reasons[]` (что именно проверено и
  с каким исходом) и `allowed_next_actions[]`; вывод завершается exit-кодом
  0 = PASS, 1 = VIOLATION, 2 = UNKNOWN. «Не удалось проверить» не приравнивается
  ни к PASS, ни к VIOLATION.
- Обоснование: надёжность следующего шага агента; UNKNOWN ≠ успех (B0 §«Гейт
  перехода»).
- AC: сценарии REQ-04 дают детерминированные вердикты по таблице решений
  design; exit-код соответствует вердикту.
- Приоритет: Must
- Источник: roadmap v4 §11; wolf-git SKILL.md «Гейт перехода».

### REQ-03 — Read-only и переносимость

- История: Как владелец проекта, я хочу гарантию, что inspect ничего не меняет
  и работает в любом репозитории, чтобы применять его без риска.
- Требование: используются только читающие git-команды и чтение файлов
  служебных каталогов; refs не меняются (без fetch/push/commit); команда не
  читает память Wolf и не зависит от harness; `branch_owner` заполняется только
  из входа `--owner`, иначе `null` («Wolf не знает»).
- Обоснование: границы §11: без commit/push/cleanup/MR; операция переносимая.
- AC: e2e-сценарий фиксирует REF-состояние до/после прогона (сравнение
  `git for-each-ref` + SHA HEAD) — идентично.
- Приоритет: Must
- Источник: roadmap v4 §11 (границы).

### REQ-04 — Честность remote-наблюдения

- История: Как L1-агент, я хочу явное различие «живое наблюдение» /
  «устаревшая локальная копия» / «remote недоступен», чтобы не принимать
  UNKNOWN за чистоту.
- Требование: при наличии upstream/remote сравнение выполняется живым
  `ls-remote` с таймаутом; недоступный remote → вердикт `UNKNOWN` с reason, без
  ложного `PASS`; деградация до tracking-ref помечается в
  `freshness_of_remote_observation`; remote не настроен → проверка
  неприменима (не ошибка, не блокирует PASS); время наблюдения фиксируется.
- Обоснование: кейс «всё чисто» при недоступном remote — исходная проблема
  среза.
- AC: e2e-сценарии «недоступный remote» → `UNKNOWN`; «нет remote» → PASS с
  reason «not applicable»; оба с фактическими прогонами.
- Приоритет: Must
- Источник: roadmap v4 §11 (приёмка); регламент B0 §6.5.

### REQ-05 — Стабильность и машиночитаемость

- История: Как потребитель вывода (L1 и B0/wolf-git), я хочу стабильный
  парсимый формат, чтобы встроить его в свои регламенты.
- Требование: вывод — единый JSON-объект в stdout с полем `schema_version`;
  повторный запуск на том же состоянии даёт тот же вердикт и те же
  факт-поля (время наблюдения может отличаться — это наблюдение, не факт
  состояния); изменение схемы — только через инкремент `schema_version`.
- Обоснование: roadmap §11 — «вывод стабилен и машиночитаем, повторный запуск
  даёт тот же результат».
- AC: e2e повторяет команду дважды на неизменном состоянии, сравнивает вывод с
  нормализацией временных меток — глубокое равенство.
- Приоритет: Must
- Источник: roadmap v4 §11 (приёмка).

### REQ-06 — Единственный сборщик, читаемый B0

- История: Как владелец архитектуры, я хочу один структурный сборщик
  Git-состояния, чтобы не плодить толкования.
- Требование: модуль среза — единственный структурный сборщик; текст
  wolf-git (B0) в §G0 ссылается на команду как источник структурного факта и
  убирает «структурного read-only git inspect … нет» из §«Что не поставлено»
  (часть про B1 остаётся).
- Обоснование: roadmap §11 — «второй сборщик Git-состояния не создаётся»;
  «тот же вывод читают L1 и B0».
- AC: в `templates/base/skills/wolf-git/SKILL.md` G0 содержит ссылку на
  команду; §«Что не поставлено» больше не заявляет inspect отсутствующим.
- Приоритет: Must
- Источник: roadmap v4 §11.

## 5. Нефункциональные требования (NFR)

### NFR-01 — Защита учётных данных

- Требование: URL remote в выводе очищается от встроенных учётных данных
  (`scheme://user:***@host/...`); команда не пишет ничего кроме JSON в stdout.
- AC: unit-проверка на URL с токеном — токен отсутствует в выводе.
- Источник: глобальные правила безопасности (не логировать секреты).

### NFR-02 — Бюджет времени

- Требование: локальные проверки без сети завершаются быстро (порядка сотен
  мс); сетевое `ls-remote` ограничено таймаутом 10 с, после чего remote
  считается недоступным (`UNKNOWN`), без зависания команды.
- AC: unit-проверка таймаута фейковым раннером; e2e-сценарий недоступности
  завершается без зависимости от реальной сети (фейковый/несуществующий
  remote-URL).
- Источник: roadmap §11 (детерминированность); регламент B0 §6.5.

### NFR-03 — Совместимость и стиль

- Требование: стек проекта (TypeScript, vitest); только стандартные git-команды
  (porcelain/plumbing, git ≥ 2.30); пользовательская поверхность (описание
  команды, строки вывода) — английский (гейт check-english-surface).
- AC: `npm run check` зелёный, включая english-surface и format.
- Источник: правила проекта.

## 6. Ограничения и допущения

- baseline/target — входы задачи, команда их не угадывает; отсутствие входа —
  отсутствие соответствующей проверки (не ошибка).
- «Позади remote» может быть не посчитано в коммитах без fetch (refs не
  меняются): фиксируется отношение и SHA, счёт честно `null`.
- Версионация: срез входит в следующий релиз после 2.26.0; номер релиза —
  вне scope этого документа.
