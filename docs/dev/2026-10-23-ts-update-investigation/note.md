## 1. Резюме (вердикт)

Гипотеза владельца различена. **H1 опровергнута**: обновление trading-signal
выполнялось — CLI прошёл 2.9.0 → 2.18.5, `wolf sync` запускался минимум раз
(2026-10-12, штампы 2.16.2). **H2 подтверждена как доминирующая причина**:
процесс обновления не переносит канонические лица в память — `wolf sync`
никогда не трогает память (по дизайну D4), посев лиц делает только `wolf
init`; шаблон executor-lead появился в base-set в **v2.11.0 (2026-09-28)** —
через 6 дней после init trading-signal (2026-09-22), поэтому у
executor-lead в памяти проекта никогда не было ни лица, ни legacy-записи →
100% fallback (16 967 промахов, 91% всех промахов проекта). **H3 подтверждена
как факт, но не как причина для trading-signal**: face-объектов нет нигде на
машине, включая сам mister-wolf 2.18.5 (`wolf face resolve executor-lead` →
`kind=none`); при этом каноническая доставка executor-lead возможна и была —
в mister-wolf 10-07…10-09 доставлена ×1 074 через legacy-путь, а текущие
промахи mister-wolf — отдельный дефект данных (v2 superseded v1 без
`owner_skill`). Версия CLI не является различающим фактором промахов.

## 3. Механизм: откуда берётся лицо и что переносит обновление (AC2)

### 3.1 Резолв лица в плагине (2.18.5, `templates/opencode/plugins/wolf-router.ts`)

1. `resolveFaceCanonical` (строка 161) вызывает `wolf face resolve <agentId>`
   — строгий запрос `type=face, status=active, owner_skill === agentId`
   (`src/app/use-cases/resolve-face.ts:36`, появление **2.18.4**). Ровно одно
   активное лицо → доставка `variant=canonical`; `multiple` → конфликт,
   `none` → legacy-путь (2.18.5: конфликт/ошибка не гасятся текстовым
   поиском).
2. Legacy-путь: `wolf search <agentId> playbook --hide-superseded` + гварды
   (`owner_skill === agentId | skill:<agentId>`, тип `note|howto|playbook`,
   статус `active`) → первый прошедший кандидат доставляется как canonical.
3. Ничего не найдено → встроенный `FALLBACK_PLAYBOOK`, в лог
   `name=fallback variant=fallback`.

Fallback-плейбук в плагин вшит (константа), source поставщика — только память
проекта. Таблицы «какой агент какое лицо получает» в конфиге нет: реестр —
сами объекты памяти через `owner_skill`.

### 3.2 Путь появления лица в памяти проекта

| Механизм                 | Что делает                                                                                                                                                                                                                                                               | Версия          |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------- |
| `wolf init` (full) посев | `seedBasePlaybooks` (`src/app/use-cases/seed-base-playbooks.ts`): на каждый шаблон `templates/base/playbooks/*.md` — создать face v1 (initiator=seed); при живом лице — skip/шаблонное обновление; при 2.16.3-популяции — посев + поглощение legacy-head одной операцией | лица — с 2.17.0 |
| `wolf face migrate`      | конверсия legacy note→face (идемпотентная)                                                                                                                                                                                                                               | 2.17.0          |
| `wolf face new`          | новая версия лица (только Стюард)                                                                                                                                                                                                                                        | 2.17.0          |
| `wolf sync`              | **только штампованные файлы шаблонов** (agents/skills/commands/plugins/AGENTS.md); «память (.wolf/, seeded playbook'и) НЕ трогается никогда» — комментарий `src/app/use-cases/sync-base-set.ts:6`; мутировавшие файлы не перезаписывает (2.18.0)                         | —               |

Ключевой пробел пути обновления: CHANGELOG upgrade notes после каждого
релиза говорят «run `wolf sync`», но sync **не сеет лица и не переносит
каноны**; посев новых владельцев — только повторный `wolf init --full`
(нужен отдельный осознанный шаг, в процессе обновления его нет).

### 3.4 Есть ли лицо executor-lead в mister-wolf 2.18.5 (проверка H3)

**Нет.** face-объектов в mister-wolf ноль (нет `.wolf/shared/faces/`, ноль
событий `type=face`); `wolf face resolve executor-lead` → `{"ok":false,
"error":{"kind":"none"}}`. Сам эталонный репо живёт на legacy-пути: с
2026-09-29 (посев `wolf-init`, v1 c `owner_skill=executor-lead`) по
2026-10-09 deliveries были каноническими (×1 074), затем v1 был superseded
объектом v2, у которого **`owner_skill: null`** (`created_by: mr-wolf`,
агент создал note в обход face-контракта) → гвард владельца отсекает
кандидата → с 2026-10-09 у executor-lead в mister-wolf снова 100% fallback
(4 253 промаха и ни одного canonical после 10-09). Это независимый дефект
данных, не отставание версии.

## 5. Вердикт по гипотезам (AC3)

### H1 «обновление trading-signal никогда не выполнялось» — ОПРОВЕРГНУТА

Evidence against: непрерывная история CLI-версий в session-metrics (11 версий
с 09-07 по 10-23); sync-проход 2026-10-12 19:15–19:16 (корень + iaac; штампы
и sync-state). Синхронизация и обновления происходили — но реже, чем релизы
(последний sync 2.16.2 при актуальном тогда 2.17.x).

### H2 «обновление выполнялось, но процесс не переносит faces» — ПОДТВЕРЖДЕНА, доминирующая (~91% промахов)

Evidence for: (а) `wolf sync` не трогает память — код и комментарий
`sync-base-set.ts`; (б) посев лиц — только `wolf init`, а init
trading-signal (2026-09-22) прошёл до появления шаблона executor-lead
(v2.11.0, 2026-09-28, E5); (в) в памяти проекта нет ни лица, ни legacy-записи
executor-lead → 0 canonical за всю историю лога; (г) повторного init/seed не
было (0 face-объектов, 0 посевов после 09-22).
Evidence against (уточнение): лаг запуска sync (с 10-12 не запускался) —
реальный, но различающего значения не имеет: даже плагин 2.18.5 без объекта
в памяти дал бы тот же fallback.

Вклад: executor-lead = 16 967 из 18 576 промахов = **91.3%**. Из 48% общей
доли промахов проекта ≈ 44 п.п. — H2.

### H3 «канонического лица executor-lead нет нигде по дизайну/пробелу версии» — ЧАСТИЧНО ПОДТВЕРЖДЕНА, причинно НЕ подтверждена для trading-signal

Evidence for: face-объектов нет нигде на машине, включая mister-wolf 2.18.5
(E1); face-механизм (2.17.0+) ни разу не активирован ни в одном проекте парка.
Evidence against (как причина промахов TS): каноническая доставка
executor-lead технически возможна и наблюдалась (mister-wolf 10-07…10-09,
×1 074, legacy-путь — v1 с корректным `owner_skill`); шаблон executor-lead
поставляется с v2.11.0. То есть «лица нет нигде» — следствие того же пробела
H2 (никто не сеял), а не отсутствие канона в поставке. Отдельно: текущие
промахи mister-wolf по executor-lead — дефект данных (E2/E3: v2 без
`owner_skill` superseded v1), тоже не «дизайн-пробел версии».

Вторичные промахи TS (mr-wolf 898 + воркеры/стюард 711 = 8.7%): вероятностный
legacy-поиск (E4) — устраняется детерминированным face-резолвером, который
ещё нигде не включён (нет лиц). ≈4 п.п. из 48%.

## 6. Рекомендации (без реализации)

### Для trading-signal (последовательность шагов, выполнять владельцу проекта)

1. `wolf sync` (глобальным CLI 2.18.5): обновит wolf-router до 2.18.5
   (канонический face-резолвер, конфликт-гварды) и базовый набор;
   мутированные файлы не тронет, конфликты покажет в отчёте sync.
2. `wolf init --full --yes` (live-проект: штампованные файлы не
   перезаписываются, подтверждение через `--yes`): сидирует недостающие лица
   по face-контракту — executor-lead получит face v1 из шаблона; владельцы с
   legacy-записями (worker-\*, стюард, wolf-review) — посев с поглощением
   legacy-head одной атомарной операцией (2.17.1).
3. Проверка приёмки: `wolf face list` показывает executor-lead; ближайшие
   строки router.log для executor-lead — `variant=canonical`; `wolf doctor`
   без жалоб на лица.
4. Опционально: прогнать те же шаги для iaac (там уже есть базовый набор
   2.16.2); mt5-edge-lab/trading-hub требуют сначала установки
   плагина/платформы (router.log отсутствует — доставки не идут вовсе).

### Для mister-wolf (собственный дефект, найден в ходе расследования)

Стюарду создать face executor-lead (например, `wolf face new` из тела v2 с
корректным owner_skill или migrate+new), иначе эталонный репо продолжает
отдавать fallback по executor-lead (с 10-09 — 100%).

### Системный фикс (связь с Волной 2.19.0 — тред mem*20261015_volna_2_19_0*…)

- Замкнуть петлю «статистика роутера → недостающие лица»: авто-детект топ-N
  владельцев с промахами и без лица → автогенерация/предложение face
  (`wolf propose` / Стюард в async-learning). Это устраняет класс «init до
  появления посева» для всего парка разом.
- `wolf sync` должен репортить владельцев base-set без живого лица (сейчас —
  только orphaned-файлы); upgrade notes — упоминать re-init посев при
  появлении новых агентов в наборе.
- Детерминизм: перевод парка на face-резолвер (посев лиц) устраняет и
  вторичные вероятностные промахи (E4).

## 7. Ограничения и открытые вопросы

- variant-метки в router.log существуют только с установки T012-плагина (у
  trading-signal — с 2026-10-12): доли промахов до этой даты неизмеримы;
  16 725 ранних доставок вошли в знаменатель 48% без вариантной атрибуции.
- 45 вызовов 2.18.4 в метриках trading-signal (10-16…10-19) при глобальном
  CLI 2.17.1 до 10-23 — источник вызова не установлен (вероятно, npx или
  локальная установка); на вердикт не влияет. Также это уточняет утверждение
  записки аналитики «вызовов 2.18.x в метриках нет» — для trading-signal они
  есть с 10-15.
- session-metrics trading-signal начинается 2026-09-07 — более ранняя история
  версий (память проекта живёт с 2026-07-28) недоступна; init 2026-09-22 —
  единственный наблюдаемый посев, более ранних посевов в events.jsonl нет.
- Числа промахов (18 576 и др.) — на момент снятия слепка 2026-10-23; лог
  растёт, возможен дрейф ±1%.
