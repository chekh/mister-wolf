## 3. Глоссарий

| Термин | Значение |
| --- | --- |
| Консоль | локальный web-сервис wolf-console поверх общих прикладных операций Wolf |
| O1 / U1 / U2 | направления: наблюдаемость и хранение / первая рабочая консоль / управление эволюцией (roadmap §3) |
| Веха U1 1/2/3 | чтение / поддержанные write-операции / сквозное поручение |
| Срез | единица поставки с собственной приёмкой; фронт O1+U1 = 2 активных среза |
| Read-model | производные агрегаты/снимки для чтения; восстанавливаемы из источников, не нормативны (N01) |
| Снимок | компактная фиксация состава/размеров памяти на дату |
| Водяной знак (watermark) | зафиксированный обработанный диапазон источника агрегатором |
| Диагностика | сырые телеметрические строки (signals, router.log, skill-invocations, legacy run-log) — ротируемый класс |
| Значимая история | events.jsonl, версии лиц и face-операции, relations, evidence, журнал операций консоли — не ротируются политикой диагностики |
| Поручение | сохранённый запрос человеку-агенту (пересмотр/агрегация) с идентичностью, входами и наблюдаемым исходом ([01-F24]) |
| Операция консоли | одно пользовательское действие через web-адаптер с operation ID и зафиксированным исходом ([01-F25], [03-M28]) |
| Writer / write-path | штатный писатель/путь изменения данных Wolf (общие use-cases, не консольные дубли) |
| Effective skill | текст инструкции, фактически доступный харнессу в каталогах скиллов (доступность ≠ доставка ≠ применение) |

## 5. Ответы на design-вопросы 1–7

Каждый подраздел: вопрос → ответ → трассировка → границы/остаток.

### Q1. Минимальная сохраняемая операция поручения и чтение её итога

**Ответ.** Минимальной сохраняемой операцией является **объект проектной памяти** (поручение): создаётся штатным `e93d733:src/app/use-cases/add-memory-object.ts:addMemoryObject` с `actor=user:console`, типом из проектной таксономии (по умолчанию `note`), `memory_class=working`, статусом `open`; точные ID и revisions входов фиксируются в теле поручения ([01-F13]) и связями через штатный `e93d733:src/app/use-cases/record-relation.ts:recordRelation` (существующие предикаты `RelationLog`, точный выбор предиката — проверяемый факт среза, не новое полномочие). Итог читается по ID поручения: его статус (переходы через `ALLOWED_TRANSITIONS`, `e93d733:src/domain/governance.ts:35`), события `memory.*` по `memory_id`, результат-объект по связи/`superseded_by`. Исполнение передаётся существующему механизму — следующим рабочим сессиям проекта, которые читают память штатно (get/search/recap); **очереди и немедленного исполнения U1 не обещает**: отсутствие исполнителя видно как открытый статус и время ожидания ([01-F28], [06-S05]). Узкий срез надёжности = (i) durable-сохранение в проектной памяти (locks/events уже есть), (ii) идемпотентность операций консоли по operation ID (§6), (iii) фиксация исхода в журнале операций консоли. Новая очередь/TaskState-store не создаётся (граница 1, ADR-06).

**Трассировка:** [01-F24, F25, F27, F28], [03-M27, M28], [06-S05, S11]; roadmap §3 (веха 3), §11/F.
**Границы/остаток:** активная доставка Стюарду (durable inbox) — направление F, вне U1; веха 3 требует видимости поручения в штатных поверхностях проекта, но не гарантии срока исполнения.

### Q2. Авторитетный источник installed/effective skill и его истории; ручные изменения до D2

**Ответ.** Авторитетный источник **installed** — фактические файлы скиллов в scope-каталогах харнесса: project `.opencode/skills/**`, global `~/.config/opencode/skills/**`, и эталон набора `templates/base/skills/**` пакета установленной версии (это то, что пишет `wolf upgrade`). **Effective** определяется харнессом (OpenCode загружает скиллы из этих каталогов); консоль показывает «доступно в scope», а не «доставлено в сессию» — доставка фиксируется только `skill-invocations.jsonl` плагина ([03-M14]). **Истории версий скиллов как механизма в Wolf нет** — происхождение выводится правилом: (a) project-scope → «проект»; (b) global-scope, побайтово совпадает с `templates/base/skills` установленной версии X.Y.Z → «поставлен пакетом X.Y.Z»; (c) не совпадает → «ручное изменение относительно пакета X.Y.Z, автор неизвестен». Никаких догадок о старых правках ([02-R08]). Ручные изменения в U1 до D2: консоль **не пишет скиллы**; для скилла доступно чтение, diff с эталоном пакета и адресное поручение на корректировку (Q1). Причина: версионирующего writer'а скиллов в ядре нет, а «простое изменение произвольного файла из браузера» явно недостаточно ([01-F19, 01-§«Лица и скиллы»]); полномочия faces на skills не переносятся (границы ред. 11).

**Трассировка:** [01-F16–F19], [03-M21, M22], [06-S07, S08]; `07-source-map` «История скилла задана fixture».
**Границы/остаток:** версионирующий writer скиллов — открытым вопрос №5 (рекомендация: поручение в U1, writer — с D2-подготовкой); интерфейс карточки скилла проектируется совместимым с будущими version-полями D2 (unknown-плейсхолдеры).

### Q3. «Объединить заметки» через ограничения aggregate

**Ответ.** Существующий путь жёсток: `e93d733:src/app/use-cases/apply-aggregate.ts:applyAggregate` принимает агрегат `proposed|active` и архивирует исходники по рёбрам `aggregates`; FIX-AGG (§5, не закрыт) добавит preflight «только active lessons». Допустимый смысловой маршрут для пользовательского «объединить заметки» в U1 — **двухшаговый и явный**: (1) пользователь выбирает записи; UI показывает допуск каждой записи к агрегации по тем же правилам preflight (тип lesson, статус active, наличие источников, self-link, scope) — до любых мутаций ([06-S05] «видно до изменения источников»); (2a) для **active lessons** — штатное создание proposed-агрегата (add + relations `aggregates`) и позже `applyAggregate` в срезе U1-s2 после FIX-AGG; (2b) для **рабочих note** — консоль не меняет type/status молча: пользователь (или Стюард по поручению Q1) создаёт новую canonical-запись с основанием и связями на исходные note (`recordRelation`), а исходные note архивирует отдельным явным действием через штатный `transition`. Автоматического смыслового переноса нет; самовольное изменение смысла типов запрещено ([01-§Память, 00-§«Границы»]).

**Трассировка:** [01-F13, F14], [06-S05]; roadmap §5 FIX-AGG, §13 («FIX-AGG обязателен до включения соответствующего write-пути U1»).
**Границы/остаток:** кнопка apply в UI отсутствует до FIX-AGG и среза U1-s2 (веха 2: только выбор+сохранение поручения).

### Q4. Доступные для записи документы; Git policy и revisions источника

**Ответ.** Разделение по `source` объекта (`e93d733:src/domain/schemas/memory-object-schema.ts`): запись через консоль доступна только объектам, чей авторитет — память Wolf (`source.kind = manual | session`); объекты, зарегистрированные по ссылке на файл (`source.kind = file`, `source.path`), консоль **только читает** — правка канона это правка файла проекта, вне U1 (граница «регистрация ≠ копирование»). Проектная Git policy учитывается через закрытый B0.5: `e93d733:src/adapters/cli/commands/git-inspect.ts` (детерминированный read-only сбор Git-состояния с вердиктом `PASS | VIOLATION | UNKNOWN`, reasons, allowed_next_actions) — консоль показывает этот вердикт и **не предлагает** git-мутаций (B1 не поставлен). Revision источника: HEAD репозитория проекта на момент чтения (из git-inspect) + mtime файла; пофайлового/blame-уровня U1 не даёт — честная граница «точность = HEAD».

**Трассировка:** [01-F09–F11, F15], [06-S03, S04]; roadmap §3 (B0.5 закрыт 2.27.0).
**Границы/остаток:** правка зарегистрированных файлов и Git-операции из консоли — вне U1 (B1/универсальный редактор исключены [01-§«За пределами»]).

### Q5. Минимальные metadata O1/U1; где нужен versioned schema change

**Ответ.** Уже есть (проверено RC): события `memory.*` с `actor` в `events.jsonl`; сигнальный лог `SignalEvent` (`session-metrics-log.ts`, writers `appendTaskEvaluatedSignal` :464-482, `appendMemoryStageSignal` :497-516, `runEntriesFromSignals` :529-544); `router.log` плагина; `skill-invocations.jsonl`; реестры сессий (`session-delivery-registry.ts`, TTL 7 дней — прецедент GC); relations; face-операции с `opId` (`face-operation.ts:generateOpId` :109-111); реестр проектов. **Добавляются O1/U1 (новое, минимально):** (1) водяные знаки/покрытие агрегатора (`coverage.json`: источник, первый/последний обработанный ts, разрывы) — носитель [03-M31]; (2) дневные снимки состава/размеров (`snapshots.jsonl`); (3) журнал операций консоли `.wolf/console/operations.jsonl` (operation ID, action, target, revision, actor, исход, ts) — носитель [03-M28] и идемпотентности [01-F27]; (4) постоянные агрегаты (дневные бакеты). **Versioned schema change публичной схемы не требуется**: `SignalEvent` не расширяется (граница REQ-23A, roadmap §6), `MemoryObject` не меняется; все новые файлы — собственные контракты с `schema_version` в записи, эволюция — в своём scope ([04-§«Откуда получать информацию»]). Дефекты семантики исправляются в расчётах (§7b), не в схеме.

**Трассировка:** [03-M28, M31], [04-§Классы данных]; roadmap §6 (разводка A1.1/O1/E2).
**Границы/остаток:** расширение публичной схемы (provenance/completeness) — E2, не здесь.

### Q6. Окна и лимиты диагностики, агрегатов, истории; признаки допустимого удаления

**Ответ — разделом §7c** (limиты — предложение, финальные числа — открытый вопрос №4). Ключевое правило допустимости удаления диагностики — **классовое**: ротация физически применяется только к файлам диагностического класса (signals jsonl, `router.log`, `skill-invocations.jsonl`, legacy run-log); файлы значимой истории (`events.jsonl`, версии лиц/face-операции, relations, evidence, журнал операций консоли, snapshots? — нет, снимки отдельно) политикой диагностики **не затрагиваются**. Дополнительно строка диагностики удаляется только если: (1) её бакет агрегирован и водяной знак зафиксирован; (2) нет незавершённой операции, ссылающейся на диапазон (открытые face-op/поручения проверяются по своим записям, не по диагностике); (3) файл принадлежит диагностическому классу. Снимки ротируются отдельно (возраст), агрегаты — бессрочно.

**Трассировка:** [04-§«Что определить в O1», §«Переход со старых логов»]; roadmap §2 п.16, §3 критерии (a)–(c).

### Q7. Показ источника, периода покрытия и неизвестного старого следа

**Ответ.** Каждая сводка/панель несёт явный блок покрытия (носитель [03-M31], данные `coverage.json`): источник → первое/последнее наблюдение, обработанный диапазон, известные разрывы, граница детальной диагностики (после ротации drill-down за границей недоступен — показывается агрегат и подпись, а не пустая таблица [04-§«Переход со старых логов»]). Старые события без достоверного `actor`/версии показываются как «историческое изменение, автор не определён» либо отдельным историческим счётчиком без атрибуции ([04-§«Переход со старых логов»]); unknown ≠ 0, отсутствующий источник ≠ нулевой результат (N06). Единый «процент coverage» без известного знаменателя не вычисляется ([03-M31] граница).

**Трассировка:** [01-F06, F08], [03-M31], [06-S12, S13]; N06/N07.

### 6.2 Изоляция контекста проекта

Каждый запрос несёт идентификатор проекта; путь резолвится **только** по записям `ProjectsRegistry.list()` — произвольные пути из запроса отвергаются (N02). Контейнер зависимостей создаётся на запрос по baseDir проекта (прецедент `createCliContainer`, `memory-complain.ts`); глобального мутируемого контекста нет — две вкладки с разными проектами не влияют друг на друга ([06-S01]).

### 6.3 Loopback, CSRF, опасный контент (N02/N03)

- Слушаем `127.0.0.1` только; проверка `Host` ∈ `{127.0.0.1[:port], localhost[:port]}`.
- Мутирующие запросы: `Content-Type: application/json` + обязательный негласный заголовок `X-Wolf-Console: 1`; CORS-заголовки не отдаются вовсе → кросс-origin fetch и простые формы блокируются браузером. Токен не требуется по умолчанию; опция `--token` — открытый вопрос №3.
- Тела Markdown/документов — **данные**: рендер экранированным текстом, без исполнения HTML/скриптов и инлайн-SVG; внешние ссылки `rel="noopener noreferrer"`. API отдаёт JSON; UI не собирает `<img src>` из пользовательских тел (защита от запросов во внутреннюю сеть).
- Секреты (ключи, settings) в API не отдаются.

### 6.4 Владение состоянием

Авторитет — существующие store'ы проекта (memory store, events, relations, face-версии) и глобальный реестр. Консоль владеет только: **производными** данными (агрегаты/снимки/coverage — восстанавливаемы полным пересчётом из источников, N01) и **журналом операций консоли** (новый постоянный файл; класс «история значимых операций» [04-§Классы] — не ротируется, мал по построению: ≤1 записи на пользовательское действие). Браузер не является хранилищем (анти-паттерн макета «localStorage», `07-§«Где макет упрощает»`).

### 6.5 Конкурентность и инварианты

Существующие `MemoryLock` (`src/ports/memory-lock.port.ts`; `edit-memory-object.ts:88` уже под lock) и `ALLOWED_TRANSITIONS` сохраняются; консоль не обходит guards, `protect`-файлы и запрет редактирования face через edit (`edit-memory-object.ts:47-51`). Для F12 добавляется revision-guard: `editMemoryObject` получает опциональный `expected_updated_at` — при несовпадении отказ «конфликт», пользователь заново открывает актуальное содержание (ADR-10; обратная совместимость: параметр опционален). Инварианты: одна active-версия лица (детерминизм `face-operation.ts:activeFace` :87-91), идемпотентность `applyAggregate` (повтор дозавершает, `apply-aggregate.ts:21-29`).

### 6.6 Отказы зависимостей, частичный сбой, восстановление, idempotency

- Недоступный проект: `missing` без удаления из реестра (`build-projects-list.ts:77-80`), экран проекта показывает диагноз ([06-S01]).
- Операция консоли: клиент генерирует operation ID; все мутации записывают в журнал «начата → исход». Повтор запроса с тем же ID: исход подтверждён → возвращается записанный результат без повтора; исход `unknown` (потерян ответ после записи) → повтор запрещён до выяснения по ID ([06-S11], F27) — UI показывает «исход неизвестен, проверьте объект».
- Частичный сбой: FS нетранзакционен (прецедент `apply-aggregate.ts:24-26`) — дозавершение штатными повторами, незавершённость видима как статус.
- Восстановление: агрегаты/снимки пересобираются из источников; консоль без своих производных файлов остаётся работоспособной (деградация: сводки пересчитываются дольше, детальный drill-down в границах окна).

| Граница | Переход | Контроль |

### 7b. Решения по 4 дефектам семантики (мини-ADR)

**ADR-01: uses = обращения, не «доставки + любые события».**
Контекст: `e93d733:src/app/use-cases/build-analytics.ts:537-559` — `uses = deliveries + triggers`, где triggers — любое событие с `memory_id`, включая изменения объекта; комментарий в коде сам называет это прецедентом readIds. Выбор: в ledger `uses` считать из retrieval/injection фактов (M03/M04: сигналы `memory_stage` retrieved|injected и delivery; уникальные id), `triggers` переименовать в `touches` (любые события по id) и не суммировать с deliveries; исправление в общем расчёте — CLI и web получают одинаковую семантику. Последствия: колонка uses меняет смысл (меньше или равна прежнему); CHANGELOG обязателен (открытый вопрос №6). Проверка: unit-фикстура «update объекта не увеличивает uses; retrieved — увеличивает».

**ADR-02: applied исключается из delivery view.**
Контекст: `build-analytics.ts:1003-1058` — delivery считается applied, если в той же CLI-сессии позже был get/search этого id — это чтение, не применение ([02-§«Извлечение, доставка и применение»]). Выбор: убрать join; панель показывает deliveries (+bytes), applied — «источник отсутствует, unknown» до появления писателя (M09 вне O1). Альтернатива (переименовать в retrieved_after_delivery) отклонена: создаёт третий псевдостатус. Последствия: поле applied исчезает из вывода. Проверка: панель не содержит applied-числа; export сохраняет unknown (N06).

**ADR-03: единица вмешательства Стюарда = операция, не событие.**
Контекст: `build-analytics.ts:1660-1671` — сводка mutations считает все мутации; признак «auto» только по `actor === 'system:wolf'`; шаги одной face-операции умножают счётчик. Выбор: вмешательства Стюарда = уникальные операции с actor-идентификатором Стюарда (действующий идентификатор из множества агентов, см. `memory-complain.ts:BASE_AGENT_IDS`), сгруппированные по `opId` (face) или по событию (memory-мутации без opId); прочие actor'ы — отдельно (человек/агент/система). Последствия: сводка steward-interventions ≤ прежнего mutations. Проверка: фикстура [06-S13] — семь шагов одной face-операции = 1 вмешательство; правка пользователя не считается.

**ADR-04: воронка жалоб — только объекты complaint.**
Контекст: `build-analytics.ts:1673-1684` — resolved/rejected считаются по всем событиям `memory.resolved`/переходам в rejected, а не по жалобам. Выбор: filed/resolved/rejected/time-to-close соединяются с объектами типа complaint по `memory_id`; некомплейнтные события в воронку не попадают. Последствия: числа воронки уменьшаются; legacy-жалобы без связи остаются в filed без исхода. Проверка: фикстура «memory.resolved обычного объекта не влияет на воронку».

История перераспределения классов (M19) начинается с baseline-снимка — прошлое не выдумывается.

**Критерии ред. 11 явно:** (a) измеримость — лимиты объёма/срока конкретны и проверяются на характерном наборе проектов (AC O1-s1, вопрос №9); (b) enforcement в ядре — GC вызывается точками записи/CLI ядра, тест «ротация выполняется при остановленной консоли»; (c) значимая история/provenance/evidence сохраняются — классовое разделение + негативный тест «GC не удаляет events/relations/face-операции/operations.jsonl».

**Граница первого полезного U1 = вехи 1–2** (работающий сервис с чтением и поддержанными правками) — после неё стартует D1 (roadmap §3/§16). **Закрытие U1 = веха 3** с honest-остатком неготовых операций: прямая правка скиллов (нет writer'а — поручение), trial/verdict/откаты (D1/U2), активная доставка поручений (F), расходы Стюарда (M18 unknown), удалённый доступ/роли (вне первой версии). Read-only (веха 1) — промежуточный шаг, не закрытие U1.

## 9. План перехода к реализации

Фронт O1+U1 = два активных среза (граница 7). Порядок: **O1-s1 → (старт U1-s1 параллельно после стабилизации контрактов O1-s1) → U1-s2**; одновременно активны ≤ 2.

### Срез O1-s1 «источники и исправления» (измерительный)

- **Цель:** исправленная семантика + агрегаты/снимки/покрытие + enforcement лимитов в ядре — без UI.
- **Самостоятельный результат:** `wolf analytics` (CLI, `src/adapters/cli/commands/analytics.ts`) показывает исправленные показатели и блок покрытия; ротация работает без консоли.
- **AC:** (1) 4 фикстуры дефектов (ADR-01–04); (2) повторный проход агрегатора/перезапуск/позднее событие не удваивают сводки, разрыв виден ([06-S12] ядро); (3) ротация выполняется при остановленной консоли (критерий (b)); (4) негативный тест: GC не удаляет значимую историю (критерий (c)); (5) на характерном наборе проектов диагностика после GC ≤ лимита (критерий (a)); (6) legacy-проход строит агрегаты до первой ротации, автор-unknown не выдуман.
- **Компоненты:** `build-analytics.ts` (правки), новые `aggregate-telemetry.ts`, `telemetry-gc.ts`, `.wolf/analytics/*`; точка вызова GC — `src/adapters/fs/session-metrics-log.ts:appendSignal` (пост-запись) и CLI-входы.
- **Зависимости:** нет (A1.1 закрыт 2.23.0; источники существуют). Не переоткрывает importer/REQ-23A (roadmap §6).

### Срез U1-s1 «консоль: вехи 1–2» (инфраструктурный; первый полезный U1)

- **Цель:** работающая локальная консоль чтения и поддержанных правок.
- **Самостоятельный результат:** `wolf console` → сервис: проекты, обзор, память/документы, лица/скиллы, правки с конфликтом, жалоба, сохранение поручения.
- **AC:** S01 (изоляция), S02 (drill-down/периоды), S03 (конфликт revision), S04 (семантика удаления/архива), S06 (жалоба), S07 (происхождение), S11 (идемпотентность по operation ID), S13 (единицы/unknown), S14-подмножество (бюджеты §13, клавиатура/узкий экран); негативные: произвольный путь в API отвергается, markdown не исполняется, CORS отсутствует.
- **Компоненты:** новые `src/adapters/web/**`, `src/adapters/cli/commands/console.ts`, `.wolf/console/operations.jsonl`; правка `edit-memory-object.ts` (ADR-10); переиспользование use-cases §6.1 и read-model O1-s1.
- **Зависимости:** O1-s1 (контракты показателей обзора до потребителя — roadmap §13); **FIX-AGG не требуется** (apply-путь не подключается).

### Срез U1-s2 «сквозное поручение» (веха 3, закрытие U1)

- **Цель:** поручение сохранено → передано → читаемый исход.
- **Самостоятельный результат:** поручение агрегации/пересмотра с точными ID/revisions входов, наблюдаемым исходом; apply агрегата в UI; судьба исходников видна.
- **AC:** S05 (полностью), S12 (в UI-части), F24–F28; apply в UI доступен **только** при закрытом FIX-AGG (preflight виден до мутаций, невалидный набор не меняет объекты).
- **Компоненты:** web-adapter (новые маршруты), поручения как объекты памяти (Q1), `apply-aggregate.ts` подключение, M26/M27-представления.
- **Зависимости:** U1-s1; **FIX-AGG (§5, не закрыт) — жёсткое предусловие write-пути агрегации**.

## 12. ADR-карточки существенных решений

> ADR-01–04 (дефекты семантики) — полные карточки в §7b (контекст/выбор/последствия/проверка; альтернативы указаны в тексте).

**ADR-05: тонкий web-адаптер `src/adapters/web/`, без API-платформы.**
Контекст: HTTP-сервера в `src/` нет; граница 2 запрещает отдельную API-платформу перед первым экраном. Альтернативы: полноценный REST-контракт v1 на все сущности; MCP-поверхность. Выбор: adapter-слой с маршрутами строго под экраны, вызывающий существующие use-cases; новые прикладные операции (журнал, read-model) — общие, не web-приватные. Последствия: контракт API меняется вместе с экранами (не публичный); CLI и web делят операции. Риск: дрейф дублированием логики в adapter — сдерживается ревью (логика только в use-cases). Проверка: в `src/adapters/web/` нет обращений к fs хранилищам напрямую, только к use-cases/портам.

**ADR-06: поручение = объект проектной памяти, без новой очереди.**
Контекст: Q1/F24; очередь/TaskState-store запрещены (граница 1), F (async) не является предпосылкой U1. Альтернативы: отдельный job-файл; complaint-объект для поручений. Выбор: память проекта (durable, locks, события, переходы уже есть) + идемпотентность операций консоли + журнал операций. Поручение ≠ жалоба (разные назначения, [02-R04]). Последствия: нет гарантии срока исполнения — видимость ожидания вместо неё ([01-F28]). Риск: поручение не замечено исполнителем — смягчается видимостью в списках/обзоре (M27). Проверка: [06-S05] — обновление страницы не теряет запрос; недоступный исполнитель = ожидание.

**ADR-07: производные данные — файлы `.wolf/analytics/` и `.wolf/console/`, без СУБД.**
Контекст: вопрос №2; [04-§«Физическое размещение»]. Альтернативы: SQLite; память процесса. Выбор: JSONL/JSON на проект, `schema_version` в записи. Последствия: пересчёт вместо миграций при изменении формата. Риск: большие логи → медленный первый пересчёт — инкрементальность по водяным знакам; spike-1. Проверка: удаление каталога `.wolf/analytics/` не ломает консоль (пересборка).

**ADR-08: enforcement лимитов в ядре (writer/GC), не в консоли.**
Контекст: критерий (b) ред. 11 — остановка/отсутствие консоли не отменяет ротацию. Альтернативы: GC в web-сервере; отдельный daemon. Выбор: GC в use-case слое (`telemetry-gc.ts`), вызов из `appendSignal` (пост-запись, best-effort, без падения основной операции) и CLI-входов проекта. Последствия: консоль не отвечает за ротацию. Риск: редкая работа CLI в «спящем» проекте — лимит объёма сработает при следующей записи, что соответствует правилу. Проверка: тест ротации без поднятого сервера.

**ADR-09: скиллы в U1 — чтение + адресное поручение, writer не создаётся.**
Контекст: Q2; [01-F19] и позиция пакета о недостаточности правки файла из браузера; право faces ≠ право skills. Альтернативы: файловый writer уже в вехе 2; отложить чтение тоже. Выбор: чтение/diff/поручение сейчас, writer — с D2-подготовкой (вопрос №5). Последствия: ручная правка скилла вне консоли остаётся файловой (видна как drift). Риск: пользователь ждёт D2 для правки — честный остаток вместо скрытой кнопки. Проверка: [06-S08] в части «недостаточное полномочие не обходится».

**ADR-10: revision-guard в `editMemoryObject` (опциональный `expected_updated_at`).**
Контекст: F12/S03 — сейчас edit не принимает ожидаемой ревизии (`edit-memory-object.ts:41-88`), форма может затереть параллельную правку. Альтернативы: ETag/If-Match на HTTP-уровне; полные версии объектов памяти. Выбор: минимальный опциональный параметр в общем use-case (CLI совместим), HTTP отдаёт `updated_at` и требует его в мутации. Последствия: отказ «конфликт» — переоткрытие актуального содержания. Риск: `updated_at` недостаточно уникален при гонке под lock — под lock сравнение атомарно. Проверка: S03-фикстура (revision A открыта, записана B → отказ).

**ADR-11: loopback-модель безопасности без токена по умолчанию.**
Контекст: N02/N03; сервис однопользовательский локальный. Альтернативы: обязательный токен; Basic-auth. Выбор: bind 127.0.0.1 + Host-проверка + отсутствие CORS + обязательный `X-Wolf-Console` на мутациях (не выставляется простой формой без preflight). Последствия: нулевая настройка; `--token` как опция. Риск: локальные соседние страницы — смягчается запретом чтения ответа без CORS; spike-2 проверяет поведение браузеров. Проверка: негативные тесты (чужой Origin, форма без заголовка, не-JSON content-type).
