# 1. Цель

Закрыть четыре замечания внешнего ревью v3.3.0 (журнал `mem_20261118_f26dfb`):
P1-1 и P1-2 — сохранность журнала противоречий, P2-1 — валидация report,
P2-2 — наблюдаемость `contradict list`. Состав зафиксирован владельцем (D1,
2026-11-18); исправления идут от базы `9ad2fea4` (тег v3.3.0).

**Главный критерий приёмки релиза — дословная формулировка эксперта** (принята
владельцем как основной критерий, D2):

> после нескольких противоречий к одной заметке и пересоздания индекса каждое
> наблюдение и решение сохранены, спорная ревизия остаётся вне доставки, пока её
> противоречие открыто

Носитель дефектов — журнал `MicroNoteDeliveryLog` (подавления, доставки,
наблюдения), сейчас размещённый в таблицах `.wolf/cache/index.sqlite`.
Требования волны R-4 (`docs/dev/2026-11-18-r4-contradiction-ops/requirements.md`,
REQ-R4-1..3) остаются в силе; патч изменяет контракт адресации подавлений
(resolve по записи, а не по заметке) и носитель журнала — сверка стиля и
нумерации выполнена с этими требованиями.

Активные ограничения:

- REQ-03 «unknown stays unknown» действует в use-case подавлений
  (`src/app/use-cases/micro-note-contradiction.ts:54,90`, v3.3.0).
- Существующие проекты с журналом в `index.sqlite` не теряют данные при
  обновлении до 3.3.1 (REQ-331-3).
- CLI и MCP ведут себя одинаково за счёт общей валидации в use-case.
- Каталог MCP-тулов зафиксирован guard-тестом (10 тулов ≤ 12); новых тулов нет,
  `note_contradiction` — один составной тул с `action`.

# 2. Требования (REQ) и критерии приёмки (AC)

Каждая REQ имеет контрактом регрессионный тест: на базе `9ad2fea4` он красный
(механизм дефекта подтверждён чтением кода), после исправления — зелёный.

## REQ-331-1 (P1-1) — каждое противоречие — отдельная запись с собственным id; resolve адресует запись

Существующее поведение (дефект): `recordSuppression` выполняет
`INSERT … ON CONFLICT(memory_id) DO UPDATE`
(`src/adapters/sqlite/sqlite-search-index.ts:396`) — повторный report по той же
заметке перезаписывает строку и сбрасывает `resolved_at`/`resolution` в NULL:
второе наблюдение стирает первое наблюдение и решение.
`resolveSuppression` адресует по `memory_id` (`:420`), use-case
`resolveMicroNoteSuppression` принимает note_id
(`src/app/use-cases/micro-note-contradiction.ts:85`).

- AC-1.1: повторный report по той же заметке (той же или новой ревизии) создаёт
  НОВУЮ запись журнала; предыдущие записи не изменяются — наблюдения и решения
  всех противоречий сохраняются.
- AC-1.2: каждая запись имеет собственный стабильный id (`cnr_…`); вывод report
  и `list` показывают id записи.
- AC-1.3: resolve принимает id записи и снимает ровно её; другие открытые записи
  (в том числе той же заметки) остаются открытыми и продолжают подавлять.
- AC-1.4: resolve по неизвестному или уже разрешённому id записи — отказ
  use-case/порта с названным текстом (REQ-03: unknown stays unknown); вызов
  resolve с адресацией по заметке (`--note`) — отказ с подсказкой: перечисление
  открытых id записей этой заметки.
- AC-1.5: спорная ревизия вне доставки, пока открыта ХОТЯ БЫ одна запись этой
  ревизии (семантика «some», а не «ровно одна»); разрешение одной записи при
  другой открытой — заметка по-прежнему не доставляется.

## REQ-331-2 (P1-2) — журнал противоречий и состояние доставки хранятся вне `.wolf/cache`

Существующее поведение (дефект): таблицы `micro_note_suppressions` и
`micro_note_deliveries` (и наблюдения) живут в кэше
`index.sqlite` (`src/adapters/fs/project-paths.ts:26`, cacheDir); rebuild
пересоздаёт индекс из объектов памяти
(`src/app/use-cases/rebuild-memory-index.ts`) — журнал при утрате файла кэша не
восстанавливается, подавления и история атрибуции теряются.

- AC-2.1: журнал хранится в постоянном месте вне `.wolf/cache` (носитель —
  решение design.md, развилка A/B); утрата, удаление или пересоздание
  `index.sqlite` не теряет ни одной записи журнала.
- AC-2.2: после rebuild индекса (или удаления `index.sqlite` с последующим
  пересозданием) активные подавления продолжают действовать: спорная ревизия не
  доставляется.
- AC-2.3: история атрибуции (deliveries) и наблюдения сохраняются при
  пересоздании индекса.
- AC-2.4: утрата самого журнала не изобретает состояние (REQ-03): доставка
  возобновляется, `list` показывает пустой журнал — поведение явное, без
  скрытой ошибки.

## REQ-331-3 (миграция, из P1-2) — существующие проекты не теряют журнал при обновлении до 3.3.1

- AC-3.1: проект с журналом формата 3.3.0 в `index.sqlite` при первом обращении
  после обновления переносит строки подавлений и deliveries в постоянный журнал;
  `resolved_at`/`resolution`/`revision`/оба evidence сохраняются без изменений.
- AC-3.2: миграция присваивает каждой записи собственный id в детерминированном
  порядке (по `suppressed_at`, затем `memory_id`).
- AC-3.3: миграция идемпотентна: повторное открытие проекта не дублирует записи;
  сбой в середине не оставляет частичный журнал (атомарная запись) и не портит
  legacy-таблицы — повтор возможен.
- AC-3.4: проект без старого журнала (чистый) — миграция ничего не создаёт и не
  меняет поведение.

## REQ-331-4 (P2-1) — общая trim-валидация reason/evidence в use-case

Существующее поведение (дефект): `reportMicroNoteContradiction` не валидирует
reason/evidence (`micro-note-contradiction.ts:47`), тогда как
`resolveMicroNoteSuppression` валидирует непустые после trim (`:89`) —
асимметрия; MCP-схема `NoteContradictionInputSchema` допускает пустые строки
(`src/adapters/mcp/mcp-schemas.ts:109`).

- AC-4.1: report с пустой или whitespace-only reason ИЛИ evidence — отказ
  UserFacingError с названной причиной, журнал не изменён; правило одно и
  покрывает CLI и MCP (валидация в use-case — один носитель правила).
- AC-4.2: значения сохраняются после trim — без ведущих и хвостовых пробелов.
- AC-4.3: MCP-схема отклоняет пустые строки до use-case (первая линия защиты,
  ошибка схемы); правило use-case от схемы не зависит — CLI покрыт тем же
  местом.
- AC-4.4: resolve-валидация не регрессирует: текст и поведение как в 3.3.0
  (`micro-note-contradiction.ts:89`).

## REQ-331-5 (P2-2) — `contradict list` показывает ревизию записи и актуальность блокировки

Существующее поведение (дефект): `list` печатает все записи с
`resolved_at === null` без id, без ревизии и без признака актуальности
(`src/adapters/cli/commands/memory-contradict.ts:60`); при этом привязка
подавления к ревизии в фильтре доставки корректна
(`src/app/use-cases/micro-note-delivery.ts:171`).

- AC-5.1: каждая строка `list` содержит: id записи, `note_id@revision` (ревизия,
  которую блокирует запись), reason, suppressed_at.
- AC-5.2: для каждой открытой записи указана актуальность блокировки:
  «actual» — ревизия записи совпадает с текущей ревизией заметки (блокирует
  доставку сейчас); «superseded» — не совпадает (заметка пересмотрена, запись
  истории); «unknown» — текущую ревизию определить нельзя (REQ-03).
- AC-5.3: пустой список — явное «no open suppressions» (без регрессии против
  REQ-R4 AC-1.5).
- AC-5.4: актуальность вычисляется тем же правилом, что фильтр доставки
  (`openContradiction`): list не может показать «actual» для записи, которая
  доставку сейчас не блокирует, и наоборот.

# 3. Ограничения и NFR

- NFR-331-1: каталог MCP-тулов не увеличивается (guard-тест 10 ≤ 12); изменения
  `note_contradiction` — только поля и действия существующего тула.
- NFR-331-2: REQ-03 «unknown stays unknown» сохранён во всех новых ветках
  (AC-1.4, AC-2.4, AC-5.2).
- NFR-331-3: обратная совместимость — REQ-331-3 (обновление с 3.3.0 без потери
  данных журнала).
- Носитель журнала — append-only JSONL (см. design.md, ADR-2); полный объём
  читается при использовании; компакция вне scope 3.3.1 (риск зафиксирован в
  design.md §11).

# 4. Вне scope 3.3.1

- Новые MCP-тулы; list-действие в MCP `note_contradiction` (замечанием P2-2 не
  требуется, каталог зафиксирован guard-тестом).
- Компакция/ротация журнала; представления журнала за пределами `list`.
- Маршрутизация `reconcileMicroNoteObservations` — вне scope с волны R-4.
- Публикация релиза — только по отдельной команде владельца (D3).

# 5. Верификация волны

- Регрессионные тесты на каждый AC каждой REQ: красные на `9ad2fea4`,
  зелёные после исправления.
- E2E-сценарий главного критерия приёмки: два и более противоречия к одной
  заметке → resolve одного → пересоздание индекса (удаление `index.sqlite` и
  rebuild) → все наблюдения и решения сохранены, спорная ревизия вне доставки,
  пока её противоречие открыто.
- Интеграционный тест миграции: фикстура `index.sqlite` формата 3.3.0 →
  открытие кодом 3.3.1 → REQ-331-3 (AC-3.1–3.4).
- Полный `npm run check` зелёный; независимое ревью diff'а до коммита.
- Выпуск: PR → merge → `npm version 3.3.1` → тег — по отдельной команде
  владельца (D3).
