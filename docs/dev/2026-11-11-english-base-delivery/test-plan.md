# english-base-delivery — тест-план

План проверок волны по утверждённым REQ-01..09 и NFR-01..04. Ожидаемые исходы
выведены из AC requirements и контрактов design (§4.1–§4.7, ADR-1..6), не из
реализации. Проверки помечены уровнем и моментом запуска; `SC-NN` — идентификатор
проверки для trace. План — не исполнение: прогонами занимается исполнительская
роль по plan.md.

## Среда и предусловия

- Ревизия: ветка волны; перед прогонами фиксируется `git rev-parse HEAD` в
  evidence. База до перевода — RU-оригиналы `templates/**` (oracle для
  семантической сверки NFR-01) берутся из git-истории до перевода, не из памяти.
- Node >= 24 (engines пакета), `npm ci` пройден, `npm run check` зелёный до
  старта волны (baseline здорового репо).
- Изоляция: e2e/demo/миграционные проверки — только на временных fixture-проектах
  (существующий helpers `tests/e2e/helpers.ts`); реальные проекты пользователя не
  используются; реальные секреты запрещены; сетевых побочных действий нет.
  Fixture-проекты со штампованными RU-файлами собираются штатным `init` на
  RU-ревизии, а не рукотворным копированием.
- Планируемые артефакты волны, на которые ссылаются проверки:
  `glossary.md`, `translation-log.md`, `token-baseline.json` (в папке волны),
  `scripts/check-delivery-language.mjs`, `scripts/check-glossary-consistency.mjs`,
  `scripts/bench-file-tokens.mjs` — контракты design §4.4/§4.5; точные флаги
  записи артефактов фиксирует plan.
- Тесты в рамках составления плана не запускаются (план, не исполнение).

## Сценарии

### REQ-01 — Правило языка сессии в ядре поставки

- **SC-01 (авто, e2e, приёмка G0): секция-носитель доставлена.**
  Given EN-поставка собрана — When рендер init/scaffold в fixture-проект —
  Then доставленный `AGENTS.md` содержит секцию «Session language» (R1).
  Команда: `npx vitest run --config tests/e2e/vitest.config.ts tests/e2e/scaffold.e2e.ts tests/e2e/bootstrap.e2e.ts`
  - планируемый `tests/e2e/delivery-language-rule.e2e.ts` (assert на секцию).
    Ожидаемо: exit 0, секция присутствует. Ошибка, которую ловит: правило
    выпало из always-загрузки при переводе/рендеринге.
- **SC-02 (авто, e2e/demo, приёмка G0): запись decision создаётся и читается.**
  Given fixture-проект без записи языка — When выполнены `wolf add --type decision
--title "Working language: ru"` и `wolf brief` — Then brief возвращает активное
  решение о языке (механика §4.2). Команда: demo-шаг (сценарий первой сессии)
  или `node dist/bootstrap/cli.js add … && node dist/bootstrap/cli.js brief`.
- **SC-03 (ручная сессия по чек-листу + demo-сценарий, закрытие волны):
  поведение «ровно один раз / без переспрашивания / смена / AC-4».**
  Поведенческое — demo-сценарий (первая + повторная сессия), не unit-тест
  (design §4.7). Протокол (4 сессии на fixture-проектах, каждая с чистой памятью
  где нужно):
  1. Сессия 1, записи языка нет, реплика без указания языка → Wolf задаёт вопрос
     о языке **ровно один раз**; после ответа — запись `decision` в памяти
     (проверка `wolf brief`), повторного вопроса нет.
  2. Сессия 2 (запись есть) → вопроса нет; общение, записи памяти и рассуждения
     исполнителей — на выбранном языке; артефакты поставки — EN (ортогональность).
  3. Явное указание «перейти на язык Y» → старое решение supersede, новое
     применено, переспрашивания нет.
  4. Первая реплика сессии явно называет язык X → отдельного вопроса нет, X
     фиксируется сразу (AC-4).
     Evidence чек-листа: лог сессии + вывод `wolf brief` по каждому шагу.
     Ошибка, которую ловит: правило сформулировано так, что модель переспрашивает,
     молчит о фиксации или тянет язык артефактов в язык общения.
- **SC-04 (авто, приёмка G0): бюджет секции.** Извлечённая секция «Session
  language» замеряется `bench-file-tokens` (chars/4): ≤ 300 EN-токенов
  (ориентир ≤ 100 — не гейт). Команда: временный файл с текстом секции →
  `node scripts/bench-file-tokens.mjs --file /tmp/section.md`. Ожидаемо: ≤ 300.

### REQ-02 — Перевод always-загрузочного ядра (G0)

- **SC-05 (авто, приёмка G0): 0 кириллицы в G0.** Given G0 переведена, группы

  находятся только вне файлов G0; отдельно assert — в `base/AGENTS.md` и
  `using-skills/SKILL.md` кириллицы нет (AC-1). Исход «exit 0» на закрытии
  волны проверяет SC-08 (после G1–G5). Временные исключения/skip запрещены
  (ADR-2, REQ-07).
- **SC-06 (процедурная, приёмка G0): циклы качества G0 зафиксированы.** В
  `translation-log.md` есть записи циклов 1–3 по каждому файлу G0
  (`base/AGENTS.md`, `using-skills/SKILL.md`), исполнители/проходы циклов
  различны. Команда/процедура: ревью журнала против перечня файлов G0.
- **SC-07 (авто, приёмка G0 — ранний контроль, финал на закрытии волны):
  токен-стоимость ядра не выросла.** `node scripts/bench-file-tokens.mjs
--baseline docs/dev/2026-11-11-english-base-delivery/token-baseline.json
--file templates/base/AGENTS.md --file templates/base/skills/using-skills/SKILL.md
--file templates/base/skills/using-skills/references/agent-language.md` —
  EN ≤ RU **по каждому файлу** (AC-2, NFR-04), иначе exit 1 с таблицей
  превышений (ADR-3).

### REQ-03 — Перевод остальных групп (G1–G5)

- **SC-08 (авто, закрытие волны): 0 файлов с кириллицей в `templates/`.**
  `npm run check` (гейт 1 в постоянной цепочке после закрытия G0) — exit 0

  без исключений (ADR-2); итоговое число переведённых файлов фиксирует отчёт

- **SC-09 (процедурная, закрытие каждой группы): нет файлов «в обход»

  REQ-05 (AC-2). Исключение G5: `base/README.md` (без кириллицы) — запись

### REQ-04 — Глоссарий RU→EN до старта перевода

- **SC-10 (процедурная, граница каждой группы): перевод не стартует без

  строками `candidate` (AC-1). Команда/процедура: чтение frontmatter + ревью
  дельты терминов группы.
- **SC-11 (авто, постоянно): консистентность глоссария** — см. SC-30/NFR-03.

### REQ-05 — Циклы качества перевода

- **SC-12 (процедурная, закрытие каждой группы): следы ревью-циклов.**
  Ревью `translation-log.md` по группе: (1) семантическое ревью против
  RU-оригинала, (2) редактура носителем, (3) повторный контроль выборки —
  записи по каждому файлу группы; машинный прогон не засчитан (в записях
  различимы исполнители/проходы). Отрицательная ветвь (AC-1): файл с записями
  только о машинном переводе → «не переведён», в закрытие группы не входит.
- **SC-13 (ручная выборка, цикл 3 каждой группы): семантическая сверка
  выборки.** Выборка ≥ 10% файлов группы (мин. 1), независимо против
  RU-оригинала из git-истории; критерий — правила/ограничения/шаги процедур
  не потеряны и не добавлены. Смысловой дефект → исправление и повтор цикла 3
  на новой выборке до первой чистой (AC-2). Приёмка группы возможна только
  после чистой выборки.

- **SC-14 (авто, до старта перевода): фиксация RU-бейзлайна — сама фиксация
  есть проверка.** Given RU-черновик секции «Session language» уже вписан в
  `base/AGENTS.md` (порядок §4.4), перевод не начат — When замер 3 файлов
  always-загрузки фиксируется в `token-baseline.json` — Then артефакт содержит
  `date`, `method` (`chars/4`), `wolf_version`, 3 файла с `tokens > 0`
  (AC гейт 3, base). Проверка порядка: секция вписана **до** замера (сверка

  `bench-file-tokens`, запись артефакта по формату §4.4, ревью артефакта.

  `npm run check` + bench-сравнение + приложение вывода к материалам закрытия.
- **SC-16 (авто, отрицательный, закрытие волны): регрессия ловится.**
  В `templates/` вносится временный файл с кириллицей → `node scripts/
check-delivery-language.mjs` → exit 1 со списком `path` (+ строки);

  тестовый файл → гейт 4 → exit 1 с `term → file:line`. Фикстуры удаляются,
  повторный прогон — зелёный (cleanup проверен).

### REQ-08 — Миграционная волна upgrade

Precondition всех проверок SC-19..SC-23: **обязательный шаг плана миграции
выполнен** — разрешение F-R3 (design §4.6): установлено, штампуются ли копии
`wolf-session-start.js`/`wolf-router.ts`; выбран исход (1) цели в update-map +
перевод G5 до релиза, либо (2) фиксация «не рендерятся» + заметка в релизе.
Проверка precondition — процедурная: в плане миграции есть шаг и запись
разрешения по критерию §4.6.

- **SC-19 (авто, e2e, релиз миграции): чистый проект мигрирует без вопросов.**
  Given fixture-проект со штампованными RU-файлами без локальных правок —
  When upgrade релиза волны — Then все штампованные файлы заменены на EN,
  бэкапы созданы (`.wolf/backup/`, путь в отчёте), вопросов нет, счётчик
  replaced > 0 (AC-1). Команда: планируемый
  `npx vitest run --config tests/e2e/vitest.config.ts tests/e2e/upgrade-language-wave.e2e.ts`
  (база — существующий контур upgrade-\* e2e).
- **SC-20 (авто, e2e, релиз миграции): конфликт не перезаписывается молча;
  take по умолчанию с бэкапом; protect не тронут.** Given fixture с (а)
  mutated-файлом и (б) protect-файлом — When upgrade — Then (а) конфликт
  показан, файл не заменён до явного resolve; подсказка по умолчанию — take
  («your edit is preserved in backup»); при take — EN-версия записана, правка
  в бэкапе; (б) protect-файл не изменён (AC-2, §4.6).
- **SC-21 (авто, e2e, релиз миграции): faces не затронуты волной.** Given
  fixture с face-копией playbook (seed — русский текст из
  `src/app/use-cases/seed-base-playbooks.ts`, вне скоупа волны) — When
  upgrade миграционной волны — Then число diverged faces до равно числу
  после (волна templates/\*\* шаблоны лиц не меняет, design §4.6 F-R2
  скорректирован); существующие diverged-лица обрабатываются штатно
  («Done with attention»/exit 2 при needsDecision > 0, steward-zone список —
  поведение до волны, не её следствие). Сверка счётчиков до/после в отчёте
  upgrade.
- **SC-22 (авто, e2e, релиз миграции): AC-3 — 0 кириллицы в штампованных
  файлах проекта.** После SC-19: grep `[\u0400-\u04FF]` по штампованным файлам
  fixture → 0 попаданий, кроме файлов, оставленных protect/keep с
  зафиксированным выбором (их выбор виден в отчёте).
- **SC-23 (авто, e2e, отрицательный + восстановление): идемпотентность и
  deferred.** (а) Mutated-файл без `--resolve` → не перезаписан: RU-контент
  сохранён, файл в отчёте deferred/needsDecision, повторный upgrade повторно
  предлагает конфликт; EN-файлы при повторе — unchanged (§4.6). (б) Откат:
  восстановление из `.wolf/backup/` копированием назад на fixture возвращает
  исходный контент (процедура откат-заметки релиза).

## NFR

### NFR-01 — Семантическая эквивалентность

- **SC-26 (процедурная, закрытие каждой группы): 100% файлов с записью
  цикла 1.** Сверка журнала C4 с инвентарём файлов группы; отклонения
  «сознательно улучшено» зафиксированы в журнале, не «потеряны» (AC).
- **SC-27 (ручная выборка):** — покрытие SC-13 (цикл 3): семантическая сверка
  ≥ 10% (мин. 1) против RU-оригинала до чистой выборки; закрытие волны —
  чистая выборка последнего контроля. Критерий: ни одно правило/ограничение/
  шаг процедуры не теряется и не добавляется.

### NFR-02 — Читаемость носителем языка

- **SC-28 (процедурная, закрытие каждой группы): 100% файлов с записью
  цикла 2** (редактура носителем, независимый проход), сверка журнала с
  инвентарём (AC).
- **SC-29 (ручная выборка, цикл 3): контроль на кальку.** Выборка ≥ 10%
  (мин. 1; обязательно ≥ 1 файл G0 — максимальная цена кальки) читается
  носителем; критерий — нет калькированного «русско-английского» текста
  (AC). До чистой выборки.

### NFR-03 — Согласованность терминов

- **SC-30 (авто, постоянно): гейт консистентности зелёный.**
  `node scripts/check-glossary-consistency.mjs` → exit 0 (0 несогласованных
  вариантов; учтены только approved-строки). Уточнения контракта (design
  §4.3/§4.5, проверены юнит-тестами 23/23): совпадение — **целым словом с
  допуском числа** (`board` не ловится внутри `onboarding`, `boot` — внутри
  `bootstrap`; при этом `orchestrators`/`health checks`/`issues` ловятся);
  алиасы из «Исключений» (общие английские слова: `log`, `limit`, `version`,
  `target`…) нарушением не считаются, но каждый ключ обязан соответствовать
  объявленному алиасу (опечатка → violation); строка без действующего латинского
  алиаса обязана быть объявлена в «Без машинного EN-контроля» с причиной, иначе
  violation. Контроль полноты исключений и waiver'ов — SC-31 и семантическое
  ревью, не гейт (ADR-4). На реалистичной английской прозе после перевода
  гейт даёт только настоящий дрейф (`knowledge base` вместо `memory`), ноль
  ложных срабатываний.
- **SC-31 (процедурная, граница групп): термины до использования.** Новые
  термины внесены в глоссарий `candidate`-строками **до** их появления в
  переводе группы; ревью дельты глоссария против дельты перевода группы.

### NFR-04 — Токен-бюджет always-загрузки

- **SC-32 (авто, закрытие волны): EN ≤ RU пофайлово на 3 файлах** — SC-07/SC-14
  (фиксация бейзлайна до перевода; сравнение тем же оценщиком); результат
  сравнения приложен к закрытию волны (AC). Порог допустимой вариативности
  не нужен: оценка `chars/4` детерминирована; абсолютные значения —
  приближение, зафиксированное в `method` артефакта.

## Ограничения плана

- SC-03, SC-13, SC-29 — ручные поведенческие проверки: воспроизводимый протокол
  есть, но результат зависит от модели; фиксируется evidence каждого шага,
  не «зелёный флаг».
- Команды новых гейтов (`check-delivery-language`, `check-glossary-consistency`,
  `bench-file-tokens`) — контрактные (design §4.5); точные флаги (запись
  артефакта, отчёт) закрепляет plan до исполнения.
- Итоговое число мигрируемых файлов подтверждается отчётом upgrade (SC-19),
  а не оценкой ~68 (допущение requirements §6).
- Сценарии SC-19..SC-23 исполняются после появления EN-данных волны: локальная
  сборка-кандидат (dist + перегенерированный update-map, T-35) или релиз;
  план исполняет их до релиза (T-37), чтобы не публиковать невалидированную
  миграцию — это выбор момента, не пропуск.
