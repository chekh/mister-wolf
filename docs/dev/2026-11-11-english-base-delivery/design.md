## Глоссарий документа

Термины волны (штампованный файл, resolve-стратегия, always-загрузочное ядро и
др.) определены в requirements §3 и здесь не повторяются. Дополнительно:

- **Группа перевода (G0..G5)** — подмножество файлов `templates/`, переводимое
  как единое целое с полным циклом качества REQ-05.
- **Журнал перевода** — `docs/dev/2026-11-11-english-base-delivery/translation-log.md`;
  пофайловые записи о пройденных циклах (носитель AC REQ-03 «нет файлов в обход
  процесса» и AC NFR-01/02).
- **Aliases** — английские варианты термина, запрещённые глоссарием; вход гейта
  консистентности (NFR-03).
- **RU-бейзлайн** — артефакт замера `token-baseline.json`, зафиксированный до
  старта перевода (AC REQ-06 гейт 3).

## Компоненты и ответственность

### C1. Onboarding-блок AGENTS.md с правилом языка сессии — `templates/base/AGENTS.md`

Ответственность: always-загрузочный контракт проекта; несёт новую секцию
«Session language» (семантика — §4.1). Владелец текста: волна; далее — обычная
эволюция поставки. Это единственный нормативный носитель правила (ADR-1).

### C2. using-skills — `templates/base/skills/using-skills/SKILL.md` (+ `references/`)

Ответственность: always-загрузочная маршрутизация; добавляет однострочную
указку на секцию «Session language» (без дублирования формулировок). Переводится
в G0/G1.

### C3. Глоссарий — `docs/dev/2026-11-11-english-base-delivery/glossary.md`

Ответственность: обязательный вход перевода всех групп; источник вариантов и
aliases для гейта C6. Утверждается владельцем (frontmatter `status: approved`);
формат — §4.3.

### C4. Журнал перевода — `docs/dev/2026-11-11-english-base-delivery/translation-log.md`

Ответственность: фиксация циклов REQ-05 по каждому файлу каждой группы
(дата, файл, циклы 1–3, отклонения «сознательно улучшено» для NFR-01,
несогласованные формулировки → новые aliases глоссария). Append-only.

### C5. RU-бейзлайн — `docs/dev/2026-11-11-english-base-delivery/token-baseline.json`

Ответственность: зафиксированный до старта перевода замер always-загрузки
(3 файла: `base/AGENTS.md`, `using-skills/SKILL.md`, `using-skills/references/agent-language.md`);
вход гейта C7. Формат — §4.4.

### C6. Гейты языка и консистентности — новые `scripts/check-delivery-language.mjs`, `scripts/check-glossary-consistency.mjs`

Ответственность: гейты (1) и (4) REQ-06; подключаются в `npm run check` рядом
с `check-english-surface`. Контракты — §4.5. Это весь новый код гейтов (ADR-2,
ADR-4).

### C7. Токен-гейт — новый `scripts/bench-file-tokens.mjs`

Ответственность: гейт (3) REQ-06 — замер тех же 3 файлов в EN и сравнение с C5
(`--baseline`); запускается при фиксации бейзлайна и в чек-листе закрытия волны;
в `npm run check` не входит (AC REQ-06 требует из постоянного check только
ловлю кириллицы и терминов; сравнение с бейзлайном — evidence закрытия волны).
ADR-3.

### C8. Перегенерированный `update-map.json` + штатный upgrade — без изменений кода

Ответственность: волна миграции REQ-08. При релизе волны генератор отмечает все
переведённые sync-цели как `changed`; существующий поток check → show → review
→ resolve → здесь/npm re-exec выполняет массовую замену. Подсказка по умолчанию
и сводка — §4.6. ADR-5.

### C9. Синхронизируемые проверки и сценарии (REQ-07)

Ответственность: приведение тестов/demo к EN-поставке. Пофайловый разбор — §6.

### C10. RU-зеркало сайта — `docs/site/ru/`

Ответственность: REQ-09; минимальная синхронизация после закрытия групп — §6.3.

## Контракты

### 4.1. Правило языка сессии (REQ-01) — семантика секции «Session language»

Нормативные пункты, размещаемые в onboarding-блоке `base/AGENTS.md` (EN,
финальная формулировка — предмет циклов качества G0):

1. Если в памяти проекта нет решения о рабочем языке — уточнить у пользователя
   ровно один раз, в первой сессии.
2. Если пользователь явно назвал язык в первых репликах — отдельного вопроса не
   задавать; язык фиксируется сразу (AC-4 REQ-01).
3. Выбор фиксируется записью памяти Wolf типа `decision` (см. 4.2) и в
   последующих сессиях не переспрашивается.
4. Общение с пользователем, записи памяти и рассуждения исполнителей ведутся на
   выбранном языке; артефакты поставки остаются EN (ортогональность).
5. Смена языка — только по явному указанию пользователя: старое решение
   supersede, новое фиксируется; переспрашивания нет.

Правило адресовано ведущему и исполняемо без новых инструментов: Wolf уже
восстанавливает состояние из памяти при старте (`wolf call`/`wolf brief`).

**Бюджет размера и порядок ввода секции (разрешение конфликта REQ-01 ↔ NFR-04,
без правки требований).** Секция — постоянный расход always-загрузки, поэтому:

- потолок размера секции — **≤ 300 EN-токенов** по оценке chars/4 (≈ ≤ 1200
  символов EN); ориентир проектирования — компактнее, ≤ 100 EN-токенов
  (~400 символов, 5–7 строк);
- секция вводится в **RU-шаблон** `base/AGENTS.md` черновиком на русском
  **до фиксации RU-бейзлайна** — тогда секция присутствует в обеих сторонах
  сравнения NFR-04 и пофайловый гейт «EN ≤ RU по каждому файлу» остаётся
  честным (арифметика и границы сходимости — ADR-3);
- ограничение проверяемо тем же `bench-file-tokens` (замер секции против
  потолка); контроль — замер после G0 против бейзлайна (NFR-04).

### 4.2. Запись памяти о рабочем языке (фиксация выбора)

Переиспользует существующий тип `decision`; нового store нет.

```
wolf add --type decision \
  --title "Working language: <lang>" \
  --body "Session language chosen by the user (<date>). Dialogue, memory records \
          and subagent reasoning are conducted in <lang>. Delivery artifacts \
          stay English. Superseded by: <id> (при смене языка)."
```

Чтение при старте — штатное: `wolf call`/`wolf brief` возвращает активные
решения проекта; правило предписывает интерпретировать их как носитель рабочего
языка. Смена языка = `wolf supersede <old> <new>` — существующая механика.

### 4.3. Формат глоссария (REQ-04/NFR-03)

```markdown
---
slug: glossary-ru-en
title: Глоссарий перевода Wolf RU→EN
status: draft # draft → approved (владелец, ревью документа)
---

| RU термин         | EN термин    | Статус   | Aliases (запрещено)     | Примечание      |
| ----------------- | ------------ | -------- | ----------------------- | --------------- |
| штампованный файл | stamped file | approved | stamped artifact        |                 |
| ведущий           | lead         | approved | lead wolf, orchestrator | Wolf term: face |
```

- Обязательные термины стартового набора: wolf face/thread/steward/skill,
  волна/upgrade/resolve-стратегии, методическая терминология requirements §3.
- Машинный разбор: строки таблицы; `status` строки ∈ {approved, candidate};
  aliases — comma-separated. Гейт учитывает только `approved`.
- Инвариант «один RU термин → один EN вариант»: уникальность колонки
  «RU термин» и колонки «EN термин» среди approved-строк (дубли → гейт красный).
- Процесс: новый термин при переводе добавляется строкой `candidate` до его
  использования; утверждение владельцем — на границе групп (AC REQ-04:
  перевод группы не стартует без утверждённого глоссария).
- Раздел «Исключения» (обязателен, как только гейт 4 включён): строки
  ``- `alias` — основание`` перечисляют общие английские слова из колонки
  aliases, которые законно встречаются в коде, именах полей CLI, статусах
  протокола и путях (`log`, `limit`, `version`, `target`…).
  Гейт 4 читает раздел как данные и не считает их нарушением (AC REQ-04:
  «список исключений — в самом глоссарии»). Каждый ключ обязан соответствовать
  объявленному алиасу, иначе гейт краснеет (опечатка/устаревшая запись).
- Раздел «Без машинного EN-контроля»: строки ``- `RU-термин` — причина``.
  Обязателен для термина, у которого нет пригодного английского алиаса (все
  кандидаты — канон другой строки, общее слово или техническое употребление в
  коде). Такие строки держатся циклами REQ-05 и ревью глоссария; гейт 1
  (0 кириллицы) сохраняет их русские маркеры до перевода.
- Правило для колонки aliases: только термин-специфичные варианты. Общие
  английские слова (`aspect`, `memo`, `milestone`, `pool`, `round`,
  `checking`) и условные записи с пояснением в скобках
  (`validation (как перевод проверки)`) машинной проверки не дают и не
  считаются алиасами.
- Многословные алиасы (`work tree`, `health check`, `knowledge base`,
  `feedback loop`, `sign-off`, `template set`, `render record`,
  `initial draft`, `work-thread`, `council-opinion`) — основной инструмент
  ловли реального дрейфа; они не попадают ни в исключения, ни в waiver'ы.

### 4.4. Формат RU-бейзлайна (REQ-06 гейт 3 / NFR-04)

```json
{
  "date": "2026-11-11",
  "method": "bench-file-tokens (chars/4, детерминированная оценка)",
  "wolf_version": "<X.Y.Z на момент замера>",
  "files": [
    { "path": "templates/base/AGENTS.md", "tokens": 0 },
    { "path": "templates/base/skills/using-skills/SKILL.md", "tokens": 0 },
    { "path": "templates/base/skills/using-skills/references/agent-language.md", "tokens": 0 }
  ]
}
```

Порядок фиксации (разрешение REQ-01 ↔ NFR-04):

1. **Сначала** RU-черновик секции «Session language» вписывается в
   `base/AGENTS.md` (компакт, бюджет 4.1).
2. Затем фиксация бейзлайна: `bench-file-tokens` на 3 файлах — секция уже
   внутри RU-замера (обе стороны сравнения содержат секцию).
3. Затем перевод G0 (включая секцию) → замер EN против бейзлайна.

Сравнение EN ≤ RU — по каждому файлу (AC NFR-04); гейт остаётся честным,
поскольку секция входит в обе стороны сравнения, а не только в EN.

### 4.5. Контракты новых гейтов (REQ-06)

**check-delivery-language.mjs** (гейт 1): walk `templates/**` (все файлы,
включая `.ts`/`.js`); байтовый тест `[\u0400-\u04FF]`; 0 файлов с кириллицей.
Нарушения: exit 1, список `path` (+ номера строк для текстовых файлов).
Исключений нет (ADR-2). Порядок подключения: в ветке волны гейт транзиентно
красный, пока в `templates/**` остаётся RU-черновик секции и непереведённые
группы — поэтому включение в `npm run check` выполняется **после закрытия G0**
(окно «черновик секции → закрытие G0» гейт запускается адресно при приёмке G0,
skip-вариант AC REQ-07 не используется). Постоянная цепочка: `npm run check` =
этот гейт → check-english-surface → format:check → build → test:run.

**check-glossary-consistency.mjs** (гейт 4): парсит approved-строки глоссария
(4.3); проверки: (а) пары RU→EN уникальны, (б) ни один alias не встречается
ни в одном файле `templates/**`, (в) статус файла глоссария `approved`.
Нарушения: exit 1 с `term → file:line`. Граница честности: гейт гарантирует
отсутствие запрещённых вариантов (регрессий), первичная семантическая
согласованность достигается циклами REQ-05 — замеченные отклонения попадают в
aliases и дальше держатся гейтом (ADR-4).

Уточнения контракта, без которых гейт неработоспособен на практике:

- **Совпадение — целое слово с числом, но без `-ed/-ing`.** Поиск подстрокой
  даёт ложные попадания на ASCII-частях: `board` внутри `onboarding`/`dashboard`,
  `boot` внутри `bootstrap`, `edge` внутри `knowledge`, `hold` внутри
  `threshold`. Границы задаются явно (`(?<![A-Za-z0-9])…(?![A-Za-z0-9])`),
  потому что `\b` в JS опирается на ASCII-класс слов. Допускается только
  окончание числа (`s`/`es`): перевод законно меняет число (`orchestrators`,
  `health checks`, `issues`), и без этого дрейф во множественном числе проходил
  бы незамеченным. Окончания `ed`/`ing` не допускаются — они порождают другие
  слова (`board`→`boarding`, `log`→`logging`), то есть ложные срабатывания на
  обычной прозе.
- **Исключения — данные глоссария, не код** (прямо предусмотрено AC REQ-04:
  «список исключений — в самом глоссарии»). Колонка aliases неизбежно содержит
  общие английские слова (`log`, `limit`, `version`, `target`, `verdict`,
  `summary`, `registry`, `role`, `tag`, `update`, `run`, `setup`, `worker`,
  `permission`, `policy`, `reference`, `resolution`, `replace`, `lock`,
  `guide`, `manager`, `observation`, `assertion`, `suggestion`, `identity`,
  `entry`, `link`, `verify`, `snapshot`) — это законная лексика кода, имён
  полей CLI, статусов протокола и путей, она останется и после перевода.
  Без исключений гейт был бы вечно красным, то есть неработоспособным.
  Раздел «Исключения» глоссария перечисляет каждый алиас с основанием;
  каждый ключ сверяется с объявленными алиасами — опечатка или устаревшая
  запись даёт violation, а не молчаливое принятие.
- **Алиасом может быть только термин-специфичное слово.** Общие английские
  слова (`aspect`, `memo`, `milestone`, `pool`, `round`, `checking`, `border`)
  как алиасы запрещены: они законно встретятся в переводе и покраснят гейт на
  ровном месте. Проверено на реалистичной прозе: после перевода единственное
  срабатывание на абзаце общеязыкового текста — настоящий дрейф (`knowledge
base` вместо `memory`), ни одного ложного.
- **Условные алиасы** (ячейка с пояснением: `validation (как перевод проверки)`)
  машинно не проверяются: без контекста такой алиас неотличим от канона
  соседней строки. Их дефицит закрывает правило покрытия.
- **Правило покрытия строк (обязательно).** Строка `approved` без действующего
  латинского алиаса (не исключённого, не условного) не ловится гейтом вовсе:
  остаются только русские маркеры, а они исчезнут с переводом. Поэтому такая
  строка даёт violation и требует либо точного алиаса, либо явного объявления
  в разделе «Без машинного EN-контроля» глоссария с причиной. Молчаливая
  потеря охвата запрещена; waiver — осознанная граница с основанием, а полноту
  закрывают циклы REQ-05 (ADR-4).
- **Многословные алиасы сохраняют силу** (`work tree`, `health check`,
  `knowledge base`, `feedback loop`, `sign-off`, `template set`,
  `render record`, `initial draft`, `work-thread`, `council-opinion`) — именно
  они и ловят реальный дрейф терминологии. Русские алиасы также проверяются:
  они исчезают вместе с переводом, то есть гейт зеленеет по мере волны.

Проверено на волне: при утверждённом глоссарии гейт даёт 376 нарушений,
все — русские алиасы (исчезнут при переводе), ноль английских ложных
срабатываний; настоящий дрейф (`orchestrators` вместо `lead`,
`health checks` вместо `doctor`, `issues` вместо `complaints`) ловится.
Юнит-тесты гейта — 23 (включая дискриминирующие: тест множественного числа
падает на варианте без суффикса, тест покрытия — при отсутствии waiver).

**bench-file-tokens.mjs** (гейт 3): `--file <path>...` печатает оценку токенов
(`ceil(chars/4)`); `--baseline <path>` сравнивает с артефактом 4.4 пофайлово:
EN ≤ RU → OK, иначе exit 1 с таблицей превышений. Один и тот же оценщик для
обеих сторон сравнения; абсолютные значения — приближение (ADR-3).

### 4.6. Контракт миграционной волны (REQ-08, В3) — поведение штатного upgrade

- **Данные волны**: релиз X.Y.Z с EN `templates/` и `update-map.json`, где все
  переведённые sync-цели = `changed` (~68 оценочно; точный набор — отчёт upgrade,
  допущение requirements §6). Гейт релиза: `generate-update-map.mjs --verify`
  - guard-тест.
- **Файл без правок**: сравнение с версией штампа — файл тождественен своей
  штампованной версии → авто-take без вопросов (AC-1 REQ-08).
- **Файл с правками**: conflicting → не перезаписывается молча; режим review/
  resolve; **подсказка по умолчанию — take** с автоматическим бэкапом
  (решение владельца `e98b3c`): «recommended: take (EN base set; your edit is
  preserved in backup)». protect не предлагается и не трогается, как всегда.
- **Бэкапы**: автоматические, до замены, штатный путь `.wolf/backup/`
  (существующее поведение); путь — в отчёте миграции.
- **Сводка (итог миграции)**: replaced / protected / kept / deferred + путь
  бэкапов + счётчики protected (существующие поля отчёта `report.backups`,
  `protectedCount`); для волны заголовок отчёта упоминает language wave.
- **Откат**: восстановление из `.wolf/backup/` копированием назад (ручная
  процедура, документируется в заметках релиза; новый код не требуется).
- **Идемпотентность**: повторный upgrade после частично выполненной миграции
  видит уже EN-файлы как unchanged/taken и повторяет только отложенные
  конфликты.
- **Face-копии playbooks (F-R2, скорректировано по факту репо)**: seed-шаблоны
  playbooks живут в `src/app/use-cases/seed-base-playbooks.ts` (русские тексты,
  вне скоупа волны `templates/**`) — перевод волны шаблоны лиц не меняет, тела
  faces в проектах сравниваются с теми же RU-seed-текстами, поэтому массовой
  дивергенции faces волна не создаёт. Волна не меняет статус faces: число
  diverged до миграции равно числу после (diverged остаются только по причинам
  стюард-мутаций, существовавшим до волны). Это — ожидание для test-plan
  (SC-21: «diverged до == diverged после») и заметки релиза: «faces не
  затронуты волной; существующие diverged-лица обрабатываются штатно
  (`memory-upgrade.ts`: `stewardZoneLines`, exit 2 при needsDecision > 0)».
- **Плагины `plugins-reserved/*` (F-R3, привязано к REQ-08 AC-3)**: проверено
  по коду: (а) в `update-map.json` цели плагинов из templates/ не попадают —
  генератор объявляет `opencode/plugins`, фактический каталог —
  `plugins-reserved`, walk пуст (карта копии не мигрирует); (б) рендерер
  берёт плагины из `harnessTemplatesRoot/plugins` и прогоняет копии через
  общий конвейер штампов (`opencode-renderer.ts:121-129`; TargetState
  unstamped/mutated); источник `harnessTemplatesRoot` (opts) за рамками
  проверки этой ревизии. Обязательный шаг **плана миграции (до выпуска
  волны, не «не блокер»)** — установить, штампуются ли копии
  `wolf-session-start.js`/`wolf-router.ts` в существующих проектах. Критерий
  разрешения: (1) штампуются → копии под AC-3 REQ-08 (0 кириллицы в
  штампованных файлах) → цели плагинов добавляются в update-map волны,
  перевод G5 обязателен до релиза миграции; (2) не штампуются → фиксируется
  «не рендерятся из templates/», копии вне AC-3, обновление при следующем
  harness-рендеринге, заметка в релизе. `base/README.md` вне карты —
  заметка в релизе (см. ADR-5).

### 4.7. Демонстрация и проверяемость правила (REQ-01 AC)

Механически проверяемо: (а) секция «Session language» присутствует в
доставленном AGENTS.md — гейт состава/тест e2e delivery; (б) запись `decision`
о языке создаётся и читается — существующие memory-команды в demo. Поведение

## ADR-карточки

### ADR-1 — Носитель правила языка сессии и место фиксации выбора

- Контекст: В1/REQ-01 требует always-загрузочный носитель и фиксацию выбора;
  ограничение requirements §6 — фиксация в памяти Wolf, не в конфиг-файле.
- Решение: нормативный текст — секция «Session language» в onboarding-блоке
  `base/AGENTS.md`; using-skills — только указка (без дублирования). Фиксация —
  запись `decision` в памяти Wolf (4.2), смена — `wolf supersede`. Секция
  вводится в RU-шаблон черновиком на русском **до** фиксации RU-бейзлайна;
  бюджет размера — ≤ 300 EN-токенов (chars/4), ориентир ≤ 100 (4.1).
- Альтернативы: (а) дублировать правило в using-skills и AGENTS.md — два места
  правды, расхождение при эволюции; (б) отдельный файл-скилл «session-language»
  — новый always-загрузочный файл против тренда снижения токенов; (в) фиксация
  в конфиге проекта — запрещено ограничением requirements §6 (иначе CR).
- Последствия: +0 новых файлов поставки; правило исполняется существующими
  memory-командами; риск — LLM-соблюдение поведенческое, механически проверяется
  только наличие секции и записи (4.7). Конфликт REQ-01 ↔ NFR-04 разрешён:
  секция присутствует в обеих сторонах сравнения (ввод до бейзлайна, 4.4),
  сходимость пофайлового гейта на AGENTS.md определяется коэффициентом сжатия
  перевода — арифметика и пороги в ADR-3; проверка допущения — замер
  `bench-file-tokens` после G0.
- Статус: proposed

### ADR-2 — Гейт «0 кириллицы»: отдельный байтовый скан templates/\*\*, код — полностью EN

- Контекст: гейт (1) REQ-06 «0 файлов с кириллицей в templates/»; существующий
  `check-english-surface` проверяет только строковые литералы `src/adapters/**`
  и не применим по scope.
- Решение: новый `check-delivery-language.mjs` — walk `templates/**`, байтовый
  тест на `[\u0400-\u04FF]` по любому содержимому, включая комментарии
  кодовых файлов плагинов (решение R3). Исключений и allowlist нет.
- Альтернативы: (а) расширить `check-english-surface` флагом — смешение двух
  разных политик (литералы-кода vs весь контент поставки) в одном скрипте;
  (б) FSM-исключение комментариев в коде — сохраняет RU-комментарии, но
  ослабляет букву REQ-06 и усложняет гейт; файлы маленькие, цена полного EN
  низкая.
- Последствия: простейшая проверка и предсказуемый красный; RU-комментарии в
  двух плагинах исчезают (сознательно); шире — правило «поставка = 0 кириллицы
  по определению» держится без перечней исключений.
- Статус: proposed

### ADR-3 — Токен-гейт: отдельный файловый замер с детерминированной оценкой

- Контекст: гейт (3) REQ-06/NFR-04 требует пофайловый замер always-загрузки
  против артефакта-бейзлайна; `bench:tokens` измеряет расход сессий из БД
  OpenCode и файлы не измеряет (находка из кода).
- Решение: `bench-file-tokens.mjs`, оценка `ceil(chars/4)`, режим `--baseline`;
  бейзлайн C5 фиксируется той же командой **после вписания RU-черновика секции
  «Session language»** (порядок — 4.4): секция в обеих сторонах сравнения.
- Альтернативы: (а) добавить токенайзер-зависимость — новая зависимость против
  ограничения «новый код только там, где без него гейт не работает»; (б)
  измерять сессиями `bench:tokens` до/после — шум сессий делает сравнение
  невоспроизводимым; (в) сравнивать байты — близко, но «токены» — язык
  требования.
- Последствия: сравнение честное (одинаковый оценщик обеих сторон),
  воспроизводимое без сети и зависимостей; абсолютные числа — приближение,
  что фиксируется в самом артефакте (`method`). Арифметика запаса
  (замер 2026-11-11, chars/4; проверка оценки ревью): `AGENTS.md` = 2216
  chars → **554 RU-токена** (кириллицы 1256); поправка: «~1.1k RU-токенов»
  из оценки ревью соответствует `using-skills/SKILL.md` (1225), а не
  AGENTS.md. Пофайловая экономия перевода AGENTS.md = 31..78 токенов
  (EN ≈ (960 + 1256·k)/4, k ∈ [0.75..0.9]) — меньше бюджета секции, поэтому
  на AGENTS.md гейт сходится механизмом «секция в обеих сторонах» (4.4):
  EN ≤ RU ⇔ S_RU·(1−k_s) ≤ 1256·(1−k); при k_s ≈ k размер секции не меняет
  знак неравенства. Пороги: секция 300 EN-токенов (S_RU ≈ 1400 chars при
  k_s = 0.85) требует k ≤ 0.83; ориентир 100 EN-токенов (S_RU ≈ 470) —
  k ≤ 0.94, сходится практически при любом качестве перевода. Суммарная
  экономия трёх файлов замера 208..519 токенов покрывает бюджет 300 при
  k ≤ 0.82, но гейт пофайловый — суммарный запас является резервом для
  ужатия секции, а не условием сходимости. Контроль — фактический замер
  после G0; при EN > RU на AGENTS.md секция ужинается до ориентира.
  Ограничение: гейт волны, не постоянный check (4.5); после волны бюджет
  NFR-04 поддерживается при закрытиях последующих волн тем же скриптом.
- Статус: proposed

### ADR-4 — Механика глоссарий-консистентности: aliases как вход гейта

- Контекст: NFR-03 «0 несогласованных терминов» должен быть машинно-проверяем;
  после перевода в `templates/` нет кириллицы, прямой поиск RU-терминов
  невозможен.
- Решение: глоссарий несёт aliases (запрещённые EN-варианты); гейт ищет
  aliases по `templates/**` + проверяет уникальность маппинга и статус
  `approved` (4.5). Пополняется aliases из циклов качества: замеченный
  разнобой становится запрещённым вариантом.
- Альтернативы: (а) проверять «использование только approved-варианта» —
  требует семантического парсинга текста, автоматика недостоверна; (б) без
  автоматики — AC NFR-03 «автоматическая проверка находит 0» не выполняется.
- Последствия: гейт гарантирует отсутствие известных дрейфов; первичная
  согласованность остаётся ответственностью циклов REQ-05 (явная граница,
  не скрытая). Риск: неполный aliases-список; смягчение — цикл 3 каждой
  группы пополняет глоссарий.
- Статус: proposed

### ADR-5 — Миграционная волна без нового кода; данные волны = translated templates + update-map

- Контекст: REQ-08 (а)–(г) + В3 решены владельцем (take по умолчанию,
  `e98b3c`); в репо уже есть полный upgrade-контур: штампы, resolve
  protect/keep/take, автоматические бэкапы, отчёт, `--yes`.
- Решение: волна выпускается штатным релизом: EN `templates/` +
  перегенерированный `update-map.json` (все цели `changed`), `--verify` гейт;
  поведение конфликта — существующее, с подсказкой take; сводка и бэкапы —
  существующие поля отчёта. Код Wolf не меняется.
- Альтернативы: (а) специальный «режим миграционной волны» в upgrade — новая
  поверхность кода ради того, что штатный flow уже делает; (б) отдельный
  скрипт миграции — дублирование resolve/backup-логики, риск расхождения.
- Последствия: минимальный diff волны в коде (только данные); риски —
  (1) `base/README.md` вне sync-целей карты — не мигрируется, заметка в
  заметках релиза; плагины `plugins-reserved/*` — отдельное разрешение до
  выпуска волны (F-R3, §4.6); (2) подсказка take —
  текст режима review/resolve, если он сегодня не различает «рекомендацию»,
  это минимальная правка сообщения (единственное допустимое исключение из
  «без кода», помечено для plan); (3) массовые конфликты у владельца многих
  проектов — паркинг deferred штатными park-режимами (см. e2e
  `upgrade-park-modes`).
- Статус: approved (решение владельца по В3 `e98b3c`; остальное — ревью)

### ADR-6 — Границы перевода в нетекстовых артефактах (закрытие В2)

- Контекст: В2 — строки ошибок CLI, update-map, термины в коде; по умолчанию
  вне scope, кроме мест, где язык поставки зашит в логику.
- Решение: инвентарь мест «язык поставки зашит в код»: (1) `update-map.json` —
  данные карты, перегенерируется волной (пути без языка); (2)
  `templates/opencode/plugins-reserved/*` — переводятся в G5 (R3); (3)
  CLI-сообщения `src/adapters/**` — уже EN: существующий гейт
  `check-english-surface` запрещает кириллицу в строковых литералах adapters,
  поэтому специальных правок CLI нет. Иных мест по коду репо не выявлено;
  контрольный grep при plan подтверждает (дешёвая проверка, не spike).
- Альтернативы: перевод строк ошибок во всём `src/**` (включая не-adapters) —
  вне scope волны (requirements §2), существующая политика english-surface
  не меняется.
- Последствия: В2 закрыт перечнем из трёх пунктов; новые RU-литералы в
  adapters по-прежнему ловит постоянный гейт.
- Статус: proposed

## Отказные сценарии и эксплуатация

- **Гейт кириллицы ложноположительный**: кириллица в цитатах/примерах после
  волны — нарушает политику «0» намеренно; правка текста, а не allowlist
  (ADR-2). Тест-фикстуры с RU в `tests/` не сканируются (гейт только templates).
- **Глоссарий сломан (битая строка таблицы)**: гейт падает с номером строки
  глоссария — fail loud, тихих пропусков нет.
- **Бейзлайн отсутствует/устарел**: `bench-file-tokens --baseline` падает с
  инструкцией пересоздания; пересоздание после старта перевода запрещено
  процедурой (бейзлайн = до перевода).
- **Прерванный upgrade**: повторный запуск идемпотентен — EN-файлы уже
  unchanged, конфликты повторно предлагаются (существующее поведение).
- **Откат миграции**: restore из `.wolf/backup/` вручную; путь в отчёте;
  документируется в заметках релиза волны.
- **Частичная миграция (deferred)**: проект остаётся смешанным; это состояние
  отчёта, не ошибка; В4 (смешанные проекты владельца) — отдельная работа после
  волны (requirements §2).
- **Совместимость штампов**: штампы версионные, языконезависимые; RU- и
  EN-файлы одной версии различимы сравнением контента — существующая логика
  mutated/unchanged не меняется.
- **Наблюдаемость**: отчёт upgrade (счётчики replaced/protected/kept/deferred,
  путь бэкапов) + журнал перевода + отчёты гейтов — достаточно для закрытия
  волны без новых логов.
