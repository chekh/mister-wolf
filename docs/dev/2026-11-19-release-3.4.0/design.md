# 2. Глоссарий

- Журнал — `.wolf/memory/micro-note-delivery.jsonl` в общем корне памяти;
  append-only JSONL, строка `{kind, record}`.
- Маркер миграции — постоянный файл-признак «первый импорт уже выполнялся»
  (ADR-340-2).
- Утрата журнала — журнал отсутствует, а маркер есть: состояние подавлений
  неизвестно (REQ-03).
- wt-журнал — журнальный файл, созданный ≤3.3.1 внутри linked worktree
  (`<wt>/.wolf/memory/micro-note-delivery.jsonl`); источник импорта.
- Критическая секция — отрезок «прочитать состояние → решить → записать
  (repair+append/импорт)», исполняемый под журнальным локом.
- re-id — детерминированное переназначение `suppression_id` входящей записи при
  коллизии (ADR-340-3).
- Fresh — журнала и маркера нет: новый проект либо документированный сброс.

# 4. ADR-340-1 (REQ-333-2): журнальный лок — файловый O_EXCL, синхронный двойник

Контекст: r2a (repair стирает чужой подтверждённый report), r2b (поздний импорт
заменяет журнал), r2c (двойной resolve) — все три это гонки read-modify-write на
общем файле; content-merges и «повезёт с таймингом» их не закрывают.

Решение: каждый публичный метод адаптера берёт файловый лок
`<root>/.wolf/memory/micro-note-delivery.jsonl.lock` на всю критическую секцию:
мутаторы — «load → решить → repair+append/импорт»; читатели — «load+parse»,
чтобы никогда не видеть разорванное окно repair. Протокол — тот же, что у
проверенного `memory-lock.ts`: `openSync(path, 'wx')` (O_EXCL), содержимое
`{pid, ts}`, retry 100 мс, maxWait 5 с (по истечении — `UserFacingError`
«journal busy, holder pid …»), кража по возрасту ≥ 30 с (без process.kill-liveness —
container-safe: два контейнера с равными pid не дают ложного «живого» держателя,
владелец определяется только по факту файла). Ожидание — блокирующая пауза
`Atomics.wait` (критические секции — миллисекунды; CLI однозадачен, MCP-процесс
одиночного пользователя блокируется не дольше maxWait).

Охват REQ-333-7: `recordDeliveries` берёт лок ОДИН раз на весь батч.

Совместимость с Docker CI: только `node:fs`, без нативных зависимостей; O_EXCL
работает на overlayfs/ext4; зависший/убитый процесс не блокирует навсегда
(кража по возрасту). Ограничение (документируется): NFS/сетевые ФС не
поддерживаются — local-first, как и остальной носитель.

Отклонённые альтернативы:

- `flock`/нативный аддон — новая runtime-зависимость (запрещена без обоснования;
  сборочное бремя ради примитива, который уже есть в проекте в файловом виде).
- Без лока (merge-политики, retry по содержимому) — не устраняет само окно
  read-modify-write; r2a/r2b невоспроизводимо чинятся только взаимным исключением.
- Перевод порта на async ради переиспользования `withMemoryLock` как есть —
  каскадная правка контракта (порт → use-cases → CLI+MCP+тесты) без выигрыша в
  поведении; синхронный двойник — ~40 строк рядом с проверенным оригиналом.
- Координация через SQLite — носитель журнала зафиксирован ограничением
  (append-only JSONL на общем корне).

# 5. ADR-340-2 (REQ-333-4): маркер миграции и fail-closed при утрате

Решение: маркер — постоянный файл `<root>/.wolf/memory/micro-note-delivery.migrated.json`,
содержимое `{ "migrated_at": "<ISO>", "sources": ["index.sqlite"|"worktree-journal", …] }`;
пишется атомарно (tmp + rename) в ТОЙ ЖЕ критической секции, которая создаёт
журнал первым импортом. Самозаживление: журнал есть, маркера нет (проект с
3.3.x, окно сбоя между rename и записью маркера) → маркер дописывается при
первой же операции под локом — состояние не меняется.

Машина состояний (оценивается под локом на каждом публичном вызове):

1. Журнал есть → нормальное чтение (+самозаживление маркера).
2. Журнала нет, маркер есть → **утрата**: каждый публичный метод порта бросает
   `JournalStateUnknownError extends UserFacingError` с текстом «suppression
   journal is missing after migration — state unknown (REQ-03); run
   `wolf contradict restore`». Никакая команда не воссоздаёт журнал молча
   (иначе утрата превратилась бы в «тихо пустое состояние»); записи
   deliveries/наблюдения тоже не пишутся.
3. Журнала и маркера нет → **fresh**: первый импорт (ADR-340-3) из всех
   доступных источников. Свежая оценка с нулевым результатом И без отказов
   источников (новый проект без suppressions) завершается созданием ПУСТОГО
   журнала + маркера `sources: []` в той же критической секции — fresh
   выполняется ровно один раз (§6, git-спавн не на горячем пути); для пользователя
   это неотличимо от прежнего «файл создаётся первой записью» (уточнение
   ведущего, REV-340 F-2: повторный пересмотр источников на каждый вызов
   отклонён). Если часть источников отказала (all-or-nothing) и строк нет —
   состояние остаётся fresh для повторной попытки (транзиентные IO-ошибки не
   замораживаются).

Поведение команд в утрате (AC-4.1): `list`/`report`/`resolve` — явный
диагностический отказ (exit ≠ 0, текст с подсказкой restore); `brief`/`call` —
delivery micro-notes приостановлена (fail-closed: ни одна заметка не
доставляется, т.к. подавления неизвестны) + явная строка в выводе
«Micro-note delivery suspended: suppression journal state unknown — run
`wolf contradict restore`»; атрибуция доставок не пишется. `restore` —
единственное явное восстановление (§10.4).

Сброс (AC-4.3): удалить И журнал, И маркер → fresh → следующий доступ выполняет
новый первый импорт. Путь документируется в docs и в выводе restore.

Что доступно при восстановлении (документируется в выводе restore и docs):
замороженная копия журнала в `index.sqlite` (строки НА момент миграции),
wt-журналы ≤3.3.1; записи, дописанные в общий журнал ПОСЛЕ миграции,
невосстановимы (носитель append-only, копий не держит) — это явная граница
потери, не угадывание. Откат на 3.3.2: формат журнала не меняется, маркер —
неизвестный старой версии файл, игнорируется безвредно.

Отклонённые альтернативы:

- Маркер внутри `index.sqlite` — кэш перестраивается/удаляется, маркер исчезнет
  вместе с причиной.
- Маркер-строка внутри самого журнала — для обнаружения утраты надо прочитать
  утраченный файл; бессмысленно.
- Молчаливый реимпорт SQLite с merge (как предложено в FINDING 3.3.1) —
  воспроизводит r4: пост-миграционные подавления теряются, состояние
  «восстанавливается» частично и незаметно.

# 6. ADR-340-3 (REQ-333-1): импорт wt-журналов и re-id

Перечисление: `listWorktreeCheckouts(baseDir)` — полные пути живых записей
`git worktree list --porcelain` (тот же парс, что `liveWorktreeBasenames`,
memory-root.ts:65; git — документированный контракт, ручной парс `.git/worktrees/`
отклонён: дублирует семантику prunable/bare/переносов). Корневой чекаут
исключается из источников (его журнал — цель). Исчезнувший каталог источника —
пропускается с пометкой в отчёте.

Когда: автоматически — только в состоянии fresh (момент апгрейда, один раз);
далее — явно командой `wolf contradict import` (идемпотентный досмотр wt-журналов).
Постоянный пересмотр на каждый load отклонён: git-подпроцесс на горячем пути
(бюджет NFR-01/AC-7.2) и неожиданные побочные записи.

Порядок слияния (детерминированный): сначала строки замороженного
`index.sqlite` (в порядке и с правилом нумерации сегодняшнего `migrateLegacy`:
`suppressed_at, memory_id`, `cnr_<день>_<счётчик hex6>`), затем wt-журналы по
лексикографическому пути чекаута, внутри — в порядке строк файла.

Что импортируется: suppression-строки целиком (открытые и resolve-снимки,
оба evidence, история решений — AC-1.2) с дедупликацией по `suppression_id`;
observations — слияние по `memory_id` (побеждает больший `updated_at`,
идентичные пропускаются); deliveries — при первом импорте/restore полностью,
при повторном `import` — дедупликация точным совпадением канонического JSON
(два неразличимых события deliveries — принятая грубость).

Идемпотентность (AC-1.3): присутствующие в журнале id пропускаются; повторный
запуск ничего не дублирует.

Коллизия `suppression_id` (AC-1.4): входящий id уже есть, но запись отличается
(канонический JSON всей записи неравен) → re-id: ВСЯ цепочка входящей записи в
этом источнике (открытая строка и её resolve-снимки) получает один
детерминированный новый id `cnr_<YYYYMMDD из suppressed_at>_r<sha256(канонический
JSON открытой записи), hex[0..12]>`; если и он занят — окно hex расширяется
12→16→24→32 до свободного (завершающийся детерминизм). Префикс `cnr_` и формат
дня сохраняются (ограничение). Порядок снимков цепочки сохраняется
(`suppressed_at`, затем `resolved_at`).

Валидация: каждая импортируемая строка проходит единый валидатор (ADR-340-4);
источник с невалидной строкой отвергается ЦЕЛИКОМ (all-or-nothing на источник),
остальные импортируются, команда завершается с ошибкой и перечнем отвергнутых
источников (REQ-03: частично применённое состояние не изобретается).

Отклонённые альтернативы:

- Перечисление по `.git/worktrees/*` — дублирование внутренних структур git.
- Автоматический импорт на каждый load — подпроцесс git на горячем пути,
  скрытые записи.
- Re-id случайным суффиксом/счётчиком — невоспроизводимость между запусками
  (AC-1.4 требует детерминизм).
- Пропуск resolve-снимков при коллизии — рвёт цепочку аудита (против AC-1.2/1.4).

# 7. ADR-340-4 (REQ-333-3): единый валидатор строки журнала

Единственная экспортируемая функция адаптера `parseJournalLine(raw, where)`:
после `JSON.parse` проверяет `kind ∈ {suppression, delivery, observation}`,
`record` — непустой объект, и обязательные поля каждого kind с типами:

- suppression: `suppression_id, memory_id, revision, reason, note_evidence,
contradiction_evidence, suppressed_at` — непустые строки; `resolved_at`,
  `resolution` — строка | null;
- delivery: `memory_id, revision, ts` — непустые строки; `channel ∈ {brief, call}`;
  `kind ∈ {selected, delivered}`;
- observation: `memory_id, revision, updated_at` — непустые строки;
  `observed_use` — строка | null; `observed_outcome` — непустая строка.

Матрица поведения (везде — явная диагностика с файлом и номером строки):

- JSON невалиден, последняя строка → обрыв записи (crash) → прежняя repair-семантика
  REQ-332-3 (AC-3.3 не меняется): валидатор-полная → финализация, иначе обрезка.
- JSON невалиден в середине → `UserFacingError` (как сегодня).
- JSON валиден, структура невалидна — В ЛЮБОЙ позиции, включая хвост:
  `UserFacingError`, состояние НЕ применяется. Молчаливая обрезка скрыла бы
  ручную правку (класс r3), молчаливый пропуск применил бы частичное состояние.
  `append` в такой позиции отказывает до ручного исправления строки.
- Потребители: `load()`, `repairTail()` (решение финализировать/обрезать/отказать),
  импорт wt-журналов и restore (AC-3.2 — один носитель правила; слабый второй
  «валидатор» `isCompleteJournalLine` упраздняется).

Отклонённые альтернативы: skip-with-warning (частичное применение состояния —
против REQ-03); truncate для полной, но структурно неверной строки (та же
скрытая утрата, что r3, в другом месте); локальные проверки на каждом callsite —
дефект возник именно из-за расхождения двух неявных «валидаторов».

# 8. ADR-340-5 (REQ-333-5): ревизия наблюдения в report

CLI: `wolf contradict report --revision <hex>` — опционально; MCP: report-ветка
`note_contradiction` получает опциональное `observed_revision` (только
добавления). Use-case: единое поле `observed_revision?: string`; нормализация —
trim, формат `^[0-9a-f]{12,64}$` (12 — длина префикса, которым журнал
пользователю всегда показывает ревизию), иначе `UserFacingError`.

Семантика: без поля — сегодняшнее поведение (привязка к текущей ревизии,
AC-5.1). С полем: если текущая ревизия начинается с наблюдаемой (или равна) —
запись как сегодня. Иначе (расхождение) — запись создаётся с `revision` =
НАБЛЮДАЕМОЙ ревизии (конфликт остаётся привязан к тому тексту, о котором
свидетельство; аудит сохранён), команда завершается успехом, но печатает явное
предупреждение: наблюдаемая ревизия ≠ текущей, ТЕКУЩАЯ ревизия НЕ подавляется,
заметка продолжает доставляться; если противоречие воспроизводится на текущем
тексте — отчётить повторно. Следствие существующих правил: `openContradiction`
(равенство ревизий) не блокирует текущую ревизию; в `list` запись видна как
`block: superseded`. `note_evidence` — наблюдаемая rev12.

Отклонённые альтернативы:

- (a) отказ при расхождении — теряет свидетельство устаревшего наблюдения,
  ломает скриптовые сценарии; AC-5.2 требует «reports the change and does not
  suppress», т.е. запись+сообщение.
- Запись под ТЕКУЩУЮ ревизию с флагом расхождения — воспроизводит r5 (старое
  свидетельство глушит исправленный текст).

# 9. ADR-340-6 (REQ-333-7): один снимок на вызов и пакетная запись доставок

Порт: `recordDeliveries(records: MicroNoteDeliveryRecord[]): void` — один лок,
один repair, ОДИН append N строк; полную парс-перечитку не делает (deliveries
путём доставки не читаются), триггер первого импорта сохраняет. `recordDelivery`
остаётся для совместимости (делегирует батчу из 1).

Use-cases `generate-agent-brief` / `get-call-injections`: `noteLog.suppressions()`
вызывается РОВНО ОДИН раз на вызов; тот же массив передаётся и в
`createDeliveryAdmission`, и в `selectMicroNotes` — один снимок на вызов
(AC-7.1; сегодня два чтения могли увидеть разные состояния). Записи доставок —
один батч в прежнем порядке строк (delivered, затем selected-не-delivered).
Loss-состояние ловится на этом единственном вызове → suspend (ADR-340-2).

Micro-оптимизация ремонтного чтения (в пределах ADR-332-3): `repairTail` может
читать только хвостовое окно (например, последний 1 МиБ) — позиции обрезки
считаются абсолютно; если `\n` в окне не найден — полное чтение. Семантика
не меняется, даёт запас по AC-7.2 на журналах большого объёма.

Свежесть REQ-332-1 не ослабляется: кэша между вызовами нет; снимок —
консистентность ВНУТРИ одного вызова (документируется). Критерий AC-7.2:
стенд r7 (синтетический журнал 100 000 строк, 8 micro-notes, реальный `brief`)
— медиана кандидата ≤ медиана 3.3.1 × 1.10.

Отклонённые альтернативы: mtime/size-кэш подавлений (отклонён ещё ADR-332-1 —
остаточная гонка); отказ от записи deliveries (изменение наблюдаемого
поведения); компакция журнала (вне скоупа, будущий CR — прецедент §12 3.3.1).

Адаптер дополнительно: `importWorktreeJournals(): ImportReport`,

## 10.3 CLI `wolf contradict` (только добавления; тексты команд — английский)

- `report`: новый опциональный `--revision <hex>` (§8); при расхождении —
  строка предупреждения в stdout, exit 0.
- `resolve`: вывод дополняется статусом заметки после закрытия записи:
  «Note still blocked by N open contradiction(s) on the current revision» либо
  «No other open contradictions on the current revision — delivery resumes»;
  description/help переформулированы БЕЗ обещания возобновления доставки
  (закрывается ровно одна запись — AC-6.1).
- `list`: каждая строка дополняется `deliverable: yes|no|unknown` — указывает
  на «запись адресована сейчас доставляемому micro-note» без обещаний
  контекстно-зависимой доставки (бюджет, дедуп, применимость — AC-6.2);
  `suppressionBlockState` расширяется: заметка есть, но не deliverable
  micro-note → `unknown` (класс r6 «block: actual» после снятия тега
  исчезает), правилоdisplay-only, фильтр доставки (`openContradiction`) не трогается.
- `import` (новая): идемпотентный досмотр wt-журналов; в loss-состоянии
  отказывает с подсказкой restore.
- `restore` (новая): только в loss-состоянии; пересобирает журнал из
  `index.sqlite` + wt-журналов; печатает отчёт источников (импортировано по
  видам, re-id-соответствия, отвергнутые источники, недоступные источники) и
  явную границу потерь («записи общего журнала после миграции
  невосстановимы»); при существующем журнале — отказ. См. §10.4.

## 10.4 Схема restore/import (отчёт)

`{ sources: [{ path, kind, imported: {suppressions, deliveries, observations}, reid: [{from, to}], refused?: reason }], unrecoverable: string }`; exit 0 при успешной пересборке (потери — ожидаемая часть отчёта), отказ — если пересобрать не из чего или IO-ошибка.

## 10.5 MCP (только добавления)

`note_contradiction`, action=report: `observed_revision: z.string().optional()`
(та же нормализация в use-case); текст ответа при расхождении содержит то же
предупреждение; action=resolve — текст ответа дополняется статусом блокировки
(§10.3). Новых тулов/actions нет; каталог не растёт (guard-тест ≤ 12).

# 11. Инварианты конкурентности и порядок записи

- Инвариант I1: любая мутация журнала — внутри журнального лока, «прочитал →
  решил → записал» атомарно относительно других процессов.
- Инвариант I2: первый импорт (SQLite/wt) выполняется только когда журнала НЕТ —
  проверка внутри лока; «поздний импорт заменяет журнал» невозможен по
  построению (AC-2.2), rename-окно миграции больше не пересекается с чужой
  записью.
- Инвариант I3: двойной resolve — второй видит уже разрешённую запись и получает
  явный отказ «unknown or already resolved»; двух конфликтующих снимков решения
  в журнале не возникает (AC-2.3).
- Инвариант I4: repair-окно (read → truncate/finalize → append) целиком под
  локом; параллельный report дожидается и пишет после (AC-2.1).
- Инвариант I5: ни одна операция не создаёт журнал в loss-состоянии.
- Управляемые паузы тестов (`PAUSE333_TRUNCATE_MS/RENAME_MS/APPEND_MS/READ_N`)
  остаются рабочим инструментом: пауза держится ПОД локом, второй процесс
  дожидается в пределах maxWait 5 с (паузы тестов ≤ 2.5 с).

# 12. Отказы, восстановление, совместимость

- Частичный сбой импорта: all-or-nothing на источник, отчёт перечисляет
  отказавшие; журнал пишется одной атомарной заменой (tmp+rename) под локом.
- Утрата журнала — см. §5; restore — единственный путь состояния-в-состояние.
- Совместимость: формат строки не меняется; 3.3.2-журнал (без маркера)
  самозаживляется; откат на 3.3.2 читает тот же журнал, маркер игнорирует.
  Новые CLI-флаги/команды и MCP-поле — только добавления; старые вызовы без них
  поведенчески эквивалентны.
- Наблюдаемость: диагностические тексты называют файл, строку и состояние
  (REQ-03); предупреждение о расхождении ревизии — в stdout CLI и тексте MCP.

# 13. NFR и зависимости

- Новых runtime-зависимостей нет: лок — `node:fs` (O_EXCL), sleep —
  `Atomics.wait`, хеш re-id — `node:crypto`; чтение SQLite — существующий
  `better-sqlite3`.
- Бюджет производительности: AC-7.2 (медиана brief ≤ 3.3.1×1.10 на стенде r7);
  метод измерения — скрипт стенда (5 прогонов, медиана), плюс структурный
  guard-тест «≤ 1 парс-чтения и 1 append журнала на вызов» (T-333-7.1).
- Бюджет лока: maxWait 5 с по умолчанию (конфигурируемо в тестах), паузы тестов
  ≤ 2.5 с.

# 15. Риски и открытые вопросы

- Блокирующее ожидание лока в MCP-процессе (до maxWait) — приемлемо для
  однопользовательского контура; при росте параллелизма — будущий CR (async-порт).
- Кража лока по возрасту может отнять лок у процесса, задержавшегося > 30 с
  (осознанный local-first риск, как в schema-guard; последняя запись выигрывает,
  append-only носитель не портится).
- Производительность валидатора на 100k-строчном журнале — линейные проверки
  типов; входит в замер AC-7.2.
- Объём импорта deliveries при restore больших wt-журналов — одноразовая
  операция с отчётом; ограничений размера не вводим.
- Релиз — вне этого дизайна (D-340-3: гейты и релиз — ведущий).
