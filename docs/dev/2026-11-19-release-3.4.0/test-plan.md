База красного прогона: `7c3674ba` (тег v3.3.2). Каждый REQ-контракт —
регрессионная проверка, красная на базе, зелёная после реализации (TDD).
Оракулы — формулировки AC-x.y из requirements.md и стенд воспроизведения
`/private/.../opencode/repro-333` (r1..r7, `pause333.cjs`), а не предложенный
код.

Единицы и уровень:

- unit — `tests/unit/adapters/fs/jsonl-micro-note-delivery-log.test.ts`
  (расширить), `tests/unit/adapters/memory-lock.test.ts` (синхронный двойник);
- integration — новые файлы `tests/integration/`:
  `micro-note-journal-races.test.ts` (гонки РЕАЛЬНЫХ процессов),
  `micro-note-journal-upgrade.test.ts` (реальный git worktree + импорт),
  `micro-note-journal-loss.test.ts` (маркер, утрата, restore);
- e2e — `tests/e2e/` (spawn CLI; MCP — stdio-харнесс `mcp.e2e.ts`);
- стенд — измерение AC-7.2 и сквозные сценарии на собранном артефакте.

Реальные процессы (ограничение requirements): миграционные и конкурентные
проверки — `spawn node <dist/bootstrap/cli.js>` с управляемой паузой
`NODE_OPTIONS="--require tests/helpers/journal-pause.cjs"` (порт стенда
`pause333.cjs`, те же переменные: `PAUSE333_TRUNCATE_MS`, `PAUSE333_RENAME_MS`,
`PAUSE333_APPEND_MS`, `PAUSE333_READ_N`, `PAUSE333_LOG`). Паузы ≤ 2.5 с —
в пределах maxWait лока (design §4): второй процесс дожидается, а не крадёт лок.
Pre-upgrade состояние моделируется содержимым: файл журнала формата 3.3.1
кладётся в `<wt>/.wolf/memory/` напрямую (фикстура из r1), legacy — фикстура
`tests/fixtures/micro-note-index-330`.

# 1. REQ-333-1 — импорт wt-журналов при апгрейде (T-333-1.x)

- T-333-1.1 (AC-1.1, integration, реальные процессы): проект с pre-upgrade
  wt-журналом (активное подавление, фикстура r1) → первый доступ кандидата из
  main и из worktree: `brief` скрывает заметку в обеих копиях, `list` показывает
  запись с тем же `cnr_`-id, `resolve --id` адресует её. Красный на базе
  (3.3.2 импорта нет — заметка доставляется).
- T-333-1.2 (AC-1.2, unit): источник wt-журнал с открытой и разрешённой
  записями (оба evidence, `resolved_at`/`resolution`) → импорт переносит всё
  дословно; порядок снимков цепочки сохранён.
- T-333-1.3 (AC-1.3, integration, реальные процессы): три пути — (а) общий
  журнал уже есть: повторного импорта и дублей нет; (б) журнала нет: первый
  импорт из SQLite + wt-журналов создаёт журнал и маркер; (в) несколько
  worktree с pre-upgrade журналами: все источники импортированы; повторный
  `wolf contradict import` не дублирует записи (сравнение снимков журналов).
- T-333-1.4 (AC-1.4, unit): входящая запись с коллизией `suppression_id`
  (содержимое отличается) сохраняется под детерминированным новым id ВМЕСТЕ со
  всей resolve-цепочкой; исходная история не перезаписана; повторный импорт того
  же источника даёт тот же новый id (детерминизм).

# 2. REQ-333-2 — параллельные операции (T-333-2.x, реальные процессы)

- T-333-2.1 (AC-2.1, integration): r2a на кандидате. Журнал с обрывком хвоста;
  процесс A — `report` с `PAUSE333_TRUNCATE_MS=2500`; через 1.2 с процесс B —
  `report`. Оба exit 0, ОБЕ записи в журнале, `list` показывает обе.
- T-333-2.2 (AC-2.2, integration): r2b на кандидате. Legacy `index.sqlite`,
  журнала нет; A — `report` с `PAUSE333_RENAME_MS=2500` (окно миграции), B —
  `report` параллельно. Журнал содержит и запись A, и запись B; поздний импорт
  не заменил журнал с подтверждённым report.
- T-333-2.3 (AC-2.3, integration): r2c на кандидате. Два параллельных
  `resolve` одного id (оба с `PAUSE333_APPEND_MS`/`PAUSE333_READ_N`): ровно один
  успех, второй — явный отказ («unknown or already resolved»); в журнале нет
  двух конфликтующих снимков решения по одному id.
- T-333-2.4 (AC-2.4, e2e, реальные процессы): CLI `report` (spawn) →
  `note_contradiction` action=resolve в заспавненном MCP-сервере (stdio) видит
  запись и успешно закрывает; обратное направление (MCP report → CLI resolve) —
  то же. Один носитель/путь порта для обоих каналов.

# 3. REQ-333-3 — единый валидатор (T-333-3.x)

- T-333-3.1 (AC-3.1, unit + integration): строка «валидный JSON, неполная
  структура» (r3: `{"kind":"suppression","record":{"suppression_id":"…"}}`) в
  середине И в хвосте: `load`/`append`/`list` (spawn) отказывают с именем файла
  и номером строки; файл НЕ изменён (молчаливой обрезки/пропуска нет); после
  удаления строки состояние равно прежнему — активное подавление не исчезло.
- T-333-3.2 (AC-3.2, unit): одна и та же неверная строка даёт одинаковый отказ
  через всех потребителей валидатора: чтение (`load`), repair (`append`),
  импорт wt-журнала — одна функция, один текст диагностики.
- T-333-3.3 (AC-3.3, unit, регрессия): обрывок JSON в хвосте — прежняя
  repair-семантика (обрезка; финализация полной строки): T-332-3.1–T-332-3.5
  остаются зелёными без изменений.

# 4. REQ-333-4 — маркер миграции и утрата (T-333-4.x)

- T-333-4.1 (AC-4.1, integration, реальные процессы): мигрированный проект
  (журнал + маркер после первого доступа) → `rm` журнала → заспавненные
  `brief` (micro-notes не доставлены + строка о приостановке), `list`,
  `report`, `resolve` — явные диагностики, exit ≠ 0; файл журнала НЕ
  воссоздан, строки legacy SQLite НЕ воскрешены (в `list` их нет).
  Красный на базе (r4: тихий реимпорт).
- T-333-4.2 (AC-4.2, integration): в loss-состоянии `wolf contradict restore`
  пересобирает журнал из замороженного SQLite + wt-журналов; отчёт называет
  источники, счётчики, re-id и явную границу потерь (пост-миграционные записи
  невосстановимы); после restore подавление эффективно (`brief` скрывает).
  При существующем журнале restore отказывает.
- T-333-4.3 (AC-4.3, integration): удалены И журнал, И маркер → следующий
  доступ = свежий первый импорт (журнал после сброса эквивалентен журналу
  первого импорта: те же детерминированные id). Документированный путь сброса
  отражён в выводе restore и в docs (проверка `docs:verify`).

# 5. REQ-333-5 — ревизия наблюдения (T-333-5.x)

- T-333-5.1 (AC-5.1, e2e, spawn CLI + unit-схема MCP): `report` без
  `--revision` привязывает запись к текущей ревизии (регресс r5-пре-стейта);
  MCP report без `observed_revision` — эквивалентно; `--revision` короче 12
  hex или не-hex — явный отказ.
- T-333-5.2 (AC-5.2, e2e, spawn CLI + MCP stdio): сценарий r5 — заметка
  отредактирована (v1→v2), затем `report --revision <v1>`: exit 0, предупреждение
  о расхождении в выводе, запись хранится с ревизией НАБЛЮДАЕМОЙ, `brief`
  продолжает доставлять v2, запись видна в `list` (`block: superseded`),
  `resolve --id` адресует её; MCP `observed_revision` — то же поведение и текст
  с предупреждением.

# 6. REQ-333-6 — честные статусы (T-333-6.x)

- T-333-6.1 (AC-6.1, e2e, spawn CLI + MCP): две открытые записи одной заметки;
  resolve первой — вывод называет остаточную блокировку («still blocked by
  1 open contradiction…», доставки НЕТ); resolve второй — «delivery resumes»;
  новый текст help resolve не обещает возобновление доставки при закрытии
  одной записи; текст ответа MCP resolve содержит тот же статус.
- T-333-6.2 (AC-6.2, unit + e2e): хелпер deliverable: yes (micro-note текущей
  ревизии, нет открытых записей сверх рассматриваемой), no (тег снят /
  superseded / заблокирована), unknown (заметки нет в store); e2e — сценарий
  r6 (тег снят, ревизия та же): в `list` `deliverable: no` и `block: unknown`
  (обещания доставки нет).

# 7. REQ-333-7 — стоимость выдачи (T-333-7.x)

- T-333-7.1 (AC-7.1, unit, структурный guard): один in-process `brief` и один
  `call` над журналом на 8 заметок со spy на fs: парс-чтений журнала ≤ 1
  (плюс одно repair-чтение — граница ≤ 2 `readFileSync` журнала), appends = 1
  (батч N строк одним вызовом), вызовов `suppressions()` на invocation = 1.
  Красный на базе (8 appends, 2 парс-чтения).
- T-333-7.2 (AC-7.2, стенд, реальный артефакт): процедура r7 на кандидате —
  синтетический журнал 100 000 строк, 8 micro-notes, `brief` ×5, медиана;
  критерий: медиана(кандидат) ≤ медиана(3.3.1) × 1.10. Результаты — в evidence
  (r7-340-times.txt); прогон дважды (холодный/тёплый кэш скана) — критерий по
  тёплому, расхождение фиксируется в отчёте.
