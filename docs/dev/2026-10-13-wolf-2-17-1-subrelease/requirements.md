# 2.17.1 — подрелиз по внешнему ревью 2026-10-13 — функциональные требования

## 1. Контекст и проблема

Внешнее ревью от 2026-10-13 (`.external_experts_review/2026-10-13-review/wolf-next-release-handoff.md`, база daac1b1) проверило выпуск 2.17.0 воспроизведениями и выявило дефекты в трёх работающих путях: сеемый playbook Стюарда учит устаревшую команду мутации (R01), изоляция памяти рабочих копий (worktree) нарушена в трёх независимых местах (R02), многошаговая мутация лица при сбое оставляет память в несогласованном состоянии без возможности восстановления (R04). Дополнительно: инструкция установки на сайте и в README обещает то, чего минимальный `wolf init` не делает (R07), документирован инцидент двух активных писателей в один worktree (R06), частичная миграция legacy-лиц не дозавершается (R05), а зелёные файловые тесты не доказывают поведение в настоящем диалоге (R08).

Владелец утвердил состав подрелиза 2.17.1 (решение mem_20261013_sostav_2_17_1_utverzhden_vladeltsem_r01_1ce61f, тред mem_20261013_podreliz_po_vneshnemu_revyu_2026_10_13_d_bec602): R01 + R02 + R04 + R07, из R06 — только запрет двух активных писателей, R08 — урезанный (проверки + два сквозных сценария), R05 — по оценке L1, R03 — целиком в 2.18.0.

**Метрика успеха**: на актуальном main каждая верифицированная точка ревью закрыта проверкой; свежая установка и обновление дают Стюарду рабочую методику; рабочие копии не видят чужую доставку; сбой посреди мутации лица восстановим без потери следа; сайт/README/итоговые документы соответствуют факту.

**Верификация на актуальном main** (HEAD 37ac8c02a6a77c14e645798cadf0a82dd687fc98, дерево чистое; diff от базы daac1b1 — только новый скилл, src/templates не затронуты): все перечисленные ниже наблюдения подтверждены повторно 2026-10-13, evidence в разделе «Ограничения и допущения» и в логах `/tmp/wolf-2171-verify/` (свежая установка: `r01-init.log`, `r01-face-show.log`, `r01-oldcmd.log`; scope: `r02-add-scope.log`).

## 2. Область

**Входит:**

- R01 — playbook Стюарда на свежей установке рабочий (`wolf face new` + 7 полей G17, атрибуция через разрешённый механизм launcher'а, без двойного generic supersede); обновление уже посеянного live-лица — штатным версионирующим путём.
- R02 — единый устойчивый идентификатор worktree + единый формат scope; фильтрация видимости до всех ветвей отбора (включая keyword-уроки); совместимость с уже записанными `worktree:<name>`; неоднозначное старое имя — честный конфликт.
- R04 — восстанавливаемый commit мутации лица (механизм — на design: журнал намерения/дозавершение либо staging+активация); повтор с тем же operation ID.
- R05 — дозавершение частичной миграции legacy-лиц + аудит путей изменения face (включено по оценке L1 — см. REQ-04).
- R06 (урезанный) — только запрет двух активных писателей на TASK/plan/report/worktree: атомарный claim + проверяемый владелец. Машина job'ов фонового learn — НЕ входит.
- R07 — два явных пути установки на сайте/в README; примеры = результат чистого запуска; итоговое состояние отчёта 2.17 и roadmap приведено к факту (append-only журнал сохранить); maturity-формулировки без преувеличения обучения.
- R08 (урезанный) — интеграционные проверки изменённых путей + минимум 2 сквозных сценария с tool traces: (1) Стюард-мутация с G17 → новое задание получает новую версию лица, активное — прежнюю; (2) доставка памяти между рабочими копиями.

**Не входит (не-цели):**

- R03 полностью — граница применения новой версии лица («лицо живёт на процесс») → 2.18.0; ограничение документируется (см. раздел 6).
- Async learning — 2.18.0 (машинное владение job, расписание, lease/heartbeat — не здесь).
- Полная серия R08 (4 сценария с измерением качества/стоимости) — 2.18.0.
- Публикация npm, релизный тег, деплой сайта — только отдельным поручением владельца; перед релизной подготовкой — скилл wolf-release-docs.

## 3. Глоссарий

- **Стюард (Наставник)** — агент, единственный уполномоченный мутировать лицо (playbook) другого агента через память Wolf.
- **G17** — обязательные 7 полей записи мутации лица: reason, minimal_change, boundaries, example_helps, example_keep, verification, rollback.
- **`wolf face new`** — версионирующая команда создания новой версии лица (сама выполняет supersede предыдущей).
- **Face** — версионируемый core-тип памяти (лицо агента); active-версия ровно одна на owner_skill.
- **Linked worktree** — дополнительная рабочая копия git, связанная с общим репозиторием (`git worktree add`).
- **Scope доставки** — метка области видимости объекта памяти (`worktree:<id>`, `main`, `project`, `global`), по которой фильтруются кандидаты инъекций при `wolf call`.
- **Legacy-инъекция / legacy-лицо** — объект, записанный до текущего формата scope/типов (call-injection-заметки; howto-записи до миграции в face).
- **Claim** — атомарное занятие владения работой (TASK/план/worktree) с проверяемым идентификатором владельца.
- **Tool trace** — сохранённая запись фактического вызова инструмента агентом (команда, аргументы, результат), в отличие от фразы «применяю скилл».

## 4. Функциональные требования

### REQ-01 — Рабочий playbook Стюарда на свежей установке и при обновлении (R01)

- История: Как владелец проекта на свежей установке, я хочу чтобы Стюард получал методику мутации, которая реально исполняется текущим CLI, чтобы мутации лиц проходили штатно.
- Требование: Когда проект инициализируется (`wolf init --full --platform opencode`) или обновляется с 2.16.3/2.17.0, посеянное лицо Стюарда должно предписывать создание новой версии через `wolf face new` с полными 7 полями G17; атрибуция мутации — `agent:steward`, задаваемая разрешённым механизмом launcher'а (не предлагать обход guard через пользовательский `--created-by`); после успешного `wolf face new` второй generic supersede не выполняется; обновление уже посеянного live-лица идёт штатным версионирующим путём (одна правка шаблона + `wolf sync` не меняют лицо в памяти).
- Обоснование: сейчас свежая установка сеет методику с `wolf add --type playbook` (steward-nastavnik.md:25) и отдельным supersede (:28), которую CLI отвергает (проверено: exit 1, допустимые типы без playbook); live-лицо Стюарда в существующих проектах продолжает учить нерабочей команде.
- AC:
  - На чистом проекте `wolf face show steward` содержит `wolf face new` и 7 полей G17, не содержит `wolf add --type playbook` как путь мутации.
  - Мутация по новой методике создаёт ровно одну новую версию лица с G17-записью и связями; повторный generic supersede не выполняется.
  - Правила/рамки других агентов не изменяются в рамках мутации методики Стюарда: diff затронутых записей памяти не содержит изменений чужих face/правил/playbook; агрегация уроков остаётся на разрешённом механизме launcher'а и не прячется внутри методики мутации (evidence: diff/лог мутации до/после).
  - Команда неуполномоченного актора отклоняется.
  - Проект, обновлённый с 2.16.3/2.17.0 (без переинициализации), получает актуальное лицо штатным путём; `wolf sync` не обновляет содержимое лица (статус mutated-skip конфликта — как сейчас).
- Приоритет: Must
- Источник: ревью R01; верифицировано 2026-10-13 (HEAD 37ac8c0, /tmp/wolf-2171-verify/r01-\*).

### REQ-02 — Изоляция памяти рабочих копий: единый ID, формат scope, фильтрация всех ветвей (R02)

- История: Как разработчик, работающий в linked worktree, я хочу чтобы память моей копии не доставлялась в другие копии и в main, чтобы задачи не смешивались.
- Требование: Когда любой путь доставки (`wolf call` в любом режиме) отбирает кандидатов, система должна применять scope-фильтрацию ДО всех ветвей отбора — включая уроки и правила, добавляемые по ключевым словам; идентификатор worktree должен быть единым и устойчивым (одинаковый basename двух копий не даёт одинаковый ID); формат scope записи и сравнения — один; уже записанные `worktree:<name>` совместимы: однозначное старое имя маппится, неоднозначное (две живые копии с тем же basename) — честный конфликт, не тихое присвоение.
- Обоснование: три независимых дефекта на 2.17.0, все верифицированы на HEAD: (a) `currentScope` передаётся голым именем (memory-call.ts:54), а сравнение идёт с префиксом `worktree:` (get-call-injections.ts:82–90) — собственная legacy-инъекция скрыта; (b) keyword-уроки/правила берутся из полного пула без visible-фильтра (get-call-injections.ts:112–126) — чужой урок доставляется в main; (c) `resolveMemoryRoot` использует basename (memory-root.ts:32) — две копии `a/task` и `b/task` получают один `worktree=task`. Явный `--scope` для lesson отклоняется схемой (exit 1, «Unknown field scope»), автоматическая простановка — отдельным путём.
- AC:
  - Объект, записанный из копии W (в т.ч. legacy call-injection), доставляется в W и не доставляется в main и другие копии.
  - Keyword-урок из копии W не появляется в доставке другой копии/main без promote.
  - Две копии с одинаковым basename имеют разные идентификаторы; записанное ранее неоднозначное имя не присваивается ни одной из копий молча — отчёт о конфликте.
  - Правила/тред-пути доставляются по действующим правилам scope; состав видимых типов не расширяется.
  - Unknown/broken git metadata не даёт доступа к чужому scope.
  - Promote делает знание общим без изменения содержания.
- Приоритет: Must
- Источник: ревью R02; верифицировано 2026-10-13 (HEAD 37ac8c0).

### REQ-03 — Восстанавливаемый commit мутации лица (R04)

- История: Как владелец памяти, я хочу чтобы сбой посреди мутации лица не оставлял память в несогласованном состоянии без следа, чтобы восстановление было предсказуемым.
- Требование: Когда многошаговая мутация лица (создание версии, supersede предыдущей, G17-запись, связи, события, индекс) прерывается сбоем записи на любом шаге, система должна приводить память в известное восстанавливаемое состояние и позволять дозавершение/откат с тем же идентификатором операции; различаются состояния «не применено», «применено, требуется восстановление следа», «завершено». Механизм (журнал намерения с дозавершением либо staging с подтверждённой активацией) — решение design в существующей архитектуре, без замены хранилища.
- Обоснование: сейчас create-face-version.ts выполняет цепочку await'ов (face → supersede → G17 → relations) без транзакции/журнала; эксперт подтверждал на реальном хранилище: после отказа G17-записи v1 уже superseded, v2 уже active, записей мутации — 0; lock сериализует писателей, но не откатывает; механизма восстановления в коде нет (grep journal/recover/resume/compensate — пусто).
- AC:
  - Внедрённый сбой после каждой существенной записи (face, supersede, G17, relation, event, index) даёт известное восстанавливаемое состояние (fault-injection тесты).
  - Повтор мутации с тем же operation ID не создаёт вторую версию вслепую.
  - Доставка не выдаёт новую неполную мутацию как подтверждённый канон; предыдущий канон доступен согласно выбранному design-контракту.
  - После восстановления одна операция = одна версия с полным следом; rollback не уничтожает историю; сбой производного индекса обрабатывается отдельно от потери первичных данных.
  - Doctor обнаруживает неполный след мутации.
- Приоритет: Must
- Источник: ревью R04; верифицировано 2026-10-13 (HEAD 37ac8c0, статика + отсутствие тестов fault-injection).

### REQ-04 — Дозавершение частичной миграции legacy-лиц (R05, включено по оценке L1)

- История: Как владелец проекта 2.16.x, я хочу чтобы прерванная миграция лица дозавершалась при повторном запуске, чтобы проект не застревал в половинчатом состоянии.
- Требование: Когда `wolf face migrate` прерывается между созданием face и supersede legacy-head, повторный запуск должен проверять целостность перехода и дозавершать доказуемо связанную незавершённую операцию (supersede legacy-head); неоднозначные случаи (несколько владельцев, изменённый пользователем объект, неоднозначный legacy-head) требуют явного конфликта в отчёте и корректного exit status; старый body не переносится поверх новой версии. Кроме того, в поставку входит явный аудит путей изменения face (та же R05 по ревью :94): generic transition/supersede и иные пути изменения face разобраны явно, административные изменения перечислены, запрещённые пути защищены в use-case, а не только в CLI.
- Обоснование включения: оценка L1 на HEAD — миграция выполняется через тот же `createFaceVersion` (migrate-faces.ts:96), сбой между :96 и :106 (supersede legacy-head) — тот же класс частичного сбоя, что REQ-03; механизм операции/журнала REQ-03 по построению покроет миграцию, добавочный объём — детект незавершённого перехода (сейчас :75 пропускает владельца по факту наличия любого face: «face already exists — re-run is safe»), дозавершение и тесты. Малая работа рядом с R04. Условие: если design REQ-03 выберет механизм, не покрывающий миграцию естественным образом, — вернуться к владельцу через L0 (открытый вопрос OQ-01).
- AC:
  - Сбой на каждом шаге миграции + повтор: завершённые владельцы не откатываются; неполный переход дозавершается.
  - Неоднозначность отражается в отчёте и exit status; «успех» не объявляется по idempotent-skip.
  - Изменённый пользователем объект не перезаписывается старым body.
  - Аудит путей изменения face выполнен: все пути (generic transition, supersede, `wolf face new`, миграция, иные) перечислены явно; для каждого указано, кому разрешён; административные изменения перечислены; запрещённые пути закрыты негативным сценарием на уровне use-case, а не только CLI (evidence: аудит-документ + негативный тест use-case-уровня).
- Приоритет: Must
- Источник: ревью R05; верифицировано 2026-10-13 (HEAD 37ac8c0, migrate-faces.ts:75,96,106).

### REQ-05 — Запрет двух активных писателей TASK/plan/report/worktree (R06 урезанный)

- История: Как координатор волны, я хочу чтобы общий план/отчёт/worktree имел ровно одного активного писателя в каждый момент, чтобы изменения не затирали друг друга (инцидент двух L1 в отчёте 2.17.0).
- Требование: Когда исполнитель (L1/воркер) начинает запись в общий артефакт (TASK-бриф, план, отчёт, worktree-ветка), система должна обеспечивать атомарный claim с проверяемым идентификатором владельца; второй активный писатель того же артефекта отклоняется с понятным отчётом; передача владения — явной процедурой, а не исчезновением первого писателя.
- Обоснование: в report-wave-2-17-execute.md задокументирован фактический инцидент: два L1 писали в один worktree, один commit захватил изменения другого; текстовых предупреждений и `ps=0` недостаточно (ревью R06).
- AC:
  - Два одновременных claim одного артефекта: один успешен, второй получает отказ с идентификатором владельца.
  - Владелец проверяем по записи (кто/когда/что), а не по соглашению в брифе.
  - Запись без claim отклоняется (защита в use-case, не только в CLI).
- Приоритет: Must
- Источник: ревью R06 (финальный абзац AC); решение владельца mem_20261013_sostav_2_17_1_utverzhden_vladeltsem_r01_1ce61f — только эта часть R06.

### REQ-06 — Сквозные проверки: интеграционные по изменённым путям + 2 сценария с tool traces (R08 урезанный)

- История: Как владелец, я хочу чтобы подрелиз доказывал поведение в настоящем диалоге, а не только зелёные файловые тесты.
- Требование: Когда подрелиз принимается, он должен содержать: (а) интеграционные проверки всех изменённых путей (face-мутация, scope-доставка, claim, миграция, установка); (б) минимум два сквозных сценария с сохранёнными tool traces: (1) Стюард выполняет разрешённую мутацию с G17 → новое задание получает новую версию лица, активное задание — прежнюю; (2) доставка памяти между рабочими копиями (своё — доставляется, чужое — нет, promote — делает общим). Засчитывается фактический tool call и артефакт, не фраза «применяю скилл».
- Обоснование: ревью R08: зелёные тесты файлов не доказывают рабочий диалог; владелец урезал серию до двух критичных сценариев.
- AC:
  - Для каждого изменённого пути — интеграционный тест на реальном хранилище/CLI.
  - Сценарий 1: trace содержит wolf face new с G17, версию в face show, доставку новой версии новому заданию и удержание прежней активным.
  - Сценарий 2: trace содержит запись из worktree, отсутствие доставки в main/другую копию, доставку после promote.
  - Traces и артефакты сохранены в папке артефактов с revision и командами.
- Приоритет: Must
- Источник: ревью R08 (сценарии 1–2 и «проверка доставки между рабочими копиями»); решение владельца — урезанный состав.

## 5. Нефункциональные требования (NFR)

### NFR-01 — Совместимость legacy-scope записей

- Требование: Существующие объекты со scope `worktree:<name>` должны оставаться доступны своей копии после перехода на новый идентификатор; неоднозначные имена дают честный конфликт.
- AC: набор regression-тестов на legacy-инъекциях (своя копия видит, чужие — нет); конфликт фиксируется отчётом, не молча.
- Источник: ревью R02 («совместимость уже записанных worktree:<name>»).

### NFR-02 — Не разрушать историю памяти

- Требование: Восстановление/дозавершение мутации и миграции не удаляет существующие записи (версии, supersede-цепочки, события); append-only характер журналов сохраняется.
- AC: после каждого сценария восстановления полный след предыдущих операций читаем; rollback создаёт новую версию, не переписывая историю.
- Источник: ревью R04/R05/R07.

### NFR-03 — Честная изоляция чтения

- Требование: Контракт «где доступ ко всей памяти допустим» зафиксирован в документации: перечислены read-пути с изоляцией доставки и без неё (doctor, MCP, brief, recap, router); состав не расширяется молча.
- AC: документ содержит явный список; тесты не создают новых изолированных типов без изменения требований.
- Источник: ревью R02 («Не объявляй все read-команды изолированными без такого контракта»).
