## 1. Глоссарий (технические термины документа)

- **WT-ID** — устойчивый идентификатор worktree: `worktree:w-<12 hex sha1(realpath(baseDir))>`.
- **Legacy-scope токен** — значение scope вида `worktree:<basename>`, записанное до 2.17.1.
- **Операция лица** — журналируемая цепочка шагов мутации/миграции/healing лица с общим `opId`.
- **Staging-статус** — `candidate`: версия лица создана, но не является каноном (не `active`), доставкой не выдаётся.
- **Activation** — шаг-точка commit: `candidate → active`; до него канон — прежняя версия.
- **Claim** — атомарно захваченная запись владения артефактом (JSON-файл в общем `.wolf`).
- **Healing** — дозавершение доказуемо связанного незавершённого legacy-перехода миграции.
- **Шаблонный дрейф** — расхождение body активного лица с шаблоном base-set.

## 3. Контракты

### 3.1 Идентификация worktree (REQ-02 (R02))

```ts
interface WorktreeIdentity {
  id: string;            // "worktree:w-" + 12 hex sha1(realpath(baseDir))
  legacyName: string;    // basename(baseDir) — для маппинга legacy-токенов
  legacyUnique: boolean; // true — ровно одна живая копия с этим basename
}
resolveWorktreeIdentity(baseDir): WorktreeIdentity | null
// null: main-чекоут, вне git, bare-аномалия, сбой git (fail-closed)
```

- Идентичность — по realpath: одинаковый basename двух копий даёт разные WT-ID; путь копии стабилен на время её жизни (переименование каталога = новая копия с новым WT-ID; задокументировано как ограничение).
- Однозначность legacy-имени: парсер `git worktree list --porcelain` (запуск из baseDir) → список живых каталогов; `legacyUnique = (копий с basename === legacyName) === 1`. Вызов ленивый: только linked-worktree при встрече legacy-токена; кэш на процесс. Main-чекоут git не запускает.

### 3.2 Предикат видимости (REQ-02 (R02), NFR-01)

```ts
// scopeOf(o): строка scope с префиксом 'worktree:' | null (остальное — везде)
function isVisible(o, id: WorktreeIdentity | null): boolean {
  const s = scopeOf(o);
  if (s === null) return true; // main/project/global — везде (как сейчас)
  if (id === null) return false; // worktree-scoped не виден вне копии
  const token = s.slice('worktree:'.length);
  // WT-ID распознаётся СТРОГО: ^w-[0-9a-f]{12}$; чужой хеш не матчится и падает
  // в legacy-разбор (паттерн-именованный каталог w-<12hex> — честный конфликт)
  if (/^w-[0-9a-f]{12}$/.test(token) && token === id.id.slice('worktree:'.length)) return true;
  // legacy-токен:
  if (token !== id.legacyName) return false;
  if (id.legacyUnique) return true; // однозначное имя маппится на эту копию
  conflictRegistry.report(s); // неоднозначное — честный конфликт
  return false; // fail-closed: не видно никому
}
```

- Применение: **каждая** ветвь отбора `getCallInjections` пропускает кандидатов через `isVisible` до ранжирования: (1) call-injections/alias-note, (2) keyword-уроки (:114–121), (3) keyword-правила (:122–126), (4) fallback-правила (:128–129), (5) thread-блокеры (:144–158). Thread-правила с `scope === 'project'` (:136–143) фильтр проходят тривиально (не worktree-scoped).
- Теоретическая коллизия (каталог, названный ровно `w-<12 hex>`) попадает в legacy-ветку и разрешается общим правилом legacy (маппинг/конфликт) — тихого присвоения нет.
- **Promote** (`promote-memory.ts`): резолвит `WorktreeIdentity` текущей копии и переводит в `main` объекты ОБОИХ токенов владельца — WT-ID и однозначное legacy-имя (два семейства scope сосуществуют после обновления); неоднозначное legacy-имя — тот же честный конфликт в отчёте, объекты не переписываются.
- `conflictRegistry` — счётчик в результате call (`CallInjectionResult.scopeConflicts: string[]`), выводится в stderr-подсказку `wolf call` и в doctor; объекты при этом не переписываются и никому не присваиваются.
- Данные не мигрируют (NFR-02): legacy-записи остаются `worktree:<name>`; запись новой версии объекта штатными путями ставит уже WT-ID.

### 3.3 Операция лица: журнал и состояния (REQ-03 (R04))

События (append-only event log, `memory.face.op_*`):

```ts
op_started   { opId, command, owner_skill, plan: Step[], input } // input = полный набор аргументов
op_step      { opId, step: Step, detail }                        // detail: id созданных объектов
op_committed { opId }
op_aborted   { opId, by, reason }
type Step = 'add_face' | 'g17_record' | 'proposal_relation'
          | 'activate' | 'supersede_prev' | 'supersede_legacy' | 'announce'
```

Порядок шагов `createFaceVersion` (все под внешним `MemoryLock`, guard — до `op_started`):

```
1 add_face          — версия лица, status 'candidate' (номер версии назначается здесь)
2 g17_record        — G17-note + relation 'mutates' (только initiator steward)
3 proposal_relation — relation 'proposes' (если --from-proposal)
4 activate          — transition candidate → active   ← ТОЧКА COMMIT
5 supersede_prev    — supersede прежней активной версии (если была)
6 announce          — public-событие memory.face.versioned (+ breakglass)
7 op_committed
```

Состояния операции (требуемые требованиями, различимы из журнала+store):

| Состояние                                   | Условие                              | Видимость канона                                                                                                     |
| ------------------------------------------- | ------------------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| «не применено»                              | op_started есть, шага `activate` нет | прежняя версия active; candidate доставкой не выдаётся (фильтр `status === 'active'` в `activeFace` и show уже есть) |
| «применено, требуется восстановление следа» | `activate` есть, `op_committed` нет  | новая версия полная (face+G17+связи записаны до activation) и active; дозавершение — только след: supersede/announce |
| «завершено»                                 | op_committed                         | канон + полный след                                                                                                  |

- Ключевое свойство порядка: всё содержимое новой версии пишется ДО activation; после activation новая версия в любом состоянии — полный канон. Окно «два активных лица» (между 4 и 5) закрывается детерминизмом `activeFace` (старшая версия) и дозавершается resume'ом.
- **Resume/повтор**: вызов с тем же `opId` (`wolf face new --op-id <id>`, при отсутствии — генерируется `faceop-<ts>-<rand4>` и возвращается в результате) не создаёт вторую версию: reconcile(журнал, store) вычисляет фактическое состояние и исполняет только оставшиеся шаги; каждый шаг идемпотентен (перед записью проверяет фактическое состояние: `add_face` — у владельца уже есть candidate с этим `op_id` → переиспользуется, новая версия не создаётся; supersede уже-superseded — skip; activate уже-active — skip).
- **Привязка объект↔операция независимо от журнала**: face-объект несёт `op_id` в extra (записывается при создании вместе с объектом). Окно «объект сохранён, `op_step` не дописан» разрешается правилом усыновления: под lock, при незавершённой операции владельца, единственный candidate владельца с совпадающим `op_id` принадлежит операции; candidate с чужим/пустым `op_id` при незавершённой op — конфликт в отчёт (не усыновляется вслепую).
- **Abort** (`wolf face recover <opId> --abort`): только в состоянии «не применено» — candidate → archived, op_aborted. После activation — только вперёд (restore штатным путём); история не переписывается (NFR-02).
- **Doctor**: `op_started` без `op_committed`/`op_aborted` → issue «неполный след мутации» с opId и подсказкой recover; авто-healing doctor не делает (обнаружение — AC; исполнение — явная команда/повтор).
- **Авто-resume**: первый же вызов мутации того же owner_skill обнаруживает незавершённую операцию владельца и дозавершивает её под тем же lock до старта новой (детерминированно из input в op_started).
- **Индекс FTS**: производный; сбой его обновления не влияет на первичные данные (event log + объекты), лечится rebuild-index — вне операционного журнала.

### 3.4 Миграция и healing (REQ-04 (R05), OQ-01)

- `migrateFaces` переходит на операции: `createFaceVersion(command 'migrate', …, legacyHeadId)` — план шагов включает `supersede_legacy` (между supersede_prev и announce). Прерывание на любом шаге → известное состояние (§3.3) → повторный `wolf face migrate` дозавершивает.
- Skip-логика (:75) заменяется разбором:
  1. незавершённая операция 'migrate' владельца в журнале → resume;
  2. лицо существует, активный legacy howto-head отсутствует → честный idempotent-skip (отчёт);
  3. лицо существует + активный legacy head → детект докомпьютерного частичного перехода: `face.reason` матчит anchor `^migrated from playbook note <head.id> \((2\.17)\)$` — точный литерал фактического формата `migrate-faces.ts:95` — `` `migrated from playbook note ${head.id} (2.17)` `` (с суффиксом; усечённое сравнение запрещено) ⇒ связь доказуема → healing-операция (шаги supersede_legacy+announce; body не пишется). Тест-план обязан проверять детект на записи реального формата 2.17.0;
  4. неоднозначности (несколько активных head, reason не матчится ни один, несколько лиц владельца) → запись в `report.conflicts` + ненулевой exit; записи не изменяются.
- «Старый body не переносится поверх новой версии»: healing/resume никогда не пишут body — только переходы статусов и события.
- OQ-01 закрыт: операционный механизм REQ-03 — общий путь `createFaceVersion`, миграция покрывается естественно (условие возврата владельцу не сработало).

### 3.5 Claim владения (REQ-05 (R06), OQ-02)

```ts
// Файл: <root>/.wolf/shared/claims/<slug>.json  (root — общий, из resolveMemoryRoot)
interface ClaimRecord {
  artifact: string; // тип+идентификатор: "plan:docs/dev/<date>-<slug>/plan.md" | "worktree:<WT-ID>"
  // worktree идентифицируется тем же WT-ID, что и память (единый ID копии);
  // читаемость даёт поле cwd
  owner: string; // actor (WOLF_ACTOR-резолв, тот же механизм атрибуции)
  session_id: string | null;
  pid: number;
  cwd: string;
  acquired_at: string; // ISO
}
```

- **Захват**: `openSync(path, 'wx')` — атомарно на уровне ФС (прецедент FsMemoryLock tryAcquire). Файл занят и fresh → `ClaimHeldError` с полем owner (AC: второй писатель получает отказ с идентификатором владельца).
- **Stale**: PID мёртв (`process.kill(pid, 0)` → ESRCH) ИЛИ возраст > CLAIM_TTL (константа 24h, локальный-first: heartbeat не вводим). Stale → перехват: старый файл уходит в след `<slug>.<epochMs>.json` через атомарный hard-link + unlink (append-only след, NFR-02; наблюдаемое поведение эквивалентно переименованию), пишется новый.
- **Освобождение**: `wolf claim release` — только владелец (owner+session+pid совпадение) либо явная передача `--transfer-to <actor>` (AC: передача — явной процедурой).
- **Проверяемость**: `wolf claim list` читает реестр; запись владения — файл с who/when/what, не соглашение в брифе (AC-2).
- **Enforcement**: use-cases записи общих артефактов (TASK-бриф, план, отчёт, артефакты worktree) вызывают `requireClaim(artifact)` до записи; отказ = UserFacingError с именем владельца и путём claim-файла (AC-3: защита в use-case, не только CLI).
- **Ограничение (документируется)**: git-коммиты в worktree-ветку wolf не перехватывает — claim защищает записи через инструменты Wolf; прямой git — вне механизма (та же граница доверия, что у lock).
- OQ-02 закрыт: файловый реестр, не память Wolf (обоснование в ADR-5).

### 3.6 Шаблонное обновление live-лица (REQ-01 (R01), OQ-03)

```
для каждого шаблона base-set с owner_skill:
  active = activeFace(owner)
  нет лица, нет активного legacy howto   → посев как сегодня (command 'seed')
  нет лица, ЕСТЬ активный legacy howto с owner_skill
      (популяция 2.16.3)                 → ОДНА операция 'seed' с шагом supersede_legacy:
        add_face (body = ШАБЛОН, не legacy-body) + supersede_legacy(head)
        — механизм §3.3/§3.4 (тот же input.legacyHeadId, что у migrate);
        legacy-howto поглощается, дублей канона нет
  лицо есть, body совпадает              → skip (без записи)
  лицо есть, body разошёлся:
    active.initiator ∈ {'seed','migration'}
      → createFaceVersion(command 'seed', body = шаблон,
                         reason "template update: <файл> (2.17.1)")  // полный журнал §3.3
    иначе (initiator 'steward'/'owner'/'breakglass') → outcome {action: 'diverged'}
      — лицо не трогаем: мутации Стюарда старше шаблона (зона Стюарда, D4)
```

Таким образом все три популяции обновления покрыты одним путём re-init: 2.16.3 (legacy howto → seed+supersede_legacy), 2.17.0 (face с seed/migration-initiator → template update), steward-мутнувшие проекты (diverged-отчёт, без перезаписи). Отдельный ручной `wolf face migrate` остаётся для миграции вне re-init (переносит legacy body дословно — это его контракт).

- Точка входа — `wolf init` (свежая установка сеет; re-init `wolf init --yes` на живом проекте обновляет лица). Это штатный путь обновления для проектов 2.16.3/2.17.0 после `npm i -g mister-wolf@latest`: бинарный `wolf upgrade` память не трогает (проверено: memory-upgrade.ts — только npm), поэтому документируемая последовательность — «обнови пакет, затем re-init». `wolf sync` не меняется вовсе (AC-5 REQ-01: mutated-skip конфликты — как сейчас).
- Атрибуция обновления — initiator 'seed' (внутренний служебный путь T-05, guard не применяется) — разрешённый механизм; активная мутация Стюарда (`wolf face new`) идёт от `agent:steward` через env-атрибуцию — путь не меняется. Двойной generic supersede исключён контрактом `wolf face new` (supersede выполняет сама команда; шаблон методики её больше не дублирует — правка шаблона steward-nastavnik.md — план-фаза).
- Гарантия неизменности чужих рамок: обновление затрагивает ровно face с совпавшим owner_skill из шаблона; diff — одна новая версия лица + её G17-free след; никаких иных типов (проверяемо AC-3 REQ-01 по diff/логу).

## 4. ADR-карточки

### ADR-1: WT-ID = хеш realpath; legacy — маппинг при чтении

- **Контекст**: REQ-02 (R02) требует устойчивый единый ID (basename-коллизии — дефект memory-root.ts:31) и совместимость с записанными `worktree:<name>`.
- **Альтернативы**: (а) UUID-реестр копий в общем конфиге — состояние создаётся на read-пути, гонки регистрации, ещё один мигрируемый артефакт; (б) имя git-ветки — отпадает на detached HEAD и переиспользовании ветки; (в) оставить basename — сам дефект.
- **Решение**: детерминированный `worktree:w-<sha1(realpath)[:12]>`; legacy-токены резолвятся при чтении через `git worktree list --porcelain`; неоднозначное имя — fail-closed конфликт.
- **Последствия**: +0 состояния, +0 миграции данных; − зависимость от неизменности пути копии (переименование = новая копия); − один git-подпроцесс на процесс в linked-worktree при встрече legacy-токена.
- **Риск**: 12 hex (48 бит) — коллизии практически исключены в масштабе проекта. **Проверка допущения**: тест двух копий с одинаковым basename (AC-3 REQ-02).

### ADR-2: один предикат видимости во всех ветвях отбора

- **Контекст**: дефект (b) — keyword-уроки/правила и fallback идут из полного пула (get-call-injections.ts:112–129); точечные фильтры в каждой ветви уже один раз пропустили чужое (история дефекта a).
- **Альтернативы**: точечная починка каждой ветви по мере находок — воспроизводимый класс регрессий.
- **Решение**: `isVisible` (§3.2) — единственная точка знания о scope; каждая ветвь обязана пропускать кандидатов через неё до ранжирования; thread-ветка — тоже (блокеры).
- **Последствия**: состав видимых типов не расширяется; новая ветвь отбора = обязательный вызов isVisible (код-ревью контроль, тест-план фиксирует негативный сценарий на каждую ветвь).
- **Риск**: забытая будущая ветвь. **Проверка**: integration-тест «объект каждого типа из чужой копии не доходит ни одной ветвью» (REQ-06 (R08)).

### ADR-3: staging + подтверждённая активация; журнал — в event log

- **Контекст**: R04 — цепочка await без транзакции (create-face-version.ts:193–353); замена хранилища запрещена требованиями. Нужны состояния «не применено / применено, требуется след / завершено» и доставка, не выдающая неполный канон.
- **Альтернативы**: (а) forward-only журнал с ранней активацией и починкой следа — в окне сбоя доставкой выдаётся неполный канон (нарушение AC-3 REQ-03) либо требуется фильтрация доставки (сложнее); (б) транзакция БД — запрещено (смена хранилища); (в) staging+activation — канон переключается одной точкой commit.
- **Решение**: версия лица создаётся в status `candidate` (уже в глобальном enum; face-lifecycle расширяется на `['active','superseded','archived','candidate']`); всё содержимое (G17, связи) пишется до activation; activation (candidate→active) — точка commit; журнал шагов — события `memory.face.op_*` в существующем append-only JSONL event log.
- **Последствия**: доставка не меняется вовсе (фильтр `active` уже скрывает candidate; после activation канон полон); окно «два активных» закрывается детерминизмом activeFace + resume; цена — 5–8 событий журнала на мутацию (JSONL уже append-heavy — бюджет допустим).
- **Риск**: рассинхрон журнал↔файлы при внешней порче — reconcile детерминирован фактическим состоянием store, doctor сообщает. **Проверка допущения**: fault-injection после каждого шага (AC-1 REQ-03).

### ADR-4: миграция на общей операции + healing по доказуемой связи

- **Контекст**: R05 — сбой между созданием лица и supersede legacy-head (migrate-faces.ts:96–106) зависший навсегда из-за skip по наличию любого лица (:75). Условие включения REQ-04 (OQ-01): механизм REQ-03 должен покрывать миграцию естественно.
- **Альтернативы**: отдельный миграционный журнал — дублирование механизма и двух классов восстановления; ручная команда починки — не «дозавершение при повторном запуске».
- **Решение**: `supersede_legacy` — шаг той же операции 'migrate'; докомпьютерные частичные переходы лечатся healing-операцией при доказуемой связи (дословный формат reason :95); неоднозначности — конфликт в отчёте + exit ≠ 0.
- **Последствия**: OQ-01 закрыт без возврата владельцу; повторный migrate из «полумиграции» дозавершивает (AC-1 REQ-04); «успех» не объявляется по idempotent-skip частичного случая (AC-2). Детект — anchored-совпадение точного формата reason (§3.4), не усечённое.
- **Риск**: изменение формата reason в будущем сломает детект — формат reason зафиксирован контрактом (тест-план: тест на детект).

### ADR-5: claim — файловый реестр в общем .wolf, не память Wolf

- **Контекст**: OQ-02 — где живёт владелец. AC: атомарность, проверяемость, отказ второму, защита в use-case.
- **Альтернативы**: (а) claim как объект памяти — нужен новый тип/фасет (схема, english-surface, гейт), попадает в пул доставки (пришлось бы фильтровать), жизненный цикл через transition тяжеловесен; (б) только текстовые предупреждения — отвергнуто ревью R06 (инцидент 2.17.0).
- **Решение**: JSON-файлы в `<root>/.wolf/shared/claims/`, атомарный `wx`-create (механика FsMemoryLock), stale по PID-живости+TTL (для сессионных держателей pid 0 — только TTL), перехват с сохранением следа (hard-link + unlink — наблюдаемо эквивалентно переименованию), CLI `wolf claim acquire/release/list`, `requireClaim` в use-cases записи артефактов.
- **Последствия**: +0 к схеме памяти и доставке; cross-copy видимость бесплатно (общий .wolf); − прямые git-записи не защищаются (документированная граница).
- **Риск**: ручная порча/удаление claim-файла — реестр не криптографический; локальный-first уровень доверия тот же, что у lock. **Проверка**: два одновременных claim → ровно один успешен (AC-1 REQ-05).

### ADR-6: обновление live-лица — шаблонно-управляемый версионный путь, не sync

- **Контекст**: OQ-03. Инвариант REQ-01: `wolf sync` не меняет память (D4, mutated-skip — как сейчас); seемое лицо на свежей установке должно учить рабочей методике; у существующих проектов лицо живёт в памяти и продолжает учить старой (дефект R01).
- **Альтернативы**: (а) sync переписывает лицо — нарушает зафиксированный инвариант и зону Стюарда; (б) разовая миграция с перезаписью body — затирает мутации Стюарда, нарушает NFR-02 по смыслу; (в) ручная команда «переобнови лицо» — не «штатный путь», владелец проекта не должен помнить про это.
- **Решение**: посевной путь (`wolf init` / re-init) сравнивает шаблон base-set с активным лицом; дрейф при initiator seed/migration → новая версия лица через общий журналируемый механизм; steward-мутации не перезаписываются (diverged-отчёт).
- **Последствия**: одна правка шаблона в пакете + re-init = новая версия лица с полным следом; повторный init идемпотентен (body совпал → skip); `wolf sync` не изменяется.
- **Риск**: владелец не делает re-init — лицо остаётся старым (как сегодня, но теперь есть документированный штатный путь); ветка legacy-howto (2.16.3) покрывает популяцию, у которой лица ещё нет (проверка сценария обновления — все три популяции: 2.16.3, 2.17.0, steward-мутнувшие). **Проверка**: сценарий обновления 2.17.0 → 2.17.1 и 2.16.3 → 2.17.1 (AC-5 REQ-01, REQ-06 сценарий 1).
