# wave-2-20-0-upgrade-intentions — функциональные требования

Волна 2.20.0 «Upgrade UX: намерения владельца и тихий апгрейд». Тред:
mem_20261024_upgrade_ux_namereniya_vladeltsa_i_tikhiy_e6daf7. Решения владельца
(диалог 2026-10-24) зафиксированы в пунктах REQ ниже; их изменение — только через
возврат к владельцу.

## 1. Контекст и проблема

Волна 2.19.0 (unified-update, docs/dev/2026-10-23-unified-update/) сделала
одношаговый апгрейд CLI и парка проектов. Живой прогон `wolf upgrade` по парку из
5 проектов на 2.19.0 вскрыл UX-пробелы:

- парковый проход печатает счётчики без имён файлов — оператор не знает, где
  именно конфликт;
- для needs-decision нет глаголов разрешения — только ручное редактирование;
- нет легального механизма «этот файл мой, не трогай» — в одном из проектов парка
  автор вручную снимал штамп и писал комментарий-заклинание в файл;
- тихий прогон (CI, скрипты) невозможен без риска потери локальных правок.

Плюс четыре механических дефекта ложных сигналов: ложный mutated от
штамп-дрейфа; вечный «behind · 1 differ» от onboarding-блока AGENTS.md (блок
вставляется один раз и вечно пропускается); doctor советует `run wolf init` при
отсутствующем `mcp.wolf`, но init конфиг не восстанавливает; differ-файлы в
`--check` видны только счётчиком.

Метрика успеха: повторный проход по тому же парку на 2.20.0 даёт 0 ложных
needs-decision; каждый настоящий конфликт назван по имени и разрешим одной
командой `--resolve`; тихий прогон обратим (бэкап + восстановление).

## 2. Область

Входит: CLI `wolf upgrade` (`--check`, `--here`, `--resolve`, `--review`,
`--show`, `--yes`, `--json`), `wolf init` (восстановление `mcp.wolf`), новый
frontmatter-контракт `protect` для wolf-управляемых md-файлов (agents, skills,
commands), свидетель sync-state, коды сверки verify, onboarding-блок AGENTS.md,
бэкапы перед take, вывод паркового прохода и `--check`.

НЕ входит (не-цели):

- обновление живых лиц — зона Стюарда, решение L0 из unified-update, не
  пересматривается;
- авто-merge содержимого — только take/keep целиком;
- редизайн exit-модели 0/1/2;
- отдельный файл политики исключений — отвергнуто владельцем: намерения живут в
  самих файлах.

## 3. Глоссарий

- Парк — реестр проектов wolf; парковый проход — `wolf upgrade` по всем проектам
  реестра; одиночный проект — `--here`.
- Base-set / эталон — канонический рендер wolf-управляемых файлов (агенты,
  скиллы, команды, плагины, AGENTS.md) для установленной версии; текущая версия
  базы — `set` свежего рендера.
- Штамп — строка `wolf:rendered base=<имя> set=<X.Y.Z>` в файле; маркер
  принадлежности wolf.
- Свидетель — записанный при записи sha256-хэш контента файла в sync-state;
  расхождение хэша текущего контента со свидетелем — признак локальной правки
  (mutated).
- needs-decision — исходы mutated / diverged / conflict: проход не решает сам,
  требуется решение владельца.
- differ — штампованный файл, отличающийся от эталона без признака локальной
  правки (безопасно обновим).
- Безштампованный (foreign) — файл без штампа на месте wolf-цели: чужой,
  wx-политика не перезаписывает.
- protect — ключ в YAML-frontmatter wolf-управляемого md-файла:
  `protect: true` (держать локальный контент навсегда) или `protect: X.Y.Z`
  (держать, зафиксировав версию базы).
- take / keep / pin — глаголы разрешения: взять эталон / принять локальный
  контент / защитить с фиксацией текущей версии базы.
- Нормализация — вычисление контента файла без ключа protect; единая база
  сравнения с эталоном и свидетеля.
- Санкционированная локальная вариация — безштампованный файл с protect: не
  конфликт, не предупреждение.
- Дайджест — итоговая сводка прохода (summary); тихий режим — не-TTY прогон с
  `--yes`.

## 4. Функциональные требования

### REQ-01 — Имена файлов в выводе паркового прохода и --check

- История: Как оператор парка, я хочу видеть имена файлов с исходами
  needs-decision и differ, чтобы решать конфликт без ручного вскрытия проектов.
- Требование: Когда шаг проекта парковым проходом (stepDetailLines) или `--check`
  (freshnessDetails) печатает needs-decision (mutated/diverged/conflict) или
  differ, система должна называть путь каждого файла (относительно корня
  проекта), а не только счётчик.
- Обоснование: живой апгрейд 2.19.0 — счётчик «1 needs decision» без имени файла
  заставил вручную перетряхивать проекты парка.
- AC:
  - AC1: Given парк, где у одного проекта 1 mutated, When `wolf upgrade`, Then в
    деталях шага проекта назван путь файла.
  - AC2: Given проект с 2 differ, When `wolf upgrade --check`, Then в деталях
    проекта названы оба пути.
  - AC3: счётчики сохраняются (обратная совместимость вывода), имена —
    дополнением к ним.
- Приоритет: Must.
- Источник: диалог 2026-10-24 (живой кейс парка), решение A1.

### REQ-02 — Авто-исцеление штамп-дрейфа

- История: Как владелец парка, я хочу, чтобы составы файлов, идентичные эталону,
  не числились конфликтами из-за старого штампа, чтобы шум не маскировал
  настоящие проблемы.
- Требование: Когда контент штампованного файла байт-в-байт равен свежему
  эталону после исключения строки штампа (`base=`/`set=`), парковый проход и
  `--here` молча перезаписывают файл эталоном (штамп обновляется) и обновляют
  свидетель; исход относится к ok-семейству, НЕ needs-decision.
- Обоснование: составы файлов идентичны, штамп 2.17.0 против базы 2.19.0 давал
  ложный mutated.
- AC:
  - AC1: Given файл идентичен эталону кроме строки `set=`, When `wolf upgrade`,
    Then файл перезаписан эталоном, свидетель обновлён, исход не needs-decision.
  - AC2: повторный прогон после исцеления — exit 0, файл не меняется.
- Приоритет: Must.
- Источник: диалог 2026-10-24, решение A2.

### REQ-03 — Версионированный onboarding-маркер AGENTS.md

- История: Как владелец проекта, я хочу, чтобы wolf-часть AGENTS.md обновлялась
  при изменении шаблона, а мой собственный текст в файле сохранялся, чтобы
  инструкция агента не устаревала вечно.
- Требование: onboarding-блок ограничен парой маркеров (открывающий
  `<!-- wolf:onboarding vN -->`, закрывающий `<!-- /wolf:onboarding -->`). Когда
  версия формата N в файле меньше версии шаблона M, upgrade обновляет содержимое
  МЕЖДУ маркерами до нового рендера (маркеры нового шаблона); пользовательский
  контент вне блока — выше и ниже — сохраняется байт-в-байт. Сегодня блок
  вставляется один раз и вечно пропускается → вечный «behind · 1 differ» без пути
  лечения.
- Обоснование: единственный wolf-управляемый блок без механизма обновления
  порождает неустранимый ложный сигнал.
- AC:
  - AC1: Given AGENTS.md с onboarding-блоком и пользовательским контентом выше
    блока, When `wolf upgrade` при изменившемся шаблоне, Then блок между
    маркерами обновлён, контент выше блока сохранён байт-в-байт.
  - AC2: контент ниже блока также сохранён байт-в-байт.
  - AC3: Given AGENTS.md без блока и без штампа, When init/upgrade, Then блок
    вставляется append-веткой (как сегодня), чужой контент не трогается.
  - AC4: после обновления блока повторный прогон — exit 0, блок не меняется.
- Приоритет: Must.
- Источник: диалог 2026-10-24, решение A3.

### REQ-04 — init восстанавливает mcp.wolf в существующем opencode.json

- История: Как владелец проекта, я хочу, чтобы совет doctor «run wolf init»
  действительно чинил конфиг, чтобы сигнал имел лечение.
- Требование: Когда `wolf init` выполняется в проекте с существующим
  opencode.json без записи `mcp.wolf` (или с некорректной), init
  добавляет/восстанавливает канонический блок
  `{"type":"local","command":["wolf","mcp"],"enabled":true}`, не изменяя
  остальной конфиг; повторный init идемпотентен.
- Обоснование: doctor советует init, но init сегодня конфиг не чинит — совет
  невыполним.
- AC:
  - AC1: Given opencode.json без mcp.wolf, When `wolf init`, Then запись
    восстановлена, остальной JSON сохранён.
  - AC2: повторный `wolf init` не дублирует и не меняет запись.
  - AC3: после init doctor больше не рапортует «wolf entry missing» для этого
    проекта.
- Приоритет: Must.
- Источник: диалог 2026-10-24, решение A4.

### REQ-05 — Ключ protect в frontmatter: намерения in-file

- История: Как владелец проекта, я хочу пометить файл «этот мой, не трогай»
  прямо в файле, чтобы парковый проход уважал моё намерение без центральной
  политики и без вечного шума.
- Требование:
  - `protect: true` — держать локальный контент навсегда: молча, без
    предупреждений, исход не needs-decision;
  - `protect: X.Y.Z` — держать; `--check` печатает info-строку «защищённое
    отставание → base <текущая>» (info, не warning, exit не меняет);
  - ключ — сигнал вне контента: сравнение «эталон == файл» и хэш-свидетель
    всегда вычисляются по контенту БЕЗ ключа protect — нормализация в точках:
    сравнение при sync/inspect, запись свидетеля, проверка свидетеля (иначе
    защита сама порождает вечный mutated);
  - безштампованный (foreign) файл с protect — санкционированная локальная
    вариация: не трогаем, не конфликт, не предупреждение;
  - `--resolve <файл>=take` — единственный глагол сильнее protect: снимает
    ключ, берёт эталон;
  - `keep` на защищённом файле = unprotect: ключ снят, свидетель обновлён на
    локальный контент (заморозка кончается, файл остаётся локальным до
    следующего дрейфа).
- Обоснование: владелец подтвердил модель in-file без центрального файла
  политики; реальный кейс парка — ручное снятие штампа и комментарий-заклинание
  в файле.
- AC:
  - AC1: Given чистый парк (все проекты ok, часть файлов с protect), When
    `wolf upgrade`, Then все ok, exit 0, protect-файлы видны строкой «N protected
    (intentional)», exit не меняется.
  - AC2: Given файл с `protect: true` без штампа (раньше foreign), When
    `wolf upgrade --check`, Then проект current, файл защищён, предупреждений
    нет.
  - AC3: Given `protect: 2.19.0` при базе 2.21.0, When `wolf upgrade`, Then файл
    молча держится, exit 0; When `wolf upgrade --check`, Then напечатана
    info-строка защищённого отставания; When `wolf upgrade --resolve <файл>=take`,
    Then ключ снят, взят эталон 2.21.0.
  - AC4: `grep -rn 'protect:' .opencode/` находит все защиты без обращения к
    wolf — in-file является источником истины.
  - AC5: добавление, изменение или снятие protect-ключа не меняет свидетель и не
    создаёт mutated (нормализация во всех трёх точках).
- Приоритет: Must.
- Источник: решения владельца 2026-10-24 (B5).

### REQ-06 — Глаголы разрешения --resolve

- История: Как владелец парка, я хочу разрешать конфликты одной командой — по
  пути или по номеру из вывода, чтобы лечение не требовало ручного
  редактирования.
- Требование: `wolf upgrade --resolve <file|N>=take|keep|protect|pin` применяет
  решение к указанным файлам: по пути файла или по номеру строки из вывода
  не-TTY прогона. Семантика: take = эталон; keep = принять локальный (шум
  прекращается до следующего дрейфа); protect = keep + `protect: true`;
  pin = `protect: <текущая версия базы>`. Нумерация N детерминирована и
  стабильна между прогонами при неизменном состоянии.
- Обоснование: без глаголов needs-decision лечится только руками — источник
  ручных ошибок и «заклинаний».
- AC:
  - AC1: Given не-TTY прогон напечатал нумерованный список, When
    `wolf upgrade --resolve 3=protect`, Then решение применено к файлу строки 3.
  - AC2: разрешение по пути работает: `--resolve .opencode/agents/foo.md=take`.
  - AC3: неизвестный номер или путь — error с подсказкой, к другим файлам ничего
    не применено.
  - AC4: protect-глагол дописывает `protect: true` в frontmatter атомарно и
    обновляет свидетель по нормализованному контенту.
- Приоритет: Must.
- Источник: решения владельца 2026-10-24 (B6).

### REQ-07 — Интерактивный --review

- История: Как владелец парка, я хочу разбирать конфликты по одному с diff'ом
  перед глазами, чтобы решение было осознанным.
- Требование: TTY: `wolf upgrade --review` проводит интерактивный разбор каждого
  needs-decision: diff/сводка, выбор [t]ake / [k]eep / [p]rotect / [v]pin /
  [s]kip, плюс «применить ко всем похожим». Не-TTY: нумерованный список
  конфликтов + готовая команда `--resolve`, exit 2, без записей.
- Обоснование: массовый проход без разбора провоцирует слепое «взять всё»; без
  TTY интерактив невозможен — нужен готовый рецепт.
- AC:
  - AC1: Given необъявленная правка и TTY, When `--review` и выбран [p]rotect,
    Then `protect: true` дописан в frontmatter атомарно (tmp+rename), файл
    больше не числится needs-decision.
  - AC2: Given не-TTY и 2 needs-decision, When `--review`, Then напечатан
    нумерованный список с готовой командой `--resolve`, exit 2, файлы не
    изменены.
- Приоритет: Must.
- Источник: решения владельца 2026-10-24 (B7).

### REQ-08 — --show для защищённого или конфликтного файла

- История: Как владелец парка, я хочу перед решением увидеть, что именно я
  получу при снятии защиты, чтобы решение было информированным.
- Требование: `wolf upgrade --show <file|N>` печатает для защищённого или
  конфликтного файла: значение protect, версию базы, diff «что получишь при
  снятии» (локальный контент против эталона). Строго read-only.
- Обоснование: слепое снятие защиты равносильно потере правок; diff — минимальная
  цена осознанности.
- AC:
  - AC1: Given `protect: 2.19.0` при базе 2.21.0, When `--show <файл>`, Then
    напечатаны значение protect, обе версии и diff; файл не изменён.
  - AC2: `--show N` по номеру из не-TTY списка работает как `--show <файл>`.
- Приоритет: Must.
- Источник: решения владельца 2026-10-24 (B8).

### REQ-09 — Секция Protections в --check

- История: Как оператор парка, я хочу при каждом --check видеть полный реестр
  защит, чтобы понимать, какие файлы сознательно держатся локальными.
- Требование: `wolf upgrade --check` (парковый и `--here`) всегда печатает секцию
  Protections — полный реестр защит всех проектов: путь, значение, дрейф против
  базы — с подсказкой, как снять. Секция печатается при каждом прогоне, не
  только при изменениях. `--check` остаётся строго read-only и идемпотентным.
- Обоснование: защиты, невидимые в сводке, превращаются в забытые файлы;
  постоянная печать делает реестр самоочевидным.
- AC:
  - AC1: Given парк с protect-файлами в двух проектах, When `wolf upgrade
--check`, Then секция Protections перечисляет их все с значениями и дрейфом.
  - AC2: секция печатается и когда изменений нет (чистый парк).
  - AC3: `--check` не производит записей (см. NFR-03), повторный `--check` даёт
    тот же вывод.
- Приоритет: Must.
- Источник: решения владельца 2026-10-24 (B9).

### REQ-10 — Тихий режим --yes без TTY

- История: Как владелец парка, я хочу тихий прогон в CI без риска потерять
  локальные правки, чтобы автоматизация была безопасной.
- Требование: не-TTY + `--yes`: необъявленные mutated — взять эталон, локальную
  копию сохранить в `.wolf/backup/upgrade/<дата>/<файл>`; дайджест называет файлы
  и пути бэкапов; protect/pin держатся молча; exit 0. Bare `wolf upgrade` при
  TTY: текущее подтверждение списка + подсказка `--review` при needs-decision.
- Обоснование: сегодня тихий прогон либо невозможен, либо опасен; бэкап делает
  «взять эталон» обратимым.
- AC:
  - AC1: Given необъявленная правка и не-TTY, When `wolf upgrade --yes`, Then
    локальная копия в `.wolf/backup/upgrade/<дата>/`, взят эталон, дайджест
    называет файл и путь бэкапа, exit 0.
  - AC2: восстановление файла из бэкапа + `wolf upgrade --resolve <файл>=protect`
    работает (восстановленный файл заморожен).
  - AC3: protect/pin-файлы при `--yes` не тронуты и не бэкапируются (нечего
    терять — их не меняют).
- Приоритет: Must.
- Источник: решения владельца 2026-10-24 (B10).

### REQ-11 — Машиночитаемый --json

- История: Как владелец CI, я хочу стабильный JSON-вывод апгрейда, чтобы
  автоматика могла разбирать исходы без парсинга текста.
- Требование: `wolf upgrade --json` печатает машиночитаемый вывод: план, исходы
  по проектам с именами файлов, needs-decision с номерами строк (совместимость с
  `--resolve <N>`), реестр protections, пути бэкапов. Схема стабильна в рамках
  мажора; exit-модель 0/1/2 не меняется.
- Обоснование: текстовый вывод парсить хрупко; имена файлов и номера строк уже
  нужны людям — переиспользуем их для машин.
- AC:
  - AC1: `--json` выводится валидным JSON и распарсивается; содержит per-project
    исходы с именами файлов и protections.
  - AC2: номера строк needs-decision в JSON совпадают с нумерацией текстового
    не-TTY вывода.
  - AC3: exit-коды `--json` совпадают с текстовым режимом.
- Приоритет: Must.
- Источник: решения владельца 2026-10-24 (B11).

## 5. Нефункциональные требования (NFR)

### NFR-01 — Exit-модель сохраняется

- Требование: exit-модель 0/1/2 волны unified-update не пересматривается:
  0 — закрыто/отменено/read-only, 1 — error, 2 — есть needs-decision; `--check`
  всегда 0.
- AC: сценарии exit-таблицы unified-update проходят без изменения семантики;
  новые исходы (исцеление, protected) не производят exit 2.
- Источник: инварианты C, unified-update design §«Exit-модель».

### NFR-02 — Идемпотентность апгрейда

- Требование: повторный прогон `wolf upgrade` стабилен: exit 0, без новых
  изменений файлов (NFR-02 волны unified-update сохраняется).
- AC: Given прогон завершился лечением/защитой, When повторный прогон, Then
  exit 0 и ни один файл не изменён.
- Источник: инварианты C.

### NFR-03 — --check строго read-only

- Требование: `--check` (парковый и `--here`) не производит никаких записей:
  ни файлов проекта, ни sync-state, ни бэкапов.
- AC: снапшот mtime/хэшей наблюдаемых файлов до и после `--check` идентичен.
- Источник: инварианты C, prior art unified-update.

### NFR-04 — Атомарность записей

- Требование: все записи волны (файлы base-set, frontmatter-правки protect,
  onboarding-блок, sync-state, бэкапы) выполняются tmp+rename по прецеденту
  writeFileAtomic.
- AC: ни один новый путь записи не использует прямую перезапись без атомарного
  ренейма (ревью + тесты).
- Источник: инварианты C.

### NFR-05 — Никакой потери данных без бэкапа

- Требование: любая перезапись локального (отличного от эталона) контекста
  сопровождается бэкапом; тихий режим и глагол take — только через бэкап.
- AC: сценарий REQ-10 AC1/AC2 (бэкап + восстановление) проходит.
- Источник: инварианты C.

### NFR-06 — Детерминированность не-TTY вывода

- Требование: порядок и нумерация строк не-TTY вывода стабильны при неизменном
  состоянии проекта (база для `--resolve <N>` и `--json`).
- AC: два подряд не-TTY прогона без изменений состояния дают идентичный вывод и
  нумерацию.
- Источник: REQ-06/REQ-11.

## 6. Ограничения и допущения

- Допущение (проверить в design-фазе): opencode игнорирует неизвестный ключ
  frontmatter `protect` у agents/skills/commands; подтверждение — spike R-01 в
  design.md.
- Номера версий всегда полные X.Y.Z — в планах, тредах, волнах, тегах.
- Центральный файл политики исключений отвергнут владельцем; источник истины —
  сами файлы (`grep -rn 'protect:' .opencode/`).
- Старые wolf (<2.20.0) не нормализуют protect: файл с ключом для старой версии
  выглядит обычным mutated. Обратной совместимости интерпретации ключа нет;
  парк обязан апгрейднуться до 2.20.0.
- Живые лица — зона Стюарда (решение L0 из unified-update), этой волной не
  пересматривается.
- Внутренняя документация волны — на русском (правило проекта: EN-витрина,
  RU-внутрянка).
