## 3. Подразделы по REQ с неоднозначностью/риском

### 3.1 REQ-02 / REQ-03 / REQ-05 / REQ-06 — «язык» не существует; лицо — не замена

Четыре требования пакета (единый словарь, версии+active, кандидат/испытание/политика/откат, пины+delta) описывают **предмет «язык проекта»**. В 2.21.0 такого предмета нет: нет core-типа, нет хранилища, нет команды `language`, нет MCP-инструмента. Подтверждения отсутствия: grep по `src/` (`vocabulary|glossary|task-state` → 0; `словар`/`language` — 45 совпадений, все несвязанные: словарь **фасетов** note и **язык программирования** в сканере), реестр из 50 команд в `src/adapters/cli/cli-entry.ts:52-395`, MCP-набор из 7 инструментов в `src/adapters/mcp/mcp-tools.ts:30`.

Единственный близкий контур — **лицо** (`face`): версионируемый playbook агента со Стюардом-мутатором, G17, supersede-цепочкой, `candidate`-статусом, откатом и доставкой в плагин. Он реализует **структурные аналоги** REQ-03/04/05/07 для своего носителя — но по назначению это «эволюция лиц агентов», а не «общий словарь проекта». Признаки, по которым их нельзя считать реализацией: носитель — конкретный агент (`owner_skill`), а не проект; версионируется **body лица**, а не запись словаря; нет команд `show/propose/validate/activate/rollback` над словарём; нет отдельного writer'а словаря и нет связи жалоба→словарь. Вывод для планировщика: либо языковой контур проектируется заново (T03 в терминах пакета), либо REQ-02/03/05/06 переформулируются в терминах лиц — но это уже изменение требований, и оно требует решения владельца, а не трактовки на этапе 1.

Отдельно: **G17 ≠ «семь оснований изменения»**. Совпадает только число (7 обязательных полей в `create-face-version.ts:79-99`). Набор «оснований» в REQ-05 — семь оснований для _изменения языка_, в пакете они не перечислены (в читаемых диапазонах RELEASE-TASK.md их нет), поэтому сверить соответствие невозможно — фиксирую как gap, а не как несовпадение.

### 3.2 REQ-09 — «единое task-state»: почему это «не реализовано», а не «частично»

Три фрагмента (`thread` с `goal/current_state/next_steps`, чекпоинты, diff треда) не образуют единого состояния: чекпоинт хранит только `thread_current_state` и список связанных id (`src/domain/schemas/session-checkpoint-schema.ts:9-14`), а чеклист/AC/scope/unknowns/evidence/бюджет живут в markdown-документах (`scaffold-artifact.ts:172-179`) и в текстовых брифах. Именно это «несколько истин», которое REQ-09 запрещает. При этом в продукте **есть** механизм single-writer на артефактах, который пакет хочет переиспользовать под состояние задачи: `src/app/use-cases/claim-artifact.ts:47-70` (claim → `requireClaim` перед записью → heartbeat → transfer), реестр в общем root (`:52-54`). Плюс CAS/lock в контейнере памяти (`src/app/use-cases/create-face-version.ts:56`, `face-operation.ts:622`). То есть строительные блоки есть, отсутствует именно **единая схема состояния задачи** и её поверхности (команда `task-state show/put/check` из §5 пакета, строки 97).

### 3.3 REQ-04 — сильная сторона 2.21.0, но не по предмету пакета

Здесь продукт заметно сильнее пакета: гвард актора в use-case, а не в CLI (`create-face-version.ts:117-132`), атрибуция только из env (`:59-62`), обязательная причина (`:160-163`), запрет generic-путей для face на уровне use-case (`tests/unit/use-cases/face-generic-guards.test.ts`), whitelist `wolf update` (`memory-update.ts:15-16`), правило создаётся только пользователем (`add-memory-object.ts:96-100`), попытки-отказы журналируются (`create-face-version.ts:134-139`). Для «языка» эта защита не переносится автоматически: пока нет типа языка, нет и его guard'а; `wolf add --type language` не появится, но и словаря не будет. Пункт «служебный seed/owner recovery аудируемы» закрыт наполовину: `initiator` ∈ {steward, owner, breakglass, migration, seed} (`memory-types.ts:243`) и breakglass ведёт отдельный журнал (`face.ts:166`), но seed/migration идут тем же `createFaceVersion` путём без отдельного «служебного» класса записи.

### 3.4 REQ-05 — самая большая функциональная дыра

Требование требует **испытания** до активации и **политики для breaking**. В продукте нет ни объекта «испытание», ни статуса, ни команды, ни поля. Более того, `face new` **автоактивирует** новую версию в той же операции (`face-operation.ts:279`: план `add_face → activate → supersede_prev`), а единственный «тормоз» — обязательный G17 и опциональный `recover --abort` до активации (`face.ts:173-186`). Слово `breaking` в коде отсутствует полностью, поэтому «breaking не автоактивируется» сегодня не может быть выполнено ни при каком входе. Если пакет требует этого от языка — нужен новый контур; если переносить на лицо — это изменение существующего контракта лица (2.17.x), и его надо вынести в отдельное требование, а не считать закрытым по аналогии.

### 3.5 REQ-08 — расхождение контракта: «не требуется готовый fix»

Пакет: жалоба сохраняет исходное сообщение, версию, понимание/неизвестное и последствия; готовый fix **не требуется**. Продукт: `--proposal` объявлен `requiredOption` (`memory-complain.ts:47`), а в контракте типа `complaint` `proposal` — обязательное поле (`memory-types.ts:174-178`). Это прямое расхождение, а не пробел реализации. Пробел реализации — в другом: в объекте жалобы нет полей «версия артефакта», «последствия», «понимание/неизвестное»; `body` = только evidence (`memory-complain.ts:77`). Связи «жалоба → версия лица» нет: `face new --from-proposal` ссылается на **предложение** (`face.ts:104`), а предложение — отдельный note-фасет `proposal` со свободным `basis` (`save-proposal.ts:33-44`), в который жалоба попадает только текстом.

### 3.6 REQ-12 — «режим standard/draft»: не путать с FULL/LITE/FIX и с bootstrap-черновиками

В продукте есть две похожие, но не те вещи: (а) профили документов FULL/LITE/FIX (`using-skills/SKILL.md:56`) — выбирает L1, меняет набор артефактов; (б) «черновики» (`bootstrap-project.ts:38-40`, статус `proposed` в `memory-types.ts:122-124`) — состояние записи памяти. Ни то, ни другое — не режим ответа/плотности. Требование «выбор L1/пользователем, независимость от FULL/LITE/FIX; неопределённость расширяет анализ» не имеет в продукте ни точки выбора, ни правила расширения. Ближайший детерминированный механизм — `routeReviewDepth` (`src/domain/review-depth.ts:49-60`): эвристика «blast radius / безопасность / объём → flat или review-council», решение остаётся за человеком. Это кандидат на переиспользование (детерминированная таблица признаков, без LLM), но он про глубину ревью, а не про режим ответа.

### 3.7 REQ-01 — разделение существует как текст, а не как механизм

Условие I1 (строка 30 пакета) в продукте отражено в `wolf-explain` (адресат по умолчанию — владелец, терминология, «машинные отчёты RESULT/EVIDENCE/ACCEPTANCE сохраняй без переименования полей; пользовательское изложение — отдельный текст», `wolf-explain/SKILL.md:16-18`) и в артефактном контуре (`scaffold-artifact.ts:172-179` — четыре человеческих документа; `lint-artifacts.ts:37` — линт docs/dev, tolerant, «находит, но не блокирует», `:36`). Чего нет: автоматической проверки компактности внутреннего RESULT и проверки понятности человеческого текста «без словаря»; нет механизма, порождающего человеческое объяснение из состояния (сейчас его пишет модель по скиллу). Для AC-05 пакета («проверены чат, requirements, README, руководство…») продукт даёт только текстовое предписание, но не проверку.

## 5. Риски и допущения

- **R-1 (риск интерпретации): коллизия нумерации REQ.** В комментариях кода 2.17.x/2.18.x `REQ-01..REQ-08` — это **другая** волна (лица/советы), напр. «Волна 2.17 REQ-01» в `src/app/use-cases/add-memory-object.ts:102`, «2.17.1 REQ-03» в `face.ts:168`. Все ссылки в этом отчёте на REQ-01..REQ-13 — **требования пакета**; при споре сверять текст, а не номер.
- **R-2 (риск подмены): «лицо» ≠ «язык», «рамка» ≠ «лицо».** Оба контура версионируемые и оба Стюард-мутируемые — их легко принять за реализацию REQ-02/03/05/06. Носители разные (лицо — агент, язык — проект), и пакет явно требует «канон языка в памяти проекта» (условие I5, строка 38), а не в памяти агента.
- **R-3 (риск счёта): `templates/base/*` (канон) ≠ `.opencode/*` (установленная копия репозитория).** Оба набора присутствуют; dogfood-копии могут отставать от канона. В этом отчёте цитаты канона — `templates/base/...`; установленные копии `.opencode/...` использовались только для проверки наличия, не как источник истины. Проверка «канон == установленная копия» — задача `wolf upgrade --review`, здесь не выполнялась.
- **R-4 (риск полноты): «семь оснований изменения» (REQ-05) не перечислены в читаемых диапазонах пакета.** Соответствие G17 не подтверждено и не опровергнуто — только зафиксировано, что это разные сущности.
- **R-5 (риск вывода «реализовано» по одному упоминанию):** для REQ-01/10/11/13 основной носитель — текстовые предписания в `templates/base/skills/*.md` и `templates/base/agents/*.md`. По методике этапа 1 такие ссылки годятся как evidence «требование предписано текстом», но **не** как «механизм реализован» — поэтому REQ-01/10/11/13 отмечены «частично» с явной пометкой, где именно нет кода.
- **R-6 (допущение): «не реализовано» означает «нет работающего механизма в 2.21.0», а не «нет следов замысла».** Ветки `playground/`, `playground-lab/`, `docs/` не учитывались как продуктовый код (использовались только как подсказки при поиске).
- **R-7 (допущение по базе):** инвентаризация сделана против 2.21.0 / 5926e41; любой вывод про «2.20.0» как реализацию пакета исключён по условию задачи.
- **R-8 (риск объёма):** `npm run check` / `e2e` / `docs:build` не запускались (запрещено границей задачи) — все утверждения о работоспособности основаны на чтении кода и наличии тестов, а не на прогоне.
