1. **Рантайм opencode.** Аудит §5 проба `g` (`docs/dev/2026-10-25-opencode-v2-config-audit/audit.md:162`): «`init,review,alpha,beta` — файлы из **обоих** каталогов» → «оба работают, WARN нет». 2. **Скан orphaned.** `opencode-renderer.ts:290-295` сканирует только 4 корня. Если поменять `LAYOUT` и забыть корни — старые файлы не попадут в `orphaned` → не будут удалены и не будут доложены (молчаливый дубль в рантайме). Если добавить старый корень — старые файлы попадут в `orphaned`, но они **не объявлены** в карте как `removed` → `project-step.ts:156-162` формирует `drift` → `orphanOutcome` (`project-step.ts:237-242`) даёт `action: 'conflict'` → `verify` даёт error → `exitKind: 'error'` (`project-step.ts:187-188`). Удаление цели по карте идёт через `project-step.ts:127-155` и **требует подтверждения** (`opts.confirmedRemovals`, `project-step.ts:128-134`) — то есть `wolf upgrade --resolve`.
4. **Uninstall / repair.** `uninstall.ts:15` и `repair-platform.ts:58` перечисляют свои корни отдельно от `LAYOUT` — их надо менять синхронно, иначе `wolf uninstall` перестанет видеть старые файлы как свои.

**1.7. «Защиты от дублей sync-state» в коде НЕТ.** Ни дедупликации, ни детекции «одна и та же команда по старому и новому пути» не существует: единственные операции над `state.files` — чтение (`loadSyncState` → `normalizeFiles`, `sync-state.ts:65-72`) и запись (`record`). Ближайший существующий механизм — категория `removed` в карте, но она удаляет **по пути**, а не по содержимому, и требует ручного подтверждения. Это и есть тот кусок, которого требует решение владельца: **нужна новая логика переноса/удаления старого ключа и явная политика судьбы старых файлов**.

### Что это значит для 2.22.0

- Миграция — не «смена одной строки». Затрагивает 9 продуктовых точек пути + ~20 тестовых ассертов + 7 мест в `docs/site` + dogfood-состояние репозитория (файлы + ключи sync-state).
- «Канонический каталог выбирается один раз» (решение владельца) означает: `LAYOUT.commands` и `OPENCODE_MANIFEST.layout.commands` должны указывать на ОДНО и то же место; сейчас это два независимых литерала, которые надо менять синхронно (или свести к одному источнику — продуктовый выбор design-этапа).
- Решение владельца требует «защиту от дублей sync-state». Фактически сегодня защиты нет, и базовая гигиена (прунинг) тоже нет. Это надо проектировать, а не «починить по ходу».
- Каталог `templates/base/commands/` (source) остаётся во множественном числе; в проекте цель станет `.opencode/commands/`. Терминология «команды» в коде (`command` kind) не меняется.
- Состав команд в 2.22.0 меняется 3 → 5 (пакет: `analyze-doc`, `complain`, `doc-review`, `language-review`, `task-status` — `.external_experts_review/2026-10-25-chatgpt-skills-review/WOLF-2.20.0-COMPLETE.md:947, 960, 975, 990, 1005`). Значит каталог наполняется заново, и вопрос «куда деть старые 3 файла в чужих проектах» стоит тем острее.

### Что это значит для 2.22.0

- `.wolf/SKILL.md` — **легаси-файл с расхождениями двух порядков**: (а) команды, удалённые в 2.13 (`blocker`/`info-request`/`article`/`thread create`/`council`) — пользователь, идущий по нему, получает ошибку-подсказку; (б) живой, но не описанный контур (`face`, `complain`, `claim`) и неверный стартовый ритуал (recap-first вместо call+brief).
- Он **не инжектится и не управляется**: правка волком невозможна, только ручная; при этом он лежит в репозитории и читается человеком/агентом, ищущим «ритуалы работы с памятью». То есть это прямой источник устаревших инструкций — ровно то, что §7 пакета называет «старые противоречия» (T09: «10 aliases, обновлённый .wolf/SKILL, installed regeneration, отсутствие старых противоречий»).
- В связке с п. 2 это второй «устаревший лицо-источник»: скилл analyze-doc говорит «мутируй сам», `.wolf/SKILL.md` не говорит «мутировать нельзя, это зона Стюарда».

### Что потребуется (описание, не реализация)

Два возможных контура — выбор за владельцем/диспетчером:

- **Контур A — переписать `.wolf/SKILL.md` под действующий протокол** (объём: §1 под `wolf call` + `wolf brief`; §2-таблица под живые 7 типов и живые команды; §3 со ссылкой на технический guard `add-memory-object.ts:96`; §4 заменить на note/фасеты; §5 пересчитать предикаты (28); §6 убрать ручной recap-шаг; §7 council → read-only history; добавить разделы про `face`/`complain`/`claim`). Плюс: файл перестаёт учить удалённым командам.
- **Контур B — объявить файл легаси и удалить** (он не инжектится, не управляется, не в карте; действующий протокол живёт в `AGENTS.md` + `templates/base/AGENTS.md` + плагине). Дёшево и убирает противоречие целиком. Минус: теряется «человекочитаемая дверь» к памяти для тех, кто ищет «SKILL.md»; решение — за владельцем (в пакете T09 прямо стоит «обновлённый .wolf/SKILL», т.е. пакет предполагает перезапись, а не удаление).

В любом из контуров:

1. Правки только в `.wolf/SKILL.md` (вне base-set) — продуктовый код не трогается; `wolf sync`/`upgrade` файл не увидит.
2. Если выбран Контур A — синхронизировать формулировки с `AGENTS.md` (единственный источник протокола) и с `templates/base/AGENTS.md` (его шаблонной копией), чтобы не завести второе расхождение.
3. Добавить в файл (или рядом) правило «мутация лица/плейбука — зона Стюарда» — то, чего сейчас нет ни в одном «ритуале» репозитория, кроме контура Стюарда.

### Неопределённости

- Не проверено, читают ли `.wolf/SKILL.md` агенты/люди в реальности (файл не инжектится, не в карте, нет ссылок на него в `docs/` или `src/` — поиск ссылок по репозиторию не дал результатов). Если его никто не читает — Контур B (удалить) дешевле и безопаснее.
- Точный список «живых» MCP-тулов для п. 3 вышел из `MCP_TOOL_NAMES` (`mcp-tools.ts:30`); проверено ли фактическое их наличие в MCP-сервере (`mcp-server.ts`) — нет.
- §7 пакета предполагает «10 aliases» (T09) — конкретный их состав в этом обследовании не сверялся; в `.wolf/SKILL.md` видны 4 устаревшие команды-ссылки (blocker, info-request, article, thread create) + council.
