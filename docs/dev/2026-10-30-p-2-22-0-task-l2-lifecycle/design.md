# 2.22.0 — срез P: компактный TASK и жизненный цикл L2 — дизайн

Вход: `requirements.md` этого пакета (draft, REQ-P01-1…REQ-P03b-2, NFR-P1…NFR-P7).
Baseline: 2.21.2, `5ec4e4f26e2eba6afa3562aa9db3f79c76a3c5cc`. Единственный источник
контрактов — этот документ; `plan.md` ссылается сюда и не дублирует.

## Глоссарий

Технические термины, вводимые до использования. Термины бизнес-уровня — в
`requirements.md` §3.

- **Канонический источник** — файл в `templates/base/**`, который после рендера попадает
  в `.opencode/**` с отпечатком `<!-- wolf:rendered base=<файл> set=<версия> -->`.
- **Отпечаток набора (set)** — версия базового набора в штампе файла; вычисляется как
  `setVersion` рендерера (`src/adapters/render/opencode/opencode-renderer.ts:109-111`),
  по умолчанию — версия пакета Wolf.
- **Дрейф штампа** — расхождение `set` в файле с текущей версией набора; лечится
  `wolf sync` (`opencode-renderer.ts:170-178`, `:246-252`).
- **protect** — запись в YAML-frontmatter (`true` или `X.Y.Z`), удерживающая файл от
  перезаписи при sync/upgrade; разбирается `parseProtect`
  (`src/domain/protect-key.ts`, используется `opencode-renderer.ts:20`).
- **Sync-state** — реестр «наши байты» (`src/adapters/render/sync-state.ts`), по которому
  рендерер отличает свой файл от локально изменённого.
- **Усечённое тело L2** — тело инъекции plugin'а для `worker-*`: без диспетчерского
  контура using-skills (`templates/opencode/plugins/wolf-session-start.js:77-83`).
- **Профиль TASK** — применимый набор полей поверх ядра (см. §Контракты).

## Контракты

### C1 — Ядро TASK (P-01)

Единый список из восьми элементов; профиль добавляет только применимое.

```text
TASK core (применимо к любой задаче)
  task_id        — идентификатор задачи, не сеанса
  цель           — ожидаемый результат одной строкой
  AC             — проверяемые критерии приёмки
  scope          — что входит/не входит; полномочия исполнителя
  входы          — необходимые источники + назначенная методика
  проверка       — как подтверждается результат
  бюджет+stop    — конечный лимит и условие возврата L1
  ожидаемый RESULT — форма отчёта и роль-специфичный вердикт
```

Профили (добавляют, не заменяют):

| Профиль     | Добавляет                                                                                                         | Не требует                             |
| ----------- | ----------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| `implement` | repo/workspace, `base_sha`, allowlist записи, разрешённые области чтения, зависимости, ссылки на design/test-plan | —                                      |
| `review`    | revision проверяемого артефакта, назначенная линза, норма и evidence-набор                                        | `base_sha`, allowlist записи, worktree |
| `research`  | проверяемый вопрос, критерий ответа, revision документа/источника, границы поиска и условие остановки             | `base_sha`, allowlist записи           |

Инварианты:

- Неприменимое поле **опускается**, а не заполняется заглушкой; неизвестный
  обязательный вход явно запрашивается (`NEEDS_CONTEXT`), не выдумывается.
- Роль-специфичный RESULT сохраняется: `implement` — `DONE|DONE_WITH_CONCERNS|
NEEDS_CONTEXT|BLOCKED`; `review` — `APPROVED|CHANGES_REQUIRED|INCONCLUSIVE`.
- Профиль не расширяет полномочия и не отменяет ACCEPTANCE принимающего уровня.

### C2 — Статический словарь (P-01)

Шесть терминов: TASK, RESULT, EVIDENCE, ACCEPTANCE, SCOPE, LIMITS/GAPS. Форма —
статический список определений рядом с ядром. Инвариант: определения не описывают
непоставленный механизм (нет «словарь обновляется сам», нет ссылки на несуществующую
команду). Граница: REQ-02 и живой язык этапа I не затрагиваются.

### C3 — Правило выбора сеанса (P-04)

```text
после решения делегировать:
  fresh    — новый самостоятельный принимаемый результат → новый L2 + отобранный TASK
  continue — тот же НЕ принятый результат → прежний L2 (уточнение | следующий
             связанный этап | evidence | ограниченное исправление по приёмке)
  replace  — та же задача, прежнее исполнение не подходит → новый L2 через handoff
```

Инварианты:

1. `task_id` ≠ id сеанса инструмента; совпадение имён параметров не делает их равными.
2. `continue` не расширяет scope: новые самостоятельные требования не добавляются под
   видом repair; несвязанная задача не дробится после каждого шага.
3. `DONE` не закрывает задачу; после ACCEPTED прежний L2 не становится свободным слотом.
4. Правило не создаёт обязательного исследователя/агента на файл; малая связанная работа
   остаётся у L1, независимая приёмка — у другого уполномоченного участника.
5. Первичное независимое review — свежий reviewer без истории родителя, чужих findings и
   ожидаемого verdict; повторная проверка своих замечаний тем же reviewer допустима.
6. При замене model/variant: resume не доказывает смену модели; неподдержанная смена →
   новый исполнитель.
7. Новый id сеанса **не** доказывает чистую изоляцию: если host наследует историю
   родителя, независимость не закрыта — результат остаётся `INCONCLUSIVE` либо
   ограниченным. Честный отчёт о возможностях host не приравнивается к успешной
   независимой приёмке.
8. Незавершённая приёмка не обнуляется при замене: известный результат и открытые
   замечания передаются через handoff. Фактический учёт расходов — A1.1/E2; при
   отсутствии связей результат помечается «неизвестно с покрытием», не нулём.

### C4 — Порядок replace (P-04)

```text
1 stop-writing   прекратить новые изменения; подтвердить завершение пишущих инструментов
2 preserve       уполномоченный владелец/L1 сохраняет результат + handoff (+ публикация)
3 hand-over      получатель проверяет доступность результата, принимает ownership
4 close          прежняя сессия закрывается после сохранения нужного контекста
```

Инварианты: `1` и `4` — разные действия; таймаут не доказывает остановку; при
неопределённости передача той же ветки не завершена; read-only review не требует нового
worktree; L2 без права коммита — checkpoint делает L1 после прекращения записи;
незавершённая приёмка и известный результат сохраняются и не обнуляются при замене
(фактический учёт расходов — A1.1/E2, см. C3 п.8).

### C5 — Усечённое тело L2 (доставка)

`WORKER_BODY` остаётся без диспетчерского контура. Срез добавляет в него **ссылку на
канон ядра** и требование отчёта по профилю, но не копию ядра: копия нарушает NFR-P1 и
создаёт второй источник. Конкретное изменение — в `plan.md`, контракт здесь: тело L2
содержит (а) «работаешь ровно одну подзадачу», (б) указание, что методика и ядро TASK
доставлены в поручении, (в) требование `RESULT/EVIDENCE` с `task_id`.

### C6 — Доставка и проверка фактической загрузки (P-03b)

| Шаг                          | Механизм                              | Доказательство                                                               |
| ---------------------------- | ------------------------------------- | ---------------------------------------------------------------------------- |
| Рендер canonical → installed | `wolf sync`                           | отчёт sync: `updated`/`skipped` по файлам                                    |
| Отпечаток набора             | `set=<версия>` в штампе               | grep штампа в `.opencode/**` = версия выпуска                                |
| Защита локального            | `protect:`                            | файл в отчёте как `protected`, не перезаписан                                |
| Идемпотентность              | повторный sync                        | второй прогон → дифф пуст                                                    |
| Фактическая загрузка         | инъекция/чтение установленного скилла | содержимое загруженного файла содержит новое правило (не «bytes изменились») |
| Откат                        | update map / backup                   | доступна прежняя версия инструкций                                           |

Ключевое разделение: «файл изменился» ≠ «версия загружена». Проверка загрузки —
чтение установленного `SKILL.md` из целевого пути (как это делает
`governanceBody()` в `wolf-session-start.js:47-63`), и/или сравнение содержимого
доставленного тела с ожидаемым.

**Состояние на baseline среза:** в `docs/dev/2026-10-26-wave-2-22-0-expert-package/requirements.md`
уже создан блок-указатель в шапке и §2.4 «Границы ближайшего среза P» с таблицами «Входит

документов.

**Дельта, которая остаётся:** §2.4 ссылается на матрицу §14 roadmap, но не воспроизводит
её построчно. Разрешённая форма — **строка-ссылка** на roadmap §14 (плюс при необходимости
одна строка статуса «применимость AC — roadmap §14»). **Запрещено:** создавать второй
блок-указатель, дублирующий §2.4, или переписывать таблицы §2.4/§2.1–2.3.

Инварианты: ни одна исходная формулировка REQ/AC не меняется (проверяется диффом: ноль
удалённых строк вне §2.4); `status:` остаётся `draft`; историческое evidence обзора
сохраняется.

**Допустимая дельта — пустая.** Если §2.4 уже даёт указатель на очередь и границы среза,
отсутствие строки-ссылки на §14 не является невыполнением P-03a: результат фиксируется
отчётом P-03a (evidence: существующий §2.4 + отсутствие удалённых строк), файл повторно
не правится. Править файл ради формальной строки-ссылки не требуется.

## ADR-карточки

### ADR-1 — Ядро TASK и правило сеанса — в разных канонах

- **Контекст:** ядро TASK используют все роли (L1 и L2); правило выбора сеанса —
  исключительно полномочие L1. Один файл для обоих означал бы, что L2 получает
  диспетчерское правило.
- **Решение:** ядро TASK + профили + словарь — в `using-skills`; правило
  fresh/continue/replace — в `executor-lead`.
- **Последствия:** `wolf-plan:23` требует переписи (был вторым источником); NFR-P1
  проверяется на явном списке целей — `wolf-plan:23`, `wolf-review:17-19`; а
  `using-git-worktrees:27` / `requesting-code-review:21,27-30` — исключения с владельцем
  B0, не «зелёный grep» по всему дереву. Зависимые методики ссылаются на два разных
  адреса — это осознанная цена.
- **Проверка:** grep по шаблонам не находит 4+ элементов ядра подряд (в одном
  перечислении/предложении) ни в одном файле, кроме `using-skills`; перечень целей и
  исключений зафиксирован строкой NFR-P1 в requirements и строкой «Зависимые методики»
  в таблице компонентов.

### ADR-2 — Профиль опускает неприменимое, а не обнуляет

- **Контекст:** текущий текст `using-skills:204` перечисляет `base_sha`, `cwd/worktree`,
  `allowlist` в одном ряду с общими полями.
- **Решение:** неприменимое поле опускается; обязательный неизвестный вход →
  `NEEDS_CONTEXT`.
- **Последствия:** поручение ревью перестаёт требовать Git-полей; риск — L1 может
  «забыть» поле, которое применимо. Смягчение: профиль `implement` перечисляет свои поля
  явно, проверка на наличие — в test-plan.
- **Проверка:** три формы в test-plan дают различимый состав полей.

### ADR-3 — Правило сеанса без нового публичного поля

- **Контекст:** соблазн ввести `session_mode` в TASK/схему.
- **Решение:** правило остаётся инструкционным; для нетривиального continue/replace
  достаточно краткого основания в существующем поручении.
- **Последствия:** нет миграции схем (NFR-P2), нет нового парсера; фактическая семантика
  host проверяется отдельно. Риск: правило не машиноисполнимо — принимается, это
  граница среза.
- **Проверка:** дифф `src/domain/schemas/**` пуст.

### ADR-4 — Проверка поведения — существующими средствами

- **Контекст:** требуется evidence фактического выбора сеанса, но structural lint его не
  доказывает.
- **Решение:** использовать существующие тестовые средства (юнит-тесты рендера/плагина,
  grep-проверки шаблонов) и разрешённую наблюдаемую работу; непроверяемое честно
  помечается. Новый e2e-harness не вводится.
- **Последствия:** часть свойств остаётся «не проверено runtime» — это допустимый исход
  при явной отметке (NFR-P5). Риск: соблазн заявить «покрыто» по тексту — снимается
  явным разделением в test-plan.
- **Проверка:** test-plan содержит колонку «как проверяется» и «чем не проверяется».

### ADR-5 — P-02 исключается из покрытия, а не имитируется

- **Контекст:** путь доставки L2 частично зависит от router fallback.
- **Решение:** срез не объявляет исправленным сценарий, реально зависящий от
  неисправного fallback; такой сценарий либо исключается из заявленного покрытия, либо
  ждёт P-02.
- **Последствия:** честное сужение покрытия; release notes называют границу.
- **Проверка:** в release notes и requirements §6 явный перечень исключённого.

## Что срез НЕ меняет (явные не-цели дизайна)

- `src/**` runtime — кроме тестов/проверок, если они нужны для evidence.
- Публичные схемы, наборы статусов, `permission:` рамок.
- `wolf-router` fallback (P-02), TaskState/writer (E1), Git-скилл (B0),
  `command → commands` (A2), живой словарь (I), измерения (A1.1/A1.2).
- Формат `protect:` и механизм `sync-state`.

## Риски и смягчение

| Риск                          | Проявление                                          | Смягчение                                                                                                                  |
| ----------------------------- | --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Второй источник правила       | Копия ядра в зависимой методике или в `WORKER_BODY` | NFR-P1 + grep-проверка в test-plan                                                                                         |
| Ложное «покрыто» для сеансов  | Текстовое правило выдано за проверенное поведение   | ADR-4, колонка «чем не проверяется»                                                                                        |
| Потеря полномочий при replace | Прежний исполнитель продолжает писать               | C4 шаг 1 + явная проверка остановки; таймаут не доказательство                                                             |
| Шум в шаблонах                | Разрастание ядра до полного брифа                   | ядро = 8 элементов; профиль не вводит полей вне применимости (`implement` перечисляет шесть применимых — это не рост ядра) |
| Дрейф установленного набора   | Пользователь остаётся на старой версии правила      | C6: проверка загруженной версии, не только bytes                                                                           |
