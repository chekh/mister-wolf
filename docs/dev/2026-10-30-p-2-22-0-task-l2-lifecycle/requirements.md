# 2.22.0 — срез P: компактный TASK и жизненный цикл L2 — функциональные требования

Тред: `mem_20261030_p_reliz_2_22_0_kompaktnyy_task_i_zhiznen_24756f`.
Действующий requirements волны: `docs/dev/2026-10-26-wave-2-22-0-expert-package/requirements.md`
(status draft; синхронизируется указателем P-03a, исходные REQ/AC не переписываются).
Активная очередь: `docs/dev/roadmap/roadmap-v4.md` ред. 6, §3–4, §13, §14.
Решение очереди: `mem_20261030_roadmap_v4_red_5_edinaya_aktivnaya_ocher_fbee51`.

Статус документа: **черновик, ожидает утверждения владельцем**. Разработка кода и релиз
в текущем этапе не ведутся; документ фиксирует границу среза, которую следующим этапом
реализует исполнитель.

База: релиз `v2.21.2` → commit `2d88c58168c630ab1ebae02f0a2b247726b317da`; HEAD
`5ec4e4f26e2eba6afa3562aa9db3f79c76a3c5cc` — следующий docs-коммит записи о выпуске.
Целевая версия среза: **2.22.0** (полный X.Y.Z, minor). Предыдущий выпуск очереди
FIX-CACHE выпущен 2.21.2 и в scope среза не входит.

## 1. Контекст и проблема

Wolf выдаёт субагенту поручение, но форма этого поручения не зафиксирована: ядро TASK
живёт в одном абзаце `using-skills` вместе с полями, которые нужны только части задач
(`base_sha`, `cwd/worktree`, `allowlist`), а профиль исполнителя (правка кода, ревью,
исследование) нигде не отделён от общих полей. Из-за этого L1 либо копирует весь абзац
целиком, включая неприменимые Git-поля, либо сокращает произвольно — и L2 получает
шумные заглушки вместо значимого входа.

Вторая проблема — выбор сеанса субагента. Наблюдение владельца: новые самостоятельные
задачи передаются прежним субагентам, которые уже держат контекст прошлой задачи.
Частота и стоимость такого поведения не измерены (REQ-23A/REQ-23B — отдельные этапы),
поэтому срез вводит только правило выбора, а не механизм измерения.

Метрика успеха среза — не экономия токенов (её нельзя доказать без A1.1), а
**проверяемое наличие**: три применимые формы поручения существуют в едином источнике,
профили отличаются только применимыми полями, правило fresh/continue/replace задано
один раз и достижимо из зависимых методик, а доставленная версия набора реально
загружена у пользователя.

## 2. Область

**Входит в срез P (2.22.0):**

- **P-01** — общее ядро TASK, три профиля (implement / review / research), статический
  словарь существующих терминов.
- **P-04** — правило выбора сеанса L2: fresh / continue / replace, применяемое после
  решения делегировать.
- **P-03a** — адресная синхронизация действующего requirements с очередью и матрицей
  применимости §14 (указатель, без переписи 30 REQ).
- **P-03b** — интеграция и доставка среза: canonical-шаблоны, generated/installed-файлы,
  проверка фактической загрузки, human-facing объяснение.

**НЕ входит (не-цели уровня требований):**

- **P-02 worker fallback** — отдельное runtime-исправление router; собственная приёмка.
  Срез P не заявляет исправленным путь, реально зависящий от неисправного fallback.
- **E1 / State** — рабочее состояние задачи, writer. Срез применяет доступный handoff,
  но не вводит TaskState.
- **B0 / B1** — Git-скилл и переносимые операции; срез использует существующие
  полномочия и методики.
- **Миграция `command → commands`**: принадлежит A2.
- **Полный словарь I** (живой язык, REQ-02): статические термины среза не равны общему
  языковому механизму (Q-09).
- **A1.1 / A1.2**, измерения эффекта, A2, E2, D1/D2, A-autonomy.
- **Новый TASK-парсер, scheduler, модельные дефолты, публичные схемы, скрытый
  reasoning-контроль.**

## 3. Глоссарий

Термины среза. Статический словарь доставляется пользователю как часть P-01; здесь —
рабочее определение для требований и проверок.

- **Задача (task)** — ожидаемый результат с критериями приёмки и границами. Идентичность
  задачи задаёт `task_id`; она не совпадает с идентификатором сеанса инструмента.
- **Сеанс (session)** — исполнение задачи агентом, включая попытки. Одна задача может
  занимать несколько сеансов.
- **TASK** — поручение L2: ядро + применимый профиль.
- **Ядро TASK** — поля, применимые к любой задаче: `task_id`, цель/ожидаемый результат,
  AC, scope/полномочия, входы/методика, проверка, конечный бюджет и stop/return,
  ожидаемый RESULT.
- **Профиль TASK** — `implement` | `review` | `research`; добавляет только применимые
  сведения, не заменяет общие контракты.
- **fresh** — новый L2 для нового самостоятельного принимаемого результата.
- **continue** — прежний L2 для того же ещё не принятого результата.
- **replace** — новый L2 для той же задачи, когда прежнее исполнение больше не подходит;
  состояние передаётся через handoff.
- **RESULT** — отчёт L2: `DONE | DONE_WITH_CONCERNS | NEEDS_CONTEXT | BLOCKED` + изменения,
  проверки, evidence, отклонения, риски.
- **EVIDENCE** — привязка утверждения к команде/процедуре, cwd, revision, результату.
- **ACCEPTANCE** — отдельное решение принимающего уровня; `DONE` не равен `ACCEPTED`.
- **SCOPE** — что входит и не входит в задачу, и какие полномочия у исполнителя;
  выход за scope — возврат L1, а не самостоятельное расширение. Омоним: в отчёте
  `worker-reviewer` раздел `SCOPE` означает **покрытие ревью** (что проверено), а не
  границы задачи; контекст различает эти два смысла.
- **LIMITS/GAPS** — границы применимости полученного результата и названные
  неизвестные; непроверенное не выдаётся за проверенное, отсутствие данных не
  равно нулю или успеху.

## 4. Функциональные требования

### REQ-P01-1 — Общее ядро TASK как единственный источник

- История: Как L1, я хочу собрать поручение из одного ядра, чтобы L2 получал значимые
  входы и не получал шумных заглушек.
- Требование: Когда L1 формирует TASK для L2, поручение должно содержать ядро: `task_id`,
  цель/ожидаемый результат, AC, scope/полномочия, необходимые входы/методика, проверка,
  конечный бюджет и stop/return condition, ожидаемый RESULT. Ядро описано в одном
  каноническом месте; зависимые методики ссылаются на него, а не переписывают.
- Обоснование: roadmap §4 «Состав»; сейчас ядро смешано с профильными полями в
  `using-skills` «Контракты передачи».
- AC: (а) в каноническом источнике присутствуют все восемь элементов ядра, каждый —
  проверяемым предписанием, не перечислением через запятую; (б) любая другая методика,
  использующая TASK, ссылается на канон и не содержит второй формулировки ядра;
  (в) ядро обязательно для каждого TASK: применимое ядерное поле не может быть опущено,
  а неизвестный обязательный ядерный вход явно запрашивается (`NEEDS_CONTEXT`), не
  заполняется заглушкой; (г) опускаются только **профильные** поля, неприменимые к
  задаче (например, `base_sha` у ревью), — и это опускание не считается дефектом
  поручения.
- Приоритет: Must
- Источник: roadmap-v4 §4 «Состав», п. 1; expert-package REQ-10, REQ-13; решение
  `mem_20261030_roadmap_v4_red_5_edinaya_aktivnaya_ocher_fbee51`.

### REQ-P01-2 — Три профиля TASK

- История: Как L1, я хочу добавлять к ядру только применимые сведения профиля, чтобы
  поручение ревью не требовало Git-полей.
- Требование: Когда задача относится к правке кода, ревью или исследованию, TASK
  использует соответствующий профиль: `implement` добавляет repo/workspace/base_sha и
  allowlist записи; `review` и `research` добавляют revision документа/источника вместо
  Git-полей. Профиль не заменяет RESULT/EVIDENCE контракт своей роли и не расширяет
  полномочия.
- Обоснование: roadmap §4 «Состав», п. 2; REQ-13 (соразмерность, не по числу строк).
- AC: (а) три применимые формы заполнены на реальной задаче и различимы по составу
  полей; (б) профиль `review`/`research` не требует `base_sha`/`allowlist`; (в) профиль
  `implement` сохраняет роль-специфичный RESULT (`DONE|…|BLOCKED`); профиль `review`
  сохраняет состав отчёта `SUMMARY / VERDICT / FINDINGS / SCOPE / LIMITS / EVIDENCE` и
  вердикты `APPROVED|CHANGES_REQUIRED|INCONCLUSIVE`; профиль `research` сохраняет
  `FINDINGS / CONFIDENCE / GAPS` и разделение источника, факта, вывода и гипотезы;
  (г) ни один профиль не вводит нового публичного поля схемы Wolf.
- Приоритет: Must
- Источник: roadmap-v4 §4; expert-package REQ-13, REQ-10.

### REQ-P01-3 — Статический словарь существующих терминов

- История: Как человек и как агент, я хочу однозначно понимать TASK/RESULT/EVIDENCE/
  ACCEPTANCE/SCOPE/LIMITS-GAPS, чтобы не переизобретать смысл в каждом поручении.
- Требование: Когда поставляется срез P, статический словарь шести существующих терминов
  доставляется вместе с ним и не описывает механизм, которого нет. Словарь не закрывает
  REQ-02 и не вводит живой язык.
- Обоснование: roadmap §4 «Состав», п. 3; Q-09.
- AC: (а) шесть терминов определены статически; (б) определения не обещают runtime-
  поведения сверх поставленного; (в) отсутствует механизм генерации/эволюции словаря.
- Приоритет: Must
- Источник: roadmap-v4 §4; expert-package REQ-02 (остаток), Q-09.

### REQ-P04-1 — Правило выбора сеанса: fresh / continue / replace

- История: Как L1, я хочу явную границу поручений, чтобы независимая задача не
  наследовала контекст прошлой, а незавершённая не теряла прогресс.
- Требование: Когда L1 решил делегировать, он выбирает: **fresh** — новый самостоятельный
  принимаемый результат; **continue** — тот же ещё не принятый результат (уточнение,
  следующий связанный этап, evidence, ограниченное исправление по исходной приёмке);
  **replace** — та же задача, но прежнее исполнение больше не подходит. Правило задаётся
  один раз в `executor-lead`; `wolf-plan`/`wolf-sdd`/`wolf-execute`/`wolf-review`/
  `wolf-handoff` ссылаются на него точечно.
- Обоснование: roadmap §4 «P-04» — наблюдение владельца о передаче новых задач прежним
  субагентам.
- AC: (а) три выбора определены с основанием и действием; (б) `task_id` явно не
  подменяется идентификатором сеанса; (в) `continue` не расширяет scope — новые
  самостоятельные требования не добавляются под видом repair; (г) после приёмки прежний
  L2 не является свободным слотом для следующей задачи; (д) в зависимых методиках —
  ссылки, не вторые формулировки правила.
- Приоритет: Must
- Источник: roadmap-v4 §4 «P-04»; expert-package REQ-13, REQ-19.

### REQ-P04-2 — Правило применяется после решения делегировать

- История: Как владелец, я не хочу платить за лишние передачи и обязательного
  исследователя на каждую задачу.
- Требование: Когда L1 может сам выполнить малую связанную работу, правило fresh/
  continue/replace не создаёт дополнительного L2 и не назначает обязательного
  исследователя или отдельного агента на файл. Требуемая независимая приёмка при этом
  выполняется другим уполномоченным участником.
- Обоснование: roadmap §4 «P-04» — «выбор выполняется после решения делегировать»;
  REQ-13.
- AC: (а) текст правила содержит явное «после решения делегировать»; (б) сценарий
  «малая связанная работа» даёт исполнение L1 без нового L2; (в) self-review не
  засчитывается независимой приёмкой.
- Приоритет: Must
- Источник: roadmap-v4 §4; expert-package REQ-13.

### REQ-P04-3 — Замена: сохранность и model/variant

- История: Как L1, я хочу заменять исполнителя без потери состояния задачи.
- Требование: Когда выполняется replace, порядок один: прекратить новые изменения
  прежнего исполнителя и подтвердить завершение связанных пишущих инструментов →
  уполномоченный владелец/L1 сохраняет известный результат и handoff, выполняет
  требуемую публикацию → получатель проверяет доступность результата и принимает
  ownership → прежняя сессия закрывается после сохранения нужного контекста.
  Task identity, evidence, права и действующая политика model/variant сохраняются;
  resume не считается доказанной сменой модели.
- Обоснование: roadmap §4 «Сохранность при замене», «Прогресс, роль и модель».
- AC: (а) прекращение записи и закрытие сессии различимы в тексте; (б) таймаут не
  трактуется как доказанная остановка; (в) read-only review не требует нового
  worktree; (г) при неподдержанной в resume смене модели требуется новый исполнитель;
  (д) незавершённая приёмка не обнуляется при замене: правило требует сохранить
  известный результат и открытые замечания через handoff; фактический учёт расходов —
  A1.1/E2, и при отсутствии связей результат помечается «неизвестно с покрытием», а не
  нулём (см. NFR-P4).
- Приоритет: Must
- Источник: roadmap-v4 §4; expert-package REQ-19, REQ-15.

### REQ-P04-4 — Независимость первого ревью

- История: Как владелец, я хочу, чтобы первый проход ревью был действительно независимым.
- Требование: Когда назначается первичное независимое review, в него передаются
  проверяемые материалы, нормы и нужное evidence, но не история родителя, не чужие
  findings и не ожидаемый verdict. Повторная проверка исправлений своих замечаний может
  выполняться тем же reviewer.
- Обоснование: roadmap §4 «Независимость первого review»; действующее ограничение
  `wolf-review`.
- AC: (а) перечень непередаваемых материалов явно назван; (б) новый id при
  непроверенной изоляции наследования не закрывает гейт — результат остаётся
  `INCONCLUSIVE`/ограниченным; (в) честный отчёт о возможностях host не приравнивается
  к успешной независимой приёмке.
- Приоритет: Must
- Источник: roadmap-v4 §4; expert-package REQ-15, AC-04.

### REQ-P03a-1 — Адресная синхронизация действующего requirements

- История: Как читатель пакета 2.22.0, я хочу видеть, какая очередь действует и какие
  AC применимы к срезу, не перечитывая 167 КБ истории.
- Требование: Когда выпускается срез P, действующий requirements волны получает
  указатель: активная очередь (roadmap-v4), матрица применимости §14 и границы среза P.
  Исходный смысл REQ/AC, evidence обзора и состав 30 REQ не переписываются; статус
  пакета обзора не повышается до approved без основания.
- Обоснование: roadmap §3 «P-03a»; §14 «NFR и AC не исчезают при дроблении».
- AC: (а) в requirements присутствует блок-указатель на очередь и матрицу; (б) ни одна
  исходная формулировка REQ/AC не изменена — проверяется диффом; (в) статус документа не
  изменён на approved; (г) перечислены явно отложенные идентификаторы с адресом остатка.
- Приоритет: Must
- Источник: roadmap-v4 §3, §14; решение
  `mem_20261030_roadmap_v4_red_5_edinaya_aktivnaya_ocher_fbee51`.

### REQ-P03b-1 — Доставка среза и проверка фактической загрузки

- История: Как пользователь, я хочу получить новую форму поручения в установленном
  наборе, а не только в репозитории.
- Требование: Когда срез P поставляется, canonical-шаблоны и generated/installed-файлы
  обновлены штатным renderer'ом, отпечаток набора соответствует новой версии, а
  проверка подтверждает, что загруженная версия содержит новое правило — не только что
  bytes изменились.
- Обоснование: roadmap §2 п. 5 (доставка сопровождает каждую возможность), §4 «Опоры»;
  AC-06.
- AC: (а) `wolf sync` приводит штампы набора к версии выпуска; (б) установленный
  `.opencode/**` содержит новое ядро/профили/правило; (в) проверка «версия реально
  загружена» отделена от «файл изменился»; (г) файлы с `protect:` остаются живыми у
  пользователя и явно перечислены в release notes как не перезаписанные.
- Приоритет: Must
- Источник: roadmap-v4 §2, §4; expert-package REQ-20, REQ-22, AC-06.

### REQ-P03b-2 — Человеческое объяснение и обратная совместимость рамок

- История: Как человек, я хочу понять новое правило обычным языком.
- Требование: Когда срез поставляется, human-facing объяснение (release notes и
  документация) описывает новое ядро, профили и правило выбора сеанса понятным текстом;
  ранее корректные рамки/скиллы сохраняются, публичные схемы и наборы статусов не
  меняются.
- Обоснование: roadmap §4 «Приёмка», п. 7–8; AC-05.
- AC: (а) release notes объясняют, что изменилось и чего срез не делает; (б) публичные
  схемы и статусы не изменены — проверяется диффом схем; (в) сжатие служебного
  сообщения не ухудшает объяснение.
- Приоритет: Must
- Источник: roadmap-v4 §4; expert-package AC-05, AC-09.

## 5. Нефункциональные требования (NFR)

Полные формулировки NFR-01…NFR-09 — в действующем requirements волны
(`2026-10-26-wave-2-22-0-expert-package/requirements.md` §5). Здесь фиксируется
применимость к срезу P.

**NFR-02 (целостность) и NFR-07 (наблюдаемость) к срезу неприменимы:** срез не вводит
writer, миграций, новых событий и нового пути записи памяти; существующие locks/revision
не затрагиваются. Неприменимость заявлена, а не молчалива (roadmap §14).

### NFR-P1 — Единый источник правила (NFR-04)

- Требование: Одно правило — одно каноническое место. Ядро TASK и словарь — в
  `using-skills`; правило fresh/continue/replace — в `executor-lead`. Зависимые методики
  содержат точечные ссылки, не копии. У L2 нет диспетчерского каталога.
- AC: ни один файл `templates/base/**`, кроме двух канонов, не содержит 4 и более
  элементов ядра TASK **в одном перечислении или одном предложении**; ни один файл,
  кроме `executor-lead.md`, не содержит одновременно двух из трёх слов
  `fresh`/`continue`/`replace` в связке с действием L1; у доставленного L2 отсутствует
  диспетчерский контур.
  - Единица счёта: перечисление = одна фраза-список после двоеточия внутри одного
    предложения или один пункт списка. Ядро, разнесённое по разным предложениям и
    пунктам, не считается четвёркой «подряд» — иначе проверка превращается в
    неограниченный grep по смыслу.
  - Явные цели правки (должны стать ссылками): `wolf-plan/SKILL.md:23` (полный перечень
    полей ядра), `wolf-review/SKILL.md:17-19` (перечень полей TASK в трёх строках).
  - Явные исключения с владельцем B0 (не «зелёный grep»): `using-git-worktrees/SKILL.md:27`,
    `requesting-code-review/SKILL.md:21` — частичные перечни полей, остаются как есть до B0.
- Источник: NFR-04; roadmap §4.

### NFR-P2 — Совместимость (NFR-01)

- Требование: Ранее корректные рамки/скиллы и публичные схемы/статусы не меняются;
  неизвестная схема не трактуется как успех.
- AC: дифф схем пуст; существующие рамки проходят структурную проверку; `npm run check`
  зелёный.
- Источник: NFR-01; roadmap §4 «Приёмка» п. 8.

### NFR-P3 — Доставка и защита (NFR-08, AC-06)

- Требование: `wolf sync` идемпотентен; файлы с `protect:` не перезаписываются; откат
  предыдущей версии инструкций доступен существующим механизмом (update map / backup).
- AC: повторный sync не даёт диффа; `protect: true`/`X.Y.Z` удерживает файл; в release
  notes перечислены удержанные файлы.
- Источник: NFR-08; REQ-22; AC-06.

### NFR-P4 — Честная измеримость (NFR-06, AC-08)

- Требование: Срез не заявляет экономию затрат или контекста. Число свежих агентов и
  длина TASK сами по себе не доказывают экономию. Отсутствие связей task/attempt/event
  означает «метрика неизвестна с указанием покрытия», а не ноль нарушений. Расходы при
  replace не обнуляются в границах доступного учёта; полный учёт — A1.1/E2.
- AC: release notes не содержат числового обещания экономии; утверждения об эффекте
  отсутствуют либо помечены как непроверенные.
- Источник: NFR-06; roadmap §6 «Наблюдение P-04»; AC-08.

### NFR-P5 — Проверки на точную revision (NFR-05, AC-07)

- Требование: Обязательные проектные проверки выполняются на точной revision; runtime-
  поведение и текстовое evidence раздельны; structural lint не доказывает фактический
  выбор сеанса.
- AC: evidence содержит команду, cwd, revision, exit code; утверждение о выборе сеанса
  либо подтверждено доступным средством, либо помечено как непроверенное.
- Источник: NFR-05; AC-07.

### NFR-P6 — Безопасность и полномочия (NFR-03)

- Требование: Правило выбора сеанса не расширяет полномочия L1/L2 и не обходит запрет
  спавна у L2; ручная передача состояния не обходит права записи памяти.
- AC: рамки ролей не получают новых разрешений; L2 не вызывает Стюарда и не спавнит.
- Источник: NFR-03.

### NFR-P7 — Достоверность примеров (NFR-09)

- Требование: Примеры в документации и release notes соответствуют поставленной версии;
  несуществующие команды и поля не документируются.
- AC: каждая упомянутая команда существует в `wolf --help` этой revision; упомянутые
  поля существуют в схеме.
- Источник: NFR-09; AC-05.

## 6. Ограничения и допущения

- Допущение: действующий requirements пакета волны остаётся draft; срез P не требует его
  повышения до approved.
- Допущение: `using-skills` и `executor-lead` — общие файлы с порядком интеграции
  **P → B0 → A1.2 → E1** (roadmap §13). Срез P идёт первым и не конкурирует с будущими.
- Допущение: рамка `protect:` — существующий механизм; срез не вводит нового формата
  защиты.
- Ограничение: срез — инструкционный. Он не вводит TASK-парсер, scheduler, модельные
  дефолты, публичные поля схем и контроль скрытого reasoning.
- Ограничение: фактическая семантика создания/продолжения субагента проверяется по
  возможностям host; недоказанная изоляция не засчитывается независимой приёмкой.
- Ограничение: P-02 (worker fallback) не входит; сценарий, реально зависящий от
  неисправного fallback, не объявляется покрытым и либо исключается из заявленного
  покрытия, либо ждёт P-02.
- Предсуществующее: гейт `npm run check` и `npm run docs:build` должны быть зелёными на
  базовой revision до правок; красное до правок фиксируется отдельно и не чинится в этом
  срезе.
