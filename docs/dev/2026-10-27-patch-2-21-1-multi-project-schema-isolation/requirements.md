# 2.21.1 — Изоляция схем памяти между проектами — требования и журнал изменений

> **Профиль:** FIX (подтверждённый дефект с воспроизведением и проверкой). Режим фиксирует L1.
> **Дефект подтверждён кодом**, не гипотезой: см. §1.

## 1. Контекст и проблема

`MarkdownMemoryStore` (`src/adapters/fs/markdown-memory-store.ts:36-40`) держал схему типов в
модульной переменной без ключа проекта:

```ts
let typeSchemaCache: Map<MemoryType, z.ZodTypeAny> | null = null;
function getTypeSchemas(baseDir: string, onProblem?: (msg: string) => void) {
  if (typeSchemaCache) return typeSchemaCache;   // ← базаDir игнорируется
  ...
  typeSchemaCache = cache;
  return cache;
}
```

Таксономия (схема типов), загруженная для первого проекта в процессе, переиспользуется для всех
следующих. Это наблюдаемо в одном процессе: `wolf upgrade` создаёт `MarkdownMemoryStore` для чужих
корней (`src/adapters/cli/commands/memory-upgrade.ts:410` и `:686` — `new MarkdownMemoryStore(root)`,
где `root` — корень другого проекта), поэтому операции в проекте B валидируются по схеме проекта A.

**Границы утверждения.** Наблюдаемая поверхность сегодня — чтение (`list({type:'face'})`, `get`,
`read`): объект типа, которого нет в таксономии текущего проекта, может быть принят по схеме чужого
проекта. Потеря данных по коду **не** утверждается — подтверждено именно нарушение изоляции схем.

**Почему отдельный патч.** Дефект в модульном состоянии: он живёт между вызовами в одном процессе,
поэтому не проявляется в тестах одного проекта и не ловится обычным регрессионным набором. Исправление
требует изменения кэша и регрессионного теста на два корня в одном процессе.

## 2. Функциональльные требования

- **REQ-01 (AC-1) — Кэш схем разделён по проекту.** Одинаковые типы в разных проектах валидируются
  по своей схеме. Минимальное решение — привязка к `baseDir` (Map по корню), по образцу уже
  существующего в проекте паттерна `syncConfigCache` (`src/adapters/fs/config-file.ts:184`).
- **REQ-02 (AC-2) — Регрессионный тест.** Два разных корня (проекта) в одном процессе: схема второго
  не наследуется от первого. Поведение зафиксировано тестом, а не текстом; тест падает на
  pre-fix коде и проходит после фикса.
- **REQ-03 (AC-3) — Регрессии в одном проекте.** Существующее поведение в одном проекте не меняется:
  регрессионный набор зелёный.
- **REQ-04 (AC-4) — Минимальный дифф.** Только изоляция схем, её тест и релизные артефакты. Без
  попутных рефакторингов, без новых зависимостей.

**Явно не входит:** переписывание системы хранения; исправление второго модульного флага
`configLoadWarned` (смежное наблюдение, зафиксировано как риск/долг); изменения таксономии или
формата `.wolf/config.yaml`; изменения черновика требований волны 2.22.0 и пакета обзора роадмапа.

## 2.1 Известные ограничения (по итогам независимого ревью 2026-10-27)

- **Ключ кэша — сырая строка `baseDir`.** Разные формы одного пути (`/p/x` vs `/p/x/`, symlink
  `/tmp` → `/private/tmp`) дают разные записи кэша. На корректность не влияет (схема всегда
  строится из конфига того же `baseDir`), цена — дублирующая сборка Zod-схем и рост `Map` в
  долгоживущем процессе. Осознанно не чинится в этом патче: минимальный дифф.
- **`configLoadWarned` остаётся общепроцессным.** Второй и последующие проекты с битым конфигом
  получают CORE-схему молча (предупреждение уже было выдано первому проекту). Вне объёма патча —
  по REQ-04; кандидат в следующий патч (`configLoadWarned` → `Map` по `baseDir`).
- **Кэш схем не инвалидируется в пределах процесса.** Изменение `.wolf/config.yaml` после первого
  чтения не подхватывается до следующего процесса. Поведение унаследовано от пре-фикса, не
  изменено патчем.
