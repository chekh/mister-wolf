# 2.30.0 — ограниченные поручения — тест-план

## Сценарии

AC определены в requirements.md; этот файл задаёт oracle и процедуру проверки.
Для каждой пробы сохранять входы, revision инструкций/артефакта, реально выбранные
TASK/session IDs, сообщения, проверки и ограничения. Не нужны отдельные файлы
отчётов в docs/dev. Независимый ревьюер проверяет решение по критериям ниже.

| ID / требования | Given / When                                                                                                                      | Then — наблюдаемый oracle                                                                                                       |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| S01 / REQ-01    | L1 завершил и получил приёмку поставки A; в том же thread поручают самостоятельную B того же класса                               | B назначена новому L1, даже без параллельности; контекст A выбран адресно                                                       |
| S02 / REQ-02    | Поставка A ещё не принята; поступили finding IDs                                                                                  | Допустим тот же L1, исправляется A без соседнего объёма, исходная приёмка не обходится                                          |
| S03 / REQ-02    | Один исходный TASK включает локальный план, реализацию и проверку одной поставки                                                  | Внутреннее согласование плана не требует нового L1; агент не создаётся на этап/файл                                             |
| S04 / REQ-02,06 | Отдельный TASK на план принят                                                                                                     | Автор плана не начинает реализацию; следующий TASK адресуется новому L1                                                         |
| S05 / REQ-03,05 | Для общей цели неизвестны границы нескольких поставок                                                                             | L0 поручает оценку/план L1, получает брифы/зависимости/интеграцию; сам не изучает код и L1 не спавнит L1                        |
| S06 / REQ-03    | План неполон: нет критерия результата одного L1                                                                                   | L0 возвращает конкретный пробел; готовый TASK не достраивает предметным расследованием                                          |
| S07 / REQ-04,08 | Две поставки с готовыми входами, раздельными writes и известной интеграцией                                                       | Два L1 запускаются параллельно в общем разрешённом бюджете; общий план имеет одного writer                                      |
| S08 / REQ-04    | B зависит от принятого контракта A                                                                                                | B ждёт нужного входа, затем получает fresh L1; ожидание не повод переиспользовать A                                             |
| S09 / REQ-04,10 | Host не поддерживает параллельный launch/close или history isolation                                                              | Ограничение указано; нет фиктивных вызовов/закрытия/заявления чистоты; последовательная B получает новый экземпляр              |
| S10 / REQ-07,10 | У того же TASK непригоден контекст; L1 использовал 4 из 5 L2 вызовов                                                              | Replace через доступный snapshot и остановку writer, task_id/решения/findings сохранены, остаётся 1 вызов до решения нанимателя |
| S11 / REQ-07,09 | Свежий L1 получил решения и evidence, применимое к проверяемым входам, включая прежнюю revision при несвязанной правке            | Не переоткрывает решения и не повторяет все проверки лишь из-за fresh; конкретные обязательные гейты исполняет                  |
| S12 / REQ-09    | L2 сообщил DONE без нужного evidence, либо evidence от revision с изменёнными проверяемыми входами без подтверждения применимости | Неподтверждённые AC не принимаются; статус не заменяет доказательство                                                           |
| S13 / REQ-08,09 | Две части зелёные по отдельности, объединённое состояние нарушает контракт                                                        | Общая поставка не ACCEPTED до интеграционного исправления и проверки                                                            |
| S14 / REQ-06    | Требуется поручить планирование, сообщить RESULT и принять план                                                                   | Используются существующие role-specific формы; нет PLAN_TASK/нового profile/слота, DONE не трактуется как ACCEPTED              |
| S14b / REQ-09   | L1 принял результат L2, интеграция зелёная, но решения L0 о поставке нет                                                          | Дочерний ACCEPTED не означает приёмку общей поставки; требуется решение назначенного L0/владельца                               |
| S15 / REQ-11    | Render/init нового проекта на candidate                                                                                           | Новый reference существует; root/L0/L1 реально указывают условие загрузки, язык доставлен полностью                             |
| S16 / REQ-11    | Upgrade staging проекта с protect/keep и локальной face mutation                                                                  | Локальные model/variant/protect/faces сохранены; конфликт старой нормы отмечен, rollout не назван завершённым                   |
| S17 / REQ-01,02 | До приёмки A добавляется новая самостоятельная B либо A формулируют как весь roadmap                                              | B не прячется в continue; неопределённо широкий мандат возвращается к ограниченным поставкам                                    |
| S18 / REQ-12    | Candidate на точном baseline и на изменившемся main                                                                               | На базе apply --check; на новой базе анализ пересечений, без force и подмены файлов старыми копиями                             |

S01/S02/S03/S05/S07/S10/S12/S13 — минимальный поведенческий набор перед заявлением,
что методика работает. Прочтение сценария экспертом — document review, не живое
исполнение. Для поставки инструкционного набора допустимо оставить live observation
открытым при явном ограничении и отсутствии заявления о доказанном эффекте;
конкретный пропуск обязательного гейта агент согласует по действующей политике.

## Прогоны

### Подготовка документов и patch

1. Экспертные линзы A/B/C по каждому документу; findings/решения в plan.md.
2. Форматирование quartet/release-agent штатным Prettier, проверка локальных ссылок.
3. На disposable worktree точной базы: `git apply --check "$PATCH_FILE"`, где PATCH_FILE — абсолютный путь к patch из checkout пакета (см. release-agent.md).
4. Применить candidate в disposable worktree; проверить diff, язык/права,
   существующие role/conveyor guards и реальную render-доставку нового reference.
5. Структурные проверки не считать прохождением S01…S17 в живом harness.

### После интеграции агентом выпуска

- Применимые узкие тесты:
  `npx vitest run tests/unit/base-frames-guard.test.ts tests/unit/coordinator-frame-guard.test.ts tests/unit/conveyor-skills-guard.test.ts`.
- Проверить доступные suite names через `rg --files tests`; выбрать реальные
  delivery/protect/upgrade тесты; проверить включённый candidate regression BA-T04.
- Параметры генератора проверять чтением `scripts/generate-update-map.mjs`;
  `--help` не поддерживается и не является read-only вызовом. В BA-T06a после
  штатного version bump: `node scripts/generate-update-map.mjs --prev 2.29.0`,
  затем `node scripts/generate-update-map.mjs --verify`. Предпросмотр без записи:
  `node scripts/generate-update-map.mjs --dry-run --prev 2.29.0`.
- `env -u NO_COLOR npm run check`; проектный e2e gate `npm run e2e`.
- `npm run docs:check` для EN/RU guides; `npm pack --dry-run` для состава доставки.
- Staging init/upgrade/re-stamp и face compatibility; затем независимый final review.

Подготовительная ветка сохраняет только документы и patch. В implementation
worktree release metadata готовятся в BA-T06a до итогового полного гейта BA-T06b;
публикация BA-T07 выполняется после приёмки. Падение map guard не обходить: до
итогового check карта обязана покрывать новый reference. Прочие падения анализировать по существу.

### Область честности результатов

Пакет подготовки не заявляет прохождение полного release check/e2e, rollout,
публикацию или сокращение токенов. Фактические подготовительные исходы — plan.md.
При ошибке окружения фиксировать точный failing step и область; не называть
проверку пройденной и не исправлять посторонний runtime в этом срезе.
