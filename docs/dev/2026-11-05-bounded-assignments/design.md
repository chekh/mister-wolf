# 2.30.0 — ограниченные поручения — дизайн

## Глоссарий

Термины языка и слоты остаются в agent-language.md/contracts.md 2.29.0.
«Наниматель», «поставка», «план назначений» — поясняющая проза, не новые формы.

## Контракты

### 1. Граница поручения

Наниматель назначает экземпляр на самостоятельно принимаемый ограниченный
результат с известными AC, SCOPE, входами и stop/return. Общая цель/thread
может включать несколько последовательных и параллельных поручений.

L1 получает поставку, внутри которой нужны организация L2 и интеграция. L2
получает конечную подзадачу без выбора общей организации. Размер определяется
связностью результата, зависимостями, контекстом и проверкой, не количеством файлов.
Весь roadmap/проект без конечной поставки не является достаточным поручением L1.
Не дробить по каждому этапу, сообщению или команде: связанная работа может остаться
у одного L1 до приёмки общего порученного результата.

### 2. Решение о сеансе на обеих границах

| Состояние работы                                                                  | Решение                                  |
| --------------------------------------------------------------------------------- | ---------------------------------------- |
| Новый самостоятельно принимаемый результат, в том числе после предыдущей приёмки  | fresh: новый экземпляр с отдельным TASK  |
| Уточнение/ответ/этап исходного мандата/исправление того же непринятого результата | continue, если прежний контекст пригоден |
| Прежнее поручение ещё действует, но исполнитель недоступен/контекст непригоден    | replace через существующий HANDOFF       |

Новая независимая работа не добавляется в старый TASK даже до его приёмки под
видом исправления. Допустимое уточнение того же результата версионирует адресный
бриф по R2 без нового runtime schema. task_id не session ID; один thread не один L1.
Принятый результат не становится свободным агентским слотом следующей работы.
Поздний дефект принятой поставки — отдельное поручение со ссылкой на evidence,
не скрытое продолжение закрытого мандата. Это не отменяет предусмотренные текущим
поручением раунды исправления до приёмки.

### 3. Подготовка назначений

L0 поручает конечному L1 подготовить план, когда выбор границ нескольких L1
требует предметной оценки. Планирующий L1 привлекает L2 по действующим правилам,
возвращает план/готовые брифы и краткую сводку, не создаёт sibling L1.

План содержит в существующих разделах/брифах, без новых слотов: результаты и AC;
входы и зависимости; готовые TASK; согласованные границы чтения/записи;
условия последовательного/параллельного запуска; назначение интеграции и общего
writer; лимиты в доступном бюджете. L1-поставка может содержать внутренний план L2,
но планирующий L1 не обязан детализировать за всех исполнителей их внутренние шаги.

L0 проверяет цель, scope, полномочия, зависимости по сводке и основание готовности,
не конструирует техническую декомпозицию. Недостаточность возвращает автору.
План принят как результат TASK на планирование; запуск поставок — отдельные TASK
от L0. Одно небольшое известное поручение не требует предварительного найма планировщика.

### 4. Параллельность и владение

L0 запускает независимые готовые L1; каждый L1 запускает свои готовые L2.
Последовательные зависимости также используют fresh при новой поставке.
План задаёт одного writer для общих plan/test-plan/памяти, а назначенный L1
организует техническую интеграцию. Общий writer не становится скрытым руководителем
sibling L1: назначения и изменение их мандатов остаются у L0.

Блокер приостанавливает зависимые назначения. Изменение общего контракта
возвращается L0 с перечислением затронутых поручений; проверка зависимостей и
evidence выполняется ответственными L1. Автоматическая dependency invalidation
не поставляется. Нет capability/budget для параллельности — честное ограничение
и последовательные свежие назначения, без обхода task permissions.

### 5. Контекст, расходы и завершение

Новый исполнитель получает выбранные доступные источники/revision, полную
назначенную методику/лицо, действующие ACTIVE_CONSTRAINTS/DECISIONS[] и evidence
с областью применимости. Унаследованный полный чат не считается fresh изоляцией.
Если host не позволяет исключить историю, указать ограничение; не заявлять
снижение контекста или независимость проверки. Независимость review — по действующим нормам.

Replace не меняет task identity, права, открытые findings и использованный бюджет.
Текущий default пять вызовов L2 относится к поручению L1; разрешение нового
бюджета даёт наниматель, а не смена session. План нескольких L1 распределяет
известный общий бюджет; отсутствие доступного учёта не превращается в нулевые расходы.
Не вводить ledger, parser, новый budget config или обязательный отчёт на каждый вызов.

Сохранять значимые результаты существующими note/context/history. После приёмки
закрыть ненужный экземпляр при доступном механизме, предварительно остановив
запись/процессы и сохранив evidence. При отсутствии close не имитировать закрытие:
перестать назначать новую работу этому экземпляру. Сессию и worktree не отождествлять.

### 6. Применение языка 2.29.0

Словарь и R1–R6 неизменны; message slots нормативны в contracts.md.
TASK задаёт поручение; RESULT сообщает результат по своей роли; EVIDENCE
подтверждает AC; ACCEPTANCE выражает решение принимающего; HANDOFF переносит
работу и ответственность. Поручение «подготовить план» выражается целью/результатом
обычного брифа, без plan-profile или нового речевого акта. L1 сохраняет
REPORT/STATUS/CRITERIA; research/review/implement — свои RESULT.

L1 принимает L2 в своём мандате, L0 — поставку L1 и итог цели. Эти решения
не взаимозаменяемы. Нельзя принять общую поставку по одному дочернему ACCEPTED.
Существующие enum/слоты ACCEPTANCE не расширяются. Уточняются область решения
и назначенный принимающий в действующих инструкциях, без второго словаря.

R2 требует ID/версии вместо «сделай то же». R3 — полная доставка языка со скиллами;
это не повод повторно копировать уже доставленный актуальный документ в каждый TASK.
Непокрытая ситуация — «вне контракта» по R6; LANGUAGE-жалоба требует реального
затруднения и не разрешает самостоятельную мутацию языка.

### 7. Доставка, active faces и границы кандидата

Новый reference входит в существующий using-skills. Реальная загрузка обеспечивается
root/role triggers; наличие файла на диске недостаточно. Источник — templates/base;
проектные .opencode copies доставляются штатным upgrade/re-stamp после интеграции.

В candidate не повышать package/lock, не генерировать ложный финальный update-map,
не менять live faces. Агент выпуска после проверки добавляет delivery-тест,
генерирует карту из фактической базы, проверяет staging init/upgrade и protect/keep.
Существующие active playbooks проверяются на конфликт долгоживущего L1 через
разрешённый контур Стюарда; несовместимое сохраняется как незавершённый rollout.
Если seed-поведение действительно меняется, версия соответствующего playbook
инкрементируется отдельно. Изменённая рамка не доказывает live face migration.

## ADR-карточки

ADR-1 — один общий reference, не новый агент/skill. Контекст: правила L2 уже
работают, проблема в границе L1. Решение: division-of-labor внутри using-skills,
обязательные ссылки нанимателей. Последствие: единый смысл без повторения приёмки.
Статус: предложено для проверки агентом выпуска в согласованном scope.

ADR-2 — единица lifetime есть ограниченная поставка. Контекст: thread и сессия
длиннее результата. Решение: fresh для нового результата; continue/replace для
непринятого. Последствие: последовательная смена L1 обязательна без этапного дробления.
Статус: направление подтверждено владельцем в диалоге; реализация подлежит проверке.

ADR-3 — язык не расширяется. Контекст: наблюдение 2.29.0. Решение: используем
существующие формы/профили и поясняющий текст. Последствие: нет новых слотов,
автоматизации speech acts и parser; пробелы наблюдаем через R6/LANGUAGE.
Статус: ограничение действующей версии.

ADR-4 — metadata release отдельно от candidate. Контекст: агент должен сначала
проверить пакет на актуальном main. Решение: patch на точную базу, без выпуска
сейчас; version/CHANGELOG/update-map/stamp после интеграции. Последствие: dry
candidate может требовать финальной карты перед широкими distribution gates.
Статус: соответствует поручению на подготовку.
