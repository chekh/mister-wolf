# Агенту минирелиза: организация работы и ранние вопросы

Владелец поручил согласованную доработку связанных скиллов и рамок. Наблюдаемый
сбой: старательный агент расширяет scope и начинает расследование там, где
достаточен прямой путь или один ответ руководителя. Лечим выбор способа работы
и противоречивые нормы; точное ТЗ и новые запреты не должны быть единственной
защитой. Пользователь явно выбрал широкий согласованный выпуск.

Подготовительные проверки: check — 222 файла, 2027 PASS / 4 skip; e2e —
61 файл, 233 PASS; сборка документации PASS; независимое read-only ревью APPROVED.
Патч проверен на применение к точной базе. Это не приёмка live rollout.

## База и применение

- Патч подготовлен поверх 2.23.1, commit 141ec577a081eec89e2660cb47134604da81a1a3.
- Новая ветка/worktree от актуального main по действующей Git policy. На базе: `git apply --check mister-wolf-work-strategy.patch`, затем `git apply mister-wolf-work-strategy.patch`.
- Если main изменился, сравни затронутые источники и интегрируй смысловые изменения; не заменяй целые файлы старыми копиями. Новый навык и связанные правки принимаются вместе.
- Версию не публиковали и не повышали. Если 2.23.1 остаётся последней, ближайший patch — 2.23.2; иначе выбери следующий свободный X.Y.Z. Используй штатный npm version, актуализируй lock, CHANGELOG, update-map.version/prev и категории от реально принятой базы.

## Принцип поведения

Агент выбирает соразмерное действие, различает обязательный гейт/условный шаг/
технику, спрашивает носителя контекста до дорогого расследования и завершает
достаточно обоснованный результат. Вопрос не считается провалом и не требует
предварительных попыток. Руководитель отвечает или даёт средство; не возвращает
неизменное «разберись». Это применимо к любому предмету работы.

## Проверки перед выпуском

См. test-plan.md: отдельно structural и behavioral. Выполни `env -u NO_COLOR npm run check` при NO_COLOR=1 в окружении (существующий TTY-тест требует цвета),
применимые e2e/docs gates по проектной политике. Проверь фактическую delivery
нового skill в целевом harness и обе команды. Не объявляй пилот доказательством
экономии: на двух парных задачах baseline и candidate оба корректны; отдельные candidate-пробы S2/S7 также пройдены; полные
runtime-метрики, holdout и сложные/ложные триггеры ещё не измерены.

## Обновление установленных проектов и active faces

Сначала staging-копия: сохранить model/variant, protect/keep и локальные мутации,
проверить diff/backup, доставить новый скилл и согласованные рамки. Отдельно
проверить доступность полного текста для L2 без повторного onboarding. Если
защита оставляет старую рамку без новой доставки, это незавершённый rollout,
а не повод молча снять protect.

`wolf sync` не меняет живую память лиц. Изменённые seeds четырёх номерных
playbook имеют v4; existing active faces нужно сопоставить с patch через
действующий авторизованный контур Стюарда/миграции. Не перезаписывать локальные
лица seed-текстом. Для каждого активного источника определить: уже соответствует,
нужна адресная мутация, либо конфликт требует решения. Сохранить ID/версии,
проектные исключения, G17 и rollback; новая seed-версия не доказывает live rollout.
Особенно убрать старое обязательное чтение разделов целиком/цитирование каждой
находки, если оно сохраняется в active researcher playbook.

## Откат

До rollout сохранить прежний пакет и состояния faces. При регрессии вернуть
пакет штатным upgrade-путём, восстановить прежние лица поддержанным механизмом
по сохранённым ID/операциям и повторно проверить доставку. Общий git diff можно
обратить до интеграции на чистой базе; чужие изменения не откатывать. Публикацию,
тег и поставку выполнять только после действующей приёмки.
