# Организация работы — тест-план

## Сценарии

### REQ-01

- Given понятный факт/готовый ответ и реально сложный случай.
- When агент выбирает способ работы.
- Then простое выполняется прямо; сложное сохраняет необходимую глубину.
- Маппинг: сценарии S2/S7 — отдельные candidate-пробы; S5 — спецификация расширенного harness-прогона.

### REQ-02

- Given неизвестный стенд и две поддерживаемые конфигурации; отдельно — известное руководителю решение о редакции каталога.
- When исследователь и руководитель исполняют свои поручения.
- Then вопрос идёт L1 без угадывания; руководитель даёт известный ответ без нового расследования/approval.
- Маппинг: S1/S3, fixtures и парный пилот ниже.

### REQ-03

- Given соседняя привлекательная проблема и запрос разной глубины.
- When агент выбирает чтение/исполнение и завершение.
- Then scope удержан, описание и фактическая проверка различены.
- Маппинг: S1/S4/S6/S7; S1/S2/S7 проверены чистыми исполнениями; остальные остаются спецификациями.

### REQ-04

- Given новые команды и номерные seeds.
- When набор рендерится и агент применяет методику.
- Then роли/permissions сохраняются, новый скилл доставлен целиком; условные техники не становятся обязательным аудитом.
- Маппинг: delivery test + existing frame/conveyor guards; runtime поведение команд и live faces требует целевого прогона.

### REQ-05

- Given неизвестное допущение, изменение поведения и обязательный гейт.
- When составляются plan/test-plan.
- Then неизвестное не выдумано, проверки связаны с риском, обязательный гейт не пропущен.
- Маппинг: S5/S7; structural conveyor guards выполнены, S7 проверен на изолированном запуске, сложный S5 остаётся непроверенным.

### REQ-06 / NFR-01 / NFR-02

- Given реальный renderer, существующий проект без нового skill-файла и protected локальная рамка.
- When выполняются доставка и повтор.
- Then skill создан целиком; protected не затёрт; повтор не пишет изменений; update-map содержит новый файл.
- Маппинг: tests/unit/adapters/render/work-strategy-delivery.test.ts. Наличие текста не считается доказательством поведенческого эффекта.

## Прогоны

### Структурные проверки

Первый targeted прогон: 6 файлов / 13 тестов PASS: новый delivery test,
conveyor-skills-guard, base-frames-guard, coordinator-frame-guard,
steward-frame-guard, intake-skill-guard. TypeScript build PASS.
Итог: `env -u NO_COLOR npm run check` PASS — english surface, format, tsc,
build, 222 файла / 2027 PASS / 4 штатных skip. NO_COLOR=1 в окружении выключает
ANSI и ломает существующий TTY-тест; переменная снята только для команды проверки,
исходники цветового вывода/теста не менялись. Первый прогон также обнаружил
ошибочное форматирование model placeholders и старый счётчик payload; оба
исправлены. Delivery test теперь проверяет точные модели всех шести ролей.
Чувствительность: новый delivery test на отдельном baseline падает 2/2 из-за
отсутствующего скилла; на candidate проходит. Это structural regression sensitivity,
не заявленная история RED до написания патча.

Независимое read-only ревью полного diff: APPROVED после исправления model
placeholders и маршрута analyze-doc. Автор не подменяет этим live rollout.

Пилот не воспроизвёл заявленный пользователем дрейф на baseline. Это проверка
совместимости двух механизмов, не доказательство устранения реального инцидента
или превосходства кандидата. Нет измеренных полных токенов/latency и целевого
OpenCode runtime. Сырые частные outputs остаются вне docs/dev; выше сохранён
достаточный итог, исходные задачи/рубрика включены в tests/fixtures.

Для расширенного сравнения: чистая сессия на каждый сценарий/версию, одинаковые
model/variant/tools/rights/cache accounting, rubric до запуска; повторы и holdout
по задаче. Учитывать L0/L1/L2, доставку, продолжения и исправления до приёмки.
Проверять качество, ранний полезный вопрос, ложные вопросы, выход за scope,
пропуск существенного риска и лишние повторы; один счётчик действий не цель.
