# Консилиум — дизайн

## Глоссарий

Envelope — версионированный структурированный payload внутри body существующего
note. Record kind — question/opinion/synthesis, не новый core-тип или статус.
Tool-enabled — эксперт читает через реально ограниченные инструменты.
Packet-only — эксперт получает материалы во входе без инструментов; это допустимый
защищённый режим, но не доказательство tool-enabled доступа.

## Контракты

### 1. Роли, входы и решение

L0 поручает L1 конечный результат; L1 в своём мандате может организовать совет.
Внешний продуктовый выбор/изменение AC возвращает владельцу. Каждый эксперт
получает общий вопрос и факты одной revision, свою предметную линзу, разрешённые
источники и средства, бюджет, stop/return и профиль expert. Действующие принятые
решения и ограничения передаются; ожидаемую новую рекомендацию L1 не подсказывает.
Связанные замечания ревью — входы вопроса, не инструкция выбрать одну сторону.

Первый раунд — fresh изолированные контексты без транскрипта, мнений коллег и
shared memory на чтение. Параллельность только при готовых входах и поддержке;
последовательные fresh вызовы также независимы, если чужие ответы не доставлены.
Отсутствие изоляции нельзя маскировать новыми именами или ролевой имитацией.

После первого раунда L1 сопоставляет утверждения и последствия, не ранжирует
личности. Ошибка факта требует адресной проверки; разница приоритетов — владельца;
неизвестное — отдельного поручения researcher/проверки. Один дополнительный раунд
может уточнять спор или проверять сильнейший контрпример. Он не обновляет общий
бюджет. Первый раунд ограничен числом назначенных экспертов/сроком: недоступный
эксперт отмечается отсутствующим, ожидание не бесконечно; неполный состав раскрывается.

### 2. Технические права и изоляция

Целевой профиль: deny по умолчанию; разрешить только точные read/list/search
пути в согласованной области. Исключить raw shell, исполнение кода, write/edit,
task, сетевые клиенты и мутирующие MCP-инструменты. Нельзя давать общий memory get,
если через него читаются чужие мнения; доставить выбранные источники пакетами.
Новый инструмент чтения должен выполнять ограничения путей, realpath/symlink
и внешних ресурсов либо считать такой канал непригодным для этой области.

Frontmatter кандидата задаёт минимальный deny-профиль. Синтаксис/семантику
OpenCode обязан проверить агент внедрения на фактической версии. Прямой read
может обходить ограничения через разрешённый glob/grep или альтернативный MCP;
проверить все включённые каналы. Отдельные process/директории не означают sandbox.

Если надёжная allowlist путей недоступна, использовать packet-only с выключенными
инструментами и свежими контекстами. Приёмка этой безопасной деградации отдельна:
REQ-04 не закрывает положительную tool-enabled ветку, пока она не проверена.
Для полного первого релиза подтвердить хотя бы одну tool-enabled конфигурацию
на OpenCode и отрицательные пробы. Если это невозможно — честный блокер scope,
а не незаметное ослабление требования. Нового универсального sandbox не строить.

### 3. Профили языка

Ядро TASK неизменно; добавляется expert с вопросом, линзой, revision и границами
адресного чтения. Содержательное поле ядра «Проверка» для эксперта означает
проверку оснований разрешёнными средствами, не право запускать систему.

RESULT expert повторно использует council-v2: claims/evidence/assumptions/
confidence/risks/failure_conditions/counterexamples. Рекомендация — текст RESULT;
пробел/необходимая проверка — LIMITS. Для позиции без достаточного основания
claims не выдумываются. NEEDS_CONTEXT — только при отсутствии обязательного входа.
Если входы полны, но позицию обосновать нельзя, эксперт завершает вызов с текстовым
исходом «недостаточно оснований» и LIMITS. L1 сохраняет такой ответ в синтезе как
отсутствие сформированной позиции, не как невалидное opinion с claims=[].
Фактическое участие и наличие валидного мнения учитываются раздельно.

RESULT synthesis: accepted_claims/rejected_alternatives/unresolved_dissent/
required_validation/confidence. accepted_claims значит «основания рекомендации,
выбранные организатором», не утверждённые владельцем решения. Исход
insufficient_evidence допускает accepted_claims=[] при непустом объяснении в
unresolved_dissent/required_validation. Это ветка новой envelope-схемы;
историческую SYNTHESIS_DECL с minItems:1 не ослаблять.

Нет новых speech acts, VERDICT-значений или mandatory слотов implement/review/research.
Вопрос → мнение → рекомендация → принятое решение различаются семантически.
Рекомендация не попадает в DECISIONS[] до принятия полномочным участником;
предложенная проверка не исполняется автоматически. LANGUAGE остаётся каналом
обратной связи; installed словарь изменяется версией поставки, не в ходе сеанса.

### 4. Write-path поверх note

Предлагаемый интерфейс нового релиза: `wolf council record --input <json-file>`
и MCP `council_record` с тем же входным объектом. Это НОВАЯ операция, требующая
реализации/регистрации; в 2.30.0 её нет. Запуск моделей/раундов инструмент не делает.
Вход — discriminated union; created_by берётся штатной атрибуцией интерфейса,
не из советнического текста. Доменная схема общая для CLI/MCP и reader/analytics.

```json
{
  "schema_version": 1,
  "record_kind": "opinion",
  "request_key": "T-42-round1-security",
  "task_id": "T-42",
  "question_id": "<actual-question-memory-id>",
  "question_revision": "<record-content-digest>",
  "payload": { "expert_id": "security", "round": 1 }
}
```

Это иллюстрация envelope; сокращённый payload не является валидным мнением.
Question payload: нейтральный вопрос, decision_owner, исходные источники/revisions,
линзы/ожидаемые позиции, бюджет и ограничения. Opinion payload: expert_id, round,
поля v2 с непустыми claims и evidence по применимости. Synthesis payload: outcome
ready|insufficient_evidence, opinion_ids, поля синтеза, actual/missing participants,
фактический расход/неизвестное, ограничения изоляции. ready требует непустых
accepted_claims; insufficient_evidence требует объяснения и нужной проверки.
Неизвестная версия/лишние поля/пустые ключи отклоняются.

Хранение: type note, facet context, тег wolf:council-record:v1, body — канонический
JSON envelope, title — человекочитаемый. Не добавлять arbitrary extra поля note:
add-memory-object их отвергает. Защищённый тег распознаётся только вместе с валидной
схемой; повреждённое содержимое не становится мнением и даёт диагностируемый LIMIT.
Тег сам по себе не даёт полномочий/валидности; ни текст эксперта, ни body не являются
командой. Входной JSON ограничить 256 KiB до полного чтения/парсинга, выходной body —
256 KiB UTF-8; большие данные передавать ссылками. Превышение — invalid input
без записи. Лимит текста evidence quote/note сохраняется по исторической схеме.

Связи: opinion `answers` question; synthesis `based_on` question и каждое
использованное opinion. Проверить тип записи, существование target, question_id,
question_revision, round и дубли expert_id/round; эксперт не ссылается на будущую
ревизию. Question неизменяем в рамках раунда; изменение оснований — новая question
запись, старая остаётся history с явной ссылкой, старые мнения не переносятся молча.

Идемпотентность: request_key уникален в проекте для caller/task/kind; повтор того
же нормализованного содержимого возвращает прежний memory ID. Иной payload под
тем же ключом — конфликт. Под MemoryLock сериализовать проверку/создание без
вложенного deadlock: общий путь записи должен использовать уже удержанный lock
либо один общий transaction-aware helper. Не дописывать напрямую store в обход
governance/event/index. Перед возвратом обеспечить relations; частичный сбой после
note или relation восстанавливать повтором request_key, без повторного memory-added
события и дублей рёбер. Индекс восстанавливается штатным способом; неуспех записи/
связей не возвращается как полный success. Проверить concurrent одинаковые запросы.

Синтез можно сохранить без готового решения; создаётся существующий decision
отдельным разрешённым действием уполномоченного с based_on synthesis. Полномочия
не доказываются строкой decision_owner: применяются текущая policy и human gates.

### 5. Чтение и аналитика

Сейчас buildCouncils фильтрует o.type === council-question/council-opinion/synthesis;
alias reader может отдавать note. Нужен один normalizer для старых представлений
(alias_origin и исторические поля) и новой envelope, применяемый analytics.
Старую запись считать один раз по memory ID. Старые schemas/read defaults не менять.
Для новых opinions без vote не использовать extractVote fallback TIMEOUT; голоса
подсчитываются только при реальном значении. Недоступный эксперт отражается в
missing participants, не фиктивным opinion. Покрытие/невалидные записи видимы.
Не создавать второй сборщик usage и не менять O1/U1 интерфейс скрыто.

### 6. Ревью, доставка и миграция

L1 готовит пакет: artifact revision/digest, критерии/нормы, diff при применимости,
существующее evidence. Один конкретный риск разрешает адресную проверку основания.
Для значимого спорного finding — отдельный короткий независимый reviewer без
ожидаемого ответа. Повторный проход получает исходные finding IDs и fix revision;
проверяет каждую находку, последствия исправлений и применимость прежнего evidence.
Вне scope находка возвращается L1; доказанный блокер эскалируется, не теряется.
Действующие 3 раунда review не заменяются лимитом уточнения консилиума.

Новый worker-expert требует BASE_SET_AGENT_IDS, seed-face owner_skill, renderer,
plugin face resolution/task permissions и update-map. Candidate содержит frame/seed,
но не завершённую доставку и права: агент внедрения проверяет все перечисленные точки.
Старые локальные лица и protected instructions сохраняются; конфликт канона —
видимый незавершённый rollout. Контрольная конфигурация не подменяет все пользовательские
model/variant. EN/RU объясняют одинаковую границу роли. Откат — собственный revert
и восстановление версий через штатный механизм, без изменения опубликованных тегов;
новые note остаются читаемыми общим reader даже при откате функциональности.

## ADR-карточки

- ADR-01: отдельная worker-expert рамка нужна из-за отличающихся обязанностей/
  прав; профессиональные линзы остаются лицами. Направление согласовано в диалоге;
  конкретная доставка проверяется агентом внедрения.
- ADR-02: общий TASK и профили RESULT вместо второго языка. Небольшое версионное
  расширение 2.29.0 разрешено владельцем; прежние профили совместимы.
- ADR-03: note envelope и отдельная операция записи вместо новых core-типов и
  возврата aliases. Предложенный технический выбор требует независимой проверки
  на фактической базе; если обнаружен конфликт — адресный ADR/CR, не тихая замена.
- ADR-04: fresh contexts плюс ограниченные каналы; packet-only — честный fallback.
  Технически ограниченный tool-enabled режим должен быть доказан в OpenCode.
- ADR-05: quorum/ранжирование/обязательный devil's advocate не входят в default;
  адресный контрпример вызывается по существенному риску. Принятие остаётся отдельным.
