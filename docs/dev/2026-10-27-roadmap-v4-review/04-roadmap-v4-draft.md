# Активный роадмап v4 — черновик

## 1. Назначение и статус

**Что это.** Активный роадмап v4 проекта Mr.Wolf: порядок этапов, границы каждого этапа, зависимости
и условия возврата. Уровень документа — **роадмап**, а не детализация реализации: состав, критерии
приёмки, проверки и планы реализации живут в требованиях волн (`docs/dev/<дата>-<слаг>/requirements.md`).

## 2. Правила роадмапа

Правила взяты из обзора (§1, §3, §7, §8) и закреплены решением владельца `…085b28`.

1. **Этап — это порядок и границы, а не номер версии.** «Этапы A–I обозначают порядок и границы
   возможностей, а не номера версий» (обзор, строка 7).
2. **Номер версии назначается при подготовке релиза** относительно последнего выпущенного релиза
   (сейчас это **2.21.0**). Исторические слоты 2.16–2.20 не воскрешаются (решение `…085b28`).
   Номера версий везде полные X.Y.Z.
3. **Каждый этап допускает подрелиз с самостоятельной пользой** (обзор, строка 55) — то есть этап
   разбивается на несколько релизов, каждый из которых полезен сам по себе.
4. **Каждое требование получает место** (обзор, строка 196): ближайший этап, последующий этап, backlog
   с условием возврата, поставлено или явно отменено. Молчаливого переноса нет.
5. **Сопутствующее обслуживание не образует отдельный поздний релиз**: миграции, upgrade, доставка
   шаблонов, актуализация README и документации, release notes и необходимые проверки сопровождают
   каждый этап (обзор, строка 196).
6. **История ведётся отдельно.** Активный роадмап содержит только актуальный порядок, результат,
   границы и зависимости; история выпусков — в своей ленте (обзор, строка 194). Файлы прежних волн
   остаются как история и убираются из активной очереди версий (обзор, строка 33).
7. **Критерий «работа поставлена»** (обзор, строка 198): реализованный механизм доступен в установке
   и обновлении, отражён в реальных скиллах и рамках, имеет понятный пользовательский сценарий и
   подтверждённую приёмку. Формат данных, существующая команда и поведение Вольфа проверяются
   **раздельно**.
8. **Приоритет** определяется частотой проблемы, ценой её повторения и сложностью исправления
   (обзор, строка 5).

**Как читать этот документ.** Уровень детализации падает от §4 (этап A — ближайшая поставка, детально)
к §8 (E–I — только результат и условие возврата). Столбец «статус на 2.21.0» в §3 ссылается на строки
фактчека `01-fact-check-stages-a-i.md`; статус означает состояние кода на 2.21.0, а не намерение.

### 4.3. Критерии приёмки этапа A

Основной критерий — обзор §4.5 (строка 63): «Проверить несколько сопоставимых задач: экономия
оценивается по завершённому результату с учётом исправлений. **Короткое сообщение само по себе не
доказывает снижение расходов.**» Отсюда:

1. **Сопоставимые задачи** — одинаковые условия (модель, effort, инструменты, права, состояние кэша),
   фиксированный порядок, отдельная holdout-выборка.
2. **Экономия считается по завершённому результату с учётом исправлений**, а не по длине видимой
   записи: ручное исправление пользователем не считается самостоятельным успехом.
3. **Короткий ответ сам по себе — не доказательство.** Проверяется расход (usage, вызовы, повторные
   попытки, возвраты с приёмки), а не число символов.
4. **Порог не заявляется.** Гипотеза «≥15%» снята решением владельца; измеряется наблюдение без порога
   (NFR-06, AC-08). Непроведённое остаётся непроведённым.
5. **Сокращение служебного текста не должно ухудшать объяснения пользователю** (обзор, строка 59) —
   проверяется отдельно (AC-05, корпус `docs/ux-scenarios/`).

**Факт состояния данных на 2.21.0.** Прибор парных измерений есть
(`playground-lab/measurements/WEV-001/`), данных нет: `withArm = 0`, holdout нет, `evals/SCENARIOS.json`

## 5. Этап B — Git и сохранность работы

**Результат.** Меньше ручной рутины и меньше потерянной работы: переносимые операции вместо
непереносимых, явный ответственный за сохранность.

**Границы.**

- Входит: переносимые `inspect` / `check` / `start` / `checkpoint` / `publish` / `cleanup`, worktrees,
  handoff и полномочия (обзор, строка 44).
- **G0–G2 и G9 вводятся вместе с** checkpoint, публикацией, передачей владения и безопасной уборкой
  (обзор, строка 123). У каждой задачи есть ответственный за сохранность; если L2 не вправе коммитить,
  ответственность заранее принимает L1. Остановка прежнего писателя подтверждается **до** передачи.
  `git worktree lock` не считается блокировкой от второго писателя.
- **Очередь G3–G5 и выпуск G6–G8 пока обслуживаются действующим процессом проекта**; частичное
  внедрение политики называется прямо (обзор, строка 125).
- Проверка собирает факты и выдаёт «пройдено / нарушено / не удалось проверить», точные SHA, причины и
  разрешённые следующие действия; изменяющая операция повторно проверяет предусловия. Неизвестные
  коммиты нельзя автоматически публиковать или удалять ради чистоты состояния (обзор, строка 121).

**Зависимости.** Достаточно небольшого явного контракта задачи: репозиторий, worktree, ветка,
baseline, ответственный, стадия, требование публикации. **Полная подсистема E не является обязательным
предварительным условием** (обзор, строка 125).

**Оговорка о происхождении нумерации гейтов.** Исходный `git-collaboration-policy.md` в репозитории
**отсутствует**; обзор это признаёт (строка 11). Нумерация G0–G9 пришла из обзора и в коде, и в
документах проекта не прослеживается: ближайшие совпадения — номера находок ревью
(`docs/dev/2026-10-23-unified-update/requirements.md:719-734`) и несвязанный G7
(`docs/dev/roadmap/wave-2.16.md:20`). Статус строки B-4 — `требует проверки` (01-фактчек, строка 87;
§5.1, строки 293–297). **До начала этапа B нумерацию гейтов надо сверять с оригиналом политики**;
иначе состав этапа определяется по вторичному источнику.

**Факт состояния на 2.21.0.** В продукте нет ни одного из шести заявленных инструментов: команда
`checkpoint` удалена в 2.13 (`src/adapters/cli/removed-commands.ts:17`), в реестре команд
(`src/adapters/cli/cli-entry.ts:54-394`) нет `inspect` / `check` / `start` / `publish` / `cleanup`.
Работа с git сегодня — это методики (`using-git-worktrees`, `finishing-a-development-branch`) плюс claim
(single-writer) на артефакты (01-фактчек, строки 84–90).

## 6. Этап C — консилиум в решении

**Результат.** Сложные проблемы получают независимый разбор и следующий шаг; решение доводится до
проверки.

**Границы.**

- Консилиум **не становится обязательной стадией каждой задачи** (обзор, строка 69).
- Один первый раунд и не более одного уточняющего; продление требует обозначить новую цель.
- Число неудачных попыток — сигнал, но **не** команда «после двух ошибок собрать совет»; важен
  повтор без новых оснований (обзор, строка 85).
- Консилиум не заменяет тесты, Git-гейты, независимую приёмку или разрешение владельца; участники по
  умолчанию исследуют и дают мнения, решение совета само по себе не даёт права менять защищённые
  артефакты (обзор, строка 97).

**Таблица триггеров (кратко, обзор §5, строки 75–83).**

| Ситуация                                                                                            | Реакция                                                                  |
| --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Пользователь прямо просит консилиум                                                                 | Созвать в пределах поставленной задачи                                   |
| Две обоснованные позиции ведут к существенно разным действиям                                       | Сформулировать спорный вопрос и созвать                                  |
| После разумной попытки диагностики причина неопределённа, новые попытки повторяют прежние основания | Остановить повторение, созвать для выбора следующей проверяемой гипотезы |
| Архитектурный выбор с существенной ценой ошибки и взаимоисключающими ограничениями                  | Созвать до принятия решения                                              |
| Исполнитель и ревьюер не могут разрешить содержательное противоречие                                | Поднять спор Вольфу; он определяет необходимость консилиума              |
| Ошибка однозначно установлена тестом, Git-проверкой или документацией                               | Исправить по обычной методике                                            |
| Рутинная приёмка, простая правка, косметическое расхождение                                         | Продолжить обычный процесс                                               |

## 7. Этап D — проверяемое улучшение лиц и скиллов

**Результат.** Замкнуть цикл «жалоба → исправление → применение → проверка эффекта»: исправления
поведения проходят испытание в реальных задачах и могут быть отменены.

**D1 — испытание лиц.** Версия с отметкой «валидировать», учёт её применения, фидбек после задачи, связь
с жалобами, принятие или откат. Условие завершения: исправляемое поведение встретилось в нескольких
задачах, решение опирается на результаты, предыдущая версия восстанавливается (обзор, строки 133, 140–146).

**D2 — улучшение скиллов.** Стюард выбирает место исправления, изменяет или создаёт скилл, обеспечивает
его вызов и испытывает версию. Сначала изменение существующих скиллов, затем создание новых; новый
скилл включает условия вызова, доступность агентам, ресурсы и проверку загрузки (обзор, строки 134, 148).
D1 выпускается раньше D2 (обзор, строка 136).

**Что уже есть на 2.21.0.**

- Версионирование лица: G17 — семь обязательных полей мутации (`src/app/use-cases/create-face-version.ts:79-99`),
  журналируемая операция с восстановлением (`src/app/use-cases/face-operation.ts:275-321`,
  `wolf face recover`), `restore` / `breakglass` как откат (`src/adapters/cli/commands/face.ts:143-186`),
  тесты (`tests/unit/use-cases/create-face-version.test.ts`, `tests/e2e/face-router.e2e.ts`).
- Ровно один active и разделение полномочий Стюарда и владельца (тот же guard `:117-132`).
- **Запись фактически доставленной версии** — `.wolf/router.log` пишет `face_id`, `version`, `hash`,
  `session` (`templates/opencode/plugins/wolf-router.ts:299-303`), и мемоизация по сессии гарантирует,
  что длинная сессия продолжает использовать старую версию (`wolf-router.ts:115-131`). Это ровно тот
  факт, который просит фиксировать D1, — не хватает только связки с записью испытания (01-фактчек,
  строки 310–314).

**Чего нет.**

- **Испытания (trial) как сущности нет.** Отметки «валидировать» среди семи полей G17 нет; состояний
  «кандидат / на испытании / приостановлено» в таксономии нет; метаданных «область применения /
  условия оценки / статус испытания» нет.
- **`wolf face new` активирует неизбежно** (`src/app/use-cases/face-operation.ts:279`) — команды
  «принять / отклонить / приостановлено испытание» нет (`src/adapters/cli/commands/face.ts:96-315`).
- Фидбека «Подходит / Нужна доработка / Не могу оценить» нет; ближайший носитель — вердикт **приёмки**
  (`accepted/rejected/partial/inconclusive`, `src/adapters/cli/commands/task-eval.ts:8-47`), а это разные
  вещи.
- Связи жалобы с **применённой** версией нет: связь идёт с **созданной**
  (`templates/base/agents/steward.md:69-73`).
- **D2 почти пусто**: Стюард мутирует лица, но не скиллы (`templates/base/agents/steward.md:92`); роль
  «куратор скиллов» помечена «по мере реализации» (`steward.md:38`); `wolf scaffold skill` создаёт
  каркас без версионирования и испытания (`src/app/use-cases/scaffold-agent.ts:28,50-53,80-90`); вызовы
  скиллов логируются без версии (`wolf-router.ts:264-270`).

**Зависимости.** D1 — на существующем контуре версионирования лиц; D2 — требует расширения полномочий
Стюарда за пределы лиц, что владельцем пока не подтверждено (полномочие ограничено лицами —
`mem_20260930_styuard_avtonomno_korrektiruet_litsa_pre_a5ea58`).

**Граница.** «Не строить универсальную экспериментальную платформу» (обзор, строка 136). Для D1
достаточно небольшой записи испытания и учёта применённых версий; полный workstate и async jobs не
являются обязательными условиями испытания лиц (обзор, строка 55). Если учёта применения пока нет —
он входит в D1.

**Дефекты 2.17, влияющие на D.** Два дефекта живы в коде: sessionInject-мемоизация без TTL и окно
полу-миграции «face создан, supersede head упал» — они мешают фиксировать, какая версия фактически
применялась, то есть мешают испытанию (03-фактчек, строки 153–161, 181–182).

**Граф (направление «нужен раньше»):**

```
A ──► B
 ├──► C
 ├──► D1 ──► D2
 ├──► E
 ├──► F
 └──► (I — по условиям возврата)

B ─┐
C ─┤
D ─┼──► (G, H — по условиям возврата, независимы друг от друга)
E ─┤
F ─┘
```

**Минимальный критический путь.** A → (B | C | D1 | E | F) → (D2 | G | H | I). Ветви B, C, D1, E, F
взаимно независимы и могут идти параллельно.

## 13. Границы роадмапа и не-цели

Роадмап v4 **не решает**:

1. **Реализацию.** Состав, критерии приёмки, проверки и планы — в требованиях волн. Роадмап задаёт

2. **Детальные проверки.** Носители проверок, тест-планы и e2e-сценарии — на этапе требований волны.
3. **Публикацию релиза.** Тег, npm, GitHub Release, деплой сайта — отдельный шаг после релизного
   чек-листа (`requirements.md:127-128`, О-06); правило публикации зафиксировано отдельно
   (`mem_20261014_avtomaticheskaya_publikatsiya_reliza_git_90c115`).

   наблюдение без порога (NFR-06, AC-08).

6. **Отмену прежних обязательств.** «Исчезновение старого номера из активного плана не означает отмену
   незавершённого обязательства» (обзор, строка 33). Запреты отменяются только новым решением владельца.
7. **Реализацию `rejected.md` в новом виде.** §10.3 — предложение, не правка.

## 15. Ограничения этого черновика

1. **Тесты не гонялись.** `npm run check` / `npm test` / `npm run e2e` не выполнялись (вне границ
   подзадачи). Все утверждения «поставлено / остаток» опираются на **наличие** кода, шаблонов и
   существующих тестов, а не на их зелёный статус в этом прогоне (01-фактчек, строки 473–474;
   02-фактчек, строки 204–206).
2. **§7 обзора (backlog) остаётся без подтверждений.** Все семь направлений имеют статус «требует
   проверки»: ни одно условие возврата не подтверждено наблюдением. Совпадение условия с фактом ещё
   не наступило ни для одного направления (01-фактчек, строки 391–399).
3. **G0–G9 — без оригинала policy.** Нумерация гейтов пришла из обзора; сопоставление с оригиналом
   `git-collaboration-policy.md` невозможно, пока файл не предъявлен (см. §5 и В-02).
4. **Телеметрия — снимок от 2026-10-26.** Числа «158 013 строк», `withArm = 0`, «43% промахов» взяты из
   снимка и из `docs/dev/2026-10-23-projects-analytics/note.md`. Файл телеметрии непрерывно растёт, поэтому
   количественные утверждения — наблюдение на дату, а не константа (01-фактчек, строки 458–461).
5. **Приёмка в живом окружении не проверена.** Обзор не различал «механизм есть» и «механизм работает на
   реальной нагрузке»; фактчеки по коду этого не дают. Например, `.wolf/router.log` пишет
   `face_id`/`version`/`session`, но сколько записей накоплено в текущем парке — по коду не определяется.
6. **Внешние источники обзора проверены в том виде, в каком лежат в репозитории** (`docs/dev/roadmap/`).
   Полные `RELEASE-TASK.md` и `git-collaboration-policy.md` отсутствуют — сопоставление G0–G9 и части
   T-задач невозможно в принципе, пока файлы не будут предъявлены (01-фактчек, строки 466–469).
7. **Память Wolf читалась на 2026-10-27**, CLI 2.20.1. Идентификаторы решений приведены по фактическим
   файлам в `.wolf/memory/shared/**`; в выдаче `wolf get` есть расхождение отображения id с именем
   файла (02-фактчек, строки 210–213). Ни один id в этом документе не выдуман — все проверены `wolf get`.
8. **Пакет 2026-10-25 (61 файл) и обзор 2026-10-25** — вне git (`.external_experts_review/`), в объём
   сверки не входили; использовались только как источник трактовки термина CoD через черновик требований.
