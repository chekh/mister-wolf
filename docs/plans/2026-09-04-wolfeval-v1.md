# WolfEval v1 — план исполнения

> **Исполнителям:** REQUIRED-СКИЛЛ: используй wolf-sdd (рекомендуется) ИЛИ wolf-execute
> для поэтапной реализации этого плана. Шаги оформлены чекбоксами (`- [ ]`) для трекинга.

**Цель:** построить минимальный доказательный каркас WolfEval v1 и провести
эксперимент WEV-001 — продольную A/B кампанию «strong-baseline vs full-wolf»
на реплеях реальных догфуд-инцидентов, с оценкой конечным состоянием через
скрытые оракулы. План исполняет спеку
`docs/superpowers/specs/2026-09-04-wolfeval-v1-design.md` (далее «спека», §-номера — её разделы); план спеке не противоречит и отличается только бюджетным решением координатора (см. раздел «Бюджет сессий»).

**Архитектура:** конвейер «реплей → эпизод → оракул → скоринг → отчёт».
Инфраструктура замирена (П8): playground-lab (reset/карты/реестр), лаунчер
`playground-lab/scripts/wolf-session.sh` (hang-guard 0/124/1, sessions.jsonl с
весовыми токенами: `weight = input + 0.1×cache_read + 5×output`), P1-телеметрия —
вторичный канал (контакты `mcp_call` с памятью). НОВОГО мерительного стека НЕТ —
добавляются только `benchmarks/wolfeval-v1/` (протокол, фикстуры, оракулы,
scorers) и харденинг лаунчера (F25). Код TS не пишется — bash, markdown, git.

**Стек:** bash, markdown, git, wolf CLI (пин — `environment-lock.json`), opencode
headless через `wolf-session.sh`.

**Важно всем задачам:**

- **Бюджет сессий — ЖЁСТКИЙ потолок 40**: плановых 38 + резерв ретраев 2
  (арифметика ниже; единица бюджета — запуск лаунчера = строка sessions.jsonl;
  эпизод E5 = 2 запуска). Превышение невозможно: ретраи сверх резерва НЕ
  запускаются, повтор помечается invalid (спека §7.4).
- **Оракулы и скореры пишутся и хэшируются ДО любых LLM-прогонов.** Порядок фаз
  это гарантирует: Фаза A (WA1–WA8, 0 сессий) → Фаза B (A/A, 6 сессий) → Фаза C
  (A/B, 32 сессии). Карточка эксперимента после старта НЕ редактируется
  (гейт E4 п.1; спека §3.4).
- **Запреты (спека §10 — осознанно отложено в roadmap):** никакого второго мерительного стека; НЕ
  включать pilot-144, матрицу абляций, WEV-002, Council-бенчмарк, NoiseTax-контроли,
  LLM-as-judge, human-minutes, unseen holdout-варианты, campaign_id в P1.
- **Волчьи команды записи — только координатор в main-репо** (память пишется в
  cwd; воркер из worktree/инстанса записал бы не в ту память). Воркеры план НЕ
  пишут в память Wolf.
- **Прогоны только live**, dry-режимов нет; все прогоны (включая невалидные)
  публикуются в `runs.jsonl` (гейт E4 п.7, 9).
- **Коммит после каждой задачи.** Инстансы-расходники живут в системном tmp
  (`/tmp/wolfeval-v1/…`, правило mem_20260901), в git — только методика,
  протоколы, измерения и traces.
- Перед задачами Фаз B/C сверять F12-контроль: `readlink -f "$(which wolf)"`
  совпадает с записанным в `environment-lock.json`.

## Бюджет сессий (жёсткий)

| Статья                      | Формула                                              | Сессий |
| --------------------------- | ---------------------------------------------------- | ------ |
| Фаза B — A/A-пара           | 2 клона WOLF-руки × 3 эпизода (E1–E3)                | 6      |
| Фаза C — WEV-001 (A/B)      | 2 руки × 2 повтора × 8 запусков (7 эпизодов; E5 = 2) | 32     |
| **Итого плановых**          |                                                      | **38** |
| Резерв ретраев (спека §7.4) | ≤1 на невалидный прогон                              | ≤2     |
| **Потолок**                 |                                                      | **40** |

Единица бюджета — запуск лаунчера (одна headless-сессия = одна строка
sessions.jsonl). Эпизод E5 механически состоит из двух запусков: обрыв
planned_kill (короткий, работа до фиксированной точки) + восстановительная
сессия в чистом контексте — это и есть механика обрыва/восстановления, оба
запуска обязательны и учтены в формуле выше (8 запусков на кампанию при 7
эпизодах).

**Правило координатора при превышении бюджета: сокращать повторы, НЕ эпизоды.**
Спека §7.2 задаёт 3 повтора на руку: 2×3×8 = 48, плюс A/A 6 = 54 > 40. Поэтому
WEV-001 исполняется в **2 повтора** (2×2×8 = 32). Последствия зафиксированы
честно, до запуска:

- 2 кластера на руку вместо 3 — заявленно **разведочный сигнал**, CI bootstrap
  шире (граница, а не спрятанное, — спека П6);
- интерпретация MPE (спека §7.3) даунгрейдится с «направленный сигнал при 3
  кластерах» до «направленный сигнал, обкатка инфраструктуры»;
- третий повтор — за бюджетом v1 (кандидат в первое расширение после A/A-чистоты,
  ср. условие возврата pilot-144 в §10);
- **A/A сокращена с 3 пар (спека §7.1/§7.4: «устойчивая асимметрия … во всех
  3 парах») до 1 пары** — то же бюджетное решение; следствие: на одной паре
  критерий «устойчивой асимметрии» не различим с шумом, сила проверки прибора
  ниже заявленной спекой; восстановление 3 пар — вместе с третьим повтором,
  кандидат в первое расширение;
- эпизоды (E1–E6b) не режутся: продольная механика накопления — предмет
  измерения, сокращение эпизодов превратило бы кампанию в набор одиночных сессий
  (анти-урок X1/X2, спека §1).

**Обоснование выбора реплеев (спека §4.1–§4.3, П3):**

- все 7 эпизодов — реплеи реальных инцидентов: сюжет гарантированно реалистичен,
  ответ известен заранее;

## Метрики (из sessions.jsonl + оракулов; спека §6)

- `weight` / `secs` / `exit` — из `sessions.jsonl` лаунчера; итерации =
  tool-вызовы из лога сессии.
- Campaign success — бинарно по `campaign-audit.sh` (все эпизодные оракулы PASS +
  проверки инстанса зелёные).
- **CPSC** = Σ weight всех сессий повтора / число успешных кампаний руки.
- **CFR** — доля повторов с ≥1 критическим событием; классы фиксированы до
  запуска (ложная приёмка / повреждение защищённых файлов / superseded-правило
  E4 / scope violation / потеря данных), НЕ усредняются — каждое разбирается.
- Вторичные: first-pass, wall-clock, токены, duplicate-work, stale-usage,
  memory-contact (`mcp_call`), симметрия E6a/E6b.
- Никаких LLM-суждений, никаких human-minutes (П5).
