# Wolf: концепция

> **Память — носитель. Процессы — суть. Агенты — форма. Инструменты — руки.**
> И руки накапливаются: каждый полезный скрипт становится постоянным ресурсом проекта.

**Версия:** 3.1 · **Дата:** 2026-08-31 · **Статус:** утверждена владельцем
**Предыдущая версия:** [archive/concept-2026-08-18-v2.0-memory-substrate.md](archive/concept-2026-08-18-v2.0-memory-substrate.md) («память-субстрат + выборочная оркестрация»; эмпирика wolf-experiment остаётся каноном в своих отчётах)

Сдвиг парадигмы против предыдущей версии: Wolf — не «память с дополнениями», а **процессы и новая организация работы агентов, опирающиеся на единую память проекта**. Память — носитель, но суть продукта — то, как агенты работают, и то, что их работа накапливается, а не испаряется.

---

## §1. Проблема

| №   | Проблема                                    | Проявление                                                                          |
| --- | ------------------------------------------- | ----------------------------------------------------------------------------------- |
| П1  | Контекст теряется между сессиями            | агент начинает с нуля                                                               |
| П2  | Опыт не переиспользуется                    | повторные задачи решаются заново: текстовые рассуждения + новые одноразовые скрипты |
| П3  | Документы проекта живут отдельно от агентов | единая точка правды отсутствует                                                     |
| П4  | Накопленное становится шумом                | память растёт, ценность падает                                                      |

### §1.1. Для кого

**Портрет:** AI-native engineering-команды и сильные индивидуальные разработчики, использующие агентов как постоянную рабочую силу над долгоживущим проектом: много сессий, повторяющиеся классы задач, значимая цена ошибки и дрейфа.

**Анти-портрет:** разовые задачи, правки одного файла, короткие проекты, случайное использование ИИ — и все, кого устраивает встроенный workflow платформы.

**Критерий окупаемости:** иерархия, процессы и память — это накладные расходы; они окупаются там, где стоимость дрейфа, забывания и повторной работы превышает стоимость координации. Границы применимости — §10.

## §2. Архитектура: четыре слоя

| Слой            | Содержание                                                                                                                                                                                  | Состояние                                                    |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| **Память**      | Единая точка правды: _всё есть память_ — решения, уроки, правила, документы проекта, процессы, инструменты. Версионированность (supersede-цепочки), связи (relations), атрибуция (actor)    | зрел: CLI + MCP, таксономия, FTS-поиск                       |
| **Процессы**    | Протоколы работы: bootstrap (подключение к проекту), cold-start (`call`→`brief`), диспетчеризация и приёмка по брифам, `complain`-канал, checkpoint/wrap-up, периодическая обработка знаний | частично в продукте, частично в практике; оформление впереди |
| **Агенты**      | Тонкие рамки + лица (playbook'и — методика в памяти). Роли, диспетчеризация, доставка в платформы                                                                                           | доказано PoC #1–4                                            |
| **Инструменты** | CLI и MCP — руки, приводящие память и процессы в действие                                                                                                                                   | зрел; ревизия surface — в плане                              |

Слои — не стопка, а **петля**: агенты исполняют процессы; процессы читают и пишут память; инструменты приводят всё в действие; результаты работы возвращаются в память как новые знания и инструменты.

## §3. Ключевые структуры

Структуры, определившиеся в ходе практики и обсуждения (2026-08-28…29).

### §3.1. Цикл жизни знаний

Память не «write-once»: **накопление → периодическая обработка → обновлённое знание**. Обработка затрагивает _часть_ памяти (по триггерам), не всё сразу: обобщение однотипного, актуализация устаревшего, забывание неиспользуемого (decay по пробегу).

### §3.2. Конвейер активации

Единый для всего, что меняет поведение или знания:

```
draft → Sandbox Replay → активация → пост-аудит владельца → доставка
```

Создание — без пре-аппрува; доставка пользователю — только после зелёного прогона. Порядок проверен (спека самообучения §2.5 — `docs/superpowers/specs/2026-08-26-self-learning-design.md`; PoC #3).

### §3.3. Канон и экспозиция

Истина всегда в памяти (playbook, tool-объект). Платформенные носители — скиллы, команды, MCP-тулы — **генерируемые отпечатки**: регенерируются scaffold'ом после каждой версии канона. Реверс-импорт внешних артефактов — с пометкой «непроверенный».

### §3.4. Атрибуция и статусы

Каждый объект памяти имеет автора (actor), статус жизненного цикла и, для изменяющих объектов, цепочку версий (supersede). Авторство мутаций агентов обязательно (`steward:<лицо>`).

## §4. Стюард — фоновый агент контура

Канон терминологии (спека базовых наборов `docs/superpowers/specs/2026-08-31-base-sets-design.md`, D5): **рамка / лицо / мутатор / доставка** — единый принцип для всех агентов.

- **Рамка** — статична: роль, границы, запреты, протокол контура лица; меняется только sync'ом с новой версией канона.
- **Лицо** — мутирующий контекст = playbook + триггер + конвейер + экспозиция. Нет playbook'а → агент безликий (статичное поведение) — это данные, не структурное исключение.
- **Мутатор** — всегда Стюард (жалоба → новая версия playbook'а через supersede); **самомутация агентов запрещена**.
- **Доставка** — per-harness: plugin-inject / pull / bake-in.

**Инвариант:** лица могут быть у всех агентов; мутатор один — Стюард.

### §4.1. Место

Стюард **никогда не выходит на первый план**: не ведёт сессий, не отвечает владельцу напрямую, не primary-агент. Вызывается вложенно; виден владельцу только как артефакты, прошедшие конвейер активации (§3.2).

### §4.2. Каналы вызова и инвариант

| Инициатор                   | Пример                                                      | Статус                |
| --------------------------- | ----------------------------------------------------------- | --------------------- |
| Координатор (Mr. Wolf, L0)  | жалоба `complain` → Наставник; порог паттернов → Архивариус | Ф22                   |
| Воркер-агент в своей сессии | apprentice получил жалобу → вложенный вызов Стюарда         | **работает** (PoC #3) |
| Автоматика                  | чекпоинт пробега, объёмный порог, decay-обход, health-check | Ф26 + исследование    |

**Инвариант:** вызов Стюарда — всегда **исполнение правила, записанного в памяти**, а не свободная инициатива LLM. Каждый вызов имеет триггер-основание в логе. _Матрица вызова_ («кто на какой триггер вызывает какое лицо») — часть governance.

_ФN — номера фаз контура самообучения (roadmap-v3, Фаза D)._

### §4.3. Лица — открытый реестр

**Лицо = playbook + триггер + конвейер + экспозиция** (формула §4, канон спеки base-sets). Лица могут добавляться; новое лицо — новый playbook, не новый агент. Рамка статична (sync по канону); лица эволюционируют через supersede playbook'ов; мутатор — только Стюард (§4), доставка — per-harness.

| Лицо             | Объект работы                        | Триггер                       | Статус                                                  |
| ---------------- | ------------------------------------ | ----------------------------- | ------------------------------------------------------- |
| **Наставник**    | методики агентов (playbook'и)        | жалоба                        | **работает** (PoC #3: мутация playbook v3→v4 по жалобе) |
| **Библиотекарь** | инструменты (tool-объекты, SKILL.md) | порог реестра / повтор задачи | спроектировано (исследование tools-as-skills, 6/6)      |
| **Архивариус**   | знания памяти                        | объём / пробег                | спроектировано (Ф21–22, Ф26)                            |

Общий механизм лиц: Analyzer-Worker → draft → конвейер §3.2. Каждое лицо доступно платформе как скилл (§3.3).

## §5. УТП: организация → память → инструменты

### §5.0. Постоянная проектная организация — УТП-0 _(консилиум + L0/L1/L2)_

Wolf — **постоянная проектная организация из временных агентов** — якорная метафора позиционирования (категория **Agentic Project Governance** — заявляемая, новая, не существующая). Трёхуровневая организация работы + консилиум — УТП-0, в позиционировании раньше памяти: **L0** (координатор) не исполняет — владеет постановкой и приёмкой; **L1** (executor) владеет поставкой; **L2** (воркеры) — ограниченные операции в чистых сессиях; **консилиум** — на развилках. Агенты приходят и уходят — организация и её память остаются.

Зрелость элементов — по образцу §4.3:

| Элемент          | Зрелость                                                                                                  |
| ---------------- | --------------------------------------------------------------------------------------------------------- |
| **L0/L1/L2**     | применяется на практике — догфудинг в собственном репо; количественного сравнения с одиночным агентом нет |
| **Консилиум**    | спроектирован; типизированные артефакты (кворум, сохранение несогласия) — впереди                         |
| Опорные механики | рамки/лица, самомутация через Стюарда, роутинг — доказаны PoC #1–4 (§9)                                   |

**Статус доказательности:** УТП-0 подтверждено практикой качественно — мы уже работаем по такому концепту (догфудинг в этом репо), — но измерений для сравнения с одиночным агентом ещё нет; они запланированы в роадмапе (эксперимент **E1**, Фаза E: vanilla vs Wolf + ablation). До данных E1 позиционирование УТП-0 — проверяемое утверждение, не измеренный факт. Издержки иерархии известны и компенсируются: fast-path для тривиальных задач у Executor, проверяемые артефакты приёмки, метрики L1.

Категория заявляется, а не констатируется: до вложений в её продвижение — план валидации (поисковый спрос, A/B формулировок README, реакция комьюнити).

### §5.1. Обновляемая институциональная модель работы проекта _(лицо: Архивариус)_

Тезис «конкуренты дают write-once память» устарел: lifecycle-механики знаний уже появляются у платформ — Copilot Memory (citations + revalidation против текущей ветки + decay 28 дней; подтверждено доками). Это превью одного вендора: такие механики не повсеместны и далёко не у всех — но и лидерства Wolf в lifecycle знаний концепт не заявляет. Позиция Wolf: local-first, vendor-neutral, работает с любыми агентами; главный дифференциатор УТП-1 — **процессное состояние работы**: брифы, рабочие нити, чекпоинты, совет, эскалации, независимая приёмка. Формула УТП-1: **обновляемая институциональная модель работы проекта** — состояние процесса плюс знания с lifecycle (§3.1). На языке пользы: пожаловался на ошибку агента — следующая сессия её не повторяет.

Направление подтверждено исследованием самообучения: 14 фокус-областей (portées) внешнего аудита; методы контура — ExpeL (накопление опыта), STOP (самооптимизация промптов), GEPA (эволюция промптов по метрике), AFlow (поиск оптимального workflow) — реализация в Ф20–26.

### §5.2. Растущие инструменты — УТП-2 _(лицо: Библиотекарь)_ — Code-as-Reasoning

**Агент рассуждает исполняемо**: гипотеза выражается кодом, факт — выводом запуска, ошибка — структурированным сигналом, а не тупиком. LLM — контроллер; детерминированное — делегируется среде исполнения.

- Удачное рассуждение-скрипт **кристаллизуется** в постоянный инструмент: вызов инструмента = переиспользование уже проделанного мышления (экономика подтверждена: Voyager — исследование lifelong-learning агентов, 2023 — рост переиспользования 15.3×; наш PoC — один checker переиспользован ×6).
- Дисциплина **search-before-write**: перед написанием скрипта — поиск готового в памяти.
- Носитель — **гибрид**: tool-объект каноничен в памяти (контракт, версии, счётчики использования), SKILL.md — генерируемая экспозиция (§3.3). Актуализация — по 5 триггерам (порог сигнала, health-check holdout, decay, deprecation, событийная инвалидация).
- Границы: исполнение — trust boundary (Sandbox Replay, read-only зоны); критерий сохранения инструмента — повторяемость задачи (N≥2), иначе одноразовая логика остаётся одноразовой.

## §6. Принципы

1. **Files remain canonical** — файлы первичны, память — индекс и интерпретация
2. **Память ≠ свалка** — запись без обработки есть техдолг знания; обработка — часть продукта (§3.1)
3. **Верифицируемое рассуждение** — исполняемая проверка предпочтительнее текстового рассуждения (§5.2)
4. **Атрибуция** — actor и статус у каждого знания; авторство мутаций обязательно (§3.4)
5. **Автономия по пробегу** — read-only зоны, матрица «кто что меняет», уровни B→B+→C (B — пре-аппрув человеком, B+ — пост-аудит дайджестом, C — автономия по метрикам доверия; детали — спека самообучения §14), возврат при ≥30% отмен
6. **Мультиплатформенность** — Wolf не знает внутренностей платформ; платформенные адаптеры — отдельные «нити» (линии развития по платформам; opencode-адаптер Ariadne: директория-«дом» зарезервирована в репо, вынесение по критериям: использование вне Wolf · второй платформенный клиент · npm-публикация · протечка в `src/`)

## §7. Интеграционные механики

**§7.1. Доставка методик** — три механизма по надёжности:

1. Плагин-инжекция в system-промпт — детерминированная, ≈цена статики — **основной**
2. Рамка + `wolf search` — вероятностная, ~2× дороже — fallback
3. Статичная рамка — дёшево, мертва к эволюции — минимальные платформы

**§7.2. Роутинг моделей** — routing-объекты = класс «параметры» в памяти; исполнитель — платформенный адаптер запуска; смена модели на лету доказана (PoC #4: одна сессия, glm-5.3-flash → glm-5.2).

**§7.3. Платформы** — рамки per-platform, содержимое общее; подключение адаптера через конфиг платформы (`plugin: [...]`); зависимость однонаправленная: адаптер → Wolf, никогда наоборот.

**§7.4. Bootstrap — подключение к проекту.** Подключение Wolf к любому проекту — лёгкое (одна команда), быстрое (минуты до первого полезного `brief`), адаптивное (под факты проекта, не заливка шаблона). Двухслойная механика:

| Слой       | Кто                                         | Что                                                                                                                             |
| ---------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Скелет     | `wolf init` (инструменты, детерминированно) | `.wolf/`, config, индекс, permissions-профиль, дефолтная таксономия                                                             |
| Наполнение | **Стюард** (по вызову координатора)         | скан проекта → регистрация документов → черновики правил-конвенций → стартовая таксономия и рамки (scaffold) → стартовая память |

Фронт — **координатор (Mr. Wolf)**: владелец не общается со Стюардом напрямую (§4.1). Всё созданное проходит конвейер активации (§3.2); владелец утверждает пакетом одним проходом. Метрика качества bootstrap: время до первого полезного `brief`, полнота стартовой памяти, доля черновиков, принятых владельцем без правок.

## §10. Что не делает Wolf

Редактирование кода как проектная функция · IDE-интеграция · веб-интерфейс · распределённая работа · оркестрация общего назначения (только протоколы, доказанные практикой) · durable execution runtime.

Durable runtime — честно: сегодня Wolf работает в attended-режимах; восстановление смысла работы после перерыва — через checkpoint/recap; физического crash-recovery (leases/heartbeats/recovery) **нет**. Сторонний durable-runtime (например, LangGraph/ADK) — кандидат на будущее; контракт стыковки — Wolf Protocol (задача Фазы B роадмапа, ещё не реализован).
