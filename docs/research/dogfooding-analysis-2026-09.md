# Dogfooding-анализ: реальное использование Mr.Wolf на localhost (сентябрь 2026)

Дата: 2026-09-27. Анализ выполнен координатором (Mr.Wolf L0) по прямому поручению владельца после двух системных сбоев спавна executor-воркеров (Task cancelled ×2, артефактов не оставили).

## 1. Методология

**Вопрос исследования:** как реально используется Wolf во внешних (не dogfood) проектах на этой машине, что работает, что создаёт сложности, куда двигать развитие.

**Источники (все — только чтение):**

| Источник                                           | Что дал                                                                                    |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Реестр Wolf `~/.config/wolf/projects.yaml`         | 16 зарегистрированных корней проектов, даты инициализации                                  |
| Скан `~/Development`                               | следы Wolf: `.wolf/`, `wolf`/`mr-wolf` в `AGENTS.md`, `.opencode/package.json`             |
| Конфиг opencode `~/.config/opencode/opencode.json` | MCP `mr-wolf` подключён глобально через локальный билд `mister-wolf/dist/bootstrap/mcp.js` |
| `.wolf/memory/` проектов                           | объекты (md + YAML frontmatter), `events.jsonl`, `relations.jsonl`                         |
| `.wolf/metrics/session-metrics.jsonl`              | телеметрия: `mcp_call` (tool_name, outcome, duration), `delivery`, `memory_stage`          |
| `.wolf/metrics/patterns.jsonl`                     | срабатывания delivery-паттернов                                                            |
| `.wolf/router.log`                                 | инъекции playbook'ов при спавне субагентов (agent-id × hit/miss)                           |
| `AGENTS.md` проектов                               | как Wolf встроен в протоколы агентов                                                       |

**Ограничения метода:**

- телеметрия `session-metrics` покрывает период с wolf 2.7/2.9 (у Tender с 2026-09-07); ранняя история (июль–август trading-signal) видна только по `events.jsonl`;
- `session_id`, `modelID`, `agent` в телеметрии почти всегда `null` — связка «вызов → сессия → модель» невозможна (сам по себе важный вывод, см. §5.4);
- CLI-вызовы `wolf call/add/...` фиксируются в телеметрии как `actor: user:cli` без имён команд — детальная CLI-статистика недоступна, оценена косвенно (delivery-события = `call`);
- анализ одного хоста, один пользователь, 5 реальных проектов — выборка мала для статистики, но достаточна для качественных паттернов;
- zsh-скан не покидал `~/Development` (по договорённости); проекты вне этой зоны могли быть пропущены.

**Read-only дисциплина:** чужие проекты не изменялись (детали в §9). SQLite чужих проектов не открывался вовсе — все данные из flat-файлов (`.md`, `.jsonl`, `.yaml`, `.log`), т.к. память Wolf v2 — файловая, БД не используется для памяти.

## 4. Таксономия: динамика и расползание

**Ответ на вопрос «растёт ли таксономия»: да, расползается.**

| Проект            | Объектов | Уникальных тегов | Одиночных тегов | Доля одиночных |
| ----------------- | -------- | ---------------- | --------------- | -------------- |
| Tender            | 268      | **442**          | 285             | 65%            |
| trading-signal    | 250      | 249              | 178             | 71%            |
| Stratographer     | 112      | 143              | 110             | **77%**        |
| Мартовский заяц   | 57       | 71               | 47              | 66%            |
| photo-restoration | 24       | 30               | 24              | 80%            |

- Тегов суммарно больше, чем объектов (442 тега на 268 объектов у Tender). Большинство тегов употреблены один раз → **поиск по тегам почти бесполезен как навигация**, таксономия не сходится к словарю.
- **Системный шум:** теги `wolf-init`, `onboarding-v2`, `wolf-review`, `worker-implementer playbook`, `steward:наставник`, `session-summary`, `document`, `complaint` генерируются самим Wolf'ом и лежат в общем пуле с пользовательскими (`eis`, `deploy`, `docker`, `mt5`, `wine`).
- Смысловые дубли: `бэкфилл`/`backfill`, `кеш`/`cache` (ru/en сосуществуют).
- **Типы объектов стабильны** (директории-каноны: decisions/lessons/rules/blockers/playbooks/...), но события содержат свободные типы: `council-question`, `observation`, `context`, `document-ref`, `session-summary`, `report` — номенклатура типов в событии шире канона директорий.
- Динамика: теги не «оседают» со временем проекта — у самого долгого (trading-signal) доля одиночных не ниже, чем у однодневного спринта. Самопроизвольной конвергенции нет.

### 5.2 Скрипты/тулы

- Реестр тулов реально существует и используется в **одном** проекте (Tender): `fetcher_status_report` прошёл v1 → v2 → v2.2 за 11 дней, каждая версия — объект памяти со статусами (deprecated → deprecated → candidate), скрипт в `.wolf/tools/`, докстринг содержит контракт (read-only, mode=ro, --json). Это зрелый паттерн productize-кандидата.
- `wolf tool list` вне dogfood не подтвердим телеметрией (CLI-вызовы не логируются с именами команд), но tool-объекты в памяти есть.
- У Tender в `.wolf/` также живут прикладные артефакты (downloader.py, manifest.json 54 МБ, analyze.log, router.log 1 МБ) — `.wolf` используется как общий каталог инфраструктуры конвейера, не только память.

### 5.3 CLI vs MCP

- **Основной канал потребления — CLI `wolf call`:** 15 172 (Tender) + 13 912 (trading-signal) доставок против 564/184 MCP-вызовов. На каждый MCP-вызова у конвейерных проектов приходится ~25–75 call-доставок.
- **Основной канал записи — MCP** (`agent:mr-wolf`, `agent:mcp` доминируют в акторах событий).
- Внутри MCP топ-4: `list` (447 суммарно), `add` (285), `search` (279), `get` (193). Хвост: `create_decision` (39), `transition` (13), `brief` (19), `create_rule` (2!), `recap` (7), `resolve_blocker` (2).
- **Уникально мало используются:** create_rule, recap, create_article, create_info_request, scan (MCP), start/conclude thinking — не подтверждено ни одним вызовом во внешних проектах.

### 5.4 Телеметрия

- **Есть и содержательна** (вопреки опасению): `mcp_call` (tool, duration, outcome, actor, wolf_version), `delivery`, `memory_stage`, `pattern`, плюс router.log. Покрытие с wolf 2.7/2.9 (сентябрь).
- Пробелы: `session_id`, `gen_ai.modelID`, `orchestration.task` почти всегда null → нельзя связать вызов с моделью/сессией/задачей; CLI-команды не атрибутируются по имени; delivery не логирует размер инъекции (токен-налог не измерим напрямую).
- MCP-ошибки: 40/564 (7%) у Tender — есть ненулевой baseline отказов.

### 5.5 Delivery-механика подробно

- Уникальных доставляемых памятей катастрофически мало: **3 (Tender) и 4 (trading-signal)**. Топ-2 у trading-signal покрывают 95% доставок.
- Т.е. `call` стабильно доставляет один и тот же микро-набор «конституции» перед каждым спавном — тысячи повторных инъекций одного контента. Работает как спроектировано (важность ≥ порога), но управляемости набора нет (ротация, cap по токенам, релевантность треду — отсутствуют).

### 5.6 Router playbook'ов

- Механика: при спавне субагента router подбирает playbook по agent-id и инъектирует.
- **Miss-рейт: Tender 46%, trading-signal 76%** (оба — почти целиком agent-id `executor-lead`, для которого playbook'а в дефолтном наборе нет: набор содержит `worker-implementer/researcher/reviewer`, `mr-wolf`, `наставник`, `жалобный протокол`).
- У Зайца (mr-wolf 163 hit / executor-lead 31 miss) и photo (5/0) — miss-рейт 16%/0%: там, где работает связка mr-wolf → worker-\*, механика подтверждена.
- Playbook-набор копируется при init (6 одинаковых файлов во всех 5 проектах); эволюция локальна (Tender добавил worker_reviewer_playbook_v2 — единственный случай мутации набора).

## 6. Трения и сложности (с доказательствами)

1. **Router miss для `executor-lead`** — 46–76% инъекций не доставляются главному связующему агенту конвейера (router.log: `agent-id=executor-lead playbook=miss injected=no` ×6 432 у Tender, ×5 973 у trading-signal). Систематическая потеря главной механики передачи знаний.
2. **Тег-шум и расползание таксономии** (§4): 65–80% одиночных тегов, ru/en дубли, системные теги в общем пуле. Поиск/навигация по тегам деградировала у каждого проекта.
3. **Машинная память вытесняет курируемую:** documents 101 + scan.updated 501 события у trading-signal; session-summary создаются каждой сессией (35 у Tender). Без сегрегации curated/machine список и поиск замусориваются (memory_class есть в схеме, но delivery/search его не различают — в телеметрии следов фильтрации нет).
4. **Повторные инъекции одного контента:** 12К+ доставок одних и тех же 2–3 памятей (§5.5) — токен-налог на каждый спавн, управление набором отсутствует.
5. **Призрак ZetaDocs:** AGENTS.md инструктирует `mr-wolf_*`, памяти нет (`.wolf` = только cache/). Протокол обещает то, чего система не доставляет; валидации при рендере AGENTS.md нет.
6. **Реестр не переживает перенос проекта** (trading-signal: память с июля, реестр с 09-22) и **засоряется эфемерными песочницами** (7 tmp-записей в projects.yaml), GC отсутствует.
7. **Гигиена репозитория и секретов:** `.wolf` не в .gitignore у 3 из 4 git-проектов (Stratographer, Заяц, trading-signal, photo-restoration — не ignored; только Tender игнорирует); при этом в `Tender/.wolf/` физически лежит `.creds` и прикладные данные (manifest 54 МБ) — один `git add -A` от утечки.
8. **MCP-ошибки 7%** (40/564 у Tender) — небесплатный baseline отказов, причина не видна в телеметрии (нет поля ошибки).
9. **Телесно-метрические пробелы** (§5.4): session/model/task null — продукт-аналитика по своим же данным невозможна.

## 7. Что работает хорошо

1. **`wolf call` как конвейерная конституция** — главный подтверждённый сценарий: 29К доставок в двух проектах, стабильный микро-набор правил реально держит дисциплину конвейера (правила «отчёты владельцу», «защиты после edge-lim» доставлены тысячекратно и живы месяцами).
2. **Onboarding-рендер AGENTS.md** — 5/5 реальных проектов имеют wolf-сгенерированный протокол в AGENTS.md (`<!-- wolf:onboarding v2 -->`); канал дистрибуции протокола работает автоматически.
3. **Lesson-культура** — уроки стали самым массовым курируемым типом (105/65/39): агенты охотно фиксируют операционные уроки («rtk allowlist не содержит ssh…»).
4. **Полный lifecycle у зрелого проекта** — Tender использует supersede/resolve/answer/open + версионируемые тулы: схема жизненного цикла достаточна для реальной эволюции знаний.
5. **Тул-реестр как паттерн** (Tender) — контракт в докстринге, версии в памяти, supersedes-цепочка: прижился без специального product-обеспечения.
6. **Оркестрационный хаб** (Stratographer) — `.wolf/orchestration/` как обменник отчётами субагентов: неожиданный, но осмысленный сценарий (единая точка обмена, живёт рядом с памятью).
7. **Память пишут агенты, не человек** (акторы agent:\* ≫ user:cli) — цель «память без человеческого труда» достигнута количественно.
