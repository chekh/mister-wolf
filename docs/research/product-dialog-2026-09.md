# Продуктовый диалог: протокол решений — 2026-09-29

Владелец × координатор (продуктовая роль). Основа: консилиум `product-consilium-2026-09.md` (3 волны). Каждая тема согласована владельцем дословно; формулировки ниже — совместный итог. Источник для спеки следующего цикла.

## Т1. Таксономия: 7 типов + фасеты с цветом (релиз 2.13, без ожидания soak)

- Выжившие типы: `rule`, `lesson`, `decision`, `thread`, `complaint`, `tool`, `note` (новый универсальный).
- 19 типов схлопываются в `note` + фасет; blocker/info_request/question — статусы `thread`.
- Фасеты: закрытый словарь 7–10 значений (первый: «характер записи» — howto/pitfall/context/metric/history), выбор из списка, свободный ввод запрещён. Цветовая подсветка фасетов в CLI-выводе и списках агентов.
- Миграция: карта «старый тип → куда и с каким фасетом», отчёт перед выполнением, подтверждение, старые каталоги — алиасы.

## Т2. Честный интерфейс команд (2.13, одной волной с Т1)

- Каноническая пятёрка: `add` / `get` / `edit` / `search`-`list` / `archive`.
- `create` удаляется СРАЗУ, без периода синонимов (осознанная цена: существующие скрипты получают понятную ошибку с подсказкой).
- `edit` правит заголовок/текст с двухстрочным diff-аудитом в журнал; замена (supersede) — только для смыслных смен.
- `relation list --of` / `relation remove` — читаемый граф (предусловие навигации после Т1).
- Группы команд типов генерируются из таксономии автоматически; ручной справочник (1400 строк) умирает.
- «Окна состояния» сливаются до трёх: `recap` (вход в сессию), `brief` (снимок проекта), `analytics --view` (все числа; эффективность и дашборд — значения --view). Старые имена — скрытые синонимы.

## Т3. Доставка 2.0 (2.12–2.13)

- Наблюдаемость: строка «доставок N, промахов M, топ промахов» в `recap`; панель доставки в `analytics` (топ доставляемых, miss-rate по ролям, средний размер).
- Сессионная дедупликация: запись доставляется в сессию один раз; повторно — только при изменении контрольной суммы текста.
- Мягкий лимит: предупреждение при >20% контекста сессии (настраивается, не блокирует).
- Метрика «доля применений» — индикатор для трендов и сравнения записей, не приговор; подсветка «доставляется много, применений не видно» — фильтр гнили конституции.
- Принцип: повторы для новых исполнителей — норма; повторы внутри сессии — налог.

## Т4. Инициализация 2.0 (2.14–2.15; объединена с «осторожный init на живом проекте»)

- Обязательность файлов (readme/манифест/agents.md) снята: пустой проект — штатная ситуация. Волф создаёт нужный минимум сам; создание файлов в корне — по явному согласию в диалоге.
- Интервью при пустом проекте: **конфигурируемый список вопросов** (в конфигурации, без правки кода); дефолт — один развёрнутый вопрос «зачем проект, цель, как будем работать»; краткий ответ допустим — Волф разберётся по ходу.
- Отдельный шаг «доинформирования» НЕ вводится: устарение паспорта лечится самой работой памяти.
- Неинтерактивный путь: те же ответы флагами/файлом; полное молчание — минимальный дефолт без ошибок.
- Приоритет источников: интервью → readme → манифесты → исходники → пусто.
- Осторожность с существующим: diff и подтверждение перед любой перезаписью (снимает инцидент «молчаливый init на живом проекте»).

## Т5. Контур поправок и Стюард (2.14–2.15)

- Маршруты: жалобу пишет воркер наверх, исполнитель передаёт Стюарду; урок оформляет исполнитель, обнаружив недостатки сам.
- Стюард-агрегатор: архивирует несколько уроков → создаёт один обобщённый/уточнённый → заодно корректирует лицо (playbook) или скилл. «Перераспределение, не надстройка»: знание живёт на одном уровне (урок по контексту / пункт инструктажа в лице лида / правило), с остальных убирается.
- Обучение лиц = лиды предупреждают воркеров в брифах ДО задач (профилактика вместо терапии).
- Триггеры вызова (событийные): (а) завершение цикла Волфа — координатор, получив отчёты и обнаружив новые уроки, вызывает Стюарда; (б) старт новой сессии/треда. Механизм вызова един с жалобным.
- Двухшаговость: «было → стало → почему», применение по подтверждению владельца.
- Метрика: снижение новых уроков/жалоб того же класса после агрегации/мутации.
- Контекст: уроки создаются агентом executor-lead (не человеком) — агентное обучение уже работает; стюард был неактивен, потому что контур мутации лиц не был замкнут ни разу.
- ОТКРЫТЫЙ пункт: автоконвейер черновиков уроков (digest/пороги/затухание) — рекомендация координатора: удалить в 2.13 (дублирует связку «лид пишет + Стюард агрегирует»); финальное решение владельца не зафиксировано.

## Т6. Мультипроектность (частично 2.13–2.14)

- Глобальная память НЕ вводится (риск шума между проектами) — отложено до явного спроса; Стюард строго внутрипроектный.
- Реестр проектов сохраняется в роли «телефонной книги»: быстрый поиск зарегистрированного проекта, сбор статистики, фундамент будущего веб-интерфейса. Истина — память в каталоге проекта, реестр — индекс.
- Гигиена реестра: автоочистка мёртвых и песочниц, самолечение, детект призраков в `doctor`.
- Минимальная команда просмотра проектов (список + статистика) — кейс владельца «быстро найти».
- Перенос: формула «память коммитится → клонирование переносит»; экспорт/импорт архивом — низкий приоритет, только при спросе вне git.

## Метрики успеха (сводно)

- Тёплый вызов контекста < 2 с; задержка роутера < 500 мс; `--version` < 300 мс.
- Справка ≤ 30 строк; одна аналитическая поверхность; ручной справочник CLI — 0 строк.
- Промахи доставки видны одной командой; пустой `call` объясняет себя.
- Инициализация в пустом каталоге — без ошибок и с первой доставляемой памятью.
- Жалобы/уроки одного класса затухают после агрегации (метрика Стюарда).
- Реестр без мёртвых записей автоматически.
