## Диагнозы (фактура для координатора)

1. **E1 не помещается в 900s — главная причина СТОПа.** Прогон №3 при
   спокойной нагрузке (load ~12, близко к ожидаемой ~7 из брифа): 56
   tool-вызовов, 50 шагов за 900s, без зависаний и без permission-фрикции —
   сессия планомерно работала и прервана лаунчером на ~90% задачи
   (правки в init-project.ts, memory-init.ts, 2 тест-файла; диагностический
   oracle-e1 на финальном состоянии: поведенческий критерий (b) PASS —
   первый init уже пишет opencode.json, регрессионный тест (в) PASS, маркер
   кода (a) FAIL — рефакторинг не завершён). Темп прогона №1 под штормом
   load 47 практически тот же (62 вызова) — значит, узкое место не CPU, а
   латентность LLM-шагов + npm/test-циклы; дожидаться «тихой» среды
   бессмысленно.
2. **Инструментальный дефект изоляции (исправлен в протоколе, не в коде).**
   `--no-global` лаунчера НЕ отсекает глобальные MCP (context7/rtk/codegraph/
   mr-wolf→main-dist) — проверено `opencode debug config` на 1.18.27/29.
   Решение: прогоны под `XDG_CONFIG_HOME`-песочницей (в ней только проектный
   `mcp.wolf` = глобальный бинарь 2.5.0 + плагины инстанса). В песочнице
   отсутствовал permission-конфиг → headless auto-reject на read по
   symlink-пути `/tmp/...` при cwd `/private/tmp/...` → прогон №2 убит за
   34s (F25-валидатор корректно пометил exit 2). Фикс: в обе песочницы
   добавлен одинаковый `opencode/opencode.json`
   (`permission.external_directory: /tmp/**, /private/tmp/** = allow`,
   `autoupdate: false`). **Требует того же решения в Фазе C (обе руки) и,
   по-хорошему, переноса в лаунчер/протокол как штатный шаг.**
3. **Кеш-прогрев наблюдаем**: cache_read ≈ 2.2–2.5M токенов за 900s-прогон —
   канал weight (input + 0.1×cache_read + 5×output) осмысленно взвешивает
   повторные проходы по коду; измерительная часть прибора готова к A/B
   без изменений.
4. **Load-шторм 29→47 — внешняя среда** (чужие opencode-сессии, OrbStack),
   не контролируется экспериментом. Документирован в `aa/load-log.txt`;
   verdict-решение на нём не основано (прогон №3 — при спокойной среде).

## Что должно решиться до перезапуска A/A (решение координатора, не исполнителя)

1. `episode_timeout_s`: 900 → **1800** (две прожитые попытки дают ~90% E1 за
   900s; запас ×2 покрывает E1 целиком и более тяжёлые E4/E6). Это правка
   frozen arms.yaml/run-configs — требует явной ревизии pre-launch freeze
   (гейт E4 п.1) с записью причины: калибровка по факту A/A, до первого
   валидного прогона.
2. Бюджет после правки: остаток 37 строк, резерв 0 — либо явно поднять
   потолок ревизией, либо согласовать A/A повтор 6 плановыми строками без
   резерва (риск: любой F21/F25 мгновенно маркирует эпизод invalid).
3. Закрепить XDG-изоляцию + permission-конфиг как штатный протокол прогона
   (сейчас — задокументированный ad-hoc шаг исполнителя).
