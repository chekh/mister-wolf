## 5 критических рисков и вопросы для проработки

### 1. Хрупкость Измерителя (Фаза 20: Сигнальный лог)

**Проблема:** В спеке написано, что метрики извлекаются из «прозы отчётов (Validation Results, FRICTION)». Парсить markdown-отчёты детерминированным скриптом — это хрупкий ад. Любое изменение промпта executor-а, добавление лишнего заголовка или смена формата списка сломает Измеритель.

**Рекомендация:** Оркестратор должен писать **структурированный JSON-артефакт** (например, `session-metrics.json`) параллельно с markdown-отчётом. Измеритель (Фаза 20) должен читать *только* JSON. Markdown — для людей, JSON — для контура обучения.

**Вопрос к тебе:**
- Какие существуют индустриальные стандарты для структурированного логирования LLM-агентских сессий? (Смотри LangSmith, Arize Phoenix, OpenTelemetry for LLMs).
- Какова минимальная схема JSON-артефакта, которая покроет все нужды Фаз 20–24 (rejected-циклы, tool errors, tokens, duration, worker count)?
- Есть ли примеры, где парсинг markdown-отчётов приводил к поломке контура обучения?

### 2. Проблема «Ключа однотипности» (Фаза 21: Паттерн-детекция)

**Проблема:** Ключ `тул + тип ошибки + контекст`. Если «контекст» включает пути к файлам, имена переменных или ID тредов, порог **N≥3 не будет достигнут никогда** (каждая ошибка будет уникальной). Если контекст отбросить, кластеры станут слишком широкими и бесполезными (например, «ошибка чтения файла»).

**Рекомендация:** Нужна **таксономия ошибок** или семантическое хэширование контекста. Либо LLM на этапе логирования (Фаза 20) должна присваивать ошибкам `error_class_id` (например, `auth_timeout`, `fs_permission_denied`), и кластеризация идёт по нему.

**Вопрос к тебе:**
- Как современные observability-платформы (Datadog, PostHog, Braintrust) решают проблему кластеризации LLM-трейсов с высокой кардинальностью?
- Есть ли SOTA-подходы к автоматическому присвоению `error_class_id` без LLM-вызова на каждый лог?
- Какие существуют техники семантической кластеризации ошибок (embedding-based vs rule-based)?

### 3. Иллюзия Holdout-валидации (Фаза 22: ExpeL)

**Проблема:** В спеке holdout описан как проверка правила на «отложенной выборке сигналов». Но правило — это текст. Проверить текст на тексте без запуска агента — это LLM-as-a-judge, который склонен к галлюцинациям и подтверждает свою предвзятость.

**Рекомендация:** Holdout должен быть **исполняемым (Sandbox Replay)**. Берём 3 исторических стимул-промпта из holdout-выборки, скармливаем их mock-агенту *со старым конфигом* (он падает) и *с новым draft-rule* (он справляется). Фаза 23 (STOP-гейт) делает это для активации, но holdout (Фаза 22) должен использовать тот же механизм replay в песочнице, чтобы отфильтровать мусор *до* того, как он попадёт к Куратору.

**Вопрос к тебе:**
- Найди работу **«Proofs, Not Promises: Governed Candidate Improvement for Agent Control Runtimes» (2026)**. Как там формализован sandbox evaluation? Какие гарантии даются?
- Есть ли примеры из ExpeL/Voyager, где текстовая holdout-валидация приводила к принятию плохих правил?
- Как построить lightweight sandbox для CLI-агента без Docker/gVisor overhead?

### 4. Оценка «Качества» в GEPA (Фаза 24)

**Проблема:** Скоринг по Парето (качество/стоимость/время). Время и стоимость (токены) берутся из Фазы 20 тривиально. **Качество — нет.** Как детерминированно измерить, что мутированный шаблон брифа стал «лучше», не запуская полный цикл задач?

**Рекомендация:** GEPA в v1 должна быть ограничена **только теми шаблонами, где качество измеряется детерминированно** (например, процент упавших тестов, количество `rejected-циклов` при использовании брифа). Для креативных/открытых брифов GEPA отключается, иначе метрика качества превратится в шум.

**Вопрос к тебе:**
- Найди работы с ICML 2026 / OpenReview про **Pareto overfitting** в prompt optimization. Какие есть доказательства, что LLM-as-a-judge приводит к дрейфу при многокритериальной оптимизации?
- Есть ли примеры, где GEPA/OPRO применялись к задачам без детерминированной метрики, и что из этого вышло?
- Какие прокси-метрики качества можно использовать для кодинг-агентов (кроме test pass rate)?

### 5. Усталость Куратора (Alert Fatigue)

**Проблема:** Гейт человека (Автономия B) на принятие `draft-rule`. Если система работает активно, Куратор (пользователь) будет получать по 3-5 пуш-уведомлений/запросов на ревью правил в день. Через неделю он начнёт нажимать «Approve» не глядя, что полностью обнуляет смысл гейта.

**Рекомендация:** Пакетная доставка. Куратор не должен получать уведомления в реальном времени. Раз в неделю (или по достижению N=5 draft-правил) генерируется `wolf learn digest` — один структурированный отчёт с evidence, где пользователь ставит галочки `[x] Accept`, `[ ] Reject`.

**Вопрос к тебе:**
- Найди исследования по **HITL fatigue** в active learning и RLHF. Какие паттерны батчинга и дайджестов доказанно снижают усталость?
- Есть ли примеры из продакшена (Devin, Cursor, Claude Code), где использовался batch-approval workflow?
- Как выглядит эффективный CLI-based digest для ревью правил без UI?

## 3 недостающих механизма (добавить в спеку)

### A. Negative Feedback Loop (Обучение на отказах)

**Проблема:** Что происходит, когда Куратор отклоняет `draft-rule`? Система запомнит паттерн, но не запомнит, что *решение было плохим*. Через месяц она сгенерирует точно такое же правило.

**Рекомендация:** Отклонённые draft-правила должны сохраняться с `status: rejected` и `rejection_reason`. Фаза 21 (Паттерн-детекция) должна использовать их как **negative constraints** (не предлагать решения, похожие на отклонённые).

**Вопрос к тебе:**
- Найди работу **«Co-Evolving Agents: Learning from Failures as Hard Constraints»**. Как там формализованы rejected trajectories?
- Есть ли примеры из Meta/Manus acquisition (2025), где negative feedback loop был ключевой архитектурной деталью?
- Как хранить negative constraints в памяти Wolf (отдельный тип объекта или поле в `rule`)?

---

### B. Decay (Механизм забвения / TTL)

**Проблема:** Правила и уроки устаревают (API меняется, рефакторинг кода). `supersede` требует явного действия.

**Рекомендация:** Добавить метрику `last_triggered_at` для активных `rule`/`lesson`. Если правило не триггерилось (не было доставлено в сессию) более X дней, оно автоматически переходит в `status: review_required` или `archived`. Память должна уметь забывать.

**Вопрос к тебе:**
- Найди работу **«Forgetful but Faithful: A Cognitive Memory Architecture» (2025/2026)**. Как там формализован forgetting-by-design? Что такое Memory-Aware Retention Schema (MaRS)?
- Как Generative Agents (Stanford) реализовывали decay? Какие были проблемы?
- Какой TTL разумно использовать для `rule` и `lesson` в кодинг-агенте (30 дней, 90 дней, adaptive)?

---

### C. Observability самого контура обучения

**Проблема:** Как пользователь видит, что система вообще «учится»?

**Рекомендация:** Добавить команду `wolf learn status`. Она должна выводить:
- Текущий размер сигнального лога.
- Количество активных кластеров (N≥3).
- Очередь `draft-rules`, ожидающих Куратора.
- Статистику срабатывания `trigger_keywords` (сколько раз знание реально спасло сессию).

**Вопрос к тебе:**
- Какие мета-метрики используют современные observability-платформы для мониторинга контуров обучения?
- Есть ли примеры dashboard'ов для self-improving агентов (Braintrust, Arize)?
- Как визуализировать эффект доставки правил (до/после) в CLI без графиков?
