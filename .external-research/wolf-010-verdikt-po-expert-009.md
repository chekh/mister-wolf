## 1. Вердикт: QH.1–QH.2 закрыты. Одна часть отклонена — auto-approve.

## 2. Что принято

1. **Документирование проблемы** — лучшее в порции: 37% review fatigue (2025 Developer Survey), кейс Claude Code («blast radius tracks with how many approvals were rubber-stamped»), attentional tunneling + cognitive load из Tang et al. Инсайт «частые запросы → tunneling, редкие → loss of context» — принимаем как рамку для дизайна дайджеста.
2. **Митигации с числами**: SIEM tuning 10–20%, aggregation 20–30%, AI ranking 40–60%, active learning 60–80% fewer annotations.
3. **AARM** как формальная база риск-тиринга (deferral borderline [0.4, 0.6] → batch).
4. **Batch-инфраструктура для Wolf**: очередь `.wolf/queue/draft-rules.jsonl` (производный файл), триггер дайджеста `N≥5 ИЛИ 7 дней`, формат digest-отчёта с чекбоксами, команды `learn queue/digest/approve/reject/defer`, расширение таксономии `lesson` (risk_level, candidate_score, evidence_count, holdout_verdict, review_state, rejection_reason). Оценка эффекта (50 мин/день → 7.5 мин/неделю) — зарегистрирована как target-метрика дизайна дайджеста.

## 3. Отклонено: auto-approve policy

**Это не вопрос калибровки — это конфликт с политикой проекта.** Решение от 2026-08-26 (уровень автономии B, выбор пользователя): *«низкий риск — автономно, высокий (новые правила, промпты ролей, мета-уровень) — через человека»*. Новые правила явно перечислены как высокий риск. Auto-approve draft-rules — снятие этого гейта, то есть фактический переход на уровень C. Такое решение может принять только пользователь, не исследование.

**Замена (включи в финальный brief вместо auto-approve):**
- Для правил: авто-действие только **auto-archive** — просроченное без ревью уходит в `archived` (уже есть в decay-решении expert-005), никогда не в `accepted`. Усталость снижаем приоритизацией дайджеста (high → medium → low, как у тебя), sticky-decline (отклонённое не возвращается — у нас это negative constraints), и лимитом размера батча — но не снятием гейта.
- AARM-подход (low → auto-approve с пост-аудитом) переносим на класс **«параметры»** — например, правки `error_class_taxonomy` (expert-007), где откат тривиален. Правила — никогда.
- Если пользователь захочет auto-approve правил — это отдельное явное решение об изменении уровня автономии, вне данной программы.

## 4. Доработка риск-модели (в финальный brief)

Твоя `classifyRisk` смешивает домены: «isSimilarToExisting → medium» — похожесть на существующее правило это повод для **дедуп-отклонения** (уже покрыто negative constraints из expert-008), а не для снижения риска. И «новое проверенное правило → low» противоречит политике B (новое правило = высокий риск по определению). Переформулируй для правил через **blast radius активации**: охват trigger_keywords (как часто сработает), обратимость отката (supersede-цепочка), какие фазы затрагивает. Черновик можно дать в expert-013.
