# Git-этапы задачи

Регламент: `reference/git-collaboration-policy-v1.1.md` рядом с этим файлом (в проекте `.opencode/skills/wolf-git/reference/git-collaboration-policy-v1.1.md`). Читать только нужный § регламента по этапу; весь файл в контекст не тянуть.

## Обязательный вход

Полномочия берутся из брифа задачи; скилл прав не выдаёт. Нет полномочия на коммит/публикацию — сохраняет назначенный L1 (§3). Спутники: `using-git-worktrees`, `wolf-handoff`, `finishing-a-development-branch`.

## Вход / возобновление (G0)

Структурный факт даёт `wolf git-inspect` (B0.5): JSON с вердиктом PASS|VIOLATION|UNKNOWN, facts/reasons/allowed_next_actions. Перечисленные ниже команды — для адресной детализации.

§6: `git rev-parse --show-toplevel`, `git remote -v`, `git worktree list --porcelain`, `git status --porcelain`, `git rev-parse HEAD`, `git ls-remote` с временем наблюдения; незавершённые merge/rebase/cherry-pick; владелец, baseline, сравнение с опубликованной ветвью и целью MR. Нет remote/сети — «не удалось проверить», не успех (§6.5). Локальный `main` впереди или разошёлся — не push и не reset (§6.2).

## Создание ветки и worktree (G1)

§7, §4.1: задача, владелец, цель MR, явный baseline SHA (не текущий HEAD). Независимая задача — от проверенного SHA `main`, подзадача — от идентифицированного SHA родителя (для передачи на другой хост он должен быть опубликован). Уникальное имя, безопасный путь; чужой непустой каталог не перезаписывается; сначала ищется существующая ветка/worktree продолжения (§15.3).

## Сохранение (checkpoint)

§8: обязателен на логической границе, перед остановкой или передачей, перед операцией, затрагивающей незакоммиченное, и перед предъявлением. Перед коммитом — просмотр diff и известный набор файлов; `git add -A` из неизвестного состояния запрещён. Секреты не публикуются. Коммит ≠ публикация.

## Передача (G2)

§9: остановить прежнюю запись, сохранить и опубликовать при доступном remote; передать задачу/владельца, repo/branch/target, baseline и опубликованный SHA, рабочую копию, состояние, проверки, следующий шаг. Получатель подтверждает вход; без подтверждения передача не завершена, таймаут не доказывает остановку записи.

## Завершение и уборка (G9)

§15: остановить писателей; подтвердить судьбу результата — ancestry исходного SHA (`git merge-base --is-ancestor`) либо запись MR при разрешённом squash; проверить незавершённые операции, dirty, коммиты после принятого SHA, ценные ignored-файлы, нужность потомкам. Чистый `git status` не доказывает безопасность удаления. Запрещены по умолчанию `--force`, `reset --hard`, `clean` с удалением неизвестного, `branch -D`; при неподтверждённой сохранности каталог остаётся.

## Приёмка, интеграция и выпуск

§10, §16, §22: стандарт — merge `--no-ff`; squash — только явное исключение. В Wolf это не автоматизировано.

## Что не поставлено

Нет MR-статусов и адаптера хостинга, CI-проверок, очереди интеграции (§11), тегов/registry/выпуска, переносимых git-мутаций B1 (структурный read-only `git inspect` и JSON-вердикт поставлены в B0.5 как `wolf git-inspect`), scheduler и постоянного контролёра. Гейты G3–G8 не автоматизированы и не являются поставленным гейтом: при необходимости их выполняют люди вручную. Отсутствующее не называть доступной командой.

## Гейт перехода

Подтверждено лишь то, что проверено командой с временем и результатом. «Не удалось проверить» ≠ пройдено; неизвестное состояние не считается чистым.

## Не пропускай процесс

| Мысль | Действие |
| --- | --- |
| «Создам от текущего HEAD» | Выбери baseline SHA явно. |
| «PR готов — уберу worktree» | Сохранность не доказана (§15.1). |
| «Git отказал — добавлю --force» | Разбери причину, не усиливай. |
| «Заметка Wolf доказывает Git-состояние» | Память не факт Git; проверь команды. |
| «Передача вроде сделана» | Нужно подтверждение получателя (§9). |
