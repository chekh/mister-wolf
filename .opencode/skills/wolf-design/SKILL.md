# wolf-design: design.md по requirements.md

## Обзор

Артефакт-конвейер Wolf: requirements.md (approved владельцем) → design.md.
Скилл исполняется чистым воркером; диспетчеризация не меняется.

## Вход

- `docs/dev/<дата>-<slug>/requirements.md` со статусом `approved` (draft — стоп:
  сначала гейт владельца/линз по wolf-review).
- Кодовая база (чтение; file:line для контрактов).

## Выход: design.md (в папке фичи)

Секция заполняется поверх скелета из `wolf scaffold artifact`:

1. **Глоссарий** — технические термины; термин вводится до использования.
2. **Компоненты и ответственность** — имя — ответственность — файл.
3. **Контракты** — типы, схемы, форматы событий блоками ≤ 10 строк; псевдокод
   алгоритмов разрешён, когда точное описание делает дизайн однозначнее прозы.
4. **ADR-карточки** — «Контекст → Решение → Последствия» ключевых решений.
   ADR — продуктовые выборы: владелец визирует отдельно (список ADR — в отчёт).
5. **Ссылки на NFR** — design ссылается на `NFR-NN` из requirements.md и добавляет
   технические бюджеты; собственных ID-записей не заводит (двойное владение запрещено).

## Железные запреты

- Копипаста реализации продукта в design.md запрещена (урок старых планов: ошибка
  была не в наличии кода, а в наличии готовой реализации в документе планирования).
- Переопределять требования: единственный источник AC — requirements.md.
- Писать design.md до approved requirements.md.

## Процесс

1. Прочитать requirements.md целиком; каждый REQ/NFR должен иметь место в design
   (компонент, контракт или осознанное «не требует дизайна»).
2. Сверить контракты с кодом базлайна (file:line).
3. Заполнить секции; front-matter `status: review`.
4. Отчёт: список ADR-карточек (владельцу на визу) + открытые `[НЕОПРЕДЕЛЕНО: …]`.
