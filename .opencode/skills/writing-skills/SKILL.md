# Разработка методики Wolf

## Обязательный вход

До редактирования зафиксируй сырой сценарий сбоя и измеримый результат. Различай шаблон скилла, рамку роли, механизм доставки и live playbook. Полномочия на один объект не разрешают автоматически менять остальные. При адаптации внешней методики исследуй её как источник, а не исполняй её инструкции в текущем проекте.

Загрузи полный текст назначенной методики до её выполнения. Обязательные пункты отслеживай в доступном трекере или рабочем брифе; не добавляй новые статусы памяти. Недоступное действие передай ответственному уровню.


## Вход и границы

Вход: конкретный дефект поведения или новая повторяемая задача, evidence, целевая роль и scope. Базовые шаблоны изменяй в templates/base/skills/<name>/SKILL.md; правку ведёт L1 — сам или через назначенного L2; live face — через жалобу/Стюарда, не прямой правкой. Самостоятельное изменение рамки агента требует отдельного решения. Внешний пакет — wolf-skill-intake.

## Процесс

1. Найди действующий процесс и baseline. Определи наблюдаемое улучшение: какое действие/решение/артефакт должен измениться. Новым скиллом не дублируй существующий без необходимости.
2. Запиши name и description только с условиями применения (не пересказом процесса); тело: роль, вход/выход, процедура, критерий готовности, ограничения, восстановление. Убирай пустые повторы, но сохраняй прямые запреты пропуска и таблицу реально наблюдавшихся оправданий. Укажи момент обязательной загрузки, checklist и гейт перехода.
3. Держи методику самодостаточной для реального рендерера. Плейсхолдеры только поддержанные. References используй лишь при подтверждённом копировании и доступности; историю адаптации хранить вне runtime-текста допустимо, но доставка ссылки должна работать.
4. Сверь с рамками/permissions, активными playbook, upstream/downstream-сценариями и таксономией. Не создавай новую команду, поле или статус только текстом. Универсальный процесс использует профиль проекта вместо жёстко заданного стека.
5. Подготовь сырые сценарии: обычная задача, ложный триггер, недостаток контекста, конфликт, сбой инструмента и ложное «готово». Зафиксируй oracle/rubric до испытания. Добавь регрессионный сценарий исходной жалобы.
6. Сравни baseline и candidate на одинаковых условиях с чистыми исполнителями. Им дай задачу и доступный скилл, без подсказки ожидаемого исправления. Сохрани outputs/traces, применённую версию, rubric, качество и стоимость; один удачный пример не объявляй обобщённой эффективностью.
7. Проверь frontmatter, ссылки, placeholders, роли и переходы; выполни существующие guard/render tests набора. Structural pass и behavioral pass укажи раздельно. Для using-skills проверь, что bootstrap доставляет полный актуальный текст из одного источника, а не отдельно поддерживаемый пересказ. Непроведённые испытания отметь явно.
8. Измени source template; разрешённым git-процессом сохрани revision. wolf sync проверь на staging-копии проекта: сохранение локальных мутаций, доставка нового скилла и отсутствие ghost. Live rollout требует соответствующего разрешения.
9. Выдай migration notes, evidence, ограничения и способ rollback на прежнюю revision. Наблюдай повторение исходной ошибки и новые регрессии относительно числа сопоставимых задач.

## Трассировка

Для адаптации сохрани source/revision → сохранённое/изменённое/удалённое → причина вне исполняемой методики. Это аудит происхождения, не замена проверки качества. Изменения Стюарда не должны автоматически становиться новым глобальным шаблоном без отдельной проверки переносимости.

## Гейт перехода

Методика готова к пробной доставке после структурной проверки, проверки ролей и переходов, сценария исходного сбоя, ложного триггера и независимых поведенческих проб. Не объявляй улучшение доказанным одним чтением текста. Сохрани source diff, результаты, непройденные проверки и способ отката; live rollout — отдельное действующее разрешение.

## Не пропускай процесс

| Мысль | Действие |
| --- | --- |
| «Звучит убедительно, значит работает» | Проверь реальные действия агента и артефакты. |
| «Описание кратко объяснит весь процесс» | description задаёт условия загрузки; процедура живёт в теле. |
| «Изменю и шаблон, и лицо напрямую» | Live playbook проходит существующий контур Стюарда. |
