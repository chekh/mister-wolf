# Доказательства перед заявлением

## Обязательный вход

До слов «готово», «исправлено» или «проверено» сформулируй утверждение и найди подтверждающее evidence. Проверяй выполненный scope, а не более широкий воображаемый результат. L0 сверяет пакет и git-метаданные, запуск поручает L1. Если актуальная проверка уже есть и её область подходит, используй её; не запускай тесты на каждое сообщение.

Загрузи полный текст назначенной методики до её выполнения. Обязательные пункты отслеживай в доступном трекере или рабочем брифе; не добавляй новые статусы памяти. Недоступное действие передай ответственному уровню.


## Гейт

1. Назови точное утверждение: какой AC выполнен, какие тесты прошли, какой симптом устранён.
2. Выбери evidence, действительно подтверждающее его. Diff подтверждает изменение, а не корректность; exit 0 одной команды не подтверждает все требования.
3. Проверь версию, dirty-state, входные данные, зависимости и существенную среду. Запускай недостающую проверку доступной исполнительской ролью. L0 проверяет ACCEPTANCE и поручает независимый запуск L1, сам не выполняет тесты.
4. Прочитай результат, exit code, пропуски и предупреждения; сохрани EVIDENCE из using-skills. Частичный вывод не трактуй как полный успех.
5. Сообщи проверенные свойства и ограничения. Не подтверждено → не подтверждено; проверка недоступна → INCONCLUSIVE, а не «должно работать».

## Актуальность

Результат применим, пока не изменились проверенный код, значимые зависимости, данные или среда. Новое сообщение/сессия не инвалидирует evidence само по себе. При изменениях повтори затронутые проверки; перед интеграцией проверь объединённое состояние. Если точное соответствие dirty-state установить нельзя, запусти проверку повторно.

Evidence содержит claim/AC, command/procedure, cwd, revision, время, exit/status, результат и ссылку на лог; при dirty-tree — digest относящихся файлов/patch, включая untracked. Отсутствующие поля отмечай, не выдумывай. Секреты в evidence не включай.

## Масштаб проверки

Targeted-проверка подтверждает только свою область; full gate — свойства своего набора. Для NFR нужны соответствующие измерения. Ручная проверка допустима с воспроизводимым протоколом и известными ограничениями. Не запускай full suite на каждый ответ, если валидный результат уже есть.

## Приёмочный пакет

По каждому AC: подтверждено/не подтверждено, evidence, revision; далее независимое ревью, отклонения, нерешённые риски и план восстановления при необходимости. L1 передаёт пакет L0; L0 выдаёт ACCEPTED | PARTIAL | REJECTED | INCONCLUSIVE. Перед вердиктом приёмщик сверяет revision и dirty-digest из evidence с фактическим состоянием (например, git rev-parse HEAD); evidence без revision по умолчанию неактуален. Отчёт исполнителя — не доказательство.

[x] в плане ставит L1 после предусмотренной проверки задачи и ревью; фиксирует evidence/revision. Задача проверена не означает, что вся поставка интегрирована или принята. Не объявляй успех на основании чужой уверенности или количества коммитов.

## Гейт перехода

Заявление допустимо только в подтверждённой области. Неполное или устаревшее evidence требует проверки либо ограниченного вывода. RESULT использует свой контракт, а вердикт приёмки — ACCEPTED/PARTIAL/REJECTED/INCONCLUSIVE; не смешивай эти словари. Пользователю поясни ограничение через wolf-explain.

## Не пропускай процесс

| Мысль | Действие |
| --- | --- |
| «Исполнитель уверен» | Прочитай результат проверки и область применимости. |
| «Тесты прошли на прежнем commit» | Сопоставь проверенное и текущее состояние. |
| «PR создан — задача полностью внедрена» | Создание PR, merge и публикация подтверждаются отдельно. |
