# Отчёт: фазы 1–4 эксперимента wolf — трёхуровневая схема агентов и Council Mode

- Период: 2026-08-17, ~10:35–11:30
- opencode v1.18.18, macOS
- Песочница: `wolf-experiment/` (без git), запуск `opencode run --agent wolf-coordinator`
- Модели: wolf = kimi-for-coding/k3-256k, executor = zai-coding-plan/glm-5.2,
  workers = zai-coding-plan/glm-5-turbo

## Гипотеза

OpenCode нативно поддерживает иерархию Wolf (координатор) → Executor
(менеджер задачи) → Workers (однозадачные исполнители) с системными
гарантиями: воркеры не спавнят агентов, глубина ограничена, обмен уровнями —
файловыми артефактами.

## Конфигурация

- `opencode.json`: `subagent_depth: 2`;
- агенты в `.opencode/agents/*.md` (md + frontmatter, models + permission);
- плагин `.opencode/plugins/spawn-logger.ts` (автодискавери, JSONL-журнал
  `logs/spawn-log.jsonl`);
- воркерам `task: deny` (на уровне 2 тул спавна не нужен), probe-воркеру —
  `allow` (для негативного теста), executor — glob `worker-*`,
  wolf — glob `executor-*`.

## Главные находки

1. **Тул `task` субагентам denied по умолчанию.** У executor'а тул отсутствовал
   при любом `subagent_depth` (D-1, D-2). Снимается явным правилом
   `permission.task` у агента. Без него субагент импровизирует обход (в нашем
   случае — CLI `opencode run` из bash), т.е. иерархия «работает», но
   не контролируется системой.
2. **`subagent_depth` работает как задокументировано**: depth 0 блокирует
   спавн первичного агента (D-3), depth 2 режет попытку 3-го уровня в
   рантайме внутри тулa (D-5) — независимо от прав на тул (probe имел
   `task: allow` и всё равно упёрся).
3. **Glob-ограничения спавна**: `permission: {task: {"*": deny,
   "executor-*": allow}}` у wolf — прямой спавн воркера падает с ошибкой,
   цитирующей сами правила (D-6, D-7). Асимметрия «wolf→executor-*,
   executor→worker-*» подтверждена в обе стороны.
4. **`tools:` (массив) в frontmatter агента — deprecated и невалиден** в
   v1.18.18; рабочий механизм — мапа `permission` (`allow|ask|deny` или
   glob-объект). Конфиг с массивом не грузится вовсе (ошибка валидации).
5. **`todowrite` субагентам denied by design** (наш чеклист — файл-ledger);
   кастомные тулы проекта (tasklog, roster) субагентам выдаются
   (наследуются).
6. **Плагин системного логирования спавнов работает** (D-7, D-8):
   `tool.execute.before` пишет `task.call` ДО permission-проверки —
   отклонённые попытки фиксируются системой; `task.result` после завершения.
   Ограничение: при ошибке тулa (depth-блок) after-hook не вызывается —
   попытка видна (`task.call`), исход — в отчётах агентов.
8. **Лимит «макс N воркеров» реализуем системно плагином** (D-9): throw в
   `tool.execute.before` абортит вызов тулa `task` до выполнения (ошибка
   видна модели). Счётчик воркеров per sessionID executor'а, лимит через
   env `WOLF_WORKER_LIMIT` (дефолт 3), попытки сверх лимита пишутся в журнал
   как `task.blocked`. Семантика: счётчик суммарный за сессию executor'а
   (не «активных одновременно»); реюз воркера — через `task_id` (нативный
   параметр тулa). Счётчик in-memory: живёт в рамках одного процесса opencode
   (один `opencode run` = всё дерево сессий в одном процессе) — для
   эксперимента достаточно.
7. **TEST-001 (калькулятор) end-to-end**: два прогона. Первый — executor без
   тулa task обошёлся CLI-мостом (находка 1). Второй (нативный): wolf → бриф,
   executor → 2 воркера параллельно (код + тесты), 8/8 тестов OK, wolf кода
   не касался, отчёт по шаблону. CLI-обходы запрещены промптом и не
   применялись.

## Фаза 3: роли воркеров, verify.sh, консилиум (TEST-002)

- **Роли**: `worker-reviewer` (read-only, edit/bash/task denied, вердикт
  `VERDICT: APPROVED|CHANGES`) и `worker-researcher` (read-only,
  glob/grep/read). Executor обновлён: ревью обязательно перед отчётом,
  лимит 3 воркера, в фазе планирования (консилиум) — ничего не создавать.
- **verify.sh** (`logs/verify.sh`): 8 проверок по системному журналу
  (spawn-log.jsonl) + артефактам: глубина, попытки из воркеров, координация,
  лимит, «wolf только executor-*», дисциплина wolf (в coordinator/ только
  брифы/decision), структура отчётов, тесты. Итог: 8/8 PASS.
- **Консилиум (D-10)**: TEST-002 — парсер арифметики (несколько валидных
  подходов). Волк: бриф → 2 ПАРАЛЛЕЛЬНЫХ executor'а (планирование без
  создания файлов) → decision-002.md (выбран план A: один implementer на
  оба файла для согласованности контракта + слот под фикс; из B заимствовано
  требование ZeroDivisionError на вычисленный ноль) → 1 executor на
  исполнение. Результат: 36/36 тестов, запрет eval/exec/compile соблюдён,
  ревью APPROVE.
- **Живучесть (бонус-тест)**: процесс убит на фазе исполнения (user abort).
  Файловый протокол пережил прерывание: новый запуск wolf'а диспетчернул
  executor'а на «довыполнение» — тот не пересоздал готовое, поймал дефект
  импорта (прямой запуск падал), заспавнил фиксера + reviewer'а, написал
  отчёт с пометкой «довыполнение после прерывания».

## Ограничения и наблюдения

- `deny`-паттерн, по докам, убирает субагента из описания тулa — в CLI-режиме
  модель всё равно попыталась и получила отказ (факт зафиксирован логгером).
- Конфиги мерджатся по дереву: песочница наследует глобальные плагины/тулы
  (roster/tasklog/skill) — изоляция частичная, на эксперимент не влияет.
- `--pure` отключает внешние плагины (включая spawn-logger) — прогоны с
  логированием выполняются без `--pure`.
- Поле `agent` в журнале пустое: объект сессии не отдаёт имя агента через
  SDK; цепочка реконструируется по sessionID + subagent_type.

## Фаза 4: Council Mode (советы)

Участники: `council-{architect,security,performance,ux,cost}` (read-only:
task/bash/web* denied; edit — только свой файл мнения по дисциплине промпта).
Модели по тирам: architect/security = glm-5.2, performance/ux = k3-256k,
cost = glm-5-turbo. Составы/кворумы/пороги — `councils/config.json`
(minimal/architecture/security/performance/full/custom-mixed/custom-csv).
Wolf получил режим 3 (Council) в промпт + `council-*` в permission.task.

Контракт голосования: каждый член пишет `councils/<ID>/<role>.md` со строкой
`VOTE: A|B|C|ABSTAIN|TIMEOUT`; wolf считает строго по файлам, применяет
quorum/consensus_threshold, пишет synthesis.md (Рекомендация / Разногласия /
Quorum), при недостижении консенсуса или human_required — escalation.md
вместо решения.

### Находки фазы 4

9. **Кворум/консенсус wolf считает корректно**: независимый пересчёт
   verify-council.sh по VOTE-строкам файлов мнений совпал с синтезом wolf'а
   во всех 10 прогонах (k3-256k справляется с процедурной арифметикой,
   если считать «строго по файлам», а не по памяти).
10. **Timeout — честная симуляция**: нативного per-task таймаута в тулe
    task нет; участник с инструкцией TIMEOUT неотличим для wolf'а от
    реального отсутствия ответа → quorum-логика тестируется полноценно.
11. **Дыра в deny-стене**: `bash: deny` не останавливает MCP/кастом-тулы —
    wolf вызывал `rtk_run_command` (ls, grep; grep с glob и споткнулся —
    rtk не разворачивает `*`), `roster`, `tasklog`. Все read-only/безвредны,
    но факт: permission-стена покрывает только встроенные тулы.
12. **Эскалация к пользователю в run-режиме** = escalation.md + второй
    запуск с решением (файловый протокол); в интерактивном TUI вместо этого
    можно было бы использовать тул question.
13. **Самовосстановление wolf'а**: упавший rtk-grep wolf пережил через
    нативные Glob/Grep (S7) — деградация инструмента не остановила процесс.

## Вывод

Трёхуровневая схема Wolf → Executor → Workers полностью воспроизводима
нативными средствами OpenCode v1.18.18: вложенный спавн (permission.task),
глубина (subagent_depth), границы «кто кого» (glob-паттерны), квота воркеров
и системный журнал (плагин на tool.execute.*). Подтверждены оба режима
работы: **конвейер** (wolf → executor → воркеры-роли) и **консилиум**
(N executor'ов планируют параллельно → wolf финализирует решением-файлом →
executor исполняет). Council Mode (фаза 4) работает поверх той же механики:
декларативные составы/кворумы/пороги, машиносчитаемые голоса, эскалация к
человеку, итерации, параллельные советы — все 8 сценариев + smoke пройдены,
независимый пересчёт голосов совпал с синтезами wolf'а. Эмуляция и
CLI-обходы не требуются.

Следующие шаги (не выполнены): взвешенные голоса (участник ×2), токен-метрики
(wolf-оркестрация vs плоская диспетчеризация), реальная задача из контекста
лаборатории, интеграция Council Mode с скиллом document-review (совет =
ансамбль перспектив).
