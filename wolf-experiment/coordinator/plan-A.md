# План A (Simplicity) — Rate limiter для локального Python API (TEST-003 / SPLIT-001)

## Подход

Алгоритм — **sliding window log**: для каждого клиента храним deque
timestamp'ов принятых запросов. На каждом вызове `acquire(client_id)`:

1. удаляем из deque все timestamp'ы старше `now - T`;
2. если в deque уже `N` записей — бросаем `RateLimitError`;
3. иначе добавляем `now` в deque и пропускаем запрос.

Почему это достаточно просто: ~15 строк кода, один словарь, нет фоновых
потоков, нет очистки по таймеру (мёртвые записи выталкиваются лениво при
следующем обращении того же клиента). Точное скользящее окно без
интерполяций иweights фиксированного окна; token bucket отвергнут как
более сложный при том же результате для однопроцессного API.

Время — только через инъекционный `clock: Callable[[], float] = time.monotonic`,
по умолчанию `time.monotonic` (требование брифа). Тесты подставляют фейковый
счётчик — реальные `sleep` не нужны.

## Хранилище состояния

Обычный атрибут `self._hits: dict[str, deque[float]]` внутри класса
`RateLimiter`. In-memory, без TTL-потоков и персистентности, потому что:
API локальный и однопроцессный (бриф), состояние умрёт вместе с процессом —
это нормально. Ключ — `client_id`, значение — deque timestamp'ов.

## Структура

Два файла, только в `workers/`:

- `workers/rate_limiter.py`
  - `class RateLimitError(Exception)` — пустой, строка docstring;
  - `class RateLimiter` — `__init__(limit: int, window: float, clock: Callable[[], float] = time.monotonic)`;
    метод `acquire(client_id: str) -> None` (бросает `RateLimitError`
    при превышении). Больше методов нет — проверка и захват в одном вызове.
- `workers/test_rate_limiter.py`
  - `FakeClock` — класс с полем `now` и методом `advance(dt)` (~5 строк);
  - `class RateLimiterTest(unittest.TestCase)` — тесты из плана ниже.

## План тестов

`unittest`, без sleep, время двигаем `FakeClock.advance`:

1. **Превышение лимита**: N=3, T=60; три `acquire` проходят, четвёртый
   в ту же секунду бросает `RateLimitError` (assertRaises).
2. **Восстановление после окна**: после превышения двигаем clock на T+ε —
   `acquire` снова проходит (окно очистилось).
3. **Независимость клиентов**: клиент A исчерпал лимит, клиент B в тот же
   момент проходит свободно.
4. **Граничный случай 1 — ровно на границе окна**: timestamp равный
   `now - T` считается устаревшим (записи строго старше T удаляются —
   `<= now - T` удаляем); запрос на границе проходит.
5. **Граничный случай 2 — N=1**: единичный лимит; второй запрос сразу
   отброшен, после сдвига на T — принят, снова отброшен (полный цикл).

Прогон: `python -m unittest discover workers` из корня `wolf-experiment/`.

## Trade-offs

- **Память растёт с числом активных клиентов** (dict никогда не сжимается
  сам): для локального API приемлемо, чистка не нужна. Мёртвые записи
  выталкиваются лениво, пустые deque по ключам не удаляем — минус пара
  строк кода.
- **Sliding log вместо token bucket / fixed window**: храним все timestamp'ы
  в окне (память O(N) на клиента), зато семантика окна точная и код
  тривиально читается.
- **Нет статистики/ретраев/backoff-инфы в исключении** — `RateLimitError`
  несёт только сообщение. Добавить позже, если понадобится.
- **Потокобезопасность отсутствует**: однопроцессный/однопоточный API по
  брифу; lock добавил бы строк и зависимость от `threading` без текущей
  потребности.
