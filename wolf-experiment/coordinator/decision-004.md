# Decision 004 — Rate limiter B (TEST-004 / SPLIT-001, раунд B)

## (a) Планы кратко

### План C (planner-simplicity) — `coordinator/plan-C.md`

- **Алгоритм:** fixed window counter — на клиента пара `(window_start, count)`;
  `now - start >= T` → новое окно; `count >= N` → `RateLimitError`.
- **Хранилище:** in-memory `dict[str, tuple[float, int]]`, без lock, без
  фоновых потоков, ленивый сдвиг окна при обращении.
- **Trade-offs:** O(1) памяти на клиента (~250–300 Б, ~25–30 МБ на 100k),
  ~50 строк кода. Жертвы: всплеск до 2N на стыке окон (принят осознанно,
  зафиксирован), отказ от переживания рестарта, нет выселения неактивных
  клиентов, нет потокобезопасности, минимальный API (без `retry_after`).
- **Тесты:** 8 (4 обязательных + граница ровно T, частичный advance,
  документирующий всплеск 2N, валидация параметров), FakeClock.

### План D (planner-correctness) — `coordinator/plan-D.md`

- **Алгоритм:** sliding window log — `deque` меток принятых запросов,
  полуоткрытое окно `[s, s+T)`; ≤ N в любом T-интервале, всплеск 2N невозможен
  по построению; `RateLimitError(client_id, retry_after)`.
- **Хранилище:** in-memory `dict[str, deque[float]]` под глобальным
  `threading.Lock` + GC-проход по неактивным + **опциональные атомарные
  JSON-снапшоты** (snapshot/load, переживание рестарта best-effort).
- **Trade-offs:** точная семантика, закрытые классы edge cases (стык окон,
  гонки, монотонность clock, битые файлы). Цена: память O(k) на клиента
  (~1 КБ холодный, типично 115–130 МБ на 100k, худший случай 420 МБ),
  заметно больше кода и публичного API (`usage`, `reset`, `snapshot`, `load`).
- **Тесты:** 14 групп — все обязательные + анти-fixed-window, clock-контракт,
  GC, потоки, снапшот-roundtrip и т.д.

## (b) Анализ несовместимости

**Ядра несовместимы.** Fixed window и sliding log — взаимоисключающая
семантика решения: один и тот же тест на стыке окон (5 принятий при t=59,
запрос при t=60.5 при T=60) проходит в C (всплеск 2N допустим) и падает в D
(отказ обязателен). Объединить ядра без потери сути одного из планов
невозможно: взять алгоритм D — теряется O(1) память и минимальность C;
взять алгоритм C — теряется главная ценность D (точная гарантия «N за любые
T»), а её надстройки (снапшоты, GC) на ядре C противоречат духу C.

Надстройки D частично аддитивны к ядру C (`retry_after`, lock, валидация),
но снапшоты/GC/расширенный API — нет.

Формальное правило эскалации (разные алгоритмы **И** разные хранилища)
**не сработало**: основное хранилище обоих планов — in-memory `dict` по
`client_id`; JSON-снапшоты D — опциональный дополнительный слой, а не
альтернативное хранилище (sqlite отвергнут обоими).

## (c) Режим синтеза: **ВЫБОР ОДНОГО (план C)** + точечные аддитивные
заимствования из D, не меняющие ядро

## (d) Обоснование через trade-offs брифа

Бриф раунда B, в отличие от раунда A, содержит **объективный критерий
выбора** — иерархию приоритетов:

1. **Память — значимый фактор** при 100 000 клиентов, «O(1) памяти на
   клиента предпочтительно». План C даёт ~30 МБ на 100k; план D — типично
   115–130 МБ (до 420 МБ в худшем случае), т.е. 4–14× хуже по оси, которую
   бриф назвал значимой. Аргумент D про глобальный потолок RPS×T корректен,
   но бриф говорит про **активных клиентов**, а не про RPS: dict из 100k
   холодных клиентов у D сам по себе ~100+ МБ.
2. **Строгость на стыке окон — явно отдана на усмотрение исполнителя** с
   фиксацией решения в trade-offs (AC #6). Значит главное преимущество D
   (невозможность всплеска 2N) не конвертируется в обязательную ценность по
   брифу — C фиксирует цену честно, как и требуется.
3. **Переживание рестарта — «желательно, НЕ обязательно»**. Снапшоты D —
   плюс, но за него D платит объёмом кода и API, а бриф прямо разрешает
   отказаться.

Все обязательные требования (лимит, RateLimitError, настраиваемость,
тесты, инъекционный clock, stdlib) выполняют оба плана; разница — только в
опциональных осях, и по всем взвешенным брифом осям выигрывает C. Выбирать
D — значит платить памятью (значимый фактор) за строгость и рестарт
(явно необязательные). Гибрид по ядрам невозможен (пункт b).

Из D берём только **дёшево аддитивное**, не трогающее ядро и не раздувающее
API сверх одной строки/одного поля:

- `retry_after` в `RateLimitError` — в fixed window это одно выражение
  `start + T - now`, полезно реальному API;
- `threading.Lock` вокруг мутаций — страховка за ~0 цену (локальный API
  может быть многопоточным; принято в раунде A, опыт подтверждён);
- валидация конструктора — уже есть в обоих планах.

Отклоняем из D: JSON-снапшоты (необязательно по брифу, против простоты C),
GC-проход (C обоснованно отложил: десятки МБ приемлемы), `ClockViolationError`
и прочий расширенный API (`usage`/`reset`/`load`).

## (e) Финальная инструкция executor'у

**Подход:** fixed window counter, in-memory `dict[str, tuple[float, int]]`,
полуоткрытая граница окна: `now - window_start >= T` → новое окно `(now, 0)`.
Без фоновых потоков, без персистентности, без GC-прохода, только stdlib.
Trade-offs (всплеск до 2N на стыке окон; состояние не переживает рестарт;
нет выселения неактивных клиентов) — зафиксировать в module docstring
(требование AC #6 брифа).

**Файлы:**

1. `workers/rate_limiter_b.py`
   - `class RateLimitError(Exception)` — атрибуты `client_id: str` и
     `retry_after: float` (секунд до конца текущего окна: `start + T - now`,
     > 0);
   - `class RateLimiter` — `__init__(max_requests: int,
     window_seconds: float, clock: Callable[[], float] = time.monotonic)`
     с валидацией: `max_requests >= 1`, `window_seconds > 0` → `ValueError`;
     `clock` callable → `TypeError`;
   - единственный публичный метод `acquire(client_id: str) -> None`;
   - внутреннее: `_counters: dict[str, tuple[float, int]]`,
     `_lock: threading.Lock` (все мутации под lock);
   - никаких `snapshot`/`load`/`usage`/`reset`/`prune`/фоновой очистки.
   - Типизация, Google-style docstrings; module docstring — с разделом
     trade-offs (AC #6).

2. `workers/test_rate_limiter_b.py` — unittest, без реальных `sleep`,
   `FakeClock` с `advance(dt)` (только точно представимые float). Тесты:
   - превышение лимита (N-й ок, (N+1)-й — `RateLimitError` с корректными
     `client_id` и `retry_after`);
   - восстановление после окна (`advance(T)` → снова ок, счётчик с нуля);
   - независимость клиентов;
   - граничный 1: точная граница — `advance(T)` ровно открывает новое окно,
     `advance(T - eps)` — нет;
   - граничный 2: документирующий всплеск 2N на стыке окон (N в конце окна +
     N в начале следующего проходят) — фиксирует принятую цену fixed window;
   - валидация конструктора (`max_requests < 1`, `window_seconds <= 0`,
     не-callable clock).

**Порядок воркеров:** один воркер пишет `rate_limiter_b.py`, затем воркер
(можно тот же) пишет тесты; прогон `python -m unittest` из корня
`wolf-experiment/`. Существующие `workers/rate_limiter.py` и
`workers/test_rate_limiter.py` **не трогать**.

**Обязательное ревью:** перед отчётом executor проверяет соответствие
каждому пункту Acceptance Criteria брифа 004 (включая AC #6 — trade-offs
в docstring), отсутствие реальных `sleep` и не-stdlib импортов, и
нетронутость файлов раунда A.
