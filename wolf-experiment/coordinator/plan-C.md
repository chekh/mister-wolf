# План C (Simplicity) — Rate limiter для локального Python API

- Бриф: `coordinator/task-brief-004.md` (SPLIT-001, раунд B)
- Целевые файлы: `workers/rate_limiter_b.py`, `workers/test_rate_limiter_b.py`
- Приоритет плана: минимум кода, минимальный API, лёгкий откат.

## Подход

**Fixed window counter** — классический счётчик в фиксированном окне:

- Для каждого `client_id` храним пару `(window_start, count)`.
- На запрос: если `now - window_start >= T` — окно считаем закрытым,
  сбрасываем `(now, 0)`. Если `count >= N` — `RateLimitError`, иначе
  `count += 1`.
- Окно «катится» лениво, при обращении клиента: никакого фонового
  таймера/потока, никакого расписания чистки.

Почему достаточно просто: одна ветка if, ~20 строк логики, ноль зависимостей,
нулевая настройка. Альтернативы отвергнуты по сложности:

- **sliding window log** (deque меток времени) — O(N) памяти на клиента,
  при 100k клиентов и N в сотнях — сотни МБ;
- **token bucket** — больше состояния (tokens, last_refill), плавающий
  «взрыв» вместо чёткого окна, код длиннее при сопоставимой защите;
- **взвешенный sliding window counter** — та же память O(1), но математика
  с дробными весами ради одного стыка окон — не стоит того (см. trade-offs).

## Хранилище состояния

**In-memory `dict[str, tuple[float, int]]`** внутри объекта `RateLimiter`
(лимитер — единственный владелец состояния, откат = удалить файл).

- Память O(1) на клиента, доступ O(1) — соответствует контексту 100k клиентов.
- **Оценка памяти на клиента:** слот dict ≈ 100 Б + ключ-str (типичный
  `client_id` ~10–20 симв.) ≈ 60 Б + tuple(2) ≈ 56 Б + float ≈ 24 Б +
  int-счётчик ≈ 0–28 Б → **≈ 250–300 Б/клиент**, т.е. **~25–30 МБ на
  100 000 клиентов**. Приемлемо для однопроцессного API.
- sqlite3 отвергнут: переживание рестарта по брифу «желательно, НЕ
  обязательно», а цена — I/O на каждом запросе + миграции схемы + код
  сериализации ≈ 3× объём. См. trade-offs.

## Структура

### `workers/rate_limiter_b.py` (~50 строк с docstring)

```python
class RateLimitError(Exception):
    """Превышен лимит N запросов за окно T для client_id."""

class RateLimiter:
    def __init__(
        self,
        max_requests: int,                      # N >= 1, иначе ValueError
        window_seconds: float,                  # T > 0, иначе ValueError
        clock: Callable[[], float] = time.monotonic,  # инъекция времени
    ) -> None: ...

    def acquire(self, client_id: str) -> None:
        """Пропустить запрос или кинуть RateLimitError."""
```

Логика `acquire` (единственный метод, вся суть):

```
now = clock()
start, count = self._counters.get(client_id, (now, 0))
if now - start >= self._window:      # окно закрыто (граница: ровно T = новое окно)
    start, count = now, 0
if count >= self._max:
    raise RateLimitError(client_id, ...)
self._counters[client_id] = (start, count + 1)
```

- Валидация аргументов в `__init__` — два однострочных `raise ValueError`.
- Docstring модуля обязан содержать решение по строгости на стыке окон
  и его цену (AC #6 брифа): «fixed window допускает всплеск до 2N на стыке
  окон; принято осознанно, цена — кратковременное 2N вместо N».

Никаких других публичных сущностей: ни `allow() -> bool`, ни
`retry_after`, ни контекст-менеджера. Проще — некуда.

### `workers/test_rate_limiter_b.py` (~100 строк)

Внутренний хелпер `FakeClock` (атрибут `now`, метод `advance(dt)`,
вызывается как `clock`). Реальные `sleep` не используются нигде.

## План тестов

Обязательные по брифу:

1. `test_within_limit_passes` — N запросов в окне проходят без исключений.
2. `test_exceed_raises` — (N+1)-й запрос в том же окне → `RateLimitError`.
3. `test_recovery_after_window` — исчерпали лимит, `advance(T)` → запрос
   снова проходит, счётчик нового окна с нуля.
4. `test_clients_independent` — клиент A исчерпан и кидает исключение,
   клиент B в тот же момент времени проходит.

Граничные (2+ по брифу, берём 4):

5. `test_boundary_exact_t` — `advance(T)` ровно: `now - start == T`
   открывает новое окно (фиксирует семантику `>=`).
6. `test_partial_advance_no_reset` — `advance(T/2)`: окно ещё живо,
   превышение всё ещё кидает исключение.
7. `test_burst_2n_at_junction` — N запросов в конце окна + N в начале
   следующего за короткий интервал проходят — документирует цену
   fixed window (всплеск 2N).
8. `test_invalid_params` — `max_requests < 1` и `window_seconds <= 0`
   → `ValueError`.

Запуск: `python -m unittest workers.test_rate_limiter_b` из корня
`wolf-experiment/` (или discovery). Существующие `rate_limiter.py` /
`test_rate_limiter.py` не трогаем.

## Trade-offs

Сознательно принесено в жертву простоте:

1. **Строгость на стыке окон:** выбран fixed window → возможен всплеск
   **до 2N запросов** на стыке двух окон. Цена принята: это локальный API,
   лимит — защита от злоупотребления, а не SLA; устранение всплеска
   (sliding log / взвешенный счётчик) стоит O(N) памяти на клиента либо
   заметно более сложный код. Решение и цена дублируются в docstring
   модуля (требование AC #6 брифа).
2. **Переживание рестарта: отказ.** Состояние только в памяти: рестарт
   процесса обнуляет все окна, клиенты получают свежие лимиты. По брифу
   это «желательно, не обязательно»; sqlite-персистентность дала бы
   ~3× кода и I/O на горячем пути. Бонус отказа: весь откат = удалить
   один файл, никакого состояния на диске.
3. **Нет выселения неактивных клиентов:** память растёт с числом
   *различных* client_id с момента старта, а не с числом «активных».
   При заявленных 100k это десятки МБ — приемлемо; при необходимости
   фоновая чистка добавляется ~5 строкками позже (в план не входит).
4. **Нет потокобезопасности:** бриф — однопроцессный локальный API;
   при переходе на потоки достаточно обернуть `acquire` в один
   `threading.Lock` (в план не входит, отмечено в docstring).
5. **Минимальный API:** без `allow() -> bool`, без `retry_after`,
   без статистики/сброса. Каждая из этих надстроек — отдельные ветки
   кода и тестов; при надобности добавляются, не ломая совместимость.

Итог: ~50 строк реализации, ~100 строк тестов, один класс + одно
исключение, ноль зависимостей за пределами stdlib.
