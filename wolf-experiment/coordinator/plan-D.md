# План D — `rate_limiter_b`: точное скользящее окно (sliding window log)

Автор: Planner Correctness (SPLIT-001, раунд B). Бриф: `coordinator/task-brief-004.md`.
Артефакты: `workers/rate_limiter_b.py` + `workers/test_rate_limiter_b.py` (новые,
существующие `rate_limiter.py` / `test_rate_limiter.py` не трогать). Только stdlib.
Приоритет плана — корректность на границах, при всплесках и при рестарте;
простота вторична.

---

## Подход

### Алгоритм: sliding window log с жёсткой ёмкостью N

На клиента храним очередь временных меток **принятых** запросов
(`collections.deque[float]`). Решение для запроса в момент `now`:

1. Ленивая чистка: `while q and q[0] <= now - T: q.popleft()` — удаляем записи,
   прожившие T и более (полуоткрытое окно).
2. `len(q) < N` → `q.append(now)`, запрос принят.
3. Иначе → `RateLimitError(client_id, retry_after = q[0] + T - now)`.

**Инвариант (индукция по вызовам):** после каждого `acquire` очередь клиента
после чистки — в точности множество принятых запросов из интервала
`(now - T, now]`; принятие происходит только при `len < N`. Следствие:
для любого клиента и любого момента t в любом полуоткрытом интервале длины T
не более N принятых запросов. Отклонённые запросы в очередь **не пишутся**
(отказ не продлевает наказание — семантика «окно из принятых»).

Границы окон как таковой нет — окно привязано к каждому запросу, поэтому
всплеск «2N на стыке окон», присущий fixed window, невозможен в принципе.

### Почему не альтернативы (анализ гарантий)

| Алгоритм | Гарантия на произвольное T-окно | Память/клиент | Вердикт |
|---|---|---|---|
| Fixed window counter | ≤ 2N (всплеск на стыке) | O(1) | Отвергнут: недетерминированный всплеск именно на границе — главный edge case брифа |
| Token bucket / GCRA | ≤ 2N в худшем T-окне, в любой момент (не только на стыке); семантика «средняя скорость + burst» | O(1) | Отвергнут: слабее и менее буквально, чем «N за T» |
| Sliding window counter (Cloudflare) | ≈ N ± ε, ε не оценивается формально | O(1) | Отвергнут: приближение, трудно тестировать на точных границах |
| **Sliding window log (наш)** | **ровно ≤ N, детерминированно** | O(min(N, k)), k — принятые в окне | Выбран: единственный с точной семантикой |

Цена — память O(k) вместо O(1). Ключевое наблюдение о масштабе: суммарно «живых»
меток по всем клиентам = (принятых запросов за последние T), т.е. глобальный
потолок = RPS × T записей, а не clients × N. Худший случай
«100 000 клиентов × N=100» требует 10 млн принятых запросов за T — нереалистично
для локального однопроцессного API.

### Точная семантика границы (контракт)

Принятый в момент s запрос занимает слот на интервале `[s, s+T)`: он влияет на
решения при `now < s + T` и перестаёт влиять **ровно** при `now = s + T`
(чистка по условию `q[0] <= now - T`). Следствие: запрос, пришедший ровно через
T после старейшей из N меток, — уже разрешён. Полуоткрытость выбрана сознательно
и закреплена тестами на точное равенство: инъекционный clock делает сравнения
детерминированными (в тестах — только точно представимые float: целые и 0.5-шаги).

Сложность: амортизированный O(1) на вызов (каждая метка кладётся и выкидывается
ровно один раз); худший единичный вызов O(N) (массовое устаревание) — микросекунды.

### Конкурентность и clock

- Бриф: один процесс, но потоки не исключены (threaded WSGI/ASGI) ⇒ один
  глобальный `threading.Lock` вокруг последовательности «прочитал clock →
  почистил → решил → записал». Атомарность check-and-act обеспечена явно,
  без рассуждений о GIL. Цена ~0.1 мкс без контеншна. Per-client локи отвергнуты
  (100 000 локов — память и сложность). Мультипроцессность — вне контракта
  (задокументировать).
- Clock инъекционный: `clock: Callable[[], float] = time.monotonic`; читается
  один раз на вызов, под локом. Нарушение монотонности (`now < previous`) ⇒
  `ClockViolationError(RuntimeError)` — fail fast, без молчаливых клампов.
- Async: внутри критической секции нет `await` ⇒ безопасно для одного event loop.

### Сборка мусора по неактивным клиентам

Чистка ленивая (на доступе), поэтому пустые/полностью устаревшие клиенты
задерживаются в dict. GC-проход: не чаще раза в `gc_interval_seconds`
(по умолчанию = T; `None` = никогда), условие `now - last_gc >= gc_interval`,
проход O(клиентов) под тем же локом, удаляются клиенты с пустой после чистки
очередью. Фоновых потоков нет — проход навешан на `acquire`; редкий всплеск
латентности (~10 мс на 100k клиентов раз в T) принят и задокументирован.

### Валидация (fail fast, на конструировании)

- `max_requests`: `int`, не `bool`, ≥ 1 — иначе `ValueError`.
- `window_seconds`: `numbers.Real`, не `bool`, > 0 — иначе `ValueError`.
- `clock`, `wall_clock`: callable — иначе `TypeError`.
- `client_id`: по брифу строка; runtime-проверки типа не делаем (Python-идиома),
  работаем через dict — unhashable ключ даст естественный `TypeError`
  (закрепить тестом). Наследуемая семантика dict: `True` и `1` — один ключ
  (задокументировать, не «лечить»).
- Конфиг (N, T) неизменяем после создания; смена лимита = новый экземпляр
  (состояние не переносится) — задокументировать.

### Переживание рестарта: опциональные снапшоты (best-effort)

- `snapshot(path)`: атомарная запись (временный файл в той же директории +
  `os.replace`) JSON-документа: версия формата, N, T, якорь времени
  (пара mono/wall, снятая в момент снапшота), клиенты → списки меток.
  Ключи — только `str`: при наличии не-str client_id — `PersistenceError`
  (json молча стрингует ключи и склеил бы `1` и `"1"` — ловим явно).
- `SlidingWindowRateLimiter.load(path, *, max_requests, window_seconds,
  clock=..., wall_clock=...)`: читает JSON, валидирует версию и совпадение N/T,
  пересчитывает метки в домен нового monotonic clock:
  `E = max(0, wall_load − wall_anchor)`; `ts_new = (mono_load − E) + (ts_old − mono_anchor)`;
  затем ленивая чистка применяется при первом обращении.
  Скачки wall-clock (NTP) дают ошибку отображения ≤ одного окна — принято
  (выживание рестарта «желательно», не «обязательно»).
- Отказ от per-request durable-журнала (sqlite-транзакция на каждый accept):
  ×100–1000 к латентности ради гарантии вне требований брифа. Потеря состояния
  между снапшотами = не более одного окна сверх-допуска на клиента —
  задокументированный риск.

## Хранилище состояния

- **Горячее состояние — память процесса:** `dict[client_id, deque[float]]` под
  одним `threading.Lock`. Авторитетно; O(1) амортизированно на вызов.
- **Рестарт — опциональный JSON-снапшот** (см. выше). sqlite3 разрешён брифом,
  но не выбран: без per-request durability он не даёт ничего сверх атомарного
  `os.replace`, а с ней — неприемлемая латентность для локального API.
- **Оценка памяти на клиента (CPython 3.11+, 64 бит):**

| Состояние клиента | Оценка |
|---|---|
| Холодный (пустой deque + запись dict + str-ключ) | ≈ 0.9–1.2 КБ |
| Каждая живая метка (float 24 Б + слот deque 8 Б) | +32 Б |
| Тёплый клиент, k меток в окне | ≈ 1 КБ + 32·k Б |
| Худший случай k = N = 100 | ≈ 4.2 КБ |
| 100 000 активных, в среднем 5 меток | ≈ 115–130 МБ |
| 100 000 активных, все в лимите N=100 | ≈ 420 МБ (требует 10 млн accept за T — нереалистично) |
| Глобальный потолок по нагрузке | (принятых RPS) × T × 32 Б (1k RPS × 60 c ≈ 2 МБ) |

## Структура

`workers/rate_limiter_b.py` — единственный модуль реализации. Типизация под
`mypy --strict`, docstrings в Google-style. **В module docstring — раздел
trade-offs (решение по строгости стыка окон и его цена) — требование
Acceptance #6 брифа.**

- `RateLimitError(Exception)` — атрибуты `client_id: str`, `retry_after: float`
  (0 < retry_after ≤ T: секунд до освобождения слота старейшей метки).
- `ClockViolationError(RuntimeError)`.
- `PersistenceError(RuntimeError)`.
- `class SlidingWindowRateLimiter` — конфиг неизменяем после создания:
  - `__init__(self, max_requests: int, window_seconds: float, *, clock:
    Callable[[], float] = time.monotonic, wall_clock: Callable[[], float] =
    time.time, gc_interval_seconds: float | None = None) -> None` — валидация
    (см. выше); создаёт `_clients: dict[str, deque[float]]`, `_lock`,
    `_last_now: float | None`, `_last_gc: float`.
  - `acquire(self, client_id: str) -> None` — под локом: `_read_clock()`
    (гвард монотонности) → чистка → решение → append → `_maybe_gc(now)`.
    Кидаёт `RateLimitError`; при отказе мутирующей записи нет (чистка —
    идемпотентный побочный эффект, допустим).
  - `usage(self, client_id: str) -> int` — под локом: чистка + `len(q)`
    (0 для неизвестного). Только наблюдение, без резервирования.
  - `reset(self, client_id: str) -> None`; `reset_all(self) -> None` — под локом.
  - `snapshot(self, path: str | os.PathLike[str]) -> None` — под локом;
    JSON → временный файл → `os.replace`; любая ошибка I/O/сериализации
    оборачивается в `PersistenceError` (с `__cause__`).
  - `classmethod load(cls, path, *, max_requests, window_seconds, clock=...,
    wall_clock=..., gc_interval_seconds=None) -> Self` — см. «Переживание
    рестарта»; битый/чужой файл → `PersistenceError`, несовпадение N/T →
    `ValueError`.
  - Приватные: `_read_clock()`, `_prune(q, now)`, `_maybe_gc(now)`, `_gc(now)`.
- Намеренно НЕ входит: `would_allow()` (TOCTOU-ловушка: результат устаревает до
  использования; наблюдение вынесено в `usage()`); смена N/T на лету.

`workers/test_rate_limiter_b.py` — unittest, без реальных `sleep`, только
инъекционный clock; в тестах — только точно представимые float (целые, шаг 0.5).

## План тестов

Хелперы: `FakeClock` (`.value`, `advance(dt)`, крючок шага назад); фабрика
`make(n, t, **kw)`; ассерты `assertAllowed(l, cid)` / `assertDenied(l, cid)`
(контекстный менеджер проверяет `RateLimitError` и его поля). Запуск:
`python -m unittest workers.test_rate_limiter_b` (и просто `python -m unittest`).

1. **Базовая семантика / превышение**: burst ровно N принят одним мгновением,
   N+1-й — `RateLimitError` с корректными `client_id` и `retry_after`
   (`0 < retry_after ≤ T`).
2. **Восстановление после окна**: отказ → сдвиг ровно на T → принят;
   T−ε — ещё отказ; T+ε — принят.
3. **Точная граница (полуоткрытость)**: метка ровно возраста T не считается;
   `retry_after` → 0 при приближении к границе; **отказы не продлевают окно**
   (спам отказов внутри окна, затем ровно T — принят).
4. **Анти-fixed-window (главный edge)**: N=5, T=60; 5 принятий при t=59
   (шестое при t=59 — отказ); запрос при t=60.5 — **отказ** (fixed window
   с границей 60 позволил бы — тест различает реализации); t=118.999 — отказ;
   t=119.0 ровно — принят. Плюс инвариантный прогон: скрипт ~50 событий,
   после каждого — проверка «принятых в (t−T, t] ≤ N» по журналу решений.
5. **Независимость клиентов**: 2–3 клиента, чередование на одинаковых метках;
   лимит одного не влияет на другого; всем клиентам одна и та же метка времени.
6. **Граничные конфигурации**: N=1 (минимум: строгое чередование отказ/приём);
   дробное T=0.5; большой N; повторный полный burst после устаревания всех меток.
7. **Валидация**: `max_requests ∈ {0, −1, True, 2.0}` → `ValueError`;
   `window_seconds ∈ {0, −1, True}` → `ValueError`; не-callable clock →
   `TypeError`; unhashable `client_id` → `TypeError`.
8. **Clock-контракт**: clock шагнул назад → `ClockViolationError`; объект после
   этого консистентен (следующий корректный вызов работает).
9. **usage/reset**: `usage` после чистки корректен; `reset` снимает лимит
   немедленно; `reset_all` очищает всех, состояние словаря пустое.
10. **GC**: `gc_interval_seconds=0` как тестовый крюк — полностью устаревший
    клиент удаляется проходом; активный (с живыми метками) — остаётся;
    возврат удалённого клиента = чистая история (доступны полные N).
11. **Много клиентов / шторм**: 1000 клиентов × чередующиеся метки — точные
    ожидания per client (`subTest`); детерминизм: одинаковая последовательность
    на двух экземплярах → идентичные решения.
12. **Потоки (без sleep)**: 8 потоков × 200 попыток, один клиент, реальный
    `time.monotonic`, T=600, N=50 → ровно 50 принятых, остальные —
    `RateLimitError`; `usage ≤ N`; никаких исключений из потоков.
13. **Снапшот/рестарт**: roundtrip с fake mono + fake wall (сдвиг обоих доменов;
    wall-назад → clamp E=0); не-str client_id при snapshot → `PersistenceError`;
    усечённый файл / чужая версия → `PersistenceError`; несовпадение N/T при
    load → `ValueError`; после load ленивая чистка применяется при первом
    `acquire`.
14. **(опционально)** документирующая проверка семантики dict: `True` и `1`
    делят один бюджет.

## Trade-offs

- **Строгость на стыке окон: выбрана максимальная** — точное скользящее окно,
  ≤ N в любом T-интервале, всплеск 2N невозможен по построению. Цена: память
  O(min(N, k)) на клиента вместо O(1) и больше кода, чем fixed window.
  Компенсация: глобальный потолок RPS × T × 32 Б делает реальную цену малой;
  теоретический худший случай (420 МБ) задокументирован и требует нереалистичной
  нагрузки. Это же решение фиксируется в module docstring реализации
  (Acceptance #6).
- **Простота принесена в жертву ради гарантий**: гвард монотонности clock,
  GC-проход, строгая валидация (включая отсечение `bool` у числовых
  параметров), отдельные типы исключений, атомарные снапшоты с якорем двойных
  часов. Каждый пункт закрывает конкретный класс багов: NTP/флейковые тесты,
  утечка dict, «N=0 вдруг работает», путаница исключений, битые файлы.
- **Переживание рестарта: best-effort, опционально** (явные `snapshot`/`load`;
  потеря между снапшотами ≤ одно окно сверх-допуска на клиента; NTP-риск
  отображения доменов принят). Per-request sqlite-журнал отвергнут: ×100–1000
  латентности ради гарантии вне требований брифа.
- **Глобальный лок вместо per-client**: простота и корректность в потоках;
  теоретический масштабирующий потолок сознательно принят (локальный API).
- **Отклонённые запросы не учитываются** (окно из принятых): отказ не должен
  продлевать наказание; альтернатива «считать попытки» отвергнута и закреплена
  тестом №3.
- **`would_allow()` не публикуется**: non-mutating peek создаёт TOCTOU-иллюзию;
  наблюдение — через `usage()`.
- **Полуоткрытая граница `[s, s+T)`**: «ровно через T — уже можно»; детерминирована
  с инъекционным clock; ULP-дрожь реального clock у самой границы принципиально
  неустранима — задокументировать как допустимую.
- **JSON-снапшот вместо sqlite**: атомарности `os.replace` достаточно при
  единственном писателе (однопроцессный лимитер); читаемость и отсутствие
  schema-migration перевешивают; не-str ключи — честный `PersistenceError`
  вместо молчаливой склейки ключей json.
