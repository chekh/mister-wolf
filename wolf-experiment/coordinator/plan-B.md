# Plan B — Rate limiter (Planner Correctness)

Бриф: `coordinator/task-brief-003.md` (TEST-003 / SPLIT-001). Локальный
однопроцессный Python API, только stdlib, инъекционный `clock`, unittest без
реальных `sleep`.

## Подход

**Скользящее окно с журналом (sliding window log).**

На каждый запрос (`acquire(client_id)`) по клиенту хранится deque
таймстампов успешно пропущенных запросов. Алгоритм:

1. `now = clock()`;
2. из deque клиента удаляются все таймстампы `t <= now - T` (окно
   **полуоткрытое** `[now - T, now]`: запрос в момент `t` «занимает слот»
   ровно до `t + T`, не включая его);
3. если в deque осталось `>= N` записей — бросить `RateLimitError` с
   `retry_after = oldest + T - now` (сколько ждать до ближайшего
   освобождения слота);
4. иначе — `append(now)`, запрос пропущен.

**Почему именно sliding log, а не fixed window / token bucket:**

- *Fixed window* некорректен на стыке окон: до `2N` запросов за интервал
  `< T` (всплеск в конце окна W1 и начале W2). Это прямой провал требования
  «N запросов за окно T».
- *Token bucket* пропускает мгновенный burst до `N` сразу после простоя —
  формально за некоторые скользущие интервалы длины T проходит `2N - 1`
  запросов. Нарушает букву ТЗ.
- *Sliding log* даёт **точную** гарантию: в любых T последовательных секундах
  не более N пропущенных запросов. Цена — O(N) памяти на активного клиента
  (см. Trade-offs).

**Граничная корректность:**

- Полуоткрытое окно детерминировано: запросы в `t` и ровно в `t + T`
  не конфликтуют; в `t + T - eps` — конфликтуют. Одно правило для всех
  сравнений: устаревает запись при `t <= now - window`.
- `time.monotonic` по умолчанию — иммунитет к скачкам системных часов
  (NTP, ручной перевод). Инъекционный `clock` — для детерминированных
  тестов.
- Потокобезопасность: все мутации `_events` под `threading.Lock` (stdlib,
  ~нулевая цена). Бриф требует однопроцессность, но локальный API часто
  крутят на многопоточном dev-сервере — страховка от гонки
  «два потока прошли проверку одновременно».
- Память: ленивая очистка — если после шага 2 deque пуста, ключ клиента
  удаляется из dict; плюс явный `prune(now)` для долгоживущего процесса.
  Неактивные клиенты не текут.
- Рестарт/пересоздание лимитера — состояние сбрасывается («чистый лист»):
  для in-memory локального API это ожидаемая семантика, фиксируем в
  тесте, чтобы поведение было контрактом, а не случайностью.
- Валидация конструктора: `limit >= 1`, `window > 0`, `clock` callable —
  `ValueError`/`TypeError` на старте, а не молчаливые сюрпризы в рантайме.

## Хранилище состояния

- **Где:** оперативная память процесса — `RateLimiter._events:
  dict[str, deque[float]]` (клиент → таймстампы активных запросов),
  защищено `threading.Lock`.
- **Почему это надёжно:** локальный однопроцессный API не требует
  разделяемого хранилища; in-memory state = нет частичных отказов записи,
  нет рассинхрона между «счётчиком» и «истиной». Monotonic-время делает
  состояние устойчивым к переводу системных часов. Lock устраняет
  interleaving даже при неожиданно многопоточном хосте.
- **Ограничение (зафиксировано):** состояние не переживает рестарт процесса;
  персистентность сознательно вне скоупа брифа.

## Структура

`workers/rate_limiter.py`:

- `RateLimitError(Exception)` — атрибуты `client_id: str`,
  `retry_after: float` (>= 0, до освобождения слота);
- `RateLimiter(limit: int, window: float, clock: Callable[[], float] =
  time.monotonic)` — строгая валидация аргументов в `__init__`;
  - `acquire(client_id: str) -> None` — пропустить или бросить
    `RateLimitError`;
  - `prune(now: float | None = None) -> int` — удалить клиентов без
    активных записей, вернуть число удалённых (для долгоживущих
    процессов);
  - внутреннее: `_events: dict[str, deque[float]]`, `_lock:
    threading.Lock`.

`workers/test_rate_limiter.py`:

- `_FakeClock` (поле `now`, метод `advance(dt)`) — детерминированное время,
  ноль реальных `sleep`;
- тесты по плану ниже; запуск `python -m unittest`.

Типизация — `mypy --strict`-совместимая, docstrings на публичном API.

## План тестов

Обязательные по брифу:

1. **Превышение лимита** — N `acquire` успешны, (N+1)-й бросает
   `RateLimitError`.
2. **Восстановление после окна** — после исчерпания `clock.advance(T)`
   → следующий `acquire` успешен.
3. **Независимость клиентов** — A исчерпал лимит, B беспрепятственно
   проходит свои N; пересоздание сценариев с разными `client_id`
   (включая пустую строку — валидный ключ).

Граничные (выбор исполнителя, с запасом):

4. **Точная граница окна** — запрос в `t0`; попытка в `t0 + T` **успешна**
   (полуоткрытость); попытка в `t0 + T - eps` — отклонена.
5. **Всплеск на стыке «окон»** (анти-fixed-window): N-1 запросов при
   `t ≈ 0`, затем запросы при `t = T - eps`: суммарно в любом
   скользящем окне T не более N — (N+1)-й отклонён, хотя fixed window
   пустил бы.
6. **`retry_after` корректен** — равен `oldest + T - now`, лежит в
   `(0; T]`; после `advance(retry_after)` acquire успешен.
7. **Валидация конструктора** — `limit < 1`, `window <= 0`,
   не-callable `clock` → исключения на этапе конструирования.
8. **Много клиентов** (сотни) — изоляция без деградации, лимитер не
   «переливает» остатки между клиентами.
9. **Рестарт/пересоздание** — новый `RateLimiter` не наследует отказы
   старого: сразу после пересоздания N запросов успешны.
10. **Память/очистка** — после истечения всех записей клиент исчезает из
    `_events` (лениво) и удаляется `prune()`; при повторном обращении
    работает как новый.
11. **Потокобезопасность (smoke)** — `threading.Barrier`, M потоков × k
    запросов к одному клиенту: ровно N успешных, остальные — корректный
    `RateLimitError`, состояние не портится (deque не теряет порядок).
12. **Инъекция clock** — все тесты идут на `_FakeClock`; отдельная
    проверка, что дефолт `time.monotonic` действительно подставлен
    (`__init__` без аргумента clock).

## Trade-offs (принесено в жертву ради надёжности)

- **Простота → точность.** Sliding log сложнее и тяжелее fixed window /
  token bucket: O(N) памяти на активного клиента вместо O(1). Зато
  требование «N за окно T» выполняется точно, без дыр на стыках окон и
  без burst-обхода.
- **lock в «однопоточном» API.** Бриф однопоточен — lock формально избыточен,
  но стоит копейки и закрывает реальный класс гонок dev-серверов.
- **Нет персистентности.** Рестарт сбрасывает лимиты (возможен краткий
  «бесплатный» всплеск после рестарта). Для локального API принято;
  иначе — внешний storage, что нарушает «локальный, stdlib».
- **Ленивая очистка вместо фонового таймера.** Нет скрытых потоков и
  недетерминизма; пик памяти между обращениями клиента держится до
  первого `acquire`/`prune`.
- **Инвариант неубывающего clock** документирован, но не форсируется
  проверкой на каждый вызов (цена O(1) → O(len)); дефолт
  `time.monotonic` гарантирует выполнение в проде.
