# Decision 003 — Rate limiter (TEST-003 / SPLIT-001)

## (a) Планы кратко

### План A (planner-simplicity) — `coordinator/plan-A.md`

- **Алгоритм:** sliding window log — `deque` timestamp'ов на клиента; на каждом
  `acquire`: выкинуть записи старше `now - T`, если осталось N — `RateLimitError`,
  иначе `append(now)`.
- **Хранилище:** in-memory `dict[str, deque[float]]` в классе `RateLimiter`,
  без lock, без фоновых потоков, ленивая очистка.
- **Trade-offs:** ~15 строк, тривиальная читаемость; жертвы — память на
  активных клиентов, отсутствие потокобезопасности и метаданных в исключении.
- **Тесты:** 5 тестов (3 обязательных + граница окна + N=1), FakeClock.

### План B (planner-correctness) — `coordinator/plan-B.md`

- **Алгоритм:** тот же sliding window log, с явной семантикой полуоткрытого
  окна `[now - T, now]`: устаревает при `t <= now - T`; `RateLimitError`
  несёт `client_id` и `retry_after`.
- **Хранилище:** тот же in-memory `dict[str, deque[float]]`, но под
  `threading.Lock`; ленивая очистка пустых deque + явный метод `prune()`;
  валидация аргументов конструктора.
- **Trade-offs:** O(N) памяти на клиента, lock формально избыточен при
  однопоточности, нет персистентности; зато точная гарантия «N за любые T»
  и закрытые классы edge cases (стык окон, burst-обход, гонки).
- **Тесты:** 12 тестов — все обязательные + граница `t + T`, анти-fixed-window
  всплеск, `retry_after`, валидация, масштаб клиентов, рестарт, очистка,
  smoke-потокобезопасность, дефолтный clock.

## (b) Анализ несовместимости

Несовместимости **нет**. Планы используют одинаковый алгоритм (sliding
window log) и одинаковое хранилище (`dict[str, deque[float]]` in-memory).
Расхождения только в надстройках, и все они аддитивны:

- полуоткрытая граница окна (B) — уточнение, а не противоречие: A сам
  выбрал то же правило `<= now - T` в тесте «ровно на границе»;
- `threading.Lock` (B) против «lock не нужен» (A) — не конфликт семантики,
  а вопрос страховки; lock не ломает ни один тест A;
- `retry_after`, валидация конструктора, `prune()` (B) — чистые добавления,
  ничего в ядре A не меняют.

Объединение возможно без потери сути любого из планов: ядро A сохраняется
как единственный метод `acquire`, надстройки B опциональны и не усложняют
базовый путь.

## (c) Режим синтеза: **ГИБРИД**

Правило эскалации не сработало: алгоритм и хранилище совпадают. Выбирать
один план целиком — терять ценность другого (A даёт минимальность API и
запрет раздувания, B — корректностные гарантии и богатые тесты).

## (d) Обоснование через trade-offs брифа

Бриф: локальный **однопроцессный** API, stdlib, алгоритм на выбор
исполнителя. Требование «N запросов за окно T» читается строго — sliding
log (единогласно выбранный обоими) даёт эту гарантию точно, fixed window и
token bucket — нет. Память O(N) на клиента и отсутствие персистентности
приемлемы для локального API. Из B берём только дешёвые гарантии
корректности (полуоткрытая граница, валидация конструктора, lock как
страховка, `retry_after` — полезен реальному API), из A — минимальный
публичный API без фоновых потоков и лишних методов. `prune()` из B
отклоняем: бриф не требует управления памятью, метод раздувает API (дух A).

## (e) Финальная инструкция executor'у

**Подход:** sliding window log (точное скользящее окно), in-memory
`dict[str, deque[float]]`, полуоткрытое окно: запись устаревает при
`t <= now - T`. Без фоновых потоков, без персистентности, только stdlib.

**Файлы:**

1. `workers/rate_limiter.py`
   - `class RateLimitError(Exception)` — атрибуты `client_id: str` и
     `retry_after: float` (время до освобождения ближайшего слота, >= 0);
   - `class RateLimiter` — `__init__(limit: int, window: float,
     clock: Callable[[], float] = time.monotonic)` с валидацией:
     `limit >= 1`, `window > 0`, `clock` callable → `ValueError`/`TypeError`;
   - единственный публичный метод `acquire(client_id: str) -> None`;
   - внутреннее: `_events: dict[str, deque[float]]`,
     `_lock: threading.Lock` (все мутации под lock);
   - ленивая очистка: пустой deque клиента удаляется из dict при acquire.
     Метода `prune()` — **нет**.
   - Типизация, Google-style docstrings на публичном API.

2. `workers/test_rate_limiter.py` — unittest, без реальных `sleep`,
   `FakeClock` с `advance(dt)`. Тесты:
   - превышение лимита (N-й ок, (N+1)-й — `RateLimitError`);
   - восстановление после окна (`advance(T)` → снова ок);
   - независимость клиентов;
   - граничный 1: точная граница окна — запрос ровно в `t + T` проходит,
     в `t + T - eps` отклоняется;
   - граничный 2: всплеск на стыке окон (анти-fixed-window): в любом
     скользящем окне T не более N;
   - дополнительно (дешёвые, из B): `retry_after` корректен; валидация
     конструктора; дефолтный clock — `time.monotonic`.

**Порядок воркеров:** один воркер пишет `rate_limiter.py`, затем воркер
(можно тот же) пишет тесты; прогон `python -m unittest discover workers`
из корня `wolf-experiment/`.

**Обязательное ревью:** перед отчётом executor проверяет соответствие
каждому пункту Acceptance Criteria брифа и отсутствие реальных `sleep` и
не-stdlib импортов.
