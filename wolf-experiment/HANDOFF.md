## 1. Зачем всё это было: предмет и гипотезы

Вопрос: можно ли на **нативном opencode** — без внешних оркестрационных
фреймворков (AutoGen / CrewAI / LangGraph / MetaGPT) — построить
дисциплинированную многоагентную иерархию, и **сколько она стоит**:

```
Wolf (координатор, k3-256k)            — брифы и решения, кода не касается
└── Executor (менеджер задачи, glm-5.2) — декомпозиция, диспетчеризация
    └── Workers (glm-5-turbo)            — однозадачные исполнители
+ Council Mode (совет: N членов голосуют → wolf синтезирует)
```

Сравнение велось с **FLAT** — одним «плоским» агентом той же сильной
модели (glm-5.2), который делает всё сам. Это ключевой базовый уровень:
все выводы «дороже/дешевле» — именно против него.

Два блока гипотез:

| Блок | Содержание | Итог |
|---|---|---|
| **H1 (механика)** | Иерархия нативно конфигурируется и держит системные границы: вложенный спавн, depth-лимит, glob-правила «кто кого спавнит», файловый протокол обмена, квоты, независимая верификация | **✅ подтверждена целиком** (H1.1–H1.5, прогоны TEST-001/002, D-1…D-9) |
| **H2 (советы)** | Council Mode: составы, кворумы, пороги, эскалация, итерации, параллельность | **✅** (11 советов, 8 сценариев; пересчёт голосов совпал с синтезами wolf'а 10/10) |
| **Экономика/качество** | «Иерархия окупается на сложных задачах» | **В основном опровергнута** — кроме одного класса задач (см. §4) |

## 2. Что делали: хронология серий

### Фаза 1–4 — механика и паттерны (TEST-001/002, D-1…D-9, советы)

- Настроили 12 md-агентов в `.opencode/agents/` с permission-границами и
  `subagent_depth: 2`; плагин `.opencode/plugins/spawn-logger.ts`
  (JSONL-журнал спавнов + жёсткий лимит воркеров через throw в before-хуке).
- Подтвердили три архитектурных режима: **конвейер** (wolf → executor →
  воркеры-роли с ревьюером и фиксером), **консилиум** (N планировщиков →
  wolf собирает гибрид → один исполняет), **совет** (голосование с
  кворумом/порогом и эскалацией к человеку).
- Отработали **докат после прерывания**: убитый процесс переживается
  новым запуском — артефакты на диске, готовое не пересоздаётся.
- Итог фаз — реестр из 12 эмпирических фактов механики opencode (M1–M12,
  §5) и 8/8 PASS независимой верификации `logs/verify.sh`,
  `logs/verify-council.sh`.

### SPLIT-001 — раскол планов (rate limiter)

Два планировщика с конфликтующими приоритетами (простота vs корректность,
обе glm-5.2). Свободный бриф → раскола **нет** (аттрактор: sliding log).
Бриф с развилками (100k клиентов, необязательная персистентность) →
раскол по **ядрам алгоритмов** (fixed window vs sliding log); wolf корректно
разрешил критерием брифа (память), без лишней эскалации. Вывод: раскол
требует задачи-развилки, а не только конфликта приоритетов (находки 14–17).

### Серия B — экономика реализации (COST-001, LONG-001, LONG-002)

| Эксперимент | Дизайн | Результат |
|---|---|---|
| **COST-001** | 3 малые код-задачи (калькулятор / rate limiter / парсер) × FLAT vs ORCH × 3 итерации; замеры токенов из SQLite opencode | Обе схемы 100% зелёные тесты; налог иерархии **+274…+1141% new-токенов, время ×4–9**. Тенденция: больше задача — меньше относительный налог |

### Аудит инструментальной асимметрии (находка 42 — обязательна к прочтению)

Постфактум-аудит SQLite-БД показал: цифры ORCH в LONG/RESEARCH —
**верхняя граница**, часть налога — артефакт песочницы. Веб-воркерам
запретили `bash`, глобальная инструкция «только rtk» с узким allowlist не
покрывала их задачи (500 rtk-ошибок + 137 веб-ошибок за серию;
worker-rs-industry ≈100% витков с провальными вызовами), каждый провал —
полный виток с перечитыванием контекста. Compliant-модели (turbo)
ретраят сотни раз, сильные (glm-5.2) уходят в обход за 1–2 провала.

**Скорректированные налоги ORCH** (после вычета waste-доли):

| Эксперимент | new: измерен → скорр. | full: измерен → скорр. | waste-доля ORCH | Время |
|---|---|---|---|---|
| LONG-001 | +211% → **+157%** | +97% → **+68%** | 17% / 15% | ≈1.3 из 7.2 мин на треш |
| LONG-002 | +410% → **+347%** | +221% → **+172%** | 12% / 15% | ≈3.1 из 16.0 мин |
| REVIEW-001 | +48% → **+46%** | **−29% → −29%** | 2% / 1% | ≈0.9 из 32.7 мин |
| RESEARCH-001 | +439% → **+258%** | +365% → **+211%** | **36% / 36%** | ≈×2.3 → ×1.35 |

Все структурные вердикты выживают; REVIEW-001 чист от артефакта
(ревьюеры read-only, rtk-ошибок 0). **Мета-урок**: инструментальная
политика — предусловие честных A/B-метрик; перед сравнением схем сверять
тул-статиусы агентов обеих веток по БД, иначе метрики измеряют ловушку,
а не схему.

квоты), **распараллеливание пика контекста** по агентам (в ревью-схеме).

## 4. Главные выводы (прямо к применению)

1. **Вся иерархия нативна в opencode** — без CLI-обходов и внешних
   фреймворков. Три режима подтверждены: конвейер, консилиум, совет.
2. **Ключевой секрет** — тул `task` субагентам **не выдаётся по
   умолчанию**; вложенный спавн включается правилом `permission.task`
   (с glob-паттернами «кто кого»). Без него субагент импровизирует обход.
3. **Файловый протокол — фундамент живучести** (brief / decision /
   report / opinion / synthesis / escalation / final-decision):
   переживает смерть процесса, даёт докат и аудит.
4. **Самодекларациям — нет**: системная правда — плагин-журнал (пишет
   до permission-проверки) + независимый пересчёт по первичным файлам.
5. **Иерархия — не экономия, а процессные гарантии** (на всех
   измеренных классах, кроме ревью): налог токенов/времени всегда; 
   выигрыш по качеству — только в изолированном ревью.
6. **Пик контекста в иерархии переезжает, а не исчезает** (wolf тонкий,
   executor распухает) — заявлять «экономию контекста схемы» нельзя.
7. **Специфицируемая задача = однопроходная** для сильной модели (2026):
   сопротивляться автоматизации может только неспецифицируемое —
   отладка живого legacy, противоречивые требования, «сделай как лучше».
8. **Судья-дженералист не дискриминируетирует хорошие документы**
   (потолок 45–48/50) — для тонких сравнений нужны контрастные пары
   или предметные рубрики.
9. **Инструментальная политика = предусловие честных метрик** (находка
   42): каждому воркеру — рабочая трасса (bash allow или rtk-allowlist
   под класс задачи); «только rtk» без покрытия — ловушка для
   compliant-моделей.
10. **Операционные грабли собраны и закрыты протоколами**: watchdog
    (bg+poll+kill) от зависаний; ретраи с паузами при параллельных
    сессиях того же провайдера; allowlist файлов и «временные — в /tmp»
    в брифах воркеров; маркеры aborted в измерениях.

## 5. Реестр механики opencode (M1–M12; проверено на v1.18.18)

> Полные формулировки — REPORT.md §4. При апгрейде opencode —
> перепроверить smoke'ами.

| # | Факт (сжато) |
|---|---|
| M1 | `permission` — мапа `тул: allow\|ask\|deny` или glob-объект; массив `tools:` в frontmatter **невалиден** (конфиг не грузится) |
| M2 | Тул `task` субагентам **denied по умолчанию**; снимается `permission.task` |
| M3 | `permission.task` поддерживает glob — жёсткая граница «кто кого спавнит», нарушение падает с информативной ошибкой |
| M4 | `subagent_depth` режет в **рантайме внутри тулa**, даже при `task: allow` |
| M5 | `todowrite` субагентам denied by design; чеклисты субагентов — файл-ledger |
| M6 | Плагины: `config(cfg)` мутация конфига; `tool.execute.before` — мутация args **или throw = блок вызова** (ошибка видна модели); `after` не вызывается при ошибке тула |
| M7 | `before` срабатывает **до permission-проверки** — отклонённые попытки видны журналу |
| M8 | Permission-стена покрывает **только встроенные тулы**: MCP/кастом-тулы проходят мимо `bash: deny` |
| M9 | Конфиги мерджатся по дереву каталогов; `--pure` отключает внешние плагины (и свои автодискавери) |
| M10 | Кастомные тулы проекта (`.opencode/tools/*.ts`) субагентам **выдаются** |
| M11 | `opencode run --agent X "msg"` — полный автономный прогон; таймаут только внешний; эскалация = файл + второй запуск |
| M12 | Токены/сессии — в локальной SQLite (`session/message/part`), атрибуция per-agent бесплатно |

## 8. Как устроена песочница и как её запустить

```
wolf-experiment/
├── AGENTS.md            # правила песочницы (кто что пишет, границы)
├── opencode.json        # { "subagent_depth": 2 }
├── .opencode/agents/    # 12 агентов (md + frontmatter: model, permission)
├── .opencode/plugins/   # spawn-logger.ts
├── coordinator/         # артефакты wolf: task-brief-*, decision-*, plan-*
├── executor/            # отчёты executor: report-*
├── workers/             # код, созданный воркерами (+ тесты)
├── councils/            # config.json + COUNCIL-*: question/opinions/
│                        #   synthesis/escalation/final-decision
├── cost/                # прогоны серии COST-001 (T1/T2/T3 × flat/orch)
├── long-task*/          # фикстуры и прогоны LONG-001 (base, flat-*, orch-*)
├── long-task-002*/      # фикстура и прогоны LONG-002 (nanohttp)
├── review-task*/        # фикстура и прогоны REVIEW-001 (спека Атлас v4.2)
├── research-task/       # прогоны RESEARCH-001 (flat-*/orch-*/, note.md)
└── logs/                # журналы: spawn-log.jsonl, отчёты серий,
                         #   verify-скрипты, cost-агрегатор, генератор
```

Запуск (на другом устройстве после `git clone`):

```bash
cd mister-wolf/wolf-experiment
opencode run --agent wolf-coordinator "…бриф…"   # иерархия
opencode run --agent flat-worker "…задача…"      # плоская схема
bash logs/verify.sh                               # независимая проверка
```

Нюанс: прогоны с плагин-журналом — **без** флага `--pure` (он отключает
автодискавери плагинов). `node_modules` в `.opencode/` не коммитится
(восстановление — `npm i` внутри `.opencode/` при необходимости).

## 9. Ограничения и незакрытые вопросы

- **Версия-зависимость**: M1–M12 проверены на v1.18.18; при апгрейде
  opencode — перепроверить smoke'ами.
- **Capacity-предел не построен**: класс задач, где flat объективно
  тонет (пик >200k), не воспроизведён. Гипотеза-кандидат —
  неспецифицируемые задачи (отладка legacy без спеки, «сделай как
  лучше»). Для честного capacity-теста нужна задача, сопротивляющаяся
  скриптованию (находка 22).
- **Взвешенные голоса совета** (участник ×2) не проверялись.
- **«Чистый» раскол планов** по всем трём критериям эксперта не достигнут
  (получен по ядрам алгоритмов; хранилищевая ось не развелась).
- **Слепой судья-дженералист**: потолочный эффект на хороших документах —
  метрика пригодна как стандарт серии, но измеряет «качество документа»,
  а не «пользу ревью».
- **RESEARCH-001 величины** — верхняя граница (инструментальный
  артефакт); для честной величины нужен повтор с рабочей трассой веба у
  воркеров (bash allow или починенный веб-стек). Направления вердиктов
  устойчивы.
- Поле `agent` в SDK `client.session.get()` пустое — рантайм-атрибуция
  из spawn-лога/конфига (в SQLite-БД атрибуция есть).
