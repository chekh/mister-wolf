## 2. Резюме (главное для будущего)

1. **Вся иерархия нативна.** Никаких CLI-обходов и эмуляций не нужно:
   спавн = вложенные вызовы тулa `task`; границы = permission + subagent_depth
   + плагин. Три архитектурных режима подтверждены: **конвейер**
   (wolf → executor → воркеры-роли), **консилиум** (N executor'ов планируют →
   wolf финализирует → 1 исполняет), **совет** (N членов голосуют →
   wolf синтезирует по кворуму/порогу → эскалация при необходимости).
2. **Ключевой секрет** — субагентам тул `task` по умолчанию НЕ выдаётся;
   снимается правилом `permission.task` у агента (с glob-паттернами «кто
   кому»). Без этого субагент импровизирует обход (CLI `opencode run`).
3. **Файловый протокол — фундамент живучести**: brief / decision / report /
   question / opinion / synthesis / escalation / final-decision. Прерывание
   процесса (user abort) переживается докатом: новый запуск читает артефакты
   и продолжает с места обрыва, не пересоздавая готовое.
4. **Самодекларациям — нет**: системная правда в плагин-журнале
   (spawn-log.jsonl, пишет ДО permission-проверки) и независимом пересчёте
   (verify-скрипты не верят синтезам wolf'а, а пересчитывают по файлам).
5. **Токены уже учитываются локально** в SQLite opencode — per agent,
   per model, с разбивкой in/out/reasoning/cache (см. §9; готовый SQL).

## 5. Подтверждённые паттерны оркестрации

### 5.1 Конвейер (TEST-001, TEST-002)
wolf пишет бриф → executor разбивает на подзадачи → воркеры параллельно
(код + тесты) → executor прогоняет тесты → worker-reviewer (VERDICT:
APPROVED|CHANGES) → при проблемах воркер-фиксер (не сам!) → отчёт по
шаблону (Summary/Changes/Workers Used/Validation Results). Wolf не читает
код — вердикт только по отчёту.

### 5.2 Консилиум (TEST-002, фаза планирования)
N executor'ов параллельно пишут планы (без создания файлов — фаза
планирования отделена от исполнения) → wolf выбирает/собирает гибрид в
`decision-*.md` (планы кратко, выбор, обоснование, финальная инструкция) →
один executor исполняет. Наблюдение: планы исполнителей совпали в алгоритме,
разошлись в схеме воркеров — wolf выбрал A с заимствованием детали из B
(аргумент: сохранение слота лимита под фикс-итерацию).

### 5.3 Совет (11 прогонов)
Вопрос → параллельный спавн членов → каждый пишет мнение с `VOTE:` → wolf
считает строго по файлам → quorum/consensus_threshold → synthesis.md
(Рекомендация / Разногласия / Quorum + «не ответил») → при недостижении
консенсуса или `human_required` — escalation.md вместо решения → решение
пользователя вторым запуском → final-decision.md. Итерации: round-1/round-2
(совет корректно подтвердил выбор при новой информации; смена «буквы» из-за
смены набора вариантов — не дёргается без причины). Параллельные советы:
7 спавнов одним сообщением, системно подтверждено по журналу (разброс 28с).

### 5.4 Докат после прерывания
Процесс убит на фазе исполнения → артефакты на диске → новый запуск wolf'а
диспетчерит executor'а «довыполнить»: не пересоздаёт готовое, докатывает
пропущенные шаги (тесты, ревью, фикс, отчёт с пометкой). Файловый протокол
переживает смерть процесса.

## 6. Контракты (переиспользуемые)

- **VOTE-контракт**: строка `VOTE: A|B|C|ABSTAIN|TIMEOUT` в файле мнения —
  машиносчитаемо; TIMEOUT = симуляция отсутствия ответа (нативного per-task
  timeout в `task` нет).
- **VERDICT-контракт** ревьюера: `VERDICT: APPROVED|CHANGES` первой строкой.
- **timeout-sim**: тег в промпте члена — пишет только `VOTE: TIMEOUT`
  (неотличим для wolf'а от реального таймаута → quorum тестируется честно).
- **Лимит воркеров** (плагин): счётчик `worker-*` per sessionID спавнера;
  превышение → throw в before-хуке (вызов абортится, ошибка модели видна) +
  `task.blocked` в журнал; реюз воркера — нативный параметр `task_id`;
  лимит через env `WOLF_WORKER_LIMIT`.
- **Независимая верификация**: скрипт пересчитывает голоса/глубину/квоты по
  первичным артефактам (файлы мнений, журнал), а не по сводкам агентов.

## 8. Находки (сводно; детали в phase-1-report.md)

1. `permission.task` — ключ к вложенному спавну (иначе CLI-импровизация).
2. `subagent_depth` работает как задокументировано; режет в рантайме.
3. Glob-границы «кто кого» — жёсткие, с информативной ошибкой.
4. `tools:`-массив невалиден → только permission-мапа.
5. `todowrite` deny by design; кастом-тулы субагентам выдаются.
6. Плагин-журнал: before пишет до permission; after молчит при ошибке тула.
7. Файловый протокол переживает прерывание процесса (докат).
8. Лимит воркеров: throw в before = жёсткая квота (D-9).
9. Кворум/консенсус k3-256k считает безошибочно при правиле «строго по файлам».
10. Timeout-член честно эмулируется (VOTE: TIMEOUT) — quorum тестируем.
11. Дыра: MCP/кастом-тулы вне permission-стены (rtk/roster/tasklog у wolf).
12. Эскалация в run-режиме = файл + второй запуск (в TUI — тул question).
13. Самовосстановление: упавший rtk-grep wolf пережил нативными Grep/Glob.

## 9a. SPLIT-001: реальный раскол планов (rate limiter)

**Схема**: wolf → 2 планировщика ПАРАЛЛЕЛЬНО с конфликтующими приоритетами
(`planner-simplicity`: «простота, 30 минут, лёгкий откат»; `planner-correctness`:
«гонки, рестарты, всплески»; ОБА glm-5.2 — раскол рождается из приоритетов,
не из разницы моделей) → каждый пишет свой план-файл → wolf анализирует
несовместимость → режим синтеза (ВЫБОР / ГИБРИД / ЭСКАЛАЦИЯ по правилу:
«разные алгоритмы И разные хранилища без объективного критерия → эскалация»).

### Раунд A (свободный бриф) — раскола НЕТ

Оба планировщика независимо выбрали **sliding window log + dict/deque
in-memory** (A: ~15 строк; B: + lock, валидация, retry_after, 12 тестов).
Wolf: ГИБРИД (ядро A + дешёвые гарантии B), исполнено, 59/59 тестов.
**Вывод: у задачи был аттрактор** — sliding log одновременно прост и
корректен; приоритеты планировщиков не смогли развести исполнителей.

### Раунд B (бриф с развилками) — раскол по ядрам достигнут

Бриф-004: 100k клиентов (память значима, O(1) предпочтительно), рестарт
«желателен, НЕ обязательно», строгость стыка окон «на усмотрение
исполнителя, зафиксируй в trade-offs».
- План C (simplicity): **fixed window counter** + in-memory dict, ~50 строк,
  осознанный всплеск 2N на стыке;
- План D (correctness): **sliding window log** + in-memory dict под lock +
  опциональные JSON-снапшоты, 14 групп тестов.
- Критерии эксперта: алгоритмы различаются ✅, ядра несовместимы ✅
  (один и тот же тест на стыке окон проходит в C и падает в D — анализ
  wolf'а подтверждён), хранилища совпали ❌ (sqlite отвергнут обоими:
  для локального однопроцессного API не дал преимуществ ни одной стороне).
  Итог: 2 из 3 — «чистый» раскол по всем осям не получен, содержательный
  (по ядрам) — да.
- **Wolf: ВЫБОР ОДНОГО (C) + аддитивные заимствования** (retry_after, lock,
  валидация). Эскалация не сработала формально (хранилища те же) И по сути:
  бриф содержал объективный критерий (память: ~30 МБ vs 115–420 МБ на 100k),
  который перевесил. Обоснование — развёрнутое, по осям брифа.
- Исполнение: fixed window + заимствования; 9/9 тестов; ревью APPROVED;
  докат после прерывания (таймаут 15 мин убил executor на финише — дефект
  импорта тестов пойман и исправлен фиксером, отчёт с пометкой).

### Находки SPLIT-001

14. **Раскол требует задачи-развилки, не только конфликтующих приоритетов**:
    при свободном брифе исполнители сходятся на очевидном аттракторе.
    Развилки, сработавшие в раунде B: необязательная персистентность,
    отданная на усмотрение строгость, явный фактор ресурсов.
15. **Хранилищевая ось провокации слабее алгоритмической**: обе философии
    отвергли sqlite для локального однопроцессного кейса — ось «память vs
    файл» не развела. Для раскола хранилищ нужны требования вроде
    multi-process / распределённости.
16. **Wolf корректно различает «принципиальный конфликт без критерия» и
    «конфликт, разрешимый критериями брифа»** — во втором случае решает сам
    с развёрнутым trade-off обоснованием, эскалацию не жжёт зря. Для
    реальных применений: если хотим гарантированный human-in-the-loop при
    расколе ядер — помечать планировочные решения human_required явно,
    не полагаться на правило эскалации (его условие «И разные хранилища»
    легко не выполняется формально).
 17. Повторно подтверждён паттерн доката (второй случай): прерывание на
     исполнении переживается, дефекты импорта тестов ловятся фиксером.

## 9b. COST-001: токен-сравнение оркестрации vs плоской схемы

зависание) — исключены из средних.

### Вердикт по порогам эксперта

Все три задачи: overhead_new 274–1141% ≫ 50% → **«иерархия только когда
плоский прогон не справляется (контекст)»**. На задачах этого размера
иерархия — налог 3–11× по токенам и 4–9× по времени без прироста качества.
Переломный пункт не достигнут даже на T3. Замеченная тенденция: overhead
падает с ростом задачи (T2→T1→T3: 1141→408→274%) — большие задачи
амортизируют оркестрацию, но до безубыточности далеко (нужны задачи,
где flat-агент реально упирается в контекст/итерации).

Ценность иерархии на этом классе задач — НЕ экономика, а: процессные
артефакты (brief/decision/report — трассируемость), независимое ревью
(ловило баги: float-точность, граница окна `<` vs `<=`), живучесть/докат,
системные гарантии границ.

### Инцидентная статистика ORCH (9 чистовых прогонов)

- голодание слота ревью (лимит 3 воркера съеден фиксом): ~5/9 (обходы:
  доводочная сессия executor'а / пропуск ревью с отклонением);
- path drift (воркеры записали в workers/cost/... вместо cost/...): 1/9;
- скретч-файл executor'а (нарушение «код только воркерами»): 1 (убитый);
- зависание сессии executor'а сразу после спавна (нет нативного таймаута
  в `opencode run` — нужен внешний watchdog): 1;
- убит внешним таймаутом батча: 1.

### Находки COST-001

18. **Иерархия как налог, а не экономия** (на малых-средних задачах):
    цифры выше; применять только при реальной необходимости (контекст,
    трассируемость, параллельные роли).
19. **Слот-голодание ревью — систематический трение-пункт** лимита 3:
    ревью следует выносить в отдельную доводочную сессию executor'а
    (executor'ы сами это изобрели в 3 прогонах) или поднимать лимит.
20. **Маркеры окон — источник ошибок измерения**: столкновение task/iter
    без фильтра типа (моя ошибка) загрязнило killed-окно; агент-фильтр
    спас от соседнего проекта. Урок: окна размечать inline (S/E вокруг
    одного прогона), при реконструкции — фильтровать по типу.
21. **Зависание возможно и требует watchdog'а**: сессия умерла на ~30-й
    секунде после спавна, `opencode run` ждал вечно до ручного аборта.

### Вывод эксперимента

Для класса «итеративное ревью длинного зрелого документа» иерархия
впервые даёт измеримые преимущества: **шире и глубже поиск дефектов
(H1) при меньшей полной стоимости (full −29%)** — изоляция сессий
режет монотонно растущий кэш-балласт flat-саморевью (cache.read
7–12M у FLAT). Но конверсия в финальное качество по слепой оценке
нулевая (паритет с base). Практическое правило: иерархическое ревью
оправдано как **процессор качества поиска** (найти больше и глубже
за меньшие полные токены), а не как генератор измеримо лучшего
документа; для молодых/черновых документов (где остались critical)
эффект может быть выше — не проверено.

### Находки REVIEW-001

32. **Изоляция перспектив бьёт по слепым зонам саморевью**: major-дефектов

    сам пишущий правки, систематически недокритикует свои же решения
    в следующих итерациях.
33. **full-токены — первая метрика, где иерархия выигрывает** (−29%):
    каждый ревьюер читает документ один раз в чистой сессии; flat
    перечитывает всё с накопленной историей (cache.read 7–12M).
    На тарифах с платным кэш-чтением длинные документы × многократные
    проходы = ниша иерархии.
34. **Слепой судья не отличает финалы от базы** (42 vs 43.0/43.7 при
    применённых 96–100% замечаниях): широкие размерности глухи к
    точечным семантическим фиксам. Судейская метрика дёшева (232k на
    7 оценок) и стабильна — пригодна как стандарт серии, но измеряет
    «качество документа», а не «пользу ревью».
35. **Пик контекста распараллеливается**: вместо одного 190k-пика
    FLAT — распределённые пики (author ~100k, ревьюеры 37–155k
    по объёму их входа), ни один не несёт историю чужих раундов.
    Подтверждение и развитие находки 27 (LONG-002): пик не исчезает,
    но в ревью-схеме изолируется в каждом агенте.
36. **Параллельный трафик того же провайдера роняет длинные прогоны**:
    4 немых обрыва (flat-2 ×3, flat-3 ×1; exit=0, ~500–630с, лог

## 9. Учёт токенов (методика; проверено живыми данными)

**Вариант 1 — уже работает, ноль кода: SQLite.**
`~/.local/share/opencode/opencode.db` (или `~/Library/Application Support/`
на macOS — симлинк): `session(agent, time_created)`,
`message(data→modelID)`, `part(data→{tokens:{input,output,reasoning,
cache:{read,write}}, cost})` у частей `type=step-finish`. Готовый запрос:

```sql
SELECT s.agent, json_extract(m.data,'$.modelID') AS model,
       COUNT(DISTINCT s.id) AS sessions,
       SUM(CAST(json_extract(p.data,'$.tokens.input')  AS INTEGER)) AS in_tok,
       SUM(CAST(json_extract(p.data,'$.tokens.output') AS INTEGER)) AS out_tok,
       SUM(CAST(json_extract(p.data,'$.tokens.cache.read') AS INTEGER)) AS cache_read
FROM part p
JOIN message m ON m.id = p.message_id
JOIN session s ON s.id = m.session_id
WHERE p.data LIKE '%"step-finish"%'
  AND s.time_created > <unix_ms>          -- окно наблюдения
GROUP BY s.agent, model ORDER BY in_tok DESC;
```

Реальные цифры за день эксперимента (фазы 1–4, все прогоны):

| agent | модель | сессий | input | output | cache read |
|---|---|---|---|---|---|
| wolf-coordinator | k3-256k | 25 | 188k | 44k | 1.16M |
| executor-lead | glm-5.2 | 14 | 137k | 19k | 714k |
| worker-implementer | glm-5-turbo | 13 | 53k | 6k | 404k |
| council-architect | glm-5.2 | 9 | 32k | 5k | 228k |
| остальные (7 агентов) | — | 32 | ~128k | ~26k | ~1.0M |

Наблюдения: кэш-чтения на порядок больше input (промпты агентов хорошо
кэшируются — реальная цена подписки сильно ниже суммы input); `cost=0`
у подписочных провайдеров (цен нет — считать в токенах против лимитов
подписки, не в деньгах); атрибуция per-agent бесплатно через `session.agent`.

**Вариант 2 — рантайм (плагин `usage-logger.ts`)**: хук `event` ловит
обновления сообщений/частей (те же `tokens`), пишет JSONL
`{ts, sessionID, agent, model, tokens}` — для live-дашборда и алертов
по бюджету запуска. Точное имя события проверить при реализации
(`message.part.updated` / `message.updated`); данные идентичны part.data.

**Вариант 3 — per-run**: `opencode run --format json` стримит события
с usage — агрегация одного запуска пайпом.

**Связка с деревом**: join `sessionID → agent` (из БД) со spawn-логом
(`task.call/result` связывают parent/child сессии) даёт разрез по уровням
иерархии: «wolf-уровень / executor-уровень / воркеры».

- **Токен-метрики «оркестрация vs плоская схема»**: измерены дважды — COST-001
  (малые задачи, §9b: 274–1141%) и LONG-001 (миграционный масштаб, §9c:
  +239% new). Переломный пункт (flat тонет) не достигнут: нужна задача,

- Поле `agent` в SDK `client.session.get()` пустое (в отличие от БД) —

5. **Файловые контракты** (brief/decision/report/VERDICT/VOTE) — принять

6. **Серия C, новые**: (а) изолированное ревью по перспективам —
   паттерн для критичных документов лаборатории (спеки MC/атлас):
   раунд security → completeness → consistency, узкий ревьюер в чистой
   сессии; (б) слепой судья (анонимные копии, seed-перемешивание) —
   стандарт приёмки документ-продуцирующих задач; (в) при веб-поиске
   — одиночный агент, не конвейер (синтез-бутылочное горлышко, находка
   39); (г) ретраи с паузами обязательны при параллельных сессиях того
   же провайдера (находка 36); (д) контракты воркеров — «результат
   текстом + allowlist файлов», временные файлы в системный /tmp
   (находка 41); (е) **инструментальная политика = предусловие честных
   метрик** (находка 42): каждому воркеру — рабочая трасса оболочки
   (bash allow или rtk-allowlist, покрывающий класс задачи:
   python3/cd/mkdir/rg); глобальная инструкция «только rtk» без
   allowlist-покрытия — ловушка для compliant-моделей (turbo ретраит
   сотни раз, glm-5.2 уходит в bash за 1–2 провала); перед A/B-
   экспериментами сверять тул-статиусы агентов обеих веток по БД
   (ошибки/вызовы), иначе метрики измеряют ловушку, а не схему.
