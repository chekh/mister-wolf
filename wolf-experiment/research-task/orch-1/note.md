## 1. Подтверждено экспериментами

Эксперимент wolf-experiment (REPORT.md, находки 1–37, §1–§11) эмпирически подтвердил **работоспособность и управляемость** трёхуровневой схемы как механизма — при количественно очерченных экономических границах (см. §2, §4).

**Управляемость и системные границы (ядро схемы):**

- Конфигурация агентов в отдельном подпроекте, загрузка и диспетчеризация нативны (12 md-агентов, все прогоны) — §1, §3.
- Вложенный спавн работает при явном `permission.task`; без правила тул `task` субагентам denied по умолчанию, и субагент уходит в CLI-импровизацию — находка 1, M2.
- `subagent_depth` жёстко блокирует 3-й уровень; проверка в рантайме режет даже агентов с правом на тул — находка 2, M4.
- Glob-границы «кто кого спавнит», квоты на воркеров, системный журнал спавнов и независимая верификация (verify.sh 8/8 PASS, verify-council.sh FAIL=0) — находки 3, 8.
- Лимит воркеров через throw в before-хуке плагина — жёсткая квота: 3 OK, 4-й блок, `task.blocked` в журнале — находка 8.
- Принцип «артефактам — да, самодекларациям — нет»: плагин-журнал пишет до permission-проверки (отклонённые попытки видны), verify-скрипты не верят сводкам агентов — находка 6, §2.4, §6.

**Режимы оркестрации:**

- Три архитектурных режима (конвейер / консилиум / совет) реализуемы нативно, без CLI-обходов и эмуляций — §2.1, §5.1–5.3.
- Council Mode: кворумы, пороги, эскалация, итерации, параллельность — 11 советов, 8 сценариев; пересчёт голосов совпал с синтезами wolf'а 10/10 — находки 9, 10.
- SPLIT-001: реальный раскол планов достижим, но требует задачи-развилки; wolf корректно различает принципиальный конфликт и конфликт, разрешимый критериями брифа — находки 14, 16.

**Живучесть и надёжность:**

- Докат после прерывания: файловый протокол переживает смерть процесса; kill@50% + resume ≈ 0.7× стоимости чистового прогона — находки 7, 17, 26.
- Самовосстановление wolf: упавший rtk-grep пережит нативными Grep/Glob — находка 13.

**Экономика и качество (первое подтверждённое преимущество):**

- REVIEW-001 H1: изолированные ревьюеры находят больше дефектов — issues +31%, major ×2.2 (57 vs 26); изоляция перспектив бьёт по слепым зонам саморевью — находка 32.
- full-токены — первая метрика, где иерархия экономически выигрывает (−29% в ревью); пик контекста распараллеливается между агентами — находки 33, 35.
- Токен-учёт локально без кода: SQLite per agent/model с in/out/reasoning/cache — §9, M12.
- Capacity-свойство уровня wolf: пик контекста координатора 11–18k токенов на широких задачах (втрое+ тоньше flat) — находка 23; декомпозиция стабильна (находка 31).

## 2. Остаётся гипотезой

Часть притязаний схемы эксперимент **не подтвердил** или оставил непроверенной (worker-rs-experiments, worker-rs-risks):

**Опровергнуто / не подтвердилось:**

- Экономия иерархии на малых-средних специфицируемых задачах: налог 3–11× по токенам и 4–9× по времени без прироста качества (COST-001, находка 18); «flat тонет на T3» не подтвердилась.
- LONG-001 H1: flat-агент справился с крупной темплейтной миграцией (3/3 чисто, 167/167 тестов) — находка 22; LONG-002 H1/H2: flat 3/3 чисто на архитектурной задаче (пик 53–66k ≪ 200k), ни один из 5 предсказанных failure-режимов flat не материализовался, ни один из 4 критериев переломного пункта не выполнен (+410% new-токенов у иерархии) — находка 28.
- «Тонкий координатор ⇒ экономия контекста всей схемы»: пик не исчезает, а переезжает на executor'а (56–76k, выше flat в 2 из 3 прогонов LONG-002) — находка 27, §10.
- REVIEW-001 H3: финальное качество по слепой оценке не выше — паритет (43.7 vs 43.0 vs base 42, разница в шуме) — находка 34.
- «Чистый» раскол по всем трём осям эксперта не достигнут (хранилищевая ось не развела исполнителей) — находка 15.

**Не проверено:**

- Переломный пункт «flat тонет» (пик >200k) не достигнут ни в одном эксперименте; гипотеза-кандидат — неспецифицируемые задачи (отладка legacy, «сделай как лучше») — §10, находки 22, 28.
- Версионная устойчивость: механика M1–M12 проверена только на opencode v1.18.18 — §4, §10.
- Взвешенные голоса советов — §10; эффект иерархического ревью на молодых/черновых документах — §9e; воспроизводимость экономии full-токенов (−29%) на других классах задач — находка 33; перенос рекомендаций в рабочие проекты — §11.

## 3. Альтернативы в индустрии

По отчётам worker-rs-industry и worker-rs-comparison (все утверждения — с URL из отчётов воркеров):

- **AutoGen (Microsoft)** — слоистая архитектура (Core → AgentChat), group chat, AgentTool; Magentic-One: Orchestrator → 4 исполнителя (2 уровня); общий chat history, изоляции в group chat нет; **maintenance mode** (багфиксы, новых фич не будет), миграция на Microsoft Agent Framework; нативный OpenTelemetry. (https://github.com/microsoft/autogen; magentic-one.md, swarm.ipynb, telemetry.md в репо)
- **CrewAI** — ролевая модель, режимы sequential/hierarchical: ровно **один** авто-менеджер (2 уровня), цепочек менеджеров нет; `respect_context_window` — авто-суммаризация истории вместо изоляции; лимиты `max_iter`, `max_rpm`, `max_execution_time`; E2B/Modal-sandbox; AMP Suite (enterprise tracing). (https://github.com/crewAIInc/crewAI; docs/edge/en/concepts/processes.mdx, agents.mdx)
- **LangGraph (LangChain)** — низкоуровневый граф (Pregel), субграфы; иерархические команды «supervisor of supervisors» (**3 уровня**) через композицию; у каждого субграфа своё состояние (наверх — только результат); interrupts/human-in-the-loop; durable execution; наблюдаемость LangSmith. (https://github.com/langchain-ai/langgraph; hierarchical_agent_teams.ipynb @23961cf)
- **MetaGPT** — SOP-ориентированная «программная компания» (Code = SOP(Team)): PM → Architect → Engineer, ~2 уровня, фиксированная иерархия, динамического спавна нет; приватные memory + msg_buffer у ролей (фильтрация по подпискам); долларовый бюджет `investment`. (https://github.com/FoundationAgents/MetaGPT; metagpt/software_company.py, metagpt/roles/role.py)
- **OpenAI Swarm / Agents SDK** — peer-to-peer handoff (flat, без иерархии), в SDK — agents-as-tools, guardrails, sessions, tracing; общего контекста между уровнями нет изоляции. (https://github.com/openai/swarm; https://github.com/openai/openai-agents-python)

**Общие паттерны индустрии** (worker-rs-industry): делегирование как ядро (handoff/AgentTool/delegation), но преимущественно peer-to-peer или один уровень иерархии; общий контекст по умолчанию; **файловый обмен как единственный канал координации не встречен ни у одного фреймворка** (MetaGPT ближе всего — артефакты между ролями, но в памяти, не на диске); глубоко вложенные иерархии как встроенный примитив отсутствуют — у CrewAI max 1 уровень менеджера, у LangGraph — ручная реализация.

**Позиция Mr. Wolf** (worker-rs-comparison): 3 уровня нативно + эмпирически проверенные пределы глубины и квоты фанаута (у альтернатив лимиты глубины/спавна не документированы); системные границы «permission glob: кто кого спавнит» — ни у одного из четырёх нет; уникальная сильная сторона — измеренная экономика (ни один фреймворк не публикует замеров overhead иерархии против flat); индустрия сильнее в наблюдаемости (OTel, LangSmith) и durable execution как промышленном аналоге доката.

## 4. Риски и ограничения

Реестр по worker-rs-risks (M1–M12 — реестр фактов механики opencode, §4; статусы — наблюдён/теория, митигация — закрыт/частично/не закрыт):

**Не закрытые риски:**

- **M8**: permission-стена покрывает только встроенные тулы — MCP/кастом-тулы (rtk, roster, tasklog, context7) проходят мимо `bash: deny`; deny ≠ изоляция (наблюдён, находка 11). С связано **M10**: кастом-тулы выдаются субагентам всех уровней (осознанно принято).
- Path drift: воркеры пишут не в тот каталог (COST-001, 1/9); скретч-файл executor'а — нарушение «код только воркерами» (1 убитый прогон) — митигации в REPORT.md не описаны.
- Слепой судья глух к точечным фиксам: конверсия ревью в финальное качество нулевая (находка 34) — не закрыто.

**Частично закрытые:**

- **M11**: нет нативного таймаута `task`/`opencode run` — зависшая сессия ждёт вечно (находки 12, 21; HANG 46 мин в LONG-001 orch-3); внешний watchdog (bg+poll+kill 1800с, находка 30) обязателен, нативного решения нет.
- **M6**: `tool.execute.after` молчит при ошибке тула — слепота after остаётся ограничением платформы.
- Немые обрывы длинных прогонов (exit=0) при параллельном трафике провайдера — 4 из 7 flat-запусков (находка 36): ретраи лечат симптом, корневая причина не диагностирована.
- Переезд пика контекста на executor'а (находка 27, развитие — 35): «заявлять экономию контекста всей схемы нельзя» (§10).
- Экономический налог иерархии на специфицируемых задачах: +239…+1141% new-токенов, время ×1.5–2 (находки 18, 24; +410% в LONG-002).

**Закрытые (наблюдённые, с митигацией):** M1 (валидный конфиг + smoke), M2 (`permission.task`), M3 (glob-границы), M4 (`subagent_depth`), M5 (файл-ledger), M7 (плагин-журнал до permission + verify), M9 (прогоны без `--pure`), M12 (токен-учёт SQLite); слот-голодание ревью (находка 19 — лимит 3→5, не воспроизвелось в LONG-001/002); «монолитный завис» executor'а (ретрай-политика + промпт-указание); fast-fail rtk (находка 25b); обход правила эскалации (рекомендация `human_required`, находка 16); ошибки верификации (находка 20); атрибуция SDK из spawn-лога.

**Открытые вопросы (топ из 7, worker-rs-risks):** существует ли класс задач, где flat объективно тонет (неспецифицируемые задачи — кандидат); устраним ли переезд пика на executor'а; даёт ли изолированное ревью прирост финального качества на черновых документах; воспроизводима ли экономия full-токенов; какая провокация разведёт хранилищевую ось раскола (находка 15); сохранится ли механика M1–M12 при апгрейде opencode; пределы ретраев против немых обрывов (находка 36).

## 5. Рекомендации

Синтез рекомендаций из отчётов воркеров (§10–11 REPORT.md, выводы worker-rs-comparison):

1. **Применять иерархию выборочно, а не по умолчанию.** Правило из §10: иерархия — когда flat не справляется или когда ценны трассируемость, независимое ревью («новые глаза», находка 32), живучесть (докат ≈0.7×, находка 26) и экономия full-токенов (−29%, находка 33). Для специфицируемых задач flat экономичнее в 3–11 раз.
2. **Приоритет закрытия рисков:** M8/M10 (поверхность MCP/кастом-тулов у субагентов — принять или ограничить явно); внешний watchdog как обязательный элемент каждого прогона (M11); код-ревью каталогов воркеров против path drift; ретрай-политика + маркеры aborted против немых обрывов.
3. **Проверить нишевую гипотезу:** класс неспецифицируемых задач (отладка legacy без спеки, «сделай как лучше») как переломный пункт экономики — главный непроверенный кандидат (§10).
4. **Наследовать из индустрии** (выводы worker-rs-comparison): стандартизированные трейсы в семантике OpenTelemetry (AutoGen) и встроенные interrupts/human-in-the-loop (LangGraph) — прямые кандидаты в развитие схемы; эскалация «файл + второй запуск» — текущее узкое место.
5. **Версионная гигиена:** smoke-перепроверка механики M1–M12 при каждом апгрейде opencode (проверено только на v1.18.18).
6. **Процессуальное:** помечать планировочные решения `human_required` (находка 16); измерять эффект изолированного ревью на черновых документах до масштабирования практики ревью; вести токен-учёт per agent/model (SQLite) как стандарт отчетности — аналог есть не во всех индустриальных фреймворках.
