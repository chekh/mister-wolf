## 1. Подтверждено экспериментами

Механическое ядро схемы `Wolf → Executor → Workers` нативно реализуемо и воспроизводимо: по отчёту experiments подтверждено 16 позиций, и все они сходятся к выводу — иерархия держится не промптовой дисциплиной, а системными гарантиями платформы (concept, принципы 2–3, 11–12).

**Границы и контроль.** Тул `task` субагентам denied по умолчанию: без `permission.task` executor уходит в CLI-импровизацию с потерей контроля (находка 1, §4 M2, §7 TEST-001). Glob-границы «кто кого спавнит» жёсткие и падают с информативной ошибкой (находка 3, M3); `subagent_depth` режет третий уровень в рантайме даже при `task: allow` (находка 2, D-5); лимит воркеров через throw в before-хуке плагина работает как жёсткая квота (находка 8, D-9). Кворум/консенсус wolf считает безошибочно «строго по файлам» — независимый пересчёт 10/10 (находки 9–10); Council Mode подтверждён целиком: 11 советов, 8 сценариев, параллельный спавн семи воркеров одним сообщением (§1 H2, §5.3).

**Файловый протокол и живучесть.** Обмен только артефактами (brief / report / VOTE / VERDICT) переживает прерывания: докат после user abort и kill@50% без пересоздания готового подтверждён трижды, включая случай, когда докат обошёлся дешевле чистового прогона (находки 7, 17, 26; §5.4, §9c). Это второй по значимости результат после границ: протокол одновременно даёт изоляцию контекста уровней и восстановимость (concept, принципы 4, 13).

**Диспетчеризация и capacity.** Дробление задач executor-ом с обязательной таблицей декомпозиции и лимитом воркеров, поднятым до 5, устранило слот-голодание в длинных задачах (находка 31, §9c). Свойство «тонкого координатора» подтверждено: пик контекста wolf — 11–18k на двух классах задач, втрое тоньше flat (находка 23, §9c–9d).

**Первое экономическое преимущество — ревью.** На классе «итеративное ревью длинного документа» (REVIEW-001) изоляция перспектив бьёт по слепым зонам саморевью: major-дефектов найдено вдвое больше (57 против 26), пик — completeness-раунд (находка 32, §9e). full-токены — первая метрика, где иерархия выигрывает: −29% против flat (у flat cache.read раздувается до 7–12M), а пик контекста распараллеливается на сеансы ревьюеров (находки 33, 35).

**Поведение flat.** Специфицируемая задача оказалась однопроходной: flat строит фреймворк по спеке за один проход с 0–1 правками (находка 28, §9d).

## 2. Остаётся гипотезой

Опровергнутое и непроверенное из отчётов experiments и risks очерчивает честную границу схемы: механика доказана, экономика — нет.

**Экономическое обоснование на генеративных задачах опровергнуто.** Токен-налог иерархии +274–1141% на малых задачах (находка 18) и +239–410% на длинных — без прироста качества; capacity-гипотеза flat опровергнута дважды: чистая миграция 48 файлов/2597 строк (находка 22, §9c) и 3/3 чистых прогона фреймворка с пик 53–66k, ни один из пяти предсказанных failure-режимов flat не материализовался (§9d). Слепая оценка финального качества в ревью — паритет 43.7 против 43.0 при шуме 41–46 (находка 34, §9e).

**Непроверенное.** Переломный пункт «оркестрация против flat» (overhead ≤50%) не достигнут ни в одном эксперименте — тренд «больше задача — меньше налог» есть, но порог не взят даже на архитектурном классе (§9b–9d, §10, находка 24 по risks). Класс задач, где flat объективно тонет (пик >200k), в песочнице не построен; гипотеза-кандидат — неспецифицируемые задачи (отладка legacy без спеки, «сделай как лучше») — не проверена (находка 28, §10). «Экономия контекста всей схемы» не подтверждена: пик переезжает на executor-а (56–76k, выше flat в 2/3 прогонов LONG-002) — «тонким» остаётся только wolf (находка 27, §10). Также не проверены: эффект иерархического ревью на молодых/черновых документах (§9e), взвешенные голоса советов (§10), версия-зависимость механики M1–M12 за пределами opencode v1.18.18 (§4, §10), рантайм-учёт токенов через плагин (§9). «Чистый» раскол планов по всем трём осям эксперта не достигнут — хранилищевая ось не развелась ни разу (находка 15, §9a).

## 3. Альтернативы в индустрии

По отчётам industry и comparison (все URL — из этих отчётов; док-сайты были недоступны из сети эксперимента, факты добыты из официальных репозиториев):

- **AutoGen (Microsoft)** — плоские teams (RoundRobin, Selector, Swarm, Magentic-One, DiGraph) на Actor model; в GroupChat контекст общий, изоляция только через кастомные Team; встроенной иерархии менеджер→исполнители нет, риск бесконечных циклов без лимитов ходов. Фреймворк в maintenance mode, преемник — Microsoft Agent Framework. (https://github.com/microsoft/autogen; https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/teams.html)
- **CrewAI** — Crews с процессами Sequential/Hierarchical (автоматический менеджер-агент делегирует и валидирует) плюс event-driven Flows; Unified Memory со scope-изоляцией (MemoryScope/MemorySlice). Иерархия — максимум 2 уровня; hierarchical требует дополнительных LLM-вызовов. (https://docs.crewai.com/concepts/crews; https://docs.crewai.com/concepts/memory; https://github.com/crewAIInc/crewAI)
- **LangGraph (LangChain)** — low-level графы состояний: nodes/edges, subgraphs, checkpointing, interrupts для human-in-the-loop; допускает иерархию supervisor-of-supervisors любой глубины, но строится разработчиком статически в коде, рантайм-спавна нет. Единственная альтернатива с явной доктриной «приватный scratchpad против общего». Порог входа высокий. (https://github.com/langchain-ai/langgraph; https://langchain-ai.github.io/langgraph/concepts/multi_agent/)
- **MetaGPT** — SOP-конвейер ролей software-компании (PM → Architect → ProjectManager → Engineer), publish-subscribe через Environment; оркестратор гибкий отсутствует, порядок фиксирован. Бюджет: `invest()`/max_budget с жёстким стопом NoMoneyException. (https://github.com/FoundationAgents/MetaGPT; https://github.com/FoundationAgents/MetaGPT/blob/main/metagpt/team.py; https://github.com/FoundationAgents/MetaGPT/blob/main/metagpt/utils/cost_manager.py)
- **OpenAI Agents SDK** (дополнительный) — handoffs (полная история) и agent-as-tool (изоляция); иерархии нет, max_turns по умолчанию 10. (https://github.com/openai/openai-agents-python)

Ключевые выводы сравнения (comparison, выводы 1–7): глубину больше двух уровней дают только Mr. Wolf (рантайм-спавн) и LangGraph (статически); файловый обмен как механизм координации не даёт нативно ни один фреймворк; Mr. Wolf — единственная схема с собственными измерениями оверхеда и найденной нишей выигрыша (full −29% на ревью), у альтернатив — только учёт (usage-метрики AutoGen/CrewAI, долларовый budget у MetaGPT); индустриальный стандарт наблюдаемости — OpenTelemetry/LangSmith/AMP с UI, тогда как Mr. Wolf силён моделью доверия (журнал до permission-проверки + независимый пересчёт по первичным файлам).

## 4. Риски и ограничения

По отчёту risks: реестр — **24 риска** (22 наблюдённых, 2 теоретических); митигации: 14 закрыто, 5 частично, 5 не закрыто.

**Главный вывод реестра:** границы схемы не ломаются — все наблюдённые сбои операционные, а не структурные. Закрытые: слот-голодание ревью (находка 19; лимит 3→5, в LONG не воспроизвелось — находка 31), зависания сессий без нативного таймаута (находки 21, 25, 30; внешний watchdog + ретраи), немые обрывы провайдера 4/7 flat-запусков (находка 36; ретраи с паузами), монолитный завис executor-а и fast-fail rtk-обёртки (находка 25a–b; ретрай-политика), прерывания (докат, находки 17, 26), конфиг-долг M1 (находка 4; smoke-проверка), пробелы журнала M6/M9 (фиксы), ложный FAIL верификатора (фикс грепа).

**Незакрытые и частичные:** токен-налог +239–1141% — экономически не закрыт, переломный пункт не достигнут; переезд пика контекста на executor-а (находка 27) — митигации нет; path drift и скретч-файлы executor-а (§9b) — ловятся только постфактум/промптом; дыра M8 — MCP/кастом-тулы вне permission-стены (находка 11) — частично; судья-метрика глуха к точечным правкам (находка 34); вырождение советов в единогласие и невыполнение условия эскалации (находки 14, 16) — частично; теория: версия-зависимость M1–M12 и взвешенные голоса (§10).

**Открытые вопросы (7, из risks):** существует ли класс задач, где flat объективно тонет; где переломный пункт иерархии; как удержать пик контекста executor-а; даёт ли иерархическое ревью прирост качества на черновых документах; достижим ли чистый раскол планов по хранилищевой оси; можно ли системно закрыть path drift и скретч-файлы; сохраняется ли механика и дыра M8 на новых версиях opencode и работают ли взвешенные голоса.

## 5. Рекомендации

Формулируются строго из выводов отчётов:

1. **Применять иерархию избирательно, по классам задач.** Правило из risks (частичная митигация налога): «иерархия только когда flat не справляется»; подтверждённая ниша — итеративное ревью длинных документов (major ×2.2, full −29%, находки 32–33). Для специфицируемых задач экономика на стороне flat (находки 22, 28, §9d).
2. **Проверить гипотезу о неспецифицируемых задачах** — единственный кандидат на класс, где flat объективно тонет (§10, находка 28; risks, вопрос 1); одновременно искать переломный пункт overhead ≤50% (risks, вопрос 2).
3. **Закрывать незакрытые риски системно, а не промптом:** механизмы против path drift и скретч-файлов executor-а (risks, вопрос 6), решение по пику контекста executor-а (находка 27), политика write-тулов для дыры M8 (находка 11); при апгрейде opencode — обязательная smoke-перепроверка M1–M12 и взвешенных голосов (§10; risks, вопрос 7).
4. **Развивать нишу ревью на черновых документах** — зрелый документ дал паритет по слепой оценке (находка 34), эффект на документах с оставшимися critical не измерен (§9e; risks, вопрос 4).
5. **Переносить паттерн, а не фреймворк.** По comparison (вывод 7, §11 REPORT.md): проверенная ценность Mr. Wolf — системные границы (permission-глобы, depth, квоты), spawn-логгер с независимой верификацией и токен-учёт — переносима в рабочие проекты независимо от выбора стека.
6. **При выборе индустриального стека** (industry, выводы): для глубины >2 уровней кандидаты — LangGraph (статическая иерархия любой глубины, доктрина приватного scratchpad) или CrewAI (2 уровня, MemoryScope); AutoGen не выбирать как устаревший (maintenance mode); MetaGPT пригоден для жёстких SOP-конвейеров с жёстким бюджетом.
