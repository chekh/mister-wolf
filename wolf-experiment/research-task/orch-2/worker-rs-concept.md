# Worker-rs-concept: принципы трёхуровневой схемы Mr. Wolf

## Сводка

Схема Mr. Wolf — иерархия Wolf (координатор, уровень 0) → Executor (менеджер
задачи, уровень 1) → Workers (однозадачные исполнители, уровень 2),
реализованная нативными средствами opencode (тул task, permission-карты,
subagent_depth, плагины) без CLI-обходов. Ниже 15 принципов, извлечённых из
правил песочницы (AGENTS.md), итогового отчёта (REPORT.md, §1–§8), хронологии
фаз 1–4 (logs/phase-1-report.md), трёх Task Briefов Wolfа (coordinator/) и
frontmatter/ролей агентов (.opencode/agents/). Рамка дисциплины: работа только
внутри wolf-experiment/, язык артефактов — русский (AGENTS.md). Только
рефлексия написанного, без оценок и рекомендаций.

## Принципы

1. **Трёхуровневая иерархия координатор → менеджер → исполнители.** Wolf
   ставит задачи брифами и выносит вердикт по отчётам; Executor декомпозирует
   и диспетчеризует; воркеры исполняют по одной подзадаче.
   Источники: AGENTS.md (шапка); REPORT.md §1, §3; logs/phase-1-report.md
   (раздел Гипотеза); .opencode/agents/{wolf-coordinator,executor-lead,
   worker-implementer}.md (маркировка уровень 0/1/2).

2. **Спавн по умолчанию запрещён; границы кто-кого — glob-правила
   permission.task.** Тул task субагентам denied по умолчанию; право
   снимается явно: wolf → только executor-*/council-*/planner-*, executor →
   только worker-*; нарушение падает с ошибкой, цитирующей правила;
   CLI-обходы запрещены Constraints брифов.
   Источники: REPORT.md §2 п.2, §4 (M2–M3); phase-1-report.md (находки 1, 3);
   wolf-coordinator.md и executor-lead.md (frontmatter); task-brief-001.md
   (Constraints).

3. **Жёсткий лимит глубины иерархии.** subagent_depth: 2; воркеры не спавнят
   агентов (тула task нет — физически не можешь); попытка 3-го уровня режется
   в рантайме даже у агента с task: allow (probe-тест D-5).
   Источники: AGENTS.md; REPORT.md §4 (M4), §1 (H1.4); phase-1-report.md
   (H1.4, находка 2); worker-implementer.md (Ограничения).

4. **Файловый протокол — единственный канал между уровнями; артефакты
   машиносчитаемы.** Обмен brief / report / decision / кодом (в советах:
   question / opinion / synthesis / escalation / final-decision), не
   пересказом; контракты VOTE:, VERDICT:, шаблон брифа (Metadata / Task /
   Acceptance Criteria / Constraints) и шаблон отчёта executorа.
   Источники: AGENTS.md; REPORT.md §2 п.3, §6; task-brief-001.md;
   wolf-coordinator.md (режим 1, п.1–2).

5. **Wolf не делает работу сам.** Не пишет код, не запускает команды, не
   читает код — только метаданные (брифы, решения, синтезы); вердикт по
   Acceptance Criteria — строго по отчёту executorа, НЕ по коду; создаёт
   файлы только в coordinator/ и councils/**.
   Источники: AGENTS.md; wolf-coordinator.md (Роль, Ограничения, режим 1
   п.3); REPORT.md §5.1; phase-1-report.md (TEST-001 №2).

6. **Executor не пишет код сам — только через воркеров (уточнено таблицей
   декомпозиции).** Базовое правило — код только воркерами; в позднем цикле
   (LONG-001) уточнено: TRIVIAL/SIMPLE executor делает сам, MEDIUM/COMPLEX —
   только воркерам; решение фиксируется обязательной таблицей декомпозиции в
   отчёте; мелкий фикс руками без классификации в таблице запрещён.
   Источники: AGENTS.md; executor-lead.md (Декомпозиция, Ограничения);
   task-brief-long-orch-1.md (Constraints); REPORT.md §9c.

7. **Узкая специализация и однозадачность воркеров.** Роли разделены:
   implementer (ровно одна подзадача, создаёт только указанный файл),
   reviewer (read-only, вердикт), researcher (read-only, findings); в
   исследовательском цикле — узкие воркеры worker-rs-* по одному вопросу
   каждый.
   Источники: worker-implementer.md, worker-reviewer.md, worker-researcher.md;
   task-brief-rs-orch-1.md; phase-1-report.md (фаза 3).

8. **Изоляция контекста уровней и контекст-бюджет воркера.** Каждый уровень
   видит только своё: воркер не видит бриф (это нормально), wolf не видит
   код; в спавн-промпт кладут конкретную подзадачу, только нужные
   файлы/интерфейсы и контракт результата — не весь бриф.
   Источники: worker-implementer.md (роль); executor-lead.md
   (Контекст-бюджет); REPORT.md §1 (H1.3); phase-1-report.md (H1.3).

9. **Тиры моделей сложность-модель.** Координатор и быстрые члены совета =
   k3-256k; исполнитель и глубокие члены = glm-5.2; однозадачные воркеры =
   glm-5-turbo — чем уже задача, тем дешевле модель.
   Источники: REPORT.md §3 (Модели по тирам); phase-1-report.md (шапка,
   фаза 4); frontmatter всех агентов (.opencode/agents/).

10. **Обязательное независимое ревью перед отчётом.** worker-reviewer
    (read-only, edit/bash denied) проверяет код против требований брифа
    дословно; вердикт VERDICT: APPROVED|CHANGES первой строкой; при
    проблемах — воркер-фиксер, а не сам executor (кроме TRIVIAL);
    замечания устранены или обоснованно отклонены.
    Источники: executor-lead.md (процедура п.3–4); worker-reviewer.md;
    task-brief-long-orch-1.md (AC7); REPORT.md §5.1; phase-1-report.md
    (фаза 3).

11. **Квоты на спавны; реюз воркера; partial — нормальный исход.** Лимит
    воркеров enforced системно: плагин-счётчик per sessionID спавнера,
    throw в before-хуке (ошибка видна модели), env WOLF_WORKER_LIMIT
    (дефолт 3, в LONG-001 поднят до 5); реюз воркера — нативный параметр
    task_id (дозапрос тому же, не новый спавн); кончились слоты — завершить
    отчётом со статусом partial, это нормально.
    Источники: REPORT.md §6, §9c; phase-1-report.md (находка 8, D-9);
    executor-lead.md (п.4); executor-researcher.md (п.2).

12. **Верификация по системным данным, не по самодекларациям.** Системная
    правда — плагин-журнал spawn-log.jsonl (пишет ДО permission-проверки —
    видны отклонённые попытки) и независимый пересчёт verify-скриптами по
    первичным артефактам (голоса/глубина/квоты), а не по сводкам агентов;
    wolf считает голоса строго по VOTE-строкам файлов, не по памяти.
    Источники: REPORT.md §2 п.4, §6; phase-1-report.md (фаза 3, фаза 4);
    wolf-coordinator.md (Ограничения).

13. **Живучесть файлового протокола: докат после прерывания.** Прерывание
    процесса (user abort, таймаут) переживается: артефакты остаются на диске;
    новый запуск wolfа диспетчерит executorа довыполнить — тот не
    пересоздаёт готовое, докатывает пропущенное, отчёт с пометкой о докате.
    Источники: REPORT.md §2 п.3, §5.4; phase-1-report.md (фаза 3, Живучесть).

14. **Три режима оркестрации: конвейер / консилиум / совет.** Конвейер
    (wolf → executor → воркеры-роли); консилиум (N executorов планируют
    параллельно и без создания файлов → wolf финализирует decision-файлом →
    один executor исполняет); совет (члены пишут мнения с VOTE → quorum /
    consensus_threshold → synthesis; при недостижении консенсуса или
    human_required — escalation вместо решения).
    Источники: REPORT.md §2 п.1, §5.1–5.3; wolf-coordinator.md (режимы 1–3);
    phase-1-report.md (TEST-002, фаза 4, Вывод).

15. **Синтез — только из отчётов нижнего уровня.** Аналитическая записка
    executorа = синтез отчётов воркеров, не выдумывать факты — только то,
    что вернули воркеры; executor-researcher сам в веб не ходит (твои
    воркеры ходят за тебя); wolf судит по отчётам, а не по коду.
    Источники: task-brief-rs-orch-1.md (Task п.2, Constraints);
    executor-researcher.md (п.3, Ограничения).
