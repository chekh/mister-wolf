# Реестр рисков многоагентной схемы Mr. Wolf

Источник: `REPORT.md` (wolf-experiment, консолидация фаз 1–4 + SPLIT/COST/LONG-001/LONG-002/REVIEW-001).
Ссылки: «Нах. N» — находка из §8/§9a–e; M# — реестр механики §4; § — раздел REPORT.md.

## Сводка

Схема `Wolf → Executor → Workers` механически воспроизводима нативными средствами opencode
(границы спавна, depth, лимиты, журналирование), и главный класс подтверждённых рисков —
не «сломанные границы», а **операционные failure-режимы исполнения** (слот-голодание, зависания,
немые обрывы, path drift) и **экономика** (налог 3–11× токенов на малых задачах; пик контекста
переезжает на executor'а). Большинство наблюдённых инцидентов закрыто ретраями/watchdog'ом/
докатом; не закрыты: path drift, скретч-файлы executor'а, переезд пика контекста, глухость
судьи-метрики, взвешенные голоса. Переломный пункт выгоды иерархии так и не достигнут —
единственный экономический прецедент (full −29%) получен на классе «итеративное ревью
длинного документа».

## Реестр рисков

| Риск | Статус (наблюдён + находка/§, или теория) | Митигация |
|---|---|---|
| Субагент без `task` импровизирует CLI-обход (`opencode run`), контроль потерян | наблюдён: TEST-001 №1 (§7), Нах. 1, M2 | **закрыта**: `permission.task` + glob-границы «кто кого» (M2/M3) |
| Совет/консилиум вырождается в единогласие — у задачи аттрактор, приоритеты не разводят | наблюдён: SPLIT-001 раунд A, Нах. 14 | **частично**: брифы с развилками (необязательная персистентность, ресурсный фактор) провоцируют раскол; автоматической гарантии нет |
| Формальное условие эскалации при расколе («И разные хранилища») легко не выполняется | наблюдён: SPLIT-001 раунд B, Нах. 16 | **частично**: помечать планировочные решения `human_required` явно (рекомендация) |
| Слот-голодание ревью: лимит воркеров съеден фиксом | наблюдён: COST-001 ~5/9 прогонов, Нах. 19 | **закрыта**: лимит 3→5 + ревью в доводочной сессии; LONG-001/002 не воспроизвелось (§9c, Нах. 31) |
| Path drift: воркеры пишут мимо целевого каталога | наблюдён: COST-001 1/9 (§9b) | **не закрыта**: ловится только постфактум независимой верификацией |
| Скретч-файл executor'а — код без воркера (нарушение протокола) | наблюдён: COST-001, 1 прогон (§9b) | **не закрыта**: только протокольное правило «код только воркерами» |
| Зависание сессии после спавна — нативного таймаута в `opencode run` нет | наблюдён: COST-001 (Нах. 21), LONG-001 orch-3 (46 мин) | **закрыта**: внешний watchdog bg+poll+kill 1800с (Нах. 30) + ретрай |
| Монолитный завис executor'а: генерирует сам вместо диспетчеризации, ноль спавнов | наблюдён: LONG-001 orch-3, Нах. 25a | **закрыта**: ретрай-политика + ранний промпт-запрет монолита (в 3b-ретрай сработало) |
| Fast-fail через rtk-обёртку: составная команда порезана, смерть сессии за 19с | наблюдён: LONG-001 orch-3b, Нах. 25b | **закрыта**: ретрай (3b-ретрай чистый за 7.2 мин) |
| Немые обрывы провайдера при параллельном трафике (exit=0, лог обрывается) | наблюдён: REVIEW-001 4/7 flat-запусков, Нах. 36 | **закрыта**: ретраи с паузами (до 4-й попытки, пауза 10 мин) + маркеры aborted |
| Прерывание/kill процесса в середине работы | наблюдён: TEST-002, SPLIT-001B, LONG-001 orch-2 (§5.4, Нах. 17, 26) | **закрыта**: файловый протокол + докат (~0.7× стоимости чистового прогона) |
| Переезд пика контекста на executor'а (56–76k, выше flat в 2/3 прогонов) — «тонким» остаётся только wolf | наблюдён: LONG-002, Нах. 27, §10 | **не закрыта**: экономии контекста всей схемы нет; изоляция смягчает лишь в ревью-схеме (Нах. 35) |
| Токен-налог иерархии: +274–1141% на малых задачах, +239–410% на длинных; перелом (≤50%) не достигнут | наблюдён: COST-001 (Нах. 18), LONG-001 §9c, LONG-002 §9d, §10 | **частично**: правило «иерархия только когда flat не справляется»; экономически не закрыта |
| Cache-балласт flat при многократных проходах длинного документа (cache.read 7–12M) | наблюдён: REVIEW-001, Нах. 33 | **закрыта**: изоляция сессий иерархией (full −29%) для этого класса задач |
| Дыра permission-стены: MCP/кастом-тулы (rtk, roster, tasklog) проходят мимо `bash: deny` | наблюдён: M8, Нах. 11 | **частично**: принятый остаточный риск для read-only тулов; для write-тулов не закрыта |
| Конфиг-долг: невалидный `tools:`-массив валит конфиг агента целиком | наблюдён: M1, Нах. 4 | **закрыта**: smoke-проверка конфигов через `opencode run` |

| `--pure` отключает собственные автодискавери-плагины — журнал исчезает | наблюдён: M9 | **закрыта**: правило «прогоны с плагин-журналом — без --pure» |

| Пустое поле `agent` в SDK `client.session.get()` — рантайм-атрибуция из SDK невозможна | наблюдён: §10 | **закрыта**: атрибуция из spawn-лога/конфига |
| Версия-зависимость механики M1–M12 (проверена на v1.18.18; апгрейд может менять семантику depth/permission) | теория — не наблюдён (§10) | **частично**: процедура smoke-перепроверки при апгрейде |
| Взвешенные голоса советов (участник ×2) | теория — не проверялся (§10) | **не закрыта**: временный эквивалент — вес при синтезе wolf'ом |

Итог: **24 риска** (22 наблюдённых, 2 теоретических). Митигации: **14 закрыто, 5 частично, 5 не закрыто**.

## Открытые вопросы

1. Существует ли класс задач, где flat объективно тонет (пик контекста >200k)? Гипотеза-кандидат — неспецифицируемые задачи (отладка legacy без спеки, «сделай как лучше») — не проверена (§10, Нах. 22, 28).
2. Где экономический переломный пункт иерархии (overhead ≤50%)? Тренд «больше задача — меньше налог» есть, но порог не достигнут даже на архитектурном классе (§10, Нах. 24).
3. Как удержать пик контекста executor'а (56–76k, растёт с задачей) — переезд пика зафиксирован, митигации нет (Нах. 27).
4. Даёт ли иерархическое ревью прирост финального качества по слепой оценке на молодых/черновых документах (где остались critical)? На зрелом документе конверсия нулевая (REVIEW-001, H3, Нах. 34).
5. Достижим ли «чистый» раскол планов по всем трём осям эксперта? Хранилищевая ось не развелась ни разу — нужны требования типа multi-process/распределённости (Нах. 15, §10).
6. Можно ли системно (не промптом) закрыть path drift и скретч-файлы executor'а — единственные наблюдённые нарушения протокола без механизма предотвращения (§9b)?
7. Сохраняется ли механика M1–M12 и дыра M8 на новых версиях opencode, и работают ли взвешенные голоса в советах — оба пункта не проверены (§10).
