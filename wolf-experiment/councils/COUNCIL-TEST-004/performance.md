# Мнение совета: производительность (COUNCIL-TEST-004)

## Оценка вариантов

- **A) Оптимизация SQL и индексов** — устраняет корневую причину медленных запросов: снижает latency в разы без дополнительной инфраструктуры, уменьшает нагрузку на БД. Но не решает проблему повторяющихся горячих чтений при пиковой нагрузке.
- **B) Redis-кэш** — даёт ответы за миллисекунды и разгружает БД, но при неоптимизированных запросах кэш-промах (cache miss) всё равно упрётся в медленный SQL; плюс стоимость инфраструктуры и сложность инвалидации.
- **C) Оба варианта** — оптимизированный SQL делает промахи дешёвыми, а кэш снимает повторные горячие чтения: это единственный путь стабильно держать p95 < 100ms при высокой нагрузке.

## Рекомендация

Для требования p95 < 100ms под высокой нагрузкой одного решения недостаточно:
индексы без кэша не выдержат пиков, кэш без индексов не спасёт при промахах.
Рекомендую вариант C с приоритетом: сначала оптимизация SQL (дёшево, устраняет
причину), затем кэширование горячих данных (стабилизирует хвост latency).

VOTE: C

## Риски

- Двойная работа повышает стоимость и время внедрения при ограниченном бюджете.
- Кэш добавляет операционную сложность (инвалидация, консистентность данных).
