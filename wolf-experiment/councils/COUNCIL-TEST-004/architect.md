# Мнение архитектора — COUNCIL-TEST-004

## Оценка вариантов

- **A) Оптимизировать SQL-запросы и индексы** — устраняет причину, а не симптом:
  не добавляет новых компонентов, точек отказа и логики инвалидации;
  сопровождаемость и наблюдаемость системы остаются прежними.
- **B) Добавить Redis-кэширование** — вносит новую зависимость в инфраструктуру:
  консистентность данных, инвалидация, эксплуатация ещё одного сервиса — при
  ограниченном бюджете это рост TCO и сложности без гарантии устранения узкого
  места. Кэш поверх медленных запросов лишь маскирует проблему.
- **C) Оба варианта** — максимальная стоимость и сложность сразу; правильный
  эволюционный путь — сначала A, затем точечный кэш по метрикам, если p95
  всё ещё > 100ms.

## Рекомендация

С позиции долгосрочной архитектуры начинать надо с устранения корневой причины:
оптимизированные запросы и индексы дают детерминированное улучшение для каждого
запроса без новых режимов отказа. Кэширование — это вторичный слой, который
легко добавить позже на конкретные горячие пути, когда метрики покажат, где он
действительно нужен; преждевременный кэш фиксирует текущую структуру запросов
и усложняет рефакторинг схемы. Это соответствует принципу эволюционной
архитектуры: минимальная сложность, достаточная для требования (< 100ms p95).

VOTE: A

## Риски

- Если после оптимизации SQL latency всё ещё > 100ms p95 (тяжёлые агрегации,
  холодные чтения) — кэш всё же понадобится; решение A нужно зафиксировать
  как первый этап с измеримым критерием перехода к кэшу.
- Без метрик «до/после» есть риск оптимизировать не те запросы: нужен
  query-профилинг до начала работ.
