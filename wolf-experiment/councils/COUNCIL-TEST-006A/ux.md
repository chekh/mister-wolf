# Мнение UX — COUNCIL-TEST-006A (council: architecture)

## Оценка вариантов

- **A) PostgreSQL** — с позиции повседневной работы команды: богатая работа с JSON (jsonb, операторы `->`, `->>`), оконные функции и CTE делают сложные аналитические запросы читаемыми и поддерживаемыми; понятный EXPLAIN упрощает отладку производительности.
- **B) MySQL** — проще в базовых сценариях, но JSON-возможности беднее, сложные аналитические запросы часто требуют обходных путей (временные таблицы, процедуры), что ухудшает читаемость кода и повышает когнитивную нагрузку разработчиков.

## Рекомендация

Для аналитического сервиса с JSON-полями и сложными запросами PostgreSQL даёт разработчикам более прямой и предсказуемый инструментарий: меньше «костылей», лучше диагностика запросов, шире экосистема аналитических расширений. Это снижает порог входа и стоимость поддержки.

VOTE: A

## Риски

- Если команда исторически работает только с MySQL, переход потребует обучения — краткосрочное трение.
- Избыточная мощь PostgreSQL (расширения, кастомные типы) может провоцировать переусложнение схемы — нужны соглашения по стилю.
