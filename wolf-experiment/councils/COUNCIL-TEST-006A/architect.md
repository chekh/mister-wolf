# Мнение архитектора — COUNCIL-TEST-006A

## Оценка вариантов

**A) PostgreSQL** — оптимален под профиль задачи: зрелый планировщик для сложных
запросов (CTE, оконные функции, материализованные представления), JSONB с
GIN-индексами и богатыми операторами, расширяемость (TimescaleDB, pg_partman)
даёт запас для роста аналитической нагрузки без смены платформы.

**B) MySQL** — приемлем для простых OLTP-нагрузок, но для аналитики слабее:
JSON-тип вторичен (без сопоставимого индексирования), планировщик и поддержка
сложных SQL ограничены, меньше пространство для эволюции схемы и партиционирования.

## Рекомендация

Профиль «сложные запросы + JSON-поля» — прямая зона силы PostgreSQL: JSONB как
первоклассный тип с индексацией и предикатами, плюс траектория масштабирования
(партиционирование, расширения, репликация для чтения) без миграций в будущем.
Выбор MySQL здесь создал бы архитектурный долг при первом же росте сложности
аналитики.

VOTE: A

## Риски

- PostgreSQL требовательнее к настройке (autovacuum, планировщик) — нужен
  компетентный эксплуатационный контур.
- Глубокая связка с JSONB может затруднить возможную будущую миграцию на другую
  СУБД — стоит изолировать работу с JSON в слое доступа к данным.
