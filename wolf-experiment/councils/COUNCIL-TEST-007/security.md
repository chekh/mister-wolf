# Мнение совета: безопасность (COUNCIL-TEST-007)

## Оценка вариантов

- **A) Удалить сразу** — максимальное быстрое сокращение поверхности атаки, но резкий
  обрыв для ~1000 пользователей без данных об использовании: отказы интеграций
  провоцируют обходные решения (кэширование токенов, самоподписные прокси), что
  само по себе риск.
- **B) Оставить навсегда** — худший вариант по безопасности: мёртвый legacy-код
  остаётся постоянной поверхностью атаки, его перестают тестировать и патчить,
  уязвимости накапливаются без плана выхода.
- **C) Deprecation warning + удаление через 6 месяцев** — управляемое сжатие
  поверхности атаки: срок даёт пользователям миграцию, а warning + метрики
  использования дают данные, к кому применим forced upgrade перед удалением.

## Рекомендация

С точки зрения безопасности устаревшая функциональность — это непатчируемая
поверхность атаки, поэтому «оставить навсегда» неприемлемо. Но и мгновенное
удаление без данных об использовании создаёт операционный риск и стимулирует
небезопасные обходные пути у пользователей. Вариант C — стандартная безопасная
практика вывода функциональности из эксплуатации: прозрачность (warning),
сбор данных об использовании, плановое сокращение attack surface через 6 месяцев.

VOTE: C

## Риски

- За 6 месяцев деприкации legacy-код всё ещё эксплуатируем: необходимо
  мониторить использование и быть готовым к экстренному удалению при находке
  уязвимости в нём.
- Без метрик использования даже к концу срока данных может не быть — нужно
  заложить telemetry с первого дня деприкации.
