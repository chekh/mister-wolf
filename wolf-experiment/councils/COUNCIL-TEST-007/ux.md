# Мнение UX — COUNCIL-TEST-007

## Оценка вариантов

- **A) Удалить сразу** — худший UX: у части из ~1000 пользователей (данных об
  использовании нет!) функциональность сломается без предупреждения. Использующие
  её клиенты узнают об удалении через ошибки в проде.
- **B) Оставить навсегда** — нейтрально для текущих пользователей, но устаревший
  API запутывает новых: документация с двумя путями, риск выбора «неправильного»
  варианта, рост когнитивной нагрузки.
- **C) Deprecation warning + удаление через 6 месяцев** — лучший баланс: пользователи
  получают чёткий сигнал (заголовки/логи/документация), предсказуемый срок на миграцию,
  а отсутствие телеметрии компенсируется наблюдением за реакцией на warning.

## Рекомендация

С позиции UX критично не «убивать» функциональность молча: при неизвестной доле
использования резкое удаление (A) гарантированно создаст негативный опыт и поток
обращений. Вариант C даёт пользователям время, предупреждение и понятный путь
миграции — стандарт отраслевой практики (Sunset/Deprecation headers), который
пользователи API ожидают и понимают.

VOTE: C

## Риски

- Если warning реализован только в документации (не в ответах API), часть клиентов
  его не увидит — нужны заголовки `Deprecation`/`Sunset` в ответах.
- 6 месяцев может не хватить «молчаливым» интеграциям; стоит зафиксировать дату
  удаления и канал уведомлений заранее.
