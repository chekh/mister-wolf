# Мнение council-architect — COUNCIL-TEST-007

## Оценка вариантов

- **A) Удалить сразу** — нарушение контракта с пользователями без переходного периода; при ~1000 пользователей и отсутствии телеметрии использования риск незаметного боя продакшена у клиентов высок. Архитектурно приемлемо только для pre-1.0/internal API.
- **B) Оставить навсегда** — вечная поддержка мёртвого кода: рост поверхности тестирования, усложнение каждого следующего рефакторинга, семантический балласт в контракте. Техдолг монотонно накапливается.
- **C) Deprecation warning + удаление через 6 месяцев** — стандартный lifecycle-паттерн: явный контракт миграции, обратная связь через телеметрию warning'ов до боевого удаления, ограниченный срок содержания legacy-ветки.

## Рекомендация

Вариант C — единственный, который управляет жизненным циклом API как процессом, а не событием: он даёт пользователям окно миграции, а платформе — данные об использовании (счётчик срабатываний warning'а) для осознанного решения об отсрочке. Шесть месяцев — разумный срок для аудитории такого размера; главное условие — фиксация даты удаления в changelog и документации с первого дня deprecation.

VOTE: C

## Риски

- Если часть пользователей не успеет мигрировать — разрушительное изменение всё же произойдёт; митигируется продлением срока по телеметрии warning'ов.
- Deprecation без назначенного владельца и даты в календаре вырождается в вариант B — нужен явный тикет на удаление.
