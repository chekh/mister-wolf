# Мнение совета COUNCIL-TEST-001 — роль: security

## Оценка вариантов

- **A) requests** — зрелый де-факто стандарт, TLS-верификация включена по умолчанию. Но: нет таймаута из коробки (риск зависших соединений/DoS сервиса) и заметная транзитивная surface (urllib3, certifi, idna, charset-normalizer) для supply-chain.
- **B) httpx** — безопасные дефолты: TLS-проверка по умолчанию и дефолтный таймаут (~5 c), современный API, меньше соблазна отключать проверки. Зависимостей сопоставимо с requests, но активная поддержка и HTTP/2.
- **C) urllib** — ноль внешних зависимостей (минимальный supply-chain риск), но слабые дефолты: нет таймаутов, нет retry, ручная работа с SSL/редиректами/заголовками — высокий риск ошибок в самописном коде (SSRF, некорректная обработка сертификатов).

## Рекомендация

С позиции безопасности минимизация зависимостей важна, но не ценой самописной обработки HTTP: ошибки ручного кода на urllib (таймауты, SSL-контекст, редиректы) — более реальный риск, чем две проверенные зависимости. httpx даёт лучший набор безопасных дефолтов (TLS on, таймаут из коробки) при сопоставимой с requests поверхности зависимостей; requests приемлем, но требует дисциплины по явным таймаутам.

VOTE: B

## Риски

- Любой вариант требует запрета `verify=False` / `trust_env` в ревью и пиннинга версий (lock-файл) для supply-chain-гигиены.
- Для requests обязательный код-ревью пункт: явный `timeout=` в каждом вызове, иначе зависания при экспорте CSV.
- Если сервис ходит по URL из внешних данных — ограничить схемы (http/https) и адреса (запрет localhost/приватных подсетей) независимо от выбранной библиотеки.
