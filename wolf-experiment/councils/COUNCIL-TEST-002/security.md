# Мнение совета COUNCIL-TEST-002 — безопасность

## Оценка вариантов

- **A) Микросервисы с самого начала** — максимальная поверхность атаки:
  межсервисные каналы, service-to-service аутентификация, распределение
  секретов, сеть. Для команды из 3 человек корректно настроить и поддерживать
  mTLS, управление секретами и аудит каждого сервиса нереалистично —
  безопасность будет принесена в жертву скорости.
- **B) Модульный монолит** — единый периметр безопасности: один вход, один
  набор секретов, один аудит-лог. Модульные границы позволяют применять
  принцип наименьших привилегий внутри приложения (изолировать модуль платежей
  или персональных данных) и упрощают будущий выделение компонентов.
- **C) Монолит с возможностью разделения позже** — периметр тот же, что у B,
  но без обязательной модульности границы доверия внутри кода размыты:
  смешение привилегий и данных, а разделение позже потребует реверс-инжиниринга
  зависимостей, включая скрытые потоки чувствительных данных.

## Рекомендация

С точки зрения безопасности модульный монолит минимизирует поверхность атаки
при дефиците людей на инфраструктурную безопасность (секреты, сети, mTLS,
патч-менеджмент N сервисов). Чёткие модульные границы дают контролируемые
точки доступа к чувствительным данным уже сейчас и делают будущее разделение
предсказуемым, без появления «диких» межмодульных потоков. Вариант C даёт тот
 же периметр, но без дисциплины границ — риск накопления переплетённых
 привилегий, которые потом дорого и небезопасно расцеплять.

## Риски

- Монолит = единая точка компрометации: пробой одного компонента даёт доступ
  ко всем данным внутри периметра; митигируется модульными ACL и шифрованием
  чувствительных данных.
- При будущем разделении возможна миграция секретов и аудита — планировать
  границы модулей заранее, чтобы выделение не меняло модель угроз.
