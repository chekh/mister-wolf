# Исполнение через L1/L2

## Обязательный вход

Оркестратор — L1, не L0 и не L2. До первого назначения проверь разрешённый scope, актуальные approved-входы, baseline, test-plan, права и зависимости. Зафиксируй ready-задачи и лимит повторов. На каждую задачу отслеживай исполнение, проверку соответствия, проверку качества и интеграцию отдельно. Не запускай воркера, если входы ещё зависят от неутверждённого решения.

Загрузи полный текст назначенной методики до её выполнения. Обязательные пункты отслеживай в доступном трекере или рабочем брифе; не добавляй новые статусы памяти. Недоступное действие передай ответственному уровню.


## Предусловия

Оркестратор исполнения — executor-lead. L0 поручает ему поставку. Проверь утверждённые входы, plan/test-plan, профиль проекта, разрешённые git-операции, baseline и workspace. Создай worktree по using-git-worktrees, если этого требует политика. До начала зафиксируй budget/retry limit и dependencies; default — 2 цикла исправления на задачу, затем пересмотр.

## Цикл задачи

1. Разрежь работу до конечных мандатов L2; архитектуру, стратегию поиска и зависимости определяет L1. Назначь владельца проверки общих связей. Выбери независимые ready-задачи, запусти параллельно в бюджете и с изоляцией; собери каждому TASK из using-skills. Передай ссылки и минимальный достаточный контекст, проверенные контракты и expected RESULT. L2 разрешено читать нужные файлы и потребителей; история родительской сессии не наследуется.
2. Доставь полную методику действия L2 и активный playbook, относящиеся нормы и TASK/RESULT/EVIDENCE; не весь процесс L1/ACCEPTANCE. Для регулярного шага/трения L1 проверяет tool-библиотеку и передаёт подходящий контракт. L2 не выбирает организацию и не спавнит.
3. Принимай RESULT по готовности: DONE → diff/evidence; DONE_WITH_CONCERNS → риск до ревью; NEEDS_CONTEXT → точный вход; BLOCKED → решение L1, готовое средство или разбиение. Следующий вызов получает решённый вопрос, короткий остаток и новый конечный лимит. Один эксперт — при точном пробеле; дорогой консилиум — только по критериям рамки L1. Изменение цели → L0. Дефект правила → жалобный триаж/Стюард. Не возвращай L2 прежнее «разберись» и не запускай идентичный провал.
4. Проверь allowlist и новые файлы, включая untracked: RESULT L2 не требует отдельного документа. Частные отчёты/скрипты в docs/dev нарушают состав папки; L1 встраивает полезные выводы в основные документы. Не удаляй чужое/прежнее автоматически. Проверь отсутствие посторонних изменений. Воркер не коммитит; L1 фиксирует результат разрешённым git-действием после проверок, включая авторизованность самого коммита.
5. Организуй независимое ревью соответствия, затем качества. Для малой задачи два мандата может выполнить один независимый reviewer в явном порядке; для значимого риска используй отдельные чистые ревью. Независимость от исполнителя обязательна.
6. Правки возвращай исполнителю с finding IDs. Изменения контракта повторно проверяются на соответствие, даже если проблема пришла с стадии качества. Minor не блокирует без объяснённого риска; сохрани техдолг в подходящем существующем объекте.
7. L1 отмечает задачу проверенной в плане с revision/evidence. Принятой поставкой она становится после интеграции и финального verdict L0.

## Бюджет действий

В каждом TASK задай execution: доступные model/variant, mode execute|solve,
лимит обращений и условие завершения. Механические действия — низкая глубина,
смысловая проверка — средняя; высокий режим только на адресный блокер, с учётом
явного выбора владельца. Проверяй фактическое применение по метаданным запуска,
не выдумывай поддержку полей. Доставленные методики и лица не ищутся повторно.
Каждый L2 возвращается после результата, первой неожиданной сложности или
конечного лимита; без заданного — не позднее 8 обращений к инструментам.
Неисчерпанный бюджет не разрешает новый способ поиска, исчерпанный — ложный успех. Повторный вызов получает только изменённые
основания, findings и остаток; свежий независимый первый проход — сырые входы.

## Параллельность

Разрешай несколько исполнителей только при независимых задачах, изолированных write sets/worktree, отсутствии общей незащищённой памяти и известном порядке интеграции. Не сериализуй ready-задачи без конкретной зависимости/риска. При неизвестной
общей границе сначала выясни её коротким мандатом. Блокер приостанавливает
зависимых; остальные идут дальше. Обновление общего контракта требует сверки
затронутых задач, не слепой интеграции. Общие plan.md и .wolf/ изменяет назначенный владелец; .wolf/ в linked worktree резолвится в общий main-чекоут, записи по умолчанию `scope: worktree:<name>`, перенос в общую память — `wolf promote`; передача незакоммиченного состояния между рабочими копиями — wolf-handoff snapshot. Не объявляй одинаковые файлы в разных ветках доказательством семантической независимости.

## Интеграция и завершение

Объедини проверенные результаты на согласованном baseline; конфликты анализируй по смыслу, не выбирай сторону автоматически. Выполни integration/NFR/full checks из test-plan на объединённом состоянии. Составь ACCEPTANCE по каждому AC с evidence и известными ограничениями. Передай L0; PARTIAL/REJECTED/INCONCLUSIVE не называй завершением.

После приёмки или согласованного промежуточного исхода используй finishing-a-development-branch в пределах полномочий. При остановке сохрани wolf-handoff, включая незакоммиченные изменения. Сессия не является единственным местом хранения состояния.

## Гейт перехода

Соответствие проверяется раньше качества; оба мандата должны быть видны в evidence. Зелёные тесты исполнителя не заменяют независимое ревью. ACCEPTANCE собирается на интегрированном состоянии; только затем L0 принимает поставку. При изменении контракта верни затронутые design/plan/test-plan на сверку.

## Не пропускай процесс

| Мысль | Действие |
| --- | --- |
| «Воркер написал DONE» | Это готовность к проверке, не приёмка. |
| «Одно общее ревью достаточно» | Явно проверь соответствие, затем качество; сохраняй оба результата. |
| «Разные ветки — значит независимы» | Проверь общие контракты, память и внешние ресурсы. |
