# Организация ревью — L0/L1

## Владение и вход

L0 задаёт цель/критерии и принимает поставку; L1 организует цикл и вызывает
worker-reviewer. L2 не получает полномочий диспетчера. Автор не является
независимым ревьюером своего результата. Полную методику загрузи один раз.
Процедура L2 — в полной рамке worker-reviewer и доставленном лице; не копируй
эту организационную методику в каждый worker-TASK. При явно назначенной иной
специализированной методике доставь её полный текст, не самодельное сокращение.

TASK: цель владельца одной строкой → вклад подзадачи → проверяемый результат,
baseline/revision/digest/cwd, норма и относящиеся политики, источники, границы,
полный мандат/AC, инструменты/контракты, RESULT/evidence, бюджет и стоп-условие.
Обязательные нормативные фрагменты передай без потери исключений и приоритета;
сохрани точные ссылки для дочитывания, не подменяй норму пересказом. Историю
родителя, чужие находки и ожидаемый вердикт в независимый первый проход не передавай.

L1 выбирает реальные доступные model/variant существующим harness; не выдумывай
поля или ID и не считай текст TASK доказательством настройки. Роли не шкала
reasoning. Механика — низкий режим, смысловое ревью — достаточный по риску;
повышение адресное, выбор владельца приоритетен. Раздели большой аудит на
короткие мандаты с конечным лимитом (без заданного — 8 обращений) и владельцем
межчастной согласованности/общего покрытия. Возврат при неожиданной сложности
не требует исчерпания лимита. На лимите — остаток, не APPROVED.

## Scope и средства

Для diff-review проверяй изменения и связанные нормы. Явное поручение общей
смысловой проверки не сужай до таблиц/ID. Укажи допустимые внешние ссылки.
Линзы выбираются по объекту: Requirements, Design, Plan, Test-plan, Code.
Security/trust обязателен по релевантным правам, секретам, внешним инструкциям,
исполнению, установке, хранению/миграциям. Новый риск позволяет запросить линзу.

Для регулярной процедуры/известного трения L1 сначала ищет подходящее средство
в tool-библиотеке, если актуальный результат ещё не доставлен. Передай L2 только
нужный путь/команду, contract-in/out/env, ограничения и ловушку, не весь каталог.
Библиотечный скрипт не даёт новых прав: reviewer не запускает проверяемую систему.
Запрос из LIMITS сначала решает L1: контекст, решение, средство или разбиение.
Один эксперт — по точному пробелу; консилиум — дорогой резерв для сложного
существенно блокирующего решения по рамке L1. Дефект правила — триаж/Стюард,
не экспертный совет. Следующий L2 получает решение и узкий остаток; совет не
утверждает scope. Явное общее ревью сохраняет все критерии в суммарном покрытии,
не превращается в набор механических проверок.

## Цикл и журнал

1. Зафиксируй применимые линзы и версии, запусти независимые мандаты.
2. Получи SUMMARY/VERDICT/FINDINGS/SCOPE/LIMITS/EVIDENCE по рамке. Сопоставь
   фактическое покрытие с AC, не только заголовок вердикта. Дедуплицируй,
   сохраняя источники и разные основания. Передай вопрос надлежащему владельцу.
3. Ответ автора по finding ID: принято/опровергнуто/отложено/нужно уточнение
   с evidence. Продуктовый конфликт — L0/владелец, технический в полномочиях — L1.
4. После исправлений перепроверь затронутые основания/линзы и регрессионный риск;
   неизменённые результаты переиспользуй только при доказанной применимости.
   Не начинай новый полный аудит без причины. По умолчанию максимум 3 раунда;
   исчерпание → UNRESOLVED в сводке L1 и эскалация, не одобрение.
5. L1 сохраняет единый append-only след ревью: artifact revision/digest, линза
   и версия методики, coverage, verdict, finding IDs, ответы, evidence и ограничения.
   Сохраняй значимые вердикты адресными рабочими note/history Wolf с ревизией,
   связью с thread и ссылками на предыдущие записи; частные ответы L2 — сообщениями.
   Это аудит, не lesson/complaint и не предлагаемое правило. Не сохраняй каждый
   инструментальный шаг; прежние записи/вердикты не переписывай.
   review.md допустим как единичный заранее обоснованный документ этапа, когда
   нужен долговечный аудит. Не создавай файл на каждого ревьювера или раунд;
   без отдельного документа обязательный след и его актуальность сохраняются.

## Гейт

Critical/Major и обоснованный блокирующий риск запрещают переход. Без доказанного
блокера существенное непроверенное свойство означает INCONCLUSIVE; полное покрытие
без блокеров — APPROVED. Справочный пробел не отменяет доказанный дефект.
Требования/существенные ADR утверждает владелец; другие артефакты — назначенный
ответственный после ревью. Совет и мнение эксперта не заменяют утверждение,
независимое ревью или проверку. Следующий этап получает нужную одобренную версию.
