# wolf-plan: план для zero-context исполнителя

## Обзор

Пиши исчерпывающие планы реализации в предположении, что исполнитель имеет **нулевой контекст** кодовой базы этой задачи и сомнительный вкус. Задокументируй всё, что ему нужно знать: какие файлы трогать в каждой задаче, код, тесты, какие доки проверить, как проверить работу. Отдай весь план как bite-sized задачи. DRY. YAGNI. TDD. Частые коммиты.

Считай, что исполнитель — умелый разработчик, но почти ничего не знает о нашем тулсете и проблемном домене. Считай, что он плохо умеет в хороший дизайн тестов.

**Вход воркеров — по брифам:** каждая задача плана становится брифом однозадачного воркера (worker-implementer). Воркер не читает кодовую базу и не видит твою сессию — план обязан содержать всё. Сомнительное качество плана = гарантированные вопросы и переделки на исполнении.

**Анонс на старте:** «Использую скилл wolf-plan для создания плана реализации».

**Контекст:** исполнение плана начинается только в worktree `.worktrees/<имя-задачи>` (правило проекта; создаётся ДО старта исполнения — см. wolf-sdd / wolf-execute). Сам план можно писать и до worktree.

**Куда сохранять:** `docs/plans/YYYY-MM-DD-<имя-фичи>.md` (предпочтения проекта приоритетнее дефолта).

## Проверка масштаба

Если спека покрывает несколько независимых подсистем, её нужно было разбить на подпроекты ещё на wolf-brainstorm. Если это не сделано — предложи разбить план на отдельные, по одному на подсистему. Каждый план должен давать работающее, тестируемое ПО сам по себе.

## Структура файлов

До определения задач спроектируй, какие файлы будут созданы или изменены и за что каждый отвечает. Здесь фиксируются решения декомпозиции.

- Проектируй блоки с ясными границами и определёнными интерфейсами. У каждого файла — одна ясная ответственность.
- Над кодом, который держится в контексте целиком, ты рассуждаешь лучше, а правки точечнее. Предпочитай маленькие сфокусированные файлы разросшимся.
- Файлы, меняющиеся вместе, живут вместе. Дели по ответственности, не по техническим слоям.
- В существующей кодовой базе следуй устоявшимся паттернам. Если она использует большие файлы — не перестраивай в одиночку; но если файл, который ты правишь, разросся — включить разбиение в план разумно.

Эта структура определяет декомпозицию задач. Каждая задача должна давать самодостаточные изменения, осмысленные независимо.

## Гранулярность bite-sized

**Каждый шаг — одно действие (2–5 минут):**
- «Напиши падающий тест» — шаг
- «Запусти и убедись, что он падает» — шаг
- «Напиши минимальный код, чтобы тест прошёл» — шаг
- «Запусти тесты и убедись, что проходят» — шаг
- «Закоммить» — шаг

## Заголовок плана

**Каждый план ОБЯЗАН начинаться с этого заголовка:**

```markdown
# [Имя фичи] — план реализации

> **Исполнителям:** REQUIRED-СКИЛЛ: используй wolf-sdd (рекомендуется) ИЛИ wolf-execute
> для поэтапной реализации этого плана. Шаги оформлены чекбоксами (`- [ ]`) для трекинга.

**Цель:** [Одно предложение — что строим]

**Архитектура:** [2–3 предложения о подходе]

**Стек:** [Ключевые технологии/библиотеки]

---
```

## Структура задачи

````markdown
### Задача N: [Имя компонента]

**Файлы:**
- Create: `точный/путь/к/file.ts`
- Modify: `точный/путь/к/existing.ts:123-145`
- Test: `tests/точный/путь/к/test.ts`

- [ ] **Шаг 1: Напиши падающий тест**

```typescript
it("конкретное поведение", () => {
  expect(fn(input)).toBe(expected);
});
```

- [ ] **Шаг 2: Запусти тест — убедись, что падает**

Запуск: `npx vitest run tests/path/test.ts -t "конкретное поведение"`
Ожидание: FAIL — «fn is not defined»

- [ ] **Шаг 3: Напиши минимальную реализацию**

```typescript
export function fn(input: string): string {
  return "expected";
}
```

- [ ] **Шаг 4: Запусти тест — убедись, что проходит**

Запуск: `npx vitest run tests/path/test.ts -t "конкретное поведение"`
Ожидание: PASS

- [ ] **Шаг 5: Закоммить**

```bash
git add tests/path/test.ts src/path/file.ts
git commit -m "feat: add specific feature"
```
````

## Никаких плейсхолдеров

Каждый шаг обязан содержать фактический контент, нужный исполнителю. Это **провалы плана** — никогда так не пиши:

- «TBD», «TODO», «сделаем позже», «заполнить детали»
- «Добавить соответствующую обработку ошибок» / «добавить валидацию» / «обработать краевые случаи»
- «Написать тесты для вышенаписанного» (без фактического кода теста)
- «Аналогично задаче N» (повтори код — исполнитель может читать задачи не по порядку)
- Шаги, описывающие ЧТО делать, без КАК (для шагов с кодом — блоки кода обязательны)
- Ссылки на типы, функции или методы, не определённые ни в одной задаче

## Помни

- Всегда точные пути файлов
- Полный код в каждом шаге — если шаг меняет код, покажи код
- Точные команды с ожидаемым выводом
- DRY, YAGNI, TDD, частые коммиты

## Саморевью

После написания полного плана посмотри на него свежим взглядом и сверь со спекой. Это чеклист для себя, не диспетчеризация субагентов.

**1. Покрытие спеки:** пробегись по каждой секции/требованию спеки. Можешь указать задачу, которая её реализует? Перечисли пробелы.

**2. Скан плейсхолдеров:** поищи в плане red flags — паттерны из секции «Никаких плейсхолдеров» выше. Исправь.

**3. Консистентность типов:** совпадают ли типы, сигнатуры методов и имена свойств в поздних задачах с определёнными в ранних? Функция `clearLayers()` в задаче 3 и `clearFullLayers()` в задаче 7 — это баг.

Нашёл проблемы — исправь на месте. Пересматривать заново не нужно. Требование спеки без задачи — добавь задачу.

## Передача в исполнение

После сохранения плана предложи выбор режима исполнения:

**«План готов и сохранён в `docs/plans/<файл>.md`. Два режима исполнения:**

**1. Через субагентов (wolf-sdd, рекомендуется)** — свежий воркер на каждую задачу через executor-lead, 2-стадийное ревью между задачами, быстрая итерация

**2. Линейно (wolf-execute)** — исполнение задач в этой сессии без субагентов, батчами с чекпоинтами

**Какой режим?»**

**Выбран wolf-sdd:** свежий воркер на задачу + двухстадийное ревью (спека → качество) силами worker-reviewer.

**Выбран wolf-execute:** батч-исполнение с чекпоинтами; верификация — `npm run check` после завершённых блоков работы.
