# wolf-debug: систематический дебаг

## Обзор

Случайные фиксы тратят время и порождают новые баги. Быстрые заплатки маскируют лежащие под ними проблемы.

**Ядро принципа:** ВСЕГДА находи корневую причину до попыток фикса. Фикс симптома — это провал.

**Нарушение буквы этого процесса — нарушение духа дебага.**

## Железный закон

```
НИКАКИХ ФИКСОВ БЕЗ ИССЛЕДОВАНИЯ КОРНЕВОЙ ПРИЧИНЫ
```

Если ты не завершил фазу 1, ты не можешь предлагать фиксы.

## Когда использовать

Используй для ЛЮБОЙ технической проблемы:
- Падения тестов
- Баги в проде
- Неожиданное поведение
- Проблемы производительности
- Сломанные сборки
- Интеграционные проблемы

**Используй ОСОБЕННО, когда:**
- Давит время (авралы делают угадывание соблазнительным)
- «Просто один быстрый фикс» кажется очевидным
- Ты уже попробовал несколько фиксов
- Предыдущий фикс не сработал
- Ты не до конца понимаешь проблему

**Не пропускай, когда:**
- Проблема кажется простой (у простых багов тоже есть корневые причины)
- Ты спешишь (спешка гарантирует переделку)
- Владелец требует «починить СЕЙЧАС» (систематичность быстрее метаний)

## Четыре фазы

Каждую фазу ОБЯЗАН завершить до перехода к следующей.

### Фаза 1: исследование корневой причины

**ДО попытки ЛЮБОГО фикса:**

1. **Внимательно читай сообщения об ошибках**
   - Не проскальзывай мимо ошибок и предупреждений
   - Они часто содержат точное решение
   - Читай стектрейсы полностью
   - Отмечай номера строк, пути файлов, коды ошибок

2. **Воспроизводи стабильно**
   - Можешь ли вызвать это надёжно?
   - Каковы точные шаги?
   - Происходит ли каждый раз?
   - Не воспроизводится → собирай больше данных, не угадывай

3. **Проверь недавние изменения**
   - Что изменилось из того, что могло это вызвать?
   - Git diff, недавние коммиты
   - Новые зависимости, изменения конфигурации
   - Различия окружения

4. **Собирай улики в мультикомпонентных системах**

   **КОГДА система имеет много компонентов (CI → сборка → подпись, API → сервис → БД):**

   **ДО предложения фиксов добавь диагностическую инструментацию:**
   ```
   Для КАЖДОЙ границы компонентов:
     - Логируй, какие данные входят в компонент
     - Логируй, какие данные выходят из компонента
     - Проверяй проброс окружения/конфигурации
     - Проверяй состояние на каждом слое

   Один прогон для сбора улик — ГДЕ ломается
   ЗАТЕМ анализ улик — какой компонент падает
   ЗАТЕМ исследование именно этого компонента
   ```

   **Это показывает:** какой слой падает (секреты → workflow ✓, workflow → сборка ✗)

5. **Трассируй поток данных**

   **КОГДА ошибка глубоко в стектрейсе:**
   - Где порождается плохое значение?
   - Кто вызвал это с плохим значением?
   - Трассируй вверх, пока не найдёшь источник
   - Чини в источнике, а не в симптоме

### Фаза 2: анализ паттернов

**Найди паттерн до фикса:**

1. **Найди работающие примеры**
   - Найди похожий работающий код в той же кодовой базе
   - Что работает так же, как то, что сломано?

2. **Сравни с эталонами**
   - Если реализуешь паттерн — прочитай референс ПОЛНОСТЬЮ
   - Не просматривай по диагонали — каждую строку
   - Пойми паттерн полностью до применения

3. **Определи различия**
   - Что отличается между работающим и сломанным?
   - Перечисли каждое различие, каким бы малым ни было
   - Не предполагай «это не может иметь значения»

4. **Пойми зависимости**
   - Какие ещё компоненты ему нужны?
   - Какие настройки, конфигурация, окружение?
   - Какие предположения он делает?

### Фаза 3: гипотеза и тестирование

**Научный метод:**

1. **Сформулируй единственную гипотезу**
   - Сформулируй ясно: «Я думаю, корневая причина — X, потому что Y»
   - Запиши
   - Будь конкретен, не расплывчат

2. **Тестируй минимально**
   - Сделай САМОЕ МАЛЕНЬКОЕ возможное изменение для проверки гипотезы
   - Одна переменная за раз
   - Не чини несколько вещей сразу

3. **Верифицируй до продолжения**
   - Сработало? Да → фаза 4
   - Не сработало — сформулируй НОВУЮ гипотезу
   - НЕ наслаивай ещё фиксы сверху

4. **Когда не знаешь**
   - Скажи «я не понимаю X»
   - Не притворяйся, что знаешь
   - Проси помощи
   - Исследуй дальше

### Фаза 4: реализация фикса

**Чини корневую причину, а не симптом:**

1. **Создай падающий тест**
   - Простейшее возможное воспроизведение
   - Автотест, если возможно
   - Одноразовый тест-скрипт, если нет фреймворка
   - ОБЯЗАН быть до фикса
   - **Используй скилл test-driven-development для написания правильного падающего теста — фикс пишется ТОЛЬКО под падающий тест**

2. **Реализуй единственный фикс**
   - Адресуй выявленную корневую причину
   - ОДНО изменение за раз
   - Никаких улучшений «раз уж я здесь»
   - Никакого сопутствующего рефакторинга

3. **Верифицируй фикс**
   - Тест теперь проходит?
   - Другие тесты не сломались? (`npm run check` — verification-примитив проекта)
   - Проблема реально решена?

4. **Если фикс не сработал**
   - СТОП
   - Посчитай: сколько фиксов ты уже попробовал?
   - Если < 3 — вернись к фазе 1, переанализируй с новой информацией
   - **Если ≥ 3 — СТОП и поставь под вопрос архитектуру (шаг 5 ниже)**
   - НЕ пытайся делать фикс №4 без архитектурного обсуждения

5. **Если 3+ фиксов провалились: поставь под вопрос архитектуру**

   **Паттерн, указывающий на архитектурную проблему:**
   - Каждый фикс вскрывает новое общее состояние/связность/проблему в другом месте
   - Фиксы требуют «массированного рефакторинга»
   - Каждый фикс создаёт новые симптомы в других местах

   **СТОП и спроси фундаментально:**
   - Паттерн в принципе здрав?
   - Не «держимся ли мы за него по чистой инерции»?
   - Может, рефакторить архитектуру вместо продолжения латания симптомов?

   **Обсуди с владельцем до новых попыток фикса.**

   Это НЕ провалившаяся гипотеза — это неверная архитектура.

## Red Flags — СТОП и вернись к процессу

Если ловишь себя на мысли:
- «Быстрый фикс сейчас, исследую потом»
- «Просто поменяю X и посмотрю, сработает ли»
- «Внесу несколько изменений, прогоню тесты»
- «Пропущу тест, проверю руками»
- «Наверное, это X, поправлю это»
- «Я не до конца понимаю, но это может сработать»
- «В паттерне сказано X, но я адаптирую по-своему»
- «Вот основные проблемы: [список фиксов без исследования]»
- Предлагаешь решения до трассировки потока данных
- **«Ещё одна попытка фикса» (когда уже попробовал 2+)**
- **Каждый фикс вскрывает новую проблему в другом месте**

**ВСЁ это значит: СТОП. Вернись к фазе 1.**

**Если 3+ фиксов провалились:** поставь под вопрос архитектуру (фаза 4, шаг 5).

## Сигналы владельца, что ты делаешь не так

**Следи за этими поправками:**
- «А это вообще происходит?» — Ты предположил, не проверив
- «Это нам покажет…?» — Надо было добавить сбор улик
- «Перестань угадывать» — Ты предлагаешь фиксы без понимания
- «Продумай фундаментально» — Ставь под вопрос основы, а не только симптомы
- «Мы застряли?» (фрустрация) — Твой подход не работает

**Увидел — СТОП. Вернись к фазе 1.**

## Типичные рационализации

| Оправдание | Реальность |
|--------|---------|
| «Проблема простая, процесс не нужен» | У простых проблем тоже есть корневые причины. Процесс быстр для простых багов. |
| «Авария, нет времени на процесс» | Систематический дебаг БЫСТРЕЕ, чем метания угадай-и-проверь. |
| «Сначала попробую это, потом исследую» | Первый фикс задаёт паттерн. Делай правильно с самого начала. |
| «Тест напишу после подтверждения, что фикс работает» | Непроверенные фиксы не приживаются. Сначала тест — потом он доказывает. |
| «Несколько фиксов сразу сэкономят время» | Не изолировать, что сработало. Порождает новые баги. |
| «Референс слишком длинный, адаптирую паттерн по мотивам» | Частичное понимание гарантирует баги. Читай полностью. |
| «Вижу проблему, давайте чинить» | Видеть симптомы ≠ понимать корневую причину. |
| «Ещё одна попытка фикса» (после 2+ провалов) | 3+ провала = архитектурная проблема. Ставь паттерн под вопрос, не чини снова. |

## Быстрая шпаргалка

| Фаза | Ключевые активности | Критерий успеха |
|-------|---------------|------------------|
| **1. Корневая причина** | Читай ошибки, воспроизводи, проверь изменения, собери улики | Понимать ЧТО и ПОЧЕМУ |
| **2. Паттерн** | Найди работающие примеры, сравни | Определить различия |
| **3. Гипотеза** | Сформулируй теорию, тестируй минимально | Подтверждена или новая |
| **4. Реализация** | Создай тест, чини, верифицируй | Баг решён, тесты зелёные |

## Когда процесс показывает «корневой причины нет»

Если систематическое исследование показало, что проблема действительно экологическая, зависит от таймингов или внешняя:

1. Ты завершил процесс
2. Задокументируй, что исследовал (`wolf add --type lesson` — следующий агент не должен повторять путь)
3. Реализуй подходящую обработку (retry, timeout, сообщение об ошибке)
4. Добавь мониторинг/логирование для будущих исследований

**Но:** 95% случаев «нет корневой причины» — это незавершённое исследование.

## Смежные скиллы

- **test-driven-development** — для создания падающего теста (фаза 4, шаг 1): фикс только под падающий тест
- **verification-before-completion** — проверь, что фикс сработал, до заявления об успехе

## Реальный эффект

Из дебаг-сессий:
- Систематический подход: 15–30 минут на фикс
- Подход случайных фиксов: 2–3 часа метаний
- Фикс с первого раза: 95% против 40%
- Новые баги: почти ноль против обычного дела
